# 从失败后补采到在线修复：Appendix G、RLEF 与自蒸馏的区别

日期：2026-09-16。状态：**专题核查与设计建议**，不是项目定案；未改训练实现，未复现实验，未独立审查。

## 1. 结论与阅读范围

在线修复值得作为项目一的候选实验。它利用失败产物和执行反馈改变后续尝试的条件，可能比重新完成一遍仓库探索更划算。但“增加失败上下文”“用什么 RL loss 更新”“把事后信息蒸馏回原始任务”是三个不同选择。**在线修复本身不超出 GRPO，也不自动成为 OPSD/SDPO。**

本轮精读 [2605.28751v1][P] 的 §2、§4.2 和 **Appendix G 全部内容，PDF p36–38**，目视核对 Eq.(8)、Tables 2–4、Figures 29–30。整篇 PDF 共 54 页，其主题是代码正确性–效率前沿与权重外推；本稿不冒充整篇后训练精读。TeX 下载返回 HTTP 406，改用官方 HTML 与原始 PDF。原件和附录页保存在[来源目录](sources/online_fixing_2605.28751v1/README.md)。

相关来源按问题定点核对：RLEF 的方法与反馈消融；SCoRe 的两阶段训练；SDPO、OPSD 的教师条件和 loss；KAT-Coder-V2.5 §2.2 的失败恢复。复用本库 [N07 SDPO](N07_sdpo.md)、[N01 KAT](N01_kat_coder_v2_5.md)、[Prime 栈 §6.4](prime_stack_20260908.md)。这些定点复核不改变各篇原有的审查状态。

## 2. 评论所指的 online-fixing 实际做了什么

原论文为 *Extrapolative Weight Averaging Reveals Correctness–Efficiency Frontiers in Code RL*。评论的 `retry-only` 在文中称 **resample-only**。两者都允许失败后增加采样，区别是第二次采样能否看到失败信息。[P, §4.2、G.1–G.4]

设原任务为 \(x\)，当前策略产生失败代码 \(y\)，执行反馈为 \(f\)。修复题为：

\[
z=\phi(x,y)=[\text{原题},\text{失败代码},\text{执行统计},\text{简短诊断提示}] .
\]

这里反馈是**聚合的执行统计**；作者明确不提供私有测试输入、expected outputs 或详细失败 traces。提示允许参考旧代码，也允许完全重写。因此它不局限于在旧答案上做小修补。

Eq.(8) 在普通 GRPO 目标上增加失败条件化的 GRPO 目标：

\[
\mathcal L(\theta)=\mathbb E_x[\mathcal L_{\rm GRPO}(x;\theta)]
+\mathbb E_{x,y\sim\pi_\theta(\cdot|x)}
[\mathbf1\{r(y)=0\}\mathcal L_{\rm GRPO}(z;\theta)] .
\]

**loss 仍然是 GRPO；改变的是送入训练的任务分布。** Resample-only 将第二项中的修复题换回不含失败代码/执行统计的原题。作者在失败轨迹与修复题的边界切断计算图，将修复 rollout 当作新样本，明确不是把它算作原轨迹的第二轮。[P, G.2、G.4]

“在线”在此表示失败材料由训练中的当前策略产生，修复题随策略的弱点变化；不表示评测时对每道题更新参数。也不要把这篇的 `online-fixing` 当成 NGU 的另一个名字：NGU 的历史失败主要进入采样/优势统计，这里的历史失败进入后续模型输入。

## 3. 结果支持到哪里

训练任务来自 CodeContestsPlus 1×，评测为 LiveCodeBench v5。主论文有纯推理、Python 工具交互和终端 agent 三种设置；**附录 G 的修复结果只列 32B/7B 纯推理及 32B 工具交互**，没有真实 SWE 仓库修复的验证，也没有终端 agent 设置的 online-fixing 对照表。[P, §2、G]

最相关的 **32B 多轮工具交互**结果如下，直接据 Table 4 抄录，单位 %：

| 训练方式 | 原题 LCB pass@1 | 原题 LCB pass@5 | 原题 hard pass@1 | 原题 hard pass@5 | hard fix@1 | LCB fix@1 |
| --- | --- | --- | --- | --- | --- | --- |
| Baseline | 64.5±0.7 | 75.6±0.6 | 34.6±1.3 | 52.0±1.3 | 15.5±0.5 | 20.3±1.3 |
| Resample-only | 64.3±0.7 | **77.6±1.4** | 34.7±0.9 | **54.8±2.5** | 13.4±2.4 | 19.8±3.3 |
| Online-fixing | **65.2±0.4** | 75.9±0.9 | **36.2±1.0** | 52.9±1.8 | **16.3±1.5** | **21.2±0.7** |

Online-fixing 相对 resample-only：完整 LCB 首次成功率 +0.9 个百分点，hard +1.5；但两者的 pass@5 分别下降 1.7、1.9 个百分点。表格不能证明修复在所有采样预算下胜出，更不能单凭这些差异断言统计显著。

论文最清晰的正面例子其实是 **32B 纯推理**：Table 2 中 resample-only → online-fixing，hard fix@1 为 14.2±0.5 → 17.9±1.3，完整 LCB 原题 pass@1 为 61.2±0.1 → 62.6±0.2。7B 纯推理的原题 pass@1 仅为 45.6±0.3 → 45.9±0.6。作者在 §4.2 自己将结论限定为探索性证据，跨设置迁移更小且不稳定。

四个重要口径：

1. **fix@k 是已知失败条件下的修复成功率**，不是从原始任务出发的总体成功率，也不是 pass@1 加上 fix@1。原题 pass@1 衡量学习能否迁移回没有失败提示的输入。工具交互设置的一次尝试可以包含多次工具调用，不应将它误称为第一个模型调用的成功率。
2. 表格说明这些数字来自**最后三次评估**，不能把 ± 自动写成三个独立训练种子的误差；附录 G 没有明确其统计定义。
3. 论文声称保持 trainer compute、梯度步数一致，并让 resample-only 匹配额外 retry 预算。但没有给出这组实验完整的生成 token、prefill、执行成本和端到端 GPU-hour 总账。相同步数/尝试数不能自动推出相同总 FLOPs 或墙钟时间。
4. 附录 G 不足以恢复完整实现配置，例如原题/修复题的实际 batch 混合比例、每个修复题的组大小、递归修复深度和固定 trainer 预算下的采样取舍。不能据 Eq.(8) 编造这些默认值。

## 4. 与 NGU、GRPO、OPSD/SDPO 的关系

| 方法/设计 | 失败材料主要用在哪里 | 学习信号与直接训练对象 |
| --- | --- | --- |
| NGU 自适应采样 | 决定原题是否继续采样；历史失败参与组统计 | 对仍以原题为条件的 rollout 做组相对更新；不因保存历史就让下一次生成看见旧失败 |
| Appendix G online-fixing | 失败代码与统计变成新的修复输入 | 原题 GRPO + 修复题 GRPO，直接训练有失败上下文的策略 |
| 端到端多轮修复 RL | 失败代码、工具结果作为同一 episode 的后续状态 | 学习整个“尝试→观察→修复”策略；可选 PPO，也可设计 GRPO 轨迹组 |
| SDPO | 反馈放入 self-teacher 输入 | 教师重新评价**学生已采出的同一段 token 前缀**；用逐 token 分布差异训练没有该事后反馈的学生 |
| OPSD | 参考答案/验证过的推理等特权信息放入 self-teacher 输入 | 同一模型、不同条件的教师和学生，在学生自采样轨迹上做逐 token 蒸馏 |

NGU 见[已有精读](ngu_2609.13443.md)；其余分别见 [P]、[R]、[D]、[O]。这些不是互斥的完整系统：可以先有失败采样策略，再决定生成修复 rollout，最后决定采用 RL 或蒸馏更新。

### 4.1 一个 SWE 例子

模型需要修某个库对空字符串的处理。首次尝试已经找对函数、改了大部分逻辑，但仍把 `""` 与缺失值混同，公开回归测试报告了相关断言失败。

- **重新采样**：从初始仓库与原题再尝试，可能再次付出搜索、阅读和定位成本。
- **在线修复**：提供失败 patch、允许使用的测试反馈和相应仓库状态，模型可以针对已定位的边界条件继续诊断，也可以推翻原方案。
- **SDPO**：先让学生从原题产生尝试，再让看到反馈的同模型教师重新评价这段尝试里的 token 分布；训练学生下次在事前条件下做出更好的决定。它的标准算法不要求先额外生成一份成功修复答案。

例如，原题采四次全部失败时，普通组中心化的 outcome advantage 为零。若给定**同一个修复输入**后采四次得到 `[0,1,1,0]`，修复任务就产生了组内区分信号。这解释了修复可能缓解稀疏奖励的原因，但只直接说明修复任务可学，不能保证原题首次成功率同步提高。这是说明性例子，不是论文实测。

SDPO 更进一步：即使本批仍全错，只要可信反馈让教师对某些 token 的分布评价不同于学生，也可能形成非零蒸馏梯度。但有梯度不等于方向正确；教师理解反馈的能力、反馈质量和稳定性都仍然重要。[D, §2、§7]

### 4.2 不能混淆的两个目标

**会修复**：模型见到错误产物和反馈后，完成本次任务的概率更高。

**会预防同类错误**：学习后，在新任务上、不依赖事后提示就更容易成功。

Online-fixing 直接优化前者，共享参数可能让收益迁移到后者；Appendix G 的原题 pass@1 正是在检验这一步。OPSD/SDPO 则显式尝试把信息更充分的教师判断转移给事前学生。因此用户提到的 `ospd` 若指 OPSD，这个联想有意义，但**反馈条件化修复与自蒸馏之间还差一个明确的教师–学生学习步骤**。[P, G.2；D, §2；O, §3]

## 5. 外部已有做法及其启示

### 5.1 RLEF：直接训练如何利用执行反馈

[RLEF][R]（2410.02089v2，ICML 2025）与当前讨论最接近的早期代码工作之一。公开测试结果进入多轮对话；公开测试全部通过或达到轮数限制后，私有测试给最终判定。其实现采用 PPO，并学习每轮的 value baseline，属于端到端多轮训练，不是 Appendix G 的独立修复题。[R, §2]

有意义的不是“大模型会反思”的一般说法，而是受控比较：§3.3/Table 2 固定三次模型生成预算，8B CodeContests test 上，未训练模型独立采样/多轮为 11.8/10.5，RLEF 后为 9.7/16.0。这里 ST 也是三次独立生成的结果，**不能把 9.7 当原题单次 pass@1**。真实反馈换成随机反馈会损害修复，说明训练学到了反馈利用；同时单轮表现可能下降。[R, §3.3]

启示：不能仅凭给基座加一段“请再想想”就预期更好。先测当前模型能否读懂反馈，再把“训练后更会利用反馈”与“只多给预算”分开。

### 5.2 SCoRe：有第二轮，不代表学会纠错

[SCoRe][S] 研究没有外部 oracle 纠错提示时的内生自我修正。其两阶段 RL 先约束首轮接近基座、训练第二轮，再联合优化并使用进展奖励；目的是避免离线失败分布失配，以及首轮变强、第二轮只重复/微改的行为坍缩。实验包含数学和代码，不能直接视作 SWE 测试反馈配方。[S, §4–6]

启示：修复成功率、改动行为、首轮表现要一起观察。不要把“新增修复轮”当作训练已经学会诊断的证据，也不要照搬其 reward shaping 后只报告最终收益。

### 5.3 KAT-Coder：先用提示救活失败，再重建原分布数据

[KAT-Coder-V2.5 §2.2][K] 对 near-miss 失败提供“读哪里/核什么”的过程提示，得到验证通过的 patch 后，固定 patch、从原始上下文重新生成不含提示的轨迹，再检查执行、提示泄漏与一致性。它不是简单删除对话里的 hint，也不是本文 Appendix G 的在线 GRPO 配方。

报告约 20% 是原零通过任务在**提示恢复阶段**的通过率，未给无提示重建后的保留率与该机制的独立训练增益。适合借鉴为成功轨迹生产候选，不能把这个数字当作本项目预期收益。[K, §2.2；本库 N01 §4.2]

### 5.4 仓库确有自蒸馏资料，但名称要对齐

[N07](N07_sdpo.md) 已完整整理 SDPO，包括标准训练与测试时自蒸馏的区别。本轮回原文核对 §2：教师通常是同模型加反馈，逐 token 对齐学生原始尝试，不等价于先生成修复再 SFT。其 coding 主结果使用同一批 131 道 LCB 题、按测试用例划分可用反馈；不能当作未见题 SWE 泛化的直接证据。[D, §2、§4]

OPSD（2601.18734v3）用参考解等特权信息作为教师上下文，本库此前有候选登记，本轮只核对其方法。[O, §3]

另一个容易混淆的入口是 [Prime 栈 §6.4](prime_stack_20260908.md)：该栈文档中的 `opsd` 指向 **SDFT / Self-Distillation Enables Continual Learning（2601.19897）**，不能仅凭名字认定它已经实现这两篇论文或完整环境反馈闭环。本轮未重新审计其最新代码。

## 6. 对真实多轮 SWE，哪些问题决定它是否划算

以下是读者对项目一的设计推论，不是已验证的本仓库效果。

### 6.1 先定义“新增修复”比已有工具循环多了什么

Claude Code 正常执行中的“编辑→运行测试→读错误→再编辑”本来就是反馈条件化的多轮决策。额外设计可能是：失败结束后多给预算；从已失败的 patch/state 启动新修复题；引入之前未提供的训练评分摘要；或者加入教师蒸馏。它们分别改变预算、初始状态、信息和学习目标，应当分开比较。

### 6.2 谁能知道失败，谁能读到反馈

| 信息或动作 | 可怎样使用 | 评测含义 |
| --- | --- | --- |
| 仓库已有测试、自写复现、编译器/运行时错误 | 正常 actor 工具观察；训练和部署均可用 | 最接近真实 agent 的修复能力 |
| 训练任务私有评分的成功/失败或摘要 | 可按明确训练协议用于失败课程、修复题或特权教师 | 需要标明哪些信息进入 actor、哪些只进教师；不是自动违规 |
| 最终 held-out 评测的隐藏测试反馈 | 标准评测中只供最终判分 | 若据此通知 agent 继续改，已经改变反馈/尝试协议，需另列实验 |

“不暴露测试源码”不足以证明无额外信息：**触发再试的失败信号本身就是信息。** 在固定失败池上研究条件修复是有效诊断，但筛出失败样本依赖 oracle，不能将其直接包装成部署时的端到端成功率。

### 6.3 何时可能优于补采

若大部分成本已经用于理解仓库，且失败集中在可诊断的局部边界/漏测/接口不匹配，复用代码与状态可能减少重复探索，并提高下一次尝试的条件成功率。

反例是总体方案错误、错误假设锚定、上下文已接近上限、失败日志缺乏信息或评分噪声。修复可能不断加补丁，重新开始反而更好。基础设施故障与题目/评分缺陷应先从模型可学习失败中分开；增加学习轮数不会自动修正错误反馈。

比较成本至少包含：生成 token、prefill（含实际缓存命中）、环境运行/恢复、评分调用、墙钟时间和 learner 更新。没有可靠状态复用时，修复依然可能重复支付容器启动和 repo 加载；轨迹条数不能替代成本。

### 6.4 训练语义必须匹配输入条件

如果采用独立修复题，采样分布是 \(\pi_{\rm old}(\cdot|z)\)，策略比值也必须以该条件定义；不能把它伪装成从 \(\pi_{\rm old}(\cdot|x)\) 采到的原题答案。修复题和原题不能在未定义新估计器的情况下当作同条件 GRPO 组混算优势。

旧失败代码、日志和快照是新修复题的输入，不应自动再次变成这一样本的 policy-gradient action。若选择同一 episode 的多轮训练，旧动作如何获得最终信用是另一种明确目标，不能同时宣称采用 Appendix G 的切断做法。

如果用修复成功结果生产原题 SFT 数据，必须让动作序列在原始仓库状态下成立：只删提示可能留下依赖失败 patch 的编辑、缺失的工具观察或无法复现的跳步。KAT 的重新生成流程对此给了先例，但其数据也不因此成为原策略的 on-policy RL rollout。

## 7. 建议如何验证，不先改大训练配方

### 7.1 先做配对的修复诊断

选一批训练/开发任务，固定模型、harness 和每任务初始预算。记录真实失败 patch、允许使用的观察及可恢复的状态；用同一失败样本作为比较起点，避免不同模型面对不同失败难度。

对照至少包含：

1. **原题重试**：干净环境再运行原任务。
2. **继续现有对话**：保留现场和已有工具反馈，增加相同的后续预算，用来判断只是原预算不足，还是新修复提示有效。
3. **显式修复题**：原题 + 失败 patch + 合规反馈，从相应失败状态继续；先限制一轮，允许放弃原方案重写。

若 3 有优势，再拆“旧代码但无新增诊断”与“旧代码+诊断”两个条件，以判断收益来自状态复用还是反馈信息。不能把所有条件都换成不同预算、不同摘要、不同 verifier 后再归因给 online-fixing。

用实际 token/GPU 时间、环境时间和端到端时间画成功率–成本曲线；先使用明确预算上限，不复制可能长期续采的高概率循环。这个失败池是条件能力诊断，端到端评测另从所有原题出发，并使用部署可获得的重试触发条件。

### 7.2 再选择训练目标

如果发现修复题可解且比重试节省成本，可以先试“原题 RL + 有限比例的修复题 RL”，保持当前优化器家族，检验是否学会利用反馈。若目标更偏原题直接解决能力，再比较成功轨迹重建/SFT 或 SDPO；不必同时上线新采样、额外奖励、教师和异步 replay。

最少分别报告：

- 未见任务上的原题成功率，以及固定整体预算下的端到端成功率。
- 公共固定失败池的条件 fix rate；另列当前策略自己的失败池，避免分母难度变化误导。
- 每解决一题的生成、环境、评分与总时间成本；训练阶段还包括教师前向和 learner 成本。
- 按可诊断错误/总体方案错/环境问题分层的收益，以及 patch 回归、重复无效修改和停止行为。
- 首轮能力和候选多样性是否下降；在相同资源口径下同时看低预算与多尝试表现。

这条方向的项目价值在于：证明真实 harness 下哪些失败可以通过什么反馈、以什么成本转化为可学习信号，并在未见任务上验证。仅增加“失败后再改一次”已有大量先例；其价值需要由反馈协议、正确训练消费、资源对照与学习结果共同支撑。
