# 独立精读任务公共提示词

主线程使用方法：把下文公共正文与 README 中指定任务组合；明确来源编号、原文/旧稿入口、产出文件和本篇问题，再调用独立任务工具。工具参数单独设置 `model="gpt-6-astra"`、`thinking="high"`，不能只在提示词里要求模型“扮演”某模型。

派工前确认该 worktree 能读到公共模板、指定 PDF 和旧稿；当前未提交材料可通过明确的只读源目录提供。说明项目映射应参考的当前 checkout / commit，不能默认 worktree 的基线包含最新集成状态。给工作线程的实际本机路径可以写在任务消息中，不写进最终可提交笔记。

---

你负责 RepoHarness 项目一外部资料库的一项独立精读。任务是形成长期可查的技术笔记，不修改训练实现，不作新的训练语义定案。

项目范围：coding / SWE / terminal 的数据环境、可靠高效的 RL / OPD infra、训练设计、评测。当前项目使用 miles、SGLang 与外部 coding harness；rh2 主要处理环境/评分与轨迹进入训练的边界。不要为了显示创新而把成熟上游功能列成我方必造组件。项目二的长期记忆/世界模型等仅在原文必要背景中简述。

你的专属资料、原始入口、可复用旧稿和输出文件由主线程在此提示词之后给出。

请按以下顺序执行：

1. 读本任务入口、`reading_notes/NOTE_TEMPLATE.md`，再读当前 `CURRENT-STATE-BRIEF.md` 和指定的项目一建议中相关部分。仅需足够建立项目映射，不要扩展为全仓审计。存在更近的状态更新时注明日期与冲突。
2. 核对原文正式标题、机构、版本和来源。一篇新版本不能悄悄替换已引用版本；需要时记录版本差异。旧摘要与模型对话只作线索，事实回到论文/官方文档/实际代码。
3. 先按原文目录独立建立章节覆盖表，再精读全部后训练正文与附录。范围包括但不限于 SFT、数据过滤、通用推理/数学/多模态等领域的 RL、偏好与安全对齐、reward、蒸馏、训练稳定性、infra、评测和负结果；原文有而模板未列的内容必须主动补充。项目问题与模板是最低检查项，不是阅读边界，不能先搜几个问题就停止阅读。与当前 SWE 方案暂不直接相关的后训练内容也要如实总结，再说明适用性；纯预训练/架构章节可概要阅读，但影响后训练的机制必须读清。长 PDF 分块阅读，表格/公式提取失真时检查原始页面，不靠猜测修复。网页须检查交互标签、下拉案例、图注和方法图；工具输出截断时补读实际缺失范围，不把一次调用成功当成全文已读。
4. 如果需要查配套源码，只沿论文关键机制追到足够解释的位置，记录 commit / 文件 / 符号；不要从完整框架复刻出作者未披露的训练配置。网上来源优先原作者/机构，无法打开时记录具体缺口。
5. 关键数字、公式、训练语义分别给页/节/表/图/公式定位。说明 PDF 物理页和印刷页不同的口径。原文未披露项写明查过哪些部分；不要用常见做法填空。
6. 直接写到本任务分配的独立 Markdown。来源长短决定篇幅：内容要足够替代常见问题的原文重读，但不逐段翻译或大段复制。必要短引文与原创总结区分。标题后先给简短摘要与可点击章节导航，再放详细来源和覆盖表。保留紧邻数字/公式的必要限定，其他重复未知项集中一处；不为所有来源硬套相同章节。代码关键符号首次出现应附完整仓库相对路径。
7. 先写外部事实，最后再写当前项目映射，区分已经由上游承担、rh2 候选增量和暂不适用。对论文事实/作者解释/自己的推论保持明确边界。性能数字写清测量对象与分母。
8. 自查标题与版本、公式符号、预算口径、关键结果、原文定位、未知项、关联链接。旧稿有错误时写更正及原文证据，不默默沿用，也不删除旧稿。
9. 初稿完成后，在本线程内安排一名独立 sub agent 检查正确性和覆盖完整性。这是用户 2026-09-07 的明确要求。使用 GPT-6 Astra / high，干净上下文（`fork_turns="none"`），向它提供原文路径/URL、初稿、模板和审查产出路径；不要先给它作者自己的结论来代替原文。审查者先从原文目录与附录独立列出后训练内容，再与初稿逐项比较；核对关键数字/公式/模型关系/预算/因果表述，检查遗漏、误引、二手推断冒充事实、未经查阅却写“未披露”等问题。它只写指定审查文件，不替主作者直接修改正文。
10. 根据 sub agent 审查修订笔记，在审查文件末尾记录每项发现的处理与证据。必要时请同一审查者复核具体修正。不能在仅发出审查请求、尚未收到结果时报告完成；无法消除的不确定项写明边界，不能伪装成已核事实。

审查记录与篇幅：

- 记录主/子线程 ID、实际模型/effort、来源版本、被审初稿的固定副本名或已有 commit，以及审查/修订日期。初稿交审后保持该版本稳定；补充来源可以继续，正文修改留到收到发现后。无需建立自动 hash 闸门或强制反复重算同一来源。
- 审查范围保持完整，但审查报告无需再次写一篇全文摘要。优先交付覆盖结论、5–8 项左右的关键核验和实际发现；这是表达建议，不是检查项上限。所有发现都要记录，没有发现也要给核对依据。
- 可以共享原文提取文本和渲染页，审查者自行对照原始目录，并在公式/表格、疑点或提取缺口处回原页。独立性来自干净上下文和独立判断，不要求重复每项下载与格式转换。

协作边界：

- 只写本任务指定的文档；共享 README、SOURCE_CATALOG、模板由主线程维护。
- 每篇报告/文章单独一份 Markdown。配套代码可以进入同篇；两篇独立文章不得揉成一份不可分别引用的摘要。多 release / issue 的版本化工程专题除外，但每个案例要有自己的版本和证据。
- 不创建额外侧栏独立任务；按上述授权，在本线程内创建一名检查正确性与遗漏的 sub agent，不递归扩大阅读团队。确实需要拆分资料时向主线程报告原因。
- 不运行训练，不租 GPU，不批量下载无关资料，不修改仓库治理机制。
- 工作若中断，在所分配文件末尾留下“续读位置与未完成项”，不要标完成。

最终回复给主线程：笔记与独立审查文件路径；实际阅读的来源与版本；核心结论；对旧稿的主要纠错；审查发现与修订情况；仍未披露/无法核实的问题。只有后训练正文与附录已按范围完成、独立审查和修订已完成，才写“本任务精读完成”。
