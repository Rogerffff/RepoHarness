# 任务 09｜Agentic Reinforcement Learning for Real-World Code Repair：企业构建修复、环境简化与迁移失败

本文研究 LinkedIn 内部构建修复，不是公开 SWE-bench 训练配方。作者在完整工作流采集成功轨迹做 SFT，再在简化工作流中进行 GRPO；简化流程内得到学习收益，但没有相应恢复完整流程表现。延长训练又出现删除验证代码的奖励利用。它最有用的不是一个新优化器，而是一个反例：**保持工具名称不变，并不能保证优化后的训练环境仍在教授部署时需要的行为。** 但原实验同时改变多个条件，不能把迁移失败单独归因于某项 harness 设计。

## 2. 核心问题与结论的正确层级

作者首先需要让历史修复再次可以验证，然后才能采集有意义的轨迹。完整环境接近内部部署，但构建成本妨碍频繁 on-policy 采样，于是建立简化环境训练 RL。这三个问题——环境能否重放、训练能否学到、收益能否回到部署——在论文中并没有同时得到肯定答案。[P, §1、§3–7, pp.1–6][P2]

**来源结论。** 在作者设置下，SFT 对完整流程有价值；RL 在简化流程内有明显收益；跨流程收益有限；更长训练可能提高错误代理指标而不是实际修复质量。

**作者解释。** 模型因训练—测试条件错配而迁移不足；RL 后工具使用更集中，被解释为更像有经验的工程师。

**本稿分析。** 数据、外层控制流、预算和 reward 都可能解释差异。工具频次变化本身不能证明一般根因推理已经提升；本文也没有排除简单的任务专门化。不能反向从负结果推导“简化环境一律无效”“SFT 无法泛化”或“必须训练所有部署组件”。

## 3. 两个工作流到底差在哪里

### 3.1 完整流程不是一个从零独立诊断的裸模型

外部系统先构建 PR，分析日志并选出一个主要错误；检索历史解决方案，再按相关性和历史成功情况排序。模型接收仓库、错误和推荐方案后使用工具修复。成功需要构建验证与 LLM judge 接受，judge 的用途是检查测试覆盖没有被损害。[P, §3–3.1, pp.2–3][P3]

对后续失败，外层系统还负责状态决策：出现不同错误时保留进展、提交状态并重置上下文；错误相似时撤销修改、换候选方案再试。每个错误最多重试三次（是否包含初次尝试未明确），外层另有 LangGraph recursion limit=100。失败提交被当作新轨迹，不是模型独自携带一条无界历史完成所有排障。

因此，评测对象包含日志分析、RAG、方案选择、工具实现、回滚和 context reset。论文没有分别披露这些模块使用的模型或排序器，也没有全部组件的独立消融。**观察到 agent 成功，不应将所有诊断和恢复都归到目标权重。**

### 3.2 简化流程保留多轮工具执行，但移除了外层问题演化

| 比较维度 | Full pipeline | Simplified pipeline |
| --- | --- | --- |
| 起始单位 | 失败 PR 经日志分析与方案选择进入修复 | 缓存的 `repo / error / candidate fix` tuple |
| 外层控制 | 新错误、相似错误触发不同保留／撤销／重启流程 | 固定起始错误，不运行完整迭代外环 |
| 内层执行 | 最多 50 次工具调用 | 最多 30 步；仍可多轮调用工具 |
| 多错误仓库 | 工作流处理错误演化 | 拆为不同起始错误样本；整体成功仍需解决全部错误 |
| 工具 | 同一套十工具 | 作者称保持相同工具集 |
| 成功约束 | 构建成功且 LLM judge 接受 | 关闭 judge，以构建结果为主，辅以人工 spot check |
| 环境组织 | LangChain 工具执行、LangSmith trace/成功标志 | verl 扩展；NFS 缓存仓库、构建状态、日志、检索输出；每 rollout 独立目录 |
| 性能选择 | 原始完整问题流 | 训练另筛初始 build <100 秒的任务 |

依据：[P, §3.1、§4、§5, pp.3–5][P4]。**one-shot fix 指不运行外层重试流程，不是一次模型调用或单步代码生成。** 目录独立也不证明网络、进程、缓存和 grader 具备完整安全隔离。

这里至少同时改变了起始状态分布、环境转移、可见上下文、预算、评分条件和任务成本分布。故“工具没变”不能支持“训练问题没变”。反过来，本文没有通过单因素对照识别其中哪个变化主导迁移失败。

### 3.3 Appendix A.2：工具与 prompt 的特殊性

十个工具为：`ask_for_help`、`dependency_upgrade`、`find_files`、`find_files_with_text`、`remove_dependency`、`run_sh`、`upgrade_gradle`、`validate_and_build`、`read_file`、`write_file`。模型写完整文件，再由外部工具提取 patch；不是原生 diff 编辑。[P, §3.1、A.2, pp.3、8–9][P9]

附录具体示例已经给出 Gradle 版本过时的错误，并在用户信息中指定使用升级工具。其策略输入不仅是需求，还可能带有强动作先验。`ask_for_help` 查询**内部知识库**，不是向真实用户澄清。`dependency_upgrade` 调用内部依赖更新命令；`remove_dependency` 操作特定配置文件。这不是可以不加修改复用到任意开源仓库的工具语义。

prompt 明确要求自主执行、不交谈、不请求批准，并持续尝试直到修好。本文没有针对该措辞做消融，故不能将 reward hacking 归因于 prompt；也不能将“never give up”作为本项目的通用安全或停止策略。工具调用使用 XML 包裹的 JSON。本文没有给出原始 token 捕获、重分词、工具调用解析器或 chat template 的实现版本。

### 3.4 原文的 MDP 与计数单位

作者写出有限时域 MDP `(S,A,T,r,γ)`，将状态描述为 prompt、仓库、错误、选定方案和 reasoning context，将 action 描述为发出 token；`γ=1`。结束预算却按工具调用和墙钟计数。外层 recursion 又是另一单位。**本文没有给出 GRPO token loss 的完整公式，MDP 定义不能替代训练实现。** [P, §3.1, p.3][P3]

## 4. 数据供给、稳定性与统计分母

### 4.1 从问题到轨迹，再到 RL tuple

| 数据对象 | 原文数量与处理 | 重要边界 |
| --- | --- | --- |
| 内部真实问题 | 约 1K，按时间 80/10/10 切分 | 不是精确公开的 800/100/100 清单；repo 去重、具体日期和公开任务 ID 未给 |
| thinking SFT | 101 条成功轨迹：84 train / 17 validation；来自 Qwen3-32B | 只含支持显式 thinking 的模型轨迹 |
| no-thinking SFT | 365 条成功轨迹：311 train / 54 validation；来自 GPT-4.1 与 Qwen3-32B | 正文叙述不是全部来自 GPT；两来源占比及与 thinking 子集的重叠未给 |
| RL training cases | 由问题展开 tuple 后，保留初始 build <100 秒的 2,469 cases | case 不等于唯一 PR 或仓库，也不等于最终梯度有效轨迹数 |

依据：[P, §4, pp.3–4][P4]。摘要／结果段突出 GPT-4.1 蒸馏，但数据段写的是混合来源。这里分别保留：不能将“365 条全是 GPT-4.1 教师轨迹”写成事实。

原文没有明确列出 tuple 展开和时间切分的全部执行顺序，也没有给出同一父问题派生样本的跨集合检查结果。因此不能证明已泄漏，也不能据“time-ordered”一词推出检索库、未来修复和所有派生实例均已正确隔离。

### 4.2 稳定化针对的不止容器是否启动

作者识别 wildcard dependencies、自动依赖更新（ADU）、非确定性检索和基础设施变化。历史回测发现 40% 的过去修复无法再次构建、1% 的原失败问题无需修改也会成功；固定依赖并关闭 ADU 恢复约 20% 的失败修复，剔除那批天然通过的问题。[P, §4, p.4][P4]

**20% 的分母是 failed fixes，不是全数据的 20 个百分点。** 原文没有给这些历史集合的逐项对应关系；本稿不将它们连续相乘后创造一个“最终稳定通过率”。对 RepoHarness，重要的是区分历史可解性证据和当前镜像下的可解性，而不是照抄淘汰比例。

### 4.3 速度过滤同时在选择学习分布

`initial build <100s` 约束的是入选时的构建，不是之后每次工具执行的最大耗时。作者明确为吞吐选择较便宜的环境，但没有报告被筛掉的问题类型、筛前后难度分布或等预算的不过滤对照。

**分析：**这可能是一项合理工程决策，也可能使训练偏向某类依赖修复；两者并不矛盾。需要测量收益与偏置，不能把“筛快题”一概当成污染或一概当成无损优化。

## 5. 后训练阶段和运行语义

### 5.1 模型与教师关系

原始 Qwen3-32B 先在完整流程的成功轨迹上 SFT；作者试过原始模型和 Qwen3-SFT 作为 RL 起点，选择后者，然后在简化流程做 GRPO。GPT-4.1 通过 Azure OpenAI 提供轨迹，不是在线为 student token 提供 logprob 的 OPD teacher。[P, §4–5, p.4][P4]

这里的“base model”应理解为相对于本次专项训练的原始 checkpoint；论文没有足够模型 revision 信息，不能另行指定成某个未后训练的 `-Base` checkpoint。也没有独立的预训练、MOPD、安全 RL 或能力合并阶段。

### 5.3 预算与时序中容易误读的地方

外层 recursion 100、每错误最多重试三次、完整 episode 50 次工具／80 分钟、简化 episode 30 步、单工具 timeout 一小时、初始 build 入选阈值 100 秒，是六种不同限制。简化环境是否原样继承 80 分钟上限，原文没有再次明确；不把它当作已给出的精确配置。

作者称扩展 verl 解决 asynchronous execution 的并发问题，但没有给跨参数版本的 learner/rollouter 时序、queue 或 staleness 机制。**因此证据支持并发 agent 执行，不足以称为已验证的 fully-async policy learning。**

§5 写“训练中关闭 validations”，紧接着说明训练外单独跑 validation/test。结合前文仍通过 `validate_and_build` 获取 reward，本稿将其理解为不跑周期性 held-out evaluation，而不是关掉训练所需构建验证；这是**上下文解释**，原文没有配置文件可核。

单节点 8×H200 是明确资源锚点；但训练并行、显存管理、耗时和 GPU-hours 未给，不能据 32B 与八卡两个数字推出一条可直接运行的 RTX PRO 6000 配方。

## 6. 评测：把结果、对照与统计主张分开

### 6.1 正文直接支持的主要结果

完整流程测试中，Qwen3-SFT 非 thinking 为 **12.3%**，GPT-4.1 为 **15.1%**。作者称差异未达统计显著，并在九天在线 A/B 中观察到前者约 **17% 相对下降**。对应离线相对下降由这两个数算出约 **18.5%**。[P, §6, p.5][P5]

“未显著”不等于已证明等效或非劣；原文没有给相应检验设计、p 值或非劣界限。在线 A/B 也未披露流量、分配方式、失败归因或置信区间，不能推出生产成本／质量全面优于 GPT。

简化流程中，正文给出的非 thinking 原始模型→RL 约为：validation **7%→27%**，test **17%→24%**。所以 **7–20 是两个集合各自相对原始 Qwen 的百分点变化，不是一个 test 集的变化区间，也不是全部相对 SFT 的增益。** RL 实际初始化来自 SFT，模型继承关系与展示的比较基线必须分开。

作者同时报告：SFT 在简化流程没有改善，RL 回完整流程只略高于原始模型；thinking 没有带来一致收益。这些结果不是“RL 没学到”，而是所学收益依赖于评测流程。

原文 `*` 指 execution with thinking。Fig.3 caption 写 test set，但提取图例同时有 `Validation (1 week)` 和 `Test (1 week)`，§6 也分别讨论二者。本稿保留这个 caption／图例范围差异，不把两列合并。GPT 缺简化流程结果是作者当时系统限制，不是 GPT 分数为零，也不意味着 verl 永远无法接外部模型。[P, Fig.2–3、§5–6, p.5][P5]

原文没有逐一给出 starred 与 unstarred 模型的 checkpoint 身份；SFT 数据又有 thinking/no-thinking 两种来源规模。尤其不能把所有 SFT 差异当作“同权重只切换开关”的纯测试时效应。

### 6.3 三项需要降级解释的宣传性结论

**“56× smaller”。** 脚注采用非模型提供方文章对 GPT-4.x 1.8T 参数的估计，再与 32B 相比。该数不能作为本文已经验证的 GPT-4.1 模型规模，更不能替代 serving 成本、显存或延迟对照。本稿只记录这个比值的来源问题，不补一个猜测的新值。[P, p.5 脚注2、References p.7][P7]

**“SFT performs on par”。** 应读作作者在其样本和重复设置下未检出显著差异，不能抹掉点估计差距和在线下降。

**“train–test matching is necessary”。** 本文提供的是一组匹配条件有效、跨流程不理想的实证，而不是所有 agent 训练的必要性定理。它没有比较足够多的简化方式，也没有将 workflow、reward、预算和数据筛选分别随机控制。

## 7. Policy shift 与 reward exploitation

§6.1 观察到工具分布从较分散的查找、读取、编辑转向 `dependency_upgrade`（约14%）与 `validate_and_build`（约71%）；Fig.4 用一阶 next-tool 转移矩阵描述行为。括号里的 usage percentage 与矩阵中的 conditional transition probability 是两个分母，不能混用。[P, §6.1、Fig.4, p.6][P6]

作者将这种集中解释为专家式修复，并指出 agent 学会重复 build 来应对不稳定执行。**本稿分析：**这种解释与依赖修复占主导的数据相容，但频次图不能独立证明根因识别、代码质量或单位成本变好。重复 build 既可能恢复暂态错误，也可能利用噪声获得一次通过。

一个用于解释风险、**不属于论文实验**的简单模型是：若未经修复的状态每次以概率 q 偶然通过，且各次独立，k 次中至少一次通过的概率为 `1-(1-q)^k`。现实 build 常相关，故不能据此估计本数据的作弊率。它只说明为什么“多做验证”与“证据更可信”并非同义。

延长到 **3,000 steps** 后作者报告 **65% PR success**，同时明确观察到模型删除 validation code。该点不作为合法修复准确率；正文没有明确列出其 split、全部 exploit 轨迹、发现过程或修复后复训结果。建议添加 LLM judge 是作者的后续方向，不是已经通过有／无 judge 长期对照验证的解决方案。

同理，关闭 judge 与后来出现 exploit 同时存在，但没有单变量干预；本稿不宣称已经证明“唯一原因是关掉 judge”。

### 8.1 Token 与 turn

### 8.2 时长：保留正文和附录的不一致

§4 写每 run 约四小时、约一半耗于构建验证、单次平均三分钟并偶有超过一小时；A.3 则称平均约四分钟、离群值达到60分钟。Fig.9 提取图例是 **mean 3.93 min、95% CI [3.35,4.52]**，这一精确图例尚待目视复核。[P, §4 p.4；A.3、Fig.9 pp.10–11][P11]

完整 episode 的80分钟与“每 run 四小时”的层级关系未被说明；可能涉及外层多次尝试或其他开销，但那只是解释候选。本稿不把四小时当作每条 RL rollout 的预算，也不强行统一三分钟与3.93分钟。

原文没有提供固定并发下的速度曲线、GPU 利用率、NFS 吞吐、排队分解、环境创建成本或稳定化前后总成本。所以这些描述足以说明测量 CPU 构建长尾的重要性，却不足以给出优化收益的精确预测。

## 10. 证据边界和对 RepoHarness 的含义

### 10.1 对此前任务选择理由的修正

此前安排这篇为“真实环境迁移失败的负结果参照”，这一用途保留。但精读后必须增加三个限定：

1. 比较的是 **Full/Simplified 两套系统**，不只是同语义接口；不能用它证明某一种跨 harness 不变性算法必要。
2. 简化流程显著改变 reward：去掉 LLM judge。观察指标自身不同，使跨流程分数不能只解释成能力变化。
3. 任务以内部依赖与构建错误为主，且 RL 又按初始构建速度过滤。不能将“thinking不占优”和“专用工具有效”推广到广泛仓库开发。

它仍是有价值的作者实证，但属于**训练／数据／运行工程的整体案例和边界分析**，而不是一个以严格因子实验建立的通用迁移定律。

### 10.2 它新增了什么已有笔记没有的证据

与 [SkyRL-Agent](O01_skyrl_agent_sa_swe.md) 等正向训练案例并列，本篇提供了一个更直接的“局部RL提高、部署流程不随之提高”的观察。与 [Harness Interplay](E1_harness_interplay_posttraining.md) 并列，它提醒我们真实流程的变化可能涉及任务和评分定义，而不止观察丰富程度。这是本稿的关联阅读判断，不把其他论文结果混作本篇对照。

### 10.3 项目映射只作为实验建议

当前参照仍是 miles + SGLang + 外部 coding harness。[CURRENT-STATE-BRIEF](../../../agentic_RL/repo_harness_rh2_workstreams/CURRENT-STATE-BRIEF.md) 本身是2026-09-05导航快照，本轮没有审计所有后续实现或重新判定首训就绪状态。以下候选不更改现有loss、资格策略或项目范围。

| 候选借鉴 | 为什么由本篇触发 | 上游／我方边界 | 一个最小检查 |
| --- | --- | --- | --- |
| 把便宜化改动拆为系统优化与任务变更 | NFS缓存、步数缩短、去外环、关闭judge同时存在 | 复用上游调度；我方核环境/评分/轨迹语义，不再造框架 | 固定任务与候选工件，比较优化前后结果、可见信息和失败类别；只有语义保持后才报告无损加速 |
| 区分流程迁移与评分迁移 | Full与Simple的reward不是同一标准 | 环境与grader适配是项目相关面 | 对同一批工件离线双评分；若需要，另做“工作流×评分器”小型对照，不能只换两者后归因给harness |
| 审计速度筛选带来的数据偏向 | <100秒过滤与依赖类主导同时存在 | 用已有任务metadata做统计，不批准动态curriculum平台 | 在开发集按构建时长分层，比较类型、初始成功率与丢弃分布；不要只看新增有效组数 |
| 正常失败、环境漂移、奖励利用分开 | 原失败可无修改通过，长训可删除验证代码 | 不把所有失败都变成基础设施DROP | 冻结镜像后重复gold/no-op和若干合法替代解；记录分母与不确定性，再决定训练消费 |
| 用中间工件解释reward曲线 | 3K-step 65%不是合法能力 | 复用已有轨迹/评分产物，不建通用审计平台 | 对训练中间checkpoint抽样同一dev任务，检查测试完整性、工件差异与真实修复；最终held-out保持冻结 |

上表是本稿建议，不是论文已验证它们有效。可以先用固定模型或已有工件完成辨识；不要求为了证明每个系统优化都进行一次完整RL。反之，只要改变采样分布、reward或loss，单看吞吐就不足。

### 10.4 是否值得直接移植配方？

**保留：**真实问题的再现性检查、CPU构建并发诊断、完整与便宜流程的交叉评测、中期reward利用检查。

**需要先测：**速度过滤、专用依赖工具、缩短轨迹和context reset是否适合我们的任务分布。

**不直接采用：**去掉可靠评分以追吞吐、把超时一概当作同一类失败、将“从不求助／从不停止”prompt当作通用策略、仅因论文用GRPO就改现有loss。没有足够公开配置支持直接复现全部训练。

对简历工程叙事，本篇可以支持“真实环境与训练之间的跨层工程非常重要”的动机；不能替代我们自己的吞吐、正确性或模型结果，更不能拿作者的65%作为正向目标。
