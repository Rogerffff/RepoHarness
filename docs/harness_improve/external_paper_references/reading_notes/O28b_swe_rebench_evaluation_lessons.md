## 3. 逐项分析：哪些说法需要收紧才能用于项目决策

以下是读者的分析与可验证问题；不是对原演讲暗中改写，也不表示对应实验已运行。

### 3.1 实际任务的价值与一个 benchmark 的证明责任

开场用职业经历和生产事故说明为何要认真评测，这是一种动机，不是医学与软件错误成本的统计比较。把自然软件任务作为训练载体是可行选择，但“真实 GitHub issue”本身并不保证题意完整、测试公正或工件有实际采用价值。

因此，读这份演讲应当关注它帮助识别了什么误差来源，而不是要求其承担没有提供的“模型总体能力”证明。

### 3.2 时间切分：保留讲者的强表述，不把它升级成我们的保证

02:25 的确包含“唯一办法”的强判断。本笔记不把它改写成讲者只说“方法之一”，但也不把它采纳为本项目定理。

至少有四条不同风险：模型参数可能记住旧答案；训练／开发流程可能重复使用评测材料；运行环境可能保留未来 Git 对象；网络工具可能访问已经公开的修复。时间切分主要针对第一条的机会窗口，不能独自阻断其他通道。

官方 W 的 **Continuous dataset updates and decontamination** 实际说按 issue/PR 创建时间与模型发布日期标记潜在污染；它同时承认自动收集不能保证每题充分描述、完全可解。[W，方法第 2 项][W]。这是其网页协议，不是对模型真实预训练截止时间的确认。

对 B 的可行做法是固定题目／补丁公开时间和模型版本，保留污染判断依据。月月换题有利于新鲜度，却也改变了任务分布；若想比较两个 checkpoint 的改善，应在相同冻结批次里做配对，而不是把不同月份的总分直接相减。这里是我们据测量逻辑提出的限制，原演讲没有给出跨月统计校准方案。

### 3.3 题意、测试和环境应分别诊断

关于严格错误字符串的例子，正确结论不是“不得验证字符串”，而是检查该字符串是不是题面要求或公共接口合同的一部分。若不是，oracle 可能过窄；若本来就是兼容性要求，放宽测试反而会改变任务。F2P/P2P 的存在也不能替代这个判断。

时间与外部资源问题同样需要依据真实失败日志。不能把所有 import error、收集失败或 timeout 统一称为坏环境：有些是候选代码造成的真实回归。应比较相同环境中的基线／gold／候选状态，找出错误出现在哪一步。

B 最需要的是逐测试身份、前后状态、执行阶段与原始日志，而不是先写一条“异常一律丢弃”的规则。原演讲没有给这种统一训练过滤策略。

### 3.4 三个特别容易失去分母的数字

**8 倍**的基线是“与 issue 相连的 PR 候选”，不是通过执行和质量验证的训练题。扩大候选来源可能引入额外题面生成工作；不能直接声称相同预算下多八倍可训练环境。

**多抽 10%**是候选预留经验，不是总体坏题率的估计，更不是任意数据源都适用的安全余量。模型执行揭露的问题可能依赖模型与工具，按一次运行暴露的问题排除后也可能改变难度分布。

**逐题一整天**在 07:58 的转录中确实以估计口吻出现，并且指向每道最终任务。不能擅改成“一天审核整批”，也不能将其改写为本文精确测得的平均人时。本轮没有音频确认口误，没有样本数、审查范围、审核者差异与时间分布。它只能作为“人工环节可能很重”的提示，不能作为所有训练题必须支付的单位成本。

这三种数量分别属于候选供给、操作缓冲和人时估计，不能拼成一个成本公式。

### 3.5 极简 harness 是实验控制选择，不是能力上限结论

对同一任务比较模型时，统一、可检查的工具面可以减少混杂；研究真实用户能获得的系统时，原生 harness 同样可以是合理对象。两种问题都成立，不应互相否定。

YOLO 设置也只是这场评测的任务约定：它不衡量向用户澄清是否合时宜，更不证明优秀 coding agent 不应提问。若本项目以后加入人机协作，必须单独定义信息和预算，不能沿用自主完成率解释协作效果。

W 的 **SWE-rebench Solution，第 1 项**说明使用统一 prompts，并遵循模型默认／开发者推荐推理参数；其上下文上限写作 128K 或模型较小窗口，支持 text/tool 两种接口。[W][W]。因此，“统一 harness”并不自动意味着各模型 temperature、reasoning effort 或处理协议完全相同；也不能反写成演讲中每次实验的精确配置。

本轮未看到工具频次原图，故不报告具体工具排名和比例。转录里对示例 agent 名称的识别不清，亦不替其确定实现版本。

### 3.6 重试必须先定义估计目标

09:09 的“1–2 次”单位是每月无效的 **model runs**，不能当作每月只有一两个失败 task 或 rollout。原文没有逐类重试次数、优先级和计分合同。

对 B 来说，最危险的不是重试本身，而是只在某个模型失败时临时追加机会，却把最终结果仍叫一次成功率。可将需要回答的问题明确分开：

| 要估计的结果 | 什么需要固定 |
| --- | --- |
| 有效环境条件下的模型表现 | 无效环境判据、重跑次数、相同任务条件与模型预算 |
| 部署系统的端到端可靠性 | 服务失败也属于实际结果；恢复规则和总成本需要报告 |
| 尝试上限内的求解潜力 | 最大尝试数及“至少一次”判定；不能冒充最终自动选解能力 |

这些是建议的统计对象，不是讲者公布的三条正式 track。未完成的尝试应保留为缺失／错误事实，不在没有合同的情况下强行归为 0 或 1。

### 3.7 缓存降低的是什么成本

09:48 的语境是模型调用费用。它与 O28a 的镜像缓存、内部 PyPI 镜像或 tmpfs 不是同一种机制，也不能等同于 RL 权重版本间的 KV 重用。约四分之一费用不代表模型少生成四倍 token，更不代表四倍墙钟加速。

建议比较时分别记录输入、缓存读取／写入、输出、子代理与重试费用，并保存实际请求参数。只记录模型别名，无法区分 checkpoint 变化与 provider 默认 reasoning／caching 行为变化。

10:47 建议先重跑公共 benchmark，适合作为接入排障。它不意味着必须把结果调到与厂商完全相同才允许开实验：不同任务版本、预算、工具和统计误差本来就会改变分数。应先对齐条件并解释差异，避免反向过拟合公开分数。

### 3.8 未来 Git 历史与网络通道是两种不同泄漏

checkout 到 base commit 仅改变当前工作树，不构成“全部未来内容不可访问”的证据。限制一个命名工具也不等于禁止同一信息通过另一个通道进入。讲者给出的案例足以提示这两条边界，却没有提供跨模型普遍作弊率或某个补丁彻底关闭泄漏的证明。

B 可以用自建、明确授权的小仓库 fixture 检查过去可访问、未来不可访问，以及预定网络边界是否一致；无需访问真实未授权资源，也不需要先训练攻击模型。

需要同时保留任务的正常可用性：历史文档、已存在的测试、合法依赖与公开参考资料，可能本来就是完成任务所需信息。去污染不应简单变成“把所有历史与测试删除”。网络和工件可见性改变后，训练与评测分布也发生了变化，应记录为实验条件。

本轮没有原始命令截图或视频，不能核定转录的 `WebPage` 是否就是某具体产品工具的准确名称。关于模型越强越可能作弊，保留为讲者判断，不转为已观察到的单调趋势。

### 3.9 评测到训练是一条建议路线，不是训练证据

13:46–14:14 提到先用验证集比较模型、harness 和配置，然后考虑提示／工具、拒绝采样、微调／蒸馏，再到 GRPO。可把它理解成尽量低成本定位问题的工程顺序；原演讲没有在这里给出 SFT→RL 的模型、teacher、训练预算与控制变量实验。

因此，它不能证明本项目一定需要先 SFT，也不能证明更简单的干预必然关闭学习缺口。验证集如果被用于选择工具或生成数据，就不是最终独立 held-out；可以复用生产代码，但不应复用最终测试身份来做选择。

### 3.10 通过测试与提交质量是不同的验收维度

结尾的残留复现文件例子，应读成工件质量问题，而不是“agent 新增任何测试都应扣分”。真正需要区分临时诊断脚本、必要的新增回归测试和与任务无关的产物。具体模型名在转录中有识别噪声，本稿不按名字归因。

本篇没有代码质量 rubric、人工评审实验或已训练的质量 reward。B 可先保留 patch 和工作区变化，用于分析，而不把一个演讲案例立刻变成新的过程惩罚。

## 4. 五次重复：三种指标不能合成一个分数

**以下定义与算例由读者构造，用于澄清转录 12:53–13:15，并非作者额外披露的公式或结果。** 对 N 道任务各有五次、在预定协议下完整可判定的运行，记成功指示为 Xᵢⱼ。

```text
mean success = 全部成功次数 / (5N)
pass@5       = 至少一次成功的任务数 / N
all-5        = 五次全成功的任务数 / N
```

在这里可以把 mean success 理解为重复的单次运行经验均值，但它不是只跑一次的原始结果。若存在缺失、无效运行或不对称重试，必须先说明补跑及分母，不能直接套用。

一个独立的两题示例：

| 系统 | 题 1 五次 | 题 2 五次 | mean | 至少一次 | 全五次 |
| --- | --- | --- | ---: | ---: | ---: |
| A | 11111 | 00000 | 0.5 | 0.5 | 0.5 |
| B | 11100 | 11000 | 0.5 | 1.0 | 0.0 |

平均值相同，能力覆盖与重复可靠性完全不同。这里的 all-5 不是一条轨迹里连续完成五个步骤，pass@5 也没有解决在五个补丁中如何自动选对的问题。

**不确定性口径。** 转录提“confidence intervals”，但没有给置信水平或计算方式；W 实际写五次完整 benchmark、SEM 和 pass@5。[W，Accounting for stochasticity][W]。SEM 不是默认等于 95% 区间，不能替演讲补成某个确定公式。固定题集上五次运行的波动，与换一批题的泛化不确定性也是不同对象。

为本项目报告配对训练前后差异时，可以保存逐题五次结果，再选择与目标估计相符的方法；不能把同一题的五次运行当五道全新独立题。若按 repository 聚集且共享环境故障，还应解释这种相关性。这里只提出评测分析边界，没有声称原团队采用了任务 bootstrap 或层级模型。

## 7. 对 RepoHarness B 线的直接用途

映射日期 **2026-09-08**。这里是设计层建议，没有重新检查整个本地评分或训练实现，也不批准新增运行合同。

| 候选工作 | 本篇触发点 | B 可交付的最小结果 | 不必立即建设的东西 |
| --- | --- | --- | --- |
| 任务质量分层 | §3.3–3.4 | 环境、题意、oracle、目标模型失败分开归因 | 大型自动修题系统 |
| 固定比较条件 | §3.5–3.7 | 模型、harness、预算、请求参数和费用记录 | 全品牌最佳 harness 榜单 |
| 运行失败与有效尝试 | §3.6、§4 | 预定重试规则、逐次结果、缺失解释 | 把所有错误折成统一 reward |
| 评分可见性与污染边界 | §3.2、§3.8 | 自建 fixture 的历史与网络检查，保留正常完成任务所需信息 | 全面封网或删全部 Git 的默认方案 |
| 完成与交付质量分离 | §3.10 | patch／工件保留及小批人工复核 | 新的密集过程 reward |

给 A 的交接应是事实而不是预先训练裁决：任务与尝试身份、结束阶段、补丁、测试结果、原始错误、token／时间／费用。A 再依据明确算法合同决定怎样进入组统计或 loss。两边不能分别静默删掉不同失败集合。

**本篇对项目方向的约束：**先利用少量任务发现评测不确定性，再选择环境或训练干预。不要把“能构建 benchmark”直接推导成“必须研究动态课程”，也不要求全部图页补核结束才开始无争议的本地资产盘点。
