# Miles v0.1: Production-Level Post-Training：完整系统报告精读

**这是一份系统能力、实现边界与参考运行报告，不是新的 RL 算法或 coding 能力排行榜。** Miles 在 slime 基础上连接 SGLang rollout、Megatron/FSDP trainer 与权重发布，重点是每个边界的保真、效率和可替换性。最完整的案例为 GLM-5.2 744B-A40B 在 64×GB300 上的单次 100-step terminal RL：前 30 个测量步的中位 step time 为 263 秒，训练 reward 的九步滑动平均由 0.438 升至 0.556；作者明确不把它解释为已测得的能力改善。本文完整覆盖低精度、offload、三种远程权重传输、LoRA/OPD/true-on-policy、diffusion 和模型／硬件证据等级，并追查参考脚本与若干关键消费点。**P2P 在单节点可能更慢，数值零差只覆盖特定小型 dense Qwen3，GLM 案例没有开启 R3；这些限制不能从摘要中省略。**

## 2. 核心问题、架构与证据强度

### 2.1 系统到底处理什么

作者把困难分为两类：一类是多轮、工具与长尾导致的执行效率；另一类是 sampled trajectory 与 trainer 所优化对象不一致，且可能不触发异常。设计原则是 verified、clean、customizable，服务准确性、效率、可靠性与可扩展性。[P, §1–2, pp.1–3][p1]

Fig.1 的闭环为：

```text
数据源中的 prompt
  → 同题多次尝试，进入 SGLang + agent/environment
  → 完成组进入 buffer：选择、等待、staleness
  → Megatron 或 FSDP：优势、loss、optimizer
  → 权重准备、传输、安装与版本推进
  → 新旧在途轨迹按调度约定继续
```

**Prompt** 是任务；**trajectory** 是一次尝试（多轮时包含消息、工具调用和观察）；**group** 是同题的一组尝试；**session** 是服务层看到的有序请求集合，可能因分支产生多个训练 trajectory。作者为其目标中的 group-relative 方法选择整组缓冲／消费；这不是宣称所有 RL 算法理论上都必须等待同题组。[P, §1.1、§2, pp.2–3][p2]

### 2.2 不应把章节画成同一个训练阶段序列

核心 loop 可用于全参 RL；LoRA 改变更新参数集合，OPD 改变信号来源，true-on-policy 改变数值执行，SFT 不需要 rollout engine，diffusion 又改变 trajectory 的物理含义。它们是共享组件的不同 recipe，**不是先 LoRA、再 OPD、再 diffusion 的一条训练流程**。[P, §5–6, pp.21–26][p21]

本文证据包括系统机制、公开配置、有限的传输／offload 测量、一个 GLM end-to-end run，以及配套训练的简要观察；没有提供所有组件的统一等预算消融、长期可靠性统计或跨模型普遍性证明。作者自己在 §1、§7、§9 明确收窄了这些结论。

<a id="rollout"></a>
## 3. Rollout：保住计算复用，也保住实际采样对象

### 3.1 Affinity 与新 session 放置

多轮下一次请求复用先前大量上下文；若逐请求按负载任意换 engine，会重新 prefill。Miles 使用 stable routing key 绑定 session 到持有前缀 KV 的 engine；启用 DP attention 时进一步绑定 DP rank。开启 session server 时自动选择这一模式，缺 key 不默默退回负载路由，而是报错。[P, §2.1, pp.3–4][p4]

只绑定也可能使长任务挤在同一 engine，所以新 session 先选择 active requests 最少的目标，然后在生命周期中保持亲和性。参考案例报告 prefix-cache hit rate 96%，但没有单独的无 affinity／无负载放置消融。**亲和性保住局部性，不等于负载永远均衡；活跃请求数也不是剩余计算量的精确估计。** 后一句是读者对指标的解释，不是原文新增实验。

本篇没有承诺权重更新后旧 KV 永远可复用；session/token 记录、请求放置、权重改变后的缓存有效性是不同问题。

### 3.2 Fully async 的资源与组语义

论文中的 fully async 使用**独立训练与推理 GPU pool**，拒绝 colocated placement。Rollout 连续生成，trainer 消费已经完成的组；安装新权重时仍需要暂停。默认 case 的 eval 也会占用生成资源，因此“fully async”不是“任何操作都不阻塞”。[P, §2.2, pp.4–7][p5]

补位有两种粒度：group 模式等全组结束才释放其占额；sample 模式让已完成成员先释放槽，攒够位置后启动替代组。**sample 粒度补位没有把 GRPO 变成 single-rollout，也没有取消完整组消费。**

默认 buffer 容量以训练侧组数的倍数设定，满时 `put` 等待；自定义接口只需 put、get、metrics。原文 Table 1 将丢弃分为：

| 原因 | 检查时机 | prompt 后续 | 解释边界 |
| --- | --- | --- | --- |
| 生成放弃／组没有完成 | 到达时 | 按 recipe 重试或丢弃 | 不完整组以终止结果被处理，不是凭空称其为成功完成组 |
| 用户 filter 拒绝，如全组同 reward | 到达时 | 丢弃 | 示例针对 outcome advantage；不代表其他辅助目标一定无信号 |
| 权重过旧 | **trainer 取出时** | 重试或丢弃 | 已在 buffer 等待的组会继续变旧，入队时检查不够 |

给定 trainer 当前版本 $v$，原文定义可写为：

$$s(G,v)=v-\min\{v_t: t\text{ 是组 }G\text{ 内带版本的生成位置}\}.$$

这是将原文文字数学化，不是新增算法。最老 token 决定年龄，不用均值掩盖早期片段。它仍是**版本距离**，不是对分布差异或梯度偏差的直接估计；限制版本距离不证明与同步更新等价。[P, §2.2.2, pp.5–6][p6]

Table 2 将 `queue_size`、消费组 avg/max staleness、buffer avg/max staleness、aborted/stale groups filtered 分开。队列空／满有助区分供给和消费瓶颈，但实际组过滤、任务结构和服务故障也会影响供给；不应看到空队列就直接购买更多推理 GPU。**当前代码的“消费 staleness”计数范围还有一处需注意的差异，见 §10.3。**

### 3.3 异步评测与版本归属

| 模式（Table 3） | 测量的权重 | 成本与等待 |
| --- | --- | --- |
| shared engines，默认 | live rollout fleet 最近收到的权重 | 停止新生成，已有请求完成；eval 挤占训练数据生产 |
| dedicated fleet | checkpoint snapshot | export 可能暂停 trainer；之后 eval 独立运行，占专门 GPU |
| external backend | checkpoint directory | 同样可能付 export 成本；后端不要求使用 SGLang |

Fig.2 的关键不是“独立 eval 免费”，而是将 export 的 collective 暂停与后台评测分开。复用周期 checkpoint 可避免一次新导出。结果归属被测权重的 dispatch step，迟到单列 lag；专用 fleet 先逐 engine 核对 snapshot 版本，再检查结果版本与 mixed-version 请求比例。[P, §2.2.4, pp.7–8][p7]

导出失败、快照缺失、在途 eval 过多、用户后端出错等被记为 skipped，不终止训练。**这是一种 eval 故障策略，不是泛化的训练故障恢复或 crash-consistency 证明。**

### 3.4 三层插件：替换多少，承担多少

Table 4 的所有权可重述为：

| 外部接入层 | agent/environment loop | token／trajectory 记录 | group reward、数据源、batch 编排 | model/engine/weight/advantage/optimizer |
| --- | --- | --- | --- | --- |
| agent function | 外部 | Miles | Miles | Miles |
| generate function | 外部 | 外部 | Miles | Miles |
| rollout function | 外部 | 外部 | 外部 | Miles |

**Group reward** 指需要整组才能计算的排序等评分；不等于 GRPO 的组相对中心化，后者仍归 Miles。Harbor、NeMo Gym、OpenEnv 走 agent 层；HUD、Strands Agents、τ-bench 走 generate 层；Prime Verifiers 走 rollout 层。sandbox provider 是 connector 内的执行后端，不是第四层。[P, §2.3、Table 4, pp.7–9][p8]

报告列 AgentENV、Daytona、E2B、Modal，可每 episode 创建销毁，也可复用长期环境服务。**生命周期策略不自动证明 reward 隔离、golden/no-op 正确、替代解接受或跨任务状态无泄漏。** 这些集成明确仍属 experimental。session server 尚不记录截图／图像视频，所以视觉连接器需要自己记录轨迹或使用较低层 TITO，不能把“支持视觉模型”与“视觉模型走统一 session”混为一谈。

### 3.5 TITO、分支与 matcher

TITO 将 tokenization 的权威留在 session server。第一次按选定模型模板渲染；完成一轮后保存 prompt/output token IDs、rollout logprobs 和 routed experts。新请求仍提交完整 messages，但服务端寻找最深适用 checkpoint，只 tokenize 新后缀；agent 自带 token 字段被覆盖。训练 mask 只覆盖模型生成位置。[P, §2.4、Fig.3, pp.9–11][p9]

**Linear** 只能扩展尾部，允许回滚最近一个 assistant checkpoint 重试，更早分歧拒绝，最终一条训练序列。**Branching** 保留 append-only tree，按最深前缀开枝，每个被选 leaf 产生序列；length-limit 停止的 branch 不再扩展。它允许真实 harness fork／compaction，但论文没有给跨 leaf 的完整去重、reward 归属和最终 loss 分母公式。

Matcher 决定 replayed message 是否算同一历史，而不是决定模型实际采样了什么 token：

| 设置 | 比较内容 | 风险与作用 |
| --- | --- | --- |
| 最严格默认 | 模板读取的 role/content/reasoning/tool calls，忽略无关 client 附加字段 | 防止无关字段造成伪分叉 |
| JSON 语义级 | 同内容的参数 JSON 可有不同序列化；call id/name/order 仍一致 | 只适配参数重序列化的 harness 无需更松 |
| 最松 | role 与 visible text；不比较 tool calls | 空文本的不同调用可能被合并；保留旧 token 历史且不修复 call id，产生静默不一致 |

因此，**“支持黑盒”不是“可以任意放宽历史比较仍忠实”**。当 matcher 合并时，存档 token snapshot 仍是权威；若动作语义真的变化，过松匹配反而把错误历史送给训练。[P, §2.4.2, pp.10–11][p10]

模型族需显式指定，经模板与 reasoning/tool parser 注册验证，不自动从 checkpoint 猜。两层检查是 CPU append-only tokenization 与 GPU 实际生成／stop／parser 检查；CPU 单过不能代替 GPU。未知架构 generic handler 会警告，不能视为已保证与 canonical 模板一致。

### 3.6 R3：token 一样，还需知道专家是否一样

同一 token 在训推的 top-k router 中可能选到不同 experts，导致更新并非作用于生成该 token 的同一计算路径。R3 将逐 token、逐层专家分配作为 rollout 数据，训练 replay；TITO 让它扩展到多轮 episode。[P, §2.5, pp.11–12][p12]

代价是 `(tokens−1)×layers×k` 个 int32。按原文例子 32K、60 层、top-8，约 60 MB/trajectory；按 32K=32768 复算为 **62,912,640 bytes，约60 MiB**。这是数据搬运／存储成本，不只是 router 计算开销。

R3 是 recipe 选择，不适用于 dense；异步情况下还存在其他偏差，收益可能有限。**§9 GLM-5.2 参考运行明确关闭 R3。** 不能从报告同时介绍 TITO/R3/true-on-policy，推出最终大模型案例全部使用。

<a id="trainer"></a>
## 4. Trainer：精度、状态存储、后端和目标是四个不同选择

### 4.1 低精度是四阶段契约，不只是修改 dtype

Table 5 的验证范围如下，状态是本论文版本的声明：

| 格式 | block / scale | 本文列出的模型 | 成熟度 |
| --- | --- | --- | --- |
| BF16 | 无量化 block | 所有列入支持的配置基线 | Baseline |
| FP8 blockwise | 128×128 / FP32 scales | Qwen3-4B、Qwen3-30B-A3B、DeepSeek-V4 | Generally available |
| MXFP8 | 1×32 / UE8M0 | Qwen3-30B-A3B、DeepSeek-V3.2 | Beta |
| NVFP4 E2M1 | 1×16 / E4M3 block + FP32 tensor scale | Qwen3-30B-A3B | Beta |

报告允许训推使用同格式，或 BF16 train + quantized serve；**NVFP4 例外，不能配 BF16 trainer**。INT4 QAT 和 BF16-train/FP8-serve 也存在，但原文没有在此展开完整 INT4 recipe。[P, §3.1, pp.12–14][p13]

需一致的四处是 **checkpoint conversion → trainer forward → live weight export → rollout**。MXFP8 还涵盖 weight-gradient/data-gradient GEMM；NVFP4 使用 per-token activation scaling，gate/up 联合量化，KV 保留 BF16；不适合该 block 轴或敏感 tensors 允许 BF16 例外，但四阶段需同步配置。**相同 quantizer 输出不等于所有算子、完整 logits 或梯度逐位一致。**

NVFP4 两个可选 refinement 必须分开：dequantized backward 在 BF16 中对前向的量化值执行反向 GEMM，改变速度／梯度稳定性；four-over-six 在4与6两种 block 映射中选择误差较小者，改变量化本身，所以训推和导出全部要同步。不能只在 trainer 加一个开关就认为量化协议保持了。[P, §3.1, p.14][p14]

本篇称所测 reward 曲线接近 BF16、rollout 更快，但没有在此给各模型／格式的完整曲线、误差条和性能表。需要专项报告才能量化；不能把某一格式在某个架构上的结果泛化到整个 Blackwell。

### 4.2 两类 offload：暂停 actor 与训练中的 optimizer streaming

**Paused actor offload** 在 actor 不训练时腾空其 GPU state。Megatron 按 allocator 块搬出 weights/grad buffers/optimizer，默认 pinned host RAM，RAM 不足时通过固定 staging buffer 流到 node-local disk；FSDP 走 model/optimizer host 移动，当前无相同 disk 路径。[P, §3.2.1, pp.14–15][p15]

**Optimizer streaming** 则在训练过程中让 Adam 状态留在磁盘，更新某参数 bucket 才载入对应 state。FP32 master weights 和两份 FP32 moments 合计通常12 bytes/parameter；forward/backward 不用这些 optimizer state，所以可以释放对应显存。moments 可降 BF16，master 仍为 FP32。它能让运行装得下，但可能让 optimizer update 更慢。

| 原文 Qwen3-30B-A3B 测量 | streaming 前 | streaming 后 |
| --- | ---: | ---: |
| actor offload | 24 s | 5.2 s |
| actor reload | 8.9 s | 1.3 s |

这不是完整训练 step 的对照：少搬已在磁盘的 state 可以缩短暂停切换，同时真正 optimizer 和 checkpoint 保存仍可能更贵。按两项相加是32.9→6.5秒，**只是一轮 offload+reload 的算术合计**，不能据此报告训练5×加速。[P, §3.2.2, p.15][p15]

限制包括：streamed checkpoint 只在相同 parallel layout 恢复；不能缺失 streamed state 后假装从普通 checkpoint 恢复 Adam；将 state 复制进 checkpoint 目录的过程同步阻塞。Megatron 普通 checkpoint 可换并行布局，与 streamed optimizer 的布局约束不是同一个保证。

colocated 默认 offload，disaggregated 默认不需要；PPO 是例外，Miles 将 actor/critic 共置，因 critic 使用显存而仍需 actor offload。**这没有把整个 PPO 的额外成本变成零，也没有表示两个模型同时常驻。**

| --- | --- | --- |

### 4.4 优势估计与训推修正

五个 estimator 为 GRPO、GSPO、REINFORCE++ plain/baseline、PPO(value function)；typed loss 有 policy/value/supervised/custom。本文没有逐一给其完整数学定义、共享前缀计权、dynamic batch 全局分母或 CP reduction，因此不能从名称推出某一默认 recipe 等于 RepoHarness 的 faithful DIS。[P, §3.4, pp.16–17][p17]

原文 ratio 是 $r=\exp(\log\pi_{train}-\log\pi_{rollout})$。两种处理可按其文字写成：

$$w_{TIS}(r)=\min(\max(r,l),u),\qquad
w_{pop}(r)=r\,\mathbf{1}\{l\le r\le u\}.$$

TIS 默认区间 `[0,2]`，主要压上尾；clip-or-pop 将界外位置权重归零、界内保留原 ratio。两者记录修正前 ratio、clip fraction、mean absolute deviation。**这里是对既有 policy-gradient loss 的修正权重，不是完整 PPO clipping 公式，也不是自动采用双侧 faithful DIS。** 当前实现保留 `loss_masks` 原样，界外权重归零不一定改变最终归一化分母，见 §10.4。

## 5. 权重更新：相同结果不代表相同拓扑成本

### 5.1 分类与共同 bucket 准备

Table 7 的三种**远程 transport** 是 NCCL broadcast、RDMA P2P、shared-filesystem disk-delta。共置时 CUDA IPC 是本地 handoff，不应因 Fig.1 同时画出 IPC 就遗漏 disk-delta 或混成相同三项。[P, §4, pp.17–18][p18]

Mega 的 broadcast/P2P 共用准备：普通权重在 PP stage 内 TP all-gather、转换HF名称／布局、填默认512MB bucket后flush。expert pass 因各EP rank持有不同专家，在flush时才做EP gather与转换；积累阈值乘EP degree，避免实际flush膨胀。dense 的 expert pass 无tensor就不发collective。

各PP stage可以准备不同参数，但broadcast flush有共享锁，若干阶段边界有trainer barrier；最慢stage仍可拖住别人。FSDP则使用简化state-dict bucketing，远程走broadcast；不应把Mega P2P/delta能力默认归给两个后端。

### 5.2 P2P 何时有效，何时反而更慢

多个源rank同时向需要其shard的目标rank RDMA写入；发送源数最多为两侧rank数较小者。CPU上的SGLang模型副本复用官方weight loader做目标reshard，减少手写布局规则；复用一块已注册pinned buffer，最后一组目标写可和下个bucket准备重叠。[P, §4.2, pp.18–19][p19]

| Table 8：H100、1GB transfer bucket | 每侧节点数 | Broadcast | P2P | 时间降低 |
| --- | ---: | ---: | ---: | ---: |
| Qwen3-30B-A3B | 2 | 2.67 s | 2.16 s | 19.1% |
| GLM-5 744B-A40B | 16 | 58.30 s | 8.48 s | 85.5% |
| Kimi K2 1T-A32B | 32 | 53.28 s | 7.23 s | 86.4% |

“每侧”意味着 trainer 和 rollout 各有这些节点，不能合计写成一侧的节点数。计时从 generation pause 结束到 update call 返回，取steady-state平均；Kimi含约884ms on-GPU requantization。这不是裸网络带宽或完整RL step。[P, Table 8, p.19][p19]

**单节点 P2P 在作者测量中最多慢约70%**，因为没有额外汇聚带宽，仍承担host reshard与staging；因此broadcast是默认。当前支持还受Mega↔SGLang weight-name mapping约束：Qwen2/3 dense、Qwen3-MoE、GLM4-MoE及DeepSeek-V3/V3.2派生，不是任意模型。

对我们八卡单节点最直接的启示是一个“不立即采用”的理由，而不是一个可以写进项目预期的86%加速。

### 5.3 Disk-delta 的原子发布与重放限制

每个rollout host从共享base开始；trainer比较相邻导出状态的原始bytes，发布压缩delta、base/version/encoding/digest metadata；每文件原子写、index最后写。host拉取并修补本地checkpoint之后，才pause/reload/advance-version/resume。前面的磁盘发布和修补可与生成重叠。[P, §4.3, pp.19–20][p20]

**XOR**紧凑、产生快，但同一delta作用两次会恢复旧值，所以要求正确base与exactly-once apply；**overwrite**记录位置与新绝对值，重复apply幂等，但更大。两者都不理解tensor语义，names/dtypes/shapes/layout必须匹配。校验是patch后完整tensor的checksum，不是仅检查delta文件。

发现base不匹配或checksum错误时在engine reload前停止。这个设计不是自动证明所有节点故障情景下拥有全局原子提交。论文还限定：Mega-only；FSDP仍broadcast；不与colocation、LoRA、prefill–decode disaggregation组合；单一endpoint后的外部rollout服务尚未实现。**“一个接口提供多个transport”不等于它们与所有功能形成全组合。**

### 5.4 在途请求与权重验证

Mega支持abort、in_place、retract，默认retract；session server拒绝abort以免破坏历史；FSDP总用retract。默认与具体recipe不同，§9对应当前脚本实际使用in_place，见§10.1。[P, §4.4, p.21][p21]

一次性可选debug检查先把engine tensors填随机值，再执行第一次更新并逐tensor对比trainer，避免漏写tensor仍“看起来正常”。可查target、draft或两者；跳过合法的inference-only tensors；默认bit-exact，量化时容差按格式推导。它只在debug/validation、CI自动启用，**不是每步对所有模型都付出的完整权重验证**。本文称P2P测试覆盖1–8GPU节点，不是自己复现。

## 6. 其他后训练方式：LoRA、OPD、true-on-policy 与 SFT

### 6.1 LoRA 的更新单元与多适配器

base冻结且保留在engine，只有adapter训练／发布，减少optimizer state、weight-gradient与传输。它仍需要执行base前向与传播，不能把trainable parameter比例直接当作总训练成本比例。[P, §5.1, pp.21–22][p22]

支持需要三个组件一致：Mega实际wrap哪些module、Miles如何命名／导出、SGLang如何分配／应用；名字相同不足以证明专家、linear attention等结构兼容。报告以validated recipes而非名字allowlist表达支持。当前LoRA训练为Mega-only，colocated用IPC、disaggregated用NCCL，P2P/delta不运adapter。GLM-5.2 recipe可以BF16 adapter train + FP8 base serve，adapter本身不量化。

experimental multi-LoRA让一份base服务多个adapter，每个有自己的dataset/reward/optimizer state/step，只发布实际更新的adapter；仅disaggregated。operation-driven backend与Tinker-compatible frontend在论文时仍open PR，不是所有功能已发布。Diffusion LoRA在engine到达时merge入base，与LLM侧单独应用adapter也不相同。

### 6.2 OPD 的信号在哪里进入

学生自己采样，teacher在同一token位置评分。原文的sampled-token reverse-KL估计为

$$d_t=\log\pi_s(x_t\mid h_t)-\log\pi_T(x_t\mid h_t),\qquad
A'_t=A_t-\beta d_t.$$

两份logprob均为固定评分输入；teacher认为更合适的学生token得到相对鼓励，反之惩罚。单次 $d_t$ 可以为负，不意味着整个KL为负。Miles先计算原advantage，**再局部减去该量**，后续PG unchanged；task reward可保留或设零。[P, §5.2、Fig.4, pp.23–24][p23]

这不等于“在loss中对teacher/student logits额外反传一个全词表KL”，也不能不加说明地等同“先改逐步reward，再重新计算所有returns/GAE”。本篇没有给所有组合的critic target处理，当前函数直接修改advantages，见§10.4。

| teacher位置 | 数据与限制 | 额外成本 |
| --- | --- | --- |
| served SGLang teacher | rollout完成后评分；可不同架构，但必须同tokenizer | 独立服务、网络、teacher forward与排队 |
| in-process Megatron teacher | 同架构的第二模型，training step专门forward | 额外模型/state显存及训练关键路径计算 |
| 多served teachers | prompt metadata选择一个teacher | 多服务管理；不是本篇验证了任意跨源teacher可稳定合并 |

top-K只用于served teacher，可取学生top-K或师生top-K交集，做加权差值；本篇没有给截断质量、重归一化、概率质量缺失处理的完整公式。不要把它默认写成精确full-vocab KL或无偏全分布估计。

**本文唯一带具体数值的OPD观察：**Qwen3.5-35B-A3B先做5步可验证RL得到teacher；student从base出发做5步纯OPD，task reward=0。held-out DAPO响应长度 **14,070→6,132（约降低56.4%）**；accuracy **84.0%→85.2%**，1.2个百分点小于约1.6个百分点标准误。作者支持的结论是缩短输出而没有可靠accuracy变化，**不是证明成绩提高，也不是正式等效／非劣检验**。teacher训练、评分与学生训练的总GPU/API成本未给。[P, §5.2, p.23][p23]

### 6.3 True-on-policy：精确到什么，尚未解决什么

相同weights仍会因kernel、fusion、batch shape、reduction不同产生logprob差异。Miles通过统一FA3、batch-invariant GEMM、per-model kernel contract、Mega local实现替换、关闭部分融合，以及cuBLAS/TE/NCCL/SGLang确定性配置来收窄它；TP linear与all-reduce也要保持布局不变性。[P, §5.3, pp.24–25][p24]

关键步骤是**rollout完成后用prefill重新评分**，而不是直接拿decode的logprob对trainer。匹配对象是这一评分路径下的已采样token。当前profile仅dense Qwen3 **0.6B、4B及对应变体**，Mega/FSDP与被支持的DP/TP/PP/CP布局；未支持模型拒绝启动。当前源码profile与这一范围吻合，见§10.5。

保证不包括完整词表分布逐项一致，不处理旧weight版本造成的off-policy，也不证明核对过任意dtype、kernel或GPU组合。**TITO一致、R3一致、quantizer一致、sampled-logprob一致与最新策略采样，是五个可分开的条件。**

配套Qwen3-4B-Base/DAPO运行中reward曲线接近基线，但rollout更慢；本文未给具体速度损失或多模型泛化对照。故不能直接给30B-A3B案例开一个“zero-KL”开关，也不能认为开启后所有IS修正与staleness处理都失去意义。

### 6.4 SFT 范围

SFT复用trainer、选择supervised loss、不挂rollout engine。作者明确不进一步讨论；本文也不虚构SFT数据、训练阶段、baseline或warm-start结果。[P, §5, p.21][p21]

## 7. Miles-Diffusion：相同架构思想，不同轨迹和数值风险

这一部分属于完整后训练范围，不能因为项目目前做文本SWE而省略。独立代码入口为 `radixark/miles_diffusion`；本轮只读论文，不审该仓库。

### 7.1 训练对象与流水线

Trajectory是从noise到image/video的一串denoising步骤，sglang-diffusion返回intermediate states与每步logprob；FSDP2 trainer对选中的步骤重新评分并优化。Wan2.2 recipe还使用sequence parallelism拆长视频。loss、batch prep、rollout和reward均可替换。[P, §6, pp.25–26][p25]

Flow-GRPO对每个支持模型有recipe；DiffusionNFT的已交付recipe在SD3.5，SFT在Wan2.2，其他model上的code path不等于完整验证recipe。**Microgroup**是共享encoder结果的一组样本，不是LLM的同题GRPO group定义可以直接照搬。

生成、反序列化、reward scoring流式重叠；视频中间tensor可能达GB级，raw bytes代替base64，worker进程pool代替主event loop反序列化。LTX-2.3测量为：

| 指标 | 旧路径 | 新路径 | 本文复算降低幅度 |
| --- | ---: | ---: | ---: |
| rollout time / step | 157.4 s | 87.6 s | 44.3% |
| total step time | 321.9 s | 252.1 s | 21.7% |

两者都少69.8秒，但分母不同。没有报告相同优化一定改善文本SWE，也没有在此列出完整硬件和长期学习曲线；不能把44.3%写成全流程加速比例。

### 7.2 确定性与recipe证据等级

确定性模式让相同硬件下、支持的attention recipe的训练forward/backward可重复，以便registered metrics与committed standard逐位比较；不支持的backend拒绝。per-parameter dtype通过FSDP2 mixed-precision patch保留timestep embedder、modulation table等FP32，其余BF16，减少训推差。**训练可重复不等于两引擎在所有输出上完全相同。**

| 证据等级（原文术语） | 要求 | 本文列出的recipe |
| --- | --- | --- |
| Fully gated | 完整训练曲线 + 至少nightly实际recipe确定性E2E，registered metrics精确匹配 | SD3.5、LTX-2.3 |
| Proxy gated | 完整曲线；nightly运行已说明的缩小单节点proxy | 多节点Wan2.2 |
| Verified | 完整曲线，但无上述deterministic gate | Qwen-Image、Cosmos3 |
| Not verified | 无完整曲线，smoke／短debug不算 | 两个Wan2.2 LoRA recipe |

MiniMax H3在论文时仅open PR。等级绑定**脚本与拓扑**，不是给整个model family一个永久认证。[P, §6, p.26][p26]

### 8.1 Day-0 与后端／精度的交集

本文列day-0六模型：Kimi K3、DeepSeek-V4、GLM-5.2、Qwen3.8、Inkling、Nemotron 3 Ultra。其中K3与2.4T Qwen3.8的release-day训练是LoRA，且相关recipe仍open PR；不能写成已在main发布的全参训练。其他九families的文档覆盖还包括DeepSeek-V3.2、Kimi K2.6、Gemma4、gpt-oss和各早期变体。[P, §7.1, pp.26–27][p27]

### 9.2 数据与评分漏斗：这篇没有声称自己生产了一批新任务

正文声称eval与train互斥，但没有披露exact task IDs、benchmark commit、image digests或held-out结果表；代码提供另一些信息，见§10.1–10.2。原文没有Claude Code或Codex版本，也没有把本例称为真实生产harness训练；不要把TITO图中的harness示意名称套到这个shell-agent case。

### 10.2 可复现配方与任务split尚不是同一件事

C2写默认训练文件 `tbench2_train69.jsonl`，eval提示20tasks×2samples，并要求自行留出disjoint集合。但 [C3 `make_tbench2_data.py`][C3] 默认发现当前checkout所有含task.toml的目录；`n=0`表示全体，只有显式`--tasks`／`--n`才缩小。**输出文件叫train69不会自动选69个任务，也不会自动创建互斥eval集。**

这不证明原实验发生泄漏；它说明照抄文档命令仍需补exact manifest和split检查。C2要求Daytona quota128、每sandbox 2vCPU/4GiB/10GiB，首题image构建约10min、复用约1min；这些是配套文档报告值，不是本轮测量，也不在论文正文成本总表里。OpenEnv任务包还要求editable源码安装、Mega带streaming hooks，普通pip依赖存在并不足以复现。

**时间口径冲突。** C2同时写“100 rollout steps in 21 h wall clock”和“~6.5 min/step incl. evals”。算术上21h/100=12.6min，6.5×100则约10.83h；可能包含不同启动、等待或统计窗口，但文档未解释。本文保留两项及差异，不挑一个数宣称完整端到端时间，也不拿它推八卡预算。

### 10.3 Buffer比论文多一个前置过滤；“consumed staleness”指标范围也需注意

完整读取 [C4 `miles/rollout/fully_async_data_buffer.py`][C4] 和 [C5 `miles/rollout/filter_hub/common_filters.py`][C5]。当前默认 `put` 顺序是 **aborted → missing reward → custom dynamic filter**；missing reward与custom reject不进unused retry handler，aborted/stale才进。论文Table1没有独立列missing-reward情形。这个顺序也意味着外部custom filter不能假设自己会看到每个异常组。

C4的`get()`在判断超限、丢弃之前，先把年龄append到`_metric_consumed_staleness`。随后`get_metrics()`用该列表生成avg/max。因而当取出时丢了stale组，**这些metrics包含被检查后丢弃的组，不只是最终交给训练的组**，与Table2的字面解释不同。

本轮做了一个隔离方法体检查：current version=5，threshold=2，先弹oldest0(stale5)、再弹oldest4(stale1)。最终只返回fresh组；但metrics为avg3、max5、stale_groups_filtered1。检查仅转录C4对应方法并注入最小状态，替代了分组年龄函数与metrics收集依赖，**不是导入真实完整运行时的上游测试，也不是GPU复现**。详细限定见自查记录。

这首先是观测口径问题，不能据此声称“过旧样本真的进入了loss”。另一方面，C5会忽略缺少oldest_version的sample；如果全无版本或没有current version则返回None。存在上游其他完整性检查的可能，本轮没有审完所有入口，故不将此局部行为定性为端到端漏洞。

### 10.4 OPD与TIS：源码确认了信号层次，也暴露需要调用方保障的条件

[C6 `miles/backends/training_utils/loss_hub/opd.py::apply_opd_kl_to_advantages`][C6]：先有base advantages，再减`opd_kl_coef * reverse_kl`；teacher、old_student、precomputed reverseKL作detach，检查list长度和tensor shape。若student_log_probs为None直接return；teacher缺失则在对应路径报错。函数不重新计算critic returns，亦不包含自有的完整policy-loss reduction。

所以把“零outcome reward组都丢弃”与纯OPD组合，需要检查该recipe实际filter，不能因为GRPO部分无方差就说OPD也无信号。当前case只用`check_no_aborted`，正好说明filter是配方选择，而不是所有能力天然兼容的固定规则。

[C7 `loss_hub/corrections.py`][C7]中`vanilla_tis_function`将clamp权重乘入pg_loss；`icepop_function`将界外weight置零，两者**原样返回loss_masks**。这与“界外token不贡献该项梯度”的说明一致，但不等于从分母移除token。函数输入`train_log_probs`在内部叫old_log_probs；是否以及何时冻结这些输入要继续追调用者。本轮不据两个函数推导完整PPO/GSPO梯度，也不判定custom loss的兼容性。

### 10.5 True-on-policy profile：声明与当前注册一致

[C8 `miles/true_on_policy/model_profiles.py`][C8]只注册一个Qwen3 dense profile，包含 `Qwen3-0.6B`、`Qwen3-4B`、`Qwen3-4B-Base`、`Qwen3-4B-Instruct-2507`；train layouts为dp/tp/pp/ulysses_cp，rollout为dp/tp，未知model抛ValueError。**没有Qwen3-30B-A3B profile。**

这证明当前注册范围，不是本轮运行了其所有kernels。没有逐一检查模型×布局×硬件×dtype笛卡尔积，也不把类型声明里的MoE family名字当成已注册模型。

### 10.6 本轮代码覆盖边界

C1/C2/C3/C4/C5/C6/C7/C8均阅读全文；未全面审计session实现、低精度kernels、P2P/delta协议、distributed reducer、OpenEnv/Daytona agent具体执行循环、diffusion仓库。相应章节以P为依据，不写“源码已证明”。既有N11的代码检查继续绑定自己的版本，本次没有重跑其中15项检查或重建rh2集成。

## 11. 对RepoHarness的意义：补强证据，而不是扩大必做清单

映射日期2026-09-09，项目基线R；参照[当前简报](../../../agentic_RL/repo_harness_rh2_workstreams/CURRENT-STATE-BRIEF.md)和[项目一建议](../../../agentic_RL/repo_harness_rh2_workstreams/project1_design_advice_20260907.md)。两者中建议与实施定案仍分开，本文不更新训练范围。

### 11.1 它重新确认哪些属于上游

Fully async、buffer的consume-time staleness、TITO、R3、通用weight update、后端、OPD和数值对齐，都已有清楚官方所有权。RepoHarness若使用它们，应写“基于／适配／验证”，而不是重新归为自行开发的框架能力。

相反，这份报告没有替我们的任务完成质量审计、fresh grader隔离、替代解检查、训练数据选择、真实Claude Code语义校验或独立held-out效果。**上游更加完整不等于项目自有层消失，但要求我们更准确地区分适配、验证、任务工程与原创改动。**

### 11.2 最直接的几项候选

| 候选借鉴 | 来源依据 | 归属与适用条件 | 最小验证 |
| --- | --- | --- | --- |
| 将版本事实与staleness裁决留给一个权威消费点 | §2.2；C4/C5；既有N11增量 | 复用上游，不再造第二个staleness阈值；先检查真实adapter版本类型 | 固定多版本、多leaf组，核实际接收／丢弃及metrics口径 |
| 保持strict或必要的JSON级matcher，核真实harness replay | §2.4 | 与模板/parser绑定；不能为“少报错”直接选最松模式 | 对同文本不同工具调用、JSON重序列化、compaction分叉做token与动作对照 |
| 以真实瓶颈决定精度／offload／传输 | §3–4，尤其P2P单节点负结果 | 单节点PCIe不自动受益于RDMA；sm_120未被本文单独验证 | 同权重同token短作业，分解生成、trainer、状态搬移、发布、环境时间 |
| 按训练目标区分“无outcome方差”和“没有任何可用信号” | §5.2；C6 | 只有启用OPD等辅助信号时才需相应消费路径；不修改已冻结纯GRPO语义 | task reward全零但teacher差非零的小fixture，核filter、advantage、mask、分母 |
| 同时记录样本级数值检查和独立学习结果 | §5.3、§9 | 不把健康KL或training reward代替能力证明 | 固定token比较 + 冻结held-out；结果回到确切policy version |
| 让支持声明绑定recipe／模型／硬件／验证级别 | §6–8 | 文档与测试纪律，不新增治理平台 | 区分CPU、GPU短测、完整曲线和独立对照；不继承上游未经本机验证的组合 |

当前30B-A3B不是true-on-policy已注册模型，GLM案例的64GB300/DP attention/MTP/Daytona也不是八张RTX PRO 6000的预算模板。R3是否启用、offload是否有利、LoRA是否满足目标，都需要本项目配方与瓶颈决定，不是“论文里都有所以都补上”。

### 11.3 值得改变的是简历证据表达，而不是立即换基座

最有价值的模式是：**说明一个具体约束，给出因果上相称的改动，再报告它实际测量的指标与限制。** 系统语义保持的效率改进可以用固定样本与完整成本证明，不必每项都发明新能力；一旦改变样本选择、分组、信息可见性或目标，则需要行为／学习层对照。

本文GLM案例本身就示范了诚实边界：可以主张大模型运行可行性和测得step时间，不把单次reward上升包装成显著能力提升。RepoHarness最终仍需自己的真实训练与独立效果，阅读报告不替代这些实验。

### 11.4 最影响后续判断的未回答问题

| 未知项 | 已查范围 | 不应如何补齐 |
| --- | --- | --- |
| GLM exact train/eval manifest、benchmark/image版本、held-out结果 | §9、C1–C3 | 不由train69文件名推任务数或无污染 |
| GLM总运行时间与费用 | §9、Fig.5、C2 | 不强行调和21h与6.5min；不直接median×steps |
