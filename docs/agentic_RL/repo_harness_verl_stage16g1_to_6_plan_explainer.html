Stage 16G.1 → 16G.6 执行计划讲解

审查/讲解对象：51-stage-16g-1-to-16g-6-execution-plan.md　·　目标是让你看懂"6 个阶段各干什么、怎么分工、最终实现什么"，用一个贯穿例子串起来　·　上游依据：16G.0 完整报告、扫盲版对比

一句话：16G.1–16G.6 是把 RepoHarness 的工具面，从"看/搜/改很强、但不会动手验证"改造成"接近 Claude Code 的真实 SWE 工具环境，同时保持可审计、可训练、不能作弊"，最后冻结成一套 profile 并决定能不能进真实训练。

分工一句话记住：16G.1 画蓝图 → 16G.2 给"改代码"的手 → 16G.3 给"动手验证"的眼睛 → 16G.4 给"复杂环境 + 接进训练"的底座 → 16G.5 真跑一遍验收 → 16G.6 盖章放行。前 4 个是实现，第 5 个是验收，第 6 个是门禁。

1 · 整条线最终要实现什么

16G.0 已经查清：RepoHarness 不是 toy，但缺"动手验证闭环"(跑定向测试、写复现、跑项目命令、装依赖)和完整的文件操作，而且这些能力还没接进训练目标。16G.1–16G.6 就是把这些缺口逐一补上，并确保每一项新能力都满足三件事：

要满足意思
① 能力到位模型真能跑定向测试、写复现、改多文件、(受控)装依赖 —— 达到 mini-SWE-agent 的动态诊断下限、接近 Claude Code 的分层工具
② 不能作弊靠确定性边界(沙箱/路径隔离/无网络/共享依赖只读/题间重置/AST 扫描)堵死偷答案、改测试、污染环境等口子 —— 不是靠削弱能力
③ 进得了训练每个工具动作都能投影进 trajectory / TrainingView / final.patch / reward / export —— "工具能跑通"不算完成，"模型能从中学到正确用法"才算

最终交付物 = 四档工具 profile(冻结) + 一个放行门禁(决定能不能进 Stage 17B 真实数据冻结 / Stage 20 warm-start / Stage 21 正式 RL)。

3 · 先立一个贯穿全程的例子

例子任务：某项目的 parse_config() 函数，在配置缺少 timeout 字段时会直接 KeyError 崩溃。要求：改成"缺字段时用默认值"。这个修复需要：改 config_parser.py（主逻辑）+ defaults.py（加默认常量）两个文件，再新建一个测试 tests/test_config_parser.py，而且项目要先 pip install -e . 才能跑测试。

下面每个阶段，我都会说"这一阶段让模型在这个例子里多了什么能力"。把 6 段连起来，你就能看到整个修复闭环是怎样被一步步补全的。

4 · 逐阶段详解

16G.1 · 画蓝图 设计，不实现

建立一个"工具能力 registry"——把后面所有工具的规则先定死，避免实现时散落在各处、各写一套。
做什么
回答 5 个问题：每个工具属于哪档 profile？对应哪个 capability_id？它的输入/输出/拒绝/artifact/权限/训练投影语义是什么？哪些调用能进 policy loss？哪些只能当诊断/负样本/quarantine。并定下四档 profile(见第 5 节)。
用例子说 这一步还没给模型任何新能力。它是在"图纸"上写死：「run_public_command 属于 swe_public_core、能进训练；persistent shell 只属于 extended、core 默认不给」。后面 16G.2–16G.4 实现工具时，必须照这张图纸来，不能临时发挥。
产出
tool_registry_contract.json / profile_taxonomy.json / training_eligibility_gate_spec.json + 一个机器验收器(能检查"27 条能力是否全映射、17 条阻塞项是否都有归属阶段、每个工具是否都有训练投影规则")。
承上启下
承接 16G.0 的 27 条对照；为 16G.2–16G.4 提供"必须照着实现"的契约。关键验收：防止"工具存在但没有训练投影"这种静默退化。

16G.2 · 给模型"改代码的手" 实现 · P0

补齐结构化文件和补丁操作，让模型能高效、可审计地改多文件、建/删/移文件。
做什么
新增 apply_patch(多文件编辑)/write_file(覆盖写)/delete_file/move_file/mkdir，并保证这些改动都进 final.patch、official prediction、TrainingView 投影。拆 4 个子阶段：2A schema → 2B 行为实现 → 2C patch 投影 → 2D 任务状态(非阻塞)。
用例子说 现在模型能：用 apply_patch 一次改 config_parser.py + defaults.py 两个文件，再用 create_file 新建 tests/test_config_parser.py。改完这三处都会干净地出现在 final.patch 里（临时文件/备份不会混进去）。在此之前只有 exact-replace 的 edit_file，多文件改起来很笨。
产出
可执行 probe 证明：多文件 patch 进 final.patch、建/删/移进 git diff、patch 失败给可学习的 reason_code、临时目录不被误纳入、hidden verifier/gold patch 仍读不到。
承上启下
它是后面的基础 —— 16G.3 的"写复现脚本"也要先能写文件。注意：完整的"测试声明 ↔ 真实事件"交叉校验留到 16G.4D，这里只负责把动作投影成结构化事实。

16G.3 · 给模型"动手验证的眼睛" 实现 · P0 · 最关键

让 RepoHarness 不再弱于 mini-SWE-agent 的动态诊断能力 —— 但用受控公开命令，不开裸 shell。
做什么
新增三个工具，共用同一套执行底座(cwd/超时/输出脱敏/artifact/拒绝语义)：run_public_command(安全公开命令)、run_project_test(项目测试路由，支持定向测试)、scratch_python(临时复现脚本)。拆 4 子阶段，底座(3A)必须先做，否则不准扩命令集。
用例子说 模型改完代码想验证：① 用 run_project_test("tests/test_config_parser.py::test_missing_timeout") 只跑这一个新测试（不是全跑）；② 改之前先用 scratch_python 写 3 行 parse_config({}) 复现崩溃、确认 bug 真存在。这正是真实程序员"先复现→再改→再针对性验证"的循环。在此之前 run_tests 没参数，模型只能全跑或不跑。
产出
probe 证明：能跑定向测试拿到 stdout/stderr/exit code、scratch 产物不污染 final.patch、被拒命令给可学习恢复路径、碰 hidden verifier/gold patch/.git 作弊路径会 deterministic hard fail、至少一个 mini-SWE 风格闭环能用结构化工具走通。
承上启下
这阶段只用"依赖已预置好"的环境；真正的"装依赖"留到 16G.4A。三个工具共用一套语义，避免各写一套不兼容规则。

16G.4 · 复杂环境 + 把一切接进训练 实现 · P0 · 最重

收口最复杂、阻塞最多(9 条)的能力。因为重，拆成 4 个子阶段执行。
做什么
4A 依赖安装 + 共享依赖只读 + 每题私有 overlay；4B 受控持久诊断 shell 进 extended profile(题间 reset)；4C 权限拒绝恢复 + hooks + 工具生命周期审计 + quarantine；4D 把工具动作接进 final answer / verifier / reward metadata / TrainingView / export。
用例子说 例子里项目要先 pip install -e . 才能跑测试 —— 4A 给受控依赖安装(装进这道题的私有 overlay，不污染别题)。如果模型敲了被拒的命令，4C 给它"换 run_project_test 试试"这种可学习提示。模型最后说"我跑了测试、通过了"，4D 确保这句话能和真实 tool event 对上(不能空口白话)，并把"测试通过"接进 reward。
产出
probe 证明：core 不暴露持久 shell、extended 的持久 shell 题间 reset 且可审计、共享依赖不被写污染、各种拒绝/超时/截断/quarantine 都进 audit、final answer 测试声明能和真实事件对齐、各处工具投影一致。
承上启下
边界很重要：16G.4 只产出"结构化 facts + 接进 reward metadata"，具体的 reward 数值/权重设计留给后续 Stage 19，不在这里展开。这是个好的职责切分。

16G.5 · 真跑一遍验收 验收，不实现

实证验证：前面四个阶段改完后，RepoHarness 是否真的接近目标工具环境。不再是"第一次对比"(那是 16G.0 干的)。
做什么
拿一批小任务真跑，从 4 个维度 probe：① Claude Code 分层工具能力；② mini-SWE 动态诊断闭环；③ 安全边界(碰不到答案/隐藏测试/历史/宿主路径)；④ 训练投影(动作进没进 TrainingView/reward/export)。
用例子说 拿"修 parse_config"这类真任务跑：确认模型能完整走通 复现(scratch)→定位(grep/read)→改(apply_patch)→装依赖(4A)→跑定向测试(run_project_test)→看 diff→收口，并且全程读不到标准答案、隐藏测试。验收看的是"模型真能解题"，不是"工具存在"。
产出
5 份 probe 报告(parity summary / CC 能力 / mini-SWE 能力 / 训练投影 / 安全边界)。硬规则：任意一个 P0 阻塞能力没过 → 整体 status=failed，且 16G.6 必须把训练放行全部置 false。

16G.6 · 盖章放行 门禁，不实现

纯冻结 + 证据汇总。不新增能力、不改语义。把通过验收的工具面"冻"成正式 profile，并决定能不能进真实训练。
做什么
冻结四档 profile 的最终字段和工具集；定下主训练默认 profile(预计 swe_public_core)；定下每个工具的训练投影策略和所有 hard-fail 安全边界；用 sha256 绑定 16G.1/16G.4/16G.5/16G.0 的证据。
用例子说 它判定：「用 swe_public_core 这套工具产生的'修 parse_config'轨迹，算合格的训练数据」，然后输出一个放行门禁 ↓
{
  "stage17a_schema_only_allowed": true,        // 纯 schema 设计：放行
  "stage17b_real_data_freeze_allowed": <真/假>,  // 真实数据冻结
  "stage20_warm_start_data_generation_allowed": <真/假>,
  "stage21_formal_rl_allowed": <真/假>
}
承上启下
如果发现缺口，只能把 gate 置为"不放行"并退回对应 owner 阶段 —— 它自己不修。这是整个 16G 通往真实训练(Stage 17B/20/21)的最后一道闸门。

5 · 贯穿全程的"四档 profile"是什么

profile = "一套工具组合"。同一个 harness 可以按任务/用途切换不同 profile。这是 16G.1 定、16G.6 冻结的核心概念：

profile包含什么用途
safe_structured_only只读/搜/编辑 + final patch（最低风险）低风险基线，最保守
swe_public_core 主训练默认结构化文件工具 + run_public_command + run_project_test + scratch_python（无状态、无持久 shell）主 SWE 强化学习默认用它
swe_public_extendedcore + 受控持久诊断 shell + 长会话 + 复杂环境特定任务 / replay / 偏好数据 / 诊断增强
redteam_restricted受限组合，专门压力测试泄漏/越权/拒绝恢复的安全验证，不做主训练默认
为什么分档：主训练(core)要干净可复现，所以用无状态结构化命令、不放持久 shell；真需要持久会话的复杂任务走 extended；安全压力测试单独用 redteam。这样"能力"和"可控/可复现"两头都能兼顾 —— 这正是你之前定的方向。

6 · 为什么是这个顺序 + 为什么拆子阶段

顺序的逻辑

  • 先画蓝图(16G.1)再实现 —— 避免回到"凭感觉补工具"，每个工具实现都能追溯到契约。
  • 先给手(16G.2)再给眼睛(16G.3) —— 写复现脚本/建测试都要先能写文件，文件能力是基础。
  • 最后做最重的环境+收口(16G.4) —— 依赖/持久 shell/训练 linkage 最复杂、依赖前面所有，放最后。
  • 先实现(1–4)→再验收(5)→再放行(6) —— 不验收不放行，不放行不进真实训练。

"底座先行"的拆分纪律（防止阶段过重）

16G.3 和 16G.4 阻塞能力多、容易做成一个不可复核的大改，所以拆成 A/B/C/D，并立了两条硬规则：

  • 16G.3A 共享执行底座(拒绝语义/输出脱敏/私有路径隔离)没做好，不准进 3B–3D 扩命令集。
  • 16G.4A 依赖环境隔离没做好，不准进 4B 的持久 shell；16G.4D 训练投影没做好，不准进 16G.5 验收。
这条拆分正好回应了我之前的提醒：16G.4 一个阶段背 9 条阻塞太重。这版计划把它拆成 4A/4B/4C/4D，并用"底座先行"挡住"地基没打好就往上盖"。这是个好设计。

7 · 我的几点观察（计划看着扎实，几处提醒）

  • 方向完全对齐我们之前的讨论：结构化优先、持久 shell 归 extended、依赖用每题私有 overlay、reward 数值设计留给 Stage 19、16G.4 拆子阶段。这版计划把这些都吸收了。
  • 16G.3 是"能不能成"的关键，16G.4 是"最重"的。真正动手时，这两阶段最需要你/我盯：16G.3 看 run_public_command 的安全白名单和拒绝恢复是否到位；16G.4 看持久 shell 的题间 reset 和依赖 overlay 隔离是否真的确定性。
  • 一个值得盯的点：计划说"安全边界够用"很多处依赖确定性策略，但 16G.3/16G.4 一旦真加了能跑命令的新工具，必须用对抗性 probe(redteam_restricted)真去试越权/泄漏，而不是只靠静态扫描声明安全。16G.5 的"安全边界 probe"应承担这个。
  • 16G.6 是最后闸门：它只盖章不修复，发现问题就退回。所以前面每一阶段的 probe 质量决定了 16G.6 能不能放行 —— 别让任何一阶段"看起来过了"但 probe 是走过场。
总结：这是一份分工清晰、顺序合理、把"重阶段"拆开、把"安全/可复现/可训练"都钉进验收的计划。它最终交付的是一套冻结的工具 profile + 一个放行门禁，让 RepoHarness 从"能看会改但不会验证"变成"接近 Claude Code 的、可审计可训练的真实 SWE 工具环境"。下一步就是按这个计划进 16G.1，从画蓝图开始。
