## 最终主算法：BS-Chunk-DAPO

### 1. 基础 RL 底座：DAPO，而不是 RLOO / PPO-from-scratch

底座用 DAPO/GRPO-style group policy gradient。原因是它和 verl 结合最自然：DAPO 文档里已经有 separated clip epsilons，也就是 Clip-Higher；有 group filtering，用 `filter_groups.enable=True` 过滤同一 prompt 下全 0 或全 1 的无梯度 group；还有 flexible loss aggregation 和 overlong reward shaping。([Verl Documentation][2])

你的主算法不应该说成“我实现了一个全新的 RL 算法”，而应该说成：

> 我基于 DAPO 做了 SWE agent long-horizon adaptation：把原本 token/trajectory 粒度的 advantage 改成 tool-cycle chunk reward-to-go，并把 async staleness、rollout log-prob、LoRA adapter version、tool-state-safe partial rollout 都放进 batch schema 和训练诊断中。

这句话对基座团队面试官更有吸引力，因为它同时命中 **RL algorithm、agent environment、async infra、credit assignment、training diagnosability**。

### 2. Chunk 定义：不要做 token chunk，做 tool-cycle chunk

一个 episode 是一个 SWE issue 的完整 agent rollout。把它切成若干 chunk：

```text
chunk k = 从一次 assistant 生成开始
          到下一次工具调用返回结束
          或到 final patch / final answer 结束
```

例如：

```text
c1: assistant 决定 grep / search + tool 返回
c2: assistant 读取相关文件 + tool 返回
c3: assistant 生成 patch / edit + tool 返回
c4: assistant 运行测试 + tool 返回
c5: assistant 根据失败测试二次编辑 + tool 返回
c6: assistant rerun tests + final submit
```

PDF 里也建议先不要做最细 token chunk，而是把 chunk 定义为 assistant 输出到工具调用完成或最终 patch/final answer；如果日志还不稳定，就退化成 assistant-turn 级。

这点非常重要：你不是在做“每个 token 一个动作”的 RL，而是在把 SWE agent 的真实决策单位对齐到“读文件 / 搜索 / 编辑 / 跑测 / 修复 / 提交”这些语义动作。

### 3. Reward 设计：terminal 为主，process / efficiency 只做辅助

我建议正式训练的 reward 这样设计：

```text
R_total = w_T * R_terminal
        + w_P * R_process
        + w_E * R_efficiency
        + R_overlong
```

正式 14B 一次训练时，权重不要太激进：

```text
前 20% steps:  w_T=0.75, w_P=0.15, w_E=0.10
中间 50%:      w_T=0.85, w_P=0.10, w_E=0.05
最后 30%:      w_T=0.90, w_P=0.07, w_E=0.03
```

`R_terminal` 是主信号：

```text
+1.0  issue resolved / verified tests pass
+0.2  patch applies and no regression, but not fully resolved
 0.0  no useful patch
-0.2  invalid patch / patch cannot apply
-0.4  timeout / repeated loop without progress
```

`R_process` 尽量用 harness 可确定计算的规则，不要一上来用 LLM-as-judge：

```text
+0.04  根据 traceback / test failure 读取相关文件
+0.05  生成非空且可 apply 的 patch
+0.04  edit 后运行相关测试
+0.04  根据测试失败信息进行二次修复
-0.05  重复相同 search / grep / read，无新增信息
-0.08  空 edit / no-op patch
-0.10  invalid tool schema / 工具调用格式错误
-0.10  未读取相关文件就盲目大改
```

`R_efficiency` 只做小权重、强 cap，避免 premature stop：

```text
+0.03  solved 且 tokens/turns 低于同 prompt group 的 solved median
-0.02  每次明显重复测试 / 重复搜索
-0.05  接近 timeout
-0.10  timeout
```

关键是：**efficiency reward 不能奖励“短但没解出来”**。只有在 solved 或至少 patch 有进展时，才允许给少量效率正分。否则模型会学会快速放弃。

### 4. Chunk-level reward-to-go 与 advantage

对每条轨迹 `τ_i = [c_i1, c_i2, ..., c_iK]`，每个 chunk 有一个局部 reward：

```text
r_i,k = process_i,k + efficiency_i,k
```

最后一个 chunk 额外加 terminal：

```text
r_i,K += terminal_i
```

然后对 chunk 算 reward-to-go：

```text
G_i,k = r_i,k + γ r_i,k+1 + γ² r_i,k+2 + ...
```

可以先用 `γ = 1.0`，如果轨迹很长再试 `γ = 0.97~0.99`。对同一个 prompt 的 `n=4~6` 条 rollout，把所有 chunk return 做 group normalization：

```text
A_i,k = normalize_group(G_i,k)
A_i,k = clip(A_i,k, -3, 3)
```

然后把这个 chunk advantage 扩展到该 chunk 内所有 assistant tokens：

```text
for token t in assistant_tokens(c_i,k):
    advantage[t] = A_i,k

for tool observation tokens:
    loss_mask[t] = 0
```

为了防止长 chunk 支配 loss，loss 聚合不要直接 token-mean，而是：

```text
episode_loss = mean_k mean_{t in assistant_tokens(c_k)} token_loss_t
batch_loss   = mean_episode episode_loss
```

也就是 **chunk-equal weighting**。这就是你的主要算法创新点之一：不是简单把同一个 trajectory reward 广播到所有 token，而是让每个 tool-cycle 决策段有自己的 return-to-go 和 advantage。

### 5. Policy loss：用 DAPO clip，但 advantage 来自 chunk

每个 assistant token 的 ratio：

```text
ratio_t = exp(logπθ(a_t|s_t) - old_logprob_t)
```

在 fully async 下，`old_logprob_t` 应该来自 rollout 侧，而不是训练侧重算。verl 文档明确说明 fully async 中默认使用 rollout 生成的 old log-prob，因为 log-prob 必须和 rollout 参数版本、tokens 对齐；文档还说明 `bypass_mode=True` 默认使用 rollout log-prob。([Verl Documentation][1])

loss 使用 DAPO/PPO-style clipped objective：

```text
loss_t = max(
    -A_chunk * ratio_t,
    -A_chunk * clip(ratio_t, 1 - ε_low, 1 + ε_high)
)
```

建议起始：

```text
ε_low  = 0.2
ε_high = 0.28
```

这和 DAPO 文档中的 Clip-Higher 配置一致。([Verl Documentation][2])

### 6. Async staleness 控制：这是你和普通 RL 复现的区别

你要把每条 trajectory 记录这些字段：

```text
prompt_id
episode_id
adapter_version
rollout_policy_version
old_logprobs
turn_offsets
chunk_offsets
chunk_type
tool_state_hash
safe_interrupt_point
terminal_result
process_rewards
efficiency_rewards
```

训练器只消费满足下面条件的样本：

```text
current_adapter_version - rollout_adapter_version <= K
staleness_ratio <= 0.25  # 起步
tool_state_hash valid
partial rollout cut happens only at safe boundary
```

verl fully async 文档里 `staleness_threshold` 就是 freshness control；文档也解释了 `staleness_threshold=0` 接近同步训练，`>0` 是异步训练，并建议不要让过期样本太多影响训练准确性。([Verl Documentation][1]) 你可以把这个设计写成：

> Bounded-staleness async scheduling：允许异步吞吐收益，但通过 adapter_version、rollout log-prob、safe tool boundary 和 stale-sample rejection 保证 policy update 不被过期轨迹污染。

这是非常适合简历的点，因为它不是单纯“我会调 verl”，而是你理解 async agent RL 的数据正确性问题。

## 一个具体例子

假设任务是：

```text
Issue: tests/test_parser.py::test_empty_config 失败。
期望 parser 在空 config 时返回 default_config，而不是抛 KeyError。
```

模型一次 rollout 产生 6 个 chunk：

| chunk | 行为                                  |                    局部 reward |
| ----- | ----------------------------------- | ---------------------------: |
| c1    | 读 failing test 和 traceback          |                        +0.04 |
| c2    | grep `parse_config` 并打开相关文件         |                        +0.04 |
| c3    | 第一次 edit，但 patch 只处理了 None，没处理 `{}` |                        +0.02 |
| c4    | run targeted pytest，仍失败             |                        +0.01 |
| c5    | 根据失败信息二次 edit，补上 `{}` case          |                        +0.08 |
| c6    | rerun test pass，提交 patch            | +1.00 terminal +0.04 process |

如果只用 trajectory-level terminal reward，那么 c1 到 c6 所有 assistant tokens 都拿到接近同样的正 advantage。模型无法知道 c5 的“根据测试失败二次修复”比 c3 的“不完整 edit”更关键。

用 chunk RTG 后：

```text
G_c6 = 1.04
G_c5 = 0.08 + 1.04 = 1.12
G_c4 = 0.01 + 0.08 + 1.04 = 1.13
G_c3 = 0.02 + 0.01 + 0.08 + 1.04 = 1.15
...
```

如果只这样算，前面的 chunk 仍然都很高，所以我建议再加一个 **局部 process delta / bad-action penalty**。例如 c3 的 incomplete patch 在测试失败后被标记为 `edit_incomplete=-0.05`，c5 被标记为 `test_feedback_fix=+0.08`。这样同样 resolved 的轨迹里，模型更倾向学习“读失败信息 → 有针对性二次修复”，而不是单纯学会“随便 edit 也能最终 solved”。

再看同一个 prompt 下 4 条 rollout：

| rollout | 结果                              | 总 reward |
| ------- | ------------------------------- | -------: |
| r1      | 6 chunks resolved，测试通过          |    +1.12 |
| r2      | 8 chunks resolved，但重复 search 很多 |    +0.93 |
| r3      | 生成 patch 但没解决                   |    +0.12 |
| r4      | timeout，无有效 patch               |    -0.45 |

group normalization 后，r1/r2 的关键修复 chunk 是正 advantage，r3 中“读对文件但 patch 不完整”的 chunk 可能是小正或接近 0，r4 的重复 search / timeout chunks 是负 advantage。这样训练信号比纯 0/1 terminal reward 丰富很多，但 terminal reward 仍然主导，不会把模型带偏。

## 1. DAPO 风格过滤与长度控制具体怎么做

这里的“风格过滤”不是文风过滤，而是 **DAPO-style group filtering / dynamic sampling**。verl 的 DAPO 文档里，`filter_groups.enable=True` 会过滤掉同一 prompt 下所有 rollout 的某个 metric 完全一样的 group，例如 `acc` 全 0 或全 1；trainer 会继续采样，直到有足够 qualified groups 或达到 `max_num_gen_batches`。([Verl][1]) 你上传的 PDF 也建议 SWE 不要只用 `acc`，而应考虑 `seq_final_reward` 或终局 reward + process reward 的混合过滤指标。

对 SWE agent，我建议用**三层过滤**。

### 第一层：硬过滤，直接不进训练

这些样本不是“负样本”，而是**坏数据**，最好只进 diagnostics，不进 RL loss：

```text
- rollout 没有完整终止，trajectory 被截断在 tool call 中间
- tool observation 缺失或 tool_state_hash 不一致
- patch apply 失败，且失败来自 harness/parser，而不是模型真实错误
- logprob / token / mask 对不齐
- old_logprob 缺失
- adapter_version 超过 staleness gate
- context 被硬截断，导致后半段 assistant action 不完整
```

对这类样本设置：

```python
sample_weight = 0.0
use_for_training = False
use_for_diagnostics = True
```

### 第二层：DAPO group filtering，过滤没有相对梯度的 prompt group

假设每个 prompt 采样 `n=4` 条 rollout。

```python
group = [
  rollout_1, rollout_2, rollout_3, rollout_4
]
```

你需要给每条 rollout 一个用于过滤的 `swe_filter_metric`。我建议不要直接用最终 reward，而是先 bucket 化：

```python
def swe_filter_metric(traj):
    if traj.resolved:
        return 3          # solved
    if traj.patch_applies and traj.ran_relevant_test:
        return 2          # useful partial
    if traj.patch_applies:
        return 1          # weak partial
    if traj.timeout or traj.invalid_tool_rate > 0.3:
        return -1         # bad failure
    return 0              # ordinary failure
```

然后：

```python
def keep_group(metrics):
    return len(set(metrics)) > 1
```

例子：

```text
Group A: [3, 0, 0, -1]  -> keep
Group B: [3, 3, 3, 3]   -> drop for RL
Group C: [0, 0, 0, 0]   -> normally drop
Group D: [2, 1, 0, 0]   -> keep
Group E: [-1, -1, -1, -1] -> hard drop
```

但 SWE 有一个特殊问题：**很多 prompt 在早期全是 terminal=0，但中间行为差异很大**。所以我建议加一个“all-zero rescue quota”：

```python
def keep_all_zero_group(trajs):
    process_scores = [t.process_score for t in trajs]
    has_valid_patch = any(t.patch_applies for t in trajs)
    has_test_run = any(t.ran_relevant_test for t in trajs)
    enough_variance = np.var(process_scores) > 1e-3

    return enough_variance and (has_valid_patch or has_test_run)
```

最终逻辑：

```python
if all_bad_or_corrupt(group):
    drop_group()
elif len(set(swe_filter_metric(t) for t in group)) > 1:
    keep_group()
elif all_terminal_zero(group) and keep_all_zero_group(group) and all_zero_quota_not_full:
    keep_group()
else:
    drop_group()
```

这个设计比单纯 `acc` 全 0 就丢更适合 SWE，因为“读对文件、生成可 apply patch、运行相关测试”这些行为在早期很有训练价值。

### 第三层：compact filtering / overlong filtering

DeepSWE 的公开 recipe 里也用了类似 compact filtering：对达到 max context、generation timeout、max steps 的轨迹 mask loss，而不是把这些轨迹当成普通失败样本训练。([Hugging Face][2]) 这点对你的 harness 很重要，因为 SWE agent 的超长轨迹常常不是“模型做错一个动作”，而是整个 rollout 分布已经坏了。

建议：

```python
if terminate_reason in {
    "max_context",
    "max_env_steps",
    "generation_timeout",
    "tool_timeout_without_recovery"
}:
    loss_mask = 0
    log_only = True
```

但如果只是轻微 overlong，没有被硬截断，可以保留并给长度惩罚。

## 长度控制怎么设置

verl DAPO 支持 overlong reward shaping：当输出长度超过 `max_response_length - overlong_buffer.len` 后，惩罚从 0 线性增加到 `penalty_factor`。([Verl][1])

例如：

```yaml
data:
  max_response_length: 65536

reward_model:
  overlong_buffer:
    enable: true
    len: 8192
    penalty_factor: 0.2
```

对应公式大概是：

```python
expected_len = max_response_length - overlong_buffer_len
exceed_len = valid_response_length - expected_len

if exceed_len > 0:
    overlong_penalty = - min(
        exceed_len / overlong_buffer_len * penalty_factor,
        penalty_factor
    )
else:
    overlong_penalty = 0.0
```

也就是说：

```text
max_response_length = 65536
overlong_buffer_len = 8192
expected_len = 57344

len = 57344 -> penalty = 0
len = 61440 -> penalty = -0.1
len = 65536 -> penalty = -0.2
```

除了 token 长度，还要有 SWE agent 专用上限：

```yaml
harness:
  max_assistant_turns: 24
  max_tool_calls: 40
  max_wall_clock_train: 20min
  max_wall_clock_eval: 30min
  max_consecutive_same_action: 2
  max_patch_files: 8
  max_changed_lines: 800
  max_test_rerun_same_command: 2
```

我建议区分：

```text
soft length penalty:
  轨迹完整，但太长 -> 训练，给 penalty

hard length filter:
  轨迹被截断 / tool 状态损坏 / context 爆掉 -> 不训练，只记录
```

fully async 部分，verl 文档里 `staleness_threshold` 是 freshness control，`partial_rollout` 只在 `staleness_threshold > 0` 时生效；文档还建议 `staleness_threshold` 小于 1，避免过多 expired samples 影响训练。([Verl][3]) 所以你的过滤还要加：

```python
if current_adapter_version - rollout_adapter_version > max_staleness:
    loss_mask = 0
```

一个起始配置可以是：

```yaml
actor_rollout_ref:
  rollout:
    n: 4
    calculate_log_probs: true
    multi_turn:
      enable: true
      max_assistant_turns: 24
  actor:
    use_rollout_log_probs: true
    clip_ratio_low: 0.2
    clip_ratio_high: 0.28

algorithm:
  filter_groups:
    enable: true
    metric: swe_filter_metric
    max_num_gen_batches: 4

async_training:
  require_batches: 1
  trigger_parameter_sync_step: 2
  staleness_threshold: 0.25
  partial_rollout: true

reward_model:
  overlong_buffer:
    enable: true
    len: 8192
    penalty_factor: 0.2
```

## 2. Group normalization、chunk 数不一致、IPA 原做法、loss 聚合

### 2.1 GRPO/DAPO 里的普通 group normalization

传统 GRPO/DAPO 是对同一个 prompt 的 `n` 条 rollout 做归一化：

```text
A_i = (R_i - mean(R_1, ..., R_n)) / (std(R_1, ..., R_n) + eps)
```

例如同一个 issue 采 4 条：

```text
R = [1.0, 0.2, 0.0, -0.2]
mean = 0.3
std ≈ 0.435

A = [
  (1.0 - 0.3) / 0.435,
  (0.2 - 0.3) / 0.435,
  (0.0 - 0.3) / 0.435,
  (-0.2 - 0.3) / 0.435
]
≈ [1.61, -0.23, -0.69, -1.15]
```

这是 sequence-level advantage。

### 2.2 chunk-level 时怎么做 group normalization

你的每条轨迹 chunk 数不一致，这是正常的，不需要强行对齐。

设第 `i` 条 rollout 有 `K_i` 个 chunk：

```text
τ_i = [c_i1, c_i2, ..., c_iK_i]
```

每个 chunk 有局部 reward：

```text
r_i,k
```

先算 chunk reward-to-go：

```text
G_i,k = r_i,k + γ r_i,k+1 + γ² r_i,k+2 + ... + γ^(K_i-k) r_i,K_i
```

然后做 **trajectory-equal weighted group normalization**。不要直接把所有 chunk flatten 后普通平均，因为长轨迹 chunk 多，会支配均值和方差。建议：

```text
w_i,k = 1 / K_i
```

于是同一个 prompt 下：

```text
μ_p = (1 / n) * Σ_i Σ_k (1 / K_i) * G_i,k

σ_p² = (1 / n) * Σ_i Σ_k (1 / K_i) * (G_i,k - μ_p)²

A_i,k = clip((G_i,k - μ_p) / (σ_p + eps), -3, 3)
```

这相当于：**每条轨迹在 normalization 里权重相同，每条轨迹内部的 chunk 平分该轨迹权重。**

这比直接：

```text
μ = mean(all chunks from all rollouts)
```

更稳，因为后者会让 30 个 chunk 的超长失败轨迹比 6 个 chunk 的成功轨迹权重大 5 倍。

### 2.3 chunk 不对齐是否不自然？

不对齐并不构成理论问题。Policy gradient 本来就是对实际访问到的 state-action pair 求期望，不要求第 3 个 chunk 和第 3 个 chunk 语义一致。对 SWE 来说，不同 rollout 可能是：

```text
rollout A:
  c1 search
  c2 read file
  c3 edit
  c4 test
  c5 submit

rollout B:
  c1 read issue
  c2 grep
  c3 read file
  c4 read another file
  c5 edit
  c6 test
  c7 edit
  c8 submit
```

你不应该做：

```text
把所有 c1 对齐、所有 c2 对齐、所有 c3 对齐
```

因为 c3 在 A 里是 edit，在 B 里可能还是 read。

更合理的是：

```text
同 prompt 下，把每个 chunk 看成一个实际发生的语义 action；
用 reward-to-go 给它 credit；
用 trajectory-equal 权重避免长轨迹支配；
必要时按 chunk_type 做分层归一化。
```

如果你担心 search chunk 和 edit chunk 混在一起比不公平，可以加一个可选版本：

```python
chunk_type in {"localize", "read", "edit", "test", "repair", "submit"}
```

然后：

```text
A_i,k = normalize within same prompt and same chunk_type
```

但 `n=4~6` 时，同类型 chunk 数可能太少，所以我建议第一版不用 type-stratified normalization，只记录 type 方便分析。

### 2.4 IPA 原报告是怎么做的？

IPA/ROME 那篇把多轮 agent 形式化成 **Chunked MDP**：state 是 chunk 开始前的完整交互历史，action 是一个 variable-length token sequence，直到 tool invocation 或 task completion；reward 是稀疏终局测试通过信号，discount 在 chunk 层面应用。公开文本明确说，chunk 把导致环境转移的一组 token 聚合起来，使优化 horizon 对齐到有意义的 intervention。([arXiv][4])

IPA 的关键不是“对齐第几个 chunk”，而是三件事：

第一，**chunk-level discounted return**。它说明 token-level discount 在几千 token 长轨迹里会指数衰减，而 chunk-level discount 可以在语义边界上重新引入 temporal credit；同一个 chunk 内所有 token 共享同一个 scalar weight。([arXiv][4])

第二，**chunk-level importance sampling 和 mask**。IPA 对一个 chunk 内所有 token 的 ratio 做几何平均式 importance ratio，用来减弱单个 outlier token 对整个 chunk ratio 的影响；同时把 masking 从 token 级提升到 chunk 级。([arXiv][4])

第三，**initialized resampling / sequential rollback**。它从 expert-like trajectory 的后部 chunk 开始初始化环境，让模型先学尾部关键步骤，再逐步往前 rollback；还提出 parallelized initialization 来并行选择多个 anchor chunk。([arXiv][4])

你的当前版本不需要完整 sequential rollback。你上传的 PDF 也建议，如果环境还不支持 checkpoint/rollback，就先做 chunked return + chunked advantage + chunk-aware reward logging。

### 2.5 是否还有其他公开做法？

有，比较接近的是 **turn-level reward design**。这类工作把多轮 agent 建成 turn-level MDP，在 GRPO/PPO 中加入 turn-level reward，从 trajectory-level credit 改为更细粒度的 turn-level credit；它们还区分 verifiable reward 和 LLM-as-judge reward。([arXiv][5])

所以你的设计可以这样定位：

```text
trajectory-level GRPO/DAPO
    ↓
turn-level reward / advantage
    ↓
tool-cycle chunk-level reward-to-go / advantage
    ↓
完整 IPA：chunk-level IS + chunk mask + initialized resampling
```

你的简历项目最好停在第三层，完整 IPA 作为 future work。

### 2.6 loss 聚合是算术平均，不是几何平均

我前面写的：

```text
episode_loss = mean_k mean_{t in assistant_tokens(c_k)} token_loss_t
batch_loss   = mean_episode episode_loss
```

是**两次算术平均**，不是几何平均。

具体是：

```python
chunk_loss_i_k = token_loss[tokens_in_chunk].mean()
episode_loss_i = mean(chunk_loss_i_1, ..., chunk_loss_i_K)
batch_loss = mean(episode_loss_1, ..., episode_loss_B)
```

也就是：

```text
L_i,k = (1 / |c_i,k|) * Σ_t L_t

L_i = (1 / K_i) * Σ_k L_i,k

L_batch = (1 / B) * Σ_i L_i
```

这里没有几何平均。

几何平均只适合用在 **chunk-level importance ratio** 里：

```text
ratio_chunk = exp(mean_t [logπ_new(a_t|s_t) - logπ_old(a_t|s_t)])
```

这个在概率空间等价于 token ratios 的几何平均。IPA 也是在 chunk-level IS 里采用类似几何平均思路，而不是对 loss 做几何平均。([arXiv][4])

## 3. 不用 LLM-as-judge 时，process reward 怎么设计成可计算规则

我建议把 process reward 写成一个**状态机**，不要写成孤立规则。

SWE agent 的合理路径大概是：

```text
LOCATE -> UNDERSTAND -> PATCH -> VERIFY -> REPAIR -> SUBMIT
```

你的 harness 每个 chunk 都能看到：

```text
- assistant message
- tool name
- tool arguments
- tool stdout/stderr
- 当前 git diff
- 当前已读文件集合
- 当前已运行测试集合
- 当前失败测试集合
- 当前 traceback / error message
- terminate reason
```

因此可以完全 rule-based。

### 3.1 先构建可计算特征

从 issue、test、traceback 中抽取：

```python
candidate_files = set()
candidate_symbols = set()
candidate_tests = set()
error_keywords = set()
```

具体规则：

```python
# traceback 文件路径
r'File "([^"]+\.py)"'

# pytest nodeid
r'([\w/.-]+\.py)::([\w\.\[\]-]+)'

# test function
r'\btest_[A-Za-z0-9_]+\b'

# class / function-like symbol
r'\b[A-Z][A-Za-z0-9_]{2,}\b'
r'\b[a-z_][a-z0-9_]{3,}\b'

# exception
r'\b(KeyError|TypeError|ValueError|ImportError|AttributeError|AssertionError)\b'
```

从每次 action 中抽取：

```python
action_type      # search/read/edit/bash/test/submit
action_signature # canonicalized tool + args
obs_hash         # normalized observation hash
diff_hash        # current git diff hash
changed_files
read_files
ran_tests
failed_tests
```

### 3.2 过程奖励表

建议每个 chunk 的 process reward 控制在：

```text
r_process_chunk ∈ [-0.10, +0.10]
episode process sum clip 到 [-0.30, +0.30]
```

否则 process reward 会压过 terminal reward。

| 行为                  | 可计算条件                                                                  | reward |
| ------------------- | ---------------------------------------------------------------------- | -----: |
| 合法工具调用              | JSON/function call 可 parse，tool name 合法，参数合法                           |  +0.01 |
| 读取相关文件              | read/view 的文件在 `candidate_files`，或文件内容包含 `candidate_symbols`           |  +0.04 |
| 有效 search           | search query 命中 traceback symbol / failing test / error keyword，且返回新信息 |  +0.03 |
| 生成有效 patch          | `git diff` 非空、可 apply、不是纯 whitespace、changed file 已被 read              |  +0.05 |
| edit 后运行相关测试        | 当前 diff 非空后运行 targeted pytest / failing test                           |  +0.04 |
| 测试反馈修复              | 在 failed test 之后 edit，且 edit 文件/符号和 failed traceback 有 overlap         |  +0.04 |
| fail count 下降       | 同一测试集合下失败数下降，或原 exception 消失                                           |  +0.05 |
| submit 前验证          | submit 前至少运行过相关测试，且没有明显 regression                                     |  +0.03 |
| invalid tool schema | tool call parse fail / 参数缺失 / forbidden command                        |  -0.10 |
| 重复 search/read      | 同一 action_signature 重复，obs_hash 没变，diff_hash 没变                        |  -0.05 |
| no-op patch         | edit 后 diff 为空或 patch 等价于空改动                                           |  -0.08 |
| blind edit          | 未 read 目标文件就 edit，且不是新建文件场景                                            |  -0.10 |
| tests-only hack     | 非测试修复任务中只改 tests                                                       |  -0.15 |
| 过大 patch            | changed files / changed lines 超阈值                                      |  -0.05 |
| premature submit    | 无 patch 或无验证直接 submit                                                  |  -0.10 |

### 3.3 规则实现示例

```python
def score_chunk(chunk, state):
    r = 0.0

    # 1. tool schema
    if not chunk.tool_call_valid:
        return -0.10

    if chunk.action_type in {"read", "view"}:
        file = chunk.args.get("file")
        if file in state.candidate_files and file not in state.read_files:
            r += 0.04
        elif chunk.obs_hash in state.seen_obs_hashes:
            r -= 0.03

    if chunk.action_type == "search":
        q = normalize(chunk.args.get("query", ""))
        if overlaps(q, state.candidate_symbols | state.error_keywords):
            if chunk.obs_hash not in state.seen_obs_hashes:
                r += 0.03
        if chunk.action_signature in state.seen_action_signatures:
            r -= 0.05

    if chunk.action_type == "edit":
        changed_files = get_changed_files_after(chunk)

        if not changed_files:
            r -= 0.08
        else:
            if all(f in state.read_files for f in changed_files):
                r += 0.05
            else:
                r -= 0.10

            if modifies_only_tests(changed_files) and not state.issue_requires_test_change:
                r -= 0.15

            if diff_too_large():
                r -= 0.05

            if state.last_test_failed:
                if overlaps(changed_files, state.last_failed_files) or \
                   overlaps(diff_symbols(), state.last_failed_symbols):
                    r += 0.04

    if chunk.action_type == "bash":
        cmd = chunk.args.get("cmd", "")

        if is_relevant_test_command(cmd, state.candidate_tests, state.changed_files):
            if state.diff_hash != state.last_tested_diff_hash:
                r += 0.04
            else:
                r -= 0.04

        new_fail_count = parse_fail_count(chunk.output)
        if state.prev_fail_count is not None and new_fail_count < state.prev_fail_count:
            r += 0.05

    if chunk.action_type == "submit":
        if not state.has_nonempty_patch:
            r -= 0.10
        elif not state.has_run_relevant_test:
            r -= 0.05
        else:
            r += 0.03

    return clip(r, -0.10, 0.10)
```

### 3.4 关键原则

不要奖励“看起来努力”，只奖励**可验证的状态变化**：

```text
不奖励：模型说“我理解了问题”
奖励：它实际 read 了 traceback 指向的文件

不奖励：模型说“我会运行测试”
奖励：它实际运行了相关 pytest，并且是在 edit 之后运行

不奖励：模型说“我修复了”
奖励：patch 非空、可 apply、测试失败数下降或最终通过
```

还要避免泄漏。process reward 不应该看 gold patch。可以看：

```text
- issue text
- public failing test / reproduction test
- agent 自己运行出来的 traceback
- 当前 git diff
- 当前测试结果
```

不要看：

```text
- 官方 gold patch
- hidden test 的具体内容
- 最终 benchmark answer
```

DeepSWE 公开 recipe 里采用了非常简单的 sparse ORM：patch 在时间限制内通过选定测试给 1，否则 0；这说明 rule-based reward 是可行的，但你的资源比 32B/64H100 小，所以加入小权重 process reward 更现实。([Hugging Face][2])

## 4. 7B 全量微调还是 14B LoRA？warm start、SFT/RL/验证集怎么选？

我的结论是：

**正式结果用 14B LoRA；7B 全量微调用于 smoke / ablation，不适合作为唯一正式主结果。**

原因有三点。

第一，公开 SWE agent RL 的强结果基本不是 7B 规模。DeepSWE 是在 Qwen3-32B 上做 RL，公开称使用 4.5K R2E-Gym 问题、64 H100、6 天训练，在 SWE-bench Verified 上 pass@1 42.2%，TTS 到 59%。([一起智能][6]) R2E-Gym 也用 32B Qwen 系模型和高质量轨迹训练，报告 34.4% Pass@1；SWE-Gym 也强调训练和推理 compute 是主要瓶颈。([R2E-Gym][7]) 你做 7B 全量，很可能工程很扎实但绝对分数不好看。

第二，8×96GB 下，SWE RL 的瓶颈不只是模型参数，而是长上下文 rollout、tool 调用、old logprob、异步同步和环境等待。14B LoRA 更容易把资源花在 rollout 数和任务数上，而不是 optimizer state。verl fully async 文档也把 `use_rollout_log_probs`、`staleness_threshold`、`partial_rollout` 这些作为关键参数，说明系统吞吐和样本 freshness 是核心问题。([Verl][3])

第三，简历叙事上，14B LoRA 更像一个可复现的 agentic RL infra 项目：你可以说自己在 8×96GB 上做了 14B SWE agent RL，而不是只在 7B 上做 toy-scale full finetune。

### 推荐模型

**首选：Qwen2.5-Coder-14B-Instruct**

理由：dense、code-specific、14.7B、长上下文 131,072 tokens、vLLM/SGLang 生态成熟。模型卡也明确说它增强了 code generation、code reasoning、code fixing，并强调 real-world Code Agents。([Hugging Face][8])

**备选：Qwen3-14B**

理由：agent/tool 能力和 thinking / non-thinking 切换更强，14.8B，原生 32K、YaRN 到 131K；但它不是专门 coder 模型。([Hugging Face][9])

**不建议作为主模型但适合作 teacher：Qwen3-Coder-30B-A3B-Instruct**

它是 MoE，30.5B total、3.3B activated、262K context，适合生成 teacher trajectories 或做强 baseline；但你当前算法主线是 dense 7B–14B，直接上 MoE 会引入额外变量。([Hugging Face][10])

### 是否需要 warm start？

需要。虽然 DeepSWE 证明了 32B 上可以只用 RL 不做 SFT，但它用了更大模型和更多资源。([Hugging Face][2]) 你的 14B + 8×96GB 更应该先做一个小规模 **tool-format + trajectory SFT / rejection finetuning**，再上 RL。

SWE-Gym 公开说明：少于 500 条从 GPT-4o / Claude 3.5 Sonnet 采样的 agent-environment interaction trajectories，就能让 32B OpenHands agent 在 SWE-bench Verified 上有明显提升；它还报告 7B/32B 通过 rejection sampling fine-tuning 在 SWE-bench Lite 上得到自提升。([GitHub][11]) 所以小规模高质量 SFT 很适合你的资源条件。

我建议优先用**你自己的 harness + 强模型生成轨迹**，而不是直接吃公开轨迹。

原因是：



## 相关工作怎么做

最直接相关的是 **ReSum / ReSum-GRPO**。它的核心做法和你的问题非常接近：当长轨迹接近上下文限制时，调用外部 summary tool 压缩历史，然后从 summary state 继续；训练时把一条完整长轨迹自然切成多个 segment，每个 segment 作为一个训练 episode，同时把完整 trajectory 的 advantage broadcast 到同一 rollout 的所有 segment。论文明确说每个 segment 是 individual training episode，trajectory-level advantage 会广播到所有 segment；短轨迹则退化为标准 GRPO。([arXiv][1])

另一个更贴近 SWE 的是 **Context as a Tool / SWE-Compressor**。它把 context management 当成和 edit、bash、submit 同级的工具能力，context workspace 被分成固定任务语义、压缩后的长期记忆、最近高保真交互三部分；它还用 offline trajectory reconstruction 在完整 ReAct 轨迹中插入 context-management tool call，形成可 SFT 的轨迹。这个思路对你的 harness 很有启发：压缩不是“偷偷截断”，而是一个显式状态转换。([arXiv][2])

Anthropic 官方 compaction 文档也支持这个建模：compaction 会在接近 token threshold 时生成 summary block，后续请求会丢弃 compaction block 之前的 message blocks，从 summary 继续。也就是说，压缩后模型真实输入就是“summary + 后续新消息”，而不是完整历史。([Claude Platform][3]) Claude Cookbook 还强调 summary 会有信息损失，应使用 custom summary prompt 保留关键状态，并在自然 phase boundary 处压缩。([Claude Platform][4])

还有 **Context Folding / FoldPO**，它把完成的 subtask fold 成 summary，再继续主任务，并用 process reward 鼓励有效任务拆解和 context management；这说明“折叠子轨迹 → 从摘要继续 → 对折叠行为训练”正在成为长链路 agent 的一个主流方向。([OpenReview][5])

所以你的实现方向应该是：

> **Logical episode 不拆；training sample 拆。压缩事件是 episode 内的 state transition；压缩后的 segment 是新的可训练上下文窗口。**

## 我建议的训练表示

一条 SWE 任务 rollout 可以这样存：

```text
logical_episode_id = django__django-xxxxx
rollout_id = 0
terminal_result = resolved / unresolved / timeout
terminal_reward = 1.0 / 0.0 / -0.2

segment 0:
  visible_context = initial issue + raw interaction until compaction_0
  trainable_tokens = assistant actions before compaction_0

compaction_0:
  summary = external LLM generated compressed memory
  compressed_range = turns 0..18
  summary_model = gpt-4.1 / claude / qwen...
  summary_prompt_hash = ...
  raw_history_hash = ...

segment 1:
  visible_context = system + issue + summary_0 + recent raw turns
  trainable_tokens = assistant actions after compaction_0 until compaction_1

compaction_1:
  summary = updated compressed memory

segment 2:
  visible_context = system + issue + summary_1 + recent raw turns
  trainable_tokens = assistant actions until submit
```

关键点是：**segment 1 的训练输入必须和 rollout 时模型真实看到的输入一致**。如果 rollout 时模型看到的是 `summary_0 + recent turns`，训练时也只能用这个，不能偷偷把 `raw turns 0..18` 拼回来。否则 old logprob、policy ratio、state distribution 都不对。

我会把 batch schema 设计成这样：

```python
{
    "logical_episode_id": "...",
    "prompt_id": "...",
    "rollout_id": 0,

    "segment_id": 1,
    "num_segments": 3,
    "segment_start_turn": 19,
    "segment_end_turn": 34,

    "visible_context_hash": "...",
    "summary_id": "compaction_0",
    "summary_text": "...",
    "summary_model": "...",
    "summary_prompt_hash": "...",
    "compressed_range": [0, 18],

    "adapter_version": 42,
    "old_logprobs": "...",
    "assistant_loss_mask": "...",
    "tool_obs_loss_mask": 0,
    "summary_loss_mask": 0,

    "chunk_offsets": [...],
    "chunk_types": ["edit", "test", "repair"],
    "local_process_rewards": [...],
    "terminal_reward": 1.0,
}
```

这里 `summary_loss_mask = 0` 很重要。因为 summary 是外部 LLM API 生成的，不是你的 policy model 采样出来的 action token。除非你专门训练一个 summarizer，否则不要对 summary 文本本身做 policy loss。

## RL 时应该如何给 reward / advantage

我建议第一版采用 **ReSum-GRPO 风格的 segmented trajectory training + trajectory advantage broadcasting**，然后再叠加你自己的 chunk-level RTG。

### 简单稳定版：trajectory advantage broadcast 到所有 segment

同一个 prompt 采 `n=4` 条 rollout：

```text
rollout 0: resolved, 3 segments, R = 1.00
rollout 1: unresolved but patch applies, 2 segments, R = 0.20
rollout 2: timeout, 4 segments, R = -0.30
rollout 3: invalid patch, 1 segment, R = -0.10
```

先对完整 rollout reward 做 group normalization：

```text
A_i = normalize_group(R_i)
```

然后把 `A_i` 广播给同一 rollout 的所有 segment：

```text
segment_advantage[i, s] = A_i
```

为了防止压缩次数多的轨迹支配训练，segment loss 要加权：

```text
episode_loss_i = (1 / num_segments_i) * Σ_s segment_loss_i,s
batch_loss = mean_i episode_loss_i
```

也就是说，一条 4 段 trajectory 和一条 1 段 trajectory 在 batch 里总权重相同。这个细节非常重要。

### 更贴合你主算法的版本：segment 内做 chunk RTG

对每个 segment 内的 chunk 仍然保留你的 tool-cycle chunk advantage：

```text
segment 1:
  chunk 1 = read relevant file
  chunk 2 = edit patch
  chunk 3 = run pytest

segment 2:
  chunk 4 = read new failure
  chunk 5 = repair patch
  chunk 6 = submit
```

你可以跨 segment 计算 logical episode 级别的 reward-to-go：

```text
G_chunk_5 = r_5 + r_6 + terminal
G_chunk_4 = r_4 + r_5 + r_6 + terminal
...
G_chunk_1 = r_1 + r_2 + ... + terminal
```

但训练输入仍然是分 segment 的：

```text
segment 0 sample:
  input = raw context before compaction_0
  loss = chunks 1..3

segment 1 sample:
  input = summary_0 + recent raw turns
  loss = chunks 4..6
```

这样你既保留了完整 episode credit，又不会违反“压缩后模型没看到原始历史”的事实。

如果你时间很紧，第一版直接做：

```text
trajectory-level normalized advantage -> broadcast 到 segment -> segment 内 token/chunk loss
```

这已经是合理版本。ReSum-GRPO 就是类似逻辑：完整轨迹只算一个 reward，归一化成 trajectory advantage，再广播到所有 segment。([arXiv][1])

## 具体 SWE 例子 1：压缩发生在定位之后

```text
tests/test_config.py::test_empty_env_override 失败。
期望空字符串 env var 被当作 missing，而不是覆盖默认值。
```

```text
  read src/env.py

turn 6-12:
  agent run targeted pytest
  看到 KeyError / AssertionError
  read more files
  grep 返回大量结果

```

压缩前原始历史很长，但 summary 应该长这样：

```text
[Compressed SWE Memory]

- Fix empty env var override behavior. Empty string should not override default config.

Relevant tests:
- tests/test_config.py::test_empty_env_override
- failure: expected default "prod", got ""

- src/config.py: load_config() calls apply_env_overrides()
- src/env.py: apply_env_overrides() currently treats "" as valid override

Important evidence:
- failing env key: APP_MODE=""
- current behavior: os.environ value "" overwrites default
- likely fix: skip override when value is None or ""

Rejected paths:
- YAML parser is not the cause.
- test fixture setup is not the cause.

Current repo state:
- no patch yet

Next step:
- edit src/env.py in apply_env_overrides(), then rerun targeted pytest.
```

训练时切成两条 segment sample：

```text
sample A:
  input = initial issue + raw turns 1-12
  train tokens = assistant 的 search/read/test 动作
  loss_weight = 1 / num_segments

sample B:
  input = system + issue + compressed memory + recent raw turns
  train tokens = assistant 的 edit/test/submit 动作
  loss_weight = 1 / num_segments
```

如果最终 resolved：

```text
rollout terminal_reward = +1
A_rollout = group_normalized(+1)
sample A 和 sample B 都拿到这个 trajectory advantage
```

如果你做 chunk RTG，则 sample B 的 edit/test/submit chunk 会得到更高、更近的 reward-to-go；sample A 的 read/search chunk 也有正信号，因为它们产生了有用的 summary state。

```text
pandas 某个 parser 在空 CSV + dtype 参数下报错。
```

```text
  rerun pytest
  submit
```

这时 summary 必须保留“失败 patch 的状态”，否则后续模型会重复错误：

```text
- parser.py modified to handle empty file path.
```

```text

segment 1:
```

```text
- tests/test_normalizer.py
```

这种情况下，逻辑上仍是一条 trajectory，训练上仍是 segment。更进一步，你可以把“巨大工具 observation 压缩”视为 **observation-level compression**，而不是 whole-history compaction。它更安全，因为它不会改写 assistant 的历史决策，只是把环境返回压成可读 evidence。Anthropic Cookbook 也提到 long-running tool-heavy workflow 中工具结果会持续累积，compaction 会保留关键处理状态但丢失完整工具文本。([Claude Platform][4])

## 你应该怎么修改“长度控制”的说法

你原来的机制确实让上下文理论上不会爆掉，所以我不再建议把重点放在 `max_response_length exceeded -> hard filter`。你的长度控制应改成：

```text
context budget control:
  控制每个 segment 的可见上下文长度

compression budget control:
  控制每条 episode 的 compaction 次数、summary 长度、压缩质量

training correctness control:
  保证训练时使用的 visible_context 和 rollout 时完全一致
```

具体规则：

```text
soft penalty:
  - compaction 次数过多
  - summary 太长
  - 工具输出反复巨大但没有新信息
  - 多次压缩后仍然没有 patch / test progress
  - token per resolved 太高

hard filter:
  - compaction 发生在 assistant response 或 tool call 中间
  - summary API 失败、空 summary、格式不可 parse
  - summary_text 在训练时被重新生成，导致 visible_context_hash 不一致
  - post-compaction segment 缺 old_logprob
  - compressed state 与 repo state 不一致
  - summary 丢失关键状态，导致无法判断当前 diff / 已运行测试 / 失败 traceback
```

也就是说，原来的“超长 hard filter”变成了 **compaction-state hard filter**。

最近的 Context Codec 工作也提出类似观点：长上下文不是单纯 token，而是一组需要保留的 commitments，包括目标、约束、决策、工具结果、证据和 artifacts；它建议把这些压缩成 source-grounded semantic atoms，并用 critical atom recall 等指标检查压缩质量。([arXiv][6]) 你的项目可以不实现完整 Context Codec，但可以借鉴“关键原子事实保留率”做 summary verifier。

## summary quality 怎么验，不用 LLM judge 也能做

你可以从 raw history 中抽取一批 critical atoms：

```python
critical_atoms = {
    "issue_keywords": [...],
    "failing_tests": [...],
    "traceback_files": [...],
    "traceback_symbols": [...],
    "files_read": [...],
    "changed_files": [...],
    "current_diff_summary": [...],
    "commands_run": [...],
    "latest_test_result": [...],
    "rejected_hypotheses": [...],
}
```

然后检查 summary 是否覆盖：

```python
summary_quality = (
    0.20 * recall(failing_tests)
  + 0.20 * recall(traceback_files)
  + 0.15 * recall(changed_files)
  + 0.15 * recall(latest_test_result)
  + 0.10 * recall(files_read)
  + 0.10 * recall(issue_keywords)
  + 0.10 * has_next_action
)
```

用法：

```text
summary_quality >= 0.75:
  正常训练

0.50 <= summary_quality < 0.75:
  保留，但降低 sample_weight

summary_quality < 0.50:
  不训练 post-compaction segment，只做 diagnostics
```

这不是给 policy 的 reward，而是**数据质量过滤**。因为 summary 是外部 LLM API 生成的，不应该把 summary 的好坏直接归因给 policy，除非你让 policy 自己决定何时压缩、如何压缩。

## 在 verl 里怎么落地

你的 trajectory store 应该存两套东西：

```text
1. raw_audit_trace:
   完整原始 turn / tool / patch / test / compaction input
   只用于 replay、debug、summary verifier、reward builder

2. train_segments:
   每个 segment 的 exact visible context
   每个 segment 的 assistant output tokens
   每个 segment 的 old_logprobs
   每个 segment 的 masks / chunk offsets / rewards
```

训练 batch 构造时：

```python
for logical_episode in episodes:
    A_episode = compute_group_advantage(logical_episode)

    for segment in logical_episode.segments:
        if not segment.visible_context_hash_ok:
            continue
        if not segment.old_logprobs_ok:
            continue
        if segment.summary_quality < threshold:
            continue

        sample = build_verl_sample(
            prompt=segment.visible_context,
            response=segment.assistant_and_tool_sequence,
            old_logprobs=segment.old_logprobs,
            advantage=A_episode or segment_chunk_advantages,
            loss_mask=assistant_tokens_only,
            sample_weight=1.0 / logical_episode.num_segments,
        )
```

这里 `sample_weight=1.0 / num_segments` 是为了避免“越长、压缩越多的 episode 对 loss 权重越大”。

## 最终推荐方案

你的正式算法可以改名为：

**Compressed-State Chunk-DAPO**

核心定义：

> A SWE rollout is one logical episode, but compaction boundaries create multiple summary-conditioned training segments. Terminal reward and group normalization are computed at the logical episode level; policy loss is computed only on assistant tokens under the exact visible compressed context used during rollout; segment losses are weighted so that each logical episode contributes equally.

实际做法：

```text
1. compaction 只允许发生在 safe boundary：
   tool return 后、下一次 assistant 生成前

2. compaction summary 固化入库：
   不在训练时重新生成

3. post-compaction segment 独立成训练样本：
   prompt = system + issue + summary + recent raw turns

4. raw pre-compaction history 不拼回 post-compaction prompt

5. terminal reward 在 logical episode 级计算

6. advantage 可以先用 ReSum-style broadcast：
   full rollout advantage -> all segments

7. 进阶版本再做 chunk RTG：
   full logical episode chunk rewards -> segment-local token loss

8. summary / tool observation / external API outputs 全部 loss_mask=0

9. segment loss 按 1 / num_segments 加权

10. summary quality 作为 hard filter / sample weight，不作为 policy reward
```

这个处理方式既符合你现在 harness 的真实执行方式，也和 ReSum-GRPO、Cat/SWE-Compressor、Claude compaction 的公开思路一致。它比简单“过滤超长轨迹”更高级：你展示的不只是长上下文截断处理，而是 **compressed-state agent RL 的训练语义对齐**。

## 1. SWE-Gym 是否每题都有 public / hidden tests？

**SWE-Gym 更接近 SWE-bench 格式：它有 hidden verifier 信息，但不等价于每题都有一个显式公开测试列表。**

SWE-Gym 官方说明它有 2.4K 个真实任务，来自 11 个 Python repo，并结合 repository context、executable environments 和 test verification 来训练 SWE agents。([GitHub][1]) Hugging Face 上的 SWE-Gym schema 包含 `patch`、`test_patch`、`problem_statement`、`repo`、`base_commit`、`PASS_TO_PASS` 和 `FAIL_TO_PASS`；其中 `FAIL_TO_PASS` 的 sequence length 最小值显示为 1，而 `PASS_TO_PASS` 可以为 0。([Hugging Face][2]) SWE-bench 官方文档也说明标准实例结构包含 gold `patch`、`test_patch`、`FAIL_TO_PASS` 和 `PASS_TO_PASS` 字段，并明确 gold patch 是“不要看”的解题信息。([SWE-bench][3])

所以对 SWE-Gym，我建议这样理解：

| 项                                      |               是否存在 |   是否给模型看 | 说明                                                   |
| -------------------------------------- | -----------------: | -------: | ---------------------------------------------------- |
| `problem_statement`                    |                  是 |        是 | 这是 agent 的任务描述                                       |
| base repo 里的原始 tests                   |                通常有 |        是 | 模型可以用 bash / file editor 查看和运行                       |
| issue 中提到的 failing test / reproduction |               有些题有 |        是 | 如果 issue 文本提到，那自然可见                                  |
| `test_patch`                           |                  是 |        否 | 应作为 hidden verifier 或 evaluator overlay              |
| `FAIL_TO_PASS`                         | 从 schema 看每题至少 1 个 |        否 | 用于判断修复是否真正解决问题                                       |
| `PASS_TO_PASS`                         |               可能为空 | 否，不直接给列表 | 用于 regression check；测试文件本身若在 repo 中，模型仍可能通过 repo 访问到 |
| `patch`                                |                  是 |        否 | gold solution，绝不能进入 prompt / SFT messages            |

因此，“SWE-Gym 每题都有 hidden test / hidden verifier”基本可以这么用；但“每题都有给模型看的 public failing test”不一定成立。更常见的是：模型看到 issue 和 repo，自己通过搜索、读文件、运行已有测试或写 reproduction script 来定位问题。你不应该把 `FAIL_TO_PASS` 测试名直接塞进 prompt，否则会变成 oracle hint。

## 2. R2E-Gym 是否每题都有 public / hidden tests？

**R2E-Gym 有可执行环境和自动 reward tests，但它不是严格的 SWE-bench `FAIL_TO_PASS/PASS_TO_PASS` 格式。**

R2E-Gym 官方 GitHub 说明它包含 8.1K+ problems、13 个 repo、executable gym environments、unit tests 和自然语言任务描述。([GitHub][4]) 它的论文/说明还强调 SWE-GEN 可以从 commits 构造 executable training environments，而不是依赖人工 PR 或人工 unit tests。([GitHub][4]) Hugging Face 的 R2E-Gym-V1 字段包含 `repo_name`、`docker_image`、`commit_hash`、`parsed_commit_content`、`execution_result_content`、`modified_files`、`relevant_files`、`prompt`、`problem_statement` 和 `expected_output_json`；这些字段里有不少是 oracle 信息，不应该直接给模型看。([Hugging Face][5])

对 R2E-Gym，我建议这样划分：

| 项                                        |     是否存在 | 是否给模型看 | 说明                                  |
| ---------------------------------------- | -------: | -----: | ----------------------------------- |
| `problem_statement`                      |        是 |      是 | 可作为 issue prompt                    |
| repo snapshot / docker env               |        是 |      是 | 模型通过工具探索                            |
| 原 repo 里已有 tests                         | 取决于 repo |      是 | 可以让模型运行                             |
| R2E 自动 reward tests / expected outputs   |        是 |      否 | 只给 reward builder                   |
| `expected_output_json`                   |        是 |      否 | 这很像 verifier answer，不能进 prompt      |
| `relevant_files` / `modified_files`      |        是 |      否 | 文件定位 oracle，除非你专门做 localization SFT |
| `parsed_commit_content` / gold commit 信息 |        是 |      否 | 等价于泄漏 gold patch 线索                 |

所以 R2E-Gym 的“hidden test”更应该被你实现成：**模型提交 patch 后，reward builder 在隔离评测环境里运行 R2E 的 unit tests / expected-output verifier；模型 rollout 过程中看不到这些 verifier 的具体内容。**

## 3. SFT 轨迹是否能说明 harness 必须有哪些工具？

能说明一个很强的共识：**SWE agent 至少需要“文件读写 + bash 执行 + 搜索 + 提交”这几个能力。**

R2E-Gym 论文明确说 AgentHub 使用 4 个最小工具：`file_editor` 用于查看和编辑文件，`search_tool` 用于在文件或文件夹中搜索，`execute_bash` 用于执行非交互 bash 命令，`submit` 用于结束当前轨迹；并且训练过程中不提供 internet 或 browser。([arXiv][6]) R2E-Gym 的 SFT trajectory 数据集也显示，轨迹 prompt 中把 agent 描述为拥有 GitHub issue 和 repository bash environment，并需要完成 file localization、testcase generation、code repair 和 editing 等任务。([Hugging Face][7]) SWE-Gym 的 OpenHands 设置则更简化：它给 base LM 配备 bash terminal 和 file editor，并禁用了 browser。([arXiv][8])

因此你的 harness **最低可用版本**可以是：

```text
file_editor / read+edit
execute_bash
search
finish / submit
```

如果你只保留 `bash + file_editor + finish`，也能跑，因为 `grep`、`rg`、`find`、`pytest` 都可以通过 bash 完成；但我仍然建议保留结构化 `search`，因为它对 RL 日志、process reward、重复搜索检测、chunk 类型标注都很有帮助。

```python
class SWEGymPolicyInputBuilder:
    allow = ["problem_statement", "repo", "base_commit"]
    deny = ["patch", "test_patch", "FAIL_TO_PASS", "PASS_TO_PASS", "hints_text"]

class SWEGymRewardOnlyBuilder:
    use = ["test_patch", "FAIL_TO_PASS", "PASS_TO_PASS"]

class R2EGymPolicyInputBuilder:
    allow = ["problem_statement", "repo_name", "docker_image", "commit_hash"]
    deny = [
        "parsed_commit_content",
        "execution_result_content",

        "relevant_files",
        "expected_output_json",
    ]

    use = ["expected_output_json", "unit_tests", "verifier"]
```

其中 `hints_text` 我建议默认也不要给模型，除非你明确做一个 “with oracle hints” 消融。这样你的训练数据、SFT 轨迹和 RL reward 都能保持一条清晰边界：**模型像真实 SWE agent 一样探索 repo；harness 像 benchmark evaluator 一样隐藏 verifier。**
