① 训练开始前在准备什么

RepoHarness 在 verl 训练前需要为每条 episode准备 3 件东西：

① 干净的源代码副本

每条 episode 不能共享同一个可写目录（不然模型 patch 互相覆盖）。但每次重新 git clone 又太慢。Stage 6 的 Snapshot 解决这件事：源代码复制一次到 snapshot 目录（只读），后续每条 episode 从 snapshot 复制到 lease（独立可写）。

② 安装好依赖的虚拟环境

每次 episode 跑 pip install -r requirements.txt 大几十秒。Stage 12.5 的 DependencyEnvironment 解决：虚拟环境初始化一次到 environments/<env_key>（chmod 555 只读保护），后续 episode 通过环境变量复用同一份 venv。

③ 路径 + 环境变量注入 AgentLoop

snapshot lease 路径和 dependency env 路径都是本地绝对路径，绝对不能进训练 batch。它们通过 LocalWorkspaceAdapter 注入到工具执行环境，对模型只暴露 opaque ref（rh://workspace-snapshot/<key> / rh://environment/<key>）。

④ DependencyEnvironment（Stage 12.5 · workspace/dependency_environment.py · 1506 行）

Stage 12.5 最大的新增模块。snapshot 解决"源代码不重复复制"，dependency env 解决"虚拟环境不重复安装"。两者在同一个 cache_root下平行存在；复用的前提是共享 manager 或共享 cache_root，并且 DependencyEnvironmentSpec 推导出的 cache key 一致。

三层 key 设计

① base_environment_key

Python 版本 / 平台 / package manager 版本 / lockfile sha256。底层依赖指纹。

② overlay_environment_key

setup command 列表 / overlay 策略。项目特定的安装步骤。

③ source_snapshot_key

source_tree_hash / base_commit。源代码版本。

完整环境 key = f"rhenv-{hash24}"，由 3 个分量哈希出来。

chmod 555 只读保护实现

已 publish 的 dependency environment 必须只读，任何 episode 都不能污染。

⑥ 共享 cache_root 完整物理布局

trainer 创建一份 cache_root，所有 Ray worker / episode 共享。snapshots/ + leases/ + environments/ 三大区独立但通过 snapshot_key 中 environment_id = env_key 绑定一致性。

shared_cache_root/ # 由 trainer 创建（如 /tmp/repo_harness_cache） ├── snapshots/ # 「干净源代码模板」区 │ └── wssnap-<source_hash24>/ │ ├── snapshot_facts.json # 18 字段元数据 │ └── workspace/ # clean 源码（只读使用） │ ├── src/... │ └── tests/... ├── leases/ # 「每条 episode 独立可写副本」区 │ └── wssnap-<source_hash24>/ │ ├── <episode_id_1>/workspace/ # 来自 snapshot 的 shutil.copytree │ ├── <episode_id_2>/workspace/ # episode 之间互不污染 │ └── ... │ └── <episode_id>/ │ └── .repo_harness_env_overlay/ # Stage 12.5：隐藏真实 env 路径的 overlay │ └── workspace/bin/... # 软链接到 environments/<env_key>/bin/ ├── environments/ # Stage 12.5：「虚拟环境共享」区（chmod 555） │ ├── rhenv-<base24>-<overlay24>-<source24>/ │ │ ├── environment_facts.json │ │ ├── bin/ # python / pip / uv / pytest 可执行 │ │ ├── lib/ # site-packages │ │ └── pyvenv.cfg │ └── rhenv-<other_keys>/ ├── lease_facts/ # 每个 lease 的 JSON facts │ ├── <episode_id_1>.json │ └── <episode_id_2>.json ├── .tmp/ # 临时目录（写完后原子 rename 到正式位置） │ ├── wssnap-<key>.<uuid>/ │ └── rhenv-<key>.<uuid>/ └── .locks/ # 本地文件锁 ├── wssnap-<key>.lock # Stage 6 mkdir 锁 └── rhenv-<key>.lock # Stage 12.5 os.O_CREAT|O_EXCL 锁

时间账：1000 条 episode 跑同一 task 的开销对比

步骤没缓存（naive）Stage 6 only（snapshot 缓存）Stage 6 + 12.5（snapshot + env 缓存）
源码 materialize（每条 episode）5s × 1000 = 83 min5s（首次）+ 0.3s × 999 ≈ 5 min5s + 0.3s × 999 ≈ 5 min
setup_command 执行（pip install 等）30s × 1000 = 8.3 hr30s × 1000 = 8.3 hr （这一步没省）30s（首次） + ~0s × 999 ≈ 30s
合计准备开销≈ 9.7 hr≈ 8.4 hr≈ 5.5 min

Stage 6 单独使用只省了源码 IO；只有 Stage 12.5 接通后才省 setup_command 这一更耗时的步骤。

复用成立的前提：上面的时间账是“同一任务、同一依赖规格、共享 cache_root”的理想账本。真实训练中，snapshot 复用需要 WorkspaceSnapshotKey 一致，dependency env 复用需要 DependencyEnvironmentSpec 推导出的 cache key 一致；如果 Ray worker 各自使用不同 cache_root，或者依赖 lockfile、Python 版本、安装命令发生变化，就会创建新的 snapshot 或新的 environment。
