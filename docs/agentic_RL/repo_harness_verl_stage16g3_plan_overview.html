这份报告讲什么

这是 Stage 16G.3 计划阶段的总览汇报。Stage 16G.2 已经把"结构化文件修改 + final.patch 投影 + TrainingView mask"贯通；16G.3 要把模型从"只能静态读 + 写补丁"扩到"能跑公开命令 / 公开定向测试 / 临时复现脚本"。这份计划有18 节 700+ 行，密度很高；本报告抽出战略层 + 每个子阶段的高级摘要 + 4 个关键设计点 + 我看完计划后的独立观察。每个子阶段的22 条共享底座要求 / Profile schema / 22 条验收矩阵等细节都留给独立子阶段 HTML。

1 · 阶段定位 — 从"会改文件"走到"会动态诊断"

4 · 三标杆参考结论

4.1 Claude Code 的启发

CC 用 Bash 作为一等公民承担测试 / 构建 / 项目命令 / 诊断；它经过权限 / 沙箱 / hook / 输出处理 / 工具结果配对的多层处理。对 RH：不让模型只会静态猜补丁，但也不要把读/写/改/测全压进不透明 shell。结构化文件工具继续承担文件修改，16G.3 补齐公开命令和测试诊断。

4.2 Codex 的启发

Codex 偏 exec_command / write_stdin / apply_patch / permission profile / approval / sandbox / event stream。每个命令执行都进 workdir / timeout / 输出截断 / sandbox permission / approval / guardian / hook / rollout trace。对 RH：命令执行应是正式工具面的一部分；技术 sandbox / 权限策略 / approval/reviewer 思想 / 事件审计必须分层；模型可见结果 / 客户端事件 / raw artifact / 训练投影不能混成一个字符串。但 RH不需要复制 PTY / ongoing session / write_stdin —— 16G.3 第一版做 stateless public command runner，单次公开命令稳定。

4.3 mini-SWE-agent 的启发

本地无官方源码，但 16G.0 follow-up 已用评测工作树日志做 tier-2 evidence。下限能力是稳定 shell 闭环：命令 / stdout / stderr / exit code 反馈 / 公开测试 / 复现脚本。对 RH：不是"照抄 Bash-first"，而是必须覆盖同等动态诊断能力，但用结构化工具实现。

核心交付

7 · 4 个高亮设计点（你确认要强调的）

🔑 ① 16G.3A 必须先做 — 共享底座决定后续三件能否一致

三个工具（run_public_command / run_project_test / scratch_python）都需要 cwd 解析 + workspace-only + timeout + stdout/stderr/exit code + 输出截断 + raw artifact 私有化 + public projection + 拒绝 reason_code + TrainingView mask + run_episode 投影。如果分别实现必然出现：三套不一致路径策略、三套不一致截断、三套不一致 artifact 可见性、三套不一致拒绝语义、三套不一致训练资格。

计划 §6.1 把这条上升为不可反顺序的约束。审查 16G.3 实施时第一个看的应该是"3A 是否真的独立成模块（tools/public_command.py）、是否被 3B/3C/3D handler 显式 import 复用"。

原文位置：§6.1 + §7（22 条设计要求）

🔑 ② Docker / sandbox 隔离不能 fallback 伪装完成

计划 §7.2 第 8 条把"16G.3A complete 的最低通过条件"明确为二选一：

  • 选项 A：Docker 或等价隔离可用 + 网络 deny + 无 run directory mount + 无宿主路径 + side effects 丢弃
  • 选项 B：只完成 schema/profile/classifier 和 planned_not_enabled evidence，不暴露 3 个新工具进 swe_public_core

第 9 条进一步明确：fallback 到本机子进程必须写 network_isolation_proven=false + core_profile_exposure_allowed=false，不能把这当完成态。第 10 条把"无网络 evidence"上升到 fail-closed 级别 — Docker 默认 bridge / 未记录策略 / 非 deny 都让 inspector 失败。

原文位置：§7.2.8 / §7.2.9 / §7.2.10 + §15.9（inspector 校验项）

🔑 ③ Public test source boundary — 本阶段新增硬边界

计划 §8 把这条从 16G.4D reward metadata 提前到 16G.3 必须落地。原因：可训练公开测试工具一旦放进 core，"模型先改公开 test 再让 test 通过"是最直接的 reward hacking 路径，不能等到 16G.4D 才堵。

具体执行：run_project_test 前判断 public test 文件是否被 candidate patch 修改。第一版二选一：

  • 策略 A：拒绝运行，返回 public_test_source_clean=false + result_valid_for_training=false + safe_rewrite_example
  • 策略 B：在干净 public test 快照上运行，返回 public_test_source_clean=false + ran_on_clean_public_test_snapshot=true

必须有 probe：先改 public test，再调用 run_project_test，验收器看到拒绝 OR clean snapshot facts。

原文位置：§8 + §10.3.6 + §16 modified public test boundary probe

🔑 ④ Codex 客户端 API ≠ 模型可见工具 — 借鉴的关键边界

计划 §4.2 末段明确：Codex app-server 中的 command/exec / process/spawn / fs/readFile / fs/writeFile 这些 API主要服务客户端或桌面端控制流程，不等同于普通模型可见动作。RH Stage 16G.3只设计模型可见、可训练、可审计的工具动作空间，不能把客户端 API 级别的宿主文件系统能力映射成模型默认权限。

这是从 Codex 借鉴时最容易踩的雷：看到 Codex 的 fs/readFile 能读宿主任意文件，就觉得 RH 也可以放宽路径黑名单。事实是：Codex 的 fs/readFile 是给桌面 IDE 用的，不是给 model 用的。RH 的模型可见工具面要继续受 L2/L3 路径黑名单约束。

10 · 我看完计划后的观察（5 条）

O1 · 22 条共享底座要求里第 3 / 5 / 8 / 9 / 10 条是互相绑定的"独立底座 + 隔离 backend + fail closed"小集合 — 建议在 3A 启动前画一张状态图

这 5 条约束实际上是同一件事的 5 种说法：(3) 必须用 workspace-only isolated backend、(5) 必须新增 public-command 专用接口、(8) 完成态二选一、(9) fallback 必须明示不可暴露、(10) 网络 fail closed。我担心实施 agent 在跨多条要求时容易"满足了第 3 条但漏了第 5 条"。建议在 3A 启动前先画一张"backend × 网络策略 × profile 暴露"决策状态图，所有路径必须能落在三类合法终态之一：(A) Docker + deny + core 可暴露；(B) Docker + 非 deny → inspector fail；(C) 本机 + planned_not_enabled + core 不可暴露。否则 22 条很容易被实施 agent 局部满足、整体失效。

O2 · §8 public test source boundary 二选一策略中"策略 B 干净快照"实现难度比策略 A 高很多 — 建议第一版强制策略 A

策略 B 要在 candidate patch 不动 public test 文件的前提下重建一份 public test 快照执行。这意味着 16G.3A 共享底座的 disposable execution snapshot 还要支持"选择性把 public test path 排除在 candidate patch 之外"。第一版做这个会很复杂，且容易留下"哪些路径算 public test"的判定漏洞。建议第一版直接选策略 A（拒绝运行 + safe_rewrite_example），把策略 B 留给 16G.5 parity probe 之后再考虑放宽。计划目前是"二选一"，没强制 — 这点值得在 3C 启动前定下来。

O3 · §7.2.13 的"受控环境变量白名单"第一版只列了 4 个（PYTHONPATH / DJANGO_SETTINGS_MODULE / CI / NODE_ENV）— 实际很多项目需要 PYTHONHASHSEED / PYTEST_ADDOPTS 等

这是个小但具体的缺口。pytest 项目常需要 PYTHONHASHSEED=0 保证可复现；很多项目用 PYTEST_ADDOPTS 控制并发。建议在 3A schema 设计阶段，先去采样 SWE-bench 任务实际 public environment 中常见的环境变量集合，再决定白名单。或者让 PublicCommandProfile.env_profile 自带这层 source-bound（来自任务公开声明的环境变量直接放过）。否则第一版 16G.3C 跑很多任务会因为环境变量缺失而失败，看上去像工具的问题而不是配置问题。

O4 · "拒绝可学习"机制（§12.3）和 §16 的 modified public test boundary probe 之间有哲学冲突需要明确

计划 §12.3 说"拒绝事件不能被简单过滤出轨迹。合理拒绝可以作为负样本或恢复训练材料"。但 §16 modified public test boundary probe 又说"public test 被修改后的拒绝 OR clean snapshot 运行 + 结果不能成为主训练成功依据"。问题是：如果"模型先改 public test 被拒绝"这条负样本进 trajectory，下一轮模型会不会学到"我应该改 public test"而不是"我不应该改 public test"？需要在 3C / 3D 设计 reward attribution 时显式定义"拒绝事件的训练标签"。这个问题计划没明说，建议在 3A 启动前先收口。

O5 · §10.5 多语言 profile 列表（pytest/unittest/django/sphinx/tox/nox/npm/go/cargo/make 共 10 项）— 第一版只实现 pytest 会让某些 SWE-bench 任务跑不起来

SWE-bench Verified / Lite 大约 70% 是 pytest 项目，但 Django 任务（用 django_test）和少量 sphinx_build_smoke 不在 pytest 范围内。第一版只实现 pytest 意味着 16G.3 完成时 Django / sphinx 任务仍跑不起来。这不是阻塞（计划 §10.5 已明确允许其他 profile 标 planned_not_enabled），但建议在 16G.3 完成报告里明确量化"当前数据集中能被 16G.3C 覆盖的任务百分比"，避免后续阶段误以为已经全覆盖。

下一步建议：O1（状态图）和 O4（拒绝事件训练标签）建议在 3A 启动前的设计审查环节先收口；O2（强制策略 A）建议在 3C 启动前确认；O3 / O5 是小但具体的执行细节，可以在子阶段实施时一并处理。其他 7 节非目标、上游依据、验收矩阵 22 项、风险回退表都已被计划本身覆盖得很完整，不再追加观察。
