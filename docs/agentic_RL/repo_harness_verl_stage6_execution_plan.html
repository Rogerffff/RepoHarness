⚡ 核心实现：WorkspaceSnapshotManager.acquire_workspace(...) 流程

最关键的并发与原子性流程。任何写盘失败都不会产生半发布的 snapshot。

┌─ [1] 进入 _SnapshotLocalLock(lock_path, timeout_seconds) │ → 同 snapshot_key 的并发请求串行化 │ → Linux/macOS 用 fcntl.flock(LOCK_EX) 文件锁 │ ├─ [2] 检查 snapshots/<snapshot_key>/snapshot_facts.json │ ├─ 已存在 → 读取 facts · 校验 snapshot_key / source_tree_hash / policy_version │ │ ↓ │ │ ┌─ 合法 → 复用现有 snapshot (cache_hit=True) → 跳到 [6] │ │ └─ 损坏 → 返回 structured diagnostics，绝不静默覆盖 │ └─ 不存在 → 进入 [3] │ ├─ [3] 写入临时目录 .tmp/<snapshot_key>.<creator_id>/ │ → creator_id 用 uuid.uuid4().hex 区分不同 writer │ → 临时目录 cleanup 失败 → 进入 diagnostics │ ├─ [4] materialize source / restore dependency │ → 复用现有 materialize_source(...) │ → 校验 clean-state（运行 post-materialization source_tree_hash） │ → 写 snapshot_facts.json + manifest │ → os.fsync(facts_file) 确保 facts 可读 │ ├─ [5] post-materialization source_hash verify │ → 重新计算 source_tree_hash · 与 prelookup key 中预期值对比 │ → 不匹配 → raise WorkspaceError，临时目录留作 forensic │ ├─ [6] atomic rename .tmp/<…> → snapshots/<snapshot_key>/ │ → os.rename(tmp_dir, final_dir) 原子操作 │ → 如果 publish 时发现已存在 → 读 facts 校验后复用 │ ├─ [7] 派生 episode workspace │ → leases/<lease_id>/workspace/ ← 普通目录复制 │ → snapshot 目录只读，不污染 │ → 写 leases/<lease_id>.json lease facts │ └─ [8] 退出 lock → 返回 WorkspaceLeaseHandle（含 timing 字段）

WorkspaceLease 4 状态生命周期

active

lease 已分配，episode 正在使用 workspace。
cleanup_status = not_started

released

release_workspace(handle) 成功，workspace 已删除。
cleanup_status = completed

cleanup_failed

release 时 shutil.rmtree 抛错。
cleanup_status = failed · cleanup_error 写入异常原因 · diagnostics 也记录

orphaned

进程崩溃 / 系统重启后留下的孤儿 lease。后续启动 manager 时识别并标记，不删除别人的 workspace。
双层 cleanup_status 映射：WorkspaceLease.cleanup_status 用稳定状态名（completed / failed / skipped / not_started）对齐 Docker / recorder 报告；WorkspaceLease.lifecycle_status 用生命周期词汇（active / released / cleanup_failed / orphaned）。同一 cleanup 语义不会在不同报告里出现两套名字。

① 阶段目标

降低训练场景中每条 episode 重复创建 workspace、重复恢复依赖、重复执行 setup 的成本，同时保持 RepoHarness 最重要的 clean-state、audit 和 verifier 可信边界。

目标数据流：
source materialization → clean workspace snapshot → dependency cache facts → 每条 episode 派生独立可写 workspace → ResourceSummary 记录 snapshot key / cache hit / restore strategy / lease id / cleanup status
  1. 第一条任务创建 clean workspace snapshot。
  2. 后续相同 snapshot key 的 episode 复用 snapshot。
  3. 并发两条 episode 不能共享同一个可写 workspace。
  4. cleanup 失败、snapshot miss、dependency cache miss 都能进入 diagnostics 或 summary facts。
  5. ResourceSummary 能解释本 episode 的环境复用事实，不只写一个模糊的 workspace backend。

两阶段规则：避开"先 materialize 才能 lookup"的顺序矛盾

阶段 A · prelookup key

用task 已声明的 hash构造可预查 key：

  • source_archive_sha256
  • mirror_sha256
  • source_tree_hash（如 task 已包含）
  • repo_ref + base_commit + environment_id

阶段 B · post-materialization verification

materialize 后再次计算并校验：

  • 重新算 SourceCheckoutFacts.source_tree_hash
  • 与 prelookup 中预期值比对
  • 不一致 → 抛 WorkspaceError，临时目录保留作 forensic
降级规则：如果 task 缺少 prelookup hash 且本地源 hash 计算成本过高 → 退化为 snapshot miss + diagnostics 记录原因，不静默改 key 算法。

⑤ snapshot 发布语义

见 §⓪ 中流程图。要点：本地文件锁 + 临时目录写入 + 原子 rename + facts fsync + 已存在时校验复用、绝不静默覆盖。

事件处置
目标 snapshot 已存在，facts 合法读 facts · 校验通过 · 复用（cache_hit=True）
目标 snapshot 已存在，facts 损坏 / key 不匹配返回 structured diagnostics，不静默删除或覆盖
临时目录 cleanup 失败进入 diagnostics，留作 forensic
原子 rename 时目标已存在读 facts 校验后复用
post-materialization source_tree_hash mismatch抛 WorkspaceError，临时目录保留
lock 文件路径是 runtime-only 信息，不进入 batch 可传播字段。
