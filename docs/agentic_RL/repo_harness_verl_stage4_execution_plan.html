TimingSummary 实际 schema（与 Stage 3 比的增量）

Stage 3 的 4 字段版本被扩成 14 个互斥分桶 + 解释率 + 计数 + diagnostics。所有新字段都有 Field(default=0.0, ge=0.0) 安全默认，旧 fixture roundtrip 不被破坏。

不变量低解释率（< 0.95）不会让 episode 被默默接受——pydantic 在构造期就会 ValueError 除非显式写出 timing_unattributed_seconds > 0 + 非空 timing_diagnostics。

4.2 互斥分桶可视化（关键概念）

这是 Stage 4 最容易理解错的地方。rollout_wall_seconds（外层总耗时）必须能被互斥的子项相加近似得到。禁止把"父阶段总耗时"和"子阶段耗时"同时加进 explained_seconds。

✗ 错误：把 agent_loop_seconds 当作"包含 model + tool"的总和又重复计入

agent_loop = 60s（含 model+tool）
model = 40s
tool = 20s

→ 合计 120s > rollout 100s，explained_ratio 假性达到 120%，掩盖真实未归因时间。

✓ 正确：互斥分桶 + residual overhead

model 40s
tool 20s
ctx 8s
verifier 15s
artifact 5s
cleanup 4s
residual 5s
未归因 3s
model_call_seconds tool_seconds context_prepare_seconds verifier_seconds artifact_write_seconds cleanup_seconds agent_loop_seconds（residual overhead） timing_unattributed_seconds

→ 合计 97s，explained_ratio = 97/100 = 0.97 ≥ 0.95 通过。未归因 3s 写入 timing_unattributed_seconds + diagnostics。

4.3 解释率公式

def compute_timing_explained_ratio(rollout, *, model_call, context_prepare, tool, workspace, docker, baseline_verifier, final_verifier, reward, artifact_write, cleanup, queue_wait, agent_loop_residual, ) -> tuple[float, float]: explained = ( model_call + context_prepare + tool + workspace + docker + baseline_verifier + final_verifier + reward + artifact_write + cleanup + queue_wait + agent_loop_residual ) unattributed = max(0.0, rollout - explained) ratio = 1.0 if rollout == 0 else min(1.0, explained / rollout) return ratio, unattributed
分桶规则任何字段如果可能含 nested duration（如 provider 报告的 model duration 实际包含 retry），必须标记为 diagnostic / reference，不参与 explained sum。
不达标处置如果 ratio < 0.95，必须写入 timing_diagnostics，且 Stage 4 不能把该 episode 标为满足 timing gate。

两者必须是同一条 episode 的两份账本，不是两套独立估算。runtime facade 第一版必须满足三条等式：

used_wall_seconds
used_model_call_seconds
used_artifact_bytes
==

TimingSummary

rollout_wall_seconds
model_call_seconds
artifact_bytes_written
暂缺字段的处理规则：
  • 暂时无法精确统计 → 填 0 或 None，但必须在 diagnostics 中说明来源缺失。
  • 禁止一份 summary 写实测值，另一份留空 / 写另一套估算。
  • timeout / cancelled / invalid_task / infrastructure_error 也必须保留已经发生过的 used_wall_seconds 和 used_model_call_seconds。

同一份 timing/resource 事实在三个不同位置以三种不同粒度出现，避免完整 JSON 泄漏到 batch。

  • EpisodeResult.resource_summary

② 落盘 artifact（可写时）

  • timing_summary.json
  • resource_summary.json
  • 仅在 recorder / run_dir 存在时写入

    timing_summary: rh://audit/<ep>/timing-summary

  • TrainingView.extra_fields：
