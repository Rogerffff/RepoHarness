OpenAI Codex Harness 总览 + 对 RepoHarness 16G 的启发

数据源：本仓库 reference/codex/（commit 61cbf357）+ codex_vs_claude_code 分析文档 + codex AGENTS.md 源码导航　·　四块内容：Codex 工具系统全景 / 权限沙箱 / rollout-trace+app-server / 对 RepoHarness 16G 启发+我的观察　·　独立专题文(不并入扫盲版三方对比)

一句话：Codex 不是"模型输出 patch 的简单壳",而是一个本地运行的开发代理运行时 —— 多入口(TUI/exec/app-server/SDK)共享同一个 core,模型在 run_turn 循环里通过工具(shell_command / exec_command+write_stdin / apply_patch / plan / goal / MCP / code mode / multi-agent)和环境(权限 profile / 沙箱 / approval / guardian / hooks)交互,所有动作进事件流和可选 rollout-trace。它和 Claude Code 在核心架构上高度一致,只是风格更 shell+patch 中心(Claude Code 更结构化分层)。

为什么读它对我们重要：① 它和 Claude Code 共同证明"真实 SWE agent 不能只输出 patch、必须能跑命令验证";② 它的 PermissionProfile / Sandbox / Guardian / rollout-trace 是"强能力+强边界+可审计"的成熟样板,正好回答你担心的"放开能力会不会作弊";③ 它不是 SWE-Bench harness(没有 hidden verifier/reward builder),所以指导的是"运行时/工具环境"而不是"训练数据治理"。这些都直接喂进 16G.2/16G.3/16G.4 的设计。

1 · Codex 是什么

① agent loop —— run_turn 是核心

核心循环在 codex-rs/core/src/session/turn.rs 的 run_turn(...)。和 Claude Code query.ts / RepoHarness run_episode 同一个心智模型:

构建模型输入
  → 调模型流式响应
  → 收集 assistant message + tool calls
  → 工具调用进 ToolCallRuntime
  → 工具结果变成 ResponseInputItem
  → 写回历史
  → 必要时下一轮模型请求

关键认识:模型不是只生成最终答案,而是在多轮工具调用和结果反馈中完成任务。这是 Codex / Claude Code / RepoHarness 都遵循的范式。

② 多入口共享同一个 core

入口形态用途
codex TUI交互式终端用户日常使用,带审批 UI / diff / 计划
codex exec非交互 CLI(JSONL 输出)自动化,最接近 RepoHarness 的评测 runner
codex app-serverJSON-RPC 服务(stdio/ws/unix)IDE/桌面端/SDK 客户端 API
TypeScript / Python SDK语言级封装第三方集成

所有入口最终都进同一个 codex-core 的 Session/Thread/Turn 状态机。这对 RepoHarness 的直接启发:run_episode(real_episode) 应当成为评测/训练/导出/smoke 的统一入口(Stage 16F 已经做了从旧 run_task(...) 收敛,16G 新工具必须继续绑定这个统一入口)。

2 · 工具系统全景

① 三层架构

层职责文件
spec_plan本轮哪些工具模型可见、哪些只注册执行、哪些延迟加载tools/spec_plan.rs
router把模型返回的 ResponseItem 转成内部 ToolCalltools/router.rs
registry + orchestrator执行:hook→approval→sandbox→denied 重试→telemetry→结果包装tools/registry.rs、tools/orchestrator.rs

关键纪律:"源码里存在的工具定义"、"当前 profile 暴露给模型的工具 schema"、"executor registry 实际能执行的工具"是三件不同的事。分析工具面时必须区分。Codex 会根据模型能力/feature flag/MCP/code mode 选择性暴露工具 —— 这正是 RepoHarness 16G.1 profile registry 要解决的同一类问题。

② 模型可见核心工具(和 Claude Code 不完全一样)

工具是什么
shell_command传统 shell command(旧路径)
exec_command + write_stdin ★统一执行工具 —— 支持 PTY、yield、长会话、stdin 续写。这才是 Codex 真实产品态命令工具的主力
apply_patch ★结构化文件修改(下面单讲)
update_plan任务计划(类似 Claude Code TodoWrite 但更强调阶段)
goal tools目标分解和状态
request_permissions主动请求扩大权限(模型可见的"请求审批"工具)
request_user_input主动询问用户
MCP tools / tool_search外部工具(连接 MCP server)+ 延迟工具发现
dynamic / extension tools动态加载工具、扩展适配器
code mode execute/wait嵌套代码单元执行运行时(scratch notebook 风格,需 feature 开启)
multi-agent v1/v2spawn / send / wait / close 子代理
hosted web search / image gen托管能力

exec_command 的 schema 字段尤其值得看:

cmd, workdir, shell, tty, yield_time_ms, max_output_tokens,
sandbox_permissions, additional_permissions, justification, prefix_rule

这套字段直接告诉我们:真实产品态需要 cwd / 超时 / 输出截断 / 沙箱权限 / 额外权限 / 模型给出 justification(为什么要跑) / 命令前缀策略。这恰恰是 RepoHarness 16G.3 run_public_command 要补的东西。

③ apply_patch —— RepoHarness 直接对标

Codex 的 apply_patch 是 freeform tool,带 Lark grammar 约束(apply_patch.lark)。关键点:

  • 模型可见的专用 patch 工具,不要求模型通过 shell 重定向或 Python 脚本改源码。
  • 支持 新增 / 删除 / 更新 / 移动 文件。
  • 执行前 验证 patch 和路径(safety.rs::assess_patch_safety)。
  • 进入 approval / sandbox / event lifecycle。
  • 产出 file change event 和 patch status。
  • 支持 streamed argument diff —— 模型边输出 patch,UI 边显示生成进度。

RepoHarness 16G.2 的方向和这里高度一致(write_file + apply_patch 主路径 + delete/move/mkdir 经 apply_patch 表达 + expected_hash + reason 字段)。Codex 是这条路线的现实证据,不是我们独有的工程选择。

④ 与 Claude Code 风格的关键差异

Claude Code 风格

显式结构化分层:

Read / Grep / Glob   # 读/搜
Edit / Write          # 改/建
Bash                  # 跑命令
TodoWrite / AgentTool / MCPTool

模型被引导"读文件用 Read、搜索用 Grep、改用 Edit、跑命令才用 Bash"。

Codex 风格

shell + patch 中心:

shell_command / exec_command + write_stdin
apply_patch
plan / goal / request_permissions
MCP / tool_search / dynamic / extension
multi-agent / code mode / hosted tools

没有专门的 Read/Grep/Glob —— 读文件、搜代码、跑测试很多都靠 shell + apply_patch 做修改。

这条对 RepoHarness 很关键:不需要在"结构化分层"和"shell 中心"中二选一。结合现有路线 —— 保留结构化 read_file/grep/glob/symbol_search/edit_file/create_file/write_file(Claude Code 路线),叠加受控 run_public_command + apply_patch(Codex 路线)。两边的优点都拿,既有清晰 action space 也有真实命令能力。

3 · 权限 / 沙箱 / 审批 / Guardian / Hooks

① 三层结构(技术沙箱 ≠ 审批策略)

层职责文件
PermissionProfile文件系统 + 网络能力边界(技术沙箱)protocol/permissions.rs、config/permissions.rs
AskForApproval什么时候要审批(策略)protocol/approvals.rs
ToolOrchestrator编排:approval → sandbox attempt → sandbox denied → optional retry approval → retry without sandboxtools/orchestrator.rs

Codex 把"技术边界"(sandbox)和"审批策略"(approval)分开 —— 这是个值得借鉴的纪律。默认 workspace profile:

  • 允许工作区写入 ✓
  • 但保护 .git / .codex / .agents 等元数据目录
  • 网络默认受限
  • 还有 read-only 和 danger-full-access profile,但都是明确配置,不混在模糊 shell allowlist 里

② 跨平台 sandbox(真的是技术边界,不是装饰)

平台后端位置
macOSSeatbelt(/usr/bin/sandbox-exec + .sbpl 策略)sandboxing/src/seatbelt*.rs
Linuxbubblewrap 或 Landlock(缺 user namespace 时失败关闭)linux-sandbox/、bwrap/
Windowsrestricted token 或 elevated backendwindows-sandbox-rs/

关键:安全设计依赖确定性运行时边界 + 可审计审批,不依赖"把工具能力压缩到无法完成真实工程闭环"。这正面回答"开放命令能力会不会作弊" —— 答案是:用 sandbox+权限边界把作弊路径焊死,不靠削能力。

③ Guardian + Hooks(辅助审查 + 生命周期事件)

Guardian(codex-rs/core/src/guardian/)是 Codex 的自动审批审查器:审查高风险命令、补丁、网络或 MCP 调用,产生 GuardianAssessmentEvent。它不是底层 sandbox(那是 PermissionProfile 干的),也不是 reward judge(产品没有 reward)—— 它是"审查 reviewer"角色。

Hooks(codex-rs/hooks/)把工具调用和 session 生命周期暴露成可配置事件:pre_tool_use / permission_request / post_tool_use / compact / session_start / user_prompt_submit / subagent_start_stop / stop。Hook 可以参与决策、注入额外上下文,不只是日志。

这对 RepoHarness LLM-as-judge 的定位有直接指引:Guardian 的角色等价于"reviewer / monitor / quarantine",不是唯一安全边界。RepoHarness 如果引入 LLM judge,应放在"审批审查辅助 / reward hacking monitor / 拒绝恢复评分 / final answer 一致性"这些位置,确定性边界仍由 path policy / network policy / runtime-private isolation / patch hygiene / verifier boundary 承担。

4 · rollout-trace + 同入口 + 客户端 API ≠ 模型工具

① rollout-trace 的"先观察后解释"原则

Codex 的 rollout-trace 是值得 RepoHarness 直接借鉴的设计。它明确分层记录,而不是把一切塞进一个 transcript:

模型可见 conversation        # 模型实际看到的
runtime tool dispatch        # 工具实际被调度的运行时事件
terminal operation           # 终端命令/输出原始记录
code-mode runtime            # 嵌套代码单元运行
MCP call                     # 外部工具调用
multi-agent edge             # 子代理边
raw payload reference        # 原始证据(私有引用)
offline reduced semantic graph  # 离线 reducer 输出的语义图

核心原则:"先观察,后解释" —— 先把原始事实记下来,语义解释由 offline reducer 做。

对 RepoHarness 轨迹的直接含义:不能把模型可见 observation / 工具原始输入 / 规范化输入 / 权限决策 / 运行时 stdout-stderr / 模型可见截断摘要 / final.patch / patch hygiene 过滤事实 / hidden verifier 私有结果 / reward-only metadata / TrainingView 可训练 token vs 不可训练 token —— 这些全混进一个 transcript。否则后续 reward builder、policy loss、SFT、偏好数据都会混淆"模型学到了什么"和"评测系统知道什么"。这是 16G.2C 接 TrainingView 投影时要严格分层的关键。

② 客户端 API ≠ 模型工具(关键区分)

Codex 的 app-server 提供 fs/readFile、fs/writeFile、command/exec、process/spawn、thread/shellCommand 等 API。这些是客户端控制 API,不是普通模型可见工具。不能直接映射成模型动作空间。

app-server API安全语义对 RepoHarness 的含义
command/exec客户端请求 server sandbox 下执行单个命令,不启动模型 turn可参考结构和流式输出,但不能等同于模型动作
thread/shellCommand用户发起的 ! shell,文档明确不继承 thread sandbox policy只能作产品控制面参考,不能作训练工具面默认语义
process/spawn实验性宿主进程能力,不经过 Codex sandbox对 RepoHarness 训练面风险过高,只能作"不要误用"的边界案例
fs/readFile / fs/writeFile操作宿主绝对路径的客户端 API不能映射成模型可见文件工具;RH 必须用工作区相对路径 + 隐藏路径隔离

纪律:分析能力对齐时必须区分四类 —— ①模型动作空间 ②客户端控制面 ③评测 harness 内部能力 ④verifier/reward-only 能力。Stage 16G 的所有工具面结论都应以①+②(实际是①)和可训练轨迹为准。

③ 我的审查观察

关键澄清 O1 · Codex 不是 SWE-Bench training harness

Codex 是产品态运行时,没有 task dataset / hidden verifier / gold patch 隔离 / official prediction / reward builder / policy loss eligibility / verl async queue / TrainingView。所以它给的是"运行时和工具环境"设计指引,不能替代 RepoHarness 的训练数据治理和 verifier 边界。Stage 17+ 的数据 / verifier / reward 部分还得 RepoHarness 自己做。

设计转换 O2 · approval 从"人参与"转成"deterministic policy"

Codex 可以让真人审批,也可以让 Guardian 自动审查。但 RepoHarness RL rollout 通常没有真人逐条确认。所以 Codex 的 approval 思想要转换:

  • 公开安全动作 → 自动允许
  • 明确越界动作 → 确定性拒绝
  • 可恢复拒绝 → 返回结构化替代建议(reason_code / safe_alternative_tool / safe_rewrite_example)
  • 可疑动作 → quarantine
  • LLM-judge → 仅辅助 monitor,不作唯一安全边界

设计选择 O3 · 不必照抄 Codex 的 shell-first

Codex 偏 shell + patch 中心(没有专门 Read/Grep/Glob);Claude Code 偏结构化分层。RepoHarness 取两家之长:保留结构化文件导航(read_file/grep/glob/symbol_search/edit_file/create_file/write_file)+ 引入受控公开命令(run_public_command/run_project_test/scratch_python)+ apply_patch 作为结构化批量入口。这样既有清晰的 action attribution(更适合 RL 训练),又有真实 SWE 闭环。

下一步重点 O4 · rollout-trace 的分层启发要在 16G.2C 之后落到 TrainingView

RH 当前的 TrainingView / trajectory / GenerationRecord 已经有基础,但没有像 Codex rollout-trace 那样严格分层(模型可见 observation / 工具原始输入 / 规范化输入 / 权限决策 / runtime raw artifact / 模型可见截断摘要 / final.patch / patch hygiene / hidden verifier / reward-only / training-eligibility)。16G.2C 把文件改动接进 final.patch 和 TrainingView 时,正是把这套分层落地的好时机 —— 不分层就训不出"模型基于什么信息采取了动作"这个关键能力。

总体判断 O5 · 现行 16G 路线和 Codex 现实样板高度一致

同一 core / 多入口 / apply_patch grammar / PermissionProfile / sandbox 多平台 / guardian reviewer 角色 / hook 生命周期 / 客户端 API ≠ 模型工具 —— 这些 Codex 给的设计约束,都和我们 16G.0–16G.2 已经做的或 16G.3–16G.4 计划要做的对得上。Codex 没有提示我们"要换路线",反而是给了现实证据证明这条路是对的。

所以最重要的不是新增工作,而是:继续按 16G.3(公开命令 + scratch + 项目测试,共享 substrate)→ 16G.4(extended profile 含持久 shell + linkage 收口)→ 16G.5(parity probe + 对抗 redteam)→ 16G.6(冻结)推进。这就够了。
一句话总结：Codex 不是替代品,也不是要复制的源码模板,而是"真实产品态 SWE agent 长什么样、用什么约束"的成熟参考。它和 Claude Code 共同把"主训练 harness 必须能让模型完成定位/复现/修改/验证/收口、安全边界靠 sandbox+权限+审计而非削能力、轨迹必须分层、客户端 API 不能误当模型工具"这套设计原则讲清楚了。RepoHarness 16G 的现行路线和这些原则一致,继续按计划做就好。
