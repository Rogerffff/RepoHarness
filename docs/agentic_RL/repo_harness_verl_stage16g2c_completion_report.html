3.1 inspector 是怎么把"真实 run_episode 调用"和"只用 builder 拼"的伪造区分开的

关键在 stage16g2_file_surface.py:1411-1418 的硬断言：

if probe.get("run_episode_invocation") != "RepoHarnessRuntime.run_episode(real_episode)":
    failures.append("probe_not_created_by_run_episode")
if probe.get("projection_writer") != "write_run_episode_compat_projection":
    failures.append("projection_writer_mismatch")
if probe.get("projection_created_from_run_episode") is not True:
    failures.append("projection_created_from_run_episode_not_true")

这三个字段都是"运行时实际 invocation 路径的字面量"，构造脚本只有真的走了那条路径才会写出来。inspector 不仅核对它们的值，还把 STAGE16G2C_PROBE_KEYS 之外的字段都视为非法（见第 6 节），就算后续有人想"加一个字段绕过断言"也会被字段白名单挡住。

3.2 final.patch 真的覆盖了五种 operation kind

inspector 强约束 operation_kinds_observed 必须等于 {replace_text, write_file, delete_file, move_file, mkdir}（stage16g2_file_surface.py:1431-1433），并且 final_patch_changed_file_facts 至少要含 added≥2 / modified≥1 / deleted≥1 / renamed≥1，且 changed_paths 必须包含指定的 6 个文件路径（line 1455）。我读 probe report 实际值：

这是结构化文件工具 → final.patch 的最小完备样本：5 种 operation 都有，且 final patch 形态正确。

3.3 training_view 上的 response mask 行为

tool_observation_span_count= 2（每个工具调用 1 个 observation 段） tool_observation_spans_response_mask_zero= true（工具回执整段不参与 loss） tool_output_response_mask_zero_count= 16（共 16 个 token 来自 tool observation，全部 mask=0） assistant_response_mask_one_count= 5（共 5 个 token 来自助手生成，mask=1） response_token_count= 21（= 16 + 5，与上面相加） generation_record_count= 2（两轮 assistant 生成）

这一段的意义：哪怕模型在轨迹里"看见"了 write_file / apply_patch 的成功结果，那段 token 也不会被算进 policy loss。这是 verl 异步 PPO 的关键契约 — 工具回执不能成为模型学习目标，否则会反复"复读"工具输出而不学习生成正确的工具调用。inspector 在 stage16g2_file_surface.py:1464-1473 强制要求 tool_observation_spans_response_mask_zero is True。

4 · audit_ref → audit_artifact_id 改名是否彻底

4.1 为什么必须改名

visibility.py:48-58 把 audit_ref 列在 FORBIDDEN_BATCH_EXTRA_FIELD_KEYS 里，并且通过 _find_forbidden_marker 在多个层面（batch extra fields、gateway extra fields、模型可见 visible text）做子串匹配。这意味着：

  • 任何 model-visible payload（包括 tool result content + typed dict）只要出现"audit_ref"这 9 个字符，都会被 gateway 视为 evaluator-only 泄漏并拒绝传给模型。
  • 但 RepoHarness 内部数据层（rl/episode.py 的 AuditRef 类、rl/training_view.py、rl/runtime.py 的 _audit_ref 私有方法）合法地使用 audit_ref 这个名字 — 它们不进 model-visible 通道。

原 16G.2B tool result 错误地用 audit_ref 作为 model-visible 字段名，会被 forbidden marker 拒绝，tool 调用看起来"成功"但模型实际收到的是 gateway forbidden 错误。如果不在 2C 修，16G.2C run_episode probe 会失败。

5 · policy_loss 阻断核查（最关键的训练边界）

5.1 阻断逻辑核心

在 evaluation/episode_projection.py:610-635 的 _provider_route_qualification 里：

formal_online_rl_eligible = (
    provider_route == "verl"
    and request.llm_gateway_route == "verl"
    and not result.invalid_for_training
    and not result.invalid_for_online_rl
)
return {
    ...
    "policy_loss_candidate": formal_online_rl_eligible,
    "qualification_reason": (
        "route_verl_formal_online_rl_candidate" if formal_online_rl_eligible
        else "non_verl_or_diagnostic_route_not_policy_loss_candidate"
    ),
}

四个必要条件——任何一个不满足都会让 policy_loss_candidate=false。本阶段 probe 全部跑的是 provider_route=mock / llm_gateway_route=mock，所以第一个条件就被卡掉。

5.2 防御性 cross-check

同一文件 episode_projection.py:380-417 还有一组兜底 — 即使有人篡改 manifest 强行写入 policy_loss_candidate=true，validator 会再检查：

  • provider_route_qualification.json 中 policy_loss_candidate 与 manifest 不一致 → policy_loss_mismatch
  • 非 verl route 但 manifest 标为 policy_loss → non_verl_route_marked_policy_loss_candidate
  • 非 verl route 但 route_report 标为 policy_loss → non_verl_route_report_marked_policy_loss_candidate
  • 非 verl route 但 status_report 标为 policy_loss → non_verl_status_marked_policy_loss_candidate
  • policy_loss 为 true 但 formal_online_rl 为 false → policy_loss_candidate_without_formal_online_rl_eligible

这是"五层校验冗余" — 任何一层意外被绕过，其他层都会发出 mismatch。

5.3 partial_failure 路径

在 tools/minimal.py:2278-2334 的 _stage16g2b_file_mutation_tool 成功分支里，typed dict 中始终硬编码 "allowed_in_policy_loss_trajectory": False 和 "sample_policy_loss_candidate_effect": "requires_stage16g2c_patch_projection_linkage"。当 outcome.partial_failure 时 status 直接置为 "error" 并打 error_type="stage16g2b_file_mutation_partial_failure"。也就是说，partial_failure 不仅不进 policy loss，工具回执本身就是 error 形式。

5.4 我直接读到的最终事实

probe 报告里policy_loss_candidate=false · formal_online_rl_eligible=false · invalid_for_online_rl=true · invalid_for_training=false training_view 投影online_rl_eligible=false result_status_reason"non_verl_route_invalid_for_online_rl"

invalid_for_training=false 但 invalid_for_online_rl=true 的组合很重要：mock 轨迹可以用于 SFT / warm-start 训练数据生成（如果 16G.5/17B/20 阶段允许的话），不可以进入 verl 异步 PPO / GRPO 的 policy loss 直接梯度。本阶段没有放开这个组合 — Stage 20 闸门仍然为 false。

6.2 这是过严还是恰好？

我的判断：对当前阶段是恰好的。理由：

  • 每个白名单字段都是语义性约束 — 让 inspector 知道"该有的字段就是这些，不该有的不会偷偷被加进来"。这是把 acceptance summary 当作契约表面来用，符合 RL evidence 防伪造的"白名单优先"原则。
  • 未来 stage 如果要扩字段（比如 16G.4 引入 parity probe 字段、16G.5 引入 reward attribution 字段），需要同步更新 inspector 白名单 — 这是设计意图，不是 bug。
  • 缺点：未来 stage 的开发节奏需要"代码 + inspector 同时改"，偶尔会让简单的字段扩展变得多一道手续。但相比"摘要刷分但字段被偷偷塞料"的风险，这点摩擦可接受。

6.3 一个相关风险（仍可接受）

operation_kinds_observed 在 inspector 里被硬约束为恰好 {replace_text, write_file, delete_file, move_file, mkdir}（!= 即 fail）。如果未来要加 chmod / link / append 等 operation 种类，必须同步更新这条断言，否则 inspector 会拒绝新 operation。这是预期行为。

8.1 为什么 16G.3 可以开，但 17B / 20 / 21 还不行？

  • 16G.3 = 状态机/会话边界 — 它要的前置是"结构化文件工具的 projection linkage"已经贯通（也就是本阶段刚完成的事），不需要 verl route 真实跑。
  • 17B = 真实数据冻结 — 它要求所有工具不仅 schema/projection 通，还要在真实 SWE 任务（不是手造 mini repo）上 parity 通过、reward boundary 稳定。要 16G.4 parity probe + 16G.5 reward policy + 16G.6 freeze。
  • 20 = warm-start 数据生成 — 要求 17B 冻结后的可用数据 + 数据合规标准。
  • 21 = 正式 RL — 要求 20 出的 warm-start checkpoint + verl 真实 route 跑通。

简单说：本阶段把"结构化文件工具 →（run_episode）→ 兼容投影"这条管子接通了；但"轨迹被算进 PPO/GRPO 梯度"的开关仍然有 5 层闸门没开。

9 · 我观察到的风险与未解问题

这一节是我自己的看法，不是 acceptance summary 里的字段。供你决定哪些需要在 16G.3 / 16G.4 之前先收口。

R1 · 死代码：_stage16g2a_schema_only_tool 已不再被调用

minimal.py:391 现在直接把 5 个文件工具全部路由到 _stage16g2b_file_mutation_tool。_stage16g2a_schema_only_tool（定义在 line 2337）的 reason_code 还写着 behavior_not_enabled_until_stage16g2b — 这段函数已经没有调用点，里面的字符串属于过期描述。
建议：16G.3 起手 PR 里清理掉这个函数和它引用的 safe_rewrite_example 分支（line 2356-2370），避免后续读代码的人误以为这是当前行为。

R2 · partial_failure 路径没有在 16G.2C 中被 run_episode 端到端 probe 一次

16G.2B 测试覆盖了 partial_failure 的拒绝语义（unit test 直接调 file_mutation 模块），但 16G.2C 的 run_episode probe 跑的都是"全部 operation 都成功"的快乐路径。代码层面 typed["allowed_in_policy_loss_trajectory"]=False 和 status="error" 是硬编码（minimal.py:2317），原子预检也几乎可以保证不会运行时部分失败。但从 evidence 角度，缺一个"在 run_episode 路径里故意制造 partial_failure，然后 invalid_for_training / policy_loss_candidate 双重拒绝"的 probe 样本。
建议：在 16G.4 parity probe 里加一个"故意触发 disk full / permission denied"的负样本场景，作为对抗性 probe；现阶段不阻塞。

R3 · reason 字段（delete/move 操作）还没接入任何下游信号

16G.2A 设计修正引入的"模型必须提供 reason"字段目前只在 audit_payload 里留底。它不进 trajectory token（避免被模型在生成时学到对应的 reward 模式），也不进 reward attribution（16G.5 才接入）。当前价值：审计 + 事后 reward hacking 诊断。
建议：在 16G.4 / 16G.5 设计 reward boundary 时，明确 reason 字段的下游归属 — 是 reward shaping 的副输入？还是只用作离线分析？现在让它"挂在那"对训练没影响，但概念上需要早一点收口。

R4 · inspector 字段白名单的"演进成本"在 16G.4+ 会显现

本阶段 inspector 共 7 个字段白名单常量。16G.3 加状态机字段、16G.4 加 parity 字段、16G.5 加 reward boundary 字段，每次都要同步改 inspector。如果未来希望加一个"忽略未知字段但记录 warning"的宽松模式，应该等到 17B 冻结之前再考虑 — 在那之前严格模式更安全。
建议：当前不动。在 16G.6 freeze 时再统一评估是否给某些演进性字段一个"warn-only"白名单层。

R5 · 模型可见 typed dict 字段名容易再次踩雷

这次的"audit_ref → audit_artifact_id"是被 gateway forbidden marker 抓到才发现的。问题根本：没有显式约束 tool result 写入 typed dict 时跑一遍 visibility filter。如果未来某个工具开发者再写一个 "gold_patch_path" 字段，目前要等 run_episode probe 才会发现。
建议：在 16G.3 期间给 _tool_result 内部函数加一个 lint pass — 构造期就跑 _find_forbidden_marker 扫 typed dict 的所有 key，发现就 raise。这样在单元测试就能拦下，不必等 integration probe。

R6 · 16G.3 闸门 _allowed_to_start=true 不代表已经设计好

本阶段 acceptance summary 把 stage16g3_allowed_to_start=true 翻成 true，但这仅意味着前置依赖（projection linkage）已满足，不代表 16G.3 的执行计划已经写好或者审过。
建议：16G.3 启动前还是按"plan HTML → 审 → 实施 agent → 我独立核查"的同样节奏走，不要被这个 true 字段带偏。
