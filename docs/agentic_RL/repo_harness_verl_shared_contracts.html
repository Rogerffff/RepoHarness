Shared Contracts

所有顺序阶段共同遵守的第一版接口契约

这一页完整展示共享 contract 的设计内容。它的目的不是描述当前已经实现的代码，而是在分阶段顺序开发之前，固定 episode 输入输出、模型调用、训练视图、审计引用、计时资源和验收门槛，避免后续接口漂移。

总原则

共享 contract 解决什么问题

verl adapter 阶段需要把 verl dataset sample 转成 RepoHarness episode request，并把结果转回 verl 的 AgentLoopOutput。Harness training_fast 阶段需要更快地产出同一类 episode result。所有阶段如果不共享字段和不变量，最终会在 token、mask、reward、audit、timing 和状态码上出现不兼容。

共享 contract 不是什么

它不是当前代码已经完成的承诺，也不是要一次写死未来所有字段。它是第一版最小语义边界：哪些字段必须存在，哪些数据不能泄漏，哪些路径必须可追溯，哪些测试必须共同通过。

Contract 01：Episode Request / Episode Result

RepoHarnessEpisodeRequest 和 RepoHarnessEpisodeResult 是顺序开发路线的中心边界。前置 Harness runtime 和 training_fast 阶段负责接收 request 并产出 result；后续 verl adapter 阶段负责构造 request 并消费 result。

第一版不要把当前 CLI 级 run_task(...) 直接暴露给 verl。它现在包含配置加载、任务加载、workspace 创建、baseline、agent loop、final verifier、reward、summary 写入等完整命令行编排，适合作为现有评测入口，但不适合作为 Ray worker 内部的可组合 episode runtime。

状态语义

succeeded 表示 episode 完整结束，轨迹和 reward 可消费，不等于任务成功。failed 表示模型完成了 episode，但 final verifier 或任务结果失败。timeout、no_progress、invalid_task、infrastructure_error 和 cancelled 必须和普通模型失败分开。

Reward 语义

score 第一版对应 RewardMetadata.final_reward。invalid_for_training=true 的样本可以保留 audit，但不应进入有效 online RL batch。training_fast 不能绕过 final verifier 权威边界。

Verifier Summary

包含 final verifier status、accepted、timeout、error_type、parser_confidence、fail_to_pass、pass_to_pass 和 final_verifier_ref。完整 stdout、stderr、test cases 和 evaluator-only 证据留在 audit artifacts。

Patch 与 Diagnostics

patch summary 包含 has_patch、changed_files、added_lines、removed_lines、diff_sha256 和 patch_ref。diagnostics 记录 failure category、no-progress、context limit、provider transient、environment failure 和 hidden_details_ref。

Contract 02：LLMGateway

LLMGateway 是 RepoHarness 内部模型调用与 OpenAI、DeepSeek、本地 vLLM、SGLang、verl 或未来 slime 后端之间的解耦层。

RepoHarness core 只能依赖 LLMGateway 抽象。VerlLLMGateway 只是一个 backend，负责包装 verl 的 LLMServerClient，不能让 RepoHarness core 直接 import verl runtime 对象。

字段组 规则
route 第一版包括 verl、openai、deepseek、local_vllm、sglang、replay、mock。
messages 和 tools messages 必须已经经过 visibility policy；tools 必须来自 scaffold 和 permission policy 解析后的允许工具集合。
sampling_params 包括 temperature、top_p、top_k、max_tokens 或 max_new_tokens、logprobs、stop、repetition_penalty。route=verl 时还要满足 rollout prompt_length、response_length 和底层 max_model_len 约束。

sticky_session_id 建议使用 episode_id 或 run_id，让同一条多轮 rollout 更容易命中推理后端 prefix cache。

Token 字段

prompt_ids 是本轮模型输入 token ids；output_token_ids 是本轮模型生成 token ids；output_logprobs 与输出 token 对齐；本轮 output token 的 response mask 全部为 1。工具 observation 不由 gateway response 生成，而是在 episode 级 training view 中以 mask 0 拼入。

Policy Version

fully async 阶段必须记录 global_steps、min_global_steps、max_global_steps 和 checkpoint ref。字段名必须对齐 verl 原始 TokenOutput.extra_fields，不能在 adapter 和 runtime 两边各自发明单复数字段。

VerlLLMGateway 约束

必须复用 verl 的 LLMServerClient、sticky-session load balancer、vLLM 或 SGLang server、token ids、log probabilities、routed experts 和 extra fields。
不能自己启动或停止 verl server，不能管理 Ray worker group，不能同步模型权重，不能绕过 server manager 直接访问底层 vLLM / SGLang 对象。
provider backend 可以通过现有 ModelClient adapter 兼容，但如果没有真实 token ids 和 logprobs，必须标记为 debug 或 teacher data generation 路径。
正式 verl online RL 路径必须以 VerlLLMGateway 的 token-in-token-out 记录为准。

Contract 03：Training View 与 Audit Ref

RepoHarness 的完整轨迹适合复查和数据治理，但不适合直接塞进 verl batch。训练器需要紧凑张量和 reward，审计系统需要完整证据，因此必须拆成 training view 和 audit ref。

字段 完整语义
prompt_ids episode 初始 prompt token ids。route=verl 时必须来自 verl tokenizer / processor / chat template。不能包含 hidden verifier、gold patch、reward metadata 或 accepted label。
response_ids 包含模型生成 token，也可以包含工具 observation token。padding 不在未 padding 的 TrainingView 中出现，由 verl worker 后处理。
response_mask 与 response_ids 等长。assistant 生成 token 为 1；工具 observation、环境 observation 和非训练 token 为 0。
response_logprobs 如果存在，长度与 response_ids 对齐。模型生成 token 使用 rollout server 返回的 log probability，工具 observation token 可以填 0.0。正式 PPO / GRPO 路径不应长期缺失 log probability。
reward_score 对应 RepoHarness RewardMetadata.final_reward。基础设施错误样本不能伪装成模型负样本，应通过 invalid_for_training 和 diagnostics 阻断。
verl_metrics 只承载能转换成 verl AgentLoopMetrics 的字段，例如 generate_sequences、tool_calls、compute_score、num_preempted。
repo_harness_metrics_ref 指向 RepoHarness 详细 metrics / timing / resource artifact。详细字段不能硬塞进 verl 原生 metrics 后静默丢失。

并发安全

每条 episode 必须有唯一 episode_id 和 run_id，写独立 run directory，使用隔离 workspace。RunRecorder 锁只能保护单个 run directory，不能证明 workspace、Docker volume 或 snapshot cache 没有污染。

环境复用

snapshot key 建议由 repo_ref、base_commit、environment_id、setup_command_hash、dependency_lock_hash 和 harness_version 组成。复用必须从只读 clean snapshot 恢复，并为每条 episode 创建 copy-on-write workspace。

Verifier Worker Pool

第一版允许 worker_pool_blocking：提交 final verifier、等待结果、计算 reward、返回 EpisodeResult。它不是 reward backfill，后者要等 fully async 阶段再设计。

资源事实

network_policy、permission_policy_ref、docker_resource_limits_effective、lease_id 和 worker pool 信息用于证明训练模式没有绕过 RepoHarness 现有边界。

Contract 05：Acceptance 与阶段门槛

进入端到端 smoke 前，每个阶段都必须经过共享 contract 验收。这里的目标不是只证明代码能跑，而是防止 token、mask、reward、hidden visibility、audit 和 failure 分类悄悄出错。

Contract schema tests：EpisodeRequest、EpisodeResult、TrainingView、AuditRef、TimingSummary 可以构造、序列化、反序列化。
Canonical fixture tests：shared schema JSON fixture 和 sha256 固定；adapter 生成的 request 与 runtime 反序列化对象逐字段一致。
Visibility tests：hidden verifier、gold patch、reward metadata 不进入模型可见上下文和训练 target。
Postprocess visibility tests：TrainingView -> AgentLoopOutput -> verl postprocess 后，extra_fields、raw_prompt、mask、reward 和 hidden visibility 仍满足 contract。
Mask tests：assistant token、tool observation token、padding token 的 mask 语义正确。
Token provenance tests：route=verl 时 token 来自真实 rollout generation；每个 GenerationRecord.prompt_ids 等于当轮传给 LLMServerClient.generate(...) 的 prompt_ids。
Audit tests：每条 training sample 可以通过 audit_ref 找到 run directory、transcript、events、artifact manifest、reward metadata 和 final verifier。
Failure tests：infrastructure_error、timeout、invalid_task 不会被误当成普通模型失败样本。
Outcome distinction tests：status=succeeded 只表示轨迹和 reward 可消费，不等于任务成功；verifier_summary.accepted=false 时不能统计成 task_success。
Schema evolution tests：新增字段必须显式标记 required、optional、default，并说明是否需要 contract version bump。
第一版不变量：没有 reward 或明确 invalid 状态的 episode 不能作为普通 online RL 样本返回；没有 audit_ref 的 episode 不能进入训练样本；没有 timing_summary 的 episode 不能声称支持训练吞吐分析。
