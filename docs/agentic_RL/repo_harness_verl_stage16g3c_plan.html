Stage 16G.3C · run_project_test — 执行计划

来源：执行计划 §8 + §10 · 前置：3A 共享底座 + 3B 已建立路由约定 · 核心交付：参数化公开测试工具 run_project_test

介绍

3C 是 16G.3 给模型新增的第二个可调用工具。它解决当前 run_tests 无参数的问题——让模型能跑单个 pytest 文件 / 单个测试函数 / 任务声明的 public smoke command，而不是只能"全跑或不跑"。它也是 16G.3 中最敏感的工具，因为公开测试通过是 SWE 任务最直接的成功信号，必须有 public test source boundary 防 reward hacking。

1 · 工具契约（计划 §10.1）

run_project_test(
    selector=None,
    test_file=None,
    test_name=None,
    command_profile=None,
    timeout_sec=None,
)

具体 schema 可在实现时选择，但必须解决当前 run_tests 无参的问题。模型必须能：

  • 运行单个测试文件（test_file="tests/test_x.py"）
  • 运行单个测试函数（test_name="test_x.py::test_y" 或拆字段）
  • 运行少量公开 selector（最多 20 条，见 §3）
  • 运行任务声明的 public smoke command（通过 command_profile）

2 · 4 类来源路由（计划 §10.2）

run_project_test 不能让模型自由提交任意 shell 命令。它从下面来源生成真实命令：

来源触发条件命令生成
① 任务 public_test_command任务 public environment 中显式声明的命令直接使用 + ingestion-time 校验
② 任务 public_test_profiles声明的 profile（pytest / unittest / django_test / sphinx_build_smoke / npm_test / go_test / cargo_test）按 profile 模板 + 模型传 selector
③ 兜底（任务无配置）任务没声明任何 public test结构化拒绝，建议改用 run_public_command 的公开 smoke 或源码检查
④ 禁止行为试图猜测 hidden verifier / official selector不能偷偷运行
关键：任务声明的公开命令本身也必须经过 ingestion-time validation / profile whitelist / 字段白名单 / sha256 绑定。不能因为某个命令写在 task public environment 中，就绕过 3A 的 command policy / runtime isolation / 网络隔离 / 路径边界。

3 · selector 安全规则（计划 §10.3）

第一版 pytest selector 必须满足：

  1. 路径 workspace-relative
  2. 路径不能含 .. / 绝对路径 / hidden path / runtime-private / 参考补丁 / 测试补丁 / evaluator-only marker
  3. selector 数量有上限，第一版最多 20 个
  4. -k 表达式（如支持）必须有长度上限和字符白名单
  5. 不允许通过 selector 注入 shell 语法
  6. 不允许修改 public tests 后把测试通过作为成功依据 — 见 §6 public test source boundary

4 · 与旧 run_tests 的关系（计划 §10.4）

不立即删除 run_tests。推荐路线：

工具16G.3C 后角色
run_tests（旧，无参）legacy compatibility / full configured public feedback；保留兼容，不在 core 主路径推荐
run_project_test（新）新主路径，支持参数化公开测试和 public command routing

后续 16G.5 parity probe 再决定是否把 run_tests 降级为兼容工具或内部 verifier facade。

6 · Public test source boundary（计划 §8 + §10.3.6）

这是 16G.3C 最关键的安全机制。不能让"模型先改 public test 再让 public test 通过"成为成功依据。

详细策略二选一已在 3A · §7 中展开（共享底座层面）。3C 这里的责任：

  1. 在 run_project_test 入口检查 public test 文件状态（hash 与 candidate patch 前对比）
  2. 选择策略 A（拒绝）或策略 B（clean snapshot）— 建议第一版强制策略 A
  3. tool result 含 public_test_source_clean / public_test_snapshot_digest / candidate_patch_included / result_valid_for_training / official_prediction_eligible
  4. 必须有 probe（见 §7 第 7 条）

7 · 8 项 probe 验收（计划 §10.6）

1单 pytest 文件：运行单个 pytest 文件并返回 stdout / stderr / exit code / parsed summary
2单 pytest node id：运行单个 node id（tests/test_x.py::test_y）
3任务默认 public test：运行任务声明的默认 public test command
4失败有可学习信息：public test 失败时返回 stdout / stderr / exit code / parsed test summary / retry hint
5timeout fact：public test timeout 时返回 timeout fact，不允许模型把它声明为测试通过
6无 public route 时拒绝：final-only 或 hidden verifier 存在时，只有 public environment 明确声明的公开测试或公开命令可以运行；没有 public route 时必须结构化拒绝，不能自动推断 hidden verifier / official selector / evaluator-only command
7修改 public test 边界：public test 被模型修改后的拒绝（策略 A）或 clean snapshot 运行（策略 B）策略
8run_episode 投影：projection 中能看到工具事件 / public test facts / TrainingView mask / sample eligibility facts
