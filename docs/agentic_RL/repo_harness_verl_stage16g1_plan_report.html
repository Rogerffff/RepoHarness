Stage 16G.1 计划汇报 + "训练投影/artifact"讲解

汇报对象：52-stage-16g-1-execution-plan.md　·　前半段简明汇报这阶段干什么，后半段用计划里的真实字段把"训练投影/artifact 语义"配例子讲清楚　·　上游：16G.1–16G.6 总讲解

一句话：16G.1 是"画蓝图"——它不实现任何工具、不放宽 shell，只把 16G.0 查清的 27 条能力固化成一份机器可检查的工具 registry + 四档 profile + 训练资格门禁，并写一个 CLI 验收器去自动检查。完成后解锁 16G.2 开始动手实现，但不解锁真实训练。

你问的"训练投影/artifact 语义"正是这阶段要为每个工具写死的两组规则：① 这个工具的数据流进哪个训练管道(或不进)；② 这个工具的输出谁能看到、什么进导出。下面第 3、4 节细讲。

1 · 16G.1 这阶段具体干什么（简明汇报）

维度内容
类型纯设计 + 机器验收，零工具行为改动（只加 builder / validator / inspector / 测试）
核心产出tool_registry_contract(27 条能力记录)、profile_taxonomy(4 档 profile)、training_eligibility_gate_spec(训练资格门禁)，共 10 份产物
机器验收器新增 CLI repo-harness inspect-stage16g1-tool-profile ... --assert-complete，自动检查约 19 项，失败返回非零退出码
重新钉死的代码事实默认 scaffold 是 simple_react、simple_react 有 create_file、mini_shell 不存在、execute_bash 窄但非空、diagnostic_shell 不属于 core —— 都让机器去核，不只继承文字结论
run_episode smoke一个极小验证：profile id / registry version 能通过统一入口 run_episode 带进 projection。做不到就出 blocked report，不许静默跳过
不做不实现 apply_patch / run_public_command 等、不放宽 shell、不把持久 shell 放进 core、不碰 reward 数值、不冻结数据
完成后解锁stage16g2_allowed_to_start=true；但 17B/20/21 仍 false
这阶段最大的价值是防"静默退化"：它用机器强制要求——每个工具不光要有名字，还必须同时声明"模型能不能看到它、拒绝时给什么提示、它的数据怎么进训练"。只有名字、没有这些规则的工具，会被判为不完整。这就是为什么"训练投影/artifact 语义"必须在这阶段定清楚。

2 · 先看一条 registry 记录长什么样

每个能力一条记录。以计划里的 apply_patch(还没实现的工具)为例，我把关键字段标注出来——后面第 3、4、5 节就是讲这三组加框的字段：

  "owner_stage": "16G.2",          // 归谁实现
  "blocking_for_main_swe_rl": true,
  "repo_harness_status": "proposed_tool_required",   // 还没实现
  "tool_ids": ["apply_patch"],
  "profiles": { "swe_public_core": "planned", ... },  // 属哪档 profile

  ┌─ 第 4 节：artifact 语义（谁能看到这个工具的输出）

    "model_visible":     "summary_or_public_result",     // 模型只看脱敏摘要
    "raw_artifact":      "private_by_default",            // 原始输出私有
    "export_projection": "public_safe_projection_only"    // 导出只放安全摘要
  },
  ┌─ 第 5 节：拒绝反馈语义（被拒时怎么告诉模型）
  "denial_feedback_policy": {
    "requires_reason_code": true, "requires_retryable": true,
    "requires_safe_alternative_tool": true, "requires_safe_rewrite_example": true
  },
  ┌─ 第 3 节：训练投影语义（数据进哪个训练管道）
  "training_projection_policy": {
    "allowed_in_policy_loss_trajectory": false,
    "sample_policy_loss_candidate_effect": "makes_sample_ineligible_until_tool_implemented",

    "diagnostic_only": false,
    "eligibility_reason": "工具尚未实现，16G.2 完成前不能进入主训练。"

3 · "训练投影语义"是什么意思 ★

先建立背景：模型解一道题时，每一步都会调用工具(读文件、改代码、跑测试…)。这些"工具调用 + 返回结果"会被记录下来，组成一条 trajectory(轨迹)。"训练投影"就是规定：这条轨迹里的数据，最终流进哪个训练管道、或者根本不进。

① 数据可能流进的几个"目的地"

投影目的地是什么例子
policy loss（RL 主训练）用"整条轨迹 + reward"来强化/抑制模型的行为，这是强化学习的主信号模型成功修好 bug → 这条轨迹被正向强化
SFT（监督微调）当"好例子"让模型照着模仿一条高质量成功轨迹拿来当模仿样本
preference（偏好）组成"A 比 B 好"的对比对训练两条轨迹比较，好的被偏好
negative sample（负样本）当"别这么做"的反例模型乱删文件 / patch 失败 → 当反面教材
quarantine（隔离）可疑，先扣下来人工 / judge 审查，不直接用疑似作弊的轨迹
diagnostic-only（仅诊断）只留着调试分析，永不进训练诊断侧通道 shell 的输出

② 关键陷阱：单个工具事件 ≠ 一个训练样本

计划反复强调一个易错点：policy loss 的训练单位是"一整条轨迹"，不是"单个工具调用"。所以不能把"一次 read_file"当成一个独立训练样本。registry 因此要分开回答两个问题：
• allowed_in_policy_loss_trajectory：这个工具事件能不能出现在一条用于 RL 的轨迹里？
• sample_policy_loss_candidate_effect：这个工具事件一旦出现，会怎样影响整条轨迹能否用于 RL？

③ 用一条轨迹把它讲透

假设模型解"修 parse_config"那道题，轨迹是：

read_file → grep → apply_patch → run_project_test → 提交
工具事件它的投影规则对整条轨迹的影响
read_file（已实现）allowed_in_policy_loss_trajectory=true正常，不影响轨迹资格
apply_patch（16G.1 时还没实现）allowed_in_policy_loss_trajectory=false让整条轨迹失格 —— 因为里面有个"还不存在的工具调用"，这条轨迹现在不能进 RL（可留作负样本）
若模型试图读 gold_patch（偷答案）deterministic hard fail整条轨迹失格 + 进 quarantine
所以 apply_patch 那条记录写 makes_sample_ineligible_until_tool_implemented 的意思就是："现在谁的轨迹里出现 apply_patch，那条轨迹就先别进主训练，等 16G.2 把这个工具真正实现了再说。" 等 16G.2 实现后，它的 allowed_in_policy_loss_trajectory 才会改成 true，含它的轨迹才可能进 RL。这就是"训练投影语义"——给每个工具事件规定它对训练数据资格的影响。

还有一条硬规则(计划 §7 第 17 点)：凡是 executor_binding_status=not_implemented 或 schema 还是 planned 的能力，禁止 allowed_in_policy_loss_trajectory=true —— 防止"工具还没实现就被误标成可进训练"。机器验收器会卡这一条。

4 · "artifact 语义"是什么意思 ★

artifact = 工具运行后产出的东西(stdout、stderr、traceback、生成的文件…)。同一份产出，对三种不同的"观众"要给不同的版本——这就是 allowed_artifact_visibility 那三个字段。

① model_visible 模型看到的

截断 + 脱敏的版本。够模型 debug，但不含敏感路径、不含完整长输出。

② raw_artifact 原始产出

完整原始输出，存到 runtime-private 文件，带 sha256。只给 harness 审计用，模型看不到、不提交。

③ export_projection 导出投影

进训练数据 / 公开 evidence 的版本，只放 public-safe 摘要 + sha256，无 secret、无本机路径。

用一个例子讲透

模型用 run_project_test 跑测试，失败了，traceback 很长，而且里面恰好出现了 <local-user-home>/.../runtime_private/secret_verifier.py 这种私有路径：

# ① 模型看到的（截断 + 脱敏）—— 够它判断哪里错
AssertionError at config_parser.py:42: expected 60, got KeyError
... (截断，路径已脱敏 [redacted])

# ② 原始 artifact（完整，私有，只给审计）
存到 runtime-private/run_xxx/tool_artifact_007.log
sha256 = a1b2c3...      // 模型看不到，不进任何导出

# ③ 导出投影（进训练数据的，只有安全摘要）
{ "tool": "run_project_test", "exit_code": 1, "result": "test_failed",
  "raw_artifact_sha256": "a1b2c3..." }   // 无路径、无 secret
这套三分法同时满足三个目标：模型拿到有用的失败反馈(能 debug)、私有路径/隐藏材料不泄漏给模型也不进导出、harness 仍保留完整可审计的原始记录。16G.1 要为每个工具写死这套规则，16G.3/16G.4 真正实现工具时必须照办。

5 · 顺带：拒绝反馈语义（denial feedback）

这是和上面并列的第三组规则。当一个工具调用被拒绝时，返回的不能只是一句"权限不足"，而要结构化、可学习，让模型知道怎么改：

字段意思 + 例子
reason_code为什么被拒（机器可识别的码）。例：execute_bash_git_history_or_metadata
retryable能不能重试。例：网络抖动→可重试；读 gold patch→不可重试
safe_alternative_tool该换哪个安全工具。例："别用裸命令翻历史，用 git_diff"
safe_rewrite_example给一个改对的写法示例

目的：让模型从拒绝里学会"换个安全方式再试"，而不是被吓得"少用工具、直接猜答案"。这也是为什么权限拒绝不能默认丢弃，要能进负样本/偏好/诊断信号。

6 · 机器验收器会查什么（防退化）

16G.1 不靠人读 JSON，而是让 CLI 自动检查。挑几条最关键的：

  • 计数对得上：27 条能力全进 registry、17 条阻塞项都有 owner stage、4 条 post-16G optional 都标了 schema reserved + revisit stage，且计数从 16G.0 重新推导(不许硬编码)。
  • 每个工具三组规则齐全：artifact visibility + denial feedback + training projection，缺一个就判不完整。
  • owner stage 不许偷改：每条记录的 owner_stage 必须和 16G.0 对照表里同一能力的 required_stage 一致；要改必须写 stage_override_reason 且同步更新源，否则验收失败。
  • 持久 shell 不许混进 core：硬检查 swe_public_core 不含 persistent shell。
  • 声明"已实现"必须真能解析：标 implemented 的工具必须在当前源码工具 registry 里找得到；找不到只能标 planned / not_implemented。
  • 没实现的工具不许标可进训练：not_implemented 却写 allowed_in_policy_loss_trajectory=true → 失败。
  • 代码事实核对：默认 scaffold simple_react、create_file 可见、mini_shell 不存在、execute_bash 窄但非空、diagnostic_shell 不属 core。

7 · 完成后解锁什么 + 我的提醒

完成态(status=passed)解锁 stage16g2_allowed_to_start=true —— 可以进 16G.2 动手实现文件工具了；但 17B/20/21 仍 false。完成态的准确含义是："工具能力还没补，但后续改造已经有了可机器验收、可追溯到 baseline 的契约。"

我的两点提醒（你/我 review 时盯这个）：
① 别让它退化成"只产 JSON、没有可执行验收"。计划已经要求 CLI inspector + 失败用例测试，review 时确认那些"失败用例测试"是真的会让 inspector 失败（比如故意把 persistent shell 塞进 core，inspector 必须报错），而不是摆设。
② run_episode smoke 别走过场。计划明确：只读 JSON / 只跑 builder / 只查文件存在不算通过——smoke 必须真的让 profile id 经过 EpisodeExecutionSpec 或 projection 这条真实路径。如果做不到只能出 blocked report，不能假装通过。
小结：16G.1 是把"该有哪些工具、各属哪档、各自怎么进训练/怎么脱敏/怎么给拒绝反馈"写成机器能查的契约。它本身不增强模型能力，但它是后面 16G.2–16G.4 所有实现的"图纸 + 验收标准"。你不细看计划没问题——盯住"机器验收器真生效"和"run_episode smoke 不走过场"这两点即可。
本文为 52-stage-16g-1-execution-plan.md 的汇报 + 概念讲解版。"训练投影 / artifact / 拒绝反馈"三组语义的字段和示例取自该计划 §6.2 的 registry 记录模板，例子(parse_config 轨迹、traceback 脱敏)用于帮助理解。
