① 阶段目标

Stage 3 只做一件事：把 RepoHarnessEpisodeRequest.run_mode（Stage 1 已经定义的枚举）真正连接到 recorder 行为。具体表现为：同一份 episode 输入，不同 run_mode 应该产出不同体积、不同保留粒度，但不能改变任务结果（verifier 判定、reward 计算、token / logprob 事实必须一致）。

一句话："换 run_mode 只换 artifact 保留策略，不换语义。" training_fast 砍体积时必须砍掉的是明文冗余（raw provider request 全文 / reasoning trace 明文 / 大 prepared messages），不能砍掉关键 evidence（patch、reward 引用、verifier 引用、artifact manifest、关键 hash、AuditRef）。

② 三种 run_mode 横向对比

每条 ✅ / ❌ / ➖ 都对应一个具体 recorder 字段或 artifact 类别。这是 Stage 3 验收时最重要的一张表。

full_audit

用途：评测、复查、人工调试。延续 Stage 0H / 1 / 2 现有行为。

✓完整 raw_provider_request 明文
✓完整 raw_provider_response 明文
✓完整 reasoning_trace（如 provider 返回）
✓完整 prepared_messages
✓全部 patch / reward / verifier 引用
✓AuditRef + artifact manifest + 关键 hash
✓timing_explained_ratio ≥ 0.95

training_fast

用途：在线训练 rollout。默认大幅压缩 artifact 体积，仍保留训练复查必需的引用。

✗raw provider request 明文（只留 hash + size + 截断预览）
✗raw provider response 明文（同上）
✗reasoning trace 明文（只留 hash + 长度 + bool）
~prepared_messages：要么完整保留，要么提供 projection artifact 同时更新 exporter / audit（不能静默改）
✓patch / reward / verifier 引用必须保留
✓AuditRef + artifact manifest + 关键 hash
✓artifact bytes 相比 full_audit 下降 ≥ 50%
✓timing_explained_ratio ≥ 0.95

training_debug

用途：训练过程出问题时的中间排查模式。比 fast 更详细，比 full 更节制。

~raw provider request：采样或截断后保留（manifest 标记 truncated / sampled）
~raw provider response：同上
✗reasoning trace 明文（不得因 debug 模式而默认放开）
~prepared_messages：可保留采样或截断版本
✓所有 sampling / truncation 在 manifest 中显式标记
✓不得隐式回退到 full_audit 或绕过 visibility
✓timing_explained_ratio ≥ 0.95

图例：✓ 默认保留 · ✗ 默认不保留明文（hash / 长度 / bool 等元数据仍保留）· ~ 部分保留 / 有条件

③ 8 条必须保持的硬边界

# 边界
1run_mode 只能影响记录粒度、artifact 保留策略、预算和执行记录方式，不能改变任务输入、workspace 语义、verifier 规则或 reward 计算语义。
2training_fast 不能通过删除关键 evidence 来制造体积下降。必须保留：patch、reward metadata 引用、final verifier 引用、trajectory 引用、artifact manifest、关键 hash、AuditRef。
3training_fast 默认不保存外部 provider 的明文 reasoning_trace / thinking_trace。
4training_fast 默认不保存完整 raw provider request / response 明文；需要保存 hash、大小、截断预览或 projection 引用。
5TrainingView.extra_fields 仍然只允许短小、扁平、repo_harness_* 命名空间字段和 opaque refs，不能放入嵌套 audit_ref、绝对路径、完整 reward metadata 或隐藏 verifier 材料。
6本阶段不能 import verl，也不能提前实现 RepoHarnessVerlAgentLoop、AgentLoopOutput 转换器、Ray / vLLM / SGLang 调度或真实训练侧 rollout。
7不能把缺失 token / logprob 的旧 provider 结果伪装成正式 online RL 样本。缺失正式 token 证据的路径仍然只能作为 diagnostic result 或 offline data。
8Stage 3 新增 / 改造的 runtime facade / recorder smoke 路径必须实现最小 TimingSummary，timing_explained_ratio ≥ 0.95。完整 ResourceSummary 留给 Stage 4。

④ 设计方案（6 个子方案）

数据类4.1 Recorder profile / policy

训练后端无关的 recorder profile 结构。具体放在 src/repo_harness/trajectory/recorder.py 或新建 trajectory/retention.py，不能放到 verl 命名空间。

# 建议字段（具体类型按现有代码风格定） mode: Literal["full_audit","training_fast","training_debug"] save_raw_provider_request: bool save_raw_provider_response: bool save_reasoning_trace: bool save_prepared_messages: bool prepared_messages_retention:Literal["complete","projection","hash_only"] artifact_compression: str | None artifact_sampling_policy: str | None raw_artifact_preview_chars: int # 截断预览长度
谁会用RunRecorder 接受可选 profile 参数（默认 full_audit 保持现有行为）；RepoHarnessRuntime.run_episode 把 request.run_mode 映射到 profile 后传给 recorder。
边界profile 不能写入 TrainingView.extra_fields 或 RepoHarnessEpisodeRequest。它是 runtime 侧策略。

扩展4.2 Artifact manifest retention 事实

让 manifest 能表达"这条 artifact 是被压缩 / 截断 / 采样 / 只留 hash 后写下的"，而不破坏现有 verify_artifact_manifest(...)。

# manifest / event 需要能表达的事实 complete | truncated | sampled | compressed | hash_only | projection_only profile · original_size_bytes · preview_size_bytes

实现策略：单独 facts artifact，不直接塞 ArtifactRef

  • artifacts.json 里每条仍保持现有 ArtifactRef 可校验形态。
  • retention 事实写入新 facts artifact，例如 artifact_retention_facts 或 artifact_projection_facts。
  • facts artifact 必须真实落盘，不能创建无文件的 manifest entry。
  • 记录字段：原始 artifact kind、原始大小、原始 hash、preview 大小、retention 原因、run mode、profile。
  • 如果将来确需扩展 ArtifactRef schema，新字段必须可选 + 安全默认 + 同步更新 manifest 校验测试。

链路4.3 run_mode 从 request 传到 recorder

RepoHarnessEpisodeRequest.run_mode │ ▼ RepoHarnessRuntime.run_episode(...) │ 把 run_mode 映射到 recorder profile ▼ recorder profile / recorder policy │ ▼ RunRecorder artifact writing behavior
注意陷阱：Stage 2 runtime facade 当前只做 1-turn fake gateway，本身不创建 RunRecorder、不写大量 artifact。所以 Stage 3 的"artifact bytes 下降 50%"验收不能只跑 runtime facade，必须额外新增一个 deterministic recorder test path：固定大 payload、固定 raw request/response、固定 prepared messages、固定 reasoning trace，分别用 full_audit 和 training_fast 跑同一组写入，再对比 bytes。runtime facade 只负责 run_mode → profile 的映射。

策略4.4 Raw provider request / response 投影

mode处理规则
full_audit保留现有完整记录行为。
training_fast默认保存 hash + 原始大小 + 截断预览 + projection / opaque artifact ref，不保存完整明文。
training_debug允许保存截断或采样后的内容，必须在 manifest 中标记 sampling / truncation。

特别约束：reasoning trace / thinking trace

  • training_fast 默认必须拒绝明文写入。
  • 可保留：不可逆 hash、长度、是否存在的 bool。
  • 不得放入模型可见字段或 batch 可传播字段。
  • model_client/provider_private_state.py 中显式 opt-in 的 reasoning trace training export 路径，不能在 training_fast 下被默认打开。只有 full_audit 或明确 diagnostic / export policy 才能保留明文 reasoning trace，且必须保持现有 explicit opt-in 语义。

⚠ 陷阱4.5 Prepared messages 的现有 exporter 强依赖

这是 Stage 3 最容易踩坑的地方。不能无脑把 prepared_messages 改成 hash-only。

现状（exporter / audit 的强依赖） exporter 会读取 model_input_snapshot 中的 prepared_messages_ref，并校验 prepared_messages_sha256 和 model_input_hash；audit 会确认对应文件存在、sha 匹配、JSON 可解析并包含期望 tool call / observation。

三选一兼容路径

  1. 路径 A · 保完整：training_fast 仍保留完整 prepared_messages_ref。在 bytes 分类报告中说明"因 exporter 强依赖暂未降级"。
  2. 路径 B · 加 projection：新增 prepared_messages_projection 或 prepared_messages_retention_facts artifact，同一 patch更新 exporter / audit 让 training_fast 能按 projection policy 校验。
  3. 禁止：静默把 prepared_messages_ref 换成无法过旧 audit 的 hash-only artifact。model_input_hash 不能被重新解释成另一个 payload 的 hash。

字段4.6 最小 TimingSummary attribution

Stage 3 自己覆盖的 runtime facade / recorder smoke 路径必须能解释 ≥ 95% 外层 wall time。完整生产级 TimingSummary / ResourceSummary 留给 Stage 4。
