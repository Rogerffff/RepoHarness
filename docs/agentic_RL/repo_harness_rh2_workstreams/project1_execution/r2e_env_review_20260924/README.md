## 2. R1 / P2：把“归因已知”当成“环境问题已解决”，导致资格结论过宽

**具体例子是 numpy `43e333e2`，不是对未来风险的猜测。** 作者自己的 [逐题 findings](../r2e_env_repair_20260924/tasks/numpy__43e333e2ff641f6dce852e46c9c650333b0d4b3d/findings.md) 第 3–16 行已经写清：

1. 题目相关的 `numpy/ma/tests/test_extras.py` 与普通公开测试均在收集阶段退出 4。`numpy/conftest.py` 调用 `hypothesis.HealthCheck.all()`，当前 hypothesis 的弃用警告被仓库 `filterwarnings=error` 变成异常。
2. 绕过警告后，pytest 8 不调用旧 nose 风格 `setup(self)`，出现 78 passed / 10 failed，失败类缺少 `data` 属性。这不是待修业务行为。
3. 隐藏测试放在 `numpy/` 外，不加载该 conftest，所以 gold 能通过。公开复现脚本也能出现题面错误，但二者都没有修好相关公开测试。
4. 作者明确写了依赖版本修复“本轮不做”，最终 [screening_record.json](../r2e_env_repair_20260924/tasks/numpy__43e333e2ff641f6dce852e46c9c650333b0d4b3d/screening_record.json) 却被并入 `environment_qualified`。

原始证据在 `runs/r2e_env_repair_20260924/p2/pubtests/` 与 `p2/followups/followups.log`；主审回查了异常与公开测试结果。

**出现原因有两层。** [checks_r2e.md](../r2e_env_repair_20260924/checks_r2e.md) 第 69 行把资格定义为若干评分检查、十项最小条件和“无未归因 issue”，没有区分已归因但未修复的开发故障。[run_dev_probe.py](../../../../../rh2/scripts/r2e_env/run_dev_probe.py) 第 161–165 行的十项确实不包含公开测试收集/运行；[apply_r13.py](../../../../../rh2/scripts/r2e_env/apply_r13.py) 第 50–64 行又允许 R13 通过后将其余状态兜底提升为合格。稳定复现一个坏开发环境也满足这些条件。

**影响与范围：** 这是当前资格工具和报告的可达问题，尚无证据表明这些记录已经作为正式 actor 的 `EnvironmentQualification` 消费。不能据此声称已有训练被污染；但用“42+1 合格”直接安排真实求解或发资格，会让本应由环境解决的依赖错误继续由模型承担。

**建议的窄修：**

- 保留“来源评分复现通过”和十条件通过；撤回全池环境已修好的概括。对已知相关开发故障、评分支撑缺口逐题保留未完成项，不急于给出新的合格总数。
- `apply_r13` 更新重复性事实即可；没有明确的逐题审核结论时，不根据 R13 单项自动补出环境资格。已有人工条件转移可以保留，但要明确它依赖哪些未完成项已经解决。
- numpy `43e333e2` 等明确历史依赖冲突进入环境配方修复或保留“开发条件受限、待修”。修后用同一解题身份验证相关公开测试能收集、执行，再做受影响题目的真实 noop/gold 对照。
- **不要求全仓公开测试全绿。** 业务 bug 在 base 上失败是正常信号；`python -m pytest`、正确工作目录等普通用法可作为条件。缺 pip 也不自动判坏。这里要处理的是实际阻断相关开发验证的依赖/支撑问题。

同样，pandas 隐藏测试缺 fixture、scrapy 缺测试资产不能仅因来源也失败就视作支撑完备；其修订要走现有材料 T0，但“待决定”不能消失在环境合格统计里。

## 3. R2 / P2：T0-5…7 的推荐依据包含过强推断，需要先修正

### orange3：固定 solver 不等于四个键对所有正确解都恒 FAILED

[T0-7 提案](../r2e_env_repair_20260924/material_revisions/orange3__9b5494e26f407b75e79699c9d40be6df1d80a040.md) 由目标测试要求 lbfgs 推出“所有正确候选恒 FAILED、假阴性风险低”，证据不足：

- 目标 `test_auto_solver` 只构造 estimator、检查 `.solver/.penalty`，不调用拟合，也不固定所有优化条件。
- 真实日志中 `result.message.decode` 在 **`result.status != 0`** 时才执行。选择 lbfgs 不证明每次都走这个错误分支。
- 另两个 scorer 失败在特征排序断言；将它们也归因于同一兼容问题仍是推断，作者详细记录自己保留了“未单独验证”。

可以确认 noop/gold 都有四个 FAILED；不能推出其他合理候选不会翻键，或换一个 SciPy 版本必修四键。请分开已证异常、待验证根因，撤回“所有正确解”的断言。具体源码和日志定位见[材料审 M1](materials_agent/README.md)。

### scrapy `cfed9b66`：相同 FAILED 隐藏了修复前后不同的异常

`test_instances_from_settings` 在 noop 中死于 `load_object(M2)` 对类调用 `.rindex`；gold 已通过这一步，才在搬迁后 M1 类身份错位的断言失败。[提案](../r2e_env_repair_20260924/material_revisions/scrapy__cfed9b6659c90e0799361911b1d72ed127edf471.md) 不能把二者都写成同一搬迁异常，更不能因此证明“任何合法改动翻不动”。

这仍支持测试搬迁有缺陷，却也说明当前映射不能检查这个实际修复差别。请分别记录 noop/gold 的失败位置；“部分解可满分”继续明确为源码推断，未做真实候选评分。无需为更正文案重跑。

### pandas：fixture 根因成立，两个后续判断还不是实验证据

- 58 个 ERROR 全来自 fixture 不可达，这一事实成立。直接把 expected 的 ERROR 改 PASSED 并不能修好它。
- [decisions.md](../r2e_env_repair_20260924/decisions.md) 第 31 行“原位公开测试同名用例全 PASSED”不适用于 `4ec87eb9`：`fixture_check/.../result.txt` 明确两项在 base 公共文件中 `not_found_in_base_public_file`。222 passed / 2 skipped 不能算验证了这两项。
- “候选在根目录补 conftest 会翻键，正确解得 0”有静态可达路径，但现有 fixture_check 是 root 下跑 base 公开测试，不是该候选的真实 RH2 判分实验。与 scrapy `9a15fcf8` 的已实测反例应区分。

这些更正影响 T0 推荐理由，不构成重开通用评分、hygiene 或本轮新增生产闸门的依据。
