## 2. 新材料改变了什么判断

### 2.1 不能把本地缺 parser 解释为 SWE-Gym 没有可用评分实现

O04 沿官方 `SWE-Bench-Fork@242429c1…` 找到了 11 个仓库的映射。此前 Claude 盘点指出的**当前安装依赖无法覆盖本地任务**仍然需要修；但“上游也没有实现”不是事实。正确下一步是还原原任务的命令、parser 和预期测试语义，再做少量实际对照。

这也不是直接换依赖就结束：例如 mypy 使用测试 case 表达式而非普通测试文件列表；某些官方评分路径允许 `SKIPPED` 脱离分母，空参考集合也可能产生成功结果。需要检查真实任务是否触发，而不是把整个上游重写成一个通用 pytest 评分器。

### 2.2 优先比较两个来源，避免被既有 216 题锁住

216 题是静态 ingestion 的存活资产，尚不是通过真实评分验证的训练集。DeepSWE 加强了 R2E-Gym 作为专项 RL 候选的证据，所以推荐同时取少量 R2E-Gym，而不是先把 216 题全部工程化再判断模型是否学得动。

可以从 Prime 已清洗的 R2E-Gym 子集开始，减少重复排查，但必须保留其验证定义。[官方数据卡](https://huggingface.co/datasets/PrimeIntellect/R2E-Gym-Subset-Verified)明确写明：初检失败任务会再试 10 次，只要至少一次通过就可能保留。因此 `Verified` 不能解释为“连续十次稳定通过”，也不自动证明无修改状态会失败。

首轮采用两个来源是信息收益与接入成本的折中。后续扩展时，优先比较 ScaleSWE、SWE-rebench 已有资产能否覆盖缺口，再决定是否自己采集 PR 和生产环境。现成任务很多，但可用镜像、可靠评分和目标模型的学习机会仍须分别验证。

### 2.3 不提前决定“先 SFT”或“直接 RL”

DeepSWE 的直接 RL 正例不能证明我们的 Qwen MoE 起点也适合直接 RL；OpenThoughts-Agent 的冷启动收益也不能证明所有模型都必须 SFT。同一题源对不同训练方式可能有不同价值。

首先区分：模型不会调用工具、模型会执行但解题能力不足、预算不合适、评分错了。只有前两类才可能支持换起点、补 SFT 或调整训练题源；后两类需要先修运行条件。若使用 SFT，保留同一 SFT checkpoint 作为 RL 的起点与基线，单独报告 SFT 和 RL 的增量。

### 2.4 “任务可靠”“当前可解”“训练有价值”分别记录

参考修复能通过，只证明这个参考解在该环境下有效。当前模型 0/4，不证明任务不可解或永远无训练价值。参考解成功率、当前模型采样成功率、训练后的独立评测增益，不能压成一个通用数据质量分。

例如每次独立成功概率为 20% 时，4 次全失败的概率仍是 `0.8^4 = 40.96%`，8 次全失败也有 `16.78%`。少量采样适合发现错误模式，不足以给每道题精确定难度。不能把 0/4 直接写成永久剔题条件。

### 2.5 项目价值需要由受控结果支撑

新的系统资料进一步说明，fresh grader、轨迹捕获、异步执行和已有任务接入本身已不是足够独特的贡献。我们需要展示这些部分接到真实 Claude Code 后，**评分和训练语义是否保持正确，完整任务成本是否下降，同样预算是否得到更多可信学习信号，并带来独立任务上的提升**。

可以借助成熟组件形成强项目，但不能把上游功能全部归成自己的实现，也不能把环境筛选后剩下的高分解释成模型变强。后续实验应保留原始候选漏斗和失败分布；不需要故意训练一个已知语义错误的基线来证明修复有效。

## 3. 现在讨论的五项决定

下面按依赖排序。B1–B4 决定首轮准备与实现边界；B5 分为现在确定运行原则、准备结束后确认具体资源。**这是一次阶段级选择，不需要每个小步骤重新审批。** 重大语义或成本变化仍按已有协作协议处理。

### B1：首轮学习目标与 terminal 的位置

- **要决定什么：** 第一轮是否聚焦真实 Python 仓库中的缺陷修复与回归保持；terminal 是否暂时只用于补充诊断/迁移评测。
- **现状：** 当前 rh2 资产和评分积累偏 SWE/Python，SWE 真实基座诊断尚未完成；terminal 需要额外环境、评分和任务覆盖。
- **可选方案：** A. SWE 先做扎实，terminal 暂作候选补充评测；B. SWE 与 terminal 同时建设并联合训练；C. 先只做便宜的函数级代码题。
- **推荐 A：** 它最直接检验项目“真实 coding 工作流的可靠 RL 链路”主张，同时控制首轮适配成本。C 可以以后作为桥接数据候选，但不能替代真实仓库验证。
- **代价与可改性：** A 暂时不能支持通用终端或多语言能力主张；来源和训练范围可以扩展。若首轮就混合训练，后续更难定位收益来源。

### B2：候选来源与第一批开发题

- **要决定什么：** 是先全做本地 216 题，还是先对照来源、再扩大。
- **现状：** 216 题覆盖 9 个仓库，尚无整体真实评分证据；R2E-Gym 有直接 RL 的外部证据和现成清洗子集，但我们尚未验证其镜像及适配成本。
- **可选方案：** A. SWE-Gym 与 R2E-Gym 各取代表性小批；B. 只做 SWE-Gym；C. 同时全面接四个来源并开始 PR 生产。
- **推荐 A：** 首批以 **12 道 SWE-Gym + 12 道 R2E-Gym，共约 24 道开发候选**为起点；按仓库、测试形式、修改跨度和预计运行时间分层。SWE-Gym 覆盖现有仓库及 mypy/conan 等特殊命令路径；R2E-Gym 避免只抽最便宜的一类任务。确切题单由资产盘点给出，24 不是硬性验收数字。
- **代价与可改性：** A 多一个来源适配，但能尽早发现本地资产偏差。B 启动较窄，却可能为不适合当前模型的题池做过多工程。C 首轮成本大、归因困难。后续可调整配比；在看结果后换题必须保留原候选、原因及补位次序，不能只公布存活者。
- **边界：** Prime 的清洗子集与原 R2E-Gym 共享来源，不是两套独立数据；首批样本不是正式训练集，也不要求 216 题全部过完才开始诊断。

### B3：环境/评分可信度如何定义

- **要决定什么：** 如何复用上游评分，什么证据足以让题目进入首轮诊断，以及如何保留异常。
- **现状：** 已批准 fresh grader；本地命令/parser 缺口待补。不同来源对 skip、空集合、参考测试和补丁应用有差异，单靠进程返回码或“官方 Verified”标签不够。
- **可选方案：** A. 复用来源专用命令/parser，显式核对任务预期与正反控制；B. 完全信任上游成功字段；C. 先建设统一评分平台并全面重写规则。
- **推荐 A：** 对修复类任务实际运行无修改状态和参考修复：目标故障应能重现，参考修复应解除故障并满足已声明的回归要求。`SKIPPED`、空解析或未执行不能作为目标测试通过的证据。少量代表任务重复执行，并用简单错误补丁及已知可行的替代修复检查明显误奖/误杀。
- **具体区分：** 空 `PASS_TO_PASS` 是回归证据缺口，不能仅据此宣判题目无效；任务正常执行后的错误修复、由候选补丁引起的测试失败，与依赖安装失败、parser 不支持、评分服务异常分别记录。超时需要过程事实，不能一律猜成模型错或 infra 错。上游原评分与我们的环境质量判断分别保存；若改变官方判分，不能把结果冠名为未经修改的官方指标。
- **代价与可改性：** A 增加少量控制实验，但能直接定位错命令和错奖励。B 最便宜，却可能训练错误目标；C 尚无足够任务反例支撑设计。先形成任务事实与薄适配，**任何训练拒绝规则或公共 reward 分类变更需与 A 合并，不能由 B 悄悄增加**。本阶段不是批准新的通用 schema 或自动剔题阈值。

### B4：划分与评测证明什么

- **要决定什么：** 开发题与最终测试如何隔离；成功率如何处理系统错误和多次尝试。
- **现状：** 当前没有已落地的正式 train/dev/test 产物；旧 8 题 Verified 是基础设施探针，不能充当独立效果证明。
- **可选方案：** A. 先划分缺陷/PR/派生家族，预留仓库层面的独立测试空间；B. 全池随机按行划分后反复看最终成绩；C. 只报一个公开榜单分数。
- **推荐 A：** 首批 24 题全部归开发诊断。先核对既有 held-out 候选和仓库预留，避免同一缺陷、修复或合成变体跨集合；之后再冻结正式题单。最终用独立保留任务验证泛化，以公开 SWE 基准补充可比性。仓库隔离、时间隔离分别标注，不能承诺仅凭这两项排除预训练污染。
- **分数原则：** 固定 checkpoint、harness、工具、预算、采样及 grader，比较训练前后。单次平均成功率、多次至少一次成功、选优后的成绩分别报告。所有计划尝试都记账；系统异常单独列原因和覆盖率，不从报告中消失。可同时给“成功/全部分配尝试”的端到端完成率和有有效评分尝试的条件成功率，前者包含运行可靠性，后者有选择偏差，二者都不能单独解释全部模型能力。
- **重试原则：** 诊断保留首次失败事实；若需要重试，事先说明允许的系统原因、次数和成本，不把重复采样直到成功记作 pass@1。训练的丢组规则不自动成为评测分母规则。按 task/repo 报告分布，避免把同仓库、同任务的重复尝试当成完全独立样本。
- **代价与可改性：** 独立保留会减少可用于调试的数据，却决定最终结论是否可信。题量和置信区间方案可以等成本/方差实测后决定；已经用于选模型、调提示或选配方的结果，不能事后重新命名为未见最终测试。

### B5：基座诊断对象、运行协议与资源

- **要决定什么：** 先测当前计划模型，还是先做模型海选；在什么条件下将一次诊断称为后续基线。
- **现状：** 仓库实验脚本及 A 的 tokenizer 核验指向 **`Qwen/Qwen3-30B-A3B`**；这不是 `Instruct-2507`、`Thinking-2507` 或 Qwen-Coder。现有脚本仍有草案限制，不能直接当成已验证的独立评测入口。目标模型在真实 Claude Code 下的完整能力基线仍缺失。
- **可选方案：** A. 先测当前计划 checkpoint，失败归因后再决定是否比较一个更合适的 coding 起点；B. 立即并行测多个模型并选最高分；C. 先 SFT 再测。
- **推荐 A：** 固定实际模型/权重与 tokenizer revision、精度、Claude Code 版本、真实上下文、工具/子 agent/压缩设置、采样和预算。先用与拟训练配置一致的推理精度做诊断；如果先用量化版探索，明确它是另一个实验条件，不能直接替代正式基线。保留模型原始请求、工具执行、交付工件、结束原因、评分和成本。
- **现在与稍后分别决定：** 现在选诊断对象和固定协议原则。准备完成后，再用真实环境耗时、A 可用入口与硬件报价确定 turn/action 上限、wallclock 上限、并发、GPU/CPU 时长和花费上限。建议先 2–4 道完整轨迹 smoke，再扩为同一协议下约 24 题 × 4 次尝试；它用于诊断，不用于宣布显著提升。
- **代价与可改性：** A 可解释性强、成本有界；B 花费与选模偏差更大；C 会遮住当前模型的真实短板。如果当前起点不适合目标任务，可以换起点，但需重新建立基线。不能为了让提升幅度好看而坚持明显过弱的基座。

## 4. 拍板后如何推进

### 第一段：先产出可审查的题单、评分对照和运行方案

1. **候选资产表与暂定划分。** 每题保留来源和版本、原仓库/缺陷/派生关系、题面、工作目录、base/修复 commit 的实际含义、镜像与依赖、参考修复、测试命令与预期测试、许可及公开材料边界。先用简单可读的表和 manifest；不提前冻结所有未来题源的统一格式。
2. **最小来源适配与控制实验说明。** 各来源先挑 2–4 道有代表性的任务，将原评分命令、解析结果、预期测试与 rh2 结果逐项对照。无修改检查必须真的执行，不能被“空补丁直接判失败”的快速路径替代。先定位命令/依赖/parser 问题，再扩大到约 24 题。
3. **具体资源计划。** 根据镜像大小、拉取/构建/测试耗时、可用入口、预计存储与 CPU/GPU 并发估算费用，明确在哪一步需要付费运行。参考论文的几十张 H100 或几千个容器不能直接缩放成我们的报价。

如果当前没有合适的 x86 Docker 条件，先完成题单、薄适配和精确命令，再按具体配置安排 CPU 验证。这里不预先授权租机、付费 API、GPU 测试或全量镜像下载。

### 第二段：先证明环境，再诊断模型

- 首批 24 个候选各做一次无修改/参考修复对照，约 **48 次 CPU 评分执行**；先跑小组验证入口，再扩大。对约 6 个覆盖特殊命令、长耗时或疑似波动的任务各额外重复两组，额外约 **24 次执行**。这些是容量估算，重复三次仍不等于证明永久稳定。
- 正反控制用于发现评分错误；少量可人工核验的错误补丁/替代修复用于检查评分是否只认参考实现。按实际反例决定补哪些检查，不给每题强加大量相同测试。
- 对验证后的开发题做 2–4 道真实 Claude Code smoke，检查工具、上下文、工件与评分的全链，再按 B5 运行约 **96 次尝试**。提前保留失败原因和完整成本，不从统计里删掉慢任务。
- 若追加到每题 8 次，只把共同的前 4 次用于首轮横向比较；追加样本属于探索分析，不能把不同次数的“至少成功一次”直接排在一张能力榜里。小样本先看失败机制与按题分布。

环境对照不需要大模型 API；基座诊断也不必等待所有训练性能优化完成，但依赖可用的执行、工件与评分入口。它不能替代 A 对真实轨迹投影、梯度、policy version 和样本消费的检查。

### 第三段：带着结果决定真正的训练实验

| 观测 | 下一步讨论 | 不能直接推出的结论 |
|---|---|---|
| 参考修复/无修改控制异常 | 修环境、命令、parser 或参考定义；必要时换来源 | 模型太弱、需要 SFT |
| 环境可靠，但工具协议/上下文处理出错 | 先修 harness 适配并重跑同题 | 任务本身太难 |
| 模型正常执行，但大部分任务都没有成功迹象 | 检查预算与任务覆盖；比较更合适起点、少量 SFT 或较易任务的成本 | 0/4 就永久不可学；全部难题应自动删除 |
| 有成功/失败差异且评分可信 | 使用已选训练链做小规模静态题池 RL；先与同起点比较 | 必须先做在线课程或大规模环境生成 |
| 平均成功率可用，但损耗集中在长任务/特殊仓库 | 修系统瓶颈，报告覆盖与耗时分布，再考虑调度/采样实验 | 只保留短题就证明了 infra 提效 |
| 训练池可用但独立仓库/任务类型覆盖不足 | 优先比较 ScaleSWE、SWE-rebench 等现成增量；再做针对性 PR/合成试产 | 需要立刻自建十万题生产平台 |

**推迟到这一阶段的决定：** 正式训练题量和配比、SFT/直接 RL/OPD、课程和难度过滤、terminal 联合训练、是否自采 PR/合成、正式最终测试题量与统计功效、系统优化的训练对照规模。这些选择现在可以列备选，不能用外部论文替我们完成实测选择。
