## 2. 应改正的四处

### F1 / P2：把兼容导出当成正式导出，并把单一构建失败推广到了所有 C 扩展

**位置**：[候选评分报告](../r2e_static_review_batch2_20260925/grader_candidates.md):144；[批次 README](../r2e_static_review_batch2_20260925/README.md):72；B 线账本本批末条的同类描述。

orange3 `4014f248` 的直接证据成立：

1. C2 只改 `.pyx`，正式回放为 26/27、reward=0；评分不自动构建，仍在使用旧扩展。
2. 同镜像以 root 真正运行 Cython/编译后为 27/27；这证明源码修法可以工作，但不证明 agent 或候选评分身份能完成构建。
3. agent 真正修改源码后运行该题 `build_ext --inplace`，链接器报 `cannot find -lpython3.7m`；`LIBDIR` 指向 `/root` 中不可遍历的旧路径。这个开发条件缺陷应修。

**不成立的是“正式 `git add -N + git diff` 不交付被忽略的 `.so/.c/build/`”。** 当前 `fa_formal` 在 `generate.py` 调 `export_frozen_patch`，基于 census 的字节差异；`patch_exporter.py` 明确不调用 Git。R2E 排除 `.git/.harness/.venv` 及约定缓存，`.gitignore` 不决定交付。探针中修改的 `.so`、生成的 `.c`、`build/*.o` 均被导出、保留在评分投影，并由真实 manager 应用循环按原字节重放；初态未变的 `datasets` 不会混入。

因此应分开三件事：**源码提交需要构建、agent 的构建环境失效、已有构建产物能否正确交付和加载**。本轮证明前两项中的 orange3 实例，以及第三项的字节运输能力；没有跑“agent 真正编译 → 正式冻结 → fresh grader 导入”的完整原生链。

同样，不能从 Python 3.7.9 的这条命令推出 numpy/pillow/pandas 的任意扩展都链接失败。不同解释器和构建系统的链接参数不同；本批 pillow 日志就是 Python 3.9.21。其它仓库列为同类风险待核实即可。

**建议修文后再定方案**：先恢复这道题的真实 agent 构建能力，确认所需库/头文件/运行时链接路径，而非预先承诺改一个 `LIBDIR` 就完成；评分代为构建另行按题定。不能以此次错误的导出推断为理由排除候选自己构建的可行路径。详见 [切片与探针](build_review/README.md)。

### F2 / P2：已知会抖动的测试键，仍被写成失败后自动归环境

**位置**：aiohttp `1c1c0ea3` 的 [screening_record.json](../r2e_static_review_batch2_20260925/results/aiohttp__1c1c0ea353041c8814a6131c3a92978dc2373e52/screening_record.json):312，以及 [old_findings_delta.md](../r2e_static_review_batch2_20260925/results/aiohttp__1c1c0ea353041c8814a6131c3a92978dc2373e52/old_findings_delta.md):66。

原文建议该键在 RH2 翻转时“按环境抖动归因”。但现成 C5 补丁删掉主任务优先取消，同一个 `test_shutdown_handler_cancellation_suppressed` 在第 1259 行抛 `CancelledError`，不是历史记录里的首次连接 `ConnectionRefusedError`。该补丁另有多个关闭流程测试失败；它不能因撞上一个已知抖动键而获得免责。

**改法**：该键只触发“疑似时序问题，需看失败堆栈和同条件对照”；保留原始 reward，核实候选语义后才区分候选错误、环境抖动或未确定。无需新增 runtime 闸门。首批已经接受的“相同失败键不等于相同根因”应在这里同样落实。

6 次 gold 确实同时运行，测试区间共同重叠约 28.6 秒且全部通过；这支持本次未复现历史抖动，不证明以后不会发生。scrapy K2 的 5 次失败也只能写成“本批未见假通过”，不足以关闭所有时序风险。见 [原日志、补丁及独立复核](aio_scrapy/README.md)。

### F3 / P2：满分并不保证“题面那一例修好了”

**位置**：[批次 README](../r2e_static_review_batch2_20260925/README.md):70。

这句话弱于“整个问题解决了”，但仍超过证据。现成反例有：

- pillow `3a61c9e9` 的 W5 原地把输入 RGBA 调色板改成 RGB，输入和输出都丢 alpha，却因为测试在调用后才取原图作比较而满分。
- aiohttp `22a12cc2` 的 K3 在代理路径上仍接收错误指纹，真实行为与 base 一样，却满分。
- coveragepy `ea6906b0` 的空 `.gitignore` 满分，实际没有忽略任何输出文件。

应改为：**reward=1 只说明当前测试集合与来源判分规则通过；题面示例、一般语义和回归需要另作核对。** 对当前诊断作业分列原始 reward 与语义核对结果，不把这些后检静默塞进训练 reward。

### F4 / P2：不能为了让 gold 继续通过，把公开需求的缺口判为题外

**位置**：numpy `5e8301c2` 的 [card.md](../r2e_static_review_batch2_20260925/results/numpy__5e8301c2b36097dd8be5a12e0bb4369a1df4fabb/card.md):49，以及 [review.md](../r2e_static_review_batch2_20260925/results/numpy__5e8301c2b36097dd8be5a12e0bb4369a1df4fabb/review.md):154。

原建议“不加 tensordot/多操作数断言：gold 过不了，这等于扩大需求”，复核又以上游另立 issue 支持。这里混淆了**参考实现的覆盖程度**与**公开题目的要求**。

公开描述泛指优化时 singleton 维度的广播，没有排除求和维。已有最小反例只需 `np.einsum('i,i', [2., 3.], [4.])` 两个输入：本 base 默认 `optimize=True`，gold 抛 `shape-mismatch for sum`；`optimize=False` 与 C-A 都返回 20。主审已回读公开描述及三份 `extra2` 原输出。不能仅凭 gold 失败，或历史上分两次修复，就认定该输入必然在当前题意之外。

**改法**：把双操作数的单例求和维与更广的多操作数/路径规划分开。前者记为有公开依据的已有缺口；如以后补测，要如实说明旧 gold 会失败。是否现在补测试仍由用户决定，本轮不改分，也不因此要求立即修 gold。详见 [NP-2](numpy_pillow/README.md#np-2--p2numpy-的-gold-失败不能用来划定公开修复范围)。

## 3. 两项统计/用途口径与脚本使用提醒

1. **“gold 有缺陷的四题”应拆成三题有具体不完整/回归反例，一题有未定性的行为变化。** numpy 求和维广播、scrapy 的两项 TypeError 与二次 fetch 挂起有具体反例。pillow `3ac9396e` 的小整数 TIFF 字段从 LONG 变 SHORT，值仍以 `int` 读回；公开接口允许类型推断，目前没有证据说明必须是 LONG。不能仅凭 wire 类型码变化就计入缺陷。另一个候选 C6 把整数改成 `IFDRational` 才有不同的返回类型证据，二者不能混为一谈。见 [纯 Python 原函数探针](numpy_pillow/README.md)。
2. **36/48 是机械命中统计，不是已逐题确认的泄漏下限。** 32 个代码行信号、26 个测试名信号、并集 36 的计数复算正确；新增四题的目标函数确实能定位到别题初态。numpy 的重构实现已有人工补证，部分测试函数 AST 也相同。但算法自己允许同名误报，故不能同时称其为可靠“下限”。优先按仓库分留出；若按时间分，还要检查后来的训练初态是否已含较早留出题的答案，时间标签本身不消除泄漏。见 [计数与抽核](main/cross_task_counts.json)。
3. **许多私有语义脚本是打印诊断，不是返回布尔判定的验收器。** 例如 coveragepy RE 的公开测试失败，外层因为 `| tail -5` 仍 rc=0；scrapy 挂起的 124 也记在打印结果中，外层脚本可为 0。这不推翻报告已按输出作出的结论。复用于下一波自动后检时，必须明确读哪些结果、哪些是失败、哪些是未确定；不能统一用外层 rc=0 当通过。已有结构化 `RH2_POSTCHECK` 的脚本可按其分项值使用，不必把所有临时探针改造成新平台。
