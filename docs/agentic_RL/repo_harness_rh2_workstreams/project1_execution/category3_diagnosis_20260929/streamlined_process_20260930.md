# 第3类精简流程（09-30 起，用于剩余 49 题）

2026-09-30 / Claude（云端，第3类负责人）。用户 09-30 要求：对照 MiMo-V2.6 技术报告 §4.2 精简流程，加快处理、减少额度；子代理改用 Sonnet 5.5。本文件是**当前生效的流程**，替代 [batch2_author_brief.md](batch2_author_brief.md) 中与之冲突的部分。已完成的 18 题不按本流程重做。

## 1．为什么改

- **前两批的成本**：18 题用了约 20 个子代理，每个 40 万～58 万 token。多轮复核，每轮新造 8～18 个候选、跑数百格私有结果；每版修订正式评分 20～40 次。用户估计已耗去约 10% 的周额度。
- **收益集中在少数几步**：决定性对照、需求—测试对照表、一次有针对性的独立核查。后续轮次多是在已明确的修法上继续加实例。
- **Codex 09-30 的要求本就偏精简**（[接续反馈](../category3_cloud_review_20260930/claude_feedback.md) §3）：
  - 一项问题优先一个能区分原因的对照；
  - 候选类别是排查提示，不必凑齐；
  - 正式材料落地、最终候选矩阵与用途验收可以由第2类负责；
  - 阻断修正后只做聚焦复核，不自动再审全题。

## 2．对照 MiMo-V2.6 §4.2.1 的做法

依据是本仓库精读稿 [mimo_v2_6_technical_report.md](../../../../harness_improve/external_paper_references/reading_notes/mimo_v2_6_technical_report.md) §5.2–5.3。原报告对 coding 环境的监督质量做三件事：

| MiMo 的做法 | 本流程的对应 |
| --- | --- |
| 先校准行为范围：测试接受满足规格的实现、拒绝违反规格的实现，不强制参考解的偶然细节；强迫题面没有的要求就改或删测试 | 保留，作为每题的需求—覆盖表（B 步），也就是统一标准 v1 的 R-b／R-c 判断 |
| 每题 4 次真实求解；审计 agent 先写出正确解要满足什么，再逐个判断候选并与 reward 对照，找误收与误拒 | 剩余 49 题只有 2 题有现成的真实模型解，不另造 4 次求解。改为：审计者在读 gold 与测试之前**先盲写一个自己的修复**作为自然候选（A 步），再加每个疑点一个决定性候选 |
| 参考补丁重跑 8 次，查不稳定测试 | 这批题已过环境检查，不重做；只在某次结果出现不一致时，对那一格重跑一次 |
| 审计模型的判断只是复查线索，不自动当真值 | 保留：私有模拟与正式评分分开写；“审计者认为正确／错误”的判断要给出违反的公开要求 |

## 3．不变的底线

- 规则仍以[统一标准 v1](../task_screening_standard_v1_20260925.md) 为准。每题落到三种结论之一：可转第1类／转第2类并交接／仍有具体问题（写明缺什么、下一条命令、谁决定）。
- Codex 09-30 的三条原则：
  1. 题面建议的实现方式不升级为强制要求；
  2. 已知错误候选不因“少见”“不自然”放过；
  3. 给出停止条件。
- 读原件后先写初判，**封存后**再读历史结论。独立核查仍由另一个不继承上下文的子代理完成。
- 每组实验结束就归档证据（`archive_evidence.py`），并扫描凭据字样；不写入密钥、token、本机私有路径。
- 只有两种读法都有公开依据时，才按 P5 交用户。

## 4．每题流程（审计者：一名 Sonnet 子代理，按仓库成批处理 2～4 题）

| 步 | 做什么 | 上限 |
| --- | --- | --- |
| 0 起点 | 从工作清单登记的具体疑点和已有静态题卡开始；公开阅读、环境恢复已完成的，只复用，不重做 | — |
| A 盲写自然候选 | 只看题面与 base 代码，写一个自己的修复 N1；记下 sha256 后再读 gold、测试与历史结论。初判（5～10 行）同时封存 | 一个候选 |
| B 需求—覆盖表 | 列出公开要求：事实、推断、需要选择的目标分开写；逐条标注隐藏测试是否覆盖、是否过严 | ≤ 10 行 |
| C 决定性实验 | 每个登记疑点一个决定性候选，加上 gold、noop、N1；私有模拟按参考名单计分。只有结论依赖、私有结果又不够时，才跑正式评分 | 候选 ≤ 6；私有运行 ≤ 30 次；正式评分 ≤ 4 次 |
| D 结论与修法 | 三选一；需要修订时，只用同一小候选集私测草案 | 不追加新的候选家族 |
| E 结论页 | 按 §6 模板写 `tasks/<id>/result.md` | ≤ 80 行 |

## 5．轻量独立核查（核查者：一名 Sonnet 子代理，一次核 4～6 题）

- 每题先写 5 行初判并封存，再读审计者的结论页；
- 只核**最强结论**，以及修订断言：
  - 是否过严，会误拒合理实现（原则 1）；
  - 是否有一个明显的错误写法能绕过（原则 2）。

  最多另造 2 个候选；
- 发现阻断时给修法并私测。负责人采纳后直接交第2类，本线不再开复核轮次；
- 修订版的正式诊断评分与最终候选矩阵，由第2类在 D6 落地后按停止条件完成（先例：moto-6185、pillow a682）；
- 核查结论写进同一题页的“独立核查”小节（≤ 20 行），不另写长篇 review.md。

## 6．结论页模板（≤ 80 行）

1. **结论**（三选一），以及一句话理由；
2. **需求—覆盖表**（B 步）；
3. **候选与结果表**：候选、性质、原材料、修订草案；私有与正式分开写，并注明 sha256 前缀；
4. **判定**：v1 §4 的步号与 S1／S2／T 标签；
5. **修法与交接**：采用版本、正对照、预期结果、停止条件、只登记不阻断的项；
6. **未做与证据**：证据目录、镜像与配方身份。

## 7．负责人

- 每批抽查 1 题的关键数字；
- 每题在 README 状态表写一行；转第2类的题追加一条交接；
- 每批提交一次。
