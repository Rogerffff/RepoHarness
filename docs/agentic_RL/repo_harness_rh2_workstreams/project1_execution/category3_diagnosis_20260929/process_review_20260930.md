# 为什么 30 道 SWE 题走完前序流程仍在第3类：流程复盘

2026-09-30 / Claude（云端，第3类负责人）。回应用户 09-30 的问题：这些题做过环境修复、静态筛查、agent 开发环境调查，为什么还不知道怎么修。只读既有记录，没有新增运行。依据见文末。

## 结论

**不是题目特别难，也不是缺少分析，而是前序流程在设计上停在“提出实验”，执行实验和拍板目标这两步没有落到任何人头上。** 第3类记录的是“还没做完的检查和还没做的决定”，是我们的工作状态，不是题目坏的程度。

| 30 道 SWE 第3类题 | 数量 |
| --- | --- |
| 环境与评分已验证（历史 grader noop／gold 跑通） | 30／30 |
| 静态筛查已完成（题卡＋独立复核） | 30／30 |
| 静态筛查提出的决定性实验，**之后从未执行** | **27／30**（其中 10 题进了 CPU 队列，队列状态至今是 `not_executed`） |
| 实验已在 09-29 CPU18 跑过，卡在“目标范围没人拍板” | 3／30（conan-13721、pydantic-5706、mypy-15139） |

| 正式 actor 开发核对已做 | 10／30（与是否在第3类无关，见发现 4） |

## 发现

1. **静态筛查的出口是“线索＋待执行实验”，执行环节没人负责。** 静态筛查流程写明本身不做运行（[静态筛查流程](../swegym_task_audit_20260920/static_screening_workflow_20260921.md) 开头与 §4），每题产出一个“最小、可区分的下一实验”。两份实验队列都停在未执行：
   - 09-21 批 14 项，状态 `not_executed`，负责人写“总协调者另行安排”；
   - 09-25 扩展批 12 项，状态 `not_executed`，`dispatched: false`，负责人为空。

   09-29 的 CPU 预探针只覆盖了 18 题。多角色阅读做足了，真正能定结论的几分钟对照却一直往后推。
2. **范围题缺少“拍板”这一步。** 静态流程要求区分事实、推断和需要选择的目标，但不授权任何角色按公开依据选定目标；修订机制 D6 当时也还没有。所以 14 道范围题只能登记“需核定”。第3类已处理的 18 题中，目标都能由审计者按公开依据定下来，只有 3 题真正需要用户选择（coveragepy-5dbbe、dask-9378、coveragepy-f5eb）。
3. **标准在筛查之后抬高了，但没有配套补实验。** 09-25 统一标准 v1 引入 D1 严格版第 4 步与 R-a–R-f；09-29 分类 v2 撤销事后审计许可，原第1类 38 题中 8 题改入第3类。题的信息量没变，分类变了，形成新的积压。
4. **环境修复与 agent 开发环境调查回答的是另一个问题。** 它们验证“能不能评分”“解题者能不能在环境里开发”（[共用开发验证流程](../actor_development_validation.md)），不判断测试是否正确。30 题中只有 dask-8597 带开发环境标签，其余都是题面、测试或 gold 的语义问题。把三个流程并列看作“完整流程”，容易产生“走完就该知道怎么修”的误解。
5. **独立复核核的是推理，不是事实。** 静态阶段每题有公开读者、主审、独立复核、协调验收四层阅读，复核能纠正论证错误（例如 moto-5406 的改名误判），但复核不跑实验，疑点仍是“疑”。第3类的经验正相反：每题 1～3 个决定性对照就能定案。已处理的 18 题中 16 题转第2类，登记的疑点大多被证实。
6. **分类把“题目缺陷”和“工作进度”混在一起。** 第3类的三种缺口所需的工作不同：待执行对照 15 题、待决定目标 14 题、待找正对照 1 题。统计成“30 道不知道怎么修”，会高估题目问题、低估积压的执行工作。

## 建议

- **把“静态审查＋决定性实验＋修订草案”合成一个环节**，每题必须以三选一收口，不再只交线索（即[精简流程](streamlined_process_20260930.md)的做法）。
- **授权审计者按公开依据选定目标**，只有两种读法都有公开依据时才交用户（P5）。
- **标准变化时**，按受影响条款对相关题补跑对应实验，不整体改分类。
- **actor 开发核对作为普通探针前的就绪条件单独排期**，不和质量诊断混在一起。
- **第3类统计改为“待执行对照 N、待决定目标 M、待找正对照 K”**，与题目缺陷分开报告。
