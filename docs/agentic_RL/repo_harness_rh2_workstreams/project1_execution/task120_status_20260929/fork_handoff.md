## 开工先对齐

1. 分叉留在当前共享目录。未提交文档和被忽略的 `runs/` 证据不会自动出现在新 worktree 中。先确认可读本文件、[分类说明](README.md)、[固定起始题单](fork_worklists.json)及所领题目的原件。
2. 当前用户已明确：影响合理求解或评分的已知问题先处理。旧作者卡的 `probe_ready`、旧“受限比较＋事后审计”不作为普通探针豁免；逐题按当前分类与理由继续。
3. 核对相关线程与机器的实际在途作业，再领取题目。特别是R2E已有负责人，不重复启动其正在运行的实验；本交接没有声称旧机器仍可用。每题记录唯一持续负责人。
4. 复用版本适用的环境、静态审查、开发验证、正式评分和独立复核。不因换负责人重跑全矩阵；也不把旧运行条件自动当成新条件。
5. 分叉继承私有材料。需要新的公开读者或独立初判时使用干净上下文；实际求解模型只接公开面与干净仓库，不能继承调查者的答案知识。

## 两边如何交接及回流

每次交接至少包含：题ID；负责人；原类别与新类别；材料／镜像／代码／预算版本；问题和实际改动；正反对照与开发验证；独立审查；全部重要剩余事项及影响。

- 线程一复核交付版本后加入统一队列；不是再从静态审查起点重做。
- 只修评分材料时，评估旧工件能否在新版本重评分；更换公开任务或开发条件，若要比较新条件下的模型行为，另建干净尝试。
- 新发现导致暂停时按影响范围处理：单题、同配方、单模型或公共组件。无关证据分析可继续；不默认整池重跑。
- 两线程各维护自己的执行记录与逐题证据，不并发改同一份题卡。总分类和HTML由汇总者合并更新；不要同时让两个脚本重写共享快照。
- `fork_worklists.json` 是本次起始名单，状态 `prepared_not_dispatched` 不等于运行看板。后续认领、转类、队列和结果另有实际记录后再登记，保留起始证据。

## 模型诊断试解的例外

已知缺陷一般先修。若第2／3类确实需要模型行为证据，须说明：新的问题是什么；为什么固定命令或CPU对照不能回答；已知缺陷为何不污染这项观察及如何检查结果。结果单列，不进入普通比较或训练奖励，题目也不因此自动转第1类。

MiMo的具体尝试次数、稳定性重复数不自动成为本项目的预算；真实试解用于发现遗漏，不能替代对已经确认缺陷的修复。
