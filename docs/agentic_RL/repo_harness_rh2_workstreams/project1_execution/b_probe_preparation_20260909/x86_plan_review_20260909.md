# x86 环境探针方案审查与实施建议

日期：2026-09-09。作者：Codex，B 线。性质：方案审查和候选执行顺序，不是环境验收或新增训练定案。

审查对象：[Claude CPU 探针方案](../B_materials_20260908/03_cpu_env_probe_plan_20260909.md)及其 [216 题命令对照](../B_materials_20260908/official_cmd_contract_216.json)。按用户要求，本轮暂不讨论模型、GPU 和训练方向分歧。未租机、拉镜像或调用付费模型；未修改评分和训练代码。

## 1. 结论

**同意先做 x86 CPU 环境探针。Claude 抓到了正确问题，但方案需要先修正评分依据、R2E 初始化与参考修复、实际 rh2 接口、扩量依据四处，才能避免得到一批难以解释的“通过”。**

推荐从现有主批的 2–4 题跑通，再完成 **SWE-Gym 12 + R2E-Gym 12** 的配对验证；备用题用于补版本、构建和评分机制缺口。216 题保留为校准后的环境盘点选项，不是今晚必须完成的前置条件。无需为了符合旧计划机械凑到 50 题，也不能因覆盖了 9 个仓库就认定覆盖了全部环境配置。

这个阶段可以形成有价值的项目资产：可复用任务包、真实评分反例、修复前后对照、逐阶段成本和保留/未完成原因。但“跑了官方脚本、加了日志、验证了若干题”本身还不足以成为高价值研究贡献。应进一步证明：**发现并解决了哪些会污染训练反馈或浪费算力的实际问题，修复保留了哪些正常解法与任务，代价和收益各是多少。**

## 2. 已核实的事实与方案修正

### 2.1 保留完整官方脚本对照，但不要把命令前缀当作评分等价

本轮重新统计 Claude 的 JSON 和现有 bundle：216 条均记录前缀一致，40 条 mypy、12 条 Conan、196 条含 install；216 题有 **78 个 `(repo, version)` 组合**，SWE-Gym 主批 12 题只覆盖其中 12 个。现有 216 题均有 F2P，22 题没有 P2P。

这些统计中，196 是“脚本包含 install”的数量，不是“196 题都需要联网重装”，也不是已经测得的评分错误数量。

当前 rh2 的 `_v2_candidate_test_lines` 直接拼接 `grading.eval_cmd` 与 `test_patch` 触碰路径；官方 mypy 则提取 `[case ...]` 组成 `-k` 表达式，另有 Conan 的 `eval_commands` 和版本相关 install。因此必须比较**最终脚本及实际测试集合**，不能只比较 bundle 字符串。位置：[prepared_task_face.py](../../../../../rh2/src/repoharness2/adapters/slime/prepared_task_face.py)，函数 `_v2_candidate_test_lines`、`build_grading_spec_from_host_view`；[官方 TestSpec](https://github.com/SWE-Gym/SWE-Bench-Fork/blob/242429c188fcfd06aad13fce9a54d450470bf0ac/swebench/harness/test_spec.py)。

还有一个小修正：对照 JSON 中 `image_key_fork` 全为 `arm64`，这是本机生成的 fork 镜像键，不能拿来拉今晚的 x86 镜像。真实拉取对象仍用候选清单中的镜像及 digest；生成脚本的架构事实与实际镜像身份分别记录。

**install 对照的准确评价：** 原方案 E1 两边都执行完整官方脚本，只改变网络，所以它本身没有混改两个变量；但它只能回答“完整脚本是否依赖联网”，不能回答“省略 install 是否等价”。在涉及编译/安装或出现差异的代表题上，增加同镜像、同身份、同资源、离线条件下的“省略 install”分支。每个分支使用独立 fresh 容器，避免第一次安装污染第二次。

观察不能止于 verdict：还要看相关模块实际从哪里导入、源码修改是否生效、扩展是否需要重新构建、依赖是否发生变化。两个分支都得 0 可能只是都没测到目标；两个都得 1 也不证明任意候选修改都能生效。需要安装的任务，应先评估冻结依赖/离线构建能否满足要求，而不是直接删除这类任务。涉及候选代码的 build/install 不能为图方便塞进正式 root 可信初始化阶段。

### 2.2 R2E 要先补来源 setup 和 gold 依据；commit diff 不一定错，但现在未证明等效

Prime 的固定实现确实默认只提取非测试 Python 文件，所以不能仅凭这个过滤就批评 Claude 的方案错误。若初始 HEAD、修复父提交和文件选择相同，`git diff` 可能得到等效修复。**未确认的是：它是否与这批数据行的 `parsed_commit_content` 一致。** 三个仓库的历史 HEAD 抽样也不能替代这 12/24 题的逐题确认。

推荐在第一轮正式 gold/no-op 验证前，按固定 revision 补齐所选 R2E 行的 `parsed_commit_content`、`expected_output_json`，核对任务身份与镜像。无需为了这件事先导入全部数据或拉取全量镜像。字段暂时取不到时，可以继续镜像/启动检查，也可以运行明确标为“由 commit 推导的正对照”的实验；其失败先查 fixture，不能直接据此判原始任务无效。

计划还需要写出完整的来源初始化：正确的解释器/虚拟环境、字节码清理、测试目录在评分时的恢复位置。在所读 Prime 实现中，评分前会将测试恢复到 `/testbed/r2e_tests`，随后才运行 `run_tests.sh`。直接在原始镜像执行同名脚本，未必经过相同路径。预期结果必须是**非空、可解析的具体状态映射**；R2E 允许预期状态含 FAILED，不能改成“所有测试 PASSED”。[Prime 固定任务实现](https://github.com/PrimeIntellect-ai/prime-envs/blob/c4d04dfe212c153a587ea4ce072ae6753e74d6e9/environments/swe/r2e_gym/r2e_gym/taskset.py)

对来源也作一处勘误：容器内 `expected_test_output.json` 的 fallback 在本轮核到的 **R2E 原始 runtime** 中存在；上述 Prime loader 直接要求数据行的 `expected_output_json`，并没有这个 fallback。若采用镜像内文件，应单独记录出处，与完整行对拍后再合并，不能笼统标为“Prime 同款路径”。[R2E 原始 runtime](https://github.com/R2E-Gym/R2E-Gym/blob/0d94c4eb9431cd195c55a7ea3abd54006c9a1735/src/r2egym/agenthub/runtime/docker.py)

### 2.3 官方判定是比较基线，逐测试事实才让差异可解释

赞同同一日志保留两份判定；但不赞同“后续 rh2 必须与官方布尔值全部相等”作为无条件标准。已知官方存在 skip 和空集合的宽松行为，修复它们后本来就可能不相等。目标应是逐项说明差异及其原因，最终 reward 定义仍由用户决定。

本轮用固定 fork 重放了三个纯函数输入，结果如下；这不是实际镜像发生率：

| 输入 | 官方结果 | 对探针的含义 |
|---|---|---|
| F2P=`f`、P2P=`p`；只有 `f=PASSED` | `RESOLVED_NO` | 缺失 P2P 本来就不能算回归保持 |
| 同样非空参考集，两个 case 都 SKIPPED | `RESOLVED_FULL` | 布尔通过不等于参考测试实际通过 |
| 参考集和解析结果均为空 | `RESOLVED_FULL` | 必须保留参考集与执行覆盖事实 |

来源：[官方 grading.py](https://github.com/SWE-Gym/SWE-Bench-Fork/blob/242429c188fcfd06aad13fce9a54d450470bf0ac/swebench/harness/grading.py)。方案 E2 的“P2P 无 FAILED/ERROR”需要补“所有非空参考 P2P 均被识别，并逐项满足明确的成功状态”，否则它的字面标准可能比官方还松。missing、SKIPPED、XFAIL、空 P2P 分别记录；不把 22 道空 P2P 题直接清掉，也不宣称它们具有已验证的回归覆盖。

gold/no-op 校准时，空日志、解释器错误、测试目录缺失、解析器不支持都不能算“no-op 正确得 0”。no-op 要展示具体的未修复状态，gold 要展示相应变化及回归结果。之后模型候选造成的导入/收集失败又可能是真实代码回归，不能因为日志有 ERROR 就一律判环境无效。

固定 fork 的 `get_logs_eval(log_fp)` 还从日志父目录名推断 repo，并检查 patch 日志标记；它与当前 rh2 使用的 swebench helper 签名、标记协议不同。runner 在本地先核清参数、目录、合并日志和真实 patch 应用记录，避免把包装失败当环境质量。无需因此另建通用日志平台。

### 2.4 现有 grader 已有 frozen_delta 入口，不必预设再造一个公共 API

方案称 rh2 “只有从 workspace 导出 patch 一个入口”，这个事实已经过时。真实链路是：

```text
generate._finalize 的评分闭包
  → _grading_submit(workspace=None, frozen_delta=...)
  → queue.submit
  → manager.grade
  → baseline 重建 / solution delta 应用 / official tests / 非 root 测试 / parser
```

证据：[generate.py](../../../../../rh2/src/repoharness2/adapters/slime/generate.py) 的 `_grade` 闭包、[manager.py](../../../../../rh2/src/repoharness2/grading/manager.py) 的 `grade` 和 `_run_eval`；已有 [frozen delta fixture](../../../../../rh2/tests/grading/test_b4_frozen_delta.py)。后者主要是 FakeDocker 证据，不能冒充真实 SWE 受控入口已跑通。

优先方案是：薄实验驱动对真实 baseline 应用 empty/gold/控制补丁，复用现有冻结工件和可信投影，然后调用当前评分接口。不能跳过 baseline 绑定、用任意 diff 伪造 frozen 数据。确有接口困难后再判断是否新增函数，不把 `grade_controlled_patch` 这个旧计划函数名本身设为交付要求。

今晚独立官方 runner 仍然可以先用。但“把官方脚本换成 rh2grader 用户执行”只覆盖身份因素：正式 rh2 还包括 root 准备官方测试、文件保护、受限候选执行、资源/tmpfs、冻结工件等。**独立 runner 的通过，必须标为参考路径验证；rh2 实际入口的配对验证随后补齐。** 不要求 B 等待 A 所有训练修复结束，也不让独立脚本结果直接核销 rh2 集成工作。

### 2.5 216 全量的价值成立，今晚必须全量的理由不成立

原方案所说的“有信号题占比”，在它引用的训练建议中定义为每题模型采样 8 次、成功数介于 0 和 8。CPU 四门不运行目标模型，不能估计这个量。一个 no-op 得 0、gold 得 1 的任务，对当前基座可能始终失败、始终成功或成败混合。

216 全量可以回答：当前这批存量资产在指定条件下，有多少可运行、可判分、重复稳定；哪些仓库/版本损耗大；成本如何。但还要支付解析异常、依赖差异与判据修订后重跑的工作量，不能称“只多花机器时间”。这批资产仍是候选，不是已选定的正式训练池。

仅原四门就有 `216 × (3 + 3 + 1 + 1) = 1728` 次评分尝试，额外网络/身份/安装对照另算。举例，若实测平均每次 5 分钟、有效并发 4，纯评分约 36 小时；这是条件算例，不是耗时预测。方案的 10–20 小时和 10–20 美元尚无本批 x86 实测支撑。

## 3. 建议今晚验证哪些内容

| 问题 | 最小实验与证据 | 结果怎样使用 |
|---|---|---|
| 环境身份是否正确 | 来源 revision、任务 ID、镜像 digest/amd64、实际初始 HEAD、解释器、依赖与测试入口；R2E 核 fix/base 关系 | 防止在错误代码或错误环境上得出真假结论；不再反复全树扫描 |
| 未修复与参考修复是否可区分 | 每题 fresh no-op/gold；保存 patch 应用、真实测试日志、逐 case 状态及缺失/跳过；目标测试与回归分别看 | 证明这次评分具有基本区分能力，不等于证明任意解法都公平 |
| 结果是否稳定、状态能否复位 | 在固定身份/网络/脚本/资源下重复 empty/gold；每次新容器、无可写状态共享，记录全部尝试 | N=3 是短期重复证据，不是“确定性已证明”；网络/身份不同的运行不能混算重复 |
| 候选修改是否真正参与测试 | 在编译/安装代表题核导入位置、必要重建；官方完整路径与省 install 分支作对照 | 防止只测镜像预装代码；据此决定能否安全减少重装成本 |
| 评分是否误奖或误杀 | 保留已有 3a 无关修改、3b 变异诊断；对可疑题加少量人工确认的错误解/合法替代解 | 自动判分之外核实题意、测试与修复关系；不因删 hunk 后仍通过就自动剔题 |
| 求解期和评分期边界是否正确 | 用实际求解用户检查参考修复/隐藏测试/expected 结果、未来 Git 对象和 remotes 的可见性；用少数控制补丁检查测试/配置修改的因果影响 | 为随后真实 Claude Code 运行准备；目录存在性或关键词扫描不能替代用户视角的可访问性 |
| 成本和失败落在哪一段 | 拉取/解压、启动、准备、安装/编译、测试、工件处理、清理；墙钟、峰值内存/磁盘、重试和实际并发 | 决定规模、缓存和调度；慢、暂时拉不到镜像、环境坏题分别统计 |

当前 [grader profile](../../../../../rh2/src/repoharness2/adapters/slime/sandbox_profile.py) 默认候选 UID 54322、2 CPU、4 GiB 内存、断网，数值仍需校准。主结果应优先靠近目标 profile；root 作为差异诊断。06 计划仍记录 W3b 身份例外待定，但今晚做对照不等于批准正式用 root，也不必先解决所有例外才测试。

**控制面检查需要兼顾正常解。** 只改评分测试的补丁不应让未修复代码获奖；同时添加开发测试并真正修复的补丁也不应因此被拒。对配置/插件相关题，要辨明哪些配置本来就是合法修复面，不能把所有 `conftest.py`、`setup.cfg`、`pyproject.toml` 一刀切丢掉。今晚先记录实际差异和可访问材料；通用评分边界改动仍与 A 协同。

## 4. 推荐的执行顺序与停止条件

1. **租机前的低成本准备。** 补所选 R2E 完整字段；冻结本批使用的脚本/parser 与运行参数；用已知日志校准判分；列出阶段结果、超时和清理的记录方式。先完成一份可运行、能给出原始证据的 runner，再估计租期，不预先承诺“约 150 行”足够。
2. **2–4 题入口校准。** 可从主批中取 pydantic、mypy、Conan，以及一题 R2E。重点分别是普通测试、case 选择、额外环境命令和另一套评分语义；题目“结构简单”不等于已测得运行最便宜。先 1–2 并发，真实核一次成功结束、一次失败/超时结束后的容器收口。
3. **完成 12 + 12 主批。** 每题先有可解释的 no-op/gold 配对；SWE-Gym 若声称完成旧四门，应按旧规定各 N=3，并包含 3a/3b，不能拿一轮初筛改名验收。R2E 也安排固定条件下的重复测量，但次数与范围写清，未重复的先标初筛。GUI/跨平台、空 P2P、大回归集等困难候选保留结果，不用简单换题掩盖失败。
4. **按缺口扩展，而不是所有因素做排列组合。** 备用题优先补不同版本/解释器、安装步骤、修改类型和测试成本。安装/网络/身份对照集中在代表题和异常题；合法替代解先检查少数问题，不要求全库生成。SWE-Gym 全量环境盘点可在判据稳定、实际成本进入已批预算后自动继续。
5. **接入实际 rh2 路径。** 尽早让同一批控制工件走 frozen artifact → fresh grader，在相同条件下逐 case 对账。无法当晚完成时单列，不据此停止独立来源核查，也不宣称集成已通过。

扩大运行前，要求已知类型的问题能区分为任务结果、fixture 问题、环境/包装失败或未完成；同一脚本/parser 的系统性问题先在小批修正。个别任务故障可以留记录、继续其它任务，不需要全池全绿。没有日志/测试尚未执行的尝试不进“正确 no-op 失败”计数。

重复测量与故障补跑分开：N=3 不是失败后重试到成功；保存 0/3、1/3、3/3 的全部原始记录，不能只保留最好一次。正式评分重试仍遵循 A 已批的 I16 窄范围，不能把旧 S2 的泛称“infra 重试”直接套到当前训练链。

**资源预算先补齐内存和磁盘实测。** “16 核、500 GB”还不足以确定并发，编译/测试的峰值内存和可写层也会限制运行。记录压缩下载量、解压后层占用与清理后的实际空间；逐批移除本批镜像，避免全局 prune 或清理其它任务资源。并发增加后若出现 OOM/超时，不直接把对应任务归为无效。

## 5. 最少保存什么，怎样形成简历证据

复用已有源清单，逐尝试 JSONL + 原始日志/工件即可。除 Claude 已列字段，补充：source revision、实际 base/解释器与脚本引用、参考结果出处、运行资源、patch 应用状态、测试是否开始/结束、结束阶段/原因、是否可判分。未完成/未知不填 0。保留请求题单和全部尝试，不能只从成功目录统计分母。

没有必要为此新增授权闸门、大型 schema、通用恢复系统或重复哈希检查。稳定性比较逐 case 状态，不比较带时间戳的日志字节。必要的来源/镜像/脚本身份一次记录，用于重跑与解释差异。

| 证据层次 | 可以形成的贡献 | 还需要的验证 |
|---|---|---|
| 环境准备与校准 | 两来源可复用输入、目标环境的 no-op/gold、版本覆盖、失败与成本画像 | 更多任务覆盖和真实 rh2 接入；不能直接宣称训练有效 |
| 评分正确性改进 | 某类真实任务的误奖/误杀或遗漏执行，在修复后被纠正，正常解法保留 | 同任务/同工件/同运行条件的修复前后对照，人工核验代表反例 |
| 环境运行效率 | 在相同任务与判定质量下提高可判分工件/小时、降低每个合格环境成本 | 冷/热缓存分开、失败/清理/人工作业成本计入，不靠删除慢题制造加速 |
| 训练贡献闭环 | 更可信、更高效的环境供给支持真实 SWE 后训练 | 后续等预算训练比较、独立评测和有效训练信号/供给成本记录 |

建议首轮沉淀一个小型、可重复执行的真实反例集合：测试选择错配、安装/编译导致修改未生效、结果缺失/skip、参考材料泄漏或配置误伤。只有真实复现的类别才写成成果；暂未发现的保留覆盖情况。后续修复和升级在这组任务上回归，比不断堆叠同构单测更能支撑项目价值。

API 可解性探针不作为今晚 CPU 环境校准的依赖。本轮不裁决其供应商和网络方案；若后续执行，单次强模型成功是可解见证，不能称能力上界。原方案“`git diff` 含新增文件”也需改为确实覆盖新增/已提交改动的工件导出；不能将不完整 patch 用于 fresh 重放。这两点留在后续模型诊断方案中处理。

## 7. 决策、审查范围与交接

本轮没有新增已批准 T0。今晚作业只需明确 CPU 作业题量/预算、参考与目标 profile 的具体运行条件；不需要先冻结训练集、基座和最终评测。评分加严、任务永久排除、身份/网络例外仍留作具体证据后的语义决定。

- **待修订的方案项**：R2E 初始化/gold 来源、E2 缺失测试口径、官方结果与 rh2 结果的对照含义、当前 frozen_delta 接口事实、216 扩量依据和预算。
- **保留的部分**：固定来源/镜像，fresh no-op/gold，固定条件下重复，官方与额外诊断并列，分段成本，小型控制补丁，候选失败不静默消失。
- **对 A 的交接**：B 交完整命令/测试事实/控制工件；通用 frozen artifact、评分进程边界与错误消费复用 A。这里只写交接需求，未向其它任务发消息或取得排期承诺。
- **本轮推翻的表述**：“只有 workspace 入口”；“CPU 四门测有信号题占比”；“单次强模型可解性上界”。不推翻：非测试 Python 提取必然错误这一断言本来就没有证据；E1 本身只改变网络，问题在缺少省 install 对照。

按 [审查标准 §10.4](../../review-standards.md) 对容器评分边界安排了一名 Production Tracer 和一名 Falsifier；主审查者独立回读关键源码、统计 bundle/候选覆盖，并重放上述三个纯函数判分例子。适用性扫描：A/E/G 检查失败模型、探针有效性与真实入口；B/F 检查任务选择影响与已有决定；D/H 检查评分所有权、配置和来源；I/J/K 检查分期、重复实现与维护成本；L/M/N 检查容量、可诊断性与固定外部依赖。C 仅确认本建议未新增或解除代码挡板。未对学习器算术或未运行的硬件行为作通过声明。

所有执行计划问题均属于待实施条件，**没有把静态反例报成已在这批真实镜像发生的生产 P0**。本轮未运行真实环境、未测成本、未证明 216 题评分一致。修订上述方案项并让小批输出可解释的逐测试证据，就足以进入下一步；不要求为所有假设补齐大规模实验后才开工。
