# 用较小资源验证候选基座，再做目标训练拓扑验收

日期：2026-09-09。状态：资源与验证顺序建议，未租机、未运行实验、未改训练配置。

## 1. 结论与顺序

**不需要先完整跑通八卡训练，再开始 SWE-Gym/R2E 能力探针。** 环境是否可靠、模型能否解题、模型在当前栈能否训练、目标拓扑是否高效，是不同问题，可以用不同规模的实验分别回答。

推荐顺序：**CPU 环境对照 → 1–2 张目标 GPU 上的推理/必要内核检查与能力诊断 → 按需做训练侧回放 → 入选模型的目标八卡短闭环。** 中间的缩小训练拓扑不是强制阶段；只有能够直接复用现有入口并减少总体成本时才做。

先缩小候选，最后验证拟用于正式训练的模型与拓扑。若模型能力很好但目标机器训练成本或兼容性不合适，再比较另一候选；若两者接近，训练工程和总成本可以决定取舍。八卡短闭环仍不等于长时间稳定训练或已取得学习收益。

## 2. 现有证据能复用到哪里

- [P3 旧八卡报告](../../preflight/preflight_report.md)记录了 PRO 6000 Blackwell、`sm_120` 上旧 Qwen3 MoE 的 forward/backward、tape 消费和权重同步。它降低了“这类卡完全无法训练”的风险；但当时是旧 slime 链，报告亦明确不保证当时的 GRPO 组归一化语义，不能作为新模型/新链的通过证明。
- 当前 `rh2/experiments/miles_gpu_spike/launch.sh` 的默认值是 **6 train + 2 rollout，训练 TP=1 / PP=3 / EP=2 / CP=1**，不是“一个模型能力测试至少需要八卡”。旧 P3 的 4+4 和当前 G1 的 6+2 也不能混为同一配置。
- 当前 miles 有 `--debug-rollout-only`、`--debug-train-only`、`--save-debug-rollout-data`、`--load-debug-rollout-data`。代码中 train-only 分支不创建推理服务器，placement 分配也区分两者；rh2 当前 launch 已有 rollout dump。**这是可复用的分阶段入口证据，不代表 rh2 的新方案已接通或无需检查附加字段。**
- Qwen3.6 的模型配置和 mbridge 已存在；rh2 启动的旧模型拓扑约束尚需对齐。原版 48 层的 PP=3 配置，不能未经检查照搬给 40 层的 Qwen3.6。
- 本轮回看 [NeMo-Gym 奖励诊断](https://github.com/NVIDIA-NeMo/Gym/blob/main/responses_api_agents/mini_swe_agent/README.md)及 [Uni-Agent RL 结果](https://uni-agent.readthedocs.io/en/latest/benchmark/rl-training.html)，它们加强了 Coder-30B 与 SWE-Gym/R2E 任务匹配的证据，但没有验证我们的 PRO 6000、miles 版本或 Claude Code 配置。NeMo-Gym 同页训练说明是 16 nodes，不能将其当成八卡最低资源结论。

## 3. 各阶段建议做什么

| 阶段 | 建议资源 | 回答的问题 | 不能据此宣称 |
|---|---|---|---|
| 环境与评分准备 | 可运行目标 x86 Docker 环境的 CPU 实例 | 无修改是否重现问题、参考修复是否有效、测试是否执行、评分是否可信 | 模型有解题能力或 learner 可训练 |
| 推理与必要内核检查 | 先 1 张完整 96GB PRO 6000；按实际显存/吞吐增至 2 张 | 完整模型加载、真实工具调用、目标上下文、推理成本；对新架构检查必要算子的 forward/backward | 多卡通信、完整模型反向或目标吞吐已验证 |
| 能力诊断 | 沿用这 1–2 张卡，CPU 沙箱独立运行 | 在相同任务和明确预算下比较成功、失败、混合奖励组及成本 | 24 题代表整个任务池；较少卡的墙钟等于最终拓扑 |
| 训练侧回放（可选） | 优先复用计划中的训练分区；只有布局合法、内存核算可行时考虑 4 卡等缩小规模 | 真实 token 行的 loss、梯度、packing、显存、optimizer step、checkpoint | fully-async 在线发布/版本/队列均已验证 |
| 目标拓扑短闭环 | 入选模型的目标八卡机 | 实际并行划分、NCCL、权重发布、rollout/train 重叠、多个真实更新、代表性长度与资源释放 | 已证明长期稳定、所有长尾均安全或 RL 有收益 |

新架构的单卡内核检查可以使用少量层或典型模块，保持真实 hidden size、expert 结构、数据类型和必要的变长/packing 输入，先发现明显的不支持。这样的检查不是完整 checkpoint 的训练测试，也不能外推总体显存。它可以与能力诊断共用一次短租，不必额外建一个验证平台。

能力诊断先选 2–4 道完整轨迹检查接口，再扩大到已有 24 道开发候选；不要先在八卡上等镜像拉取、依赖安装、parser 调试。环境是否应接受进入诊断，仍依据之后具体确认的任务预期与评分处置，不能凭元数据清单直接跳过验证。

## 4. 为什么 1–2 卡值得先试，而单卡能推理不等于能训练

[NVIDIA 规格](https://www.nvidia.com/en-us/data-center/rtx-pro-6000-blackwell-server-edition/)列出该卡 96GB GDDR7。以 30.5B 参数的 Coder 模型为例，BF16 权重裸数据约 `30.5e9 × 2 = 61 GB`，约 56.8 GiB；35B 参数约 70 GB。实际需加运行时、缓存、临时空间和可能的其他模型部分，不能只按裸权重决定并发。

根据已保存的 Coder config（48 层、4 KV heads、head dimension 128），**未量化的 BF16 KV cache** 每 token 约 `48 × 4 × 128 × 2(K/V) × 2 bytes = 96 KiB`：单条 32K、64K、128K 序列分别约 3、6、12 GiB。多条轨迹会叠加，还未计运行时开销。这个公式不适用于混合注意力的 Qwen3.6，需要按其实际后端状态测量。

因此，单张 96GB 卡承载完整 BF16 模型、低并发推理是值得验证的起点；不保证任意上下文和并发都能放下。先降低同时运行的任务数，尽量保留每题既定上下文/turn 预算；如果需要两张卡才能满足目标运行条件，就用两张。不要为挤进单卡而悄悄砍掉任务预算，再把失败归为模型能力差。

全参数训练还需要梯度、optimizer 状态及 activation。常见混合精度 Adam 的一种朴素账目是 BF16 参数 2 bytes + BF16 梯度 2 bytes + FP32 master 4 bytes + 两个 FP32 moment 8 bytes，合计 **16 bytes/参数**：30.5B 约 488 GB、35B 约 560 GB，尚未算 activation。当前实现可能使用 FP32 梯度、不同分片、CPU offload、不同主权重存储，实际数值会变；此处只是解释为什么不能拿“激活 3B”或“推理能装下”推断训练需求。

当前 launch 片段未显式带 optimizer CPU offload；不能把旧 P3 曾启用 offload 的实测当成当前默认。是否用 offload、缩小并行布局或短序列诊断，由 A 对照当前完整参数与内存核算确定，不在本稿暗中改训练方式。

## 5. 怎样复用轨迹减少八卡等待

在基座推理诊断时保留原始 token、必要的行为策略 logprob/support、模板与权重版本、mask/边界和终止/评分事实；routing 等字段按 A 已定方案和可用接口收集。普通 API 返回的文本不够用，不能重新 tokenize 或编造缺失信息来冒充训练输入。

之后用 miles 的调试 dump/load 路径检查真实训练形状：先验证字段和准入，再检查 forward/backward、非零且有限的梯度、实际 optimizer 更新与 checkpoint。训练回放的 checkpoint 仅为调试产物；固定旧轨迹反复更新不是在线 RL 学习证据，不改我们已选在线训练语义。

回放阶段可以先不保留 GPU 给在线生成。例如维持原计划 6 卡训练分区、暂不启动 2 卡 rollout，已经减少了同时占用；若 4 卡需新写复杂 offload 或改变关键实现，就直接跳过这一中间层，合入准备好的八卡短验收。**少一个卡数不等于更便宜：排错与额外适配时间也计成本。**

最后的八卡实验仍需要真实在线 rollout 和不止一次权重发布，检查新请求确实使用新版本、在途轨迹如何处置、训练与推理同时运行时是否出现通信或内存问题。预先选定代表性长轨迹，不能只凭短输入的一次 backward 验收正式长程训练。

## 6. 其他更便宜方式的适用范围

| 方式 | 什么时候有用 | 主要限制 |
|---|---|---|
| 第三方模型 API + CPU 沙箱 | 少量工具/题面探索；模型和预算可准确说明时做方向性能力诊断 | 权重 revision、精度、模板/采样常不可完全控制；不能证明本地性能、token 保真或 learner 支持；付费调用需另定预算 |
| 已有消费卡上的量化模型 | 便宜发现明显协议问题，评估大致可用性 | 是另一推理条件；不能替代 BF16 基线或全参数训练兼容验证 |
| 单张其他大显存卡，如 A100/H100/H200 | 目标卡难租，且重点仅是能力诊断时 | 可测该机器上的完整模型，不能验证 PRO 6000 的 `sm_120` kernel 与 PCIe 拓扑；仍需目标卡确认 |
| 4B/9B 小模型 | 提前跑通环境、编排和部分通用链路 | 不代表 30B/35B 的容量、MoE 与对应 kernel；若正式改用小模型，那是项目实验规模的选择 |
| LoRA/QLoRA | 如果全参 RL 成本超过预算，可作为独立训练方案讨论 | 改变训练方式；通过它不等于原定全参 Megatron 链通过，不建议只为第一轮探针临时另造一套 |

优先建议是 **同一类完整 PRO 6000、同一精度、较低并发**，这样既降低一次资源占用，也减少需要解释的实验条件差别。能力诊断与目标硬件性能可以分开，但能在一轮小租期兼顾最好。

选实例时核实完整 96GB 卡还是 MIG 切片、可用 CPU/RAM、镜像和存储、Docker 运行条件、功率设置与实际卡间拓扑；这些是选择运行环境所需的配置事实，不新增生产资格闸门。GPU 推理端与 CPU 环境端若分离，仍复用真实 Claude Code/harness 语义与可信 grader，不换成另一套代理来取得不可比成绩。

## 7. 成本与当前建议

按同一每卡小时单价计算，同样 6 小时纯能力诊断：1 卡为 6 卡时、2 卡为 12 卡时、8 卡为 48 卡时。但若两卡完成时间不到单卡的一半，两卡反而更便宜，应比较**每条有可信评分的完整轨迹成本**以及失败分布，而不是单看租价或 tokens/s。

2026-09-09 查到的 Runpod 页面分别展示 PRO 6000 每卡小时 $1.69（[机型总表](https://www.runpod.io/gpu-models)）和 from $2.09（[机型页面](https://www.runpod.io/gpu-models/rtx-pro-6000)）。它们不是具体实例/八卡整机报价，不用于承诺本项目总预算；CPU 环境、存储、数据搬运、初始化和调试等待另计。此处只说明没有必要为所有能力采样保留八张卡。

新增的同模型 SWE 训练证据与当前对成本的关注，使我建议 **Coder-30B 优先做训练可行性核验，Qwen3.6 同批做低卡数能力诊断和必要的新架构检查**。这修正了只按模型能力潜力给 3.6 最高执行优先级的建议；正式选择仍是能力、学习信号与可承受训练成本的交集。两者不需要各自先完整租八卡验收。

下一步具体准备：CPU 环境可执行对照；两个候选的完整推理命令和 revision；1/2 卡容量与必要内核检查清单；可保存给 A 的轨迹字段；最后一次目标拓扑作业的范围与费用。这里只提出方案，尚未启动资源作业，也未向 A 发送消息或代表其承诺交付。
