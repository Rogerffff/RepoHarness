# 探针准备与 Qwen MoE 基座候选

日期：2026-09-09。状态：开发候选元数据已准备；运行及基座选择仍待定。

当前 CPU 环境工作见 [x86 探针方案审查](x86_plan_review_20260909.md)：核对 Claude 的方案与真实评分入口，建议小批校准后完成两来源 12+12 主批，再按覆盖与实测成本扩展；216 全量是候选环境盘点，不用于代替模型学习信号诊断。尚未执行环境实验。

后续资源讨论见 [低成本验证顺序](resource_validation_strategy_20260909.md)：能力诊断不必等完整八卡训练通过，可以先用 1–2 卡推理、按需回放训练，最后验收目标拓扑。结合新增的同模型 SWE 训练证据，执行上建议优先核验 Coder-30B 的训练可行性，并对 Qwen3.6 做低卡数能力/内核检查；下文的“3.6 主候选”是能力潜力的初始排序，不是已批准的唯一模型或八卡执行顺序。

## 1. 本轮用户决定与工作范围

用户基本确认首轮能力目标：真实 Python 仓库缺陷修复并保持回归，terminal 暂作补充评测候选。用户询问是否可先准备 SWE-Gym/R2E-Gym 的约 24 道探针，把其他决定留到后续，并要求重新比较相近规模 Qwen MoE。

据此先完成不依赖模型或评分定案的准备：选出 **24 道主批候选，另列 24 道扩展备用**，核对现有来源记录和官方模型配置。备用题量是 Codex 建议，不是用户批准的运行规模。

准备候选题不要求先确定正式训练集、SFT/RL 配方或最终评测题量。这里也没有批准新的 reward、训练过滤、付费运行或永久划分。正式评分前补齐具体预期结果和错误处置；模型运行前固定 checkpoint、harness 配置与资源预算即可，不应把所有远期决定变成选题前置条件。

## 2. 24 题够做什么，扩展到多少

| 阶段 | 建议规模 | 主要用途 | 解释边界 |
|---|---|---|---|
| 入口检查 | 从主批中取 2–4 题 | 检查任务加载、实际测试、工件、评分和真实 Claude Code 请求 | 不作能力比较 |
| 第一批探针 | 24 题，两来源各 12 | 覆盖仓库、特殊命令、依赖和典型失败；识别模型是否有明显协议问题 | 不能准确估计整个来源的成功率，也不能可靠区分小幅模型差距 |
| 扩展开发诊断 | 暂以 48–96 题为讨论范围，按缺口扩展 | 比较候选基座与来源、观察长任务和仓库差异 | 成本及不确定性实测后再决定实际规模；仍是开发集 |
| 正式效果评测 | 另行决定 | 同一基座训练前后、独立任务上的效果与成本 | 不用前三阶段调过的题伪装成独立测试 |

24 题不是训练规模目标。它们已经覆盖 SWE-Gym 的 9 个仓库和 R2E 的 8 个仓库，其中 pandas 跨来源重合；平均每仓库只有一两题，足以触碰多种执行路径，但不够描述仓库内的难度分布。扩展批应补同仓库不同模块、修改跨度、测试成本等，不能只重复更多采样。

`24 题 × 4 次 = 96 次尝试` 仍只有 24 个不同任务。增加重复次数有助于看采样波动，不会自动扩大任务覆盖。即使理想化为随机独立任务、成功率约 50%，24 个单次结果的常见正态近似 95% 误差也约为 ±20 个百分点；我们这里还有目的抽样与仓库相关性，因此这个数字仅用于说明量级，不是本题单的正式置信区间。

## 4. 基座建议需要从“沿用旧配置”转为实际选型

**修正上一轮默认先测原版 Qwen3-30B-A3B 的优先级：它的主要优势是已有接线证据，不足以证明是今天最合适的训练起点。** 对当前项目，我更倾向将 **Qwen3.6-35B-A3B 作为主候选，Qwen3-Coder-30B-A3B-Instruct 作为一个有针对性的对照**；原版保留用于复查已有链路问题，不要求先花一轮完整实验在它上面。

这里的“基座”是继续后训练的起点。下表均为已后训练模型，不是名称带 `-Base` 的预训练权重。

### 已核实的本地接线边界

检查版本为 `reference/miles-rh2-integration@98a0272e4158b2c20e3a34d210c79b50159af0f6`：

- `scripts/models/qwen3.6-35B-A3B.py` 已有 40 层、256 experts、混合注意力模型配置；`miles_plugins/mbridge/qwen3_5.py` 已登记 Qwen3.6，并处理 MTP 权重打包差异。因此“上游 miles 完全不支持，需要从头重写”不是当前事实。
- rh2 的 `experiments/miles_gpu_spike/launch.sh` 仍按原版 Qwen3 的 `qwen3_moe`、48 层、128 experts、151936 vocab 校验。换 3.6 需要 A 对齐配置与实际训练路径；已有上游配置不等于 rh2 的新模型端到端已验收。
- 原版与 Coder/2507 的 `rope_theta` 分别为 `1e6` 与 `1e7`。即使同属 `qwen3_moe`，也不能沿用旧模型参数和 tokenizer/parser 而不检查。
- 官方模型 API 与 config 已按具体 revision 保存；没有加载权重、运行 kernel、检查显存实测或执行训练。相同“约 3B 激活”不代表相同训练显存或吞吐。

### 如何最终确定

先核对两个候选在当前链上的加载/转换、模板与工具解析、长上下文和资源条件；在已验证的小批环境上，以相同任务与明确预算做真实 Claude Code 诊断。各模型使用自身正确的模板和 parser，不能把接口错配当能力比较。24 题可以发现大差距和明显故障；差距不清楚时再扩到预先准备的开发任务。

最终依据是任务完成质量、失败类型、可训练性、吞吐和总成本。选择强起点不会破坏训练收益归因：固定这个起点做 before/after 即可；较高起点可能使增量更小，但这与因果归因是两回事。现在不写死从文献跨 harness 分数推导的成功率阈值，也不要求先把原版扩测到全部 216 题才允许换模型。

**结论：可以现在定主候选优先级，同时推进模型无关的探针准备；正式基座选择和 GPU 运行参数等少量实际证据后确认。** 本稿没有修改 A 的模型配置，也不重新选择已经批准的 I01 上下文方案。
