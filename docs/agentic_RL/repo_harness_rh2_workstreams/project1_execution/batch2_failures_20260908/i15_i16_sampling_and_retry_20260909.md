# I15 / I16：整组损耗、训练分布与分层重试

日期：2026-09-09。状态：**用户已确认首版完整组＋原因观测、可变组外部调查留后续；最多追加一次同工件评分及 §8 的允许失败阶段/类别范围均已确认，实现待办。** 最新确认来自用户“同意，后续决策我也会交给claude来检查”这一消息。未批准可变组、单成员/整组重新 rollout 或 staleness 改判。I13 已单独批准，不代表 I15/I16 已解决。本稿没有实现修改或训练实测；§1–7 保留前轮的解释与比较，批准状态以本段和 §8 为准。

## 1. 先区分模型失败和基础设施丢样本

一题采样八次。可信评分 `[1,0,0,0,0,0,0,0]` 是正常训练组，七个未修好的执行提供负优势；正常 turn 预算耗尽也按第一组决定使用真实评分。它们不是 I15 所说的“坏成员”。

若第八个成员没有可信评分，真实状态是 `[1,0,0,0,0,0,0,?]`，不能把 `?` 填成 0。问号可能来自模型未实际获得执行机会、轨迹无法重建、grader 没运行成功等不同情况。当前合同是固定八个完整合格 member，任一不合格则整组不消费。其它成员的成功失败不能代替问号的真实结果。

当前三处主要筛选分别是：`put` 时遇到 ABORTED；dynamic filter 判资格或零方差；`get` 时判版本超龄。全 0 / 全 1 的零方差组过滤是既定算法选择，不与 infra 损耗混为同一个坏组统计。用户已批 hard wall 整组排除也应单列。

**固定 n=8 是项目当前合同，不是 GRPO 数学上唯一可能的实现。** 七条有效样本也能计算均值与优势，但需定义可变组的权重、GBS/损失归一化、slot/身份及选择偏差。当前 `group_admission` 要求 slot 集齐，`_drain` 也断言固定 n；不能只删一个判断就认为算法与原合同等价。

## 2. 第一类风险：小的成员损耗被组规则放大

假设每个成员独立以概率 p 因基础设施失去训练资格，且暂不计其它过滤，则完整组保留概率为 `(1-p)^8`。

| 假设的单成员损耗率 | 组保留率 | 组丢弃率 |
|---|---|---|
| 1% | 92.3% | 7.7% |
| 2% | 85.1% | 14.9% |
| 5% | 66.3% | 33.7% |
| 10% | 43.0% | 57.0% |

这是独立性算例，不是本项目生产发生率。真实故障常按主机、时间窗口、任务或动作相关，不能直接套表预测损耗。

例：八条轨迹已全部采完，只差最后一个 grader；它遇到容器创建的暂时服务错误，当前可能损失整组已经完成的模型生成工作。无效算力不只属于出故障的那个成员。若故障发生较早，实际浪费会不同；不能把所有丢组都算成八条完整长轨迹成本。

## 3. 第二类风险：训练分布发生无意筛选

若丢失与任务、动作、长度和 reward 完全无关，主要代价是浪费样本。但 SWE/terminal 的容器、工具、测试和推理耗时差异很大，不能先假设缺失是随机的。

举例：发起 100 组短任务、100 组长任务；在独立算例中，前者每成员有 1% infra 损耗，后者 5%。预期分别留下约 92.3 与 66.3 组，消费构成由 50:50 变成约 58.2:41.8。长并不必然代表难，此例只说明保留概率不同会改变构成；也未计零方差、staleness 等其它筛选。

更隐蔽的是动作选择：某种合理但较慢的测试/搜索行为更容易撞墙或暴露 capture bug，它就更少进入 loss。表面 reward 上升可能部分来自更容易消费的样本占比增加，而非相同任务上能力提高。是否发生及大小仍需测量，不能仅凭机制断言训练已偏。

不断补采后续 task 可以让 batch 始终装满，不能自动修复这种选择；同一 task 下一 epoch 再出现，若同样故障仍存在，也可能再次丢失。no-progress 只能防没有可消费组的等待，不能发现所有“快组持续供应、慢组持续消失”的情况。

## 4. 第三类风险：完全有效的旧组也会被 staleness 排除

当前 staleness = 消费时已发布版本 − 整组可训练 token 的最老行为版本。举例设阈值 N=2：

| 组 | 最老可训练 token | 消费版本 | lag | 结果 |
|---|---|---|---|---|
| 较快完成的组 | v100 | v101 | 1 | 满足版本条件 |
| 较慢完成的组，八条评分均可信 | v100 | v104 | 4 | 整组超龄丢弃 |

N=2 只是现有 spike 起点下的算例，不在本轮重新冻结数字。一条长轨迹早期来自 v100，即使后期响应来自 v104，最老版本仍是 v100。

这道限制有目的：限制旧行为策略与当前策略的差距，不能把它一律当多余防御。faithful DIS 处理进入训练样本的行为概率差异，不会恢复已被整组删除的动作，也不保证无限大的版本差都能稳定有效训练。

处理时要分辨：组完成前已经老化，还是完成后在 buffer 等太久。前者涉及任务时长、长尾、并发与训练更新速度；后者优先排查完成队列积压和生产/消费失衡。必要时调整 N，但要同时看有效 token、DIS 接受/拒绝及训练表现，不能只追求 drop 数下降。现有 B-1 已允许把 N 作为 profile 参数调整，不要求重新建设准入体系；本轮不改算法或发布节奏。

## 5. I16：三种重试的代价和语义不同

| 重试位置 | 可以保留什么 | 主要风险与成本 | 建议 |
|---|---|---|---|
| 同一冻结工件重评分 | 八条模型轨迹、原 action/logprob/版本全部不变 | 多一次评分与等待；需要识别可重试基础设施错误；可能让整组继续老化 | **最值得现在单独讨论的窄候选** |
| 只重新 rollout 失败的第八个成员 | 七条旧轨迹 | 新的模型输出与物理 attempt；预算、失败选择、混合版本与旧七条老化都要处理 | 暂缓通用支持 |
| 整组重新 rollout | 同一道 task，可重新形成完整组 | 已有七条成果不能复用；又承担八条生成；确定性失败会再次发生 | 不直接打开现成无界 retry |

**重评分例子。** 第八条模型已交出补丁，grader 创建前发生已识别的可重试连接故障，尚无可信评分。旧请求已明确结束，使用同一冻结工件与相同测试条件重新启动 fresh grader。第二次可信得 0 就接受 0，得 1 就接受 1；第一份没有可信结果的失败记录保留，但不先进入组统计。这里不重新让模型解题，也不新增第九个训练成员。

**禁止按成功择优。** 已有可信 0/1 不能为了“再试试”重复评分，更不能反复跑直到通过或取最高分。对于 flaky 测试的专门评测协议是另一问题，不属于这里的 infra retry。配置缺失、parser bug、baseline/身份矛盾、候选测试超时/OOM、原因未知的失败，也不能仅因返回 `failed_to_grade` 就自动重试；测试超时/OOM 的具体模型/环境归因留第 4 组。

**补第八条不能让旧七条变新。** 七条最老版本 v100，第八条重采后全是 v104；消费时最老版本仍为 v100，N=2 时全组仍会过期。混合行为版本本身不被当前 fully-async 禁止，但必须保留真实来源并满足现有条件。重算旧 token 的当前 logprob 不能改写当时采样版本。

当前 miles `retry` handler 是 `_recycle`：重置并回队整个 prompt group；它不是上述“只重评分”，不负责定义有限重试次数，且 dynamic-filter DROP 不经过这个 handler。直接把 `drop` 改成 `retry` 不等于解决 I16。

## 6. 建议怎样推进，以及需要用户决定什么

**先落实、无需新算法选择：**

1. 修 I05 等确定性内部错误，提前发现已选 profile 的确定配置缺失。它们不能靠重试掩盖；评分侧具体来源与 B 联合处理。
2. 补齐从发起、完成、进入 buffer、消费到丢弃的已有事实关联。按 task、根因、已知轮数/token/耗时比较消费前后；分别列 infra、hard wall、stale、零方差。未知长度记未知，不能把未完成任务记成长度 0。
3. 汇总除了组数，还记录已知丢弃动作量与成本。当前终局事件的 attempts 不包含全部在飞/关停对象，不能作为所有已发起尝试的分母；缺少的发起/终止事实沿现有身份记录补接，不建 ledger。
4. 在原定短作业中查看损耗来源、消费组构成与版本等待，不新排完整算法消融或预设任意百分比自动闸门。观测是用来选修法，不是观测到以后就不处理。

**现在值得提请窄改判：允许同一冻结工件因已识别的暂态评分基础设施故障，最多追加一次评分尝试。** 条件为：没有可信评分；首次评分工作已停止；输入工件/评分配置不变；不重新采样模型；沿现有队列；共享一个有界的评分总预算，不每次重置；关停后不重开；保留首败原因；最终只产生一个供 projection/admission 消费的评分，消费时仍执行 staleness 检查。预算数字后定。

这会修改 B-2“首版不实现有界重试”的一小部分，**后续用户已确认该窄方向，并在最新消息中确认 §8 的具体范围，尚未实施**。不是要求先达到某个损耗率才允许考虑，也不是对所有 `failed_to_grade` 打开重试。准确错误集合需在具体 producer 处辨明；不靠泛化的错误关键字猜归因。

保留完整组与版本条件的理由是先避免同时修改算法、身份和故障恢复三条边界；不是宣称当前合同无偏或永远不能改。若主要损耗来自超龄长组，评分重试救不了根因，应该先处理供需、等待与 N；若主要是已知短暂 grader 故障，则有限重评分比重新采样整组更有针对性。

## 7. 当前代码能复用什么，仍缺什么

- formal 路径在冻结工件持久化后释放 rollout 容器，评分只读 `FrozenDeltaSource`，重评分不需要恢复模型执行容器：`generate.py:3186–3196,4384–4420`。
- 最小候选插入点是 `_finalize` 内 `_grade` 获得报告后、返回给 `finalize_rollout` 的 projection/admission 前；最终结果已经交付后不得再重新打开终态：`generate.py:4384`、`wrapper.py:177–181`。
- 每次 `SWEGradingManager.grade()` 已有新 nonce、独立 report/timing ID，并为 fresh grader 分配新容器名；同一 trajectory/frozen 输入可以再次送入现有评分队列：`manager.py:1012,1079,1297`、`queue.py:206–224`。这是静态接线可行性，不是已完成重试功能。
- `GradingInfraError` 目前原因过粗，`failed_to_grade` 还包含解析错误等不能自动重试的情况；需要从错误产生处取得可重试分类和阶段事实：`manager.py:655–669,1214–1237`。
- `grade()` 的 finally 会尝试清理，但不等于旧容器一定已停。候选需要确认旧工作收口，沿用关闭拒绝与既定 I14 修复，不叠加遗留 grader：`manager.py:1005,1239`。

本轮复用一对窄核查：Production Tracer 核冻结评分/报告身份/终态时序，Falsifier 核七人组、混合版本和选择偏差；主审回读关键函数并用标准库计算表内数字。没有新故障注入、标准测试、Docker/GPU 或训练执行；没有修改源码/配置，没有提交推送。

## 8. 重评分条件的具体边界（2026-09-09 后续讨论）

**用户已确认的部分：** 首版保留完整组，完善观测以定位具体原因后修复；后续补可变组外部资料调查。用户已同意最多追加一次同工件评分，并在 09-09 最新消息中确认以下范围。无需再次索取相同许可，也不立即开启新的外部阅读队列。

**已批范围：首版只开放镜像就绪/获取与新 grader 容器创建/启动两个早期环节中，可识别为可重试的传输或服务故障；候选测试尚未发起。** 不对所有测试前失败自动重试，不把所有连接错误或非零退出码都当成已证明的瞬态。一次失败无法证明第二次一定恢复，此处定义的是可做一次有限尝试的错误类别，不是宣称已测得恢复概率。

| 真实发生位置与事实 | 首版已批处置 | 原因与限制 |
|---|---|---|
| 镜像就绪/获取时，已识别的可重试传输中断或临时服务错误 | 可使用一次追加评分额度 | 本地缺镜像后正常 pull 不是重试，也不是 infra 丢失；镜像名错、权限/认证错、digest 错配不在允许范围 |
| 创建/启动新的 grader 容器时，同类可重试服务/传输错误；未进入候选执行 | 可使用一次追加评分额度 | 请求回包丢失不证明未创建容器，先按本次已生成的容器名确认/收口旧工作 |
| 上述两个阶段，但原因未知，只有非零返回码、泛化 timeout/infra 字样，或错误源不能分辨 | 不自动重试 | 保留真实原因并走原分类，不能为命中重试规则改标为局部暂态 |
| 确定的镜像/权限/配置错误；profile、baseline、身份或数据完整性矛盾 | 不重试；沿用原有报错/fatal 规则 | 第二次不能修复同一错误配置，完整性错误也不能降级 |
| 其它准备阶段或候选测试已经发起后的中断、超时、OOM、空日志/解析失败 | 首版不纳入自动重评分 | 有些将来可能可重试，但涉及模型行为、评分归因及执行状态；本轮不顺带决定第 4 组的 reward 规则 |
| 已有可信评分 0/1 | 不重试 | 不通过重复评分择优，不把普通模型失败当 infra |
| 已进入 shutdown、已有 run-fatal、旧工作无法确认结束、共享总预算耗尽，或最终评分已交付 | 不启动追加评分 | 不绕过已有停止/资源/终态规则；测试前发生也不能豁免 |

**所有允许情况共用原窄方案边界：** 同一冻结工件与同一评分配置、同一模型 execution；各次 grader 使用独立已有报告/容器身份；首次失败与追加结果均记录，最终只交付一个评分。整次评分任务总共最多两次尝试，不是 pull、start 各能加一次；准备、等待与重试共用有界评分预算，数字另定。仍走现有队列，不绕过并发上限；不改 rollout 行为版本，最终只在既有 consume-time 权威处判 staleness。

**实现对应与尚缺事实：** 当前 `ExecResult` 只有 exit_code/stdout/stderr（`manager.py:81–109`）；`GradingInfraError` 只有宽泛类别。需要在明确 Docker 操作边界上做小范围映射，保留原始错误供诊断；可以使用已核对的 CLI 错误形态，不以一个 `timeout` 子串匹配所有来源。没有可靠映射的返回不自动放行。此处不要求新 Docker 服务、通用分类引擎或全局健康探针。

`_start_container` 在调用前已生成 name，但 `_ContainerRecord` 在 run 成功返回后才建立（`manager.py:1297,1355–1368`）。因此创建回复丢失时，现成 `record is not None` 清理条件不足以作为“旧容器不存在”的证明。实现需保留本次已生成名字，复用现有关闭责任处理该次创建的不确定结果；只在异常/重试路径核实，不新增每次正常评分的检查平台。清理失败时不自动追加。这是待落实的生命周期要求，未宣称生产已出现重复容器。

窄核查补充：同一 `_start_container` 函数还包含镜像 ID inspect 与启动后 profile 检查，不能按函数名整体标成可重试。当前 ID inspect 未检查 exit_code 就构造租约（`:1303`），不能从后续校验错误反推传输故障；profile 违规仍按原 fatal。`_container_running=False` 也可能来自 inspect 失败，不是清理完成证明；沿名字收口属于待实现的接线，当前 `_remove_container` 仍接收 record。CLI 取消回收缺口按既有 I14 一起落实，不从 wait 取消直接推断旧工作结束。

**决策分工：** 上述失败阶段/类别范围已获用户确认。范围内具体错误映射、字段在内部怎样携带、最多两次的循环和必要正反例由实现者按 T1 说明；新增测试启动后的重试、未知错误默认重试或降低已有 fatal 都超出该范围，需要单独讨论。现有记录可复用，不因为新增一次重试重新引入 artifact hash/审批闸门。

本轮主审与复用的两位角色仅核早期准备故障、创建不确定性及语义排除项；没有新故障注入、代码/配置修改、Docker/GPU 作业或提交推送。
