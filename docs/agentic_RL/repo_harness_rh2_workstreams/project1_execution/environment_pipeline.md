## 2. 已形成的工作方式

| 环节 | 已有方法与产物 | 当前边界 |
| --- | --- | --- |
| 来源与条件对齐 | 固定题面、base、gold、测试、参考集合、镜像和实际运行条件，区分公开/私有材料 | 同仓配方可复用，逐题合格结论不能直接继承 |
| 环境与评分验证 | 真实RH2 noop/gold、逐测试核对、安装/构建生效、资源与清理；异常时定点对照 | 原独立脚本、真实grader、真实actor是不同证据层级 |
| 版本化修复 | 缺依赖/资产、服务、资源、参考绑定和材料分别修订，保留失败版本与修后证据 | 修订参考/测试材料要显式标版本；不能用删断言、放宽容差或错误相同凑通过 |
| 静态质量审查 | 每题独立公开阅读；主审先原件后历史；独立reviewer先形成初判再交叉复核；根按包验收 | 需求—断言双向映射、合理替代解、错误解、回归与开发需求；源码推断不写成实测 |
| 选中题的开发条件 | 统一环境说明＋逐题最小命令；以真实解题身份核解释器、权限、资产和公开复现 | 评分侧安装成功不能证明解题侧可用；无需先让agent运行隐藏测试或全仓测试 |
| 真实求解与回流 | 同条件独立求解，审阅成功和失败，区分能力、接口、环境、预算与评分问题 | 强模型失败只是调查线索；见过gold的调查者不充当独立solver |
| 正式用途与扩大范围 | 依据证据选择训练/开发/评测用途，冻结实际消费的环境版本，再分批扩池 | 当前尚未定案完整训练题单、基座、训练配方或最终独立测评集 |

这些环节按小批交错推进，不要求先做完一条庞大的串行流水线。已有40项清单用于查漏，42条CPU方案按问题选择，均不等于同数量的生产闸门。先把少量候选送进真实求解，再让新证据反向改进筛查。

## 5. 后续协作与更新方式

1. **开工先查本页和任务题号。** 到修复目录、静态题卡及当前执行单核对版本和已有证据；不要只读旧README顶部或重新猜同一依赖问题。详细结果必须注明适用的来源/配方/角色和实际验证范围。
2. **新工作仍可有一个具体执行文件，但必须登记到本页。** 在§4更新状态/下一步，在§6追加日期、负责者、范围、结果与证据链接。已有同一主题文件优先续写；不再另起无入口的“总计划”“最终总报告”。
3. **状态只写到证据支持的位置。** 建议、已决定、已实施、已验证、隔离/待查分别写。历史证据不回写；新结果纠正旧结论时，在本页指出被替代的结论，并链接修订记录。
4. **保留既有决定和实现归属。** 本页负责导航与当前事实，不替代具体决策文件。A的通用实现与B的题级配方共享文件时确定单一写入者；写文档不等于已通知对方。跨线沟通仍记入[环境交接板](env_data_eval.md)，并链接本页相应工作。
5. **公开协作资料与solver输入分开。** 本页及链接含gold、隐藏测试和审查线索，只供协作者阅读；不能整目录塞进基座工作区或提示词。新solver仅收到指定公开题包。
