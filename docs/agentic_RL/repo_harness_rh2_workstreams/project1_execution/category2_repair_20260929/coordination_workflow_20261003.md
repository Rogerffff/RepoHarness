# 分类二协作流程简版

更新：2026-10-04。**三方协作现行规则：用户已批准实施并恢复实验，更新工具、总账与路由已迁移。CPU／GPU实际开放以各自运行回执为准。** 范围为15个仓库、52题，不是当前未完成数量；GPU线程原来负责的旧题保持原归属。迁移与逐仓接续见[恢复记录](coordination_resume_20261003.md)。

**文件记录待办和证据，消息负责交接提醒。** 落账后仍发送请求，完成后仍回告；取消管理线程中转、抄送、接单确认和普通进度播报。

本文只调整协作方式，不替代[统一处理标准](../task_screening_standard_v1_20260925.md)及用户后续确认的准入边界。已知会妨碍合理求解或造成错误评分的缺陷，须修复并复验后再进入普通探针；发布成功、命令退出0或原评分通过都不能单独核销这些缺陷。已有有效审查与运行证据按适用范围复用，不因换流程重新全套审查。

## 三方职责

| 角色／线程 | 负责什么 |
| --- | --- |
| 各仓库线程 | 题目修订、CPU实验、安排非作者subagent核查、探针申请、结果分析和后续修复；维护本仓逐题进度。 |
| 发布：负责处理分类二的明确问题 | 共享consumer、正式登记、冻结版本、封包、CPU部署和校验；接管CPU资源文档、共享运行环境及机器异常的处理入口。只核共用改动、材料消费与身份、部署事实，不重复终审题级语义或轮询15仓进度；验证按受影响范围做。 |
| GPU：负责处理第一类的模型探针 | 探针链路和GPU环境、输入身份核对、单卡排队、执行、运行证据和回执；题级语义结论由题主负责。 |

CPU日常按现有固定分组和作业槽自助运行，无需发布线程逐次放行。CPU公共问题以`cpu_support`请求交发布，GPU链路问题找GPU；两者确有共享依赖时直接对接。

题主按已批准规则决定普通题级处理，并自行安排非作者核查，**无需等待管理线程分派、追加常规审批或再次终审**。已有专项裁定只适用于其明确对象和边界，不转化为所有题主可修改任务目标、公共契约或安全边界的新授权。确实超出公开依据或已有授权时，附证据和具体选项交用户决定；已有明确委托的专项裁定仍按原范围处理。

**独立委托，不属于题目交接链：** 用户在取消普通管理中转后，又于2026-10-03明确委托“梳理分类二处理背景”每30分钟观察GPU覆盖与外部调研，后来增加评分性能跟进。这项[独立巡检](overnight_watch_20261003.md)继续按其授权执行；题主、发布和GPU无需向它汇报常规进度，也不等待它才能推进。旧观察与裁定记录保留。停机、销毁、租机及超出本批的项目目标仍须用户明确授权。

## 一题怎样走，何时发消息

| 步骤 | 文件动作 | 必要消息 |
| --- | --- | --- |
| 先做关键诊断 | 题主复用已有材料、入口及候选，先验证具体缺陷和最小修订；材料草稿、私有定向检查不必先请求发布。 | 普通准备不发消息；公共环境确有缺口才提`cpu_support`。 |
| ① 必要时请求发布 | 只有需要新的正式材料身份或共享消费能力时，固定修订材料，在总账创建`publish`请求，指明入口、摘要、需要支持的改动和CPU主机。已有版本满足要求时跳过。 | **题主→发布**：请求ID＋总账路径。 |
| ② 发布处理 | 领取请求，完成所需登记、封包、部署和校验；复用未变且已验证的镜像和代码，不重复构建或审查。回执分别注明模型运行镜像（actor）与评分镜像（grader）的身份、交付范围和证据，未覆盖项明确列出，再将请求标为已回执。缺输入则列明缺项。 | **发布→原题主**：请求ID＋结果摘要＋回执位置；输入不足时发一条具体补充要求。 |
| ③ 题主CPU验收 | 新正式材料须验证实际消费和正负对照。题主安排非作者subagent核查本次受影响部分，复用未变部分的有效证据，不自动再做全题终审；公开题面变化时增加干净上下文的公开读者。 | 普通进度不外发。若需再次发布，回到①。 |
| ④ 题主提交探针 | CPU验收和独立核查通过后，固定`probe_request.json`，列出材料、所需consumer，并分别链接实际actor环境及grader镜像的身份与验证证据，在总账创建`probe`请求。模型／次数／预算引用GPU统一冻结配置版本，并遵循用户最新覆盖优先指令；题级资源或评分时限只列已批准差异，GPU派发时核对实际配置。等待期间继续同仓其他题。 | **题主→GPU**：请求ID＋总账路径。 |
| ⑤ GPU执行并回告 | 已有发布支持该材料时，GPU自行核差异、冻结部署兼容版本并做受影响窄验证，再执行探针；仅共享实现／登记缺失或有缺陷时，创建关联的`publish`请求。 | **GPU→原题主**：请求ID＋结果摘要＋回执位置；共享兼容缺口由GPU直接找发布，不让题主转话或重审已发布内容。 |
| ⑥ 题主分析和收口 | 分别记录执行／评分运输是否正确、候选语义是否正确。发现妨碍普通探针的缺陷，即使请求已回执，也回写`blocker`及受影响材料版本；修订后按影响复验。 | 普通结论只落账；确有受影响的排队／在途作业或共享缺陷时，才定向通知GPU／发布。 |

正常一次发布是两条消息，一次探针也是两条；补充信息按实际缺项沟通。同批请求可以合并通知，不需要另发“收到”。题主核收结束回执后仍执行工具`ack`，再更新下一步并清除已结束的`active_request_id`；这只是落账，不代表验收通过，也不清除尚存的题级阻断。**探针执行完成不等于题目处理完成，也不自动代表训练资格。**

评分镜像发布或评分通过，不能代替实际actor环境、运行身份及公开开发操作的验收。本批可沿用冻结code4或经窄验证的后续兼容版本中的精确`actor.image_override`诊断入口，绑定固定镜像SHA和来源／配方证据，并核实际容器镜像；它不代表正式训练的typed actor租约已接通，也不要求所有探针等待该训练接线。具体边界见[GPU接口核查](../../../../../runs/ordinary_gpu_probe_20261002/migration_20261003/swe_actor_image_interface_readback_v1.json)。

一个`probe`请求可对应多个实际job。GPU总回执逐模型／次数列出job ID、实际code／material／profile与预算、结束分类、原评分和证据，以及未执行部分和原因；首个模型完成不算整项完成。追加／恢复须关联旧request／job，只运行未覆盖或有依据需重跑的部分。

GPU在接收及新派发前读取题主的阻断记录，不自动复用已知有缺陷的版本，原评分保留。发现共享缺陷时，题主可立即停止自己的相关CPU工作并要求GPU停发相关作业，不必等旧请求完成。发布／GPU负责各自范围的现场保存、修复验证和局部恢复；在途代码不热换。用户全局暂停仍须用户明确恢复。

## 总账记录什么

沿用[repository_work_packages_20261002.json](repository_work_packages_20261002.json)，保留已有分组、题ID、owner线程ID及证据字段。线程名称可改，消息按线程ID寻址。现已增加以下两部分，不把长报告复制进总账。

**每题增加`progress`，由题主维护：**

| 字段 | 内容 |
| --- | --- |
| `material_version`、`phase` | 当前材料版本；阶段为修订、CPU验收、探针、结果分析或收口。等待发布不另造一套题目阶段。 |
| `checkpoint`、`next_action`、`blocker`、`blocked_material_versions` | 最近完成事项、在途作业ID、下一步、阻塞及受影响版本；保留缺陷证据和修复状态，不能随请求回执自动清空。 |
| `active_request_id` | 只指题主当前正常发布／探针交接，每题一个。公共支持、GPU发起的发布兼容请求独立登记并关联，不占此位置，不被已领取的探针阻塞。 |
| `revision`、`updated_at` | 记录版本号及更新时间，由更新工具维护；已有`evidence_refs`继续链接证据。 |

**顶层增加`requests`，按唯一请求ID保存交接：**

| 字段 | 内容／写入者 |
| --- | --- |
| `task_key`、`kind` | 普通请求绑定来源＋题ID；类型为`publish`发布、`probe`探针或`cpu_support`公共CPU故障。题主可发起，GPU也可直接发起所需兼容发布。 |
| `scope`、`affected_tasks`、`related_request_ids` | 支持／兼容请求关联主机或组件、受影响题和已有请求；同一故障合并一项。跨题支持请求可不绑定单一`task_key`；恢复探针的旧job引用放在详细输入中。 |
| `recipient_thread_id`、`reply_to_thread_id` | 发布／GPU接收方及发起线程；普通请求回题主，GPU发起的兼容发布回GPU。工具从登记信息填入，不经巡检线程中转。 |
| `material_version`、`input_ref`、`input_sha256` | 固定版本、请求或材料清单路径及摘要；提交后不覆盖。 |
| `status`、`claimed_by`、`receipt_ref` | 接收方领取并回写；状态为`queued`待领取、`claimed`已领取、`needs_input`待补充、`returned`已回执、`cancelled`已取消。缺项清单也写入回执。 |
| `notices` | 按唯一事件ID记录提交、缺项、补充、取消意图、回执等通知及`sent_at`；发送方确认发送成功后登记时间，为空表示待通知。 |
| `revision`、`updated_at` | 工具维护，用于并发更新检查。 |

`returned`表示本轮已收口并给出总回执，可以是部分结果或失败；仍在执行或将继续执行时保持`claimed`。完成范围看回执及GPU账本。**下一步执行者由请求推导**：待领取／已领取归接收方，待补充／已回执／已取消归发起方。补充说明后落账并通知，工具将请求转回待领取；输入字节变化须建新请求。

取消先登记意图并通知接收方；未确认安全收口前，已领取请求保持`claimed`。接收方确认无在途、保存清理回执后才标`cancelled`，题主据回执释放`active_request_id`。独立故障报告不受此等待限制。

发布线程维护总账中的公共路由和CPU分配信息；原管理线程字段留作历史，不再参与寻址。全局暂停记录保留，CPU和GPU分别由发布、GPU线程按用户指令执行。

发布线程维护[更新工具](../../../../../rh2/scripts/category2_task_board.py)，命令见[最小用法](task_board_usage_20261003.md)：**全文件锁保护读改写，只核对本次目标记录的`revision`**，再按字段归属原子写入；无关题更新不互相制造版本冲突。保留现有运行入口，不另建调度系统。先落账再通知，失败留待发送；允许重复提醒，按request／job ID防止重复执行，不为零重复消息增加事务系统。

暂停或交接前保存检查点；接续时读本文、自己的待办和对应证据。已有领取记录先核实真实作业及回执，不能因上下文压缩就重跑。

工具与路由已于本轮切换。15仓使用更新工具维护自己的字段，不手改共用JSON；发布线程接管CPU资源文档、`control/`、`setup/`及部署清单。此前暂停点保留为历史，恢复通知和实际CPU／GPU回执决定接续位置；解除行政暂停不解除题级缺陷阻断。
