### 需要改进或继续保留的边界

- **实现方式偏逐题特化。** 为逐步验证新机制，目前每种修订都增加受限类型、登记与代码分支。后续仓库线程先复用已有入口；遇到具体不支持的修订操作，由共用维护者补齐并验收，仅相关正式运行等待。不以先整理通用schema作为全体开工前置。
- **验收工具和记录重复较多。** 每题复制prepare／replay／actor／直评脚本，再维护多个清单，容易发生空格、字段和路径的预期错误。先复用现有工具，遇到重复再整理；不强制先重写共用runner。详细原件保留，用户入口只维护一张题卡。共享树发生真实变更仍需回归，但不应机械重复无关检查。
- **公开检查必须对应实际交付内容。** Moto5406暴露了旧命令把题面表名偷偷统一的问题。本批发现后另做正式题面修订，未放行。以后准备公开命令时就要逐项记录它与原题示例的差异，不能等CPU接线末段才发现。
- **三方对照不能证明测试已穷尽合理解法。** 当前五题关闭了已经证实的漏判，并未对所有等价正确实现、多次随机稳定性或全部模型路径作保证。是否补第二种独立正确实现、边界输入或重复运行，应按修订风险决定，不能机械每题加满，也不能省略已出现的相关疑点。
- **真实运输目前主要检查noop工件。** 五题原actor工件均无代码改动；非空gold／错误补丁经正式replay验证。二者各有证据，但不能称每题均验证了“由真实actor导出的非空修复补丁”。后续应按共享运输组件变更和风险补代表性非空往返，不默认每题重跑。
- **资源与独立性不夸大。** 15秒采样有缺口，正式终止字段为null时仍未知；不把准备期copy-up峰值当测试内存需求。部分交叉review有既有上下文，已披露，不叫fresh盲审。公开题面发生修订时，才另用未读私有材料的新读者核对。

上述工程问题是历史总结，后续实现与验证以对应发布及执行记录为准；用户已于10-02确定题主持续负责到模型反馈处理、统一探针执行的方式，10-03已恢复实验。

每题由原负责人持续完成修订、CPU验收、探针申请、结果分析和必要的再次修复，最终形成有证据的用途结论，或具体阻塞与解除条件。达到普通探针条件只是本题一个进度节点。不能用“受限比较”“事后人工审计”替代已确认缺陷的修复。CPU验收通过仍不是训练资格，也不证明模型一定能解题。

每个修订都先利用已有材料与结果，只补受影响路径：公开开发操作、正确修法、noop，以及能触发已知漏洞的错误候选。需要正式评分时，验证测试确实执行、参考键与测试身份一致、安装子命令与测试实际退出、完整日志和容器清理。改变题面另由未接触私有材料的公开读者检查。经独立复核满足条件后，题主向执行者提交固定版本、目的与证据；执行者回传完整结果并通知题主，由题主继续审计成败。不能仅转发旧 `probe_ready` 标签，也不能把执行完成当作题目处理完成。
