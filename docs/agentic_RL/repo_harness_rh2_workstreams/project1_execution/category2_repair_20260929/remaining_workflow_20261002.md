### 一分钟说明

- **本批52题按15个仓库分工，一个仓库一个线程**，每题只有一个持续负责人；就绪一题就提交探针，不等同仓或全批完成。线程可以并行准备和修订，CPU容器并发另按机器资源设置。
- **原第一类线程承担两项工作**：统一执行所有人的GPU探针；继续负责它原来尚未完成的题目。这些旧题不再为了新分工重新移交。
- **其他题的修订线程负责到底**：接续已有证据 → 修必要的问题 → CPU验收和独立核查 → 提交探针 → 审计回传结果 → 必要时继续修复。
- **原第一类线程同时准备统一入口，发布线程负责题级D6共用修订能力和版本。** 题主不各自写探针脚本，也不各自热改生产评分入口；执行队列尽量持久运行，避免执行者分析自己题目时让GPU无故空等。

派发时曾逐线程登记owner，并验收三台CPU、按仓库固定分组，这是历史部署快照。当前主机与并发见[CPU资源入口](cpu_resources_20261003.md)，逐题进度见总账，真实GPU作业查执行账本；不把旧准备状态当作今天的剩余工作，也不把宿主就绪等同于题级验收通过。

## 2. 一题由同一负责人走完闭环

按仓库分配持续负责人，逐题维护独立记录。负责人可以委派实验和复核，但修订验收通过、开始排队或探针结束都不改变题目归属。分类1／2／3仅描述当前需要什么处理，不再决定题目由哪个线程接走。

| 步骤 | 要做的最少工作 | 可以复用／结束依据 |
| --- | --- | --- |
| ① 接续已有证据 | 核本题版本、公开要求、全部已知缺陷、可信正对照和触发反例。写清哪些还没做。 | 读原件与已有题卡，不重启一套静态角色链；只补影响本次决定的缺口。 |
| ② 做窄修订 | 修改本题测试／参考／题面或配方，先复用已有入口和对照验证关键缺陷；材料草稿及私有定向检查不必先请求发布。 | 一项独立缺陷优先一个有区分力的实例；已有多种候选不机械再造。 |
| ③ 正式落地与验收 | 需要新正式材料身份或共享消费能力时才请求发布；新材料仍须验证正式消费与正负对照，确认真正执行对应断言。 | 未变镜像、代码和有效证据不重复构建或审查。新测试通常做0／1／0；有缺陷的gold可为0，由经核实的替代正对照为1。 |
| ④ 补开发缺口与独立核查 | 只补本次影响的actor公开命令；非作者核公开依据、关键断言、正对照与真实结果，必要时补一个不同机制的候选。 | 题面变更请新公开读者；纯私有测试变化不自动重做公开阅读。复核发现问题只回到相关步骤。 |
| ⑤ 直接提交探针请求 | 题目负责人提交固定材料版本、CPU验收证据、调查目的和适用条件；引用统一模型配置与预算，由执行者接单。 | 已知影响普通求解或评分的缺陷已处理；链路与资源就绪后即可运行，不等待全仓或全批修完。接单不转移题目责任。 |
| ⑥ 统一执行并回传 | 原第一类线程作为探针执行者，按单卡队列运行独立solver、评分并保存轨迹、补丁、实际配置／预算、异常和清理记录；完成或失败都通知原题负责人。 | 执行者负责结果完整、运行条件一致，不自行改变题目、验收范围或题级结论。 |
| ⑦ 原负责人分析、修复和收口 | 审计成功与失败候选，区分能力、题目、环境、预算及链路原因；发现题级问题就修复、定向复验并提交新探针，公共问题跟进链路维护者。 | 形成有证据的当前用途及剩余事项，经必要独立核查后收口。探针执行结束不等于题目处理结束，CPU通过也不等于训练资格或有RL信号。 |

```text
同仓题目负责人：调查 → 修订 → CPU验收 → 提交探针请求
                                             ↓
统一探针执行者：                         排队 → 求解／评分
                                             ↓ 结果与通知
原题目负责人：                分析 → 必要修复／复验／再提交 → 用途结论
```

模型求解使用干净上下文，只接收公开材料与中性环境说明；题目负责人的gold、反例和私有结论不能随执行请求进入solver上下文。负责人排队期间可继续同仓其他题，回传后仍须处理本题结果。

每题保持**一张当前题卡、一份机器可读修订单、一份结果清单**。现有原件、失败尝试、候选、日志继续保留，不为了精简丢证据；公共配置与代码版本引用批次记录，不重复抄写。没有新增独立问题时，不再写一轮长篇“从头分析”。

## 3. 怎样控制实验量

- **默认从小矩阵开始，不设为了凑数的候选。** 新验收通常先选noop、有效正对照、已知错误候选。放宽实现／文案约束时再选一份不同合理实现；gold本身有缺陷时保留它作为负对照。常见是3～6个候选，这是起步规模，不是遗漏已知缺陷的硬上限。
- **已有20～40个候选怎么用：** 私有定向检查可批量复用已有工件；正式矩阵按“每个独立已知失真机制都有对应对照”去重。删去重复候选须说明被哪一项覆盖；若预期、身份或运行差异不能等价，保留该项正式复验。不能只留下最容易通过的三行。
- **区分工具验收和题级验收。** 共享修订入口变更做一次相关代码检查、代表性真实往返与受影响题回归；入口冻结后，后续题主要是材料配置和自身评分，不再为每题复制生产分支、做同一套公共检查。
- **开发验证按影响补。** 只改私有测试且actor镜像／公开材料／入口均未变，可引用已有正式开发证据；换依赖、题面、构建或工具链则补原失败路径。换宿主至少验共用入口和各题关键身份／导入，不默认把所有旧命令重跑。root私有对照不能顶替尚缺的actor证据。
- **题面-only修订不必重跑不变评分矩阵。** 证明评分材料及执行条件未变，补新读者和实际消息交付即可；材料身份的联动与接收仍需核。
- **独立核查每题保留，深度按变化。** 已有独立语义意见就接续它，不要求每次fresh全题盲审；新增断言要核是否绑定实现。核查者可以审同仓小包，但不能自审自己改的修订。

题级CPU结果的非作者核查由仓库负责人安排符合上述要求的子agent完成，按已有清单读原件、逐参考结果、退出状态、版本身份与清理，并披露核查者接触过的上下文；不要把15仓全部结果排到共用材料发布者。题主在自己的记录和总账保存复核摘要与原件指针，满足条件后直接提交GPU。材料发布者集中处理共享consumer、不可变登记、跨类型合并和必要抽验；已有复核按当前有效证据接续。已完成的独立核查按适用版本复用，不因分工明确而新增一轮审查；公开题面变更仍使用干净上下文公开读者。
- **稳定性只在有风险时加测。** 环境通过不等于已证明稳定；出现随机、顺序或资源疑点才按具体假设重复，不统一照搬8次，也不规定重跑一次就够。

建议每题初次执行预算覆盖“一版修订＋一次定向修正”，复核覆盖“一次核查＋一次阻断关闭检查”。这是CPU修订的投入安排，不是模型求解的token／回合预算。若同一核心问题仍反复出现新缺陷，题主记录已证问题、最后有效版本和继续成本，先推进同仓其他题；在已有授权和资源范围内自主安排必要补证，超出范围再提交用户，不设协调者逐题追加审批。**这是投入检查点，不是放行条件；已知必要行为没有修好，仍不进普通探针。** 新出现不同根因时按影响决定，不机械算轮数让它消失。

## 4. 共用工具按题补齐，不作为全体开工前置

**仓库线程直接接题推进。** 能用现有正式入口完成的修订，直接做材料、CPU验证和独立核查，不等待通用工具重构，也不重复验收已完成五题。

如果某题需要的操作尚未被正式入口支持，例如替换有效测试补丁，题主说明具体输入、预期行为和缺口，直接提交发布线程补齐并验收。只等待依赖这项能力的正式运行；该题的材料准备、私有定向检查及其他题仍可继续。私有模拟不能代替正式落地验收。

这里保留的只是**共用代码由一位维护者统筹、运行绑定冻结版本**：避免多个线程同时改评分入口，或在他人的在途作业中热换代码。复用现有脚本，不把建设通用schema、重写共用runner或全批兼容检查设成必经阶段。确有重复再按实际需要整理，改动的验证范围由受影响路径决定。

### 题目责任与共用执行分开

| 角色 | 持续责任 |
| --- | --- |
| 同仓题目负责人 | 逐题调查、修订、CPU验证、提交探针、审计结果、后续修复及最终用途；不得在提交探针后把题目标为自己已完成 |
| 探针链路准备／维护（原第一类线程） | 在新GPU机上跑通统一入口，固定代码、模型服务、Claude Code及实际配置；题级D6共用能力由发布线程维护，超出探针范围的公共生产修复与A线对齐 |
| 统一探针执行（同一原第一类线程） | 使用已验入口管理单卡队列，执行求解与评分，保存完整结果并通知对应题主；不接管本页52题的调查和修订。同时继续负责原12题和已接收5题，从分析到后续修复均由它收口 |
| 发布线程 | 公共路由、共享consumer、冻结发布、CPU部署与公共环境；题主按已有作业槽自助运行 |

探针请求和完成回执沿用同一任务ID、材料版本及题主记录。执行状态与题目结论分开：`待运行／运行中／结果已回传`只说明作业进度；是否有误拒、漏判、能力信号及是否需再修，由题主依据证据判断。通知只发本批获授权的题主和执行／维护任务；本次修改文档不代表已建立自动通知或运行队列。

最小提交／回传约定如下，沿用已有材料和证据文件，不要求题主另写一套长报告：

- **题主提交自己的请求文件**：题ID、固定材料／镜像／配方、原题主线程ID、调查目的、CPU验收证据和统一探针配置版本；公开solver输入与私有评分／调查材料分开引用。
- **执行者独占队列状态**：记录唯一尝试ID和在途作业，重启先查真实进程和已产证据，避免重复运行；各题主不同时改一个共享状态文件。
- **结果回执**：题目及材料版本、尝试ID、实际模型／配置／预算、完整轨迹与候选、原始评分、异常／清理证据位置。成功和失败均通知原题主，题主再作语义审计，不把回执的raw reward直接改成最终用途结论。
- **就绪一题即可排队**：不要求凑齐同仓、先审完上一批所有题或重跑全池；确有公共可信性异常时，仅暂停受影响的派发和成绩采信。

公共入口需变更时，维护者先协调执行者暂停受影响派发；在途作业按影响保存或收口，验收新版本后恢复。旧运行仍绑定旧版本，不能在同一批比较里静默混用。题级修订由题主提交新版本，不必因此暂停无关题目。
