## 2. 先分清四个问题，避免一个名单承担全部决策

## 3. 跨篇阅读后，最影响方向的七个判断

**第一，SWE 主线可以保留，任务覆盖不要永久等同于修 bug。** R3、R4、R13 的工程任务还涉及功能/API、测试、终端与最终产物。但任务范围扩大需要对应 verifier 和成本，材料没有要求八卡首训全覆盖。当前较稳妥的候选仍是先把仓库修复做扎实，terminal 作为独立诊断/迁移候选；是否进入训练取决于后续数据和基座证据。[配方整合 §2–3](03_model_training_recipes.md)

**第二，复用现成资产与研究环境生产并不矛盾。** SWE-smith 已提供仓库内 bug 合成路线，R2E-Gym 与 SWE-rebench 提供真实修复来源；选现成数据并不意味着放弃 PR 或合成。先核它们在我们条件下的可用性，可减少同时调试模型、安装和制题三套未知量；之后针对确切缺口再新增供应。个人项目的贡献可以来自可重复的筛选、评分纠错与有效供给改进，未必来自重新爬取最多 PR。[环境整合 §2–3](01_environment_sources.md)

**第三，环境有效、模型难度、学习价值要分别判断。** gold 能过、no-op 会失败仍不足以证明题意充分、测试完整或合法解不被误杀；0/4 也只代表四次未解，不证明任务无解。外部 teacher 的成功率、O11 A/B 标签和环境安装成功率都不能替代当前策略的学习机会。更不能用最终评测集上的基座表现反复筛题，再把它称为独立测评。[环境整合](01_environment_sources.md)、[评测整合 §1–3](02_evaluation_and_harness.md)

**第四，真实 Claude Code 下的基座诊断应先于训练配方终选。** Polar 的不同原生 harness 起点、E1 的协议变化、KAT 的环境错误，都说明低分可能来自接口或反馈。诊断要分清请求/解析、工具调用、环境执行、评分与有效解题失败。修接线就能恢复的能力，不应当作 RL 学习增益；接线无误后仍采不到成功路径，才讨论任务匹配、提示条件或有限 SFT。[评测整合 §1、§3](02_evaluation_and_harness.md)、[配方整合 N01](03_model_training_recipes.md)

**第五，不能从几篇材料拼出一条“大家都这样训练”的配方。** E2/E5/O03/Nemotron-Terminal 的相关证据主要是 SFT，O11 没有 RL 学习实验，O01、Polar、Agent Lightning 等才提供指定设置下的 RL 结果。成功轨迹过滤、保留全失败题、课程、超长处置、多教师合并的结果存在真实差异，且任务量与计算预算经常没有匹配。当前材料不支持同时把动态课程、OPD、critic、compaction loss 和多 harness 设为首轮必做项。[环境整合](01_environment_sources.md)、[配方整合 §3](03_model_training_recipes.md)

**第六，固定 harness 下的权重改善与跨 harness 泛化要分别证明。** 多 harness 参与训练也可能留下明显迁移缺口；CompactionRL 在有压缩的评测中提升，不开压缩的 SWE 却退化。主比较先固定任务、grader、工具和预算；第二 harness 或另一上下文机制应单列结果。若同时改环境与权重，要保留未训练模型在新环境下的结果，避免混淆来源。[评测整合 E1/R0](02_evaluation_and_harness.md)、[配方整合 R2](03_model_training_recipes.md)、[长程整合 R14](04_training_and_system_context.md)

**第七，有价值的效率证据必须接到独立质量。** RollArt、SkyRL 与 Forge 分别测量或讨论不同等待/供给边界。环境数、生成 tokens/s、GPU utilization、optimizer steps、有效组吞吐和达到目标分数的时间不是同一个指标。B 需要给 A 提供按任务族与成本分层的样本视图，检查加速、超时、重试和过滤是否改变了真实消费分布。[环境整合 R11](01_environment_sources.md)、[系统整合 N10/N11/O01](04_training_and_system_context.md)

## 4. 下一次与用户讨论的首份决策，应包含什么

建议准备一份**首轮任务与诊断方案**，把下面三项放在一起讨论。现阶段不必先批准最终混合比例或投入大规模制题。

| 决策项 | 建议作为讨论起点 | 初步实验后才能决定的部分 |
| --- | --- | --- |
| 项目首轮核心主张 | 在指定真实 Claude Code 条件下，可靠训练仓库任务，并证明自己的环境/供给改进降低有效学习成本、保持或提升独立任务表现 | 能提升多少；实际贡献主要来自评分质量、数据覆盖还是执行供给 |
| 主任务与探针范围 | 仓库修复主线；开发探针覆盖不同仓库、测试框架、修复机制与执行成本；terminal 是否加入少量探针单独讨论 | 正式题量、语言范围、复杂功能/测试任务扩展、terminal 训练比例 |
| 评测结构与诊断边界 | 开发诊断、内部独立任务、公共外部坐标分开；主比较固定 harness 与预算；先核任务与评分，再解释模型分数 | 最终 benchmark 版本、题量、重复次数、预算、迁移面的规模与停止规则 |

评测结构的具体建议如下，均待结合任务和成本细化：

- **开发诊断集**用于修环境、定工具与预算、识别学习空间，不能事后升级为最终未触碰测试。
- **内部独立任务**至少阻止同一原始 PR/缺陷及其派生变体跨集合；若要声称未见仓库泛化，需要按仓库留出。只留出题目但仓库仍见过，可以报告，但结论不同。
- **公共外部坐标**选与主任务相符、版本和协议可恢复的对象。N13 提醒其质量与污染有局限；内部划分也不能证明基座预训练从未见过公开 PR。需分别说明两类独立性。
- **指标分层**：固定预算的任务级成功率与配对变化是主质量证据；重复尝试时区分平均单次成功、any-of-N 和全部成功的稳定性。辅以失败类型、action/输入 token、turn、wall-clock、环境/评分开销和不确定性。不能把平均成本/成功率简单解释成实际逐题重试到成功的费用。
- **评测中的异常**按预先声明的协议保留与复跑；运行有效性和模型成功率分别报告。不要因某个 checkpoint 失败就删题，也不把所有 infra 失败自动算模型失败。具体 reward/丢组/重试语义与 A 和用户另行对齐。

## 5. 阅读之后的执行顺序建议

这里记录依赖关系，尚未启动这些工作。

1. **形成候选资产与目标矩阵。** 从已有 216 题候选及少量外部现成资产开始，核来源/许可信息、版本、任务与派生关系、实际镜像、grader、可见材料和预计成本。216 的 ingestion 不代表环境验收；不因旧投入锁死该来源。
2. **选小批开发任务，核环境与评分。** 用 no-op、参考修复和有代表性的错误/合法替代解，观察题意与测试的一致性、reset、稳定性、解析和控制面。检查应围绕实际风险，不给每题机械增加一套无限防御测试。
3. **固定基座做真实 Claude Code 诊断。** 先人工可核验的完整轨迹，再用适当重复描述任务成功与成本分布。记录准确 checkpoint/tokenizer、模板、工具、thinking/history、compaction/subagent、预算与采样；并非每个维度都要开消融。
4. **依据失败和供给缺口决定扩展。** 缺仓库覆盖再比较新 PR；稳定仓库缺某类错误再比较 bug 合成；协议技能薄弱再比较有限 SFT；terminal 有明确收益空间才提升为训练候选。每种扩展都保留简单基线与独立评测。
5. **与 A 合并首训条件和实验包。** B 给出任务与评分事实，A 闭合调用、样本和 learner 运输；正式训练配方、成本和停止条件由用户根据具体方案决定。B 的固定权重诊断无需等全部训练优化完成，也不代替训练侧验证。

候选资产核查是下一项有用的准备工作，但本轮按用户指示止于阅读与建议，不预先制题、采集 PR 或启动收费模型/GPU 作业。
