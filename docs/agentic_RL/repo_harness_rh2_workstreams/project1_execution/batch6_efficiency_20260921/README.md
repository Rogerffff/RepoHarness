## 2. 给 Claude 的实施切片建议

以下是落实 §1 的具体方案候选与验收目标，不是生产事实或加速结果。每片先给真实调用链、消费者、文件归属和最小前后对照，再实施；不为等价优化引入新的准入规则。

### E1：权限初始化，I25

- 先核 `sandbox_profile.py` 的可信初始化、`bringup.py` 和 vendored sandbox 的实际三段调用。同一个 rollout 容器只由明确的一层建立用户、配置 workspace/HOME 写权限，其余重复入口复用该完成事实。
- 不能用“用户存在”代替目录权限已正确；UID、当前文件属主、目标解释器写权限、其它直接启动入口都要保留。grader 是不同容器/身份，它的初始化不能作为 rollout 的重复项删除。
- 先处理已证重复 chown。CC 预装、HTTP 连接复用、轮询和网络复用另看成本与具体边界，不捆成一次大改。与 B 的派生镜像/属主配方对齐，避免刚省掉一遍又在安装配方里加回。
- 验收：已有用户/新用户、正式 profile/既有直接入口的写入与启动行为不变；记录实际 chown 调用和时间。先用本机/既有镜像的窄验证，真实 overlay2 成本留目标机。

### E2：批量 census，I26

- 优先用一次固定的枚举/摘要程序批量处理文件，替代每个文件反复创建 shell、`sha256sum`、`cut` 进程。Python `os.scandir`/`hashlib` 可作候选，先确认所选镜像的可用解释器和可信执行入口；不要依赖候选工作区的模块导入。
- 三次 census 观察的状态仍分别读取；保留文件内容、执行位、软链目标、排除政策、缓存省略计数和错误语义。先证明同一输入输出的 manifest/digest/增量等价，不借此改路径支持范围或排序规范。
- 验收复用既有正常与类型变化/软链/缓存同名文件等反例，比较最终工件与评分输入，补一次足量文件树的进程数和耗时对照即可。基线共享、取消 hash/fsync 属另外的设计，不塞进本片。

### E3：路由 tape 紧凑表示，I23

- 优先保留规范的小端 int32 字节及 shape/引用，避免 `base64 → list[int] → tuple → pack` 的反复全量展开；只在真实消费者要求时产生必要视图。先减表示，不同时引入工作线程和异步提交队列。
- 保留轮次、分支、版本归属、现有工件字节与摘要语义；不能因为当前消费者取末轮就删除前序捕获。若 public schema/序列化边界确须变化，在 Brief 单独指出，不假称局部容器替换。
- 验收：同一多轮多叶捕获在表示改动前后得到相同工件、同一训练路由内容和对应关系；测 CPU 时间、峰值内存、事件循环阻塞，分别报告，不把条件内存估算写成实测 RSS。I18 的近似是否可接受仍未决定。

实施入口：[E3 Brief](e3_routing_tape_brief_20260922.md)，[2026-09-22 聚焦复核](e3_plan_review_20260922/README.md)。复核接受主方案对 RH2 自有 `projection.py` 的窄等价优化与 `TurnTape` 改名；E3b 可在主体之后独立实施。bytes-like 兼容边界、回退/形状校验、实际内存生命周期按复核补入后开工，无新用户决策；尚未实施或验收 E3。

### E4：完成历史释放，I29

- 分开活记录和完成历史。完成结果已交付/落盘、容器确认清理且后续消费者无需完整对象后，释放 setup/partial log、inspect 等大对象；必要时保留有上限的摘要，累计计数独立维护。
- 先列 manager、queue、lease、close/report 的读者。不能仅因清理完成就删掉 driver 尚未取走的结果，也不能让历史裁剪使清理/失败计数变小。未知或待清理资源继续保留，不恢复年龄清扫。
- 验收：连续完成多次后的活对象数量/历史容量有界；取消、清理失败、晚清成功、最终报告与累计计数仍符合既定语义。磁盘工件自动删除不在本片。

### E5：诊断/效率配置与 GPU 测量入口，I24、I27、I28、I30

- 当前 fork 的 actor forward 条件是 `not skip_actor_forward_only and (not use_rollout_logprobs or get_mismatch_metrics)`。优先核对现有配方与这些开关的组合，而不是新写一套 forward 调度。
- **不要只加 `--skip-actor-forward-only` 就声称等价**：当前上游在未用 rollout logprob 时可改用 detached training logprob 作 old baseline。Brief 必须列出本配方实际使用的 logprob、优势/loss 与路由消费者，并明确哪条对拍不再产生。
- 配置准备只改变额外 forward/诊断能力，不改变 faithful DIS、组分母、更新边界或 I18 来源。首轮完整诊断保留对拍；效率配置的正式启用由真实验证支持。
- 测量复用 I20：合格组/有效评分产出（包括可信 0 分）、模型/环境/评分等待、prefill/decode/cache、发布与重算、训练显存、分行重复输入及 CPU/RAM/I/O。缺指标再补少量 producer，不新建监控平台。额外 forward 对照和大规模收益放既定 GPU 作业。

## 3. 受控依赖供应：单独设计，不阻塞上述优化

**方向可行，下面是推荐首版方案，具体实现尚未批准或启用。** 目标是让真实 agent 能安装合理依赖，让 fresh grader 能按候选声明安装；已有可用题的基座诊断不用等它全部完成。A 负责公共供应/网络/运行阶段，B 负责公共环境、解释器、仓库安装入口和代表题，两侧消费同一供应定义。

2026-09-22：以下保留最初设计建议；包源历史限制与 §3.2 阶段顺序的最新备选、取舍和工程修正见[Codex 方向复核 §3–§5](codex_direction_review_20260922.md)。用户尚未选定这两项，不把任一建议记成已批准的网络实现。

### 3.1 最小供应结构

```text
做题容器 ───────────┐
                   ├─ 内部 Python 包索引/下载缓存 ─ 获准上游包源
grader 的安装阶段 ─┘
各容器各自安装；共享上游下载产物，不共享可写 site-packages。
```

- Python SWE 首版优先评估现成 PyPI 缓存服务，例如 [devpi-server](https://github.com/devpi/devpi)；它提供 PyPI 缓存索引。产品尚未选定，不为本需求自建通用互联网代理或多生态制品平台。
- 缓存未命中时由服务从批准来源取包，不预猜全部包名。候选只能使用下载入口，不得到服务管理/上传能力；不能把候选自己编译的同名 wheel 回灌为其它题的可信下载。缓存服务自己持有数据目录，不给所有候选挂同一个可写 pip 缓存。
- 先核现有 isolated network/relay 到固定内部服务的接法。`PIP_INDEX_URL` 只配置包管理器，不能阻止 `curl`、直接 URL 或另一个索引绕路；真实出口由网络连接限制。Git/任意 HTTP、conda、apt 等不自动纳入 Python 包源的支持承诺，按选中题实际需要列例外和成本。
- 包版本、来源、安装阶段与失败信息优先复用日志/安装报告。缓存降低重复下载，不保证未锁定依赖两次解析相同，也不省掉全部源码构建。不要宣称它天然重建了 rollout 的终态；对照时检查实际版本、解释器和候选源码导入。

### 3.2 评分阶段顺序是主要接缝

当前 `manager._run_eval` 先执行 trusted setup、注入和保护官方测试，再运行包含候选安装与测试的脚本。因而**不能直接给当前整个候选段开放包源出口**。

推荐 Brief 具体设计为：

```text
应用候选仓库修改 → 不含私有材料的安装/构建（受控包源）
→ 结束该阶段并撤掉实际取包出口 → 恢复/注入官方私有测试
→ 运行正式测试（默认离线或题目明确的本地服务）→ 按原规则评分/清理
```

需要以真实仓库配方核对两点：部分安装依赖 test patch 改动，不能机械调换两行；安装后环境已经执行过候选代码，后续 root 只做可信文件操作，不能再次激活候选可写环境去运行初始化。现有 deadline、取消/后台进程回收、评分资源与失败归因也须贯穿分段。先解决该切片的具体接缝，不扩成完整反作弊项目。

### 3.3 最小验证与设计交付

Claude 的网络 Brief 需把产品/部署方式、初始来源、真实出口、阶段切换、A/B 修改文件和失败分类写具体；已同意的方向不重复问。仅有超出当前范围的取舍再提交用户，例如需要一般公网、私有测试可见时保持出口或引入明显更大的服务系统。

实现验证可用：缓存冷/热各一次安装；实际 agent 与 grader 用户/解释器安装成功；候选声明确实被读取；包源不可用与确证候选安装错误分开；正式测试期和直接 URL 的出口按配置生效；超时/取消仍清理。它们验证实现，不用于推算模型使用频率或训练收益。无需专门 GPU 作业，也不要求全池三路评分比较。

原容器评分保留为后续优化：真实候选出现具体问题后，按需与当前 fresh/补齐供应后的 fresh 比较；用来源一致的评分依据判断误差和总成本。未来若选择快路径加抽样 fresh 校准，抽样方式与可接受差异届时讨论，本轮没有预批准。

资料边界：[MAI 官方报告](https://microsoft.ai/wp-content/uploads/2026/06/main_20260602_2.pdf)支持缓存代理/域名允许列表的方向，不提供本项目完整实现。[pip 缓存文档](https://pip.pypa.io/en/stable/topics/caching/)区分 HTTP/下载与构建缓存并说明局限；[pip install 文档](https://pip.pypa.io/en/stable/cli/pip_install/)说明索引选择、构建和安装报告。本节是基于这些能力提出的本项目方案，未宣称部署验证。
