# 第六组补充：fresh 评分、依赖供应与原容器评分

2026-09-21 / Codex A。**状态：讨论建议，用户尚未改判 D2；不是实施授权。** 用户提出原容器评分是否更适合安装新依赖、降低三次扫描与重建成本。本次核对当前源码、MAI 原文、216 题和环境修复记录，未修改生产代码或运行新实验。

## 1. 推荐与真正的取舍

当前 SWE 仍以可重建的仓库修改为交付物时，建议保留 fresh 评分，单独重议依赖供应能力并简化扫描/初始化。理由是验证候选产物的可重建性、评分可以不依赖原执行存活；不是因为已经写了很多代码。

如果用户希望“agent 完成后留下的可工作环境”也算完整成果，原容器评分更符合目标，值得替换当前主路径。没有必要为了维持 fresh 而建立完整命令录制、容器状态复制或通用环境重放平台。原容器评分也不是退步，但不能把其通过直接解释成仓库补丁可独立重建。

三个维度应分别决定：**交付物是文件修改还是最终环境状态；评分复用还是重建容器；哪些阶段允许访问哪些包源。** fresh 不等于必须完全断网，同容器不等于必须开放公网。

## 2. 外部资料核验

已在线回查 Microsoft 官方 [MAI-Thinking-1 报告](https://microsoft.ai/wp-content/uploads/2026/06/main_20260602_2.pdf)，2026-09-21 所读版本 109 页：

- p.40：每个任务创建独立 SEE 容器；默认隔离网络，必要安装可经缓存代理与域名允许列表访问网络。
- p.41、p.101：训练 SWE 和相应评测在 agent 所用容器内评分。
- p.43：评分前恢复测试文件、后注入隐藏测试；作者明确承认测试框架 monkey-patch 等剩余作弊路径，并结合模型监控、人工检查与启发式改进。

因此“MAI 使用 fresh grader”是错误推论；同容器路线有公开先例，但报告不证明我们只把私有 test patch 覆盖进去便已足够。其模型、题单、预算、控制机制和测量条件不能等同本项目。既有精读见 [R1 §6](../../../../harness_improve/external_paper_references/reading_notes/R1_mai_thinking_1.md)。

## 3. 用户提出的依赖问题确实存在，但需区分情形

| 情形 | 当前文件增量评分的含义 |
| --- | --- |
| agent 临时安装调试工具，提交不依赖它 | 不必复制该工具；缺少它不应妨碍最终解答 |
| 新源码依赖包 X，仅执行 pip install，未留下必要声明 | 若交付物是仓库修改，成果可能不完整；若交付物包含终态环境，该安装可能是合法成果 |
| 已正确声明包 X，grader 没有 X 的缓存且禁止取包 | 是当前供应能力未覆盖合理新依赖，不能仅据此归罪模型；声明还必须被对应安装配方读取 |
| noop/gold 的原始安装、测试材料或环境本就有缺陷 | 两种评分方式都需要修公共环境，原容器无法自动补全 |

当前只冻结 workdir（SWE 是 `/testbed`）的受支持文件增量，不是容器快照：工作区外的 site-packages、HOME、系统文件、进程、shell 状态不随工件重放。仓库内的声明或 vendored 文件可以进入增量，但不会重放 agent 的安装命令历史。

[环境修复总结](../env_recipe_repair_20260919/README.md)明确：166 题是修复范围，并不代表 166 题原先均打错分；其中 144 题原 gold 已为 1。164 题完成修订环境组合对照，2 题隔离，尚未统一冻结并接入 actor/grader。DVC4778、Pydantic8500 新依赖 canary 证明了“声明新增依赖＋预置该 wheel”可安装，不证明任意新包均可用。

216 题主要是 noop/gold；尚没有这批数据支持真实 CC 经常发生“安装成功后因 fresh 遗失状态而失败”，也没有相应损耗比例。当前正式 rollout 的出口主要是模型代理与环境声明的内部服务，尚不能假定已经允许 PyPI/npm。

## 4. fresh 的收益与可以独立简化的成本

旧 D2-1 的实际合同是：冻结增量持久化后立即释放 rollout 容器，评分只接收该工件，排队/后续诊断不要求原容器存活。它隔离了仓库外的偶然状态和直接环境修改；**不保证完全防止 reward hacking**，当前候选仓库代码仍可能影响测试框架与 stdout。

三次扫描分别观察执行前、执行后及 fresh grader 基线。它们有具体消费者，但“三次每次全树扫描”并非所有 SWE/RL 系统的数学要求。可单独评估可信不可变镜像对应的基线复用、批量文件 hash、去重复权限初始化；不能用同镜像名字草率代替同一物化状态，也不能一边保留完整重放承诺一边直接删证据来源。

从原 216 题主批 432 条账本重汇总，431 次实际评分：

| 阶段 | n | 中位秒 | p90 秒 |
| --- | ---: | ---: | ---: |
| grader 启动与核对 | 431 | 1.032 | 1.272 |
| grader 基线重建 | 431 | 4.567 | 7.429 |
| delta 应用 | 431 | 0.001 | 0.117 |
| trusted setup | 431 | 5.144 | 9.589 |

这是旧实验真实开销，不是原容器方案的提速结果；delta 应用含 noop，不能推断所有非空补丁都近乎零成本。trusted setup 也含原容器仍要执行的测试恢复/注入。各阶段中位数不能相加冒充总时延。脚本与出处摘要见 [汇总脚本](grading_cost_from_existing_ledgers.py) 和 [结果](grading_cost_from_existing_ledgers.json)。

修后 pandas 的约 709 秒重编译、14 秒测试说明安装/构建值得重视；但原容器只有在相应修改已正确构建时才能复用成果，不能直接减去全部构建时间。原容器运行过旧二进制不证明最终源码生效。

## 5. 原容器方案可省什么、必须保留什么

可省：第二个容器启动、clean checkout、grader 的基线重建和 delta 重放，以及有条件的重复安装/构建。若主动放弃完整文件重放合同，前两次扫描和冻结工件也有更大简化空间；仅改容器参数不会自动省掉它们。

仍需：模型调用/工具进程停止、私有测试后注入、选定测试恢复规则、来源测试命令与 parser、资源与基础设施失败归因、日志与 reward 关联、最终清理。资源终止仍是 infra/None，不自动变模型 0。

当前代码不是原地评分的现成开关：

- `generate.py` 导出后立即 `_release_rollout_container`，后续 workspace=None，manager 收 `FrozenDeltaSource`；原地须重新安排明确的容器交接和排队持有。
- rollout/grader 默认 UID 分别为 54321/54322、HOME 不同。即使同容器，照搬 grader 身份也未必看到 pip --user 的包；执行解释器/虚拟环境亦须一致。
- trusted setup 当前以 root 激活环境并执行 Git 操作，依赖 fresh 环境的前提。不能将整份脚本照搬到 agent 已修改过的环境中执行。
- 当前 P-B 的正式 `test_globs=()`；不能为原地评分恢复旧“所有 tests 路径通配排除”。只保持实际已选的官方文件/控制面规则，额外规则仍按题目设计。
- 评分排队期间必须持有原容器；原方案文件工件可排队、原执行容器已释放。复用后的资源占用需与节省的初始化成本一并计算。

## 6. 建议下一步

1. 先确认当前 SWE 交付物是否仍是可重建仓库修改；不要因沉没成本维持方案，也不要把改变验收对象称为纯性能优化。
2. 若保持该目标，复用已修公共环境，明确支持哪些依赖声明与安装入口；建议讨论受控包供应，测试阶段的网络策略分开。若开放包获取，私有测试材料可见时点和候选安装代码权限需同时核对，不能简单把 `deny_all` 改一个字符串。
3. 若希望终态环境是正式成果，优先设计同容器的最小阶段切换，而不是为 fresh 搬运整个活环境；SWE parser/报告、数据修复和训练接线仍可复用。
4. 不需要八卡来决定交付物语义。实际能力辨识可并入既定基座诊断，用“已声明且缓存覆盖”“已声明但缓存缺失”“仅安装不声明”“源码改动需重编译”几例；不先建设两条完整生产评分链，不重跑全池。

以上均为建议。旧 D2 的 fresh、独立角色和 deny_all 在用户新决定前继续有效；第六组其它窄优化可独立讨论。
