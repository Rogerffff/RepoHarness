# 第六组方向复核：效率切片与依赖供应

2026-09-22 / Codex（A 线）。对象：[Claude 方向检查](claude_a_direction_review_20260922.md)、[本批决定与设计建议](README.md)。

**状态：设计复核与建议；网络的两项取舍待用户选择。** 已批准的四项效率方向与继续 fresh 评分不重开。本轮没有修改生产代码、维护测试、配置或 fork，没有运行 Docker、GPU、远端作业，也没有提交、推送或向其他任务发送消息。

## 1. 结论与实施节奏

- 同意 E3 可先做，E2 优先评估批量 coreutils，E1+ 可以先测量、评估。E1–E5 不依赖网络两项选择，Claude 不必等它们才写效率 Brief。
- 不同意“600 秒预算足以证明 E1/E2/E4 不影响吞吐”“OverlayFS 改属主总会全量复制”“下载出口基本不存在信息外发”“服务健康即可排除取包故障”等推论。
- **需要用户选择两项**：包源的历史限制范围（§3）；私有测试可见时是否允许受控取包（§4）。E1+ 的测量评估已在效率方向内，不需要再审批一次；权限或身份边界的实际变化再看具体方案。
- 网络 Brief 还须修正 §5 的真实接缝。这些是实现者应处理的问题，不是让用户逐个选择技术细节。

## 2. 效率方案：同意哪些，修正哪些

### 2.1 E3 排第一可以，估算不能当实测

历史探针的 `172 ms × 6.4 轮/秒 ≈ 1.1 秒/秒` 在给定负载下说明单事件循环可能饱和，足以支持先排查 E3。但要核对单个 adapter 进程实际承担的并发、轮长与转换路径，不能将全 run 并发直接当成一个事件循环的负载，也没有实测证据证明 GPU 已因此空等。

Brief 先量实际关键路径的解码、转换和事件循环阻塞；紧凑表示前后逐轮内容及现有消费者一致即可。保留全部轮次与分支，不借机决定 I18 的路由来源。E5 配置/测量准备可并行，E1/E2/E4 按文件归属推进；CR1 诊断余项继续随 E4、在既定八卡作业前收口。

### 2.2 600 秒是预算上限，不是收益分母

旧评分账本可支持“某些固定阶段通常为秒级”，不能支持“只影响稳定性，不影响吞吐”。真实执行平均多久、CPU/存储是否拥塞、grader 是否成为供样瓶颈，都尚未由这份账本回答。

[既有汇总](grading_cost_from_existing_ledgers.json)的测试段只有 424 条计时，其他主要阶段是 431 条；超时等未完成阶段没有同样完整的测试计时。“测试占 75%”是已记录时长的比例，不能当完整作业的成本分解。继续优化有依据，不预报加速倍数。

### 2.3 E1+ 值得评估，但不能把本机 copy-up 推广成所有目标机事实

Linux OverlayFS 支持 metadata-only copy-up：开启适用的 `metacopy` 后，`chown/chmod` 可以先复制元数据，数据到写入时才复制。[内核文档](https://docs.kernel.org/filesystems/overlayfs.html#metadata-only-copy-up)

本仓库也有目标机证据：[评分接线记录](../swe_grading_wiring_20260915.md)记录 dvc 的 chown 从约 180 秒降到 11 秒、pandas 降到约 5.5 秒；后续又发现特定 metacopy/native-diff 与 `docker commit` 组合产生零内容文件，撤回了无条件机器前置。**本机 0.25/1.2 GB 是该探针条件下的事实；不直接推广，也不因此建议所有机器打开 metacopy。**

E1+ 的具体建议：

1. 在既定目标机诊断中记录存储驱动/挂载模式、首次和重复 chown 的耗时及可写层增量，顺带测 CC 安装。无需专门租机或新增八卡实验。
2. 若成本显著，比较按角色预置属主的镜像层与现状。rollout/grader 可以各有适合其 UID 的派生层，**并非必须合并 UID**。
3. 预置基线属主不等于 delta 重放后所有新文件权限也正确；候选新增/替换文件与官方测试恢复后的权限仍须处理。只读核对不能取代这一步。
4. 不把“优化初始化”扩大为“扩大 agent 可写目录”。需要改变可写前缀、UID 或题包镜像身份时，Brief 明列与 B 的接口。

### 2.4 E2 的 coreutils 方向同意，命令仍须证明等价

相较候选可写的 Python 环境，使用镜像内可信的固定 coreutils 路径较合理；仍须核对实际镜像和环境变量，不把任意 PATH 查找自动当成可信执行。批量摘要应保留路径、文件类型、执行位、软链目标、排序与既有排除规则；注意 `sha256sum` 对反斜杠/换行名字的输出格式及批次错误。无需扩展目前不支持的文件名范围，也不新增扫描内容或准入条件。

## 3. 用户选择一：限制未来答案，是否等于所有依赖都按题目日期截断

### 3.1 Claude 指出的风险成立，提出的必要性结论不成立

能下载被测项目的后续发行包，确实可能拿到修复。公开的[未来 Git 历史利用案例](https://github.com/SWE-bench/SWE-bench/issues/465)支持对此保持警惕；它没有证明 PyPI 就是该案例的通道，也没有证明全体第三方依赖必须采用每题历史视图。

**本项目已有实际的取舍例子：** MONAI-763 的原始 `created_at` 是 `2020-07-15T16:38:37Z`；B 已验证的修复配方使用 `nibabel==4.0.2`，该版本在 **2022-08-31** 发布。[PyPI 发布记录](https://pypi.org/project/nibabel/4.0.2/)

本地证据：原始数据 `runs/env_probe_20260909_codex_backup/data/swe_gym_lite_full_f70b1a29.jsonl`；资格记录 [repair_catalog.json](../env_recipe_repair_20260919/repair_catalog.json)；已运行配方 `runs/env_recipe_repair_20260919/numeric_v1f/tasks/Project-MONAI__MONAI-763/gold/recipe/recipe.json`。后者从预置 wheel 目录离线安装较新的兼容依赖。

所以，只过滤远端索引**不会立即使这份离线配方失败**；但继续允许这些预置 wheel 时，就不能声称整题环境严格冻结在 2020 年。若连这些依赖也禁掉，需要重新修环境。我们的目标是可靠的 coding 训练，目前没有“完整复原任务当年的依赖世界”这项用户决定。

此外，任务创建时间不普遍证明修复版本一定更晚；回补等情况要看数据。历史截止减少暴露，不证明完全没有答案；版本撤回、来源元数据变化和预装包也不因一个截止日期自动消失。

### 3.2 两个可选政策

| 选项 | 规则 | 实际取舍 |
| --- | --- | --- |
| **1A，建议首版采用** | 默认不提供被测项目自身的远端发行包；本地候选的 `pip install -e .` 保留。已验证配方确需某个固定发行包时单列允许。第三方依赖以 B 验证的兼容环境为基础，不普遍按每题创建日期截断 | 直接限制一个明显的答案入口，保留合理的新依赖/工具。需要 repo 与发行包名的对应；不是完整防泄漏证明，已知其他答案来源再具体处理 |
| **1B，Claude 倾向** | 对所有新增下载采用该题的历史截止视图，现有已验证镜像/wheel 作为明确例外；若要求没有例外，则连环境配方也重审 | 历史包范围更窄，但可能挡住合法工具/新依赖；需处理缺失日期、时区、元数据和例外，流水线工作量更高 |

不论选哪项，**下载缓存不是版本冻结**。网络 Brief 需写清正式作业固定哪些配方/供应版本、哪些新依赖仍允许动态解析，并记录实际取得和安装的版本。不能用“有缓存”或“按日期过滤”替代实际可复现性说明。

### 3.3 现成组件是候选，不是已经成立的访问边界

- [pip 官方选项](https://pip.pypa.io/en/stable/cli/pip_install/#cmdoption-uploaded-prior-to)确实提供 `--uploaded-prior-to`；客户端可修改选项，不能单独执行本项目的约束。
- [pypi-timemachine](https://github.com/astrofrog/pypi-timemachine/blob/d744aab8e009a17a7cdecfaafcc89ca907fea38c/README.rst)自述 alpha，日期是请求 URL 的一部分。已查[固定版本代码](https://github.com/astrofrog/pypi-timemachine/blob/d744aab8e009a17a7cdecfaafcc89ca907fea38c/pypi_timemachine/core.py)：缺少 upload time 的文件允许通过。直接暴露它，不能证明候选无法换日期。
- [devpi-constrained](https://github.com/devpi/devpi-constrained)按版本约束，不能与时间过滤混称；[devpi-timemachine](https://github.com/jonafato/devpi-timemachine/blob/02a940700ab0f2c43eb96fa7589f34e25139a544/devpi_timemachine.py)确有实现，但该版本按同一 release 的最早文件时间判断，并非逐文件截止。

若选时间政策，需在服务端绑定题目/截止，检查索引页、实际文件下载及未过滤父索引能否绕过。若选 1A，同样不能让候选换一个入口就取消当前题的包名限制。先选策略再做一个小组件探针，不先承诺“一两百行就足够”。

## 4. 用户选择二：首版评分阶段保持现顺序，还是先装依赖后注入私有测试

我可以接受 Claude 的首版顺序建议，但需要修正理由，并让用户知道实际放宽的边界。

**root 风险的提醒正确。** 候选安装之后，不能让 root 再激活候选可写 conda、执行其 Git 配置或钩子。我上一版 README 已要求后续 root 只做可信文件操作；所以“简单交换当前两个脚本”不可用，不代表安全的后注入方案不存在。该方案需要重新拆分和物化官方文件，首版改动范围确实更大。

**“只能下载，没有信息外发路径”不正确。** 即使禁用 POST/上传接口，GET 路径和查询参数也能携带数据；实际是否传到上游取决于服务如何验证、规范化及转发请求。此处是未来网络设计的条件风险，**没有做出测试内容已泄漏、或后续 rollout 能读到上游日志的证据**。不为缓存时序等理论通道建设大系统，但文档不能承诺它没有任何出站信息。

| 选项 | 首版行为 | 取舍 |
| --- | --- | --- |
| **2A，建议首版采用** | 保持 root setup/官方测试注入在先；随后候选安装可用受控 PyPI 供应；正式测试前撤掉该出口 | 保留现有可信初始化顺序，避免本次重做私有文件注入；明确接受私有测试已可读时仍可向包供应服务发请求，不能声称“私有材料可见后无出站请求” |
| **2B** | 坚持私有材料可见后无取包出口；先联网安装、撤出口、再仅通过可信文件操作注入测试 | 边界更清晰，但需处理安装依赖 test patch、root 注入方式及脚本状态；必要时 grader 联网后置，已批准效率切片照做 |

2A 的建议基于当前工程范围和包供应用途，不以“官方测试不可改就一定没有 reward hacking”为理由；已知评分 stdout/控制面问题仍按 B 线既定工作处理。本次也没有批准一般公网、GitHub、conda 或上传能力。

## 5. 不需要用户决策，但网络 Brief 必须具体解决的接缝

### 5.1 同一 relay 不等于 grader 只能到包源

[`RolloutSandboxProfile.relay_listen_map`](../../../../../rh2/src/repoharness2/adapters/slime/sandbox_profile.py)总是包含模型代理和全部内部服务；relay 监听所有地址，挂到它的网络会使这些监听端口可达。可达不代表通过服务鉴权，但不能据此声称 grader “只通包索引”。复用实现可以，grader 的实际接法必须只开放其批准的目标，不直接照搬整份 rollout relay 端口集合。正式测试期的断开、异常/取消清理也要覆盖。

同一脚本的 relay 会为上游建立新 TCP 连接，不传原始来源身份。包索引按来源 IP 看见的是 relay，不是每个 attempt；仅靠这条链当前无法按“来源网络”分题记账。Brief 要给出宿主绑定的 attempt/题目视图与日志关联方式，不信任候选自行填写的身份。

### 5.2 不能把一次 Bash 机械拆成两次 exec

[`prepared_task_face.py`](../../../../../rh2/src/repoharness2/adapters/slime/prepared_task_face.py)模块说明明确保证安装与测试同一 shell，安装段 `export` 传到测试。真实 MONAI numeric_v1f 配方开头就设置 `OMP_NUM_THREADS`、`MKL_NUM_THREADS`、`OPENBLAS_NUM_THREADS`，不是凭空设想的需求。

主审使用当前 `_v2_install_lines` / `_v2_candidate_test_lines`，仅替换 vendor 命令为 `export RH2_REVIEW_INSTALL_STATE=present` 与读取它的测试，运行真实 Bash：

| 运行方式 | 安装 rc | 测试 rc |
| --- | --- | --- |
| 当前同一 shell | 0 | 0 |
| 直接分成两个 shell | 0 | 1 |

[探针](probe_install_shell_state.py)、[结果与源码摘要](probe_install_shell_state.json)。它证明直接拆分会改变已支持的状态传递，不证明完整评分或 Docker 网络行为。Brief 应选择保留所需 shell 状态的阶段交接，或用实际配方证明拆分等价；不要求实现通用 shell 序列化。

同时保留：现有总期限、阶段超时与取消语义；日志拼接和 tee 追加；候选安装/测试 rc、收口与 partial 事实；P-A 所用资格记录与脚本摘要的一致性。不能因两次 exec 各自获得完整 timeout 而悄悄扩预算，也不能把只含测试的日志当成完整评分日志。

### 5.3 访问日志不能证明安装，事后健康检查不能证明原因

- GET/下载日志证明请求过或取得某个包，不证明装入了哪个解释器、安装成功或测试用了它。优先与已有安装日志/报告、导入观测结合；不先建完整环境录制重放。
- “安装失败后索引不可达 → infra；可达 → 按现状处理”证据不足：服务可能在失败后恢复，也可能安装因候选编译错误失败后服务才抖动。健康检查可作诊断，不能独立改变 reward 归因。沿用确证的取包错误、阶段事实与现有资格基线；无法判定的继续按未确定处理。
- PyPI 首版范围可以继续设计；不顺带开放其他生态。先做代表安装、真实出口、阶段切换、失败/取消的窄验证，再按影响面决定哪些题需重验，不先要求全 216 题重跑。

## 6. 审查范围与交付

按审查标准对网络边界、阶段状态作生产链追踪与反例两路复核；主审独立核对关键源码、真实配方、已存目标机证据，并运行上述 CPU/Bash 反例。外部组件核对官方文档与固定版本源码；没有把其他人的既有测试数作为本轮验证。

本轮结束于设计层：已能明确两个用户取舍及必须补齐的工程接缝。没有启用网络，没有重审全部 manager 修复，没有重跑题池或训练。下一步可先做 E3 等已批窄 Brief；网络选择后再产出可审查的短 Brief，不再把所有效率实施都挡在网络讨论之后。
