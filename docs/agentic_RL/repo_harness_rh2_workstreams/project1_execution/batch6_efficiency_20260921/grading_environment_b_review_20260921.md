# B 线补充：现在是否改成原容器评分

2026-09-21 / Codex B。讨论建议；未修改生产实现、D2 决定或评分语义，未运行新实验。核对入口为 [A 线讨论稿](grading_environment_options.md)、当前源码、既有环境修复记录及下列在线原始资料。

**我的建议：当前保留独立评分作为 RH2 的主路径，同时支持 agent 受控安装依赖、补齐评分侧对应的包供应。暂不为此改成原容器评分；后续可以根据真实候选的对照结果采用同容器优化。** 两条路线都能用于 SWE 训练，关键是评分是否反映我们要训练的修复能力，以及付出了多少成本。

**本轮讨论后的优先级调整：先检查选中题的基本解题条件，随后推进真实模型求解；三路对照改为真实问题触发后的定点调查，不作为基座探针前置。** A 线的第六组效率优化、受控网络与包缓存可并行准备，具体访问边界仍需在实施中明确。人工安装小样例可以验证新能力的实现，但不能说明当前任务是否需要、模型是否会使用或真实收益有多大。

## 2. 对 A 线建议的赞同与补充

赞同保留 fresh 主路径、重新讨论网络，以及先量成本再改架构。需要补充的是：**“成果是仓库补丁”并不逻辑上要求每次换容器；“同容器评分”也不自动等于目标变成终态环境。** 同容器可以是补丁任务的执行优化，但单次通过不能独立证明补丁离开原环境仍成立。目标是同一个，实际奖励的依据可能不同。

对我们当前 Python 仓库修复任务，更准确的交付定义是：**指定的公共环境版本＋仓库修改（含必要的依赖/构建声明）＋该仓库约定的安装入口，能够重现修复。** 不要求从空白操作系统重建一切，也不要求把 agent 的命令历史、site-packages 或整个容器复制出来。

保留独立评分的理由有三项：

1. 它能发现“只在当前会话成立”的成功：例如装了目标项目的新发布版而未实际使用候选源码，或只在虚拟环境改了代码。对以可交付修复为目标的训练，这个区别有价值。
2. 当前冻结工件后即可释放解题容器，评分可以排队、重放和独立诊断；同容器路线需要接管并持有原环境。两者的内存占用、失败恢复和调度成本都应计入。
3. 现有 216 题主要是 noop/gold 环境对照，尚未测出真实模型有多少合法修复因 fresh 丢失安装状态而失分。没有依据先认定这已是主要损耗。

这不意味着保留所有现有扫描、哈希和初始化。它们可独立简化。A 线从旧账本汇总的 grader 启动/核对中位约 1.03 秒、基线重建约 4.57 秒，不能直接当作新方案收益；修后 Pandas48106 每次约 709 秒构建、14 秒测试，则提示特定题的重复构建可能更值得优化。[原统计](grading_cost_from_existing_ledgers.json)、[维修记录](../env_recipe_repair_20260919/README.md)

## 3. 支持安装，但区分安装的作用

| agent 的操作 | 应如何对待 |
| --- | --- |
| 安装本来就应具备的测试/运行依赖 | 公共环境应尽量预置；模型发现缺失可以补装，但长期应修公共配方，不能每条轨迹重复承担旧环境维修。无需为了补装已声明的依赖而改项目声明。 |
| 安装调试工具 | 可作为合法开发手段；若最终修复不依赖它，不必在评分环境复制。 |
| 修复确实引入新依赖 | 允许，按该仓库约定留下声明；grader 应读取候选声明并能取得对应包。只因缓存缺包而失败，是供应能力问题，不能自动判模型错。 |
| 仅修改虚拟环境、替换已安装的目标包，未留下可交付改动 | 对当前补丁目标，不能仅凭原容器通过就认定修复成立；要核实际导入和候选源码。若以后专门训练环境修复任务，再采用相应终态验收。 |

建议采用一条清楚的供应路径：**准备阶段预装常用依赖/资产 → agent 可经受控包源安装 → fresh grader 根据候选声明安装/构建 → 按题目要求运行测试。** 包缓存未命中时允许经批准的来源获取，并记录实际版本；缓存不是阻止合理新依赖的包名白名单。共享下载产物可以，不能让不同候选共用可写虚拟环境。

网络与写权限必须配套：有包源但目标解释器不可写、`pip` 装进另一环境，能力仍不可用。agent 和 grader 应消费相容的公共基线、包供应和安装规则，不要求复用 agent 的最终虚拟环境。现有 DVC4778/Pydantic8500 canary 只证明“声明＋已准备的 wheel”路径，不代表通用取包已接通。

安装取包与测试运行的网络分别配置。普通测试优先固定依赖后离线；确需服务的题提供明确服务/资产，不靠任意公网碰运气。包源访问也不等于没有答案泄漏：目标项目的较新发布包可能包含修复，必须确认测的是候选工作区代码。当前 RH2 在候选安装前已注入官方测试；若安装段开放网络，须一起设计私有材料可见时点和取包边界，不能只改网络参数。

## 4. 当前先做什么，何时再比较评分路线

先沿[已有首批入口建议](../swegym_task_audit_20260920/quality_batch01_20260921/acceptance/morning_cpu_shortlist.md)，准备 Conan15422、DVC5839、Moto5134 等少量跨仓候选。在实际解题用户和 Claude Code 工具使用的 shell/解释器下，确认候选源码导入、必要写入、相关公开复现/测试及资产或本地服务可用。原 bug 导致的断言失败可以是预期结果，不要求隐藏验收或全仓测试先通过；已有 grader 维修记录用于确定基线，不能直接替代 actor 运行。

随后进行只接收公开材料的真实模型求解，观察实际安装命令及结果、依赖声明改动、代码是否生效、工具与评分失败位置、安装/构建/测试时长。优先复用轨迹、工件和现有日志，不新建完整环境状态录制平台。少量环境已就绪且不需新增网络能力的题可以先跑，不等第六组所有优化或完整网络方案完成；不同运行条件分别记录。

A 线可并行优化已确认的开销，准备受控包源、缓存及实际安装权限。先定义允许访问的来源和供应方式，不必静态猜出所有未来包名；新增来源、特殊版本/服务和缓存缺失再结合真实访问记录及逐题调查处理。不会给模型使用的特殊依赖，不需要为了比较容器路线刻意引入题目。

只有出现具体迹象时再安排对照，例如模型在开发中安装了依赖而 fresh 无法恢复、合法声明未被读取，或重复构建已成为明显成本。届时保存同一候选，必要时比较：**A 原解题容器；B 当前 fresh；C 安装入口/包供应补齐后的 fresh。** 不要求每个问题都跑三路；原日志已经能定位供应缺口时，直接修正并定点验证即可。

对照时原评分测试、恢复/投影规则和参考保持一致，候选在注入隐藏测试前冻结；实际身份、解释器、包版本和资源差异记录清楚。当前正常路径会释放原容器，首次异常可能只能先靠日志和工件定位，再针对该题新运行显式保留容器复现，不因此保留全部解题容器。原地探针需单独处理进程停止和测试注入，不能直接复用依赖 clean 环境前提的 root 初始化脚本。

| 观察 | 可以推导的下一步 |
| --- | --- |
| A 通过、B 失败、C 通过 | 优先修供应/安装路径，不必为该问题改成同容器。 |
| A 通过、C 仍失败 | 追查未声明依赖、必要状态、旧构建产物或评分差异；不能直接归罪模型或 fresh 架构。 |
| A 失败、C 通过 | 原工作区也可能被调试过程或陈旧环境损坏；fresh 可能提供更清楚的验收。 |
| 分数一致，A 显著减少总成本 | 才有依据设计同容器快路径，保留抽样 fresh 重放和独立评测作为校准。抽样比例及残余偏差到时决定。 |

同时量每小时有效评分数（包括有效 0 分）、安装/构建/测试时长、等待时持有的内存和清理失败。原容器能否省构建，取决于最终源码是否已经正确构建；不能把全部构建时间直接算作节省。

因此当前优先项是受控安装与两侧环境一致性；同容器是可考虑的后续优化，不是被否定的设计。若以后任务本身要求修复服务、系统配置或运行态环境，则应按那类任务直接评估终态，不强行把它们装进 SWE 补丁契约。
