# 外部沙箱是否值得接入：Prime、替代服务与 RH2 迁移边界

日期：2026-09-25。作者：Codex，A 线。**状态：资料与源码调查、设计建议；不是已批准迁移，也不是服务实测。**

本轮核对官方发布、当前文档、Prime SDK 固定提交及 RH2 接缝。未购买服务、创建沙箱、登录验证机、修改生产代码或运行配置。RH2 阅读期间 HEAD 已到 `b50bdad126bb16bd18b05191e65830b120568a0d`，共享工作区另有 B 线在制品；本研究不代替这些改动的实施复核。

## 1. 建议结论

**值得现在做一次有边界的接入验证，不建议凭发布博客立即整体迁移。** Prime 是第一候选，Modal 是具体的备选；保留当前 Docker 实现作为对照和回退。不要同时实现四个服务后端，也不要为了引入沙箱而把 miles/SGLang 换成 prime-rl。

长期值得把环境执行与 GPU 主机资源解耦，但“移到独立 CPU 机器”和“购买托管沙箱”是两种选择。后者能减少运行时维护，前者通常保留更多控制权；哪一种更划算取决于真实并发、镜像异构性、环境等待时间和 GPU 空等。

目前最值得先查的不是启动有多快，而是服务能否少量适配后满足我们已经修好的四件事：**候选与可信操作分权、进程终态可信、安装后真实撤出口、同一来源环境上的评分一致。** Prime 当前 SDK 在前两项和网络切换上有明确接缝，见 §4。

## 2. 不要把三种选择混成一个

| 维度 | 可以选择什么 | 对本项目的意义 |
| --- | --- | --- |
| 环境在哪里跑 | GPU 主机 / 独立 CPU 主机或集群 | 避免拉镜像、编译、测试、磁盘与内存争抢影响训练和推理 |
| 隔离实现 | Docker / gVisor / microVM | 兼容性与宿主隔离边界不同；不决定评分是否正确 |
| 谁维护运行时 | 自管 / 托管服务 | 谁负责节点、镜像缓存、容量、故障与运行时升级 |

“继续 Docker”和“始终在 GPU 主机上跑环境”并不等价；托管服务通常也能继续接收我们的 Docker 镜像。

技术报告中的专业沙箱说明环境基础设施值得投入，**不等于这些团队购买了商用沙箱，也不证明我们应该自己复刻相同规模的平台**。例如 Kimi 相关的 [AgentENV 官方仓库](https://github.com/kvcache-ai/AgentENV)是可自部署的分布式环境平台，采用 Firecracker 等设施。采用它仍要维护机器、镜像和调度服务。现有 [Kimi K3 精读](../../../../harness_improve/external_paper_references/reading_notes/R13_kimi_k3.md)可作为进一步追溯入口；本轮没有重读全部 DeepSeek/Kimi/MiMo 报告，不据此断言它们用了某个商业供应商。

## 3. 外部沙箱能省掉什么，省不掉什么

| 工作 | 托管后可能由服务接管 | RH2 仍须负责 |
| --- | --- | --- |
| 环境生命周期 | 节点选择、运行时启动、资源分配、镜像缓存、平台清理 | attempt 与沙箱归属、期限、取消后的确认、孤儿资源对账 |
| 隔离与网络 | VM 边界、资源限制、允许列表、远程接入 | 候选用户权限、实际可达范围、安装→测试阶段政策 |
| 命令与文件 | exec、输出流、文件传输 API | 真实退出与连接断开分开；日志完整性、工件身份与持久化 |
| 环境制作 | 镜像构建、分发、可复用模板 | 激活正确解释器、依赖配方、资源档位、noop/gold 资格 |
| 评分与训练 | 提供运行测试所需算力 | 私有测试、候选归因、reward、丢组、动作覆盖、版本和 loss |

我们近期修复的解释器激活、root PATH、候选 stdout 伪造、解析与奖励归因，不会因为换成 microVM 自动消失。VM 把候选代码与宿主分开；同一 VM 内的候选与 grader 仍需要我们设计边界。

**三次扫描不是 Docker API 导致的。** 它们来自当前“冻结候选修改，再在新评分环境重放”的验证合同。换服务仍可能执行相同扫描。快照只能改变成本和交付方式，不能自动证明可删掉某道检查。

同理，求解后快照会同时保存候选新装的包和候选对环境的改动。把它用于评分，不等价于“干净基底 + 允许交付的修改”；若以后改变这项语义，需单独比较评分结果，不能藏在沙箱迁移里。

## 4. Prime：很匹配方向，但当前并非即插即用

### 4.1 已公开能力与尚未交付能力

[9 月 23 日发布文](https://www.primeintellect.ai/blog/sandboxes)宣布 GA：独立 CLI/SDK、完整 Linux microVM、可接收 Docker 环境、面向大量异构任务的镜像调度。它不要求用户采用 prime-rl。文中规模和速度是供应商陈述，本轮未独立复现。GPU 沙箱、运行中快照/分叉、持久工作区仍列在路线图，不能计入当前收益。

[运行文档](https://docs.primeintellect.ai/sandboxes/overview)同时说明：某镜像首次转换为 VM 镜像可能需要数分钟。因此应分别测首次转换、缓存命中和异构镜像并发，不能只测一个热镜像反复启动。

[镜像文档](https://docs.primeintellect.ai/sandboxes/images)支持导入既有环境。我们应保存“原 OCI digest → 服务镜像 ID/版本”的来源关系，验证激活、属主和资格结果；不能仅以 tag 一样认定环境完全相同。CC 等大文件宜随镜像预置；[SDK 文档](https://docs.primeintellect.ai/sandboxes/sdk)的单文件上传有 16 MiB 限制。

### 4.2 固定 SDK 源码发现的三个接缝

源码固定在 `PrimeIntellect-ai/prime@ef4d17614ebfeeb6596910240609ac694d8df3f4`。调查时源码与 PyPI 都标示 0.3.1，但未逐文件比较发行 wheel，也未验证部署中的服务端。

| 源码事实 | 对 RH2 的实际影响 |
| --- | --- |
| `set_network` 文档明确：规则应用后约束新连接，已有连接不撤销 | 不能直接用一次 deny-all 替代已批 2A 的“安装后撤掉实际出口”。需验证额外断连方法，或选择提供此能力的后端 |
| `open_process` 拒绝非空 `user` 参数 | 不能直接把当前 `docker exec -u agent` 改成 SDK 参数；要核实可信降权包装能否保持候选非 root、信号与子进程回收 |
| live process 可重新观察保留的退出事件，但断开期间的输出不重放；background job 则用 VM 内日志与退出标记文件 | 不能把重新连接等同于完整日志，也不能默认后台作业文件对候选不可伪造；优先核实服务进程终态与可信收集路径 |

对应源码：[网络更新](https://github.com/PrimeIntellect-ai/prime/blob/ef4d17614ebfeeb6596910240609ac694d8df3f4/packages/prime-sandboxes/src/prime_sandboxes/sandbox.py#L3791)、[实时进程](https://github.com/PrimeIntellect-ai/prime/blob/ef4d17614ebfeeb6596910240609ac694d8df3f4/packages/prime-sandboxes/src/prime_sandboxes/sandbox.py#L3873)、[后台作业](https://github.com/PrimeIntellect-ai/prime/blob/ef4d17614ebfeeb6596910240609ac694d8df3f4/packages/prime-sandboxes/src/prime_sandboxes/sandbox.py#L4159)。这些是静态兼容性发现，不是已证实的服务漏洞。尤其不能从 `user` 参数缺失推导“无法非 root 执行”。

已批 1A 的“禁止候选获取被测项目的远端发行包、保留确认的配方例外”仍要在我们的供应网关实施。允许访问 PyPI 域名不等价于按题目控制具体发行包。Prime 的网络 API 可以替换部分运输设施，不会替代政策本身。

[Prime Tunnel](https://docs.primeintellect.ai/sandboxes/tunnel)可把本地模型代理暴露给远端沙箱，减少接入工作；默认公开访问的隧道需要配置认证。应只开放 RH2 的模型请求入口并绑定 attempt，不开放原始 SGLang 管理面。候选环境不持有沙箱账户管理凭据。

## 5. 其它路线怎么排

| 路线 | 值得考虑的原因 | 需要核实的代价 / 限制 | 当前建议 |
| --- | --- | --- | --- |
| Prime | 面向 RL 的异构镜像与规模、当前资源价格低、保留 Docker 包装 | §4 接缝；地域/RTT/稳定性未测；关键快照能力仍在路线图 | 第一候选，先检查语义可适配性 |
| Modal | 资源与沙箱接口完整；动态网络文档明确可切断新政策禁止的已有连接 | VM runtime 为 Beta，动态政策为 Alpha；组合使用和实际计费需验证 | Prime 撤网或进程接口不适配时的具体备选 |
| E2B | 自定义镜像、进程工具、暂停与快照、生态已有接线经验 | 订阅/并发额度；暂停/快照影响连接；我们现有 E2B 包装不是正式链一键切换 | 有具体优势时再试，不并行写第三套 |
| Daytona | 提供动态网络策略、镜像与生命周期 API | 严格自定义出口受账户等级限制；资源与创建速率也受配额约束 | 保留候选，本阶段无需接线 |
| 独立 CPU 主机 + Docker | 复用最多、从 GPU 主机移走资源争抢、控制细节可见 | 仍要维护运行时和镜像；当前收集器也不能直接改成远程 Docker 地址 | 保留为成本/复杂度对照 |
| 自部署 AgentENV | 有面向 agent 环境的平台实现可借鉴 | 仍要运营平台，与本次“少维护”目标不完全一致 | 当前不建议另开平台建设 |

来源与边界：

- [Modal VM runtime](https://modal.com/docs/guide/vm-sandboxes)已存在，不能沿用“Modal 只有 gVisor”的概括；VM 的某些快照能力仍有限制。[动态网络文档](https://modal.com/docs/guide/sandbox-networking)写明已有连接终止，但要求创建时配置对应允许列表类型。本轮未测该 API 与 VM runtime 的组合。
- E2B 支持[自定义基础镜像](https://docs.e2b.dev/template/base-image)和[运行时网络更新](https://docs.e2b.dev/api-reference/sandboxes/update-sandbox-network)，本轮未找到已有连接撤销的明确承诺。[快照文档](https://docs.e2b.dev/sandbox/snapshots)说明活跃流连接会断开；不能不改 harness 生命周期就把等待推理的 CC 随意暂停。
- [Daytona 网络文档](https://www.daytona.io/docs/en/network-limits/)与[配额](https://www.daytona.io/docs/limits)需一起读，不能拿低档账户的价格和高档账户的网络控制拼成一套已可用方案。

## 6. 成本：有吸引力，但不能只比较沙箱单价

以下按公开资源价格计算，**不是报价或实测账单**。CPU 的性能、超卖/保留语义、存储和套餐不等价。

以单个环境 **2 vCPU、4 GiB RAM、20 GiB 磁盘**为示例（不是批准训练配置）：

| 服务 | 资源价格推算 / 小时 | 范围 |
| --- | ---: | --- |
| Prime | $0.094 | `2×0.02 + 4×0.0125 + 20×0.0002`；发布期价格截至 2026-12-22 |
| E2B | $0.1656 | CPU + RAM；套餐另计，Pro $150/月，所需并发决定套餐 |
| Daytona | 约 $0.1672 | CPU + RAM + 超出免费 5 GiB 的磁盘；网络等级另核 |
| Modal | 约 $0.2380 | 用 Sandbox 表的一物理核（其定义为两 vCPU）+ 4 GiB；不含其它费用，VM 档位实际计费需核实 |

价格来源：[Prime](https://docs.primeintellect.ai/sandboxes/overview)、[E2B](https://e2b.dev/pricing)、[Daytona](https://www.daytona.io/pricing)、[Modal](https://modal.com/pricing)；Modal 还应结合[资源计费口径](https://modal.com/docs/guide/sandbox-resources)。这张表不能证明 Prime 的单位完成任务成本最小。

Prime 示例：

- 64 个求解环境加 4 个评分环境持续运行：`68×0.094 = $6.392/小时`，全天约 $153.4。
- 一次求解 600 秒加 fresh 评分 180 秒、资源档位相同：约 `$0.0204/attempt`；一万次约 $203.7。
- 以上均不含 GPU、镜像制作/首次准备、重试、额外存储/传输等；实际启动和等待也占用时间。取值只是算例，不代表当前耗时或正式预算。

**等待模型返回的沙箱仍处于运行态，也要计费。** 不能把 Kimi 式等待期暂停的收益提前算给尚未交付快照能力的 Prime。

另一方面，若 GPU 租金已经包含足够空闲 CPU/RAM，当前 Docker 的增量现金成本可能很小；若环境导致 GPU 空等，则便宜 CPU 服务可能减少总成本。以纯假设 GPU $24/小时、外部环境 $6.392/小时、其余成本不变为例，纯算力成本持平要求外部方案把总时长缩到原来的约 79%。这是说明比较方法，不是对训练机报价或效率收益的预测。维护时间价值另计。

最终比较应采用：**每小时进入训练的有效完整组、每组总成本、GPU 等待占比、环境维护时间**。只提高创建速度而增加长尾超时，可能反而多丢完整组。

## 7. RH2 的迁移量在哪里

| 现有接缝 | 迁移需要做什么 | 不应趁机改变什么 |
| --- | --- | --- |
| `sandbox_profile.py` 的 Docker 参数、inspect、relay、资源与网络 | 映射服务资源、用户、出口、状态证据 | 不伪造 Docker inspect 以绕过现有检查；保留实际不变量 |
| `envpack/materialize.py` 的镜像与环境来源 | 导入镜像并保留 digest/ID 对应，重核少量资格样本 | 不能假设导入成功即资格通过 |
| `docker_sandbox.py` 与 `bringup.launch_claude_code` | 服务 exec/真实退出/日志/取消实现 | 连接断开不能写成模型正常退出；候选不能成为终态事实提供者 |
| `grading/manager.py` 的创建、分段 exec、撤网、清理 | 服务化评分生命周期；新 grader 仍从规定基底创建 | reward、候选归因、私有测试政策和 fresh 语义 |
| attempt/run 清理与 audit | 记录远端沙箱 ID、请求幂等性、终态与清理事实 | 不以 HTTP 请求成功代替资源已停止 |

本地锚点：[Docker 收集器](../../../../../rh2/src/repoharness2/adapters/slime/docker_sandbox.py)、[正式启动](../../../../../rh2/src/repoharness2/adapters/slime/bringup.py)、[评分生命周期](../../../../../rh2/src/repoharness2/grading/manager.py)、[沙箱配置](../../../../../rh2/src/repoharness2/adapters/slime/sandbox_profile.py)。

当前 `run_exec_collected` 直连本地 Unix socket；设置 `DOCKER_HOST=ssh://…` 不能直接把整条链移到 CPU 主机。现有 [vendored E2B 包装](../../../../../rh2/src/slime/agent/sandbox.py)也有网关专用镜像映射与旧分离日志机制，不能因类已存在就宣称迁移仅几行。

可以保留 miles、SGLang、capture、loss 和组语义：CC 的模型请求经远程入口回到现有 RH2 adapter，采样与路由证据仍在本地捕获。要新增的是沙箱运输与生命周期边界，不是把整个训练框架换掉。异地 RTT、长流、工件回传与取消确认的尾延迟则需实测。

## 8. 建议的有界试验

### 第一步：先验证四个接缝

以 Prime 为主，不先建通用多后端平台。目标是在约一至两个工作日的调查/窄探针投入内判断可适配性；这是投入上限建议，不是完成工期承诺。

1. 使用一个现有镜像，root 可信初始化、agent 非 root 跑正式 CC；候选不能改可信日志/退出记录。
2. 长输出、断开重连、内部非零退出、超时/取消各核一次；能区分进程结束、连接失败与未知，能确认整个 execution 停止。沿用当前“控制端在期限前收到停止确认”的口径。
3. 安装访问指定包网关后撤出口；测试新连接与**已建立连接继续传输数据**均不可达，宿主控制 API 仍能完成清理。只看规则字段或 TCP connect 不足以验收。
4. 同一固定镜像来源导入后，解释器、属主、候选工件与评分正反控保持一致。

如果这一步需要我们重新写一套复杂守护进程、可信日志协议和 VM 内网络平台，就记录真实改动量，转查 Modal 的对应 API，或保留 Docker；不要因已有接入投入持续扩张。

### 第二步：通过后才比较小批成本

选 5–8 个已获资格且特征不同的环境：轻量 Python、conda、需编译的 pandas 类、R2E `.venv`、MONAI 类内存任务。先用 noop/gold/已知候选和真实 CC + 桩模型入口，避免 GPU 与模型行为掩盖沙箱差异。

同一任务、工件、CC 条件、网络政策和资源档位下，对比本地 Docker 与候选服务。记录首次镜像转换与热启动，随后逐级小并发；只有稳定后再试 8/32 等并发，不直接放大到整池。

记录创建到可执行、命令延迟、产物上传下载、评分、取消确认的 p50/p95/p99；记录评分一致率、资源残留、供应商错误、每有效完整组成本。之后用真实模型入口测 RTT、harness 行为与训练供给，不要求第一步就租八卡。

**选择条件**：现有语义可用少量代码保留，完整组产出/总成本或维护负担有明确收益，再接入正式 rollout 与 grader。否则保持当前方案。没有公开文档能替我们回答这个项目上的最终吞吐。

## 9. 对当前实施顺序的影响

- 已经发现的正确性问题继续修，E5 观测继续收口；本研究不宣布 `b50bdad1` 已通过独立复核。
- E2 的批量扫描、E4 的完成记录释放具有跨后端价值，不必因为调查外部服务停下。更深的 Docker 专属池化、缓存与运行时改造，可等接缝探针结果再扩大投入。
- 1A 的包供应政策、缓存与逐题数据仍有价值；实现时把它们与 Docker relay、接网/撤网放在清晰边界，避免把供应政策写死到 Docker 生命周期里。当前已批实现不被本调查自动撤销。
- 此次不同时改原容器评分、RL 组规则、I18 或训练框架。把多个变化绑在一起会使成本和评分差异无法解释。
- 对项目贡献而言，选择合适运行时、证明环境与评分语义可靠、量出有效训练吞吐，同样是 infra 能力。无需为简历价值坚持自管每一个容器，也不能把供应商的规模宣传算作自己的成果。

建议下一步交付是**一份 Prime 接缝探针的小 Brief 与结果表**；实际服务试用和正式迁移另按用户安排推进。本轮只完成研究文档。

## 10. 用户所示 240 vCPU / 720 GB 八卡机器的容量判断

用户截图标示 RTX PRO 6000 PCIe ×8、240 vCPU、720 GB 内存、200 GB 存储、Verda 提供，平台显示起价 $9.70/小时。以上是截图条件，不代表本轮核验了实际可租库存、CPU 拓扑、磁盘性能或最终订单价。

**判断：CPU/RAM 规模适合作为首轮几十路 SWE 执行的验收机器；不能据此保证足够供满八卡，也不能凭担心并发就判定必须外置。若 200 GB 是全部可用盘，则不适合直接承载当前题池与训练产物。**

当前 rollout 与 grader 默认均为 2 CPU / 4 GiB（`sandbox_profile.py`），粗算如下。这里只算列出的活跃执行容器，准备/待清理容器、relay、模型与训练进程另计；不是实测容量或正式配置。

| 求解容器（训练与评测合计） | 评分容器 | CPU 配额合计 | 内存上限合计 |
| ---: | ---: | ---: | ---: |
| 32 | 8 | 80 | 160 GiB |
| 64 | 8 | 144 | 288 GiB |
| 96 | 8 | 208 | 416 GiB |
| 128 | 8 | 272 | 544 GiB |

`--cpus=2` 是 CPU 时间上限，不是独占预留两核；等待模型时通常用不到上限，因此配额和超过 240 不代表容器开不起来，但所有任务同时忙时会争抢。反过来，配额和小于 240 也不证明没有内存带宽、磁盘或单线程瓶颈。见 [Docker 资源限制](https://docs.docker.com/engine/containers/resource_constraints/)。240 vCPU 不能直接解读成 240 个物理核心；实际 CPU 供给与拓扑需在租用形态下核实。

两个项目内事实应优先进入作业规划：

1. [216 题诊断](../swe_grading_wiring_20260915/full216_results_20260919.md)记录，镜像拉取及执行期间空闲盘从约 767 GiB 降到 366 GiB，净变化约 401 GiB，包含容器层与证据，不能当成纯镜像体积。还未算正式模型/训练 checkpoint 的长期空间。应按题包、权重、checkpoint 留存与活跃可写层列容量账，优先核对约 1–2 TB 高速工作盘的方案；这个区间是规划候选，不是必够承诺。[Verda 官方部署文档](https://docs.verda.com/cpu-and-gpu-instances/set-up-a-gpu-instance/)允许配置额外存储，具体转售平台是否透出同样能力待核。
2. `bringup.py` 的 `RH2_FA_LIMIT_GRADING` 默认仍是 4。大机器不会自动增加评分并发。举一个**非实测**稳态算例：64 个持续求解槽、平均求解 600 秒，约每秒产出 0.107 条；若平均评分占槽 60 秒，平均需 6.4 个评分槽，仅 4 个会积压。实际应使用修复后题池的均值与长尾，不能把旧批中位数代入当作平均服务时间。

建议八卡验收按 32→64→96 的求解在飞数逐级观察，并独立测试 4/8/必要时更多评分槽；先保留训练/推理 CPU 与 RAM 峰值的余量。评测与训练在飞重叠时一起计入容量。停止增加并发的依据是有效完整组产出不再提升、工具/评分尾延迟恶化、CPU/I/O 压力或内存峰值明显影响训练，而非容器数量本身。

只有确认 GPU/learner 等待主要来自本地环境执行与评分资源不足，外部沙箱才直接解决这个瓶颈；若主要是推理引擎吞吐、KV 容量或单事件循环串行，多开远端沙箱不会解除它。首轮硬件判断建议为：**先补足存储，以这台机器测试 64 路量级；把 96 路作为扩展探针，保留外部服务作为测得环境容量不足后的扩容路线。**

### 10.1 Spheron 挂载卷补充：容量可扩，但 Verda 文档给的是 NFS

用户补充：Spheron 默认 200 GB，控制台可外挂最多 10 TB volume。因此不把截图的 200 GB 当成该作业总容量上限；具体上限按用户所选 provider/region 的控制台规格，本文未登录账户核实。

2026-09-25 核对 [Spheron 共享卷文档](https://docs.spheron.ai/connecting/volume-mounting)与 [Verda 挂载指南](https://docs.spheron.ai/connecting/volume-mounting/data-crunch)：截图所选 Verda 的共享卷使用 **NFS**，实例与卷须在同一数据中心；卷独立持久化，按配置容量另计费。其它 provider 有块设备卷，不能把它们的挂载能力套到这个 offer。文档未给出这台机器/该区域卷可据以验收的实际小文件 IOPS 与延迟。

部署时区分两类用途：模型文件、checkpoint、数据与归档可以优先考虑共享卷；Docker 的展开镜像和容器可写层则需要适合的运行时文件系统。当前 overlay2 的 writable upper 不能直接放在 NFS 上，这是文件系统兼容性限制，不只是性能可能较差，见 [Linux OverlayFS 文档 Upper and Lower](https://docs.kernel.org/filesystems/overlayfs.html#upper-and-lower)。不要直接把整个 Docker 数据目录移到 NFS。

优先核实该 Verda offer 能否扩大系统盘或附加 ext4/XFS 可用的块设备；若只有 200 GB 本地工作盘加 NFS，需单独核算本地镜像工作集与活跃容器写层，NFS 留作权重/产物/归档，不能仅凭 10 TB 总容量宣布 Docker 工作盘已充足。本轮不新增存储框架，不推荐为此立即迁移外部沙箱，也不改变上文 CPU/RAM 的初步并发判断。
