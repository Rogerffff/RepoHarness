## 阶段二：核对

1. **评分：原分 1（resolved / RESOLVED_FULL）。** F2P `test_presets_njobs` PASSED；P2P 40/40 PASSED；3 个 skip 是非参考的 OSX / Windows 用例（E13）。候选确实被测：fresh 容器 `git status` 显示两文件已改，官方测试文件从 base 恢复后打测试补丁，只跑集成测试文件，install / test rc=0（E14）。同机对照 noop=0、gold=1（E15）。
2. **与 gold 的语义差异（E16）：**
   - 取值来源相同：都是 `build_jobs(conanfile)`（配置优先，否则 CPU 数）。
   - 未配置默认：gold 无条件写；候选在单配置下同样写（实测 2）。题卡担心的"只在显式配置时写"不适用于本候选。边角：`tools.build:jobs=0` 时候选因 `if jobs` 省略、gold 写 0，无公开依据判对错。
   - 多配置：**相反**。gold 对所有生成器写；候选对 Visual Studio / Xcode / Ninja Multi-Config 一律不写，并用自带测试固化。
   - 覆盖：F2P 只测"默认生成器 + 显式 42 + 首个条目"；P2P 的多配置用例不断言 jobs。默认值与多配置都未覆盖，与题卡一致。
   - **疑似假阳性（窄）**：输入 `conan install . -g CMakeToolchain -c tools.build:jobs=42 -c tools.cmake.cmaketoolchain:generator="Ninja Multi-Config"`；预期 `buildPresets[*].jobs == 42`（gold 如此；仓库既有 helper `cmake.py:18` 也给名称含 "Ninja" 的生成器加 `-j`）；实际无 `jobs` 键，模型自己的验证输出即证据（E17）。Visual Studio / Xcode 上的分歧属题卡所说"未唯一规定"，不计错。模型的两条理由中，"上游如此"被 gold 证伪；"CMake 的 jobs 只支持单配置"未经验证（我的推断：很可能不成立，离线无法核文档）。阶段一的"训练记忆嫌疑"据此减弱：与 gold 重合的部分也是仓库惯例的自然写法。
3. **测试文件处置（E18）：** 分类 `projectable`、无 reason code；候选改的单测文件不是官方测试文件，被**纳入投影**（`included_paths` 两项、`ignored_paths` 空），只在 `candidate_test_like_paths` 留痕。评分不执行该文件，新增测试不影响分数。对照：a2 / 冒烟改的是官方测试文件，被按 `official_test_file` 忽略（E19）。
4. **三次补丁不实质相同。** a2 与冒烟的源码段逐字节相同（无多配置门，语义≈gold），a1 多了多配置排除（E19）；三者同为 1，奖励分不出这一差异，组内优势为零。
5. **归因：** `model_success`（主路径真实修复）+ `suspected_false_positive`（多配置分支与 gold 相反且不受测试约束，范围窄）。评分与过程事实置信度高；假阳性定性为中（公开题面没写多配置）。
