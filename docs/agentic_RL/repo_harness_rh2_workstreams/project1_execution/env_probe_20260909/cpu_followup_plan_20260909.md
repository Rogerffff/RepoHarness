# CPU 环境后续工作建议：真实评分、可迁移环境、扩充候选与题目语义审计

日期：2026-09-09；记录人：B / Codex。**这是供用户决定执行范围的建议，不是已批准的训练题单、评分修改或新运行任务。** 本轮只读核查代码、文档与远端状态，取回新增阅读文档；未启动容器、付费模型求解或大批镜像下载，未改生产代码。

## 1. 结论与当前证据

CPU 机器现在最值得承担的工作，依次是：

1. 用现有工件走真实 rh2 评分，补齐来源与生产配置的接缝。
2. 在同一流程中测清依赖准备、离线运行、资源上限、并发和迁移成本。
3. 扩大来源与仓库版本覆盖，形成可供后续基座诊断选择的环境候选池。
4. 对需求与测试是否一致、测试是否漏错建立有执行证据的小规模审计。

以上能证明环境有效、奖励更可信，**不能代替目标 Qwen 的学习性诊断，也不能单独证明训练收益**。不应现在把历史 216 题或新筛出的全部题冻结为正式训练集。

## 2. 第一项：真实 rh2 评分与跨机器一致性

### 2.1 不需要 GPU，但不是换个函数名就完成

生产组件 `SWEGradingManager.grade(..., workspace=None, frozen_delta=...)` 能接收冻结工件、创建 fresh grader 并评分，不依赖 learner 或一次新模型求解。可以写很薄的实验入口调用真实组件；不再复制一套 parser、补丁投影和测试流程。

关键源码：

- `rh2/src/repoharness2/grading/manager.py`：`SWEGradingManager.grade`、`GradingManagerConfig`、`GradingEnvSpec`。
- `rh2/src/repoharness2/adapters/slime/prepared_task_face.py`：`build_grading_spec_from_host_view`、V2 trusted setup 与 candidate test 脚本。
- `rh2/src/repoharness2/envpack/scoring.py`：`_parse_official` 仍调用安装的 swebench。
- `rh2/src/repoharness2/adapters/slime/sandbox_profile.py`：真实 grader profile。

已存在的独立评分单测和 Docker toy fixture，不是这批真实任务在正式 profile 下通过的证据。`sandbox_profile=None` 的 legacy 评分也不能替代正式路径。

**先解决或用真实任务暴露的接缝：**

| 接缝 | 当前证据 | 本轮需要取得的结果 |
|---|---|---|
| SWE-Gym parser 与执行命令 | 现有评分仍接 stock swebench；V2 脚本按 `eval_cmd + files` 生成，来源命令并不都能这样组合 | 具体任务的测试选择、环境变量、安装/编译步骤、解析器与上游基准一致；不能用兜底空解析冒充 reward 0 |
| 真实资源与权限 | grader 默认 2 CPU、4 GiB、非 root、deny_all；未见共享内存显式参数 | 用当前默认和必要的资源对照定位差异；明确候选测试失败、资源故障、准备失败，按 A 已定分类处理 |
| 工件投影 | 六条候选在独立 runner 与 rh2 测试路径投影上有差别；MONAI-2454 有同名新增测试反例 | 同一冻结补丁经过真实投影，比较实际文件与逐测试状态，不只比较最终 0/1 |
| R2E 来源 | V2 任务来源仍固定 `swe_gym_lite`；R2E 虚拟环境、测试入口和 expected-state 语义不同 | 需要来源适配；不能把 R2E 行改名塞入 SWE-Gym，也不能一律要求全部测试 PASSED |

A 的预算终止批在 `92d165aa` 对应第四次窄复核已经收口，不应继续把旧复核 finding 当未修复。其记录也明确没有本轮真实 SWE/CC/Docker 验收；预算修复不能替评分正链验收。B 不必等所有训练优化完成，但应使用双方可追溯的评分代码版本，避免复制正在改动的工作树后无法解释结果。

### 2.2 最小实跑包

先用现成七个候选工件：dask-7656、modin-6298、pydantic-8793、pydantic-5706、conan-13326、pandas-48106、MONAI-2454。每题重用原始候选；按需加 empty/gold 对照。它们涵盖投影差异与新增官方测试文件，不需重新付费解题。

再补少量只覆盖缺失风险的任务：mypy 命令选择、需要编译的代码、参考 ID 转义、modin 网络依赖、MONAI 共享内存。MONAI 的长 CPU UNet 测试先做窄定位；正式接受该题前再明确完整测试与预算，不盲目重复长任务。Pydantic-8500 终版题面原例重放放在语义审计中。

需要比较：输入基线、候选投影文件、实际评分命令、退出/超时/OOM、逐测试状态、最终 reward、清理结果。真实 rh2 与旧 runner 不要求无条件同分：如 MONAI 同名测试应解释旧 error 为何消失，而非强行维持它。

随后走一次“真实物化 → 写入现成候选 → 冻结工件 → 释放求解容器 → fresh grader”的 CPU 路径。这里可用确定性动作代替模型，仅验证环境和工件运输；这不宣称已经验证 Claude Code 与目标模型协议。

### 2.3 将来换机器怎样降低漂移

交付同一组：数据 revision、仓库 base、镜像 digest、准备配方、评分命令/parser 版本、rh2 版本、资源/权限/网络配置、候选工件与预期逐测试结果。按环境包或 run 记录一次，复用现有字段，不新增逐轨迹证书或审批闸门。

现在在 CPU 机完成冷启动和热启动、全新容器、并发负载下的验证。之后每种实际承载评分的主机仍要跑约 6–12 个有区分力的迁移样例；kernel/cgroup/Docker/文件系统和 CPU 争抢不能由镜像 digest 完全保证。若评分继续留在独立 CPU worker，就验那个 worker；若在 GPU 主机，短评分检查也不需要启用八卡训练。

## 3. 第二项：安装、镜像、存储与吞吐准备

准备流程建议为：

`来源清单 → 固定镜像与依赖 → 联网完成必要安装/编译 → 检查实际初始代码 → 离线评分 → 保存环境配方与测量 → 新主机预拉取 → 小批迁移检查`

分开三类东西即可，不需要新平台：

1. **宿主评分工具**：rh2 的 CPU 所需依赖与对应来源 parser/runner；不为独立评分安装整套 GPU 训练依赖。
2. **任务运行环境**：仓库、解释器、依赖、必要编译产物。镜像内 HEAD 正确不等于工作树干净；先记录预置的源码改动与依赖改动，不能把全部预置变更误算模型补丁，也不能盲目清掉才能运行的依赖。
3. **harness 工具**：固定版本 Claude Code。现有 `ClaudeCodeDriver._install_native_cli` 已支持上传 x64 平台原生包离线安装并验版本，默认 2.1.205；不需要重新发明 Node/npm 安装。测清每容器复制/解包成本后，再决定是否复用共享层。**grader 不需要装 Claude Code。**

准备时联网、评分保持已批准的 deny_all；求解器经代理访问模型 API 是另一个通道。不能以需要 API 为由放开候选任意下载上游修复。若制作派生镜像，记录它的新 digest 并重验，不能沿用原始镜像身份。gold、私有测试与 API 密钥不进入 agent 可读镜像层。

容量预算用：**去重后的镜像层 + 并发容器可写层峰值 + 编译/包缓存 + 临时测试数据 + 留存日志 + 余量**。建议预留约 25%–30% 空间，但这是初始运维建议，不是论文或训练合同。逐批测新增占用，不按目前 49 镜像外推全量源。

这台机建议用相同任务分批比较并发 1/2/4；稳定后才试 8。测有效评分数/小时、排队与实际执行时间、长尾、CPU/RAM/共享内存/磁盘峰值、OOM 和残留；19 vCPU 的机器不应默认八个重测试容器都能满配。空镜像缓存与已有缓存分开计时，避免训练时每个 attempt 重新拉取和安装。取消或超时后确实停止并回收也属于本轮验收。

旧任务反复缺依赖或同一 parser 系统性失败，应暂停该类批次修接缝，不靠每题无限重试。针对基础设施瞬态失败，沿 A 已批准的窄重评分原则；测试失败、题目缺陷与资源上限不因重试成功就自动洗白。

## 4. 第三项：怎样扩大环境筛选

### 4.1 先做便宜的全量盘点，再分层实跑

完整 SWE-Gym 数据卡为 2,438 题、11 个 Python 仓库；R2E-Gym Subset 约 4.6K。先盘点两来源全部元数据：来源 revision、仓库/版本、镜像、语言、测试入口、补丁类型、时间、重复 PR/任务关系、与预留评测仓库的重叠。镜像清单可查不等于镜像已能拉取；不能只凭 `Verified` 名称标为 rh2 验收通过。

**建议第一轮新增 128 题：SWE-Gym 完整集 Lite 之外 64 题，R2E Subset 已有 24 题之外 64 题。** 64 是控制首轮范围的建议，不是统计充分性保证；按仓库/版本、测试框架、编译依赖和修改类型覆盖抽取，兼顾慢任务，避免只挑最便宜的题。

执行先每源 8–16 题，再扩到 64。每题先 fresh no-op/gold 各一次；异常、资源敏感、网络敏感题针对性复验，并随机抽取约 10%–20% 正常题重复，避免只看异常而漏掉整体不稳定性。初期不将每题三次作为固定昂贵门槛。来源适配未闭合时，上游 runner 的结果只记来源级环境证据，不能宣称真实 rh2 就绪。

看覆盖增加、失效率、单位成本后，再决定扩到约 500–1,000 题的候选池或更大。该池包含待处理/待模型诊断项，不等于保留全部用于训练；后续目标模型判断成功失败混合、轨迹长度与奖励成本。

### 4.2 第三个来源与新 PR

现阶段先盘点 Prime 的 SWE-rebench V2 Filtered Verified、Scale-SWE Verified 中的 Python 任务。优先考虑前者做 16–32 题的第三来源试接，前提是确实增加未覆盖仓库/任务类型且镜像可用；若实际覆盖重复或成本差，再选 Scale。不要一次引入二者和 SWE-smith 三套新适配。

SWE-smith 的环境先行、同镜像派生多题，对后续扩充成本很有价值；但其 bug patch 方向、测试可见性、合成题语义不同，不能按 SWE-Gym 的 gold/test_patch 套用，也不宜直接充当最终评测。

暂不批量爬 PR 自建环境。已有来源仍有大量未消费资产。等覆盖表显示需要更近期仓库、特定缺陷类型或独立分布，再做 2–3 仓库的小试点，并复用上游构建能力。CPU 便宜不能抵消安装维护、题面澄清与评分审查的人力成本。

扩展前先留出开发与最终测评分界，按仓库/PR/派生 bug 家族查重；正式规模可后定。预留评测环境可以做安装与 gold 资格检查，但不能用最终评测模型表现反复选择训练配方。修过题面/测试的版本必须与原指标分开。

## 5. 第四项：读题审计和模型求解怎样配合

**推荐“静态筛疑点 + 执行证据定性 + 少量模型轨迹补充”，不选单独一种。** empty/gold 只证明参考补丁能改变现有测试判定；不能证明需求完整、合法替代解均能过、错误解均会被拒绝。

| 层次 | 做法 | 防止什么误判 |
|---|---|---|
| 元数据与结构预检 | 全池检查缺失/截断题面、参考 ID、测试目标、镜像与重复关系 | 静态通过不冒充运行通过 |
| 题面独立理解 | 审查 agent 先只看实际 prompt、base 代码、公开文档和既有测试，写明可推导行为 | 避免先看 gold 后把实现细节误当用户要求 |
| 私有评分对照 | 再对照 gold、隐藏测试、维护者补充、现有候选与轨迹；保留不确定性 | 与 gold 不同不等于错，修改测试不自动等于作弊 |
| 运行反例 | 对原版、gold、候选执行具体原题例子、必要回归、合理替代实现或有语义的错误变体 | 同时抓假阴性与假阳性；不能删掉 docstring 就称为错误补丁 |
| 补充求解 | 修好可见性与环境后，对仍有疑问的题和随机正常对照少量求解 | DeepSeek 失败不等于坏题，更不代表目标 Qwen 学不会 |

先复用 24 条轨迹，优先把 Pydantic-5706 的 Sequence 回归与 Pydantic-8500 的终版题面原例做成可执行对照；参考 ID、modin 与 MONAI 分别归解析、环境、投影处理，避免全部混入“题目质量”。新池先审 24–32 题，混合异常与随机正常题，再根据实际发现调整投入；不预设每题都要昂贵的多 agent 深审。

有证据的坏题才能考虑排除；缺少证据时标待核验。合理补充需求、修正 parser/参考 ID、扩大回归测试，分别涉及不同口径，先形成具体前后对照再交 owner 决定。原官方分数与增强诊断分数分开保存，不能悄悄改变 reward。审查用私有材料不回流 agent prompt。

如仍需 DeepSeek 补充，后续另提一小批有目标的题单与调用预算。当前没有必要先让 DeepSeek 把几千题全做一遍。目标模型确定后再做学习性探针，才知道哪些题能产生有效 RL 信号。

## 6. 新阅读对本轮的影响

本轮从远端 `research/frognano-20260909@73a0b781` 取回 FrogNano 来源说明、精读正文和作者自查，未合并分支或覆盖共享索引。阅读了 B 相关章节及自查，不声称重审全文代码或独立验证该报告全部结论。

- FrogNano 把任务有效性与当前策略难度分开，并展示题面信息改变成功率的例子。对本项目的借鉴是先验证题目，再校准目标模型难度；**不是为达到 50% 通过率删掉必要需求**。当前没有核实到可直接接入的完整 TaskPilot 发布任务包。
- SWE-smith 支持共享已经装好的仓库环境、降低每新增任务的准备成本；它没有证明自然语言需求和评分覆盖自动可靠。
- SWE-rebench 与 Prime 材料说明镜像、任务运行、候选工件、评分实现是不同对象；来源的验证标签不能替代本项目的 fresh grader、权限和资源检查。
- OpenAI coding evaluation 审计材料支持“agent 调查 + 运行反例”的组合；自动筛查不能直接当排除裁决，还要检查未报警的对照题。

## 7. 建议执行次序与交付

| 顺序 | 建议范围 | 可以交付的证据 | 依赖/边界 |
|---|---|---|---|
| 第一批 | 七个现成工件真实评分；少量针对性反例；两来源全量元数据盘点；冷/热准备与并发测量 | 真实评分差异表、来源接缝清单、资源与镜像成本表、候选覆盖表 | 不新增模型求解；需改变来源契约或评分语义时先给具体决策包 |
