# 环境筛查流水线：阶段重排与下一步设计建议

日期：2026-09-11。作者：Codex（B 线）。性质：依据现有 CPU 证据、真实评分入口和外部资料提出的讨论稿；不是新一轮实验完成报告，也不是生产契约或筛题规则的批准记录。

用户本轮要求重新审视[原分阶段计划](cpu_followup_stages_20260910.md)，暂缓环境包与跨机迁移，优先真实评分接通，再设计、校准、扩大环境筛查。本稿保留这个主要方向，并修正“必须先接完所有来源，才能设计和验证流水线”的串行依赖。

## 1. 判断：调整工作组织，而不是继续给阶段一追加零散探针

建议顺序为：**先形成一版材料与评分约定 → 接通代表题的真实评分 → 用已知反例和正常题校准完整筛查流程 → 分批扩展 → 在求解和训练后持续复审。** 流水线设计与来源适配可以交错推进；不能先接一个只返回总 reward 的接口，再发现质量诊断所需的逐测试、安装、资源事实全部丢失。

原计划的问题主要有四项：

1. 把环境条件诊断、实际评分接线、题目质量审查拆成了先后孤立的工作包，缺少一份贯穿三者的材料和结果约定。
2. 阶段四先扩题、阶段五后审质量，容易把安装、fixture、题面和测试问题大量复制后再返工。
3. 断网诊断太容易被解释为“所有阶段最终必须断网”。准备依赖、agent 解题、候选安装构建、测试执行并不是同一个网络边界。
4. 阶段二仅写成代码 T1 不准确：按原配方接线与改变评分输入、错误归类、网络、来源 expected 的含义，需要分别处理。A 的[第四组评分讨论](../batch4_scoring_20260910/README.md)已有对应待定项。

阶段一仍有明确价值。它发现了可缓存权重、真实服务依赖、共享内存不足、参考 ID 漂移、测试 fixture 依赖遗漏等不同问题。现在应将这些整理成固定的校准案例，停止以“机器便宜”为理由继续无目标扩大重复测量。后续每项探针应说明它要区分哪两种解释、改变哪个实现或决策。

| 旧工作包 | 建议处理 | 理由 |
| --- | --- | --- |
| 阶段一：补测 | 已有大批诊断收口；未解问题进入新流程的具体案例 | 不要求现在逐个修完所有离线失败，才能接真实评分 |
| 阶段二：接通与对账 | 成为下一实施主线；从代表题纵向接通，再扩到两个来源 | 对账本身就是本阶段的工作，不必等整个阶段二“完成以后”才开始 |
| 阶段三：环境包与迁移 | 按本轮要求暂缓大规模分发、全量镜像缓存、跨机启动验收 | 每题依赖和资产准备仍必须现在做，不能一并推迟 |
| 阶段五：质量审查 | 设计前移，与真实评分共同校准；细则仍单独讨论 | gold 通过不足以证明题目公平、测试充分 |
| 阶段四：扩展筛选 | 放在小规模校准之后，按来源/仓库分批 | 新仓库继续允许小规模探索；不等于一次冻结所有未来情况 |
| 阶段六：处置 | 贯穿各批次，证据充分就讨论 | 不再让一个已查明的资产问题等待全池语义审计 |

| 来源 | 对本次有用的原文事实 | 我们采用的设计启示及限度 |

| [SWE-Gym](https://arxiv.org/html/2412.21139v1)、[R2E-Gym](https://arxiv.org/html/2504.07164v1) | 历史仓库环境需要恢复相应依赖；R2E 还从修复、测试、执行反馈生成问题描述 | 现成镜像值得复用，但仍需核对当前执行。论文曾验证可执行不等于当前镜像/parser/权限条件下仍正确 |

| [SWE-rebench V2 §3–4](https://arxiv.org/html/2602.23866v2) | 仓库级生成并复用安装/测试配方；逐题修复前后执行，结构化测试结果三次一致；另做题面清晰度审查与诊断标注 | 最接近可复用流水线骨架。编译后测的是新代码、具体测试集合一致，比“命令 exit 0”更强。我们不直接照搬其多 judge 一致过滤或全套阈值 |
| [SWE-smith §2](https://arxiv.org/html/2504.21798v1) | 先建稳定仓库环境，再在其中合成多个任务；任务可使用 agent 可见的现有测试 | 自产任务有另一条便宜路线，不必每个 PR 从零建环境。其可见测试/bug patch 方向不同，不能按 SWE-Gym 隐藏 test_patch 的假设机械接入 |
| [Prime R2E Verified 数据卡](https://huggingface.co/datasets/PrimeIntellect/R2E-Gym-Subset-Verified) | 先全量 gold，失败者重试十次；至少一次成功的 flaky 行仍保留 | 可复用其排除线索；“Verified”不是十次全通过，更不代表已完成题意、no-op、合法替代解审查。我们需要自己定义可接受的稳定性 |
| [OpenAI SWE-Bench Pro 审计](https://openai.com/index/separating-signal-from-noise-coding-evaluations/) | 对题面、尝试和评分测试先初筛，再对可疑项做可执行的调查 agent 审查及人工判定；区分过严测试、欠明确/误导题面、覆盖不足 | 静态阅读与真实执行相结合。审查必须能查看相关源码、运行反例；通过题也可能是假阳性。该审计的初筛子集不能代替我们对未标记题的随机检查 |
| [Real-World Code Repair](https://arxiv.org/html/2510.22075v1) | 固定依赖可恢复部分历史修复；简化工作流内 RL 收益没有相应回到完整工作流 | 环境优化应验证行为等价。不能为了更快而无证据删除安装、构建或真实开发步骤；该论文多项条件同时变化，不给单一因素因果结论 |
| 新 DeepSeek 精读 §6.2–6.3 | 据精读，原报告以问题、环境、验证系统共同定义任务，并描述多求解器、独立质检、修复再验与使用后复审 | 支持把求解轨迹纳入持续复审；没有公开完整题数漏斗或可复现任务资产，不能替我们定筛选阈值。此行为建议也由上面公开来源和本地反例独立支持 |

FrogNano 的当前策略通过率校准，以及新 Miles 的训练接入设计，是后续能力诊断/训练消费参考。它们没有替我们解决参考测试是否合理的问题。尤其不能为追求某个模型 50% 的通过率而删掉题面必要条件；也不能因 Miles 支持某个环境接口，就认为任务质量已被上游验证。

## 3. 真实 rh2 对账：需要最小接通，不需要完整训练栈

源码核查基线：`bc2cfa71` 的本地工作区。这里只核对接口和已登记缺口，不是新的完整评分安全验收。

- `rh2/src/repoharness2/grading/manager.py::SWEGradingManager.grade` 已接受 `spec`、`frozen_delta` 和可选 `workspace`。可以在 CPU Docker 上直接调用；不要求先运行 miles、SGLang 或 GPU learner。
- `envpack/scoring.py::parse_official_eval` 仍调用安装的 `swebench` 来构造 spec 和解析。它尚未沿 `spec_vendor_id` 接入 SWE-Gym 的完整来源配方。
- 正式 profile 要求分开的 `trusted_setup_script` / `candidate_test_script`，并在 fresh grader 中重放冻结候选。传入普通 workspace、直接应用 gold 或使用 root 的 legacy eval，均不能替代这条验收。
- `GradingEnvSpec.parse_log` 当前与 `EvalVerdict` 的 SWE F2P/P2P 结果绑定。R2E 的 expected 状态映射不能简单伪装成“全部测试应 PASSED”；适配时要保留来源语义，明确怎样映射公共结果，不伪造 SWE 计数。

**第一条真实对账路径应是：**

```text
固定来源任务、镜像、公开/评分私有材料
    → 用真实物化路径建立候选工作区
    → 脚本重放已有候选补丁、gold 或 no-op
    → 调用真实冻结与投影逻辑
    → SWEGradingManager + 正式 grader profile
    → 逐测试结果、阶段、退出/资源事实、最终 reward
```

这里脚本只替代“模型写补丁”，不重写冻结、投影、安装、测试和解析。现有 7 个候选工件可先做来源核验后使用，不假定文本 diff 本身已是合格的 FrozenDeltaSource。正式调用所需的期限等参数也应显式给出，避免直接调用绕过训练侧配置。

另保留固定版本官方 runner，使用对应材料在独立环境运行，作为对照。对账先判断：候选重放后的文件是否相同、可信测试与 fixture 是否完整、安装是否作用于候选、测试选择是否相同，再比较逐 ID 状态和总分。**不是要求官方 runner 和 rh2 的所有失败分类逐字相同，也不是发现差异便改 rh2 追平总分。** 官方 expected 自身有问题时，正确结果应是准确重现差异并进入任务复审。

推荐先用 SWE-Gym 建立这条路径，并同时整理 R2E 的输入/结果约定，随后接 R2E 代表题。不等待所有 216 题完成质量处理，也不等待未来所有数据集 parser。真实队列的期限/并发另做小组测试；这里只通过 grader，不能宣称真实 Claude Code、完整训练或 GPU 链验收通过。

## 4. 一份任务需要共同说明哪些内容

复用现有任务包、冻结工件和 JSONL 记录，补齐当前缺失信息；下表是信息清单，不要求现在新建一套 schema、服务、数据库或权限闸门。

| 信息 | 必须能回答的具体问题 |
| --- | --- |
| 来源与分组 | 哪个来源版本、仓库、commit/PR？跨来源是不是同一个修复或派生任务？是开发候选还是保留评测候选？ |
| 题面与公开工作区 | agent 实际看到什么？外链内容是否为必要规格？镜像是否有未来修复、来源预先修改、隐藏材料或旧运行残留？ |
| 解答范围 | 哪些代码/配置/依赖文件允许作为解答？哪些是可信评分入口、测试及 helper fixture？不能只靠文件名包含 test 判断 |
| 环境与资产 | 解释器、包、系统库、权重、测试数据、服务分别是什么；何时准备、谁可见、放在哪里、怎样校验可访问？ |
| 执行配方 | 候选重放、安装/重新编译、可信测试注入、测试命令与选择器的实际顺序；执行用户、cwd、HOME、网络及资源条件 |
| 评分含义 | 使用 F2P/P2P 还是 expected 精确匹配？缺失/额外/跳过/ERROR 怎样解释？来源结果和 rh2 错误分类分别保存 |
| 质量与成本 | 原始和修复后测试是否区分目标行为？有无题意/覆盖问题？哪些经过实测，哪些尚未知？准备与每次执行各花多少成本？ |

不能把一个 `valid=true` 同时当作镜像能跑、题目公平、当前模型可学、正式评测无污染。至少保留这些不同维度的观测和原因；不由一个模型标签直接触发生产排除。

## 5. 四段网络与两种使用视角

既有正式 grader 仍为 deny_all，本稿没有将其改成联网。**建议优先研究“准备时联网补齐固定资产，解题和评分按其任务需要分别配置”**；是否放开某阶段，应依据具体需要另作决策。

| 环节 | 典型网络需要 | 本轮建议与验证对象 |
| --- | --- | --- |
| 环境准备 | 下载包、权重、数据；恢复历史工具链；准备文档或服务 | 可以联网。尽量得到固定输入、镜像层或资产缓存；准备动作只用来源材料，不执行候选解答。公开资产和评分私有材料分开 |
| agent 解题 | 读文档、复现问题、安装任务允许的新依赖、使用指定服务 | 属于要训练的能力边界。若需要文档/依赖，先考虑公开快照、离线包或受控服务；确有在线能力目标再设计访问范围。不能开放上游答案获取却按独立解题率记账 |
| 评分安装/构建 | 让评分检查真正的候选代码及其依赖，而不是镜像中的旧包/二进制 | 优先使用预装工具链、离线包仓等；某题确需指定包源时单独分析。候选的安装/构建脚本仍可能执行任意候选代码，应保持非 root，不因叫“安装”就视为可信 |
| 测试执行 | 访问静态资产、本地服务，或依赖真实外部服务行为 | 静态资产预置；本地服务固定状态。确依赖公网时检查稳定性与任务含义。把真实服务改成 mock 可能改变 oracle，不能作为无语义改动 |

**还要分别验证 agent 视角和 grader 视角。** grader 能运行隐藏测试，不代表 agent 能运行公开开发测试；反过来，agent 测试通过也不代表 fresh grader 重放正确。agent 不必看到所有 hidden tests，但应拥有完成题面合理要求所需的公开信息、工具和资产；关键复现命令不可执行的原因要说清楚。

当前案例的正确落点：

- **MONAI-1121**：本机 root 下“在线无预置 / 离线无预置 / 离线预置”分别 FULL/NO/FULL，预置权重恢复 8 个参考回归测试。将其作为资产准备案例；下一步验证非 root agent/grader 的实际 HOME、缓存路径、权限。不能从 root 的 `/root/.cache` 可用外推其他用户可用。
- **MONAI-3205**：已识别 Hippocampus 数据下载依赖，尚未完成预置恢复对照；登记待验证，不能写成已解决。
- **moto-4799/4833**：停止 mock 后访问真实 EC2，断网改变异常类型。先判测试究竟要验证 SDK 行为还是公网结果；联网一次通过不足以证明它稳定、公平。moto-7105 的原因仍未收敛，不并入同一结论。
- **modin S3**：某些路径可能比较两边异常而通过。需要核对断言实际验证的行为，不能把 FULL 当成成功访问了 S3。
- **候选依赖修改**：假如任务要求增加依赖，agent 不能安装且 grader 只用旧缓存，就可能形成无法验证的工作流。应明示任务范围或准备合法包供应，而不是把所有安装失败记成模型不会修复。

## 6. 筛查流水线的建议骨架

| 步骤 | 主要工作 | 输出及下一步 |
| --- | --- | --- |
| ① 来源初筛 | 保留原始行，检查材料完整性、仓库/修复去重、外链与测试/修复关系；标记开发/评测用途 | 得到可诊断候选。静态疑点不立即等于坏题 |
| ② 可执行环境准备 | 恢复依赖和静态资产；核对初始工作区；分别验证公开开发测试和评分材料的依赖 | 可重建的准备步骤及未解决依赖；按仓库/版本复用，逐题验证 |
| ③ 真实评分一致性 | 脚本候选经过真实冻结/投影/非 root grader，与来源 runner 对拍 | 找出 adapter、工件重放、安装、选择器、ID 与来源 expected 问题 |
| ④ 执行有效性与稳定性 | fresh base/gold，核对具体测试与失败原因；对异常及随机正常项做固定次数复测；逐步校准资源与并发 | 说明在哪些条件下可稳定验证。no-op 的 0 必须是目标行为未修复，不是启动/解析失败 |
| ⑤ 题目与测试质量 | 阅读题面、邻近源码、gold、测试和轨迹；执行最小反例、合法替代实现与有依据的补充回归 | 区分欠明确/冲突、测试过严/覆盖不足、环境缺陷、正常难题；保留证据和不确定性 |
| ⑥ 实际 harness/模型诊断 | 使用固定 Claude Code 配置试做；记录公开复现、测试、补丁、原始响应、工具事件和成本 | 区分 harness/工具问题、环境问题、能力不足；有限采样 0 成功不定义不可解 |
| ⑦ 修订与复验 | 环境修复、题面补全或测试更正各自记录版本，重跑受影响检查；已保留样本也接受后续轨迹复审 | 原始任务、修订任务与结果都可追溯，再决定训练/评测使用方式 |

第⑤步的自动审查建议先产“疑点＋证据”，不自动改题和丢题。审查角色先根据公开题面及代码形成合理要求，再用 gold/私有测试核对；直接一开始只照 gold 判断，容易把唯一参考实现当成唯一正解。模型求解器不应拿到审查角色的特权材料。

对争议题应尽量构造两种可执行证据：**合理解被拒**，或**明显违背题意的解仍被接受**。代码覆盖率、变异测试、LLM 标签都只能辅助；一个等价变异存活不是覆盖不足的充分证据。扩展回归也要在 base/gold/candidate 上对照，避免把原有失败或无关要求算到候选头上。

不要求每道题都做多模型、多轮全文审查。先用便宜检查覆盖候选池，再对已知问题、异常模式和一份随机正常/未标记样本深审。必须包含通过题，才能发现 Pydantic-5706 这样的假阳性；只读未通过轨迹会系统性漏掉它。随机样本与定向反例统计分开，不能从反例集推全池坏题率。

## 7. 用什么校准，而不是马上重新跑几百题

优先复用已有 SWE-Gym 216、R2E 原/新增各 24 题，以及可核验的真实候选。首批按风险和配方选最小覆盖集，不为了凑 24 个数字重复采样；详细清单在评分接线 Brief 中列明。它应包含普通通过题、普通失败题、当前已用仓库的配方差异和下列反例：

| 案例 | 要求新流水线识别的区别 |
| --- | --- |
| mypy、conan 正常题 | 测试选择/额外 eval_commands/安装不是一条通用 pytest 命令 |
| 参考 ID 脆弱题，按根因取代表 | 测试是否真的不存在，还是 parser/转义/名称不一致；不自动改 expected |
| MONAI-1121、3205 | 权重/测试数据依赖；准备后对 agent 与 grader 是否均按需可用 |
| MONAI-763 | 64 MiB vs 更大 shm 的短复现；完整测试仍需验证，不能把短 DataLoader 成功当整题通过 |
| moto 网络敏感、modin S3 | 服务/异常含义与公网可达性；不按最终总分归因 |
| R2E coveragepy 016af5 | 历史依赖相关 FAILED 写入 expected；目标修复成功而原 exact-match 判 0 |
| R2E datalad 58ba51 | 可信测试依赖了旧的 helper fixture，新断言和旧输入不匹配；不能只注入主测试文件 |
| Pydantic-5706、8500 | 官方通过但回归覆盖不足，或题面原例未覆盖；真实 candidate 必须进入质量审查 |
| 合法 testing 辅助源码修改、测试同名候选文件 | 保留有效修复与可信测试控制面的边界；避免投影把解答静默丢掉 |

资源实验放在可运行且材料稳定的条件下：先测少量高峰/慢例的单题内存、shm、时限，再改变并发，观察评分状态与吞吐是否同时稳定。本次两路并发、8 GiB 配额下观测到的峰值不能直接推导正式 4 GiB 可用，也不是并发最优点。并发增加导致失败必须与单任务资源不足区分。

正式池是否全量做三次 fresh 重复、随机深审比例及可接受 flaky 水平，留到试运行后用成本和观测决定。保留每次尝试，区分固定重复与故障重试；不能不断重跑直到一次成功，就把成功率记成稳定性。

## 8. 扩展时怎样保住多样性和项目价值

先在已接好的 SWE-Gym/R2E 来源内扩展，观察新增仓库、版本、测试工具和问题类型。一个新来源接入是否值得，以它带来的有效任务覆盖和成本判断，不只比较数据集行数。SWE-rebench/ScaleSWE 可以进入下一轮候选；自产 PR 或 SWE-smith 式合成在现成供给确实不足时，以已有稳定仓库做小规模尝试。

扩展之前至少保留仓库、PR/commit、近重复/派生关系，给评测候选划出单独用途。最终 split 尚未冻结，也不妨碍先做环境资格检查；但不能把被用于反复调题、调 parser、挑策略的样本，再称作完全未接触的最终评测。跨来源同仓、同 PR 和派生任务需要一起处理；仓库分离也不等于已经排除基座预训练污染。

项目的有说服力证据建议分成两层：

1. **环境生产与评分本身**：来源 runner/rh2 的差异及关闭情况；修复前后的重复一致性；被判环境故障、题意问题、测试问题的数量；准备 CPU 时间、每次评分耗时、任务可用产率；分仓库/类型/长度记录保留与剔除，避免只剩便宜易题。
2. **训练是否因此更有效**：之后在固定题目/评分版本与可比训练预算下，观察有效正负反馈、奖励获取成本和独立评测收益。修题、改测试或换网络带来的分数变化，不能写成模型权重学习收益。

先用人工复核的校准集比较“只有 base/gold 检查”和“增加完整环境/质量诊断”发现了哪些误判，以及多花多少成本。由于这些案例是定向选择，只能说明能力覆盖；需要另外的随机留出审查才能估计全池错误率。这比宣称建了很多道门或复刻某家平台更容易证明贡献。

## 9. 下一次只需要讨论的近期决定

本轮已形成可供审阅的方案，尚不启动生产改动、付费解题或新一轮扩池。建议把下一批分成可独立推进的两件事：

**A. 真实评分最小接线。** 优先 SWE-Gym 代表题，随后 R2E；调用真实冻结/投影/grader，保留来源 runner 对照。另一个选择是同时支持所有候选来源，但会延迟发现共有接口问题。推荐前者；其长期代价只是新来源逐批增加配方，不需要现在设计通用多语言框架。与 A 线共享的投影、失败表达由同一实施者修改并集中复核，避免两边各修一份。

**B. 筛查流程校准。** 先复用现有工件、异常与正常题，明确四段网络和资产可见性，形成逐题检查表；再单独讨论第⑤步的审查提示、人工裁定、采样和模型预算。另一个选择是现在全量静态审题或继续大批 DeepSeek 求解，两者都难替代实际材料与评分验证，成本和误判也难解释。

需要 owner 在具体实施前决定的实质项是：来源 expected 是否以及如何修订、候选文件/评分控制面的边界、候选失败的 reward 表达，以及任何改变既有 grader 断网边界的方案。它们不能被“接 parser”这个标题隐去。当前只是发现依赖并设计四段网络，不要求立刻批准公网访问或所有筛题阈值；不依赖这些决策的材料核验可以继续。

本轮修正的旧结论：离线 gold 失败不是坏题判定；FULL 不是所有测试全过；阶段一不是正式评分验收；模型未解出不是题目不可解；上游 Verified 不是统一质量认证。没有新增生产挡板、排除规则或正式资源数值。

本轮证据：远端新文档回传记录在本地忽略目录 `runs/external_reading_intake_20260911/intake.json`；既有 CPU 事实见[白天收口](morning_followup_20260911.md)及其链接账本。本轮没有启动 SSH 实验、Docker、Claude Code、模型 API、GPU 或测试套件；没有提交推送。

## 10. 成文期间新增的 Claude 方案：一致点与保留意见

成文时共享留言板新增了 [Claude 流水线方案](env_pipeline_design_20260911.md)。本轮已读该稿；以下仅对直接影响下一步的设计作回应，不替代后续实施审查。

**同意补记“上游参考结果是在什么条件下生成的”。** coveragepy 正是实际反例：历史 expected 包含一个依赖不可见导致的失败。除四个执行环节外，参考结果的生成条件也应作为来源信息保存；未知写未知，不假装已经复现历史环境。它不必变成每次评分都执行的第五个阶段。

**不建议把“本地重新生成的参考集自动成为训练 reward 权威”作为默认。** 需要区分三类改动：

1. 补齐权重/包/fixture，让原任务在新环境正确执行：优先保留来源参考集合；fixture 内容变化仍需确认与任务版本相符。
2. 有证据的一一对应 ID 映射：保存原始 ID、映射和解析证据，避免改变测试身份和含义；不是删掉匹配不上的 case。
3. 修改测试状态、删除/增加测试、改题面：形成经过复审的任务修订版本。说明为什么新标准对应合理需求，保留旧/新结果，不能仅以 gold 在本地能过为依据。

例如把所有离线 gold 的实测状态复制成 expected，当然容易让 gold 满分，却可能把缺资产导致的 FAILED 也固化为“正确结果”。即使重新抽 F2P，也要排除环境差异制造的假 F2P，并检查回归要求是否被漏掉。**本地重验证是必要的；自动替换原始评分定义不是必要前提。** 无法证明等价或合理修订的项先保留为待核候选，不能让“保留官方错误”与“全量重定义”成为仅有的两个选择。

另有三处建议收窄：

- “所有成熟流水线都有全部七层”缺乏公开证据，也与该稿表内多项“无”不一致。准确说法是不同来源分别给出这些部件，组合成我们的设计；不能把建议写成前沿团队已统一执行的事实。
- “必须离线 build，真实外部端点题不进训练池”是特定工作流的选择，不是一般环境质量定律。首轮可以优先静态依赖可备齐的任务，但不要未经决策写成永久剔除规则；本地服务桩也需验证语义。
- S1 不必先为全部 216 + 24 题生成归因表，才允许 S2 设计。先用代表题确定材料与结果约定再扩展更省返工；候选安装/构建只要可能执行候选代码，仍应按非 root 候选执行处理。

Claude 稿部分“之前当成什么”的总结过宽：阶段一原执行卡已经标为诊断，后续也已撤回同名文件缺陷、笼统省 install 等解释。本次确实需要改进设计，但不应把已更正的推测重新写成当前定案。新增 R2E 24 题也已有完整逐文件快照与最终 diff 核验，后续清单应把原/新增两批区分，避免只按旧 24 计数。
