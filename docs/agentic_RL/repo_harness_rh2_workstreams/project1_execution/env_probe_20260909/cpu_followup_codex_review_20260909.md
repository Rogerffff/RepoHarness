# 对 Claude CPU 后续建议的核查与合并决策建议

日期：2026-09-09；B / Codex。被审稿：[Claude 建议](cpu_followup_claude_20260909.md)；前稿：[Codex 建议](cpu_followup_plan_20260909.md)。本文是计划讨论与证据核查，不是生产修复验收，也不批准新实验、训练题单或评分变化。本轮未启动容器或付费模型，未改生产代码，未提交推送。

## 1. 总体判断

同意真实 rh2 评分、可迁移用例包、扩大环境候选、执行与语义审计结合这四个方向。接受把 **SWE-Gym 新增 256 / R2E 新增 128** 作为分批执行的阶段上限；原稿 64+64 是首轮范围建议，不应成为争论焦点。先各 32–64 题，检查来源适配、覆盖、资源和单位成本后，在用户批准的上限内继续，不逐小批重复申请批准。

但 Claude 稿有几项必须改的判断：R2E 评分不能统一要求全 PASSED；镜像虚拟大小不能当去重落盘量；函数还原后仍通过不是测试不足的充分证据；5% gold 不通过不等于只有 5% 题需要质量审查；不能从未经验证的日志量公式决定丢弃完整轨迹。

## 2. 需要修正的事实或推论

### 2.1 R2E 的预期状态不是全部 PASSED

Claude §3.3 的“gold 里全部参考 case 出现且通过”若统一用于 E1/E2，就会误判 R2E。

本轮直接读取前轮冻结的 24 条完整 R2E 数据：`expected_output_json` 总计 **1,256 个 PASSED、35 个 ERROR、15 个 FAILED；10/24 题包含非 PASSED 预期**。例如 orange3 某题为 20 PASSED / 1 ERROR / 2 FAILED，datalad 某题为 2 PASSED / 5 FAILED。结合此前固定官方函数的 144 次重放，不能把这些状态自动视作无效环境。

**建议**：逐来源保留官方判定语义；SWE 的 F2P/P2P 与 R2E 的 expected-state map 分开。来源不支持的假设只能作诊断提示，不能成为统一删除条件。上游预期含错误是否值得额外清洗，可以另查，但不能偷偷改成全绿后仍称原分数。

数据与镜像只读统计已保存到 [核查证据](cpu_claude_review_evidence_20260909.json)。本轮没有重跑 R2E；数据中 10/24 这个比例也不外推全部 Subset。

### 2.2 约 1 TB 是未经正确去重的外推，不能据此定 registry 架构

重新读取远端 `docker system df -v` 后，可复算 Claude 的 118.6 GB，但这是 **25 个 SWE 镜像 SIZE 相加**，包含重复共享层：

| 来源 | 镜像数 | SIZE 相加 | UNIQUE SIZE 相加 |
|---|---:|---:|---:|
| SWE-Gym | 25 | 118.590 GB | 66.540 GB |
| R2E | 24 | 39.535 GB | 37.650 GB |

UNIQUE 之和还需加共享层去重后的体积，也不是该来源的最终落盘量。前次相同 49 个镜像的 Docker 总量为约 110.9 GB，已说明 158.1 GB 的逐镜像 SIZE 总和不能当总占用。Docker 官方明确 SIZE = SHARED + UNIQUE。[Docker 字段定义](https://docs.docker.com/reference/cli/docker/system/df/)

这 25 个保留镜像也不是全 216 题的随机样本，不能用均值可靠外推 216 或 Full。216 个 registry 清单的压缩大小相加，同样需要检查共享 blob 去重。

**建议**：当前只做固定 digest、选中工作集预拉取、逐批增量占用和清理操作记录。需要复用时保留镜像，批次完成后按明确清单清理；暂不新建自动 LRU 或 registry 服务。把 registry 放在同一磁盘，还要容纳压缩 blob 与正在使用的解压层，不能把它当作消除存储需求的办法。多评分节点或源站限速成为实际瓶颈后，再比较共享 registry、独立缓存盘等方案。

fully-async 工作集由在飞任务、已调度待启动任务及保留策略决定，不是简单的“当前训练 step 的任务数 × 镜像均值”；同题多个成员可以共享镜像，但有各自可写层。

### 2.3 两项“自动覆盖检查”只能部分成立

- **扩展回归**：方向成立，但“gold 触及模块的整个测试文件”没有定义可靠的源码到测试映射。Pydantic-5706 官方已经跑了 `test_json_schema.py` 的大量测试，遗漏的是其他文件里的 Sequence 行为；再跑同一个文件不能暴露它。应先选与公开行为相关的额外测试，对 base、gold、candidate 做对照，并区分原有失败与新增回归。不要求全仓所有测试必须全绿。
- **逐函数还原 gold**：仍通过可能是等价实现、冗余修复、防御或性能改动，也可能是其他改动已经满足需求，不足以证明测试漏约束。语法破坏、依赖改坏产生的错误也不等于有效语义变异。暂不造通用 AST 变异系统；先用现有题手工构造少量明确违反需求的补丁及合法替代解，校准诊断价值。

### 2.4 成本、耗时与噪声判断需收窄

- 12/216 gold 不通过约 5.6%，是特定筛选后题单在特定条件下的评分结果，不是全池坏题率。Pydantic-5706 等通过组反例直接否定“人力只花在失败题”的说法。
- 先前五并发为该配置提供可运行证据，不证明正式 2 CPU / 4 GiB / tmpfs / deny_all 配置的吞吐、尾部或并发上限。也不必为形式把全池重跑并发 1/2/4；选同一组快慢代表题做短对照即可。
- 每 2 秒 `docker stats` 的最大读数只是采样峰值，不能叫精确峰值 RSS。Linux CLI 内存读数会扣除部分 cache。应记录采样口径，并在宿主支持时结合 cgroup 峰值、OOM 事件和容器退出事实，容器删除前取回。[Docker 内存统计说明](https://docs.docker.com/reference/cli/docker/container/stats/)
- 24 个迁移样例可能有价值，但“每台机 20 分钟”尚未实测，尤其包含慢任务与冷拉取。保留完整风险用例集，另选较短启动子集；资源敏感/慢例不因追求 20 分钟而失去验证。
- `216×8×50` 假设每个 step 都求解全题库；当前没有这样的训练配置依据。日志量应按实际 attempts、每条压缩体积和保留周期算。完整 stream-json 可以压缩、转移存储；不能据此直接决定“训练不能全留”。训练必需的 token/logprob/工件信息与调试展示日志也不是同一种产物。

## 3. 对执行安排的调整

### 3.1 合并重复跑数，优先得到正式路径证据

不建议把 216 题 gold 内存轮、216 题离线 empty/gold 轮、MONAI 26 题共享内存轮、真实 rh2 轮默认作为四组全部执行。

先在少量代表题上确定命令、parser、投影和资源观测方式；将正式 profile 下的评分与资源记录合并采集。资源差异的对照只加在相关题上。MONAI-763 先沿已有短复现检查，完整长测试有明确目的再跑，不能把短复现升级为完整验收。

若来源适配暂未完成，可以推进元数据清单、R2E 来源 runner 小批、少量离线对照；但这些只记来源级证据。此时不宣称正式 rh2 环境已经验收，不把临时 runner 扩成第二套长期评分器。

### 3.2 接受较大上限，修正覆盖与留出集合

建议新增 SWE-Gym 上限 256、R2E 上限 128；首段各 32–64。应按 Full 的实际候选重新建立 repo/version 覆盖表，不只照搬 Lite 的 78 个组合；“每组至少两道新的非 Lite 题”先查是否存在，不能为填配额重复计题。

Claude E1 同时写“同 9 仓库”及 hydra/bokeh，口径矛盾。hydra/bokeh 是额外两仓，tornado/pyramid 也被建议作为留出仓。建议将这些明确列为**评测候选环境资格检查**，与训练候选扩充分别计数；不因为安装/gold 已通过就进入训练池。该留出方案目前仍是建议，不冒充已经完成正式切分。

本地 R2E Subset 有 4,578 条精简元数据，只有已选 24 条有完整记录。扩 E2 还需要从固定来源取回新增题的完整 gold/expected 信息或对应私有测试材料，不只是修改 ID 列表。

### 3.3 审计分深浅，避免“标签字段齐了”冒充逐题审清

接受全池结构检查与分批轻量 agent 初筛。先对约 24–32 题做完整需求—测试—执行对照，包含已知反例、正常通过题与随机未报警题，测量漏检、误报和成本，再扩深审。

如果用户希望把现有 216 题全部深审，可以作为额外投入选择；但每题几分钟的预估未证实，不能宣称低成本完整覆盖。标签先存旁路审查记录，包含范围、理由、证据与不确定性；暂不修改生产 manifest、加入拒绝轨迹逻辑或据标签自动排题。

### 3.4 优先复用现有网络与初始工件边界

赞同新求解前关闭上游答案下载通道，但不建议先造第二个“小转发器”。现有 rh2 rollout profile 已有私有 internal 网络、阻断宿主直连的网络安排、固定上游 relay 和启动探针。先验证能否复用，确有 API 协议差异时才作最小适配。普通 `--internal` 加一个转发器不能直接称与正式边界同构。

`git status` 只列状态，不保存原始文件内容，不能单独支撑增量工件重建。应复用现有基线机制，记录预置 tracked diff 与必要的 untracked 内容，明确源码和依赖覆盖层，验证导出的候选没有混入原镜像变更。仅 HEAD 正确不够。

2. 七个工件已经含 MONAI-2454、pandas-48106，不应在“七个再加”中重复计数；modin-6937 是可额外加的网络对照。
3. OpenAI 138 题是 o3 多次运行“未稳定解决”选出的审查子集，不是全部稳定失败；59.4% 不能外推全池。N13b 的四分类适合作起点，但应保留环境、parser 和其他类别。

## 5. 现在需要用户决定什么

### 建议本次明确的三项

| 决策 | 推荐方案 | 代价/替代 |
|---|---|---|
| 执行范围 | 批准真实评分小包、资源观测与增量镜像盘点；新增候选上限 SWE-Gym 256 / R2E 128，先各 32–64，首段评估后在上限内继续 | 较原稿扩大上限，但不一次盲跑；若只想尽快完成首个诊断池，仍可止于 64+64 |
| 实施分工 | B 负责来源专属 parser/命令适配、候选材料与实验驱动；共享 grader/profile 改动与 A 同一批对齐，明确单一修改者 | 已定官方评分的等价接入可按 T1 执行；正式来源 schema、评分定义、安全/默认资源边界的变化不能全包成 T1 |
| 审计投入 | 全池轻量初筛 + 首批 24–32 题执行深审；暂不新增 DeepSeek 调用、registry 服务、通用变异系统 | 全 216 题深审可另选，需要明确更高 agent/人工投入；轻量标签不代表验收完成 |

### 不必重复决定、或应留待具体证据的事项

- **deny_all**：正式 grader 已批准；将来源探针按正式断网条件验证是在落实既定目标，不重开“是否允许候选公网访问”的讨论。是否现在执行全 216 题离线轮，属于本次运行范围选择。
- **共享内存测量**：在探针中测 1 GiB 等参数，是校准实验；正式给 rollout/grader 多少内存、共享内存、超时，取得测量后再给具体配置建议。新增内部参数本身不自动是 T0，改变公共契约或明显影响覆盖的正式阈值才需按协议升级；不能以“只是加字段”掩盖这些变化。
- **参考 ID 与不可 FULL 的 12 题**：先逐类给出原 ID、实际日志 ID、解析差异和执行对照，之后讨论修正还是排除。本轮不需要凭数量先选去留。
- **DeepSeek**：复用边界并完成工件基线检查后，再提出具体题单、次数与金额；现在不需要批准泛化的“持续筛题”。
- **迁移用例数量与输出目录**：属于实现选择，按风险覆盖及实测耗时调整，不必把 12 对 24 或文件命名升级成 owner 决策。

角色和 T0/T1 的判定依据是现行[协作协议 §2](../../collaboration-protocol.md)，其中落实已确认语义是 T1，修改公共 schema/重要依赖/评分与系统性筛除规则需另辨认。本次提出的是合并方案，不因文件里写了“T1”就自动取得新业务语义的授权，也不为已有授权增加确认。
