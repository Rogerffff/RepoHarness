# 分阶段实施计划审查与阶段一建议执行卡

日期：2026-09-10；B / Codex。受审文件：[分阶段计划](cpu_followup_stages_20260910.md)。本轮审查计划、既有 runner、数据与 A 最新评分决策说明；未执行探针、付费模型或生产修改，未提交推送。下面的执行卡是待用户确认的建议，不是运行授权。

## 1. 判断

**同意拆成独立批准的阶段。阶段一不应等待题目质量筛查设计，批准阶段一也不批准后续任何阶段。** 阶段内可完成已说明的小步、归因与收口，不逐命令申请；涉及后续阶段或改变评分/选题/资源正式规则，再按相应阶段讨论。

Claude 保留“一次全 216 题离线 empty/gold”有独立诊断价值，我接受。此前反对的是将内存、离线、共享内存与真实评分默认拆成多轮全量跑数；现在内存观测合入离线一轮，不需为此继续争论。此轮仍是上游 runner 的环境证据，不能代替正式 rh2 验收。

**原稿不宜直接写成无条件可执行**：阶段一的共享内存范围、日志隔离、对照条件、停止规则和结论口径还需收紧。以下给出可直接供用户审查的版本，不要求用户现在决定后续阶段。

## 2. 阶段一应先修正的五点

1. **MONAI 范围自相矛盾。** §0 写“MONAI 只跑短对照”，1c 却写 26 题完整 gold 各一次，763 上限 1,800 秒。给完整评分设置上限仍是完整评分尝试，并非短复现。建议 1c 只保留已定位的 MONAI-763 短 DataLoader 对照；其他题若 1a 暴露共享内存疑点，登记到阶段二的针对性校准，不默认再跑 26 题。
2. **不同条件必须隔离输出与任务命名。** 现有 `swegym_probe.py` 的日志路径为 `out/logs/<iid>/<gate>/<variant>/a<attempt>`；恢复键是 `iid|gate|variant|attempt`，容器键也不含 shm/内存参数。只换账本文件名不会隔离原始日志，同一 `offline/gold/a1` 的 64 MiB 与 1 GiB 运行还会复用名称。按独立 run 输出目录与条件名称保存，不复用昨夜 `a1`，资源对照不同时以相同容器名运行。使用现有目录参数和一个实验条件标记即可，不引入新存储平台。
3. **比较逐测试状态，把网络敏感视为待确认判断。** 最终同为 NO 的两次运行，也可能有新增或消失的失败。先比较 F2P/P2P 的逐 ID 状态、缺失、测试阶段、退出与资源事件，额外测试差异旁路记录。一次离线变化是“条件相关差异候选”，不是全部网络因果已证明；后续只对需要解释的差异作同配置对照，不改参考答案。
4. **对照条件应明确，观测读数不能改名。** 1a 保持前轮的 root、3 CPU、8 GiB、64 MiB shm、官方安装与测试脚本，仅改变网络并增加观测，实际参数与代码版本入本轮记录。`memory.peak` 可用时在容器删除前读取，注明是否包含安装/测试整个生命周期；不可用则标缺失或采样峰值，不能填零或改称精确 RSS。8 GiB 限制下测得的峰值只是阶段二的校准输入，不是已经证明正式 4 GiB 足够。
5. **“翻转超过 20 题”“普遍超过 4 GiB”不宜直接作为停工判据。** 这些是本轮要观测的现象，数量本身不证明运行无效。可标为汇总讨论项；真正停止应针对无法产生可信数据的配置/parser/镜像问题、宿主资源异常或明确预算上限。无解析、超时、OOM、未完成均保留原因，不因总分为 NO 就登记成正常负例。

“不改代码”应改为“只允许为实验 runner 增加参数与观测，不改 rh2 生产代码或官方评分语义”。加参数和采集逻辑确实属于代码工作，属于本阶段应说明的小范围实现。

## 3. 阶段一建议执行卡（待用户确认）

| 项目 | 建议范围 |
|---|---|
| 目的 | 补离线评分结果、资源使用与已知共享内存问题的输入证据；不选训练题、不改变 reward、不裁决题目是否公平 |
| 主批 | 原有 216 题，fresh 容器 empty/gold 各一次，共 432 次评分尝试；使用固定上游 fork、脚本、数据与镜像身份 |
| 主批条件 | 断网；其余先沿前轮 root / 3 CPU / 8 GiB / 64 MiB shm；每题脚本预算沿前轮显式设置，不悄悄变为正式 rh2 profile |
| 起跑核验 | 先少量代表题确认参数、评分脚本、日志、资源观测与回收可用，再在本阶段批准范围内继续全批；不重复请求批准 |
| 共享内存 | MONAI-763 已保存的短复现，64 MiB 与 1 GiB 同工作负载对照。短复现有单独上限；不自动扩为 26 题完整 gold，不宣称 1 GiB 已通过完整评分 |
| 资源观测 | 同主批采集内存峰值/采样口径、OOM、退出、耗时；容器删除前取回。必要的 runner 参数与采集改动独立记录 |
| 输出 | 新 run 目录；主批和 shm 对照不同条件名称；原始脚本/日志/状态表、逐任务结果、基线差异、资源分布与一页汇总；完成后同步本地 |
| 初始预算建议 | 先用已租 CPU 实例；约 4–5 小时仅为旧数据外推，建议首轮墙钟上限 6 小时。到点停止新增调度、有界收尾与清理，记录未完成任务；不自动扩机或续开下一批。实际费用按当前实例费率核算，不承诺小于 $1 |
| 阶段产出判据 | 每个已调度任务都有结果或明确中止记录；计划 432 次的完成数/缺失数可对账；日志可回读；差异按测试与资源原因分开；不要求所有 gold 都通过 |
| 不包含 | 正式 rh2 parser/投影修复、正式 profile 改值、扩新题、题面/测试更改、全池语义审计、付费模型求解、自动排题 |

如采集工具不可用，先在小批修正或明确降为采样观测，再继续；不能在整批结束后才发现资源数据全部缺失。无法建立可信基线或相同配置持续系统性失效时，保留证据并暂停受影响类别，其他独立任务可继续。

这张卡可以单独确认。批准它不要求同时批准共享内存正式值、parser 修改、数据扩容或后续题目筛查。

## 4. 后续阶段的预约问题（不阻塞阶段一审查）

- **阶段二不宜整体定为 T1。** A 新的[第四组评分决策](../batch4_scoring_20260910/README.md)仍有候选执行失败、投影边界等未定语义。按既定官方定义接入 parser/命令可作为实现；新来源契约、共享投影、错误分类和正式资源变化需在阶段二分别说明。原始任务包应保留官方安装/编译与测试选择，不仅复制两个 parser 文件。不能把 workspace 路径通过当作正式 frozen-delta 投影闭环通过。
- **阶段三不应要求先拉齐全 216 个镜像。** 上次磁盘只剩约 463 GiB，而作者最新容量仍是 0.6–0.8 TB 的未验证外推；“一次拉齐来量落盘”没有已证可用容量支撑。先做增量层清单与工作集测量；必要的完整实测等容量明确。制作环境包也不必等待选定八卡机或重新批准已经暂缓的 registry。“20–40 分钟”继续作为目标，不能称已证明。
- **阶段四的 R2E 计数仍有矛盾。** 本地固定 Subset 的十仓中确有 `pyramid`（189 题）与 `tornado`（261 题）。若把它们保留为评测仓，就不能同时要求训练候选 E2 覆盖十仓各三题。阶段四应明确哪些是训练候选、哪些仅资格检查；留出方案本身尚未批准。
- **阶段五保留为待详细设计。** “24 个候选 + 13 个通过题”含重复；扩展测试选择、审查上下文、抽样和复核判据仍需另审，当前不背书这些细节。仅改 relay 上游是否足够，要届时用协议与实际访问验证。
- **阶段六应是按证据就绪分别讨论的决策清单。** 资源配置未必需要等整个阶段五，参考 ID 归因也可先于全池语义审计完成。不要让用户为处理一个已具备证据的问题等待所有质量审查。
- **并行不等于授权。** 最后“2a 可与阶段一并行”“E2 可并行”应补为“对应阶段已分别获批时”。只批准阶段一时不启动 2a/E2；没有任何技术依赖要求用户一次批准多个阶段。

## 5. 当前连接状态与核查边界

本轮使用此前同一专用 SSH key 对原地址做了两次只读连接，均返回 `Connection closed ... port 57541`；未进入远端 shell。因此没有核实当前实例费率、磁盘、kernel/cgroup 或 `memory.peak` 可用性，也不据此断言实例已关闭。执行前须恢复连接或取得新地址；当前计划审查不受影响。

本轮静态核对的是日志/恢复键及计划边界，没有运行新 black-box CLI、评分或训练，不宣称上述 runner 参数修改已实现或任何新条件已经通过。后续实现只需与其实际变更范围相称的检查。
