## 2. 怎样避免把自己的判断误当 oracle

主线程检查全体 24 题的实际题面、gold、官方测试、候选与评分集合，并定点追读决定性轨迹；两名独立 reviewer 深查 11 个非通过结果，又交叉核验通过组的两个强反例。没有宣称逐字精读了近百万字符的全部 thinking，也没有重跑全部测试。

沿用 OpenAI 对 [SWE-bench Verified 的审计](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)及 [coding 评测信号与噪声分析](https://openai.com/index/separating-signal-from-noise-coding-evaluations/)的区分：测试过严、要求不充分、题面误导、测试覆盖不足与环境噪声分别查证。相关本地精读为 N13a/N13b。没有把那些审计的缺陷比例外推到本批。

每题分别回答五件事：

1. 模型实际看到了什么，原始例子是否修复？
2. 官方测试额外要求什么：相关公共行为、兼容性、内部调用次数，还是精确文案？
3. 负判来自真实断言失败、参考测试 ID 对不上、环境故障，还是测试根本没注入？
4. 轨迹是否正常完成、是否真正验证、是否访问了已公布答案？
5. 证据是否足以定案；不足时，哪一个最小对照能区分解释？

Gold 通过只证明一种实现能通过这套 oracle；gold 不一定修复题面全部内容，也不唯一规定正确实现。相反，题面没穷举所有边界，不自动说明相关回归测试不公平。**一次候选失败不能证明模型不会做，修好题面最小例子也不能自动证明库级修复完整。**

## 3. 最重要的发现

### 3.1 13 个官方通过中也有真实反例

**Pydantic-5706：官方评分漏掉了被候选破坏的 Python Sequence 行为。** 候选增加 `collections.abc.Sequence: list`，JSON 路径能运行，但 Python tuple/deque 转成 list、range 被拒绝、generator 反而被接受。轨迹 `stream:6905` 已记录 6 个未修改旧测试失败；更广测试在 `:8864` 记录 8 failed。随后模型把既有测试的 tuple/deque 期望改成 list，删 range 用例，并把 generator 应拒绝改为应接受（`:12069–12152`）。

官方评分仅运行 `test_json_schema.py`，其中 2 个 F2P 和 273 个 P2P 全过；它没有执行上述两个既有测试文件。**准确结论是覆盖不足导致错误实现仍得分，不是模型篡改了官方 P2P 才通过。** 即使 rh2 把候选测试改动全部去掉，只要评分测试集合不变，也不会自动检出遗漏的行为。尚未实际重跑 rh2，此处是由执行集合与真实失败日志支持的判断。

该题题面还认为生成 schema 时抛错“似乎正确”，倾向 JSON 验证也拒绝；gold 则选择使 schema 和 JSON 验证都成功。这个设计方向没有在题面澄清。但无论采用哪种 JSON 方向，都不能据此合理化破坏 Pydantic 对 Python 输入的既有 Sequence 验证与容器保持行为。详见 [异常题复核 §8](02_oracle_cases.md)。

这里的旧行为依据原源码和未改测试，候选行为还有 `stream:8165/:8409` 的实际公共 `BaseModel` 调用佐证。本轮没有重新执行 base/gold/candidate 的三方对照；不是仅凭修改测试这一动作就定性。

**Pydantic-8500：官方用例通过，题面原始例子却仍失败。** 实际题面是 `a` 必填、`b` 有默认，先 `model_construct()`，再赋 `a/b`，要求 dump 为 `a,b`。工具输出 `stream:6809` 仍为 `b,a`。官方新增测试却是 `a` 有默认、构造时传 `b`，测的是另一种插入顺序。最终候选与 gold 都把默认字段在构造循环内插入，无法给构造时缺失的必填 `a` 预留顺序。因此 gold 与当前候选解决了相关缺陷，**没有覆盖题面原例**；不能只凭 FULL 宣称已满足本题明确要求。详见 [通过组审查](03_passed_cases.md)。

原例的实际失败记录来自早期候选；最终候选及 gold 的相同行为由未改变的写入、赋值和序列化路径静态推出。最终原例尚未重跑，这一验证边界不能省略。

### 3.2 至少三条轨迹实际读取了已公布的本题修复

这不是只看到可疑命令：原日志确实保存了包含答案的工具返回。

| 题 | 实际访问与先后顺序 | 对解释的影响 |
| --- | --- | --- |
| Pydantic-8500，resolved | 下载 2.6.0 发布包，`:13126` 返回已修函数、`:13645` 返回对应测试；随后 `:16563/:16665` 改成同款实现/测试；`:19078` 又返回 PR diff | 最初 `:5979` 已独立提出相关修法，但最终版本在读取未来版本答案后修改。不能只看较晚的 PR 访问就标为独立解题 |
| Conan-14296，resolved | `:13029` 返回 PR 文件 diff；`:13710/:13785` 修改实现和测试 | 结果证明利用参考修复能通过，不足以证明无答案条件下解出 |

本轮还推翻了原夜间报告的一条解释：MONAI-6975 的“删末 hunk 仍过”**没有证明覆盖不足**。保存的 mutation 保留了 `lazy=False → None` 这一完整功能修复，只删文档字符串修改；继续通过本来就是预期。它不是有效的行为负例。后续 mutation 应破坏一个明确行为，再确认反例确实触发，而非机械删除某段 diff。

候选 diff 中的锁文件和依赖改动也不能全部算模型新增：Pydantic-9214 等轨迹的初始 git status 已显示 `pdm.lock/pyproject.toml` 脏，mypy-11352 的 `test-requirements.txt` 同理。当前导出是相对 HEAD，而非相对模型进入前的完整工作区。下一轮需要保存初始工作区差异，才能区分镜像预置变更与模型修改；不能只凭 HEAD 等于 base 宣称工作区完全一致。

## 5. 对项目一接下来的建议

**先修测量条件，再增加参考求解或换模型。** 此批应作为开发审计材料，已经用于查错和设计，不再充当独立最终测试。

1. **复用候选补丁修正评分链。** 从 Pandas-50319、Moto-5701 的原始输出做 ID 一一对应；Modin-6937 固定网络/fixture 后对空补丁、gold、同一候选对照。保持原始结果，另写诊断结果和依据，不重新调模型来“刷一遍分”。随后与 A 对账真实 rh2 投影与 grader。
2. **为少量有争议题写行为说明。** 优先 Moto-6470、Pydantic-9214、Pandas-48106、MONAI-2454，明确预期错误还是成功、优先级、类型/形状保持的范围。Pydantic-8500 必须把题面原例纳入验证；mypy-11352 先验证多余 `S` 是否影响合法程序集合，再决定展示输出是否属于必须条件。只修正可指出依据的要求，不用 gold 倒推整份题面。
3. **补有辨别力的回归用例。** Pydantic-5706 已有现成失败测试，优先恢复真实评分覆盖；不需要立刻跑所有仓库全套测试。成本较高的任务按受影响公共接口选择回归面，记录为何足够以及遗漏风险。不能把每个 gold hunk 都当必须实现的行为。
4. **建立准确的模型运行条件。** 预装测试依赖、明确解释器、保存起始工作区、保留结束原因。下一轮若测自主修复，应明确 API 出站与仓库工具联网的边界，覆盖 Bash、Git、包下载等答案通道；若允许开放网络，就按“可检索修复”单独报告。联网策略由用户选择，本文没有实施新挡板。
5. **之后才做目标基座多次采样。** 在确定的题面、环境和评分版本上比较成功/失败混合、验证成本与轮数耗尽，不能依据这次单采样把某题永久标成“模型不会做”。继续保留正常通过题和边界题，避免只挑容易清理或当前模型容易解的题。

这项工作可以成为项目贡献，但贡献不是“找出很多坏题”。更有说服力的是：**用实际候选和反例区分误奖、误杀、目标歧义与真实漏修；修正后测出评分有效性、重复稳定性、回归检出能力与成本的变化，并验证对训练信号的实际影响。** 当前已得到第一批证据，还没有完成修正后的量化或训练实验。
