## 4. 机器怎么用，脚本结果能说明什么

**建议先用现有机器继续 P-B/e2；如你提供新机器，再用 1–2 台承担③/④及必要的测试收集。** 静态审查 agent 可以多于机器数，不必一人租一台。每台先从一个评分/构建作业开始，核对 RAM、磁盘、shm 和进程占用后增加并发；重编译、MONAI 与轻量 Python 测试分开排。机器数和并发可随队列调整，不在本文写死全池配置。

镜像、包、权重均由远端直接拉取；只拉分配任务需要的镜像，尽量按仓库复用层。每包独立容器名、输出路径、代码/配方变体；共用机器的并发由主会话统一分配，不热改正在运行的代码、不全局 prune。RH2 补丁按[既有 worktree 安排](environment_screening_pilot_20260915.md#4-真机发现-bug漏洞或低效时怎样试补丁)隔离，原评分实现者负责共享代码合入。

**一项已知的机器限制必须沿最新记录处理：**当前旧机器的 metacopy/native-diff 组合曾使 `chown → docker commit` 导出内容变为全 0。不能把旧“开启 metacopy”指令复制成新机默认；做派生镜像前验证实际构建/导出路径和重新启动后的内容。见[e1 复核 §2](swe_grading_wiring_20260915/e1_codex_review_20260916.md#2-一个需要立即修正文档的真机问题)。它不推翻未经过 commit 的普通评分结果。

每条结果标清验证方式与条件：

| 方式 | 可以支持的结论 | 后续仍要补什么 |
| --- | --- | --- |
| 静态分析 | 已有代码/规格关系、具体疑点和实验假设 | 实际运行；无法由静态证据确定时保留未知 |
| 直接行为实验 / 固定版本的来源 runner | 某条件下的行为反例、依赖修复、测试身份与来源结果 | 真实 RH2 投影、权限和评分配方下的同工件复验 |
| 当前 RH2 driver | 记录所注明版本和条件下的实际冻结/投影/评分结果 | 受 P-B/P-A/P-D 等变更影响时复验；不外推未测来源或正式训练验收 |

直接脚本实验优先复用已有 runner、来源命令和 parser，只补必要观测。保存 base/gold/candidate、实际测试命令、状态、日志与条件，日后将同一反例交真实链对账。题面或测试修改留独立提案；网络需求可调查，但不自动扩大既定 agent/grader 权限。需要新语义才能继续的题暂存，转做其他题。

**新增完整解题暂非优先。** 先完成已有反例的实验。只有某个公开工作流或可解性疑点确实需要实际尝试，才安排少量、明确条件的独立求解；看过答案的调查补丁不计自主成功，旧 DeepSeek 结果也不作为 Qwen 能力成绩。
