## 3. 持续题主和单卡执行怎样协作

| 角色 | 负责到底的事情 |
| --- | --- |
| 同仓题主 | 调查、修订、CPU验收、申请探针、阅读返回的完整轨迹和补丁、必要复修、最终用途结论。申请提交和探针结束都不算题目完工。 |
| 本线程／统一执行者 | 跑通并冻结共同链路，维护模型服务和单卡队列，执行、评分、保全证据，完成或异常后通知原题主。同时持续负责原12题和已接收5题。 |
| 公共代码维护者 | 处理超出探针脚本的公共契约／安全／生产链修复。本线程负责定位、交接和恢复验证，题主不各自热改共同入口。 |
| 非作者reviewer | 核题目修订依据、关键控制和重要用途结论；按变化复核，不对每题重新进行同一套从零阅读。 |

模型求解永远使用独立干净上下文和公开材料；知道gold的题主不能充当该题solver。

建议从最小队列开始，不建立新的大型调度平台：

1. **题主只提交自己的请求文件。** 必须带任务ID、材料／镜像／配方版本、原题主线程ID、调查目的、CPU验收证据和统一配置引用。不把私有调查资料放进solver输入。
2. **只有统一执行者写队列状态。** 唯一作业ID绑定题目版本、模型配置、尝试序号；持久记录待运行、运行中、证据收口、已通知。重复通知不重复运行，执行者重启先检查真实进程和已有结果。
3. **GPU初始一条求解会话。** 同一模型连续处理已就绪小包，避免每题换模型；已结束求解的CPU评分可以在有资源时与下一题重叠，完整评分与清理后才发送完成回执。共享链路出现可信性异常即停相关新派发。
4. **运行结果立即回原题主，不等整批报告。** 回执含完整轨迹、原候选、评分、实际预算和版本、异常／清理状态。题主分析期间可继续运行其他已就绪题，避免GPU等长报告；分析积压超过题主承接能力时优先换已能审阅的题主小包。
5. **代码更新形成新版本。** 先停止受影响的新派发，在途作业按影响保存或正常收口；验收新版本后恢复。禁止热换代码、重指在用镜像tag或改写旧结果。题级材料更新无需暂停无关题目。

通知只发本批已登记的题主／相关执行任务。用户已经授权这类结果通知；不扩大成通知其他人。串行派发和文件回执已实施，见[提交与回执](gpu_queue_handoff_20261003.md)。线程通知由本线程核完证据后执行，不能把回执中的待通知字段当作已经送达。

| 项目 | 当前约定 |
| --- | --- |
| 模型 | Qwen3-Coder-30B-A3B-Instruct、Qwen3.6-35B-A3B，BF16，一次驻留一个；先Coder，再让3.6跑相同的已就绪题。DeepSeek用于有明确价值的争议对照，不自动每题三模型。实际checkpoint摘要随部署冻结。 |

### `probe-wide-v1`：单次求解预算

| 参数 | 目标值 | 解释 |
| --- | --- | --- |
| 总上下文窗口 | **196,608 tokens** | 包括实际输入和本次输出空间，不是允许输入占满196K。服务、adapter、CC感知窗口及token计数须一致。 |
| 单次模型响应输出 | **65,536 tokens** | 包括该响应的思考及可见输出；是每次响应上限，不是整道题累计生成上限。实际请求和SGLang生效值必须回读，不能因只设置了环境变量就宣布64K生效。 |
| CC回合 | **240** | 比首轮60和上轮120留出更多探索空间；与HTTP请求数不同。正常完成即收口，不要求跑满。 |
| 求解墙钟 | **10,800秒／3小时** | 从solver启动起计，覆盖工具操作、编译和公开验证；镜像准备及事后评分另计，不用准备耗时提前消耗模型求解预算。 |
| 网关生成请求护栏 | **1,024次／会话** | 给240回合及压缩留余量；当前网关只计`/v1/messages`，不计`count_tokens`。不沿用旧180次形成隐藏的提前截断。异常触发需单列原因，不混称模型正常失败。 |
| 无上游数据的HTTP等待 | **1,800秒** | 传输层等待，须覆盖长prefill／生成，仍受求解总期限约束；不以这个数控制每次普通Bash命令。 |
| adapter空闲回收 | **至少14,400秒** | 避免旧40分钟回收在长CPU工具操作期间丢会话；这是会话保留参数，不是GPU工作窗。已结束会话按实际收尾主动释放。 |
| 评分及准备预算 | 沿每题已验配置 | 分别记录setup、安装、test、whole和cleanup；外层等待覆盖其真实生命周期。需要增加的题单独解释，不给全池盲目统一改时限。 |

不另设整道题累计输出token硬上限，不把一次压缩当作失败。需要在新链上验证主动／溢出后压缩能继续工作，不能一触及上下文就交空补丁结束。若正常预算仍耗尽，先保存候选与完整轨迹；有可靠候选可以按原规则评分，并标明预算受限。题主再判断是否做一次有目的的扩大预算对照，不自动续跑所有触限题，也不把基础设施截断补成0。

**选择这些值的依据：**首轮67次尝试有17次触及60回合；其中存在截断仍在推理的情况，不能断言全是无效兜圈。旧Qwen单次输入峰值约77K；最近四条DeepSeek最大输入约21K–50K、完整求解约171–335秒，未观察到结构化压缩事件。196K／64K／240回合／3小时为后续不同题目及工具路径留裕度，不是从四条短轨迹推导出的必需资源，也不能保证所有题永不触限。依据：[首轮运行与完整轨迹分析](../base_model_probe_run_20260922.md)、[最近四次回读](../../../../../runs/ordinary_probe_20260930/diagnostic_batch_v1/cost_context_readback_v1.json)。

9月22日两款BF16模型在96GB单卡只实测过131K，**196K新档位尚未GPU验证**。租用应为RTX PRO 6000 96GB档；先做显存、长请求和压缩恢复小检查。若实际无法稳定承载，记录原因与可运行共同档位，不在正式作业中悄悄降上下文、改量化或让两款模型使用未声明的不同限制。具体部署适配由本线程处理，不把每项参数重新交给用户拍板。

模型模式不同，不伪装成相同内部计算：Coder为非thinking；3.6采用thinking，使用经共同链路确认的思考运输政策。采样按对应模式固定，不做网格；温度、模板、思考保留和截断配置随实际部署一起冻结。官方依据：[Coder模型卡](https://huggingface.co/Qwen/Qwen3-Coder-30B-A3B-Instruct)、[Qwen3.6模型卡](https://huggingface.co/Qwen/Qwen3.6-35B-A3B)。上述共同预算是项目配置，不冒称两张模型卡的统一推荐值。
