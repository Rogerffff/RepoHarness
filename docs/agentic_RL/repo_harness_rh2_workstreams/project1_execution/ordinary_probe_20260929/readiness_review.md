## 1. 可以使用 CPU，无需为 API 推理租 GPU

DeepSeek 在服务端推理；本机运行 Claude Code、解题容器、编译与测试，再由独立评分容器评分。我们已有09-22真实 API 工具往返经验，本轮可以复用其网络结构，不能直接沿用其旧运行脚本和结果口径。

官方提供 [Anthropic 格式接口](https://api-docs.deepseek.com/guides/anthropic_api/)。模型必须显式指定并回读：官方文档说明未知模型名会回落到 `deepseek-flash`，不能把 CC 的内部模型别名当作实际调用了 Pro。建议延续此前对照的 `deepseek-v4-pro`，记录发送值、响应值、日期与实际用量。`thinking.budget_tokens` 不被该兼容接口采用；不能用它代替输出、请求数、时间和费用边界。

这批首先回答“题目是否支持真实求解、分数是否可信、DeepSeek 如何使用工具”，不能据此决定尚未运行的本地基座型号，也不能视为 miles 训练运输、token/logprob 对齐已经验证。

## 3. 开跑前必须收口的接缝

### A. root仍会执行模型可改的Git配置

当前 [`quiescence_barrier.py`](../../../../../rh2/src/repoharness2/adapters/slime/quiescence_barrier.py) 的 `_digest_script` 在终止agent之后调用仓库内 `git status/diff`。SWE旧 `solve_attempt.py` 的状态读取、`git add -N`和diff导出也以root执行。可信PATH只限定Git程序本身，不能禁止它读取候选仓库中的hook/filter配置。

已有[独立审查](../r2e_lifecycle_20260929/codex_reviews/review_probe_chain_20260929.md)和一次性容器uid=0证据；本次重读当前源码，执行面仍在。后果是容器内权限与私有材料边界受破坏，**没有宿主逃逸证据**。

应先修公共屏障及探针中的对应调用，再让真实模型进入。建议复用可信的文件普查与内容指纹，避免模型结束后又以root运行仓库Git配置；验收要覆盖配置诱导执行、忽略文件、mode与软链变化。不能仅加两个Git开关，或直接降权后允许重新产生后台写者。负责范围：公共实现由A线收口，本线程核探针消费。未在本轮修改或通知A线。

### B. 两个数据源还没有统一接入可用的求解—导出—评分入口

- **SWE**：`base_probe_20260922/solve_attempt.py`仍以Git diff导出，忽略规则和文件mode处理与正式冻结导出不同。脏文件基线的F4窄问题已用物化快照修复，不能再说它完全未修；但这不是统一冻结导出完成。
- **R2E**：`r2e_lifecycle_20260929/r2e_solve_attempt.py`已有覆盖表、解释器预检、实际工作树基线和冻结产物导出，普通题及编译产物已有CPU证据。它依然调用上述公共屏障。共用 `run_matrix.py`仍写死SWE求解入口和一个prepared summary，没有传R2E覆盖表；现成 `r2e_probe_e2e.py`是脚本化CPU验收器，不是已经上线的DeepSeek批量执行器。
- **材料消费**：不能只传题ID。mypy10308需评分侧 `materials_v2`；Moto5134需已验SDK开发配方；Dask6626需actor pytest7.4.4与对应离线grader配方。R2E9题必须逐题绑定实际修订材料和覆盖表，不能统一退回来源镜像或旧v3包。

改动应集中在一个派发入口和少量按来源分派的适配中，复用正式helper，不让各题维护一套runner。两侧均保留原冻结产物、重放结果与身份核对。

### C. 出错后停止派发、分数有效性仍未贯通

当前代码已经拒绝“导出失败冒作noop”和“求解侧清理失败继续派发”。**剩下的是另一段**：

- `run_matrix.py`只把grader退出码带回结果，评分之前就清零infra连续计数；评分fatal/清理不明不会可靠地停止后续任务，整个matrix仍可返回0。
- `r2e_probe_e2e.py`记录roundtrip和补丁摘要比较，但主流程及重评仍只按资源残留决定退出码。已有内存桩反例：不一致且grader失败，只要资源已清就返回0。本次源码形态仍如此。
- 共用solve在driver异常或预算结束后都可能保留 `result=ran`。不能把它当有效求解标志。要联合CC结束事实、完整轨迹、网关终局、冻结与评分记录判读；**预算结束但有合法候选不等于链路失败**，两者必须区分。

验收：人为注入导出/往返不一致、评分fatal、manager close失败、网关断流，核退出码、停止标记和下一任务确实未启动；普通0分和预算耗尽的合法候选按声明规则正常保留。恢复运行也必须检查这些状态，不能只找到旧账本行就跳过收口核对。

### D. 既知评分信任边界不能隐去

当前R2E渲染器文档明确：恢复隐藏测试和入口，不等于阻止仓库根conftest、导入期代码及同形stdout摘要影响结果；manager的测试样路径、runner摘要变化主要是诊断字段。numpy准入卡也注明 `numpy/testing/` 是候选可改的测试辅助代码。SWE此前已有stdout伪造的证据，最新infra记录未将它核销。

这不是本轮新做出的攻击实测，也不能外推为12题的历史分数已经伪造。但按用户“影响普通求解或评分的已知缺陷先处理”的最新规则，不能将这些具体已知路径以“求解后人工审计”一笔豁免。需确认已有处置是否覆盖本批，再对未关闭的可达路径做窄复验与修复；受影响题在关闭前不作普通能力比较。**不要求证明可以抵御任意恶意程序，也不把隐藏测试只读称为全面防作弊。**跨题公共边界单列，不在此静默重写第1类的题级分类。

## 5. 哪些已经修了，哪些可以稍后处理

**已有修复，本轮不重新列为未实现：**正式激活与子shell继承、五工具白名单、关闭auto-memory、轨迹宿主收集、G1临时目录执行权限、缺 `message_stop` 时中止下游连接、按真实SSE事件识别终局、导出失败不送noop、求解清理失败停批、旧dirty基线窄修；A线共用溢出400构造已经存在，Qwen探针adapter也已挂上。这里核对的是源码和既有验收，不冒称本轮已在新机器重新跑过。

**API首轮不必等待：**SGLang本地模型部署与EOS/tokenizer专用验收、GPU性能、miles训练闭环。DeepSeek绕过Qwen adapter，但仍要验证自己的工具/流/预算与压缩行为。官方接口支持不等于当前CC配置自动正确。

**R2E正式冻结直评暂不可宣称通过：**已有aiohttp反例中，条目相同但sanitize改变 `.git/logs/HEAD`，导致排除区摘要不同、正式直评fatal。若首轮按既有设计走“冻结→渲染→回放评分”，必须先落实第3节的往返硬检查，精确列明已知排除区差异；这是探针回放路线，不等于训练直评已修复。不能把整个摘要检查删掉或静默忽略其它差异。

## 6. 建议执行顺序

1. 本线程固定12题运行材料与公共缺口清单；公共root执行面及既知评分信任问题先获得明确修复/验收结论。第2类线程继续自己的题级修复，无需等待本线程全体完成。
2. 修正统一探针适配与失败传播，使用真实CC加本地桩端点做窄验收，先不花API费用；普通源码、初态dirty、构建产物和错误收口各覆盖必要分支。
3. 在目标CPU机核选中镜像与版本，分别用一条SWE、一条R2E做实际API冒烟。先读完整轨迹、候选与评分，再扩到其余第1类题；模型与预算须在运行清单中先固定。
4. 每小批立即分析0/1/infra，任务新问题回交相应负责人；不等12题全部跑完才读轨迹，不因此自动扩到第2/3类。

本轮没有启动容器或模型批次，没有付费调用、生产代码修改、机器暂停或提交推送。机器原件与代码摘要保存在本线程独立目录，供下一步复用。
