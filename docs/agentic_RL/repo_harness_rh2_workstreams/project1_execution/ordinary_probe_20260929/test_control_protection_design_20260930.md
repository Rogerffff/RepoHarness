## 1. 本轮结论、保证边界与已证实范围

先看执行摘要：

| 遇到什么 | 默认处理 |
| --- | --- |
| 普通题的测试控制文件 | 解题时可以调试；评分副本恢复可信内容，完整原始改动留档。 |
| 候选新增控制文件或安装过程生成 hook | 重新扫描评分范围；不能只覆盖旧文件。 |
| pytest 配置或插件发生变化 | 按实际pytest版本核对允许的加载入口；保留正常构建字段和产品源码。 |
| 题目本身要求修改 fixture、插件或配置 | 采用题级例外，保留相关实现，另用固定驱动验收它的行为。 |
| 同仓同版、相同启动方式再次使用 | 复用清单与已有验收，只核本题目标冲突、材料差异及实际摘要。 |
| 真实试解暴露新的路径 | 回到原题定向处理；不重复全池检查，不把旧分数直接当作正确性结论。 |

建议维护一份**与仓库版本和实际测试启动方式绑定的可信控制清单**，评分阶段使用它重建测试控制，保留候选产品实现、合法构建改动和原始候选证据。清单既记录存在的可信文件，也记录哪些位置应没有控制文件；每次应用候选和安装结束后重新扫描控制名字，不能只恢复原清单中的几个文件。

最先可实施的候选切片是 Scrapy e938 已证实的 exact 根 `conftest.py` 恢复。通用扫描、混合配置、插件集合和安装后恢复分期实施、按相关入口验收；不能要求所有 DeepSeek 诊断题等通用方案完成才继续。尚未覆盖的入口可以继续跑明确标注的诊断，不把受影响分数当有效比较结果，也不把题目从计划分母静默删掉。

继续诊断必须有独立可审的候选、原日志与行为依据，能说明实际观察到什么；“diagnostic”不是信任坏分的理由。已知控制缺陷若使本次观察本身无效，就只停该题的相关观察/分数采信，先换可信行为对照或修该入口；其它可审题目继续。不能用暂停所有题替代这个判断，也不能用诊断标签掩盖已知无效结果。

两条边界直接可见：

- **评分前恢复不等于阻止运行中的所有动态注入。** root/sticky 能保护已存在的 root 文件，却不能阻止在空名字上新建文件。新路径的补丁与安装产物应本期处理；任意被测 Python 在测试期间新建 hook、修改 pytest 内存或伪造 stdout，仍是声明的残余。若某固定入口实际出现这一新故障，只停该入口采信并处理该接缝，不无限扩展对抗测试。
- **可信测试控制不是整个依赖图。** 测试控制专用 helper 可冻结；被测产品模块、`setup.py` 和合法共享 helper 不因被控制文件 import 就全部恢复。否则会抹掉正常解答。

## 2. 可信清单的来源、版本和复用

版本依据首先用 [pytest 8.3 插件文档](https://docs.pytest.org/en/8.3.x/how-to/writing_plugins.html)，与本题实际版本对应：pytest 启动会处理 `-p`、内置插件、已安装的 `pytest11` entry points、`PYTEST_PLUGINS`，再加载初始 conftest；conftest 与测试模块中的 `pytest_plugins` 可递归加载更多模块。初始发现涉及测试路径的父目录与 `test*` 子目录，收集过程中还有更深的 conftest。因此不能把“当前磁盘上存在的根 conftest”当完整入口清单，也不能只在 `pytest_configure` 之后才检查：部分不可信模块届时已执行。

[8.3 环境变量文档](https://docs.pytest.org/en/8.3.x/reference/reference.html#environment-variables)确认，`PYTEST_ADDOPTS` 会进入参数，`PYTEST_PLUGINS` 可加载插件；`PYTEST_DISABLE_PLUGIN_AUTOLOAD` 只关 entry-point 自动加载。它不关闭内置插件、显式 `-p`、conftest 或 `pytest_plugins`，也不保证显式模块名解析到可信文件。

[8.3 配置文档](https://docs.pytest.org/en/8.3.x/reference/customize.html)确认，配置选择依赖路径、祖先目录和优先级；`pytest.ini` 即使为空也有优先级，`pyproject.toml`、`tox.ini`、`setup.cfg` 也可承载 pytest 配置。`rootdir` 影响 nodeid，却不限定 Python import 搜索路径。使用 `-c` 会影响 rootdir，不能把私有配置搬到仓库外却忘了保留原 nodeid 基准。

[8.3 import 文档](https://docs.pytest.org/en/8.3.x/explanation/pythonpath.html)说明 `python -m pytest` 和 `pytest` 的搜索路径形状存在差别；模式和 cwd 也会影响模块来源。清单因此必须固定解释器、启动形态、cwd、import mode 和允许的搜索路径，不能仅凭插件名称相同复用。

另核 [当前 stable 配置文档](https://docs.pytest.org/en/stable/reference/customize.html)：pytest 9 新增 `pytest.toml`／`.pytest.toml` 等行为。**不能把当前 stable 的名字和优先级直接套给 8.3 或旧 SWE 镜像**；扫描器由实际版本适配器提供配置候选名及选择算法。

以上是入口事实，不是建议改变来源 parser、expected map 或 reward。

### 2.1 清单的可信来源和内容

#### 可信来源

可信字节来自**模型运行前的固定评分基线**：明确 base commit、实际镜像 ID／digest、已批准环境配方和评分材料版本后，取安装准备完成的可信快照。必要的官方测试补丁／R2E 隐藏树恢复必须先纳入这份基线。上游 Git 原文不是唯一来源：环境修复、隐藏测试搬迁后的固定控制可能与上游不同。

Scrapy 原公开快照只能帮助定位；九组已从实际镜像读回根文件并确认 SHA。以后换镜像或配方必须重新比对，不能因为仓库提交相同就默认相同。可信内容存于私有材料目录或只读挂载，**不从候选工作树、候选 Git、候选安装输出或可改的 tag 导出**。root 不启动候选 Python 做验证；只按固定路径读文件、元数据和摘要，避免 `sitecustomize`、安装后的 import 钩子先运行。

#### 最小清单结构（私有 sidecar，不是本轮公共 schema 变更）

| 项目 | 必须记录的内容 |
| --- | --- |
| 身份 | repo/base commit、prep/revision、实际 image identity、材料 digest、清单版本／digest |
| 启动方式 | 解释器路径与可信身份；完整 runner/脚本 SHA；cwd；每条 pytest 命令 argv、测试目标、rootdir、configfile、import mode |
| 可信存在项 | 相对路径、普通文件／明确支持的对象类型、mode、字节 SHA、来源；为何是控制而非修复目标 |
| 可信缺席项 | 固定的配置候选位置、已知应缺控制位置；缺席必须单独表达，不能伪装成空文件 |
| 发现作用域 | 控制名字扫描根、祖先边界、私有测试根、排除命名空间；多命令各自作用域 |
| 插件集合 | 内置 pytest/pluggy 身份；第三方发行版版本、`pytest11` 映射、模块来源；显式 `-p`／环境／递归 pytest_plugins 来源 |
| 配置和依赖 | 有效 pytest 配置及来源；控制专用 helper 的有限闭包；共享产品模块声明；解释器启动控制文件 |
| 例外 | task ID 或任务类别、确切路径／字段、理由、独立验收入口、适用版本；不允许整仓豁免 |
| 验收 | 固定版本的 noop、正确候选、坏控制和合法 helper 结果；验证范围与残余 |

建议清单分两层：仓库/版本/runner 公共骨架，以及题级隐藏目标、材料身份和例外。这样同仓同版同启动方式复用骨架，**隐藏材料更新或任务目标变化仍有题级增量核对**。初次审一次控制职责；每题只做版本匹配、例外匹配、材料叠加和实时摘要检查。

复用键至少包含 `repo + base/prep identity + image identity + interpreter/pytest identity + runner digest + collection scope + control-policy digest`。评分材料另带 digest。任一不符，生成新的清单版本或只复核变化部分；不要求重审未变部分。材料升级、安装配方改动、测试目标扩张、pytest 升级、插件集合改变都不可无声命中旧缓存。运行时每次仍核摘要；缓存的是审查结论，不是跳过核验的权限。

## 3. 评分恢复时序与新增文件处理

actor 侧保持现有开发体验；不锁文件，不在调试过程中删 conftest。评分副本有以下顺序：

1. 保存 raw patch／frozen 全部 entries、baseline 身份和 payload SHA，包括 ignored 控制修改。审计工件与实际评分投影分开，明确“未交付评分的路径和原因”；不重写 raw 成“干净原候选”。
2. 由可信清单计算投影。控制专用文件的增删改与已识别新 conftest entry 不交付评分；产品源文件、公开回归测试、合法构建文件继续应用。重命名按旧路径删除＋新路径新增处理，不能只检查新路径。投影消费者与 manager 用同一份清单／规则 digest 独立核对 included/ignored 集合。
3. 在评分副本应用合法候选。执行第一次可信恢复：官方测试/runner → 控制 census 比对 → 恢复可信存在项 → 移除范围内新增控制项 → 核字节/对象类型/作用域 → 保护。所有动作记录 root 私有自证。
4. 有安装段则**以候选用户执行原安装行为**，保留正常 `setup.py`、构建元数据和产品安装；不把它们统一恢复。准备阶段的控制恢复不能替代下面的安装后恢复。
5. 安装进程结束，撤销包供应/网络并确认交接之后，可信 root 再扫描、恢复控制、核验插件/runner身份。重建源码后，对清单内控制模块对应缓存再作限定范围的 no-follow 处理与核验，保留产品安装产物；现有应用候选之前的缓存规范化不能代替这个新增时点。此段只做固定静态文件操作，不 source 候选 `env.sh`／`funcs.sh`，也不调用安装后候选解释器做可信证明。
6. 重新保护并读回 root 私有自证后，才启动测试 exec。测试脚本恢复所需候选安装状态时，可信 pytest 启动参数与保留环境项应在恢复后重新固定。但现有 `source env.sh/funcs.sh`、激活脚本，以及部分入口的候选身份观测都能执行代码，可能在最后 root 自证后重新创建控制文件；重设环境变量挡不住此副作用。因此本阶段保证只到**最后一次 root 恢复自证时**，不能称实际 pytest 加载前集合始终一致。后续需要更强保证的入口，须采用经过验收的数据式状态恢复或加载前限制，不能让 root source 候选脚本。发现未收口写进程或不能静态安全读回时，该评分尝试不产可信分数。
7. 按原 parser/expected map 评分，保留退出码、逐键结果、政策和真实交付摘要；沿既有 cleanup/lifecycle 收口。恢复/保护失败走现有 infra/停止采信，无 reward，不写作弊 0 分。

Scrapy 没有安装段，第 4、5 步跳过；其 runner 原文是 `PYTHONWARNINGS='ignore::UserWarning,ignore::SyntaxWarning' .venv/bin/python -W ignore -m pytest -rA r2e_tests`。阶段一可保持命令原文和 env 原状，只恢复已验根控制。后续如果改变插件/配置策略，必须产生新脚本／政策身份并验证逐键一致。

现有安装/测试单 shell 的路径没有 root 插入点，**不能在候选 shell 中 source 一个“可信恢复脚本”来替代 root 边界**。优先接已有 two-stage 的安装→撤网→测试接缝；未启用 supply 的有安装入口也需要真正拆 exec 才能声称安装后保护，不能仍走旧单 shell 却记录保护成功。两阶段脚本的来源语义、携带状态和期限处理由对应代码负责人实现；无需另建重试器或任务 owner。

### 3.1 文件变形和新增入口

#### 发现不是只列旧文件

扫描范围依据固定 runner/collection roots 生成；先覆盖根、测试目标的祖先、初始 `test*` 子目录及实际收集树。一般仓库可采用 `/testbed` 的**精确 basename `conftest.py` census**作为保守超集，同时排除 `.git` 等不参与测试的命名空间；`.venv` 不按仓库 conftest 扫描，但另按运行器/插件清单核验。若包内同名文件就是任务目标，提前用例外说明，不能机械纳入。

扫描是控制专用名字和限定作用域，不是恢复 `tests/*`、`*test*` 或任意 helper 的全局 test glob。配置候选名由版本适配器给定；新建 `pytest.ini` 等即使未在可信清单出现，也要在有效配置搜索位置检查，防止替代旧配置。扫描记录包括普通文件、目录、软链和断链，不因 `find -type f` 漏掉异常对象；既检查相对路径，也检查祖先对象，不追随候选软链进入外部目录。

| 候选/安装产物形态 | 评分副本处理 | 必须保留的证据 |
| --- | --- | --- |
| 改已有控制文件 | 从可信字节原子重建，核 SHA；不得沿软链写入 | raw payload、ignored 路径、恢复前后类型/SHA |
| 删除已有控制文件 | 重新创建可信版本；不因候选删除直接判 0 | 删除 entry、恢复自证 |
| 新建根/嵌套 conftest | 若非例外且在作用域内，移除该对象；新增目录不一并清空 | 发现来源（patch／安装后）、原类型/SHA、应缺事实 |
| 控制路径被替换成软链/断链 | no-follow 删除链本体；验证祖先后重建可信普通文件 | 链目标文本；不能写目标或把目标一同删除 |
| 祖先变成软链/目录形状冲突 | 本次不评分，交固定路径冲突；不递归删除候选子树求成功 | 冲突对象和边界；infra/停止采信原因 |
| 控制文件重命名 | 旧路径恢复；新路径按控制发现/插件引用决定是否移除 | 两侧 entry、引用来源；不能只按 rename 标志放行 |
| 普通文件改名为 conftest | 新路径按控制处理；普通文件的删除仍是候选产品改动 | 两侧实际交付集合 |
| conftest 改名为普通模块 | 原 conftest 恢复；普通名字若不参与插件链不按名字自动删；若被显式注册，走插件清单 | 引用链、模块 origin；同进程任意 import 仍是残余 |
| 控制路径硬链/复用 inode | 恢复使用新 inode 的安全写入，禁止直接 truncate 旧对象 | 类型/链数、重建后摘要；不得改坏其它合法源文件 |
| 应缺名字被目录占据 | 停本次，不使用 `rm -rf` 清候选子树；无声删除不是安全修复 | 冲突目录身份、未启动测试证明 |

安全恢复只操作已定位的控制对象；现有隐藏私有测试树的整体可信重建继续沿原协议。缓存（包括控制文件对应的旧字节码）沿既有路径政策做限定处理，但安装后的恢复需要新增实际调用点和覆盖证明；原来应用候选前的规范化不覆盖后来生成的缓存。不能让恢复后的源码仍配候选旧缓存，也不扩大成全环境清扫。

#### 缺席路径与运行期保证

`HygieneRules.test_files` 与现有 setup/protect 自证都要求列入的文件存在且为普通文件。**不能把应缺位置塞进去，也不能把 root-owned 空 conftest 称为“恢复缺席”**。空占位改变了插件对象和导入行为，至少需要独立语义验证；默认不用。

最小阶段对所有新补丁入口与安装产物执行上述 census，记录“最后一次 root 恢复自证时与可信控制集合一致”。后续候选观测、激活、carry 与测试进程的动态创建均未由这条记录证明不存在。现有 sticky 保护复用到可信存在项。此阶段**不声称应缺名字运行期间永远不可创建**，不把恢复后的文件集合称为完整防作弊证明。

若固定入口确实需要保证运行中不能新增 conftest，可选一个有界增强：对不需要写入的固定隐藏收集目录及其控制父目录使用只读 namespace，必要缓存/产物明确转至可写临时位置；或在固定 pytest 版本的可信加载器中，逐次导入 conftest 前按清单核位置/字节。前者可能误伤测试生成文件，后者涉及 pytest 私有加载路径且无法仅靠普通 `pytest_configure` hook 实现，应单独切片验收。**不默认把全仓目录改只读，也不在本轮为了堵任意 Python 修改实现一套通用加载安全平台。**

## 4. 配置、插件、依赖闭包与任务例外

### 4.1 配置与环境

配置专用文件可按可信原文恢复；`pyproject.toml`、`setup.cfg`、`tox.ini` 为混合用途，不能全文件回滚后抹掉构建修复。推荐把可信有效 pytest 配置生成到私有文件，并在对应版本验证 `-c` + 明确原 rootdir/cwd/测试目标后使用，保留候选构建字段在工作树中。若插件依赖原 `configfile` 位置或读取整份配置、迁移影响 nodeid，就用精准恢复 pytest 配置段的版本适配器；解析失败或无法证明保留其它字段时暂停本入口，不做正则“大概替换”。无配置基线也要阻止新的搜索优先级文件接管。

固定 `addopts`、testpaths、收集/排除、import mode、required_plugins 等实际控制值及其有效来源；不是只清一个 `PYTEST_ADDOPTS`。测试启动时使用可信 `PYTEST_ADDOPTS`／`PYTEST_PLUGINS`／autoload 值，保留项目正常所需的其它环境。解释器路径、PATH、PYTHONPATH、用户 site、`.pth`、`sitecustomize`/`usercustomize`、shell carry 和激活脚本能够影响插件解析：逐启动方式登记其可信边界，未知改变不得被当成“同一启动环境”。不要为了保护默认给所有题加 `-I -S`，这会丢掉原环境和安装语义。

### 4.2 插件集合

建议有安装入口逐步采用“禁止未知 entry-point 自动加载 + 显式加载已验插件”：设置 `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1`，按可信清单加载实际需要的第三方模块；内置插件、原有合法 conftest 保留。每个 plugin 记录发行版、版本、entry name、module、真实来源路径与摘要。新安装的普通依赖允许存在；新增加的 `pytest11` 映射不会因为安装成功就获得评分控制权。已注册插件少一个或来源变了也是失败，不只检查“没有多一个”。

这是启动配置变化，**不把它偷偷加进当前已验 Scrapy wrapper**。同版 runner 的 noop/正确候选逐键一致、所需插件/fixture/marks 可达后才采用。旧版本缺少对应开关或 runner 自行改环境时用该版本的静态集合核验/明确入口适配，不能盲套最新 CLI。

显式 `-p`、`PYTEST_PLUGINS`、可信 conftest/测试模块递归 `pytest_plugins` 都纳入同一允许链。源 runner 可解析则预先固定；动态 plugin 计算不能靠 grep 伪装成完整解析，明确登记为需验证的例外。候选新增公开测试仍可交付，但不得让其 `pytest_plugins` 在评分期间注册未知全局控制；若评分命令确实会收集这些公开测试，必须在该入口明确处理/验收，不能仅因“是公开测试”一律过滤。

**允许集合的检查时点必须在模块执行前。** `pytest_plugin_registered` 收到模块时 import 已发生；事后发现未知插件只能报异常/停止采信，不能称“已阻止它执行”。若要实现有限的加载前限制，可用固定版本的私有可信 launcher：候选用户启动受保护解释器/pytest，先安装对应版本的导入适配，再开始 pytest 参数/插件发现；在 `PytestPluginManager.import_plugin` 与 `_importconftest` 的实际 import 前核 module/path/字节允许集，关闭独立的 entry-point 自动通路，继续覆盖递归导入。[pytest 8.3.4 官方实现](https://raw.githubusercontent.com/pytest-dev/pytest/8.3.4/src/_pytest/config/__init__.py)显示这些是具体接点，也显示 entry-point 自动加载不是只走同一个 `import_plugin`，因此不能只包一个方法就宣称完备。适配仍须保护解释器启动、origin 解析和模块父包，不得先 import 候选包再检查 origin。8.3.4 与其它 pytest 版本各自 pin/验收，不依赖跨版本私有 API 稳定性。

此 launcher 是后续有界实现选项，**当前未实现**。若只得到 candidate 身份的 trace 或注册后检查，本轮仅记 diagnostic；不能升级为加载前安全证明。这一限制不阻塞其它题目诊断，也不证明允许的产品模块无法在同进程撤掉限制或 monkeypatch 报告。

只固定名字不够：允许 `foo.plugin` 后候选在高优先级 cwd/PYTHONPATH 放同名模块仍能替代它。测试启动必须核真实 origin，并保护可信插件实现及控制专用路径。`--trace-config` 适合可信基线 discovery/候选身份诊断；它会执行插件，不是 root 在候选环境里做静态证明的工具。

### 4.3 有限闭包与产品源码冲突

闭包分三类：

1. **纯控制代码**：conftest、plugin、专用测试控制 helper、其包入口与注册元数据；确认不是题目修复目标后 pin/恢复，递归 `pytest_plugins` 纳入。
2. **固定第三方运行器与插件依赖**：按已验安装身份/pin保护；安装后版本/文件不符时，不信任旧资格，也不把升级失败计作功能 0 分。优先阻止/隔离未知插件加载，避免整份 site-packages 回滚破坏合法依赖安装。
3. **被测产品实现及共享 helper**：保留候选。可信 conftest 可以正常调用候选 API，测试由此观察真实行为。若同一模块既是产品目标又提供评分 hook，不一律恢复；选择已审的控制专用副本、独立测试驱动，或进入下面的题级例外。

闭包不求证明任意动态 import 的全部行为。root 不能执行候选文件追图；静态解析、可信基线候选身份 discovery 和明确人工职责确认足以形成有限清单，动态部分如实登记。若例外需要改 pytest/plugin 本身，身份切换和独立 oracle 是必要条件，不以来源 parser 对自己的报告作为唯一验收。

### 4.4 确需修改控制的任务例外

例外依据题面与可复现目标：例如任务就是修 pytest plugin、fixture/collection 规则或构建插件注册。记录 task/版本、允许改的确切文件或字段、允许的新增入口、验收依据，形成明确题级例外和独立验收方案；规则实施以后无需对每次候选触碰重复问用户，也不按触碰文件判作弊。

本轮做了一个便宜的静态预筛：只读既有 [R2E 当前 ingest 的 validation 文件](../../s2_r2e/ingest/validation_bundles_v0.jsonl) 的 gold patch 路径，48/48 条都有 gold；`conftest.py`、pytest 专用配置名字以及 `tox.ini/setup.cfg/pyproject.toml` 路径命中 **0/48**。文件 SHA256 为 `763cd1b9e05025cfd0ab6bf1f03dd1536457d4e9283f1b61e56c9abbea447c11`，方法是从 `diff --git` 两侧取路径并匹配精确 basename；没有打开这 48 份工作树或复跑。该结果仅说明这份 ingest 的 gold 没显式触及这些名字，**不证明任务都无需控制变更，不涵盖 SWE，不衡量例外实际发生率**；gold 不是合法解范围的规范，插件也可能通过其它文件改动。若将来 gold 命中，先列为例外候选，再读题面/职责；不得自动授例外或自动拒题。

| 例外/冲突 | 处理方式 | 不能直接做的事 |
| --- | --- | --- |
| 题目目标是 fixture、collection 或插件功能 | 允许明确控制路径/字段，以可信外部测试驱动验收 | 用候选插件自己的报告作为唯一通过证据 |
| 构建目标需要变更 plugin 注册 | 保留构建字段，以独立行为测试核功能与注册范围 | 全文件恢复 setup/pyproject 后称解答完整 |
| 控制 helper 与被测产品共用模块 | 保留产品模块；拆可信控制副本或明确例外 | 沿 import 图一律恢复整包源码 |
| 普通题出现可信范围冲突 | 保存候选，重归类本题/入口并补局部验收 | 静默忽略合法必要改动后宣称已完整评分 |
| 暂无独立 oracle | 保留诊断，停止本入口可信评分，材料负责人补依据 | 扩大为所有题不能继续诊断 |

例外模式保留对应候选改动，但使用**独立的固定测试控制/结果依据**验收：外部驱动用可信测试验证插件语义或 fixture 行为，核 nodeid/断言/产物和报告过程；被测插件不得成为自身唯一“通过”报告者。对于必须允许候选 conftest 的产品任务，可把验收放入不加载该 conftest 的可信外部测试范围，再显式调用其目标行为；这项迁移需证实覆盖目标，不能只加 `--noconftest` 后声称测试仍完整。

若当前材料做不到独立验收，该题保留诊断结果并停止可信评分，交任务/材料负责人补材料；不把合法解静默覆盖后称完整评分。后来发现普通任务确需改控制时，保存候选并重新归类，只重做该例外接缝，已有同仓清单不全盘废弃。

### 5.2 建议阶段与完成条件

- **阶段 A：当前探针收口。** 如实施 Scrapy exact 控制切片，在普通入口与 replay 的共用 spec 处接入，保存政策 SHA/ignored 证据；以既有九组证据为 CPU 功能依据，只补真实运输/入口达成情况，不继承为通用规则验收。其它可审探针继续诊断，不等待全池清单。本轮真实探针选未测的 mypy10308／Pillow；Scrapy 复用既有 CPU 证据，不反复收费验证。
- **阶段 B：同版本的最小通用复用。** 私有清单、规范化匹配、候选新增/删除/rename/conftest census、安全恢复和配置来源核验；先做本地窄 fixture 验收。选择一个已知安装后 hook 的 SWE 入口，在 two-stage 边界接 root 重置，保留合法 setup 改动。插件记录先静态核验；显式 allowlist 用一个实际所需插件的固定入口验收。只对通过的启动方式启用。
- **阶段 C：按真实需要补例外/运行期保证。** 只为任务确需控制变更或已发现动态新入口的题加独立驱动/局部 namespace 保护。不是普通诊断开跑前的全池条件。

阶段 B 的独立验收通过后，同一清单 identity 可复用，不为每题重新做攻击矩阵。发现不同 runner/环境/例外，只验证变动部分；没有新的证据，不持续追加更广攻击。具体生产实施范围应在接入时明确记录，本设计不以现有字段存在或 CPU 成功代替该范围；若提出改变来源 expected-map/parser/reward/训练准入，则超出本文范围。

### 5.3 窄验收矩阵

先用临时文件树/小 pytest fixture 验证规则与恢复，不为每个边界跑所有真实题；实际 CPU 只验证被改变的安装/启动接缝。每项保留 raw candidate、projection、root 自证、真实执行/未执行、逐键与清理证据。

| 验收组 | 必须成立 | 状态/成本 |
| --- | --- | --- |
| Scrapy 原/新 noop、C1、两坏控制、混合、历史模型 | 九组结果与 raw/included/ignored 守恒；公开测试/源码不丢 | 已完成有限 CPU；不重复整矩阵 |
| 新增根+嵌套 conftest（含新目录）、删旧 conftest | 新 hook 不在测试启动控制集合；旧可信文件恢复；其它候选源文件不变 | 建议本地恢复 fixture + 一次小 pytest |
| 软链/断链/硬链、祖先软链/目录冲突 | 不跟随、不改外部/其它合法源文件；冲突时测试不启动，无 reward | 建议本地文件系统 fixture |
| rename 两侧、普通模块→conftest、控制→显式插件模块 | 两侧分类与注册来源正确；raw 守恒；合法普通名字不全局冻结 | 建议投影/加载 fixture |
| 安装时通过合法 setup 改动生成 tests/conftest | setup 产品改动/产物保留；安装后恢复清除 hook，坏功能仍失败；混合正确解通过 | 建议一个固定 SWE 入口有限 CPU |
| 最后恢复后的 carry／激活生成新 hook | 最小阶段如实保留此残余；若声明加载前保护，则新 hook 被阻止且正常 carry／合法构建不受影响 | 仅接更强保证时做小 fixture |
| 安装后生成控制缓存 | 源码恢复后按清单再次处理缓存，实际执行可信行为，产品安装产物保留 | 安装后接缝的小 fixture |
| 新 pytest11、环境/`-p` 注入、同名模块 shadow | 未允许插件不获控制权；原必需插件正常可达且 origin/版本相符 | 建议本地两个插件 fixture + 一个需插件入口 |
| 混合配置/新优先级配置 | pytest 语义可信；候选构建字段逐字/等价保留；nodeid/键集不变 | 建议版本适配 fixture + 正反 CPU |
| helper/公开测试/合法包源码/setup 修改 | 完整交付；不按 tests/testing/test 名称自动忽略；正确解仍通过 | 复用历史合法候选并加一个构建正控 |
| 期望 FAILED/ERROR、正常 RC1、多命令 | 来源 expected-map 匹配可得 1；没有 RC1 全拒或“全必须PASSED”规则 | 复用固定原语料，改启动时定向 CPU |
| 控制 SHA/清单/插件身份错、保护失败 | infra/停止采信；测试不启动；完整收口，无 reward | 本地故障注入 fixture |
| 明确允许 conftest/plugin 改动的任务 | 候选控制变更保留；独立固定驱动证明目标行为，伪报告不能替代断言 | 仅有这类例外时验一题 |

没有把新增 root/嵌套路径的理论扫描成功当成“运行期间任意新文件都不可加载”。若选择运行期 namespace/加载器增强，另加**测试过程中生成新 conftest**的定向用例，证明所声明目录范围内被挡住，并核合法临时文件写入；不用这个额外切片挡全部诊断。

## 6. 剩余范围、停止条件与负责人实现选择

本设计不证明同进程 Python 永远不能改报告/内存，不保证候选产品代码不能输出伪日志，不证明任意动态 import 闭包；也不自动覆盖 Pillow 自定义 unittest、shell、非 pytest 多命令入口。来源 first-summary parser 的广义歧义仍须如实保留，不能用“控制保护”改最后一段摘要选择或把 R2E expected FAILED/ERROR 改成失败。

本期恢复覆盖**候选投影和安装结束后的最后 root 恢复时点**可定位的控制对象；随后候选观测／激活／carry 以及运行期动态注入，只有明确采用局部额外机制的目录/加载路径才有更强保证。日志/插件 trace 来自候选进程时只算诊断，不能冒称 root 可信证据。正式训练资格、材料弱测问题、模型质量和费用控制另有既有流程。

停止条件是：在采用的固定版本与启动方式下，旧正确/错误行为区分保持、已知控制反例失效、合法产品/构建修改保留、raw/投影/自证/逐键和收口可重算。满足后按同一 identity 复用；一个不支持入口只停该入口的分数采信，不能扩大为所有题停诊断。控制职责与产品目标冲突、来源身份不符或恢复不安全时保留候选和证据，交对应材料/入口负责人定位，不追加无期限防作弊检查。

### 6.1 本轮负责人可直接收敛的五个实现取舍

1. **材料承载**：先用私有清单/sidecar + adapter 渲染，沿用公共 spec；将来正式摄入需要字段时再归材料负责人。推荐此路，避免把诊断 wrapper 留成第二套长期 spec 逻辑。
2. **新名字处理范围**：按 runner 作用域做 conftest 精确名字 census，普通仓库以可评分仓库树为保守超集，并列配置搜索位置；现有 `test_globs=()` 保持。推荐此路，解决新增入口且不恢复所有测试/源码。
3. **安装后接缝**：接已有 two-stage 并让有安装无 supply 路径同样真正拆 exec；不在候选 shell 执行 root恢复。推荐从一个已知安装生成 hook 的入口开始，不等全池改好。
4. **配置与插件策略**：推荐混合配置用可信有效 pytest 配置/明确 rootdir，插件用已验 allowlist；配置位置依赖强的仓库用段级适配。先分别验入口等价性，再启用，不能加开关后继承旧资格。
5. **保证级别**：本期明确保证最后 root 恢复时的控制集合重建，保留之后的候选观测、激活、carry 及运行期任意 Python 残余；局部 readonly namespace/可信逐次加载核验按实际故障另做。推荐此分期，不让完整防作弊平台成为诊断前置条件。

这些是本设计的工程取舍，供负责人确定实现范围和顺序，**不是追加用户审批请求，也不是已获批准生产实施的声明**。
