# SWE 题目静态筛查：实际流程与一个例子

2026-09-21 / B Codex。本文介绍已经执行的工作；后续实验明确标为待做。

**我们已有一版可重复的小批静态复核流程：本夜在 5 批、7 个仓库的 40 道不同题上执行，并完成逐题独立复核和总协调验收。** 它负责判断“公开要求、合理修复和评分依据是否一致”，并把疑点变成具体实验。此前的环境运行与维修为它提供证据；本夜没有新增 CPU、模型或训练实验。

这还不是完整、自动验收题目的流水线。静态审查能发现明确的源码、题面或断言问题，也会提出需要运行确认的假说；不能据此保证所有正确解都能通过、所有错误解都会失败。

## 1. 一道题经过哪些步骤

| 步骤与负责人 | 实际做什么、为什么这样做 |
| --- | --- |
| **① 协调者固定材料** | 先登记题目 ID、来源、base commit、公开题面、gold、测试补丁、参考测试及适用的环境版本。公开材料、私有评分材料、旧质量调查分开提供；旧运行引用精确到本题和条件，缺材料明确记录。避免把不同版本的源码、配方和结果拼成一题。 |
| **② 单题公开读者** | 新上下文只读公开题面、base 源码/文档/旧测试及中性环境说明。先写清“开发者应解决什么、哪些行为应保留、哪些信息确实缺失”。不看 gold、私有验收和旧结论，不要求它完成解题。产物：`public_read.md`。 |
| **③ 私有主审先调查原件** | 结合公开阅读，追源码、gold、测试断言和既有运行日志，完成下节八方面调查。保存 `analysis_before_history.md` 后，协调者才开放本题旧质量调查。这样先形成自己的判断，再核旧报告。 |
| **④ 主审核对旧调查** | 对旧结论逐条确认、推翻、标过时或未核实，保留改变判断的理由。产物：`old_findings_delta.md`，以及供用户阅读的短卡和结构化记录。旧报告是线索，不能作为当前结论的依据本身。 |
| **⑤ 独立 reviewer 复核** | 另一新上下文先读原件、形成并保存 `reviewer_initial.md`，之后才读公开读者、主审和旧调查的结论，写 `review.md`。既核主审是否有证据，也主动找遗漏。分歧按原件或可区分实验处理，不按多数票。 |
| **⑥ 协调者收束，总协调者验收** | 将修正写入最终 `card.md`、`screening_record.json`，原初稿保持不变。总协调者按包抽验关键源码/断言/日志，核材料引用、角色顺序和结论边界；不是再从头重审全部源码。最终分别列候选、先诊断项和未执行 CPU 方案。 |

**人员安排：**一个协调任务管理一批；公开读者每题独立，主审和 reviewer 通常按同仓 2–3 题小包复用版本知识，逐题交付。不是一个 agent 长时间顺读整个仓库的所有题。不同题可并行，同题遵守材料开放顺序。共用 reviewer 复核多题时，先保存包内全部独立初判，再开放任一主审结论，减少跨题暗示。

**环境不让每个 reviewer 自己猜。** 协调者统一提供[解题环境卡](quality_batch01_20260921/actor_environment_card.md)；逐题填写“开发需要什么 → 公开依据 → 已有证据适用于谁 → 缺口 → 最小验证命令”。例如评分用户能安装成功，只证明评分侧条件，不能替代解题用户的解释器、权限和资产可读性验证。

每题最终有七份文件，详细调查与用户短卡分开；保存初稿、摘要及开放记录是为了追溯判断是否受后续信息影响，**不是给生产训练增加一套哈希闸门**。[角色与产物约定](quality_batch01_20260921/record_template.md)

## 2. 每题具体查什么

| 方面 | 核心检查 |
| --- | --- |
| **公开需求** | 从题面、接口、文档和公开旧测试提取目标；区分正常查代码才能知道的约定，与只能从隐藏测试猜到的要求。 |
| **材料与初始问题** | 题面/base/补丁/环境是否匹配；初始失败发生在哪条路径，是否其实来自安装、依赖或资源故障。 |
| **测试覆盖** | 读新增、修改断言和决定性 fixture/helper，逐个解释目标参考测试；追相关回归测试。检查输入、执行路径和最终断言，不按测试数量推断覆盖。 |
| **误拒合理解** | 测试是否强制没有公开依据的内部方法、精确文案或调用方式；是否有不同于 gold、同样满足要求的实现路线。 |
| **回归与 gold** | gold 是否修到原例、破坏合理旧行为或依赖未交付改动。gold 是待核对的实现，不是唯一正确答案。 |
| **开发条件** | 解题者需要哪些导入、构建、公开测试、资产和服务；区分环境准备、解题、评分安装、测试运行四阶段的网络/权限/资源需求。 |
| **交付与评分边界** | 合法改动是否会被补丁投影忽略、被官方恢复覆盖；是否有本题特有的答案暴露、评分干预或材料问题。共享链路审计引用已有结果。 |
| **关系与用途** | 是否有具体的同源题、未来修复或答案线索；适合哪种诊断、还缺什么。不静态预测模型通过率或训练收益。 |

核心产物是一张双向表：**公开要求/合理旧行为 → 对应测试与断言 → 覆盖、缺失或冲突；关键测试要求 → 公开依据。** 先调查，再用清单查遗漏；八方面和既有 40 项编号都不是自动淘汰规则，也不要求穷举几千条无关测试。

结论始终区分四层：**直接读到的事实、源码推断、指定条件下的历史运行结果、尚未验证的未知项。** 不把“可能漏测”写成“已出现错误满分”，也不把未知一律算题目缺陷。

## 3. 例子：Moto-5406 怎样筛出一个具体风险

这是一道 DynamoDB 模拟服务的修复题。ARN 是 AWS 资源标识，其中包含地区。用户选择 `us-east-2` 创建表，返回的 ARN 却写成 `us-east-1`。

**第一步：公开读者先确定正确目标。** 它在未见 gold 和私有测试时，沿公开源码发现：请求后端已经按地区区分，生成 ARN 的函数却把地区写死为 `us-east-1`。因此应让 ARN 使用请求地区，并保留其它地区的正确行为；不能仅凭错误 ARN 宣称“表实际存到了另一地区”。它也发现题面示例表名不一致，但现有接口足以消解这个笔误，不据此判整题不可用。[公开阅读原件](quality_batch01_20260921/expansion/batch05/results/getmoto__moto-5406/public_read.md)

**第二步：主审把要求与评分逐项对应。** gold 保存并使用传入的地区，静态上符合核心目标。来源参考集有 1 个 F2P（预期修复前失败、修复后通过的测试）和 26 个 P2P（预期修复前后都通过的回归测试）：

| 合理要求 | 实际评分依据 | 静态判断 |
| --- | --- | --- |
| `us-east-2` 的表应返回该地区 ARN | 唯一 F2P 检查完整 ARN，输入地区为 `us-east-2` | 覆盖核心实例 |
| 原有 `us-east-1` 等地区仍正确 | 26 个 P2P 不检查 ARN 地区；已有公开 `test_create_table_standard` 检查 `us-east-1`，但不在本题评分命令中 | 有具体回归覆盖缺口 |
| 普通表和数据操作继续工作 | P2P 仍检查删除、读写、查询、分页等行为 | 这些测试有价值，不能因它们不查地区就说全部无效 |

由此产生一个明确假说：**如果只把硬编码从 `us-east-1` 换成 `us-east-2`，可能满足原评分，却继续给其它地区返回错误 ARN。** 这是待验证的错误候选，不是已经运行得到满分的记录。

**第三步：回读真实 RH2 原日志，确认已有分数意味着什么。** 历史 noop（不修改代码）安装退出 0，测试为 **1 失败、26 通过**，失败位置就是 ARN 地区不符；gold 安装退出 0，**27 项全部通过**。主审还核对了实际评分命令、参考缺席/跳过、测试退出码和清理。这支持“该次原评分确实测到了目标失败”，但没有验证上述错误候选，也不能证明实际解题用户的开发条件已就绪。[分析与运行引用](quality_batch01_20260921/expansion/batch05/results/getmoto__moto-5406/analysis_before_history.md)

**第四步：独立复核纠正旧论证。** 旧报告把 P2P 的改名说成回归保护无效。复核原补丁发现实际是 **22 个改名、4 个保留原名**，而改名保留的测试体仍在检查旧行为。正确的问题是“地区 ARN 缺覆盖”，不是“测试改名就失效”。这也说明本次工作不只是替旧报告确认问题。[独立复核与更正](quality_batch01_20260921/expansion/batch05/results/getmoto__moto-5406/review.md)

**第五步：形成最小、可区分的下一实验。** 在相同、明确记录的评分条件下，比较三种代码，同时另跑上述公开 `us-east-1` 测试：

| 代码 | 原 27 项 RH2 评分 | 另跑公开 `us-east-1` 断言 |
| --- | --- | --- |
| base / noop | 历史结果为 0 | 预计通过，待验证 |
| gold | 历史结果为 1 | 预计通过，待验证 |
| 只把常量换成 `us-east-2` | 预计可能为 1，待验证 | 预计失败，待验证 |

**这个三路实验尚未执行。** 只有错误候选确实获 1、同时违反公开旧行为，才可报告“已复现错误修复被接受”。原 reward 与新增公开诊断分开记录；若要补测试，另存版本并说明依据，不偷偷改变来源分数。若实验不支持假说，就修正审查判断。

当前处置是**保留为开发诊断题、优先做这项 CPU 对照，暂不列普通模型探针的优先候选**，不是永久淘汰。也不因此要求先验证全部 AWS 地区、所有服务或全仓测试。[最终题卡](quality_batch01_20260921/expansion/batch05/results/getmoto__moto-5406/card.md)

## 4. 哪些已经稳定，哪些还要验证

**已经可复用的是组织与证据流程：**固定版本、公开视角、原件先行、独立复核、需求—断言映射、证据分层，以及短卡到定点实验的交接。流程在批次中有实际改进：首批补充了“同包全部初判后再开放结论”；第二批发生有界跨题误读后，记录暴露并给尚未开始的相关题更换新主审。[首批方法调整](quality_batch01_20260921/method_adjustments.md)、[第二批调整](quality_batch01_20260921/expansion/batch02/method_adjustments.md)

**还没有得到的是筛查准确率和运行闭环。** fresh 上下文、阅读约定与时间/摘要记录不等于操作系统强制隔离；私有角色会看到历史 gold/noop 结果，也不是完全不知结果的盲审。40 题含校准样例和受限仓库抽样，不能估计全池缺陷率。独立复核可以纠错，但尚未测量漏检率、误报率或相对单次审查的增益。

下一步应选少量高价值对照，确认静态假说，并对模型候选补实际解题用户的开发验证。需要时再修订题面、测试或配方。**不用先跑完全部 42 条 CPU 方案或筛完 216 题才能接触基座。** 本夜 21 个受限候选与 19 个先诊断项是调度结果，不是合格/坏题标签。[夜间结果及下一步](quality_batch01_20260921/night_summary_20260921.md)

面试时可以按已经完成的范围这样介绍：

> 我在真实 RH2 评分与环境验证的基础上，组织了可追溯的 SWE 静态质量复核：固定题目版本，分开公开阅读、私有调查和独立复核，把公开需求与测试断言双向对应，检查漏测、误拒、gold 回归和开发条件。已经覆盖 7 个仓库的 40 题；发现既包括具体评分风险，也包括旧审查的错误。每项高价值疑点交接为可区分的 CPU 对照，静态推断与实测结果分开记录。下一步用这些实验验证结论，再决定题目修订和基座探针。
