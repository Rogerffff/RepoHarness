## 3. 当前可以独立推进的工作

1. 核对来源、许可信息、仓库/base/派生关系、镜像与依赖、题面、参考修复和评分材料；区分真正缺失与尚未验证。
2. 在目标运行条件下验证构建与复位。对 SWE 检查应失败的基线、参考修复、目标测试与回归测试；用正反例检查误奖、误杀和评分控制面的实际边界。
3. 准备训练/开发/最终测试划分，避免同一缺陷或其变体跨集合；用于调试和选配方的题归开发探针，不能事后再当独立最终测试。
4. 盘点任务多样性、预估时间与资源；环境有效性、模型当前难度、真实学习价值分别记录。
5. 准备真实基座测试：准确 checkpoint/tokenizer、Claude Code 版本、工具/子 agent/压缩设置、预算、采样参数、运行环境和证据位置。具体未定项与用户沟通，先完成不依赖它们的准备。

主链通用执行/消费修复归 A。发现 parser 不支持、评分含糊、超时或缺工件时，提供任务级事实和建议，与 A 合并通用分类，不自行把所有失败改成 reward 0 或 infra 丢弃。

## 4. 基座模型测试怎么解释

目标是区分模型能力、harness 适配、环境/评分异常和预算约束。先做少量人工可核验的完整轨迹，再扩大；记录成功与失败尝试的请求、工具、工件、结束原因、时间/token 及成本。

至少观察：是否正常使用工具；失败主要发生在定位、修改、验证还是交付；是否反复绕圈或被截断；长任务是否更易遭遇系统问题；评分结果与实际工件是否一致。发现真实上下文改写、分支或错误分类反例时交给 A。

该阶段结果是基座能力与诊断链证据，不证明 learner 的梯度、版本和样本消费正确；A 使用同批轨迹补齐训练侧验证。明确初期结果是否使用最终拟定的预算和入口，变化后不得不加说明地当作正式模型比较基线。

## 5. 有了初步结果以后再决定

- 当前任务池是否足够，是否需要换来源、补特定缺陷类型或少量合成。
- 是否存在工具协议/基础能力短板，需不需要完整轨迹 SFT。
- 是否重配任务难度，是否引入 terminal 训练；不得用最终测试反馈指导制题或筛选。
- 正式训练/评测规模、重复次数与预算；与 A 合并资源计划。
- 是否值得做 OPD、反馈蒸馏或第二 harness。论文启示是候选，需结合本任务实际失败与成本。
