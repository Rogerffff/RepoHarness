# 项目一执行与交流入口

日期：2026-09-07。状态：分叉准备；任务尚未在此登记。用途：两条主线记录当前工作、用户决定、交接需求和外部意见。

这是工作入口，不替代 [06 执行计划](../06-first-training-local-execution-plan.md)、[协作协议](../collaboration-protocol.md) 或 [审查标准](../review-standards.md)，不新增审批层。分工是启动建议；具体修法、数据源、训练语义及实验成本仍按已有授权推进。角色分工与独立审查按用户授权及既有协议执行。

## 1. 两条主线

| 入口 | 负责的结果 | 第一项交付 |
| --- | --- | --- |
| [A：链路正确性与运行效率](infra.md) | 真实 harness → 评分运输 → 轨迹与组 → learner 的消费可信，错误可定位，性能可测 | 合并复核旧 finding，确定近期修复与未定决策；说明 B 可使用的最小真实执行入口 |
| [B：环境、数据、评测与基座诊断](env_data_eval.md) | 可重复任务、可信评分、独立划分，以及目标基座在实际 Claude Code 下的能力与成本画像 | 代表性小批任务、评分正反例、基座诊断方案与资源估算 |

两条任务均负责主动发现遗漏、准备方案、与用户沟通、安排实现与审查、更新证据。遇到交叉问题先提出交接，不另造一套重复实现。当前主会话可在联合实验或关键决策时做整合，不需要第三条常驻协调任务。

范围依据：[项目一设计建议](../project1_design_advice_20260907.md)、[当前状态简报](../CURRENT-STATE-BRIEF.md)。后续论文阅读继续由用户安排的外部 Pro 任务完成；本工作区消费相关结论，不重复派发整批阅读。

## 2. 最容易交叉的职责

| 事项 | A 主责 | B 主责 |
| --- | --- | --- |
| 评分 | 通用执行、冻结工件、隔离、异常传播与训练消费 | 具体任务的测试命令、parser、参考修复、判分依据及有效性 |
| 失败与预算 | 落实终止事实、重试/丢弃/停机等通用处置及计数 | 用真实任务辨别失败原因，提出任务预算与评分处置建议 |
| Eval | W8 的 checkpoint、执行生命周期、结果运输与失败传播 | 划分、评测协议、运行题单、任务级结果与统计解释 |
| 基座诊断 | 可用的模型接入、harness 运行、日志与资源释放 | 固定模型/工具/预算，运行诊断题、分析表现并回传反例 |
| GPU 作业 | 训练正确性、并行方式、权重发布与系统测量方案 | 基座与最终评测、任务成本和能力测量方案 |

跨界语义只保留一个决定：例如测试超时是否算模型失败，由 B 提供任务证据，A 检查通用处置与训练影响，涉及 T0 时由用户决定。不得两边分别拍出矛盾规则。共享 `grading`、启动、eval 或 schema 文件，每个实现批次指定一个实际修改者；无需为方便分工先重构模块。

首轮交接只需说明：任务与评分材料如何交付；准确模型/tokenizer 与 harness 版本；工具、上下文和预算设置；结束原因与评分状态；结果与真实请求的保存位置。尽量复用现有字段，不提前冻结完整新 schema。

## 3. 并行顺序与联合实验

1. A 复核旧审查、定位近期决策并推进已授权的修复；B 同时做任务盘点、环境与评分验证、独立划分和基座诊断准备。
2. 尽早选一小批代表性开发题，走环境初始化 → 真实 Claude Code → 工件冻结 → fresh grader → 结果记录。允许先不进入 learner；这只证明诊断链的相应范围。
3. A 用该批真实请求与结果验证训练投影、组装和消费；B 检查模型失败与环境失败的分类是否合理。关键共享改动后做一次窄回归，不等全部工作结束再联调。
4. 基线暴露实际瓶颈后，再决定正式题量、SFT、数据扩容/重配、OPD、第二 harness 或系统优化。外部论文不能替代本项目的实测结果。

GPU 租用、API 调用和大规模构建先准备具体作业与成本估算，再按用户已有预算授权执行。两边合并资源安排，明确一次作业的启动、停止和结果汇总负责人，避免重复租卡、端口冲突和互相清理容器。

## 4. 留言板怎么用

最初只维护三份文件：本入口、`infra.md`、`env_data_eval.md`。A 维护 A 文件，B 维护 B 文件；本入口由协调者在确有公共变化时更新。两条任务每次开始工作、形成新决定或交接前，读取双方最新进展。

每次有实质变化，在所属文件追加简短记录：日期/记录人、事实与证据、决定或建议、影响另一条线的事项、下一步。用户决定标明原话要点与消息定位；已有定案链接到其权威记录。尚未回应的建议不能标成用户已批准。

与 Claude、外部 Pro 的交流记录保留结论、分歧和原始来源位置；长原文确有保留价值时另存附件并链接，不复制整段聊天历史。论文主张、模型建议和用户决定分开记录，发现旧结论错误时追加修正说明。

文件变化不会自动唤醒别的会话。一般需求由对方开工时读取；阻塞、跨界语义或需要立即处理的事项，应另行送达到具体任务，或由用户转发给外部 Pro。不要将“写了留言”记成“对方已收到并接受”。

## 5. 文件隔离与可见性

如果两个任务使用同一工作目录，应遵守文件修改归属，避免同时暂存、提交或变更共享文件；各自只提交自己的明确路径。如果需要同时进行较多代码修改，建议使用独立 Git worktree，在集成点合并。

使用 worktree 时，本留言板可继续保留在主工作区这一份共同可见目录；在各任务对话里明确其实际位置，不把不同 worktree 内的副本误当成实时共享状态。代码交接写明分支、提交和证据；对外同步时再汇总到远程。公开文档不记录本机绝对路径。

本目录目前新建于主工作区。旧代码审查及部分复现材料也是未跟踪文件；新 worktree 不会自动带上它们。分叉后先核对所需资料能否访问，可从主工作区读取或显式同步，不能把缺失资料当成不存在相应审查。

## 6. 决策与完成边界

近期只处理会影响下一步的决定。已有授权范围内的调查、方案准备、局部实现和验证继续推进；确有 T0 的部分向用户提交具体选项和推荐理由，同时继续不依赖该决定的工作。

两条任务分别交付可复用结果，但训练闭环、主改进与独立学习证据需要共同完成。局部测试通过不代表正式训练已获资格；完成文献阅读也不代表应采用某个算法。所有完成声明应说明实际证据范围。
