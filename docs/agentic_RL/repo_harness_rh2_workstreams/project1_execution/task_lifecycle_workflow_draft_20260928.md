## 0. 为什么重新设计完整流程

此前的工作主要按阶段组织：先集中验证、修复一批题的评分环境，再安排静态审查，随后另批验证开发条件、进行模型求解。这个方式帮助我们摸清了共同问题、建立了工具和规则，但也让一道题多次交接：静态审查留下的疑点等待后续实验，评分环境通过后又在求解时发现开发依赖缺失，模型暴露的误拒、漏判再交给下一阶段处理。负责人和报告分散，用户需要反复追问每题还差什么、安排谁继续。

**本次调整的核心是让 agent 对一道题的持续推进与最终用途负责。** 在已有规则和授权范围内，尽量把调查、确定性验证、修复、模型求解和反馈接起来；交付应说明这道题现在能怎样使用，以及哪些问题仍影响使用。已有静态审查与环境证据继续复用，重点是把已提出的问题处理到有结论。

因此，本文的七个环节用于说明单题负责人需要完成哪些工作，不能再实施成“整池完成第一阶段，统一交接第二阶段”。负责人可以管理同仓小包、委派子任务；CPU 调查与修复可并行，GPU 求解由共用入口统一执行。模型发现的新问题仍回到原题负责人；公共链路交 A 线修复后，负责人继续跟进恢复验证。公开阅读、真实 solver 与独立复核的隔离仍保留。

这项改变希望减少阶段间积压、重复阅读和用户逐题协调。连续负责也允许有依据地暂挂：缺少材料、超出授权或修订不收敛时，明确阻塞、负责方和恢复条件；不要求把所有题都修成训练题。

## 1. 范围与责任

来源共用准备先提供材料读取、公开／私有分离、环境配方与 RH2 评分接入。题目负责人使用这些共同能力，不为每题重写 parser、启动器或模型网关；新来源缺少接入时，先登记共用实现的依赖。

| 职责 | 做什么 | 边界 |
| --- | --- | --- |
| 持续负责人 | 维护题卡，组织调查、运行、修复、求解与验收；可负责少量同仓题，但逐题下结论 | 可先读工程状态与历史，避免重复；不能冒充独立盲审者。交给 A 线的问题仍由其跟踪恢复验证 |
| 公开读者 | 只读公开材料，解释需求、合理路线与开发命令 | 使用未接触 gold、隐藏测试和旧质量结论的新上下文 |
| 私有主审／实验执行者 | 调查隐藏测试、gold、评分与行为对照，实施授权范围内的处理 | 新主审先形成原件初判再读历史；实验执行可连续复用上下文，私有脚本不交给 solver |
| 真实求解模型（solver） | 在统一入口、干净初态中自主做题 | 独立会话，仅接收公开任务与中性环境说明，不继承调查者的答案知识 |
| 独立 reviewer | 核对原件、决定性实验、修订和用途 | 每题覆盖；新独立审查先形成初判，再读主审结论。修订继续按现有 Claude 实施／Codex 复核分工 |

这是职责划分，不要求每轮重新创建全部角色。已有合格的公开阅读、独立审查与运行证据按适用版本复用；新增修订只补受影响部分。上下文更换时围绕同一题卡交接，不重启一次无目标审查。

## 2. 正常路线与执行方式

```text
材料核对与环境恢复
        ↓
静态调查 ↔ 公开开发验证、私有评分对照
        ↓
已授权修复与定向复验
        ↓
统一入口真实模型求解
        ↓
成功／失败分析 → 题级修复或公共问题跟进 → 相关复验
        ↓
独立验收与用途交付
```

- **按题连续推进。** 不等整池完成一个阶段才进入下一个阶段；明确可修的问题在本题内处理。
- **静态与运行交错。** 可在公开阅读期间准备镜像，在私有调查期间执行公开命令；存在依赖的操作顺序执行。私有 gold 对照与真实求解使用干净、分开的实例。
- **先拿便宜且有区分力的证据。** 不用 GPU 反复发现已知安装错误；也不要求穷尽全仓边界后才让模型做题。
- **按变化复验。** 共同根因修一次，逐题核自己的适用条件；不从同仓一题推广合格结论，不因更换流程重跑已有有效证据。
- **逐题暴露完整剩余事项。** 可以指定优先动作，但不能只留下“唯一下一步”而隐藏其它重要缺口。

## 3. 七个环节

### 3.1 核对材料、恢复本题环境

**工作：**

- 确认公开题面、仓库初态、测试、评分参考、镜像与配方对应。实际工作树可能不同于名义 base commit，要记录镜像自带的已跟踪改动、构建文件及缺失材料，不随意清成干净状态。
- 按来源配方拉取或构建本题环境，准备解释器、依赖、权重与其它资产。分别记录准备、解题、候选安装／构建、测试运行的网络条件。
- 区分公开包、私有评分包、gold／验证工件和历史调查；登记同 issue、修复相互包含、同仓库及模型选择／调参暴露情况。

**留下：**题目与材料版本、实际初态差异、环境配方、公开／私有范围、已有证据入口及缺项。公共运行条件引用批次记录，不逐题抄整份配置。

**继续条件：**材料足以支持公开阅读和私有调查即可继续；某次实验依赖的缺口在该实验前补齐。材料未导出不等于镜像缺文件，镜像构建成功也不等于开发可用。

### 3.2 理解公开需求，检查题目与评分依据

**工作：**

- 公开读者先写目标、约束、合理实现路线、疑义，以及机器可读的开发命令：`id / cmd / timeout_s / expect`。
- 私有主审建立“公开要求 → 核心测试断言”的对应表，并反查关键断言的公开依据；保留八方面调查：公开需求、材料初态、测试覆盖、合理解误拒、回归与 gold、开发条件、交付评分、跨题关系与用途。
- 检查示例拟合、核心路径漏测、无依据的文案／helper／顺序限制，以及 gold 自身的遗漏。先保存原件初判，再对照历史质量结论。

**留下：**需求—断言表、公开开发清单、全部重要疑点及其影响；明确哪些是源码推断、哪些已有实测。无需逐字注释几千条无关回归测试，但须说明阅读范围。

**继续条件：**疑点已具体到可以运行验证。不能只核 Claude 的旧标签，也不能因为目录中没有某类问题就不调查。

### 3.3 验证公开开发和真实评分两条路径

**公开开发：**用正式解题身份、profile、解释器激活和实际 CC shell，执行工作区导入、题面复现、相关公开测试、必要 CLI／构建。CPU 上的真实 CC 加桩端点可以验证这条命令路径，不等于真实模型 adapter 全链已验证。

**私有评分：**通过真实 RH2 导出、投影和 grader 做 noop（不改代码）与 gold／经独立核实的正对照。没有 gold 的新来源，不能虚构“gold 通过”；须另有可信正对照或明确缺口。核查安装生效、实际加载来源、参考测试执行、解析、终止与清理。

**质量对照：**按 v1 做一个已确认违反公开要求的退化候选；怀疑误拒时，再用有依据的合理替代解区分原因。已有同版本对照可复用，不机械构造多份候选。

**留下：**原样命令及输出、退出码、候选工件、逐参考状态、完整日志、资源与清理事实。命令写错应保留失败记录、按公开依据修正，不能静默改命令或误判为环境缺陷。

**继续条件与解释要求：**

- base 能复现目标 bug 是有效证据；缺依赖、权限错误或未执行不能冒充目标失败。noop 得 0 必须解释原因。
- 正对照得 1 也要解释本次看到的参考集外失败。R2E 的期望 FAILED 键按来源语义解释，不要求所有状态变 PASSED。
- 核心调用链的依赖语义在解题侧与评分侧一致；私有测试工具可以不同。不要求 agent 能运行隐藏测试或全仓测试全绿。
- 编译题沿实际交付路径核查“改源码 → 构建 → 导出 → 全新 grader 加载新产物”。共同链路证据可引用，题级缺口另验。
- 核自己特有的资产、权限和残留；gold、私有测试与历史解题轨迹不能进入 solver 可读范围。怀疑偶发问题时再做针对性重复，不统一机械跑多轮。

### 3.4 完成授权范围内的修复并复验

按 v1 §5 的 R-a 至 R-f 模板处理：无效断言／ID、无依据的实现约束、窄范围行为覆盖、环境资产、真实行为测试和有公开依据的题面修订。**本文不扩大这些模板的范围。**

**工作与验收：**

- 环境修复后，原失败开发操作恢复、实际使用候选工作区，未修源码时目标 bug 仍在；不能升级被测项目或带入答案替代解题。
- 测试修订需有公开依据；正对照通过、noop 失败、本次误判纠正、已知相关错误解仍被拒。gold 不满足有依据的新要求时，使用独立核实的替代正对照，否则暂挂，不为保住 gold 缩小题意。
- 题面修订请新公开读者复查；不把隐藏测试细节写进题面。修订版本与原 benchmark 区分。
- actor 专属改动先复验 actor；影响 grader 或共同语义的再补真实评分对照。涉及权限、构建、资源的结论不能只用 root 实验支持。

**留下：**父／新版本、公开依据、触发反例、实际改动、修后结果、独立复核与剩余项。配方依赖的自建资产要可取回或可完整重建，保留失败版本。

**继续条件：**已授权且具备实施入口的阻塞应处理到验证。模板外的目标选择、公共语义／安全政策变更按既有决策办理。SWE-Gym 测试／题面修订机制等共用前置按最新实施记录核对，不能把已授权当成已接线。停止条件沿用 v1：修订不收敛、聚焦复核仍有分歧且没有便宜的辨别实验时暂挂，写明恢复条件。

### 3.5 通过统一入口做真实模型求解

负责人提交任务与待验证问题，统一执行入口管理模型服务、代码版本和单卡队列。每题负责人不各自修改工具集、上下文、网关或预算。

**进入方式：**

- **质量调查：**有足以回答问题的运行条件即可定点求解；可以包含争议题，结果单列，不进能力比较分母。
- **能力比较：**满足 v1 的公开开发、评分依据与有效条件要求；使用共同题单和明确计分口径。已知漏判只在预登记后检的条件下受限比较，未消解的题意争议／误拒不能靠后检豁免。

**运行要求：**独立 solver、干净初态、公开输入；记录实际生效的模型、CC、工具、上下文、网络、token／轮数／时间预算。预算建议相对宽裕但有限，具体值和模型数另议；这不改 v1 的审查／CPU 工作不设统一预算决定。

**留下：**派发记录、完整可获得的请求响应与工具过程、实际预算消耗、停止原因、补丁、评分及异常。模型没有返回的 reasoning 记不可得；派发数、有效评分数和成功数分列。

**继续条件：**先分析小批尝试，再决定是否补采；不要求每题跑遍全部模型。明确暂挂的题不用为了凑完整流程硬跑 GPU。

### 3.6 解释成功与失败，并继续回修

| 观察 | 必须回答的问题 |
| --- | --- |
| 得 1 | 是否满足公开要求，是否漏修或破坏合理旧行为，是否读到答案或利用评分缺口？ |
| 得 0 | 是否确实未修好，还是环境、预算、误拒、题意或链路导致？ |
| 无有效评分 | 哪段没有完成，已有工件和终止事实是什么，能否安全恢复？不能直接算模型能力失败 |

每次尝试在题卡有记录；这一轮小批建议逐轨迹核查。重复机制可合并说明并列出覆盖的尝试，不重复写长文。原始 reward、语义后检 `PASS / FAIL / UNKNOWN`、运行有效性与归因分别保留；后检脚本只能证明其覆盖的性质，仍需对照公开需求读候选。

**回流：**题级问题由原负责人修复并回到相关对照；公共链路问题交 A 线，原负责人继续跟踪恢复。暂停受影响的题、模型或组件，保留现场，无关工作继续。

**复验：**评分侧窄修且旧工件仍适用时，可以另版本重评分；题面、解题信息或行为条件改变后，要评估新条件就应干净重解。先做窄验收，不默认整池重跑，修前修后不未经核对混算。

**留下：**逐尝试解释、跨轨迹问题、修后证据、可比范围及剩余项。全成功不证明题目可靠，全失败不证明题目有错；不能删除某模型失败的题来美化共同比较题单。

### 3.7 独立验收与用途交付

每题独立复核。重要修订在使用前已按 v1 复核，最终验收补查后续模型反馈及交付结论，不把全部复核推迟到最后，也不完整重审所有旧材料。

分开判断：问题定位、能力比较、训练候选、留出评测。训练候选按 v1 需要核心覆盖与正负对照，没有未处理的严重评分缺口；难度、成败混合和成本另用于判断学习价值。用于选模型或调配方的题，不因此成为未暴露的留出评测题。

**完成建议：**正常路径形成经核查、可用于声明用途的题目版本；或者形成有依据的暂挂／不采用结论。已可运行但还在等 GPU、或分数尚未分析的题，不记作本设计的端到端闭环完成。这个完成标签与 v1 用途资格分开，不新增训练准入条件。

## 4. 最终题卡与已有工作的接续

沿用现有题卡和记录字段，不另建一套平行状态系统。当前题卡至少能回答：

| 内容 | 必须写清 |
| --- | --- |
| 身份与版本 | 题目目标、公开输入、实际初态、镜像／配方／运行版本、持续负责人 |
| 需求与评分依据 | 核心行为、对应断言、来源语义、修订版本和覆盖限度 |
| 处理与验证 | 发现了什么、依据是什么、实际改了什么；开发和评分证据分开 |
| 模型记录 | 每次派发、实际条件、轨迹／补丁／原分／后检、成功失败归因；未做写未做 |
| 当前用途 | 四类用途各自 yes／conditional／no，依据和限制 |
| 全部重要剩余项 | 影响、负责方、解除条件与下一步；暂挂也要可恢复 |
| 复核与追溯 | 复核范围、证据位置、变更后哪些旧结果仍适用 |

已有题从当前位置继续：只有环境对照的补静态与开发／质量检查；已有静态的执行已提出的辨别实验；已有模型轨迹的先解释和处理旧反馈。共同机制、同版本有效证据直接复用；未知和旧版本不冒充当前通过。

**Conan15422 的例子：**工具链与 G1 权限修复后，所选功能测试组由 8 通过／2 失败变成 10 通过／0 失败；但 v1 仍记录真实候选遗漏默认值、多配置路径等核心行为。这张题卡应同时写“开发操作恢复”和“原评分覆盖仍不足”，由负责人继续跟进后者。早期模型尝试不能算作 G1 修后统一条件下的新复验。证据见[任务二结果](task2_swegym_dev_conditions_20260925/results.md)、[独立复核](task2_swegym_dev_conditions_20260925/codex_completion_review_20260925.md)与[v1 §10](task_screening_standard_v1_20260925.md)。

## 5. 请 Claude 重点复核的部分

1. 七个环节是否遗漏真实执行时必须完成的工作；尤其是环境恢复、编译交付、评分有效性和模型反馈。
2. 静态与 CPU 交错、按变化复验的安排是否可操作，是否仍有容易积压给“下一阶段”的空隙。
3. 公开／私有角色、持续负责人和独立 reviewer 的边界是否清楚，是否存在不必要的重复角色或复核。
4. 进入质量调查与能力比较的条件，以及暂挂／完成定义，是否与 v1 冲突或过度加门槛。
5. 最终题卡是否足以支持交接、统一 GPU 排队与后续修订；具体脚本、队列字段和预算数值留到下一轮设计。
