### 3.2 把自动化写进每道题的交付

用户的目标是边做边形成自动化程度更高的流水线。讨论稿 §5 第 5 条把脚本、队列都推到下一轮；建议把下面三条写进"完成"的要求：

- **机器可读、带版本的题卡。** 在现有 `screening_record.json` 上扩字段，不另建一套平行状态系统。每条证据记下它适用的版本：材料版本、派生配方哈希、镜像 digest、RH2 提交、求解条件编号。这样"改了配方后哪些证据过期""这题下一步缺什么"都能由脚本算出，不靠人记。现在的 `environment_status_20260928.json` 只有是／否标记和文字说明，算不出这两件事。（09-29 更正：此处原以 orange3 为例，不成立，见 §2。）
- **同一手工操作在第二道题上出现，就收进共用工具。** 例如 noop/gold 复跑、退化候选评分、公开题包生成、后检，并登记到 v1 §7.4 的共用工具表。
- **题卡记录每一步花的会话时间和机器时间。** 试行一轮后，按实际耗时决定先自动化哪里。

### 3.3 待用户决定事项的统一出口，以及规则缺口的回路

- **统一出口。** 负责人不直接找用户，由协调者把各题的待决定项汇成一张清单，按批送一次。每项写选项、建议和它阻塞了什么。按现状会进清单的有：探针模型与预算、GPU 租用时机、coveragepy `5dbbe143` 的两种读法（P5）、coveragepy `97997d2c` 的"替换还是合并"（两种读法都有公开依据时）、SWE-Gym 修订机制设计。
- **规则回路。** 负责人遇到 v1 没覆盖的情况，先登记在当批规则问题表；批末由协调者提 v1.x 修改，Codex 复核，只有 T0 级别才交用户。否则各负责人会各自解释规则。

### 3.4 GPU 排队：明早讨论时需要覆盖的内容

- **看板字段。** 每条请求至少写：请求线程与负责人、题目、材料与镜像版本、求解条件编号（代码提交、模型、CC 版本与工具设置、预算）、目的（质量调查／能力比较／训练价值）、次数、状态、结果路径。另有一个全局暂停开关，写明暂停原因、影响范围和恢复条件，对应用户说的"链路出问题就暂停各线程"。
- **按窗口开机。** 单卡要在不用时释放。建议求解请求先排队，攒够一批或到约定时间再开机，跑完取回证据就释放；排队期间负责人继续做 CPU 工作。
- **预算口径。** 首轮探针用 60 回合 / 131K，正式链默认 25 回合 / 32,768；46 次成功里只有 14 次落在正式默认之内（[环境总入口 §6](environment_pipeline.md) 09-23 行）。讨论稿 3.5 的"相对宽裕但有限"建议补一句：判断"成败混合、有训练价值"时，用计划中的训练预算，或者两种预算都记录。
- **可选。** 只为发现题目问题的求解，可以先用 API 模型并行跑，不占单卡；结果只作问题定位。

### 3.5 较小的建议

- **接手说明。** "持续负责人"实际靠题卡加协调者维持，具体会话会换。题卡里放一段接手说明：当前状态、上一步及证据、下一步、阻塞。试行时让一个新会话只看题卡接着做，检验交接是否够用。
- **状态。** 进行中之外，定三种结束状态：可用（写明用途与版本）、暂挂（写明恢复条件）、不采用（写明理由）。"每批 12 题"（D5）建议理解为同时在做的上限和汇报单位，做完一题补一题，不再是全批做完才进下一步。这是对 D5 的新解释，需要用户确认。
- **复核合并。** 有修订的题，"Codex 复核修订"和"最终独立验收"可以合成一次，由 Codex 一并看修订、模型反馈和用途结论。静态结论那一层的新会话复核保留。
- **CPU 机作业排队。** 构建和评分走统一作业队列，按 CPU 和内存限并发，不要各负责人各自 SSH。
- **镜像可取回。** 派生镜像存到可取回的位置（私有仓库，或带 digest 的导出包）。Spheron 机器不能暂停，重建一次要 1–2 小时；R-f 机上 128 GB 镜像至今状态不明。
