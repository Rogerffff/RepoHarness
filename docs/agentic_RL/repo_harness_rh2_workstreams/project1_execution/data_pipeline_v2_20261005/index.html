数据集的处理顺序

越靠前，环境越现成、单题成本越低。后一项不必等前一项全部做完。

    为什么

    环境和 noop/gold 对照都已经有了，成本最低。顺便校准新工具和审计员的耗时，并检验新流程能否找回已知的 5 次误奖。

每道题怎么处理

旧流程是“先审后测”，每题要三个会话审查。新流程反过来：先用脚本和模型采样把信息拿到，只审真正需要审的题。

1

脚本检查

脚本

空补丁应得 0，参考修复跑两次都得 1；扫描题面有没有泄漏答案；排除留出仓库、去掉重复题；确认以 agent 身份能跑公开测试。新来源的题没通过就直接换下一道。

为什么：这些检查全部可以批量跑，432 次评分 4.7 小时就能完成。后面的题有几千道，单独修一道题不划算。

2

Coder 采样 4 次，全对再加 4 次

链路执行器

按结果分层：成败混合的进入审计；8 次全对的作储备；全错的在批末让 Qwen3.6 跑 2 次，用来判断是题太难，还是评分有问题。

为什么：采一次分不出难易。训练时全对或全错的组会被在线丢掉并补采，所以离线只需要粗分，不必精确估计每题的成功率。

3

自动后检，只打标记

脚本

逐条检查每次尝试：附近的测试有没有被改坏，有没有改测试文件，有没有用 git fetch 或访问上游 issue 去取答案，候选有没有把环境弄坏。

为什么：已推翻的误奖多是“主路径修好了，旁边的行为被改坏”，脚本可以先筛一遍。只打标记、不改分，留给审计判断。

4

一次审计：静态审查和轨迹审查合并

审计 agent

只审成败混合的题和被标记的题。步骤固定：列出要求，查测试覆盖，逐个判断真实答案，给出结论。每题不超过 45 分钟。

为什么：已发现的误奖都是读真实答案才发现的。MiMo 也是先跑 4 次，再按固定步骤审计。这样一次就能看清题和测试两方面的问题。

5

按仓库成批修订

修订 agent + 脚本验收

只修被真实错误答案证明存在的漏洞。每题最多加 3 个检查，只改 1 轮，外加 1 次小修。修完后，判为正确的答案必须仍然得 1，否则撤回修订。

为什么：防止越修越严：外部实验中加固测试后，正常解的通过率从 76% 降到 65%。每批只升一次材料版本，以前曾 5 小时连升 7 版。

6

Codex 按批复核，随机抽查后准入

Codex

每批复核一次：全部修订、推翻原结论的判断，以及 15% 的准入题。另外随机盲抽得 1 和得 0 的尝试，估计噪声水平。

为什么：允许有噪声，但要量出来：误奖 ≤10%，误拒 ≤5%。同一根因如果集中出现在一个仓库，就按仓库整体处理。

给审查 agent 的四条硬规则，防止无限发挥

  • 反例只认四种来源：模型的真实答案、每题至多 1 个退化补丁、历史上正式评过分的错误补丁，以及 gold 与 noop。不允许自己再造。
  • 每加一个检查，都要能拒绝一个已经观察到的错误答案，并且有公开依据。
  • 预算用完就按默认去向处理：淘汰，或只作诊断。超时永远不会变成准入。
  • 复核只能通过、驳回或改措辞，不能新增反例，也不能要求重审。
