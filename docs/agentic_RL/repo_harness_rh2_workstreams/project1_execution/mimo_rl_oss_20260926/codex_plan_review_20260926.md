## 2. 第一部分应纳入的修改

### F1：评分脚本读取不完整；抽样框与风险分层会漏题

**当前行为与证据。** `analyze_v0.py:82` 的 `grading_scripts()` 只读 `mimo_test_command.sh` 和构建包里的 `.sh/.py`，不读补丁直接添加的 `usercase-test-coderl/usecase.sh`。外层脚本经常只是 `exec bash .../usecase.sh`。`language()`（104 行）先按测试文件扩展名多数决，也可能把测试辅助工具语言当成任务语言。计划第 3 步只在已判 Python 的集合抽查，不能有效发现被排除的 Python 题。

具体反例：

- `002942`：v0 判 Python、`script_flags=[]`，实际内层脚本执行 `python -m pip install --no-index --no-build-isolation ...`。它是本地安装需求，不能进一步说成必须联网。
- `000673`（bsdetector）、`002469`（blueprint_book）：v0 判 `other`、无脚本标记，但内层脚本对目标仓库做 Python 可编辑安装并验证 CLI；至少应进入 Python 语言复查队列。
- `000349`：Python 标签来自 `fixtures/registry_mock.py`，主测试实际执行 `make cmd` 后验证 image-syncer CLI；不能据这个辅助文件认定目标实现语言。
- 仅补读这些 `.sh` 后，原正则在 31 道题产生额外匹配，其中 4 道原标 Python。**31 不是确认漏掉的风险题数**：`make([]byte...)` 和报错文本里的 “make a fresh request” 也被 `compile` 正则命中，说明还需区分命令、内嵌代码和字符串。

**不变量与影响。** 清单必须区分“未见风险”与“相关脚本未覆盖”。否则普通层混进安装／构建题，而语言假阴性永远不参与 Python 抽查，改变第二部分的样本分布。当前是本机静态分析缺口，不是 RH2 运行故障。

**建议分期与最小修法。** 本轮 v1 完成前修：收集补丁内被入口调用的脚本、构建包、命令清单；记录引用关系与未取得的镜像内脚本。无需实现通用 shell 解释器。语言记录目标仓库语言、验证工具语言及置信度；未知保持未知。`pip/local_install`、网络下载、本地服务、构建分别记线索，不能合并成“必须联网”。

保留 30 道抽查，但按题面层、工作目录、构建包和规则置信度覆盖；每个风险除了 5 个命中案例，也选未命中／脚本未覆盖案例。另从 `other` 和其它语言中定点查 shell 入口及混合语言题。不建议机械增加第二份随机 30 题；独立复核优先检查这些边界和修正规则。

**复现与验收。** 运行 §6 探针，查看 `extra_shell_matches.json`、`selected_examples.json`。v1 应覆盖上述案例、保留命令证据与 unknown 状态；重新报告各抽样层分母和与 v0 的变化，再生成正式样本。不能用 30 道内部抽查宣称全表语言或风险精度。

### F2：包名线索不能直接成为 D3 的仓库隔离键

**当前行为与证据。** 计划 `part1_plan.md:93–98` 准备按仓库线索归组，未知仓库仅排除留出。v0 的 `package_key()`（125 行）可能取依赖名或测试目录，`REPO_RULES`（224 行）又是一套独立规则。已发现三个内部不一致：`001261` 匹配 moto-5725、`002373` 匹配 pydantic-5624、`002376` 匹配 pydantic-9111，但三题的 SWE-Gym `repo_overlap` 都为空。`002870` 的线索是 `jax`，计划人工注释却是 rljax；`001178` 取到了测试目录 `codespec_tests`。

**不变量与影响。** D3 已决定按真实仓库隔离，不能把 import 名当身份。只禁止“仓库未知题进入留出”还不充分：把未知题放进训练，也可能污染已知仓库的留出题。当前 65 / 44 是规则命中数，不是已确认的完整仓库重叠数；596 是不同 `pkg_key` 的数量，不是已确认的仓库数。

**建议分期与最小修法。** 本轮建立 `repo_candidates / repo_identity / evidence / confidence / unresolved_reason`，精确字段与推断分开。同 issue 人工确认后，把已知参考库身份回填，统一旧名、新名、fork／上游关联；模块名和 GitHub 提及保持线索。issue 组、规范仓库组、跨池连接关系分别保存，并在全部拟用来源上检查划分冲突。身份未知题可继续调查，但不能默认分到训练后宣称 D3 隔离已成立；拟纳入正式划分时再核实。

查重不必立即上大模型检索。先保留规范化正文 hash、issue/PR URL、已发现的文字／测试名称／测试内容关系；人工看高相似但未过阈值的候选。v0 近重复只对倒排召回的前 10 个候选评分，且正文改写也会漏检，所以“没有发现匹配”不能写成“逐题重叠确为 0”。

**复现与验收。** §6 输出 `known_issue_repo_gaps` 应展示上述三题；v1 三题的 issue 身份与仓库身份一致，`codespec_tests` 不能成为已确认仓库。所有分组边有依据，未决身份和跨池冲突可被划分脚本显式识别。无需为完成本轮元数据清单而拉完所有镜像。

## 3. 第二、三部分在执行前补清的事项

### F3：借来的 gold 应先叫“移植候选正对照”

**当前行为与位置。** `part1_plan.md:106,112–115` 把上游补丁称为已知正确修复，将“打不上”归因为 base 不同，并允许换题；“打得上但失败”列为误拒候选。后一个作为线索可以，前两项的因果和正确性说得过满。

**证据、不变量与影响。** 14 道同 issue 题未发布 MiMo base commit，且大部分换了验证器。同 issue 不保证相同源码初态、依赖或验收范围，`git apply` 成功也不证明语义正确。原项目的统一标准 §4–5 已明确 gold 不决定公开要求。补丁应用失败还可能是路径、脏树或部分修复等原因，不能一律记成版本不同。若把这些失败归入误拒，会夸大验证器问题。

**建议。** 4 道对照保留。上机先封存镜像 digest、HEAD、实际工作树差异及目标文件；对照两边公开需求、补丁修改位置和失败症状。结果至少分为：应用不兼容／已经部分修复／环境阻断／有效候选被测试拒绝／有效候选被测试接受／未知。只有独立核实候选满足 MiMo 的公开要求后，才把它当正对照并讨论误拒。

“打不上换同仓另一对”改成“原题保留失败和原分母，另按预登记顺序增加比较题”；不要让替换后只剩可移植题。原始样本与追加对照分开统计。

**复现与验收。** 静态复现为比较 15 对原文及 `same_issue_candidates.json`；运行部分尚未验证。第二部分每对必须带初态、移植状态、公开行为证据和失败阶段；“上游 gold + apply 成功”不能单独满足正对照验收。

### F4：原始评分协议与 RH2 适配应分层核验，保留日志和独立初态

**当前行为与位置。** README 45 行写“只有退出码，看不到逐测试结果”；计划 165 行说按固定评分流程做断网 noop、失败后联网、非 root 复跑，但没有明确每次的状态重置及原始结果与健康诊断的记录方法。

**证据。** 官方 [opensource_code.py](https://github.com/XiaomiMiMo/mimoagent/blob/467f0a19016f0ac4d63b8d17a1f0da9ba07f232c/src/mimoagent/environments/datasets/opensource_code.py#L190-L251) 在评分前恢复测试补丁触及的路径，再应用完整测试补丁并执行命令；返回原始输出、returncode、耗时，并为 reset/apply 失败附错误类别。它的原生模式是 solver 与 grader 共用文件系统；不能只运行命令就说复现了来源协议。数据确实没有统一 F2P/P2P 映射，但测试日志可能含逐测试结果。官方 verl runner 只保留 `test_output` 末 5,000 字符，诊断时不能只存这个摘要。

另一个具体状态反例：`002430` 的评分脚本会创建 venv、安装依赖并写 `.stage3a_pytest6_deps_installed`。在同一容器先联网再断网，会改变后续试验的含义。

**不变量与影响。** 失败必须能归因，重复实验必须有可比初态。退出码非零可能是断言、收集、安装、服务、超时或测试未运行；来源 reward 为 0 不等于已经证明是模型失败。官方返回了部分错误分类，也不意味着其所有异常都分类完整。

**建议与验收。** 第二部分开始前写清：

1. 固定来源协议、镜像、输入 patch 和具体运行 profile；各条件使用独立新容器或可证明恢复的同一快照，保留初态脏文件，不能盲目 `reset --hard` 清空任务初态。
2. 分列原始 reward、reset/apply 状态、准备／安装、测试执行、服务、超时、完整 stdout/stderr 和耗时。能解析时附逐测试诊断，不能解析就保留 unknown；本轮不改 reward 语义，也不强造 SWE 的 F2P/P2P。
3. 联网仅作为失败归因变量；区分“准备阶段供包后断网测试”与“测试本身依赖外部网络”。按已批准的网络 profile 对照，不把未来供应机制当作当前已验证条件。
4. 来源兼容性与 RH2 可用性分别下结论。非 root 重跑私有评分不足以证明 actor 能开发；使用既有公开读者→命令清单→真实 actor 流程核对导入、相关测试、CLI／构建。正式评分接入还要验证候选交付、解释器、工作目录与 fresh grader 中的依赖语义。

复现证据为上述官方代码和 §6 保存的 `002430` 脚本；容器实测待第二部分。验收应可区分“一次来源评分成功”和“一次 RH2 开发／交付／评分成功”，不得混写。

### F5：先明确公开需求，再取自然候选；候选通过不自动成为正确答案

**当前行为与位置。** `part1_plan.md:166` 写先强模型求解 2–3 次、得到正对照，再静态审查。若照字面顺序执行，容易用已过分的解反推题意，还会给明显环境阻断题花 API。

**依据与影响。** 统一标准 §7.1 的公开读者须先看公开材料，§2 要求需求—断言证据、noop 和正对照；§5 允许经独立核实的替代解，不能按 reward 选“真值”。MiMo 没有原始 gold，使这层核实更必要。README 中 Home Assistant `001505` 只因题面没写 `expire_after` 就称误拒也偏早：尚未检查当时公开代码／文档是否已有约定。

**建议。** 顺序改为：轻量公开需求与私有测试检查→原生环境及公开开发路径→盲于隐藏测试的自然求解→独立核实可行正对照→需求—断言核对、必要的退化探测和误拒调查。测试、上游修复、借 gold 报告与审查线索不进入 solver 的公开包；派生正对照记录公开输入、生成方式、补丁和核实依据。

2–3 次自然候选可以是首轮安排，不应被解释为证明可解性／不可解性的阈值，也不替代 D5 已定的“按问题停止，不按次数宣判”。全部失败保留难度／环境／规格未知；有成功也检查核心覆盖。缺陷、功能、来源重合对照和工程难类分别统计。

**验收。** 第二、三部分 brief 引用现有公开／私有角色边界；在候选运行前已有公开需求记录，正对照有独立语义依据，至少能按现有标准解释 noop、正对照、决定性断言和退化候选。未知保持 conditional，不因没有 gold 批量淘汰，也不因强模型得 1 批量准入。未执行这些检查的题不能冒充已验收。

4. **给第二部分补一份短执行说明。** 明确来源评分调用链、各实验初态、原始 reward 与错误诊断、对照补丁核实、actor 开发条件、资源观察和停止方式。普通元数据阶段不先开发 MiMo 的正式 RH2 scorer。

第一部分到“来源冻结、字段边界可读、已知误分修正、同 issue 逐对确认、未知身份显式保留、样本可复跑”即可收口。**不要求解决全部匿名仓库、不要求证明零污染、不要求提前为 2,698 题做质量审查。** 容器事实留给第二部分；没有 gold 的最终资格、材料修订机制和正式评分异常映射在来源接入设计中处理，不能靠本轮清单暗自决定。

决策分类：当前第一部分没有必须新增的训练语义决定；按仓库划分、D1 严格版、每批 12 题及独立核实替代正对照的原则已有依据。D4 的原文场景是 gold 不能通过有依据的新断言，不应把它扩大解读为已批准所有无 gold 题。MiMo 的具体正对照证据要求和评分接入语义随接入方案确认；不重新请用户表决已有原则。

审查维度：本轮主要覆盖 A（数据／失败归因）、B（抽样分布）、E（验证器与对照）、F/H（既有决定／来源版本）、I/L（分期与资源）、J/K（规则与接入复杂度）、M（异常可诊断性）、N（上游版本与适配）；C/D/G 只核对未来接入边界。本轮没有运行时 owner、并发、恢复、GPU、在线样本拒绝或正式训练闸门变更，因此不做这些边界的集成验收或强制子代理调查。
