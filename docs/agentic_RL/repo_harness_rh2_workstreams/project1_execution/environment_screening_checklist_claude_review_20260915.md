# 环境筛查清单与试运行安排：Claude 的意见

2026-09-15 · Claude / B 线 · **讨论意见，未定案、未改代码。** 对象：[40 项清单](environment_screening_checklist_20260915.md)、[试运行安排](environment_screening_pilot_20260915.md)、[环境文献专题汇总](../../../harness_improve/external_paper_references/environment_processing_survey_20260915/README.md)（含 01–07 章）。参照：[已批的第四组决定与实施计划](batch4_scoring_20260910/README.md)、[接线状态](swe_grading_wiring_20260915.md)（§6.10–6.12）、[09-11 两份流水线稿](env_probe_20260909/env_pipeline_design_20260911.md)。

## 0. 结论

1. **40 项作为"检查目录"是完整的。** 把我们已知的 11 类现象（09-11 稿 §1）、三轮接线审查发现的 43 条选择器错配、parser 整份日志回退、超时丢日志，以及清单 §11 的校准案例逐条映射，每一类都能落到至少一项；没有发现漏掉的问题类别（映射见附录 A）。清单里"怎么查"的方向也与外部做法一致：可执行验证与题意检查分开、通过题也要审、替代解与错误解成组、修题保留原版。
2. **它还不是一条能跑的流水线。** 40 个问题回答的是"查什么、怎么查"，没有回答"一道题的记录长什么样、什么事实由机器产出、什么事实触发 agent 深查、达到什么证据才能进哪一档、仓库配方和派生镜像怎样版本化、训练 reward 到底用哪份参考集"。这些不定，几十个 agent 包产出的就是几十份自由文本报告，第 40 项要求的漏检率、误杀率、成本统计算不出来，第 39 项要求的"共享修复重验受影响题"也找不到受影响集合。试运行安排解决了组织问题，没有解决记录与判定问题。
3. **建议不改清单内容，另补一页"流水线定义"**（对象与记录字段、状态与处置规则、自动事实层与触发表、配方与修订工件、默认策略、产物与统计），然后按试运行安排执行，但第一包先跑自动事实层，让 agent 从事实表出发而不是从原始日志出发。下面 §1 是缺口，§2 是逐项意见，§3 是外部做法里尚未吸收的部分，§4 是实施安排，§5 是怎样检验清单本身，§6 是需要你决定的事。

## 1. 结构性缺口

### S1 · 每题记录的字段与状态没有定义

现状：清单 §10 说"每题最低产物：一段可用性结论和适用条件……复用现有 JSONL 与文件目录"；试运行安排 §6 说"每题几行结论＋证据引用"。这在 6 题试点里够用，在 216 + 48 题、之后几千题时不够：无法聚合、无法抽样、无法比对两个 reviewer。

建议（不要求新平台，只要一个 JSON 形状）：每题一份 `screening_record.json`，字段大致是——`task_id / source / revision_id`；`recipe_id`（仓库-版本配方版本，见 S4）；`env_asset`（原镜像 digest 或派生镜像 image ID 与配方）；`policy_digest`（grader profile + 网络四段声明）；`runs[]`（指向 driver 账本行：gold / noop / 候选 / 重复）；`facts{}`（自动事实层产出，见 S2）；`checks{编号: {status ∈ not_checked|pass|issue|unknown, evidence[], by, model}}`（40 项逐项，默认 not_checked）；`issues[]`（类别、严重度、证据、修复引用）；`revisions[]`（见 S5）；`disposition{state, min_evidence_met, reviewer, model}`；`costs{machine_minutes, agent_tokens, human_decisions}`。driver 账本（§6.5 已有）是运行级，这份是题级；两者用 `run_id` 关联。

### S2 · 自动事实层与触发表没有写出来

清单里 16–21 项本质上就是接线 driver 已经在做的事（安装退出码、导入路径、运行器摘要、参考缺席/跳过、段外解析、投影忽略路径、阶段耗时、内存、日志截断），2、8、9、13、14 也大半可以由脚本产出。清单把它们标成"执行＋分析"，试运行安排让每个包"跑真实基线、读阶段与逐测试结果"——这会让每个 agent 重新从日志里抠事实。应当先由脚本把 driver 账本 + sidecar + 静态预检（S1-p）+ oracle 账本合成 `facts`，再按触发表决定 agent 深查什么。触发表建议如下（事实来源都是现有产物）：

| 自动事实 | 触发的检查项 |
| --- | --- |
| gold 未 resolved | 6、7、9、12、13、17、18、19、20、27 |
| noop 未 tests_failed，或 noop 的 F2P 失败集合 ≠ 官方 F2P | 2、18、19、20 |
| `reference_missing` / `reference_skipped` 非空 | 19 |
| 安装退出码非 0，或导入路径不在 /testbed，或编译型版本串无 `.dirty` | 6、8、9、11 |
| `runner_integrity_changed` 为真 | 31 |
| 投影忽略路径含 official 精确文件之外的路径；候选触碰 conftest / fixture / pytest 配置（P-B 观测） | 4、17、31 |
| ×2 重复判定或逐测试状态不一致 | 12、14、15 |
| 内存峰值、耗时、shm 信号超过仓库画像 | 13 |
| 候选 resolved 但扩展回归失败（有轨迹时） | 25、26、35 |
| 轨迹含出网、下载、恢复 remote、读取 .git 对象 | 29、30 |
| 镜像扫描：未来提交可达、tags/remotes 残留、site-packages 内目标包版本 ≥ 修复版、pip 缓存 | 29 |
| `test_patch` 触碰非测试源码 | 17 |
| 同仓库同 PR、补丁高相似 | 5 |

没有触发的题仍要抽随机样本做 23–25、35（§5）。

### S3 · 处置规则与最低证据缺失；"评测保留"没有轨道

清单 §10 列了五种处置（可进入能力探针、修复待验、争议待审、当前条件不支持、拒绝该版本），但没有说每种处置要哪些项达到什么状态。建议写成表（阈值可在试点后改）：

| 处置 | 最低证据（示意） |
| --- | --- |
| 训练候选（可进能力探针） | 1、2、3、6–9、11、13、16–21 自动层 pass；4、17、23 有 agent 简查记录；gold/noop ×2 一致；无未关闭的 P1 issue |
| 评测保留 | 训练候选条件之外：×3 一致；5 无与训练候选重叠且仓库分离；24/25 至少一组替代解/错误解；**没有任何修订触及题面或测试**；未被用于调参、调 parser、挑策略 |
| 隔离（带原因码） | 任一 P1 issue 未修：资产缺失、服务依赖、参考集错误、fixture 缺失、泄漏通道 |
| 待核 | 触发了深查但 agent 未收敛 |
| 拒绝该版本 | 材料错配、初态不含问题、无效修复题 |

"评测保留"是 09-11 稿 E6 就有的轨道，清单第 5 项提到"拟留出评测"却没有对应处置；而且外部资料（FrogNano、SWE-1.7）都把"按策略通过率调题"与评测分开——一旦某题被 refine 或用于选题校准，就不能再当未接触评测。这条规则要写死。

### S4 · 仓库-版本配方与派生镜像没有成为版本化工件

清单 §10 说"仓库负责人维护有版本范围的共性事实"，第 39 项要求共享修复后重验受影响题；试运行安排 §4 要求派生镜像用新标签并记录 image ID。但没有定义配方本身：安装串是否逐字来源、`eval_commands`、parser 版本、资源画像（cpu/mem/shm/超时）、网络需求（四段）、预置资产清单（wheel 缓存、权重、数据、服务桩）与 sha256、`pip freeze` 快照、适用版本范围。09-11 稿的 `EnvAsset` 就是这个对象。没有它，第 39 项的"受影响题"只能靠人记。外部资料里 SWE-rebench V2、ScaleSWE、MEnvAgent、SWE-smith 全部以仓库（版本）配方为一等公民，并且都强调复用配方不免逐题验证（汇总 README 第 5 点）。

建议：`recipes/<repo>/<version-range>/recipe.json` + 每次改动一个版本号；题级记录引用 `recipe_id`；派生镜像属于配方的一个版本。

### S5 · 参考集与修订政策没有定案

第 19、27、37 项都触及"expected 有错怎么办"，但没有说训练 reward 用哪份参考。09-11 稿的 P4 与 Codex 稿 §10 的三类划分已经收敛过：本地重验证必做；**训练 reward 的参考 = 上游 F2P/P2P（或 R2E expected），除非存在经复审的修订版本**；修订分三类记录（补资产不改参考；有证据的 ID 映射；改测试/题面/状态的修订版本），每类保留原版、差异、理由、复验结果、复核者。这一条要进流水线定义，否则第 37 项无法执行。

还缺一个默认：**参考集里的 flaky 项**（×2/×3 不一致的 P2P）怎么办。SWE-rebench 要求三次一致才保留，Prime 保留"至少一次通过"的 flaky 题。建议默认隔离该题（不静默删 P2P、不重试到绿），要么走第三类修订把该测试从 P2P 移除并记录。

### S6 · 分阶段网络默认与预置资产的自依赖检查

第 11 项只要求"盘点"。试点需要一个默认，否则每个包各自决定。建议沿 09-11 稿 §3.2：P0 预置联网（root，一次性，固定 sha256）；P1 agent 解题只通模型代理（rh2 rollout profile 现状；包源白名单是训练设计选择，rollout profile 的 `internal_services` 经 relay 已能表达，是否打开另议）；P2 评分安装离线 + 缓存；P3 测试 deny_all + 本地桩；P4 参考生成条件记录。标签 `build_needs_network`、`test_needs_service` 作为隔离原因码。

一条清单没写的检查：**预置的 wheel 缓存或派生层不能包含"目标包的已修复版本"**。D4 为 moto 做 `pip download` 时若把 moto 自身或其修复版拉进缓存，安装段的 `pip install -e .` 之外任何 `pip install moto` 都可能覆盖候选；pydantic 的 `pdm add pre-commit` 会重解析锁文件。第 6 项说"不要通过升级成已修复的目标库消除任务"针对的是安装步骤，预置资产也要同一检查（MiMo、Cursor 都记录过"镜像里的系统包已经修好"这一泄漏形态，汇总 04、06）。

### S7 · 盲解与求解轨迹的运行条件

第 30、33、34 项依赖真实求解轨迹，试运行安排说"solver 只接收实际公开材料"。但昨夜 24 条 DeepSeek 轨迹是在 Bash 出网未禁的条件下产生的（3 条下载了上游修复）；如果试点的盲解继续用 `cc_probe.py` 那种直接起任务镜像的方式，第 30 项的证据就被条件污染。盲解应走 rh2 rollout profile（deny 除模型代理、agent 用户、git-sanitize），或至少等价的隔离。这需要 A 线确认：rollout relay 能否把模型上游指向 DeepSeek 的 Anthropic 兼容端点；如果暂时不行，试点的求解项只能标"出网未禁条件下的调查材料"。

### S8 · 试点的量化验收与训练后回流

试运行安排 §6"收口看四件事"全是过程性的。建议加五个数：自动事实层覆盖率（多少题的 facts 完整无 unknown）、触发深查的比例、两个 reviewer（不同模型）处置分歧率、每题成本（机器分钟 + agent token + 人工裁定次数）、校准集检出率（§5）。第 40 项提到"求解与训练新发现回流审查"，但没有触发器与 owner：建议写死"每次 RL run 结束，always-fail 与 suspicious-pass（低分组里高 reward）任务自动进入待核，owner 为 B 线"，这是 DeepSeek V4.1 与 SWE-2 都在做的循环（汇总 02）。

### S9 · 缺"来源适配器一致性"这一层

清单按题与按仓库两层。还有第三层：来源适配器（SWE-Gym 的 fork 命令/parser/`-k`/`eval_commands`；R2E 的 `/r2e_tests` 布置、`run_tests.sh`、expected 精确匹配、venv 属主、git 历史里修复提交可达；将来 SWE-rebench 的结构化结果与重建）。接线三轮审查发现的问题（43 条选择器、parser 回退、超时丢日志）都是这一层的，逐题清单不会再发现它们，但新来源接入时会重犯。建议把 09-11 稿 E2"合同"写成每来源一张短表，作为接入新来源的验收单。

## 5. 怎样检验这份清单本身

- **校准集检出率**：§11 案例 + 09-11 稿 §1 的 11 类 + 三次接线审查发现的三类，每类至少一题，混入正常题，不告诉 worker 哪些是反例；统计漏检。
- **随机正常题深审**：抽 10 题（含通过题），做 23–26、35；统计误杀与漏检，Pydantic-5706 这类只在通过题里。
- **双模型分歧**：同一题由 Claude 与 Codex 独立产出记录，处置分歧率作为清单歧义的度量；分歧题交人裁定并回写清单措辞。
- **训练后回流**：第一次 RL run 的 always-fail / suspicious-pass 与筛查记录对照，看哪些问题类别没有被检出。
- **成本**：每题机器分钟、agent token、人工裁定次数；若自动层覆盖率低于预期，先补脚本再扩 agent。

## 8. Codex 复核回应（2026-09-15）

**主要缺口成立：目前有运行器和问题清单，缺少把运行证据整理成逐题事实、修订关系和处置依据的小工具与统一记录。** 但原稿已包含来源级检查、版本引用、参考修订和实际工作流要求；应把它们具体化，不宜描述成全部缺失。“已知案例都能映射”只说明覆盖已知问题，不能证明清单完整。

本轮读取全文、现有设计、第四组最新实施审查及当前 driver/manager 输出。已补[最小记录与处置约定](environment_screening_definition_20260915.md)，同步[清单](environment_screening_checklist_20260915.md)与[试运行安排](environment_screening_pilot_20260915.md)。**仅设计文档变更，未实现汇总器、运行远端实验或新增正式筛选规则；上文保留为 Claude 原意见，采纳范围以下表为准。**

| 意见 | 复核结论与调整 |
| --- | --- |
| S1 题级记录 | **采纳并精简。** 机器 `facts.json` 与人工 `screening_record.json` 分开；检查可稀疏填写，未列项为未检查，未知不填 0。运行引用用账本路径＋行号，附任务/候选/attempt；当前 `run_id` 是批次标记，单独使用会混运行。不新增公共 schema 或 policy digest。 |

另有四处执行建议需要调整：

1. **每题仍做简短的题意—测试对照。** 自动触发加随机深审适合安排昂贵的独立复核/反例，不能完全替代逐题语义简查；欠明确、弱测试的题可能没有任何执行异常。
2. **回归可复现靠记录具体测试和选择依据。** 保留轨迹失败、调用关系和公开要求线索，不写死“轨迹失败测试＋同包全测”；该范围既可能过大，也可能漏掉跨模块回归。
3. **校准与规模数字后定。** 若 worker 已看见清单 §11 的案例标签，应称已知反例回归；测盲检需另给干净上下文。10 个样本报告发现数，不估全池漏检率；全池 10% 和 1–2 天暂不作为承诺。
4. **不等待所有评分切片才整理事实。** 按[第四组最新审查 §5](batch4_scoring_20260910/impl_plan_20260915.md#5-codex-实施前审查2026-09-15)，P-C 可后置，e1 可继续。P-A 未接通时相关失败只记事实/限制；可信候选编译失败已获 A 授权，不因发生在 install 段就重开决策。未落地规则和隔离补丁结果仍须标清版本，不混作统一版本验收。

**下一实施片建议：**先人工整理一题验证记录形状，随后用一个只读汇总器复用 driver/sidecar/日志/来源参考，同时生成事实和来源对账摘要；无需另造重复的 `reconcile` 系统。再执行两个仓库小包，各 2–3 题，按实际缺口调整后扩量。记录/汇总归 B，涉及共享生产评分代码时按当批分工复核。

本轮无需把 §6 六项全部重新交用户批准：现有权限和参考规则直接沿用；正式评测划分、稳定性阈值、抽查比例留待试点证据；确遇未批语义或权限变化时再提出具体方案。
