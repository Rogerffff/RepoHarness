## 3. 本轮真正需要决定的四项

### A. 已确认的候选执行失败，在没有测试计数时也能给 0

**例子**：候选把合法 Python 源码改成语法错误，正确的测试入口在 collection 阶段失败，没有产生逐测试结果。问题已经由候选造成；若仍当 infra 丢组，模型会失去这类失败的负反馈。

**推荐**：允许可信归因于候选的编译、导入、收集等执行失败作为 reward=0。具体 producer 先只覆盖所选 adapter 已有依据的少量情形；复用环境资格/基线结果、测试阶段、退出与资源事实，不新建通用异常分类平台，也不每次追加 gold 重跑。原因不明时保留无 reward 及具体诊断；确定的配置/实现矛盾按既有 fatal 规则处理。

这不是把“空解析”全部改成 0：环境缺 Python、parser 用错、共享内存不足均不是候选失败证据。日志里出现 `SyntaxError` 也不能单独替代来源判断。

**为什么确实需要决定**：当前 [GradingReport 契约](../../../../../rh2/src/repoharness2/contracts/grading.py)要求 `tests_failed` 的四项 F2P/P2P 计数齐全，仅 `patch_apply_failed`、`test_execution_timeout` 允许无计数的 0。需要允许一种明确的候选执行失败表达，不能伪造四个 0，或借用 patch apply 类别隐藏实际原因。最终类别名称与兼容方案由实施 Brief 列明。

**另一选择**：近期继续把没有可信计数的此类事件排除，只做观测。改动小，但有系统性少收失败样本的代价。推荐前者，因为 reward 依据是“任务确实失败”，不应强制所有失败都必须先跑出逐测试计数。

### B. 按所选 adapter 明确解答文件与评分控制面，修正过宽 glob

**推荐**：对实际选择的来源先做有限规则：正常库源码，包括合理的 testing 辅助模块，应能作为解答重放；可信测试文件、测试选择与评分入口继续由评分侧决定。保留现有 official 文件运行期保护，B 给出具体目录/配置含义和对照工件，A 落通用投影及事实传递。

`conftest.py`、插件、`pyproject.toml` / `setup.cfg` 可能影响测试，也可能属于合法构建或依赖修复；不能改成“一概允许”或“一概删除”。先处理当前任务实际用到的接口，不现在构造适用于所有 SWE/terminal 的规则引擎。新来源的特殊能力以后按其任务契约决定。

**另一选择**：继续沿用粗 glob，暂时排除与它冲突的任务。短期省实现，但会缩窄训练问题类型；若仍留在任务集中却忽略正常修复，则不是可接受的等价实现。

**为什么保留 F2**：非 root 加文件权限保护确实阻止了“候选代码在测试运行时覆盖官方文件”这一条路径。stdout/插件缺口需要具体分析，不构成删掉这条保护的理由。检查保护时同时重放合法解，避免只测能拦攻击却误伤正确修复。通用抗作弊平台与整套新防线不在本轮推荐范围。

### C. 当前 Python SWE 范围只过滤可再生、非答案的缓存

**推荐**：允许在所选环境的工件规则中明确排除少量可再生成、不是解答交付物的缓存。具体路径先由 B 根据环境与工件确认；baseline、冻结及 fresh grader 视图一致修改，不能只在传输端偷偷丢文件。

**例子**：一次执行新建 500 个缓存文件，若逐文件重放，就会增加约 500 次对应操作；这是机制示例，不是当前运行的实测均值。过滤这样的缓存有直接收益。

不能把“所有 gitignored 文件”“所有 build/dist”“所有生成文件”作为通用排除条件：其中可能有锁文件、生成源码、编译成果或任务要求的输出；候选自己修改的 `.gitignore` 也不能成为评分输入的权威。未来 terminal 输出工件另按任务约定。

**另一选择**：暂保完整工件，测量后再改。可以接受，但继续承担冻结/存储/重放成本。推荐范围很窄的过滤，不顺带改变冻结工件作为唯一评分输入的原则。

### D. 支持普通文件变目录这一种合法变化

**例子**：旧解答含普通文件 `config`；候选删除它、增加 `config/default.json`。当前 `FrozenPatchArtifactV1` 在构造时因父子路径冲突拒绝，尚未到重放步骤。

**推荐**：允许“确实删除普通祖先文件，再增加普通子文件”的窄形态；验证实际评分投影后的操作仍包含必要删除，并保持 symlink/no-follow 边界。不要仅删除整个前缀校验。目录反向变文件等额外形态不自动包含在本次许可中。

**另一选择**：暂不支持并明确限制这类任务/解答。实现更少，但限制真实仓库的重构方式。此窄支持无需 GPU，也不改变 reward 算法，建议顺手确认。

注意旧例子 `module.py → module/__init__.py` 没有父子路径关系，当前能通过；不再用它证明本问题。

## 6. 进入环境筛查前的收敛方案（2026-09-15；B 及排期为建议）

**建议先修复已知会影响样本判定的评分缺口，再展开规模化筛查；少量真实 RH2 校准应与修复交替进行。** 不以“评分器已经没有任何问题”为开工前提。部分环境资格和候选失败归因，恰好需要小批实际运行才能建立；反过来，把已知误删解答、丢失负样本的评分器用于批量筛选，会把 grader 的缺陷变成数据分布偏差。

### 6.1 A：先保留事实与明确失败表达，细粒度奖励不用现在定

当前代码 `GradingReport.reward_scale_version` 只接受 `binary_v1`，resolved 必须为 1、unresolved 必须为 0；这不是整个项目将来只能二值。实施时先将三件事分开：

1. **真实执行与测试事实**：来源/参考规则版本、观察到的逐测试状态、缺席与跳过、运行阶段、退出和可获得的资源证据。没有逐测试输出时记录全局候选执行失败，不伪造 F2P/P2P 计数或逐 case FAIL。可在现有报告/sidecar 中保存可重算的明细，避免将来换配方就重跑环境。
2. **失败归因**：资格已验证的相同环境和入口下，候选引入语法/编译错误，且证据定位到候选变化，可以作为任务失败。缺库、拉取失败、保护性资源终止或原因不明仍不能直接归给模型。资格证据按环境/配方复用，不要求每次评分先重跑 gold。
3. **训练 reward 映射**：当前二值配方按已批准的候选失败给 0；已有可信测试结果保留，未来可按来源规则聚合细粒度分数。比如实际跑完 10 项、2 项失败，可保存这些结果；若导入阶段就失败，不能描述成“已观察到 10 项全部失败”。整体如何计分以后单独版本化，不在本次实现平均通过率等新算法。

最终类别及字段由实施 Brief 列清，覆盖 report → RewardFacts/准入 → 样本交付，确保可信候选失败不再走 infra 丢组。与 R2E 已批准的最小契约扩展由同一实现者协调：某条 expected 为 ERROR 的测试，观察到 ERROR 可能是来源合同下的匹配，不能用字面状态统一判训练失败。

### 6.2 B：早前的较完整讨论（后续已收窄为 §6.5，不作当前开工前置）

“排除文件”至少涉及三种不同动作：从冻结中省略可再生缓存；不重放候选对评分材料的修改、由可信来源恢复它；限制测试运行期间对该材料的写入。它们不能共用一个未经解释的 ignore 清单。**正常解答范围也不应变成“只能修改某份白名单里的文件”。**

| 材料 | 首版建议 | 需要防止的误判 |
| --- | --- | --- |
| 正常库源码与合理的 testing/helper 模块 | 保留候选修改，修正宽 glob 的误伤 | `pandas/_testing/_io.py` 这类源码不能因名字像测试而消失。 |
| 确认的官方测试、评分入口、参考结果材料 | 明确可信来源与恢复/注入规则；保留现有运行期保护 | 先前修改被恢复，不等于运行时无法再篡改；单纯应用 diff 也不等于完整恢复。 |
| fixture、conftest、插件、构建/依赖配置等混合职责材料 | 看具体调用关系、题目目标与来源配方，记录允许修改的范围和验证依据 | 修依赖、改 API 或更新 fixture 可能是合法解答；不能按扩展名/目录一刀切。 |
| 已确认的可再生非答案缓存 | 按已批准 C 的具体范围省略 | 不混入测试控制面规则，不让候选自改 `.gitignore` 成为权威。 |

**agent 的工作放在环境准备/校准阶段：**

1. 按仓库/版本读取真实测试入口、来源 `test_patch`、依赖配置与相关源码，形成可复用的规则草案；每题补充官方测试和实际冲突的例外。不要求逐文件穷举整个仓库，也不为每个 rollout 调一次分类模型。
2. 每条规则留下路径/模式、职责、具体处理方式、依据和适用范围，接入已有任务/环境材料；首版不另建配置服务或规则平台。程序检查路径存在、候选与可信材料是否冲突，再以固定版本执行同一任务的所有候选。
3. 如果一个 `test_patch` 同时改测试和正常源码，先核对各段职责及恢复顺序。不能直接冻结整份文件，也不能为让 gold 通过就默许候选源码被覆盖。当前实现若只能按整文件处理，真实冲突题先做针对性校准/修订，不把它悄悄算作合格或永久排除。
4. 不确定的普通文件继续保留，不凭猜测删除；只有确实涉及评分材料与解答边界的冲突才进入进一步复核。agent 可以用私有 gold 检查误伤，但不能据 gold 触碰路径生成“唯一允许修改清单”，也不能把特权材料传给盲解 solver。
5. 同一规则修改后复验受影响的题/版本；保留原候选工件、来源规则和结果，避免为调查评分变化重新采样模型。不能依据某个候选得分临时修改规则，再把新旧分数当成同一配方。

**规则要同时接受正反两侧验证。** 已有 no-op/gold 是起点；共享评分机制再配少量合法替代解和已知篡改反例。优先覆盖 testing 源码修复、合法依赖/fixture 更新，以及改写评分材料、跳过测试、伪造通过等机制；复用现存 24 条候选和已发现的冲突，不要求每道题完整跑一轮攻击—修补—求解 agent 系统。结果用来改规则、识别未覆盖能力，不能宣称有限反例通过就证明完整抗作弊。

可选的更小方案是：先只给当前 SWE-Gym 代表题维护人工核对的有限规则与已知误伤修复，暂不把 agent 规则提案纳入流水线。它的初始改动更小，但增加来源/版本后需要重复整理。**推荐前一种“仓库/版本共用规则＋逐题例外＋agent 辅助分析”**，与 B 正在建设的筛查流程更一致；前期成本主要是少量职责分析和对照工件，后续规则表达仍可调整。

本节保留作为后续流水线设计参考，不要求现在批准或完成整套步骤；当前首版范围以 §6.5 为准。

### 6.3 外部资料支持什么、没有替我们决定什么

### 6.5 B 首版收窄：现在移除 I08 默认通配，额外排除留给流水线（2026-09-15 后续讨论）

用户认为前一版仍过于抽象，提出更直接的方向。**Codex 推荐采用这个更小的方案，不将完整逐仓/逐题规则流程作为 I08 修复的前置。** 以下是具体修改边界与后续设计方向，未宣称代码已经修改。

**现在做：** 当前 SWE 评分入口不再自动传入 `DEFAULT_SWE_TEST_GLOBS`；默认 `test_globs=()`，取消 `*tests/*`、`*testing/*`、`test_*.py` 等名字通配对候选修改的剔除。修正真实 spec 构造入口和相关旧 oracle，不通过给 pandas/numpy 加白名单绕过。通用规则接口可保留，供以后经过确认的任务规则使用；本轮不要求新建字段、平台或自动规则生成器。

例如 `pandas/_testing/_io.py` 的修改原先命中 `test_glob` 而不重放；移除默认通配后，若它没有被其它明确规则列为评分材料，就应完整重放。代码名像测试不是排除理由，修改测试也不自动判作弊或给 0。

**这项删除的范围：** I08 的默认测试名通配。官方测试从可信来源恢复/注入、精确官方清单的现有处理、候选非 root 与既有运行期权限保护继续执行。空的“额外排除清单”表示不额外屏蔽其它候选修改，不表示关闭基础评分步骤。其它独立规则的合理性不能借本次修复一并宣称已经验证。

**以后在流水线中决定：** agent 按题目、测试入口和仓库代码检查有没有具体的评分篡改通道。发现某项候选修改应被排除时，说明修改会如何伪造/影响判分，以及为何该内容不属于合法解答，再落实最小范围的规则；未发现有依据的额外项，则清单为空，不强迫每题加限制。记录“当前检查未发现需要增加的规则”即可，不要求证明绝对不存在 hacking。分析方法、复核方式、是否按仓库复用、字段格式和验证力度全部留流水线设计讨论。

举例：假设某题的评分器从仓库内 `grader_expected.json` 读取判分答案，且它不是题目允许修改的交付物；候选修改它即可改变答案，则可以针对该材料恢复可信内容或不重放候选修改。相反，一个测试目录中的 helper 是本题需要修复的库功能，没有对应评分篡改依据，就不因目录名排除。

仍需如实保留的边界：当前 `test_files` 来自 `test_patch` 触碰的全部路径；如果其中混入正常源码，移除 glob 后仍可能被恢复/忽略。这是流水线要检查的具体冲突，不能把取消 I08 描述成所有评分输入误伤都已解决。默认通配撤销也可能放开此前被屏蔽的非官方测试修改，是否会影响某题判分应在该题检查，不预先用另一套全局通配补回。

**本轮窄 CPU 对照：** 使用真实 `HygieneRules` 与 `classify_control_plane_path`，只把默认 `test_globs` 换为空；`pandas/_testing/_io.py`、`pkg/tests/helper.py` 从 `test_glob` 变为普通候选，精确列出的 `tests/test_official.py` 仍为 `official_test_file`，既有保留名规则及普通 `src/fix.py` 的分类不变。此对照证明该窄改动的分类边界，不代表实际 driver/grader 已完成修改或验证；未运行 Docker、模型或 GPU。
