## 1. 检查对象与分工

验收对象是一道题在明确条件下的完整工作流：**来源版本、初始仓库、实际题面与可见材料、工具/权限/网络/资源、提交方式、评分材料与执行配方。** 同一个镜像，换了安装用户、测试选择器或公开输入，原结论可能不再适用。

- **执行**：固定执行器创建环境、调用真实 RH2 冻结/投影/grader、保存逐测试结果和阶段事实。一次运行可支持多项检查；额外诊断测试单列，不偷偷并入 reward。
- **分析**：agent 阅读题意、相关源码/文档/调用者，提出假设与修复，必要时运行最小反例。先保存基于求解者可见材料的解释，再查看 gold/隐藏测试，避免事后迎合参考解。
- **求解**：在独立上下文与实际 Claude Code 工作流中尝试完成任务，不提供 gold、隐藏测试或审查者提示。可先复用已有轨迹和补丁；需要新证据时再新增求解。

下面 40 项是检查责任和问题分类，可共享证据，不对应 40 个代码闸门。1–36 关注单题及其适用环境，37–40 关注修订与流水线自身。每题做基础检查与题意/测试对照；昂贵的替代解、攻击、全套回归、多次求解按风险和抽样加深。未做的检查保留“未检查”，不能因没有发现问题而记成通过。

## 2. 来源、初态与实际输入

| 编号 / 要查的问题 | 怎么查、发现后怎么处理 |
| --- | --- |
| 1. 题面、base、gold、test patch、镜像、expected、scorer 是否对应同一任务版本？ | **执行＋分析**：保存来源原件、版本与公开/私有材料映射，核对关联字段、补丁目标与初态；含子模块、二进制、LFS 或附件时检查材料完整性。错配先恢复对应材料；找不到则标缺失，不拼接邻近任务凑成通过。 |
| 2. 初态是否确实包含题目所述问题？ | **执行＋分析**：先记录镜像自带的已跟踪改动/未跟踪文件，再运行题面复现和真正的 no-op 评分，核查失败位置；不盲目清空初态改动。已修复代码、错误安装版本或无关报错可能掩盖初态，先恢复正确起点。未修改即完成目标的任务另列，不能计作有效修复题。 |
| 3. 求解者实际收到的输入是否完整、准确？ | **执行＋分析**：检查实际渲染消息和公开文件，含代码块、路径、错误信息、外链附件、编码与长度。补必要公开资产或修渲染；只拿原始 JSON 审题不足以发现实际输入丢失。 |
| 4. 可读、可改、可提交的范围是否支持合法解？ | **分析＋执行**：按第四组 B 检查默认测试名通配已取消，额外排除允许为空；核查配置、依赖、testing helper 等合法修改是否可交付。新增排除要说明具体判分影响及为何不属于合法解，并做正反验证；公开/私有测试按来源区分，已有官方恢复/保护保留。 |
| 5. 是否重复、派生自同一修复，或与拟留出评测重叠？ | **执行＋分析**：按仓库/commit/PR、补丁及题意检查跨来源重复、回移植与衍生关系。维护同族关系，再依拟测的泛化能力划分；同仓库不必自动全排除，但同题改写不能当独立评测。模型预训练污染另有不确定性。 |

## 3. 安装、资产与开发条件

| 编号 / 要查的问题 | 怎么查、发现后怎么处理 |
| --- | --- |
| 6. 历史依赖与工具链是否可恢复？ | **执行＋分析**：从冻结初态安装/构建，读锁文件、历史 CI 和实际错误，核对 Python、系统库、编译器及测试依赖；配方可引用安装快照（如 `pip freeze`），固定浮动依赖/自动更新。不要升级成已修复的目标库消除任务；属于题目本身的依赖修复不能预先代做。 |
| 7. 权重、测试数据、fixture、外部文件是否齐全？ | **执行＋分析**：真实运行相关加载路径，记录用途、准备阶段、来源版本和实际用户可读的位置；检查缓存/wheel 是否带入目标库修复或答案。静态资产预置后在实际条件复验，公开开发资产与私有评分资产分开。替换数据或删测试不是单纯补依赖。 |
| 8. 安装和测试能否在真实用户与权限下工作？ | **执行**：用实际 actor/grader 的 UID、HOME、cwd、PATH、缓存目录、conda 环境与挂载权限运行，导入等观测脚本也用对应身份。修镜像准备和授权目录；root 的成功不证明非 root 可用，不默认提权执行候选脚本。 |
| 9. 测试执行的确实是本次候选代码吗？ | **执行＋分析**：检查完整安装步骤、导入路径、版本、可执行文件与编译产物；安装非零却 resolved 必须解释，必要时用诊断性行为改动确认关联。`.dirty` 缺席或导入位于 site-packages 不能通用判错。修安装/缓存生效；可信候选编译失败按已批 A 归因，不把 RC 单独当因果证明。 |
| 10. agent 能否进行必要的本地开发验证？ | **执行＋分析**：在公开工作区按实际身份运行相关复现、公开测试、构建/启动命令，核对工具和输出是否可用。补必要工具、资产或说明；私有测试保持私有，但 agent 应有合理路径检查公开要求。评分环境可跑不代表解题环境可跑。 |

## 4. 网络、资源与稳定性

| 编号 / 要查的问题 | 怎么查、发现后怎么处理 |
| --- | --- |
| 11. 哪个阶段为何需要网络？ | **分析＋执行**：分别盘点准备、agent 解题、候选安装/构建、测试执行的访问需求，并记录来源 expected 的生成条件。静态包/权重可预置，文档可提供快照；确需联网的功能明确访问对象与策略后验证，不因断网失败就判坏题。 |
| 12. 测试是否依赖不稳定或错误的外部服务行为？ | **分析＋执行**：沿请求、mock 与断言追踪实际行为，用服务可达/不可达或受控服务作有目的对照。检查异常类型、过期数据和“两边都下载失败所以相等”等假通过。录制回放/mock 需说明是否保留目标语义；稳定不了则标当前条件不支持或待修。 |
| 13. 资源与期限是否造成假失败？ | **执行＋分析**：按安装、测试、求解分别记录 CPU、内存、shm、磁盘、进程数、超时与 OOM 事实；在 gold、合法候选和代表性并发下复验疑点。校准资源档位，区分下载/排队与执行；候选死循环或自身耗尽资源另归因，不一律当环境故障。 |
| 14. 同一状态重复评分是否一致？ | **执行＋分析**：在固定配方的 fresh 环境重复 no-op/gold，比较逐测试状态及失败原因，不仅总分；异常和随机正常题加深。追查随机数、时钟、时区、locale、测试顺序及服务波动。固定次数复测，保留全部结果；三次稳定只提供有限证据，不重试到绿后隐藏失败。 |
| 15. 重置、缓存复用与并发是否改变题目？ | **执行＋分析**：按仓库/版本组比较独立运行、连续复用和小规模并发，检查残留文件/进程/数据库、共享缓存、端口和资源争用。修重置或隔离，保留已验证的缓存；代表测试不能外推任意并发，也不要求逐题穷举全部机器组合。 |

## 5. 真实 RH2 评分的可解释性

| 编号 / 要查的问题 | 怎么查、发现后怎么处理 |
| --- | --- |
| 16. 候选是否被完整、准确地交给 grader？ | **执行**：实际工作区经过 RH2 冻结、投影与 fresh grader，核对允许提交的文件状态。用代表补丁覆盖已提交/未提交/新文件、删除/重命名，以及来源实际使用的其他文件类型。修导出或重放；文本 diff 可读不能替代真实交付验证。 |
| 17. 可信测试与配套文件是否正确恢复，且没误删解答？ | **分析＋执行**：核对官方测试、helper、fixture、配置与注入/安装顺序。特别查 `test_files` 从 `test_patch` 全部触碰路径生成时，是否仍把正常源码恢复覆盖；取消 glob 不消除这一残余。混合职责逐题处理，不因文件名带 `test` 排除。 |
| 18. 正确的测试是否真正执行完？ | **执行＋分析**：按实际 runner 对照选择器、收集 ID、执行事件、完整命令及退出路径，覆盖特殊 runner、额外 eval_commands 与管道错误；利用已有 JUnit/CTRF，不统一套 pytest。收集错误摘要不代表测试体执行，命令成功或日志含 PASSED 也不足以证明完成；修错选/漏选及吞错误。 |
| 19. parser 和 expected 是否表达正确的测试身份与状态？ | **执行＋分析**：原始日志→逐 ID 结果→参考集逐项对账，检查 ANSI、转义、参数名、重复 ID、MISSING、SKIP/XFAIL/ERROR。有证据的映射修 parser；真实 expected 缺陷另审。R2E 原始 expected 可含 FAILED/ERROR，不能自动改成全部 PASSED。 |
| 20. no-op 与 gold 的分差是否来自目标行为？ | **执行＋分析**：二者同样走安装、测试注入和完整评分；区分 F2P（失败转通过）和 P2P（原本通过且应保留）。确认 no-op 的 0 来自问题未修复，gold 达到来源定义，不是无提交提前返回、安装失败或零解析凑出 0。原有无关失败单列分析。 |
| 21. 失败原因有没有被总分或重试隐藏？ | **执行＋分析**：记录准备、补丁应用、安装/编译、导入/收集、断言、解析、超时/取消及平台错误。第四组 A 已允许可信归因的候选执行失败作为负信号；当前二值表达可为 0，不伪造未运行测试的计数。资源保护终止、未知原因与 scorer bug 不能据此给 0；具体 producer/运输按实施记录核验。 |
| 22. 与来源 runner 的差异能否解释？ | **执行＋分析**：固定材料和可比条件，在独立环境运行来源 runner 与 RH2；先比重放文件、安装产物、测试集和逐 case 状态，再比总分。接线缺陷修接线，来源错误留反例，条件差异另记；不以“追平官方分数”作为唯一目标。 |

## 6. 题意、参考解与测试是否公允

| 编号 / 要查的问题 | 怎么查、发现后怎么处理 |
| --- | --- |
| 23. 要求是否充分、相互一致，而且可由公开材料推断？ | **分析**：盲审先读题面、相关文档、调用者和旧测试，写出目标行为/约束/未知项，再对照私有材料。区分正常需要查代码与真正缺信息；题面错漏提出最小补全，仍有争议则待审，不能看 gold 后倒推“显然如此”。 |
| 24. 测试是否错误地强制唯一实现？ | **分析＋执行**：检查新 helper 名、内部调用顺序、非公开布局与精确字符串约束是否有依据；构造满足公开要求但不同于 gold 的合法替代解。若被拒，修无依据的断言；真正的公共接口/格式约定仍需保留。 |
| 25. 测试是否会放过错误或不完整的修复？ | **分析＋执行**：把题面原例与关键要求逐项映射到检查；针对缺口构造部分修复、硬编码或错误分支。错误实现仍获通过才形成具体反例。补有依据的行为检查；覆盖率/变异存活只是线索，等价变异存活不证明缺陷。 |
| 26. 修复有没有破坏原有合理行为？ | **分析＋执行**：沿修改 API 的调用者、类型、边界/异常、相关模块及轨迹失败线索选扩展回归，记录具体 ID/命令与选择依据，在 base/gold/candidate 上对照。确认新增破坏而非旧失败或无关要求。Pydantic-5706 可校准；不强制同包全测，也不局限同目录。 |
| 27. gold 本身是否正确、完整且与本题对应？ | **分析＋执行**：拆解 PR 中多项改动、参考解、测试依赖和题面范围，复验目标行为。允许 gold 也有缺陷或依赖未交付修改；修材料/参考解或明确任务修订，不能为了保住 gold 而调低测试标准。 |
| 28. 新增检查与“修复方案”有没有引入审查者自己的要求？ | **分析＋执行**：每条新断言/题面改动关联公开需求或合理回归依据；用合法替代解和已知错误解双向复验，由独立审查者核对。代码风格、可合并性与功能正确性分别记，不把未约定的审美或唯一架构要求偷偷变成失败条件。 |

依据：[SWE-rebench V2](https://arxiv.org/html/2602.23866v2)将可执行验证与题意检查分开；[OpenAI Pro 审计](https://openai.com/index/separating-signal-from-noise-coding-evaluations/)明确讨论欠明确/误导题面、过严测试与低覆盖测试。[FrontierCode 等专题记录](../../../harness_improve/external_paper_references/environment_processing_survey_20260915/02_model_environment_recipes.md)提供正确替代解与错误解的双向检查经验。这里具体的检查组合与处置是我们的设计建议，不是任何单篇已验证的完整流程。

## 7. 答案泄漏与奖励漏洞

| 编号 / 要查的问题 | 怎么查、发现后怎么处理 |
| --- | --- |
| 29. 本地可见材料中有没有未来修复或私有答案？ | **执行＋分析**：以 actor 身份检查 Git 对象/引用、补丁、日志、缓存、预装包及可见挂载；抽查仓库总结是否混入读 gold 后的提示。清理或隔离并复测，保留任务允许的公开测试；只删 remote 或只查 `.git` 不足以覆盖已发现的通道。 |
| 30. 网络或工具能否直接取得本题解答？ | **分析＋执行＋求解轨迹**：区分查合法文档/装依赖与下载目标仓库未来修复，核对实际访问和获得内容；策略在真正的执行路径验证。记录受限/拒绝原因；已取答案的成功标明受污染，不计独立解题能力。提示词约束不等于访问已被限制。 |
| 31. 候选能否改写评分控制面或伪造成功？ | **分析＋执行**：按共享机制和题目特有入口检查测试删改、报告输出、插件/config、跳过测试及提前退出等反例。按第四组 B 决定是否需要额外路径处理，未发现依据就保留空清单；测试样路径触碰只是观测。新增规则同时重放合法解；发现 RH2 漏洞按试运行安排隔离修复，不据怀疑自动扣分。 |
| 32. verifier 有没有验证错误的性质或走捷径？ | **分析＋执行**：查看是否只匹配 gold 文本、文件存在、固定输出或错误的外部异常；用改变实现形式但保持语义的正例、保持表面特征但破坏行为的负例验证。改为检查任务目标；配置/静态接口任务可合理使用静态检查，不机械禁止 grep。 |

## 8. 真实求解与训练适用性

| 编号 / 要查的问题 | 怎么查、发现后怎么处理 |
| --- | --- |
| 33. 真实 Claude Code 工作流能否把任务做完并交付？ | **求解＋执行**：固定 CLI/代理/工具/公开输入、身份、网络、Git/材料隔离与预算，验证模型端点、工具交互、退出和交付，最终调用真实评分。替代 runner 说明已验的等价范围；旧出网未禁轨迹单列。脚本直接应用 gold 只验证交付/评分的一部分。 |
| 34. 未解出究竟是能力、环境、题意还是评分问题？ | **求解＋分析＋执行**：读取失败轨迹与候选，围绕具体阻塞运行最小反例；必要时独立换 solver，或由特权调查者构造验证补丁。特权补丁不算盲解成功，有限次数 0 成功不证明不可解；证据不足保留未知。 |
| 35. 已通过的真实解是否完整、诚实且无未测回归？ | **求解轨迹＋分析＋执行**：同样检查成功样本的补丁、下载、删改测试及题面原例，重放疑点与相关回归。发现假阳性、泄漏或过严测试遗漏时回流前述修订；不能只审核 unresolved。 |
| 36. 有效题是否适合当前基座与训练阶段？ | **目标基座求解**：在环境资格检查后测固定条件下的成功/失败混合、token、工具耗时与有效奖励成本；区分 grader 重试与独立求解。按能力/成本用于选题或课程，不能把模型 0/n、n/n 或慢题直接改标“环境无效”。 |

## 9. 修订、复验与流水线质量

| 编号 / 要查的问题 | 怎么查、发现后怎么处理 |
| --- | --- |
| 37. 修复究竟改变了环境还是题目定义？ | **分析＋版本记录**：区分安装/parser 接入修复、题面/测试纠错、改变任务范围三类，保留原版、差异、理由与结果。更改 expected、补规格或改 oracle 明确形成修订版；公共 benchmark 的修订结果不能冒充原版分数。 |
| 38. 修复能否在干净条件下由别人复验？ | **执行＋独立分析**：从冻结初态重建，复跑相关 no-op/gold、触发问题的候选/反例，以及必要的合法替代解；独立 reviewer 先看关键原始证据、复跑决定性对照。探索容器里的成功和同一 agent 自评不能替代这些证据。 |
| 39. 共享修复会不会破坏其他题？ | **分析＋执行**：标明 parser、安装配方、资产与保护规则适用的仓库/版本/题目范围，重验受影响项并保留无关正常对照。复用安装经验，不复用逐题合格结论；共享文件由负责人合并，避免并行 worker 相互覆盖。 |
| 40. 筛查流程本身有没有漏检、误杀与偏差？ | **分层抽样＋独立复核**：检查接收、拒绝、待审集合中的随机样本，并单列定向疑难样本。统计漏检/误排线索、修复复发、成本和仓库/长度/资源分布；求解与训练新发现回流审查。抽样率与阈值用试点校准，不从反例集外推全池坏题率。 |

## 10. 如何执行而不堆重复工作

具体分包、可复制派发卡、真实 CLI 入口、临时 worktree 补丁与复核交付集中在[试运行安排](environment_screening_pilot_20260915.md)，本节保留检查覆盖层次。

建议运行顺序：**来源/版本组准备 → 每题基础运行与公开视角审题并行 → 题意/测试/gold 对照 → 按风险设计反例和必要求解 → 最小修复 → 干净复验及独立抽查 → 分批扩池 → 运行后持续复审。** 与[最小评分接线](swe_grading_wiring_20260915.md)交错校准，不等待所有来源适配完成才设计输入/证据。

| 范围 | 建议承担的检查 |
| --- | --- |
| 来源 / 仓库＋适用版本组 | parser 与 runner、安装/测试机制、提交/可信边界、网络/资源/重置代表对照、共享运行知识；每题继续确认版本适用性和实测结果。 |
| 每道候选题 | 材料/实际输入核对、开发侧基本可用性、真实 no-op/gold 与逐测试对照、关键题意—测试—gold 分析、资产/网络/资源事实与未检查项。先发现且尚未修好的基础阻塞允许暂停后续昂贵检查。 |
| 异常、共享变更及随机对照 | 固定次数重复、较宽回归、合法替代解、错误解、独立深入审查；低覆盖和未标记的通过题也应抽到。不能因异常消失一次就停止计入失败。 |
| 实际 harness 求解 | 每个新工作流/版本组做基本贯通；对语义疑点、工具/网络需求不确定项、随机正常项增加盲解，先复用旧轨迹。目标基座大样本能力筛选另做。无需每题先成功盲解，才能积累环境资格证据。 |

复测初始建议改为：先各一次 no-op/gold，拟接受的试点题再各确认一次；已有同条件证据可复用，明确故障无需重复凑数。**不在本稿批准全池统一次数或稳定率门槛**，×3 也不等于评测有效；flaky 待诊断，不静默删 P2P。[Prime R2E Verified](https://huggingface.co/datasets/PrimeIntellect/R2E-Gym-Subset-Verified)保留 gold 重试中至少成功一次的任务；来源标签不能替我们回答重复稳定性。

**最小人员组织：**仓库负责人维护有版本范围的共性事实、调查和修复；固定执行器留运行证据；共享复核者独立检查关键语义/修订；solver 只接收实际公开材料。仓库负责人可调度逐题 worker，但其含 gold 的知识不能传播给盲审或求解上下文。遇到新问题允许增补假设与实验，不以清单未列为忽略理由。

**每题最低产物：**一段可用性结论和适用条件，原始/修订版本引用，实际运行与逐测试证据，问题/反例/修复关系，仍未知的内容；由[最小约定](environment_screening_definition_20260915.md)的 `facts.json` 与题级审查记录承接。可用性、稳定性、题目质量、泄漏、基座难度分开记，保留处置与检查范围；训练/开发/评测用途另记，不新建平台。
