## 2. 加快讨论的方法

### 2.1 按子问题分流，不给整个 I 编号统一贴“简单”标签

- **已有定案下的明确修正**：直接进入实施清单；T1 实现后报告，T2 留普通变更记录，不再逐项要求用户重复确认。例如 receipt 写失败已经要求 fatal 并继续清理，修掉旧分支是在落实既有规则。
- **有实质取舍，但推荐明显**：形成一张批量确认表；写明推荐、代价与适用范围，用户可整批采纳或只改个别项。不能把尚未证明等价的删除混进去。
- **真正的 T0**：每轮聚焦两三个决定。涉及 reward、训练覆盖、路由来源、预算终止、恢复或安全边界的，说明最有价值的另一种方案及其代价；不展开无关候选。
- **依赖运行结果的优化**：先决定当前保留什么、下一次正常作业顺手测什么；没有必要先实现全部候选再竞争。也不能把“待测”当作无限期搁置明确正确性缺口的理由。

这是现有阶段级批量确认的具体应用，不新增审批层，也不把用户未回复当作批准。讨论可以合并，实现仍按具体代码边界分成可验证的小批。

### 2.2 每轮只给一份短决策说明

正文默认一页左右，详细代码与已有证据用链接：

1. 现在发生什么：一个具体例子，最多两三句话。
2. 要决定什么，以及推荐方案和理由。
3. 最有价值的另一种方案，以及主要取舍。
4. 对训练分布、上下文、资源或维护的实际影响。
5. 哪些以后容易改，哪些改变会让历史实验不可直接比较。
6. 必要验证：已有证据、本机还需补什么、哪些并入原定 GPU/Docker 作业。

六项对应原协议的决策包要素，不重复贴源码全链和论文历史。普通 T1/T2 不机械套此格式。仅在证据冲突、生产路径不明或方案改变关键边界时，补窄追踪/反证；不为每项重新精读资料或重复运行相同探针。
