## 2. 加快讨论的方法

### 2.1 按子问题分流，不给整个 I 编号统一贴“简单”标签

- **已有定案下的明确修正**：直接进入实施清单；T1 实现后报告，T2 留普通变更记录，不再逐项要求用户重复确认。例如 receipt 写失败已经要求 fatal 并继续清理，修掉旧分支是在落实既有规则。
- **有实质取舍，但推荐明显**：形成一张批量确认表；写明推荐、代价与适用范围，用户可整批采纳或只改个别项。不能把尚未证明等价的删除混进去。
- **真正的 T0**：每轮聚焦两三个决定。涉及 reward、训练覆盖、路由来源、预算终止、恢复或安全边界的，说明最有价值的另一种方案及其代价；不展开无关候选。
- **依赖运行结果的优化**：先决定当前保留什么、下一次正常作业顺手测什么；没有必要先实现全部候选再竞争。也不能把“待测”当作无限期搁置明确正确性缺口的理由。

这是现有阶段级批量确认的具体应用，不新增审批层，也不把用户未回复当作批准。讨论可以合并，实现仍按具体代码边界分成可验证的小批。

### 2.2 每轮只给一份短决策说明

正文默认一页左右，详细代码与已有证据用链接：

1. 现在发生什么：一个具体例子，最多两三句话。
2. 要决定什么，以及推荐方案和理由。
3. 最有价值的另一种方案，以及主要取舍。
4. 对训练分布、上下文、资源或维护的实际影响。
5. 哪些以后容易改，哪些改变会让历史实验不可直接比较。
6. 必要验证：已有证据、本机还需补什么、哪些并入原定 GPU/Docker 作业。

六项对应原协议的决策包要素，不重复贴源码全链和论文历史。普通 T1/T2 不机械套此格式。仅在证据冲突、生产路径不明或方案改变关键边界时，补窄追踪/反证；不为每项重新精读资料或重复运行相同探针。

### 4.2 准备具体清单后，适合一次快速确认的部分

- **I05 异常分类**：先对照既有 D1，把确定的程序自相矛盾、确定配置不支持与局部 infra 故障列成短表。已属既有 FATAL 的落实不重问；新类别或改变现行处置的部分再确认，不提出“所有异常 fatal”。
- **I13 退出语义**：把“训练已完成、期限是否满足、资源最终是否释放”三个事实讲清；保持还是修改现有合成 verdict 可以一次决定，不能包装成免费 bugfix。
- **I22 恢复错配**：推荐使实际加载权重与恢复状态绑定；明确合法 override 的支持范围。只讨论该错配，不重开已批 B-3 的版本编号/冷恢复设计。
- **I24 额外 forward**：限定当前 GRPO/faithful DIS、零 KL 配方，讨论普通训练如何跳过、诊断时如何保留同版本对拍；不推广到 OPD/PPO 或直接删除唯一诊断来源。
- **I25/I26 确定重复的工作**：先列具体调用、不可变前提和唯一消费者，再确认去重/批量处理。fresh grader 的独立权限初始化与真实树检查不自动属于重复。
- **I33 窄原型退役**：优先准备 attempt_ledger、governed_buffer 及专用测试/导出的准确引用清单；单批处置。旧 ModelCallProxy、仍用的 CLI、历史验收与整个 slime adapter 不混入。

I23 的紧凑表示、I29 的已结束历史释放也可以很快形成方案，但须先证明保留了消费者仍需的数据和清理引用；不能把“最后一轮就够”“删所有历史”当默认。
