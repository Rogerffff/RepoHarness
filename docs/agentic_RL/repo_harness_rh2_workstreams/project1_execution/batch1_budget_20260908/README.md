## 1. 用一次修仓库任务串起四个问题

```text
占用执行资源 → 准备环境/启动 Claude Code
  → 请求模型 → 执行 Read/Edit/Bash 等工具 → 再请求模型
  → 正常结束，或预算触发停止
  → 收口模型请求与容器工作 → 确认停止 → 冻结文件变化
  → fresh grader 评分 → 决定哪些样本进入训练
```

这里分三个问题：为什么停、是否已真正停止且记录完整、完整记录是否参与训练。一个 `timeout` 字符串不能同时回答三者。评分阶段自己的测试预算和清理超时也不能被并成同一个 episode timeout；I07/I11 的评分归因留第 4 组。

| 问题 | 当前行为 | 具体例子与影响 |
|---|---|---|
| I02 请求次数上限 | 默认每 sid 放行 25 次模型 API 请求，第 26 次返回 429；没有相应 `max_turns_exhausted` 生产事实。 | 第 25 轮已修改文件，第 26 轮准备总结/再检查，却收到类似服务限流的错误。代码文案说 killing run，但 429 本身不停止 scope；实际 CC 怎样重试/退出尚未测。 |
| I03 多钟与排队 | harness 等 done marker 才起表，proxy 首个模型请求才另起表；两者不是资源占用时的同一 deadline。proxy 还在等待额度前算 timeout，等待后不重算。 | 假设同一 deadline 还剩 10 秒，却排队 20 秒，代码仍可能使用旧的 10 秒发请求。既有真实 proxy 窄探针已证 20ms deadline 后约 41ms 才 send；不代表生产频率。 |

## 2. 决定一：首版使用什么模型行动预算

**推荐：保留“请求次数上限＋执行资源墙钟”两种约束。** 请求上限明确策略可以再向模型请求多少次；墙钟防止执行长期占资源。首版复用现有请求计数，不同步新建累计 token 预算或“纯模型活动时间”系统。

请求次数的推荐口径如下：

- 每次 HTTP 请求通过现有前置校验、被 adapter 接纳进入渲染/模型调用路径，扣一次。它不是工具数，也不是成功生成轮数。
- 一次模型响应带三个工具调用，仍只扣一次模型请求；若首版允许子 agent，同一次物理执行的同 sid 请求共享预算，不各获一份 N。是否启用子 agent 仍归第 3 组。
- 扣次数后渲染/API 失败，现有计数不退；CC 另发 HTTP 重试也会再计。首版不增加语义重试识别/去重平台；实际 infra 失败仍按其事实处置，不能因次数用完就改写成正常策略失败。
- 对同一 HTTP 请求内部的引擎重算，不另算一次请求。通用 proxy 有重生成循环，但当前生产工厂是 `StaticActiveCoordinator`；不能宣称该 proxy 重试分支已在生产正常工作。这个接线事实不影响按入站请求计数的定义。
- 达到 N 后阻止第 N+1 次请求，并产生明确预算终止事实交给编排收口；不靠 CC 如何解释 429 推断结束原因。不在第 N 次结果尚未交付时仅因计数达到 N 就提前抹掉该轮。

**另一种选择：只保留墙钟，不设请求次数上限。** 少一个上限，但不同推理速度、排队与工具耗时将决定可获得的模型请求机会，单题请求量也更难控制。若同时选择墙钟截断不训练，较慢的未完成尝试会直接进入丢组面。

**数值分期：** 25 次、600 秒是当前默认，不是已验证合理的正式 SWE 配方。本次先定单位和作用域；首次真实诊断/训练作业的数值与 B 的任务预算一起确定，不为每个常量另开一次设计讨论。以后调整数值容易，但实验比较须记录预算变化。

**已有规则：资源墙钟从资源占用起表。** 这已在 06 A5-c 写明，不改为第一次模型请求或取得 GPU 额度后才起表。修 I03 应找到真实资源获取事件、生成统一 deadline 并下传；现有审计开始时间不能直接冒充已实现该 timeout。落实后准备/排队会占用总预算，可能缩短相对于旧路径的可行动时间；因此不能把原 600 秒称为完全相同的模型机会。grader、停止与清理仍各有有界预算，不在 episode 到点时连清理一起取消。

## 3. 决定二：正常用完策略预算，完整轨迹是否训练

**推荐：满足既有完整性、评分和资格条件时 KEEP_FULL。** 另一种选择是 DROP_GROUP；没有“只留下七人”或“保留 reward 但只 mask 该成员”的现成首版选项。

例子一：模型用了允许的 25 次请求仍未修好，最终冻结补丁经可信 grader 得 0。保留这条轨迹，能让策略学习在规定机会内完成任务；丢弃它会让训练更偏向早结束的执行。

例子二：第 25 次已经生成正确修改，工具执行后修复成立，只是模型没有第 26 次机会说“完成了”。grader 得 1，就按 1 训练。**截断不等于固定 reward=0，奖励来自实际评分。**

对 n=8，若 reward 是 `[1,0,0,0,0,0,0,0]`，其中一个 0 是正常请求预算截断：KEEP 时该成员与其它成员一起算优势并训练；DROP 时丢全部八个成员，不是少一个成员继续 GRPO。零方差过滤、staleness 等其它既定规则仍有效，KEEP 也不保证最终一定被消费。

两种选择的长期代价：KEEP 会训练预算约束下的策略，预算过紧可能大量 0 分、缺乏有效信号；DROP 会损失长/难轨迹及其正常兄弟，增加补采。首版推荐 KEEP，但不因此声称无任何长度影响。当前直接要接的是请求 cap 的 producer；已有枚举中的 token/context horizon 不等于全部已实现，本组不顺带承诺所有 producer。

## 4. 决定三：混有排队的 hard wall 截断是否训练

**推荐沿用 06 A5-b 的建议：hard wall 截断先 DROP_GROUP，单独记录真实原因。** 不把它伪装成 API 崩溃，也不因为可评分就直接认定是策略失败。

例如以下两次执行都在同一个 600 秒资源上限结束：

- A：大量时间在推理、改代码、运行模型请求的工具，最终未完成。
- B：大部分时间在等服务额度或主机资源，真正获得的模型行动机会很少。

现有计时不足以可靠地给所有执行分离这两种成分。选 KEEP_FULL 是把当前调度/机器条件也纳入任务环境；可以这样定义，但不能同时声称训练只反映模型本身的效率。

**另一种选择：把 hard wall 明确当作环境 horizon，完整可信截断 KEEP_FULL。** 同样用实际 grader 的 0/1，不自动给 0。优点是减少丢组并学习在该运行环境下完成任务；代价是模型结果会受排队、机器和资源调度影响，训练/eval 必须说明实际资源条件。

推荐 DROP 也不是无偏：慢/难执行更容易被排除，而且一个成员可拖掉整个 n=8 组。先用现有 drop/no-progress 和首批诊断判断预算是否可用；不新建“只扣 policy-owned 时间”的归因平台，也不新增自动阈值。本次两个方案都不覆盖已证 OOM、Docker/服务故障等已归因 infra/resource failure：D2/B 已规定它们不能伪装成 reward=0。

## 5. 停止规则已有决定，直接落实

预算耗尽应触发停止接收新工作，并有界收口在飞工作；确认动作/文件不再变化后才冻结和评分。停止宽限用于收口，不应成为另一段不受策略预算限制的自主行动时间；当前 wall 返回与真正冻结之间有延迟，不能宣称精确第 600 秒取得补丁。

- 停止成功、capture 闭合、冻结与评分可信：再按上述两个 disposition 判断训练。
- 最终已经停止，但 capture 不完整或其它事实不可信：不能冒充完整截断；保留对应失败归因，按既有规则处理。
- execution scope 最终无法终止：A4 已批 run-fatal，仍继续清理，不再让 owner 重选。
- 一次 drain 超时不等于最终无法终止；不能把所有超时一律升级 fatal。grader 等待取消、宿主 docker CLI 回收、容器测试停止分别落实到现有 owner，不另建服务。

I13 的综合退出 verdict 是否改变留第 2 组；本组不利用 I14 重写已批 B-6。资源 OOM 与测试超时的具体 reward 归因留第 4 组。

**建议的实施边界：**

- 本次不引入 SkyRL 的成员梯度 masking，也不增加专门训练消融。先保证选定语义能准确执行；预算大小在真实任务诊断时选择。
- 较宽 watchdog 仍从已有约定的资源占用起表，不在排队后重置。停止/清理有自己的有限宽限，不能因 episode 到期把释放资源也取消；具体数值后定。
- whole-group DROP 仍会排除较慢任务，一个成员到点会损失正常兄弟。复用现有观测，至少能看出触发数、丢组数、发生时已走轮数、总耗时及已有原因；已有排队耗时可直接使用，不建设新的精细归因系统或自动阈值闸门。
- 训练中 DROP 不自动决定评测分母。后续与 B 约定 base/checkpoint 在相同评测行动预算下比较，并公开超时/故障数及处理协议；训练和评测的预算可以不同，但应记录差异。本条是交接建议，不代 B 冻结评测设计。
