**第一组 I02/I03/I04/I14：决策反证与最小边界（2026-09-08）**

本轮只读 [06 计划 A2/A4/A5/A6](../../06-first-training-local-execution-plan.md)、[已批准的 D2/B v2](../../miles_spike/decision_package_D2_B.md)、[四项问题底稿](../issue_inventory_20260908/README.md)与对应局部源码；不写训练代码，不增预算归因平台，不运行新探针。以下候选不替 owner 拍板。

**先分清已定与待定。** A2/A6 的 n=8 整组合取、无 `MASK_MEMBER`、可信 0 分完整参与，以及 B-2 的 drop/no-progress 已批准。A5-a 确定性 horizon 与 A5-b 混合 hard wall 的训练处置仍待定。A5-c 已写明资源占用起表、正常 owner shutdown 不训练不补采、scope 无法终止 fatal；不应把 I04 的四个代码槽重新包装成四个全新的 T0。

**预算事实不能只按错误名称归类。**

| 边界 | 可以确定什么 | 不能据此推出什么 |
|---|---|---|
| 请求次数 / 累计生成 token / 上下文容量 horizon | 在计数单位、作用域与扣减规则已固定后，达到既定上限 | 任意 HTTP 重试都代表一次策略动作；枚举存在即已有 producer |
| `hard_wall_timeout` | 某个执行期限已到 | 等待时间都是模型行动时间；评分完整就能排除排队/主机抖动影响 |
| 已证资源限额 OOM/timeout | D2-2 明定为 infra/resource failure，不能伪装 reward=0 | 可以借 A5-b 的 KEEP 选项覆盖这个已定规则 |
| Python 等待结束 / drain 超时 | 调用者不再等，或尚未完成 drain | 容器/引擎内工作已经停下；所有 drain 不干净都等于永久停止失败 |

I02 当前计数是 `common.py:_check_turn_cap`（285–306）在渲染/发送前递增的 **每 SID 放行请求数**；第 26 次返回 429。后续翻译或模型调用失败也已消耗名额。这个上限不是工具调用数，也不是成功采样轮数；“确定性请求预算”须说明此差别。主/子 agent 同 SID 时共享预算，不能把子 agent 自动算成 n=8 的新成员。

**最小选择面。**

1. 请求预算可先沿用现有每 SID 放行请求口径与配置旋钮，明确重试/子 agent 的计数，再把命中上限接成真实预算终止事实，避免依赖 CC 如何解释 429。代价是请求重试也可能消耗预算。若要改为“只数成功逻辑模型调用”，须另明确定义失败/重生成的扣减规则；不必为此同步实现新累计 token 预算、重试平台或所有 horizon producer。
2. A5-a 的最小推荐仍是 **完整、可信的 `present_truncated` → KEEP_FULL**；另一种合法选择是 DROP_GROUP，代价是排除长/难任务及同组正常成员。必须先满足 capture、停止、冻结产物、评分、资格与版本等既有条件，KEEP 不能绕过这些条件。
3. A5-b 可以选 **DROP_GROUP**（沿用 06 推荐，避免混合墙钟被直接作为策略环境 horizon），也可显式选 **KEEP_FULL**（接受当前调度/排队条件属于实验环境）。前者仍会偏向较快完成的组，绝非无偏；后者可能把基础设施延迟对结果的影响带入训练。不能用“只训 policy-owned 时间”折中：06 已因缺真实分段归因而删去该选项。

**n=8 的实际取舍。** 假设可信评分为 `[1,0,0,0,0,0,0,0]`，其中一个 0 来自正常 horizon 截断：KEEP 时它仍参与组均值，均值中心化后成功成员为 `+0.875`、各失败成员为 `−0.125`（尚未除标准差）；截断成员也训练自己的动作。DROP 时按 A2 丢全部 8 人，不是只丢 1 人或留下 n=7。若把截断成员留作 baseline 却 mask 掉自身梯度，就是已经从选择面删除的 `MASK_MEMBER`。

“保留截断 = reward 0”同样错误：截断时补丁可能已经解决问题，应使用可信 grader 的实际 0/1。全组 reward 相同仍会被既有动态过滤排除；因此 KEEP_FULL 不保证整组最终被消费，也不自动产生有效梯度。DROP 后由持续 producer 的后续 prompt 补足，不是同 prompt 自动重试（B-2 已定）。

**资源占用起点不能悄悄后移。** 06 A5-c 明写 episode 从资源占用起表。若改成首次模型请求、拿到推理许可或真正开始 decode，已占资源的启动/排队时间就可能不再计入该上限；这是改既定资源预算，须显式提出代价和 owner 改判，不能叫作单纯修 timer。若确需新增模型行动预算，应保留原资源总墙钟；两者是不同约束，不要求首版新增第二套政策钟。

I03 已证缺口可独立修：同一既有 deadline 必须约束 semaphore 等待，拿到许可后重算剩余量，过期不得进入 send。至于把当前 harness/proxy 两个起点对齐到哪个实际资源获取事件，应指认真实生产事件与 owner，不能只把几个时长常量改成相等。cleanup/drain/grader 各自的有界收口仍有必要；不建议把它们合成一个会在 episode 到点时连清理也取消的大 timeout。

**停止失败的 fatal 已批，不再问一次。** A4 与 D2-3 已规定 execution scope 无法终止 → run-fatal，仍执行 revoke/终止/容器清理；B-6 已规定 shutdown 不干净 → 非零退出。D2-2 规定实际资源/隔离配置未生效时不启动或停止 run；任一 engine 死亡按 B-5b 停 run。把这些事实落实到路径是履行旧决定。

但不能反过来“所有超时都 fatal”：正常预算耗尽、可归因任务局部失败、最终成功回收的等待超时各有原有出口。`run_docker`（`grading/manager.py:95–109`）没有取消后的子进程回收；`_exec_bash_checked:1463–1470` 的 `wait_for` 超时只说明等待停止。杀宿主 docker CLI 也不能证明容器内测试停止。I14 应补齐现有所有权下的取消与回收，再核最终资源状态；不是重新选择是否允许遗留活动进程。

停止已失败或尚未证明停止时，不可先冻结一份仍在变化的 workspace 再宣称“完整可信截断”。另一方面，grader 阶段的 infra failure 按现有 Outcome 契约保持评分不可得的形状，不能只看到 D2-2 的 ABORTED 概述就把所有阶段一律改成 missing；本组不改写 I07/I11 的评分分类。

**必要验证清单，实施时一次有界完成。**

- I02：真实 adapter 入口覆盖第 25/26 次、一次请求多工具、同 SID 子请求、请求失败后再请求；核计数与真实终止事实，不靠“收到 429 必然 crash”的猜测。内部重生成是否增加请求数按实际调用层检验。
- I03：复用已有 semaphore 反例，检查过期排队不 send、许可不泄漏、获得许可后只用新余量；用可控时钟覆盖 harness/proxy 到期先后，确认预算终止不会仅因先观察到 proxy 错误就伪装 API 失败。
- I04：从实际启动配置走到生产 filter，支持的处置缺失在入口尽早报错；同一完整截断样本分别注入 KEEP/DROP，验证 n=8 全员训练或整组拒绝，以及零方差过滤不被绕开。未支持的 producer 不冒充已支持，也不扩成全局策略框架。
- I14：本机子进程/假容器 runner 验取消、异常与清理失败交错，核 reap/cleanup 均尝试、原失败不被吞、失败退出可见。真实“宿主 CLI 已停而容器子进程仍活”的验证并入原定目标后端作业；本机 mock 不能代替。

应避免的过强建议：统一所有 timeout 的处置；把 hard wall 全当模型失败或全当系统损坏；为了减少丢组放宽停止完整性；改变计时起点却宣称资源合同不变；直接把 25 提到 100 就认定 I02 已修；重建逐阶段归因平台来批准本次两个 disposition。
