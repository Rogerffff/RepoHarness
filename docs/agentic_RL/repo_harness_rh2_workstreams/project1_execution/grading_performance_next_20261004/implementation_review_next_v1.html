三个具体缺陷；已测提速仍然有效

1

缓存内部出错，没有回到原编译器 P1

私有缓存里的临时目录被普通文件占用时，实际 ccache 返回失败；相同源码直接用原 GCC 能成功。

修复目标：这类缓存环境故障自动旁路。源码本身的编译错误仍原样失败，不能对所有错误重复编译。

2

Prime 账本只在运行结束后登记 P1

两个作业都看到“已用 7 次”，可能各创建一次，合计 9 次；进程中途退出也会漏记在途资源。本批六次没有超额。

修复目标：创建前锁定并持久占额，结束更新同一记录，中断后先对账。可用本地测试完成，不需要付费制造故障。

3

Git 核验可能吞掉读取错误 P2

枚举只完成一部分却返回失败时，脚本仍可能输出“核验成功”。独立故障注入已在 GNU/Linux 复现。

修复目标：任何读取／哈希错误都不能形成成功证明。评分时仍按原期限回到原清理。本批正常日志没有这种故障。

为什么“十组缓存反例通过”也要改口径？

删除源码的一组在安装元数据阶段就失败，根本没有编译。两边遗留的旧二进制相同，不能证明删除后正确重建。未来 mtime 的一组还绕过了正常缓存处理；本次窄验用完整统计证实了这一机制。

已有的源码／头文件改变、缓存缺失和损坏证据仍有价值。需要分清实际覆盖范围，无需重新跑全部十组。

Pandas 安装脚本吞掉早期编译失败，是已存在的 B 线材料问题；本轮未改判分规则，也没有把它归咎于 ccache。
