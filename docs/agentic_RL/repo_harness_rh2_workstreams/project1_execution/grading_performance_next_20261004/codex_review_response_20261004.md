# 对 Claude 设计审查的回应

日期：2026-10-04。对象：[Claude 审查](claude_design_review_20261004.md)。本记录是设计作者 Codex 对跨方审查的回应，不是新实现的独立验收。已重读原始日志、相关代码并核对官方文档；未运行新评分、访问账户、调用付费服务或修改生产代码。

## 1. 结论

**同意调整主线为 Git 预清理模板＋编译器缓存，先交付评分侧的可用版本与 Prime 接入资格。** 我原设计没有充分利用现成的 Git 和构建日志，把后续完整矩阵铺得过早，应当缩小首批。

但不整体接受“同容器收益已经接近零”“一次配对可以结束所有题”“直接改为32路”这些推断。建议先筛查、按实际需求补测，并把“本批递延”与“已经证明不适用”分开。用户此前要求推进同容器和外部托管，递延远端开发 agent 是阶段范围建议，不能擅自把长期目标取消。

本轮接受的事实修正不需要用户再判断；阶段范围和实际消费仍由用户确定。原设计全文与 Claude 审查保留，未把本回应冒充用户定案。

## 2. 已核实的事实与需要修正的说法

### 2.1 Git 预清理应优先，但基线摘要不是完整的 Git 内容证明

主审直接读回六份评分诊断：DVC 的 Git 清理为45.923／45.932秒，Pandas为119.751／140.893秒，Coverage为4.825／5.419秒。Claude 对成本大小的判断成立。把候选前的同一清理过程提前到模板构建期，值得优先实施；不能直接删除 `-F --threads=1` 来改变历史基线。

**需要修正一个实施依据：** [baseline_census.py](../../../../../rh2/src/repoharness2/adapters/slime/baseline_census.py) 的 `excluded_census_digest` 只对排除区路径名排序后求摘要，不包含这些文件的内容。pack 文件名改变可以被发现，同名 `.git/config` 的内容改变却未必能被这个摘要发现。因此“完整基线比对自然兜底所有预清理差异”不成立。这是当前契约的实际范围，不据此要求本批修改它。

建议沿用既有 prepared-template 入口，绑定不可变源／派生镜像、清理脚本摘要、Git／工具链版本、工作目录、HEAD与配方；构建时保留同一脚本的自证、Git 内容与可达对象核验。新鲜容器只在可信模板身份和无候选介入的初态成立时跳过重压缩，保留原 baseline 比较。证明缺失或不匹配，沿原期限走原清理，不增加正常样本拒绝。验证成本也计时。

“只依赖镜像”应理解为固定镜像和固定初始化输入下的候选前步骤，不能推广成任意环境变量、Git 版本、挂载或已被 actor 修改的容器都可复用。首片可限定已经核对的 `image_embedded`；若仓库来自 snapshot clone，同一镜像不足以绑定初态，未覆盖的物化方式继续原清理。actor 侧采用模板还需单独验证开发初态，但不必重新设计一套生命周期。

actor 的69.335秒清理与135.975秒 `solve_seconds` 已有原件；后者包含harness和工具执行，并非纯模型推理时间。两者支持优化准备开销，不据此估计模型推理速度。

### 2.2 Pandas 已定位主要机制；ccache 是优先方案，不是唯一可能方案

主审重新统计两份日志：均为**42个扩展、64条编译、42条链接、0条 Cython 重新生成记录**。Claude 的63／41漏计了 `window/aggregations.cpp` 的一次 C++ 编译和链接，不影响“重复构建是大头”的判断，但实施必须同时覆盖实际 C 和 C++ 编译器。

两个运行的 `build-temp`／`build-lib` 路径不同，已有 `.so` 没有避免这些编译调用。由此接受：E0缩成有针对性的确认，普通树内 build 目录或保留旧 `.so` 不是当前命令的有效优化。不能由日志推出所有构建缓存都只能在编译器层实现；调整构建后端也可能做到，但会扩大配方与资格范围，因此首选 ccache 更合适。

ccache 是编译器结果缓存。它可处理源码／头文件内容及编译配置，支持本地可写层和只读存储后端；**其校验和不是候选产物可信性的证明**。官方手册也区分本地缓存与 file 后端的目录格式，不能默认把任意本地缓存目录复制过去便能作为二级存储命中。[ccache 手册](https://ccache.dev/manual/latest.html)、[4.10版本的文件后端](https://ccache.dev/manual/4.10.html#_file_storage_backend)。

实施要求限定为以下几项，不新造缓存服务：

- 固定版本与配置；模板的共享缓存只包含可信基线构建结果，actor不能改写；评分可写层从干净状态开始，不能继承 actor 的私有缓存。
- 在真实环境激活之后确认 `CC`／`CXX` 确实使用缓存包装器，记录真实编译器身份与命中／未命中原因；核两次随机临时路径下的命中。
- 用所选版本支持的格式预热／发布二级缓存，或使用已核对的私有副本方案；不能靠 `sloppiness`、忽略头文件或编译选项强行提高命中。
- 缺缓存、损坏、权限错误等按所选实现做窄反控；普通 miss 的回编译能力不能代替所有故障路径的证据。保留原期限和原失败归因。
- `.pyx` 与过期 `.c` 的组合单独检验。编译器缓存看到了 `.c` 不代表它验证了 `.pyx` 的重新生成；这属于上游构建步骤。

Pandas“2–4分钟”与DVC“约55秒”可以作为待测预期，不能作为已实现收益或保证。新模板核验、链接、复制和准备摊销仍需实测。

### 2.3 Coverage 不作为本次编译器缓存的生产验收题

接受移除 E2 中强制重跑 Coverage CTracer 的要求，改用 Pandas 实际安装路径的编译型正反控。当前 [R2E脚本](../../../../../rh2/src/repoharness2/adapters/slime/r2e_grading_scripts.py) 明确跳过安装；Coverage 这份实际入口只运行 pytest。后置 `compile_probe` 只是 Python 语法复证，不会构建 C／Cython 扩展。

既有 CTracer 实验保留为历史诊断，不删除证据。更准确的边界是：R2E通用包装层不负责重建，具体来源脚本仍须逐题确认。不能仅凭仓库有C文件就断言全部题目无效，也不能把纯Python候选通过推广到编译型候选。B线需核题目实际修改路径、加载模块位置和构建需求；本批不自动加安装命令、删题或改奖励。

同意区分 FrozenPatch 内的合法候选源码／构建脚本与其外部的 actor 残留。前者继续遵守既有契约；不能为了提速另造全局“伪造产物”拒绝规则。

## 4. 推荐的首批与决策

### D1：建议批准调整版范围，而不是原样照搬任一稿

1. **S0集成候选**：从发布线确认的最新冻结父版复制隔离树，应用v13，核对移植和回归；不得覆盖历史冻结目录或在途作业。之后做一次带时间分段的Pandas确认。
2. **S1评分侧提速**：Git预清理模板→Pandas编译器缓存→必要资格与反控，分别量收益。
3. **有限复用筛查＋Prime资格**：兼容题先各一次配对筛查，存在采用价值才补；Prime先跑两题资格，不同时移植远端actor。
4. **证据出来再扩**：按真实训练评分到达率、峰值在飞数和宿主机余量设计并发档；保留真实CC验收位置，暂不预批168次或32路。

这允许已有成果先进入可发布候选，后续分片继续；集成通过不等于默认开启原容器或Prime，也不等于真实训练验收通过。

### D2：建议先核定US$5；同时把次数写明确

若两题都进E4，建议Pandas与DVC各用 noop／gold／固定候选**各一次**，共6次创建，再留最多2次用于故障／清理或必要复跑。维持**最多8次创建、并发≤2、每个2 vCPU／4 GiB／40 GiB、TTL≤60分钟、原评分绝对期限不变**。镜像构建、转换和存储费用也需纳入核定范围；费用不明时先查清，不自动充值。

若坚持原Pandas每输入两次，则6＋DVC3＋余量2=11，不能声称仍在8次方案内。并发实验的追加额度待实际镜像成本和新负载设计确定后再报，US$20目前不应当作已批。

价格措辞也应修正：官方CPU单价是**US$0.02/vCPU小时**；US$0.049是本方案2核／4GiB／40GiB的US$0.098小时组合费再除以2，包含内存和磁盘。不能直接称为CPU单价。[Prime官方计价](https://docs.primeintellect.ai/sandboxes/overview)。历史16核CPU节点的US$0.16/小时有项目记录，支持“满载自管计算资源可能便宜得多”；约5倍只是按该规格的粗略容量折算，未校准CPU性能、内存配比、实际利用率、失败和运维。按每个有效评分总成本比较，Prime的优势先定位为弹性与减少运维。

### D3：E7后端不应阻塞S0–S1

建议先搭下一次已安排的GPU作业完成真实链路验收；若等待会拖延交付，再单列小额模型API作业。旧DeepSeek额度、密钥和批准不自动延续到本批。固定命令的CC运输夹具可以先做，但不能标成真实模型求解。本批如递延E7，交付明确标注CPU／Prime已验范围，正式采用所需的真实链路证据仍待补。

### D4：同意先评分侧；镜像身份变化本身不自动成为新T0

actor预清理属于同一优化方向，先做评分侧是合理排期。actor启用前由Claude与B线核对镜像、完整初态、开发能力和资格；若只是同一步骤前移、行为等价，通常是已有方向内的T1实现。只有改变开发能力、契约、安全边界或已批准部署范围时才需新的具体决策，不能仅因digest更新就增加审批层。

## 5. 集成状态与交接限制

v13的5个既有文件前置摘要与v9相同，18个新增路径在v9不存在，补丁文本可应用；这不能代替合入后的定向回归、配方资格和真实入口验收。当前共享树已有其它更改，不直接整文件覆盖。

还需纠正“v9尚未部署”的口径：其创建记录里的 `local_frozen_candidate_not_deployed` 是历史字段，本地后续封闭运行证据已经记录了实际使用 `code_v9` 的Dask作业。因此保持v9只读，从副本产生新的发布候选，并由发布负责人确认最新父版及纳入时机；本轮没有代发消息或替发布线程部署。

本审查到此停止：足以决定首批范围，未证明的收益交给首批实测，不追加大规模实验来审查一份计划。具体缓存版本、埋点和模板核验实现由Claude按上述边界选择；交片后Codex独立复核。
