## 逐项回应

### F1 · P1：缓存内部临时路径故障会新增编译失败

**判断：接受。** 原始证据可复现。在 Codex 的反例里，`/tmp/rh2-ccache/tmp` 是普通文件，ccache 报 `Not a directory`，包装器返回 1，原 GCC 返回 0。缓存属于性能优化，不应因为私有目录状态让本能编译的候选失败。

**修复前先核对 ccache 4.14.1 的事实**（证据 `fix_v2/ccache_internal_paths_matrix.sh` 及其输出）。在显式配置 `temporary_dir` 的前提下逐项测试：

- 缓存根目录或临时目录只要是文件、不可写或悬空软链，编译就会失败。
- 统计子目录被占为文件或不可写，都不影响编译。
- 两个目录若是指向可用目录的软链，可以正常工作。

**修法（包装器 v3、配置 v2）：**
- 配置中显式写入 `temporary_dir = /tmp/rh2-ccache/tmp`。ccache 的默认值会随 `/run/user/<uid>` 是否存在而变化，Prime VM 上可能与本地不同。
- 包装器先执行 `mkdir -p` 建出临时目录，再核对缓存根目录和临时目录都是可写、可进入的目录，全部通过才经 ccache 调用编译器，否则直接调用原编译器。
- 不对非零退出重编，不新增候选拒绝，不另建服务。

**没有采纳的做法：** 我曾考虑顺带清除候选环境中的 `CCACHE_*` 变量，最后没有做。E2 的无缓存对照正是依靠 `CCACHE_DISABLE=1` 实现的。候选通过这些变量也只能影响自己的构建，这与它本来就能在 `setup.py` 里执行任意代码等价，不会造成跨运行影响。

**验证：**
- **本地单测：** 把生成的包装器换成临时路径后真实执行，配合替身 ccache 和替身编译器。覆盖正常、根目录是文件、根目录不可写、临时目录是文件、临时目录不可写、临时目录是悬空软链、ccache 不可执行、真实源码错误共 8 种情况，均通过。同一组测试放到 next_v1 代码上，三种临时目录故障都失败。
- **真实 CPU**（cpu-c，最终 L2v3 模板，正式 profile、候选 UID、断网；`fix_v2/narrow_probe_01_result.json`）：

  | 情况 | 结果 |
  | --- | --- |
  | 正常 | 经缓存，产物与原 GCC 逐字节一致 |
  | 根目录是文件／不可写；临时目录是文件（Codex 原反例）／不可写／悬空软链 | 均回退原编译器，返回 0，产物一致 |
  | 统计子目录占为文件 | 返回 0，产物一致 |
  | 私有 `ccache.conf` 伪造 | 被忽略 |
  | 真实语法错误 | 包装器返回 1；错误行数与直接调用原编译器相同（3 行），`compile_failed=1`，没有重复编译 |

- **正常路径未变：** L2v3 模板复用原共享缓存，基线安装 19.6 秒、64 次全部命中、`.so` 摘要与基线相同；原先让 v1 失败的「私有目录不可写」小检查，在 v3 上通过。L2v3 空补丁 62.2 秒、原候选 61.9 秒，1040 项逐测试与此前 L2／v13 fresh 一致。另用 v3 从头重新预热一次（537.3 秒），共享缓存同为 109 个文件、7,913,732 字节；摘要与旧预热不同（`c6cbbc8a…` 对 `b7bdb4f4…`），说明预热产物不能逐字节复现，模板里记录的摘要只用于绑定当次产物。用这份新缓存，空补丁 61.9 秒、原候选 61.7 秒，安装约 19 秒，逐测试一致。

### F2 · P1：全局 Prime 账本漏掉在途和进程中断

**判断：接受。** 原实现在启动时只读账本，直到 finally 末尾才追加记录，且没有跨进程锁。在并发或中断的情况下，账本可能超额或漏记。

**修法（`run_prime.py`）：**
- 「读账、核对、占一个名额、登记本次的 provider 租约路径」放在同一把文件锁（`flock`）下完成，并在创建之前落盘（fsync 后原子替换）。
- 正常结束和异常都在 finally 中按 backend 的实际租约更新同一条目。backend 尚未建立就失败（例如 key 文件校验失败）时，按 0 次创建记账。
- 硬中断的处理：进程已不在（同机核对 PID；有 `/proc` 时另核启动时间，防 PID 复用）的占额，只按它自己的 provider 租约证据对账：
  - 证据缺失，或有 `requested`、`creating`、`running`、`create_unknown`、`delete_unknown` 状态，或有未确认删除的记录：名额保留并拒绝新建，跨多次启动都不自动释放。
  - 全部确认删除或明确未创建：按事实闭合。
  - 其它主机登记的占额无法核对，一律按在途保留。
- 同时用同一账本限制在途数（`--max-concurrent`，默认 2，对应用户批准的「并发 ≤2」）。
- 兼容本批旧格式的 6 条记录。

**顺带修正：** noop 分支复用了变量名，导致 `prime_plan.json` 的 `image_binding` 字段在 noop 运行里记成了空补丁 FrozenPatch。这只影响证据记录，不影响评分输入。

**验证：**
- `tests/grading/test_prime_global_ledger.py` 共 9 项，用真实子进程测试，不访问账户或 API，覆盖：
  - 已用 7 次时两个进程重叠启动，最多放行一个。读账后人为加 0.4 秒延迟放大窗口；去掉锁做反控，测试即失败。
  - 占额后进程被硬杀：名额保留并拒绝新建；补上已确认删除的租约证据后自动闭合。
  - `requested`、`create_unknown`、`running` 未删、`delete_unknown` 四种状态，跨两次启动都保持拒绝。
  - 正常关闭、明确未创建、backend 未建立三种情况按事实记账。
  - 在途上限、总量上限、重复作业名。
- 真实使用：第 7、8 次 Prime 创建已经走新账本（见下方「E4 正向资格」）。账本从已暂停的 cpu-a 原样迁到 cpu-c，迁移前后条目一致，现在是唯一的权威副本。

### F3 · P2：Git 内容核验会把部分读取失败报告为成功

**判断：接受。** 原脚本是 `{…} | sort` 结构，前段失败不会传播出来。我另外发现一处同类问题：`echo "…$(sha256sum …)"` 在求摘要失败时也会照常输出成功标记。

**修法：**
- 改为 `set -euo pipefail`。
- 三次枚举依次写入临时文件后再排序；摘要和条目数先赋值给变量，再校验摘要是 64 位十六进制。
- 任一阶段失败都以非零退出，不打印成功标记。
- 各行的格式和排序都没变，因此同一 `.git` 得到的摘要与旧脚本相同，已有模板继续有效。

**验证：**
- **本地单测：** 用替身 `find`、`xargs`、`sha256sum`、`sort` 驱动真实脚本。正常情况成功；枚举中途失败、单个文件读取失败、排序失败、求摘要失败四种情况，均非零退出且没有成功标记。同一组测试放到 next_v1 上，枚举、读取、求摘要三项失败（旧版本来就能拦住排序失败）。
- **真实 GNU/Linux：**
  - 在真实 Pandas `/testbed/.git` 上，新旧脚本摘要一致（`985f3dba…`、58 条），也与模板记录一致。L2v3 模板构建时用新脚本重核 `.git`，同样通过。
  - 注入枚举中途失败：新脚本退出 1、无成功标记，旧脚本报成功。
  - 注入文件读取失败：新脚本退出 1。
