## 2. 各条路线能减少哪些成本

| 路线 | 要减少的成本／获得的收益 | 仍然存在的成本／代价 |
| --- | --- | --- |
| 重环境预构建 | 编译器、系统库、第三方依赖、可信仓库基线的重复准备；把一次工作摊到多次尝试 | 初次构建、镜像传输／转换／存储、版本维护、环境资格；候选引起的必要重建 |
| 同容器评分 | 第二个容器的创建、工作树运输、环境再次安装，以及满足可信条件的构建重复 | 进程停止、断网、冻结核对、官方材料保护、清理；保留容器等待评分也占资源 |
| Prime 独立评分 | 外部 CPU 弹性、降低本地评分排队、减少评分宿主机调度与回收工作 | 远端启动、控制 API、数据传输、按占用计费；actor 仍在本地，因此只减少部分运维 |
| Prime 承载 actor 与 grader | 在上项基础上减少开发环境宿主机管理，复用同一 attempt 环境 | 模型网关连通与延迟、开发供应、网络撤销、远端轨迹收集；GPU／推理服务仍需独立提供 |

预构建和新容器兼容；同容器和外部托管也兼容。必须分别测量，再组合。扩大并发不等于减少 CPU 工作量，托管也不自动保证账单更低。任务配方、评分依据和资格检查仍由项目维护。

## 3. 推荐架构与不可改变的边界

### 3.1 三层构建状态

1. **可信固定环境**：按不可变基础镜像、依赖锁、工具链和配方构建，私有发布；不含候选、私有评分材料或凭据。
2. **可信基线构建缓存**：在候选介入前生成，放在评分源码树以外、actor 不可写的层。每个 attempt 只获得自己的可写副本。先核对原 baseline 并重放 FrozenPatch，再在受控构建中消费缓存。
3. **候选相关产物**：来源不明或 actor 任意可写的 .so、wheel、build 目录均不自动晋升为可信缓存。首片由评分侧按最终源码执行增量构建；只在工具链、完整构建输入和产物来源可验证时复用。同一候选的缓存不跨候选传播。

FrozenPatch 仍是唯一候选输入。缓存是可丢弃的加速材料，不能成为第二份答案。匹配一个 hash 只证明字节身份，不证明产物由那份源码构建；必须有受控的生产过程。构建候选代码保持原非 root 身份，不把 setup.py／构建脚本作为宿主或可信 root 代码执行。

**基线身份必须保持真实。** 若预构建往 /testbed 写入 census 计入的生成文件，会改变旧 FrozenPatch 绑定的 baseline。首选把缓存放在树外；不通过扩大排除集、忽略二进制 diff 或改写旧工件摘要来保住“同输入”标签。确需改变基线时，另建新环境资格线，重新冻结，并明确区分“同一源码变更”与“同一 FrozenPatch 字节”；该线不混入严格配对统计。

### 3.2 缓存命中与失效

缓存身份至少覆盖：基础镜像及架构、工具链版本、构建配方和选项、依赖锁与实际解析结果、源文件及传递依赖（含头文件、生成器和构建配置）、必要环境变量。固定输入清单由具体构建系统核实，不能只用 patch 文本摘要。

- 纯 Python 修改也先核对该文件是否参与代码生成或构建配置，不能按后缀一律跳过。
- 文件删除、重命名、旧时间戳、头文件变化、构建后再次修改源码必须正确失效。
- 不确定依赖关系、缓存缺失、缓存损坏：回到原全量构建，沿用原绝对期限，不新建“编译型补丁不支持”的样本拒绝规则。
- 不把 actor 环境改动静默忽略；合法依赖安装和既有任务开发能力不能因只读优化而失效。环境布局调整先验证任务行为，不能靠禁用能力制造速度收益。
- 半写缓存不得发布；失败、取消和崩溃后只消费已完整封存的版本。共享只读基线缓存与 attempt 私有写层不能互相覆盖。

### 3.3 同容器交接

沿用已经实现的物理 attempt 绑定、唯一清理 owner、队列背压与取消收口：开发结束→排空会话→静止屏障停止 actor 并确认进程归零、双读工作树稳定→导出并持久化 FrozenPatch→移交评分→撤销开发网络和供应权限→评分侧再次停止／复证进程归零→验证评分输入与可信层→恢复所需状态／重放成果→受控构建→原评分和清理。冻结前的静止屏障不能移到工件持久化之后。官方材料写入与保护的准确顺序继续服从原两段评分和实际任务配方，不在通用层擅自改动。

第一片复用可信基线缓存，测清全树恢复／环境普查是否仍抵消收益；如要缩小恢复范围，必须证明被保留的状态不影响最终评分，不直接删去原核对步骤。actor 过程中任意编译产物的直接复用另需来源证明，不能当成本片已经具备的能力。

复用不适用、镜像／资源不兼容时 fresh 回退；记录实际执行模式和原因。Pandas 现行 actor/grader 镜像不同，需要先核对开发与评分所需依赖，形成双方都通过资格的共同环境，不能只改镜像 ID 断言。

### 3.4 Prime 的关键接缝

现有 PrimeGradingManager 从创建时就全断网。远端 actor 要求额外接入命令执行、文件运输、进程事实、网络供应、冻结和清理；这些没有被现有独立 grader 证明。

固定 SDK 的 set_network 文档明确：更新策略不会撤销已经建立的连接。实验必须创建真实长连接，验证切换后旧流、新流、DNS 和已发放供应凭证的处置。仅检查 allowlist 为空不能验收。若服务商接口不足以做到原要求，就提交局部可靠撤销方案或改用新的离线 grader；不能把“关了模型进程”当成网络边界证据。复用失败不影响独立 Prime grader 路线继续验证。

文件系统快照只作为一个有限对照：优先测试候选介入前的可信环境快照，确认持久化、恢复、身份和成本。它不保存进程／内存，也不使被 actor 修改过的文件变可信；源码工作树和私有材料边界仍须验证。SDK 中存在字段不等于该账户线上可用。[官方 SDK](https://docs.primeintellect.ai/sandboxes/sdk)、[固定 SDK 源码](https://github.com/PrimeIntellect-ai/prime/blob/3c7f8bf88df0b0da6c79d0992206cf5fabcf6888/packages/prime-sandboxes/src/prime_sandboxes/sandbox.py)。

## 4. 实验共同规则

### 4.1 题目与输入

- **Pandas48106**：重安装／编译主样本；首先定位实际编译调用和重复来源。
- **DVC9395**：较轻构建样本，检验启动、权限和队列收益。
- **Coverage EA69**：保留历史固定候选作性能保真；另用真实 CTracer 受控反例验证二进制重建，不用争议分数证明训练资格。
- 正确性输入使用已有可信资格记录中的 noop、gold、已知错误候选。E0 核对其来源与预期，不能先假设所有任务都是 0／1／0。缺少 oracle 的题先补证或仅列为性能样本。

### 4.2 严格比较与统计

固定代码快照、原候选字节、评分材料、parser、官方命令、资源、超时和终止语义。优化构建步骤若涉及配方变更，记录新配方身份并逐题做语义等价验收；不删除正式测试或调整判分来获得提速。

先在同一宿主、同一资源限制下以交错顺序比较。外部搬迁不可保持物理 CPU／I/O 完全相同，报告 CPU 型号／可见硬件事实、资源额度和磁盘表现；托管差异不能归因于软件优化。固定输入和资源的相等，也不能证明宿主能力相等。

分开记录首次环境准备、首次服务商转换、后续重复启动。无法确认底层缓存状态时标为“首次访问／重复访问，缓存状态未知”，不冒称完全冷启动。**3次筛查、拟采用补至5次只适用于E1明确指定的Pandas档位和E3本地配对格。** E0诊断、E1另外两题保真、E4每输入2次、E5每模式3次、E6每档3波和E7按各自段落执行，不能自行套用补跑规则突破资源包。报告全部原始值、中位数和范围，小样本不宣传稳定 p95。跨格、跨实验重复利用的证据以 run_id 去重，不累加为独立样本。

### 4.3 正确性与失败

对比测试 ID 集合及逐测试状态、原始退出事实、评分输出和异常类别；缺日志／少测试不能算更快。环境或运输错误不转为模型 0 分。保持现有停止、隔离、取消和 fresh 回退语义；任何要新增拒绝轨迹、改变 reward 或弱化隔离的方案回到用户决策。

不为优化延长既有评分绝对期限。实验新增资格检查不占用真实 episode，但其消耗单列。缓存回退耗时计入原期限；若导致额外超时，既记录实际行为，也评估按题型的影响，不通过放宽期限隐藏。

## 5. 八项实验及验收

### E0｜固定基准并拆清安装／构建

**问题／理由：** 约十分钟的 pip 安装究竟耗在哪里，旧产物为什么没有被使用？先回答它，避免选错优化对象。

**做法：** 在 v13 的隔离集成树建立 input_manifest；核对三题原 FrozenPatch、完整基线、正式脚本、镜像和已有 oracle。把 Pandas 安装段分解为依赖处理、元数据、代码生成、编译、链接、复制；记录真实编译单元数及 CPU／I/O，不用命令名推断。比较 noop、Python 修改与受控编译修改；每类先一次诊断。诊断开销另用同配置开／关对照确认，成功后对照组同样埋点。

**通过／产物：** 能用原日志和阶段时间说明主要成本及可复用输入；输出 baseline_receipt、build_breakdown、case_catalog。不能把总安装段全部记为编译。没有重编译证据时，先定位构建系统，不直接加缓存。

### E1｜可信重环境与基线构建缓存

**问题／理由：** 保留全新容器，单独预构建可以省掉多少重复工作？这是同容器和 Prime 的共同底座。

**做法：** 阶梯比较 L0（当前权限优化 fresh）→L1（完整固定依赖／工具链）→L2（再增加可信树外基线构建缓存）。Pandas 每相邻档先 3 次交错筛查；只有有收益或能解释必要差异的档继续，拟采用档补至 5 次。DVC、Coverage 对最终选中档各做 3 次保真检查，不机械运行所有组合。每个新环境单列准备和资格成本，按已有 oracle 做 noop／gold／错误输入核对。

**通过／产物：** baseline 身份真实、结果等价、收益来自可指认阶段。保存 recipe、缓存来源与只读证明、实际加载模块位置／摘要、编译计数、准备成本和摊销曲线。开发筛选建议：安装段中位数下降至少 30%，或总评分有明确收益；达不到也提交负结果，不修改正确性标准。此数值是建议的选型指标，不是训练准入阈值。

### E2｜证明缓存不会加载旧答案

**问题／理由：** 防止“少编译”实际是在运行过期二进制。

**做法：** 先完成以下八类最小反控，每类对照干净全量构建与优化构建：纯 Python 且不参与生成；C／Cython 源码改变；头文件或生成器改变；依赖／编译选项改变；删除／重命名；源码 mtime 变旧；最后一次构建后再修改最终源码；actor 伪造／改写缓存或产物。关键反例必须让旧二进制与最终源码有可观察的相反结果。

**通过／产物：** 两条路线对最终输入的逐测试结果一致，实际加载模块对应最终源码；可信共享层不可被 actor 修改，私有伪造产物不能进入评分；取消时半成品不可命中。至少 CTracer 真实编译反控和 Pandas 实际构建路径均落证，不能只用玩具工程。无法可靠失效的配方回全量构建，正常补丁仍可评分。

### E3｜同一环境下的新容器与原容器

**问题／理由：** 预构建之后，再保留同一个容器是否还有净收益？恢复扫描与等待占用是否抵消节省？

**做法：** 使用 E1 选定配方，在每题的真实 rollout profile 下，对 prepared fresh 与 prepared reuse 各做 3 次配对固定成果回放；拟采用题补至 5 次。先确认 Pandas actor/grader 共同镜像资格。所有分段都计入，包括预封存、恢复核对、排队持有容器的时长、峰值内存和清理。旧 v13 reuse 只作历史诊断，不当新缓存方案的代表。

**通过／产物：** 除分数等价，还需进程归零、实际断网、唯一清理 owner、取消／满队列／删除失败按原语义收口。输出 net_reuse_benefit 与 fallback_by_case。开发筛选建议：完整 attempt 中可比较的基础设施耗时中位数下降至少 10%，且排队占用不抵消吞吐；不要求所有题启用。无收益的题明确使用 prepared fresh，并解释原因。

### E4｜Prime 实际接入资格

**问题／理由：** 本地 SDK 测试能否转成可用的远端评分服务？

**做法：** 先只读核账户、额度与费用口径；准备最小、私有、无凭据的镜像构建上下文。核对源镜像、Prime 发布 ID、转换回执和内容映射。首先用 Pandas 一份选定镜像，运行 noop／gold／固定候选各两次（6 个 sandbox），再留最多 2 个用于取消或删除异常后的清理验证。单实例 2 vCPU／4 GiB／40 GiB、TTL 最多 60 分钟，并保留原评分期限；并发先 1，最多 2。无新模型调用。

**通过／产物：** guest 非 root、资源／网络事实、依赖兼容、原评分输出、日志完整性和精确 ID 删除确认均可验证。首次转换时间单列。403 不当作已删除，未知创建保留记录并停止新增资源。失败只修本接缝，不顺手迁移 actor。镜像与数据必须私有，不能因为发布流程方便改为公开。

### E5｜Prime 同 sandbox 交接及方案对照

**问题／理由：** 区分云主机差异与容器复用收益，并查清 Prime 是否支持开发→评分的真实交接。

**做法：** 在 E4 环境中补齐 actor 命令／文件／网络／生命周期接口，先用固定成果夹具做交接。Pandas 的 prepared fresh／prepared reuse 各3次：fresh每次需actor＋grader两个sandbox，reuse每次一个，共9次创建；真实回退另计。DVC的三个资格输入是E6混合负载的独立前置，即使同sandbox路线失败也必须完成，另计3次创建。可信候选前快照使用这9个实例中的一个作donor，另留1次恢复创建；先确认DURABLE再继续污染夹具。E5计划共13次创建。由此与E1/E3本地两组形成2×2对照，但不把不同CPU的差异归为复用收益。

**通过／产物：** 真实已有连接必须被撤销或隔离，模型／供应授权随 attempt 退役，guest 进程归零；实际执行模式和 fallback 原因可追溯。快照仅是额外对照，未支持时如实标注。若无法满足同 sandbox 的网络／来源要求，该组合不启用，Prime fresh 和本地复用仍独立完成验收；后续给出具体替代或采用决定，不无限挂起。

### E6｜并发吞吐与运维成本

**问题／理由：** 外部托管能否缓解排队、扩大有效评分容量，并减少维护工作？单次时延不能回答这件事。

**做法：** 固定每波12个输入，DVC与Pandas各6个，顺序固定后轮换。必须先完成两题独立资格；本轮各档统一使用同一合格配方的prepared fresh独立grader，每次评分创建一个sandbox，不含actor。Prime并发1／2／4／8，每档3波，共最多144次计划评分；本地只测现有许可的1／2路，不越过公共每机两槽规则。先过低档再提高。E5复用成功也不改变这144次的模式；需要同容器并发时另列实际actor负载作业，不能偷换这一轮分母。

**通过／产物：** 保存每波完成时间、有效评分吞吐、排队及运行时间、全部失败／回退／超时、清理残留、资源占用和费用。每档仅 36 个结果，按题仅 18 个，报告中位数、最大值和分布，不宣传可靠 p95 或全题集容量。若正式选择依赖尾延迟，再单列足够样本的后续运行。

记录搭建、镜像迁移、故障处理、升级／清理的实际人工介入分钟和次数；本次只能估计试点运维，不能伪造长期节省工时。现有 backend 的并发≤2、创建≤8是程序限制，E6 需要受预算约束的显式实验配置与全局账本；不能启动多个实例绕过限制。

### E7｜真实 Claude Code 端到端验收

**问题／理由：** 固定成果回放不包含真实开发中的依赖安装、反复编译、模型网络和容器等待，不能直接推出训练端收益。

**做法：** 前六项通过后，先用真实 CC 固定命令作运输检查，再使用已确认的模型、工具与预算，至少 DVC／Pandas 各 3 个真实 attempt；每个最终 FrozenPatch 用合格 fresh 对照复核。不同部署方式的生成结果不能假装相同配对输入，性能比较区分相同成果回放与独立求解。若比较本地／Prime actor，则分别记录模型调用和网关延迟，固定题目与模型设置；不以这一小批推断解题率提高。

**通过／产物：** actor→冻结→评分→上游消费的真实链路完整；token／时间预算不被改变，训练端等待有记录。提交明确的按题采用表、未适用原因及回退方案。GPU／模型成本另按具体作业已有授权核对；本设计和 API 文件不自动授权新训练、租卡或更换模型。

## 6. 指标、分母与采用判断

| 指标 | 定义与注意事项 |
| --- | --- |
| 有效评分 | 完整、可信且可消费的评分报告，包含真实 0 分和 1 分；不等于“解对题” |
| 有效吞吐 | 有效评分数 ÷ 从本波提交到最后清理／失败收口的墙钟时间；同时给全部提交数与完成率 |
| 出分延迟 | 提交→报告可用；清理延迟和资源释放另列，不能用提前出分隐藏资源泄漏 |
| attempt 总耗时 | actor 就绪、求解、排队、交接、评分与清理的完整时间线；嵌套段不相加，并行段不重复计入 |
| 单个有效评分总成本 | 本批全部计算、准备摊销、存储／传输、失败重试和闲置费用 ÷ 有效评分数；分母为零时报无有效结果 |
| 模板摊销 | 按每模板实际使用次数 N 计算：准备成本/N + 每次执行成本；报告 N=1、10、100 的情景，不把假设次数写成实测 |
| 运维投入 | 实际介入分钟、次数和原因；机器账单与人工工时分列，不虚构人工单价 |

所有实验建立“提交 = 有效完成 + 明确失败 + 取消 + 在途”的守恒表；结束时在途应为零，未收口资源单列。优化回退仍计原组，不只挑真正命中的快样本。输入清单、模式和顺序在运行前固定；结果不好不换分母。

采用顺序：先满足评分／隔离／清理等价，再比较预构建摊销、端到端时延和吞吐，最后结合实际费用与运维决定部署。允许不同题使用不同合格模式；这种路由不能改变样本准入、reward 或预算。任何正式路由规则影响任务覆盖时按原 T0 规则处理。
