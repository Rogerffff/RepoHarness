### 已实施的内容

- **L1：**
  - 构建模板时，按评分侧的同一顺序跑血缘探针和同一清理脚本，收尾记录 `.git` 全部条目的类型、权限位、大小、内容摘要（不含属主）和 Git 版本。
  - 评分时在血缘探针之前核对：内容摘要、Git 版本、清理脚本摘要、HEAD、工作目录全部一致，才跳过重压缩，并记 `template_attested`。任何一项不一致，或核对本身失败、超时，都回到原清理和原期限；评分期限耗尽或容器死亡，照原归因上抛。
  - 核验脚本的枚举、读取、排序、求摘要任一阶段失败，都不打印成功（`next_v2` 修 F3）。同一 `.git` 的摘要与旧脚本相同。
  - 只覆盖 `image_embedded`；actor 侧未改。
- **L2：**
  - 使用 ccache 4.14.1 官方 musl 静态版。模板只把 `CC`／`CXX` 入口换成包装脚本，原编译器保留。
  - 共享缓存在 `/opt/rh2/ccache/base`，位于评分树外、root 所有、候选只读，配置为 `remote_only`、`read-only`、`compiler_check=content`，不用 sloppiness。
  - 包装脚本 v3（`next_v2` 修 F1）：私有缓存目录 `/tmp/rh2-ccache` 和其中的临时目录（配置显式写 `temporary_dir`）都是可写、可进入的目录时，才经缓存调用编译器；否则直接调用原编译器。真实源码错误照常报出，不重复编译。
  - 预热在一次性容器里进行：以候选身份执行从评分脚本原样截出的安装段，`/testbed` 不进模板。
- **Prime 绑定（T1）：**
  - 镜像引用形如 `prime/<用户ID>/<名>:<tag>`，没有 digest 形式，所以绑定为“引用＋产物 ID”。每次创建前用 SDK 核对：唯一的 `VM_SANDBOX` 产物，ID 一致，状态 `COMPLETED`，可见性 `PRIVATE`。
  - 推送输出的 Build ID 与完成后的产物 ID 不同，绑定取完成后的那一行。
  - 这能发现部署时写错 ID，但**不等价于不可变 digest**：创建时仍传 tag，查询与创建之间不是原子绑定，guest 内只核 `.git`。
- **Prime 全局账本（`next_v2` 修 F2）：**
  - 读账、占额、登记在同一把跨进程锁下完成，并在创建前落盘。
  - 结束时按实际租约更新同一条目。
  - 进程已不在的占额只按它自己的租约证据对账：证据缺失或租约未闭合，就保留名额并拒绝新建。
  - 同时限制在途数。
- **实验入口：** `run_case.py`（`--prepare-git`、`--prepare-build-cache`、`--frozen-source`）；`run_prime.py`（`--template`、`--noop`、`--frozen-source`，以及全局账本）；`build_cache_probe.py`（E2）；`e7_entry.py`（E7 的 DeepSeek 服务核对）。
- **交付：** `runs/grading_performance_next_20261004/deliveries/next_v2/`，相对 `frozen_code_v9`，补丁 SHA-256 `1938128c…86f1f8`，共 28 个文件：v13 的 23 个，加本批新增的 2 个实验入口和 3 个测试文件。已在全新 v9 副本上 `git apply` 通过，修改后摘要一致；回归 414 passed、1 deselected（原因同 v13：冻结快照缺历史 `container_train_disaggregated.sh`），ruff 通过。`next_v1` 保留原样。
