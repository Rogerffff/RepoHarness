## 2. 对 §3 五个流程问题的意见

**2.1 材料对应实际工作树。** 09-25 已把协议改成"用实际初始工作树"，这是对的。首轮有一个现成反例：mypy11236 的公开镜像里 `/testbed` 带一个**已跟踪的脏文件** `test-requirements.txt`，被卷进候选，导致 4 条首评 apply 失败。建议新批次每题的材料登记附一行镜像内 `git -C /testbed status --porcelain` 的结果（空也要记），而不是只记 base commit。成本很低，能直接暴露这类初态差异。

**2.2 公开角色的隔离。** 分叉出来的线程继承了本线程的全部上下文：它已经读过 gold、处置卡、评分日志和旧结论，**不能再担任公开读者或独立 reviewer**。这两个角色必须由分叉线程另起新上下文的子 agent 承担，并且提示里只给公开包路径。另外，共享工作区里 `runs/base_probe_20260922/analysis/`、`docs/.../base_probe_analysis_20260922/` 等私有结论对任何 agent 都可读，只靠提示词约束。协议已承认这一点，但新批次的公开读者提示应**显式列出禁止读取的目录**，并在产物里记录实际读取范围，事后抽查。

**2.3 开发条件证据要来自实际 actor。** 首轮 8 题的 actor 证据都在诊断变体 `bash_env_v1` 下取得。A 线 #1 修复（`47755976`）后，正式链自己提供 `/rh2/bash_env`，工具面也收窄到 5 个（#10）、自动记忆已关（#9）。因此：

- 任务二的新开发验证应走**修复后的正式启动路径**，不要再用 `bash_env_v1`，否则证据不能迁移到下一轮探针；
- A 线已有一个无需 GPU 的真实入口：真实 CC 2.1.205 + 桩端点（`rh2/experiments/base_probe_fixes_20260923/stub_anthropic_endpoint.py`），经正式 `ClaudeCodeDriver.run`（见 [#1/#2 Brief §6.4](base_probe_chain_fixes_20260923/brief_startup_1_2_20260923.md)）。让桩端点按脚本发出 Bash 调用，就能以真实 agent 身份、真实 CC 子 shell 执行每题的开发命令，正好满足共用流程第 1、2 步"采用准备交给 Claude Code 的用户、非交互 shell"的要求。建议任务二把它作为默认的 actor 验证入口，逐题只写命令清单。

**2.4 逐命令解释与复验原路径。** 共用流程写得清楚，没有补充。只提醒一点：首轮 DVC5839 的 10 条"验证"都绕开了修复点（直接调内部函数或断言 Mock）。开发验证的命令清单里，至少要有一条经过题目公开入口（CLI 或公开 API）的命令，否则"相关测试能跑"不能说明模型能用它区分修没修好。

**2.5 分包与交付的简洁度。** 每题 7 份文件对 40 题是合适的；今晚任务一目标 8–12 题校准，量级合理。不建议新增全池闸门。一个简化建议：交接页三条线**只在自己的小节放链接和三五行摘要**，详细结果写到各自目录；三个线程同时编辑同一个文件，容易互相覆盖（Edit 工具在文件被他人改过后会失败或基于旧内容覆盖）。

## 3. 线程分工建议

- **任务二需要机器。** 当前 B 线没有可用的 x86 CPU 机：探针机已删除，A 线的 Spheron 机归 A，R2E 对账机归 R2E 线程，本机 Docker 是 arm64，跑 x86 题目镜像要走仿真，不适合作为证据。任务二开工前需要租一台 x86 CPU 机（带 Docker，约 16 vCPU / 64 GB / 300 GB 足够）。任务一是纯静态审查，不需要机器。
- **§4 的探针接线建议留在本主线程做。** `qwen_adapter_server.py`、`solve_attempt.py`、`model_gateway.py` 都是本线程写的，按 A→B 交接改四处装配、CC 条件、网关断流收尾和宿主轨迹路径，可以用同一个桩端点在 CPU 上验证，不需要 GPU。溢出 400 依赖 A 抽出的共用函数，在它就绪前先记为未装并在 `adapter_config.json` 里如实标 `overflow_400: false`。这样三条数据线并行时，探针入口也同步就绪。
