整体结构四层：训练驱动（1 个 actor）；GPU 上的训练与推理（64 个 Megatron actor 和 32 个 SGLang actor 共用同一批卡）；agent 层（框架、网关、负载均衡等 actor，外加每会话一个 Ray task）；环境（每会话一个 K8s Pod）。
Ray task 是不是沙箱不是。Ray task 是在 Ray 集群上驱动 agent 的一个进程，记账 0.5 个 CPU；沙箱是它通过 K8s API 另外创建的 Pod，可以在另一个集群。
Ray 怎么分资源，用不用 group用 placement group：每台节点一个 STRICT_PACK 的 PG，8 个 bundle 各 {GPU:1, CPU:3}，Megatron worker 放进 bundle。SGLang、网关和每会话 task 都不在 PG 里，靠节点亲和或默认调度。
rollout 结果要不要用 Ray 同步大数据不走 Ray：样本写进 TransferQueue（张量走 ZMQ推断），Ray 调用只传键和标签。Ray 负责调度和控制消息；会话内的轨迹在网关内存里攒，收尾时作为 Ray 返回值交给框架。
你说的“默认 colocate，但也能训推分离、权重同步和 partial rollout 都接好了”：基本对，有三点要补充。
  • 代码里有 separate_async 模式：推理池单独一个 PG，权重用 NCCL 等 checkpoint engine 同步，partial rollout 复用同一个续传客户端。code recipe 默认没开（TRAINER_MODE 默认 colocate_async）。
  • 开启有约束：rollout.nnodes > 0，checkpoint engine 不能是 naive，train_batch_size = parameter_sync_step × ppo_mini_batch_size。训练池启动时也兼做推理，第一次采样后切到训练，之后切回推理的逻辑是 TODO（should_switch_to_rollout 恒返回 False）。
  • 上游 verl/experimental/fully_async_policy 是另一套全异步实现（Rollouter + Trainer + MessageQueue），和 v1 的 separate_async 不是同一份代码。

基础回顾

每张卡片：概念是什么，在 MiMo 里对应哪里。

进程与 Ray

进程 / 线程 / 协程

进程有独立内存和自己的 GIL；线程共享进程内存，同一时刻只有一个线程在执行 Python；协程在一个线程的事件循环里轮流执行，遇到 await 才让出。

MiMo：一个 Ray task 是一个进程。它的主线程跑 asyncio.run，同步的 agent 代码交给 to_thread 开出的工作线程，避免阻塞事件循环。

集群：GCS 与 raylet cluster

head 节点上的 GCS 记录所有 actor、task、placement group 和对象的元数据。每台节点跑一个 raylet，负责本机调度、启动 worker 进程和管理对象存储。

MiMo：先用 ray start 起好集群（8 台 GPU 节点加一个无 GPU 的 head），driver 再用 ray.init(address="auto") 连上。

资源只是记账 resources

num_cpus 和 num_gpus 只用来判断“放不放得下”，不绑核，也不限制实际用量。GPU 的隔离靠 Ray 给 actor 设置 CUDA_VISIBLE_DEVICES。数值可以是小数，比如 0.5 CPU、⅓ GPU。

MiMo：每会话 task 记 0.5 CPU，实际用多少不受限。SGLang server 申请 0 张 GPU，自己设置 CUDA_VISIBLE_DEVICES 去用卡，所以 Ray 并不知道它占着 GPU。

Ray task：一次性的远程函数 task

f.remote() 立即返回一个 ObjectRef；raylet 找一台有空闲资源的节点，从进程池借一个 worker 进程执行，执行完把进程还回池子复用。同时运行 N 个 task，就同时占用 N 个 worker 进程。task 没有状态，返回值放进对象存储；默认在系统故障时重试 3 次。

@ray.remote(num_cpus=0.5)
def run_session(cfg): ...

ref = run_session.remote(cfg)  # 立即返回
await ref                      # 要结果时再等

MiMo：每个会话一个 task（framework.py:176），一批 64 题 × 16 = 1024 个，并发上限 2048。task 只返回 None，轨迹不经它回传。

Ray actor：常驻的远程对象 actor

Cls.remote() 创建时独占一个进程，状态一直留在进程里，之后通过句柄调用方法。默认调度时需要 1 个空闲 CPU，运行起来后占 0 个。

@ray.remote
class Gateway:
    async def create_session(self, sid): ...

gw = Gateway.options(
    scheduling_strategy=NodeAffinitySchedulingStrategy(
        node_id, soft=True)).remote()

MiMo：Megatron worker、SGLang server、网关、框架、负载均衡都是 actor；共约 124 个，其中 TransferQueue 的 9 个是推断。

Ray actor 的三种并发方式

普通 actor：方法调用排队，一次执行一个。async actor：只要有 async def 方法，所有调用都跑在一个事件循环上，默认最多 1000 个同时进行。threaded actor：设置 max_concurrency，用线程池并发。

MiMo：网关和 AgentFrameworkWorker 都是 async actor。网关还把 uvicorn 挂在同一个循环上，所以 HTTP 请求和 Ray 方法调用共用一个线程。

Placement group PG

一次性预留一组资源块（bundle），要么全部给，要么一个都不给。策略：PACK（尽量同机）、SPREAD（尽量分散）、STRICT_PACK（必须同机）、STRICT_SPREAD（必须不同机）。之后可以把 actor 指定放进某个 bundle。

pg = placement_group(
    [{"GPU": 1, "CPU": 3}] * 8, strategy="STRICT_PACK")
Worker.options(
    num_gpus=1/3,
    scheduling_strategy=PlacementGroupSchedulingStrategy(
        placement_group=pg,
        placement_group_bundle_index=i)).remote()

MiMo：每台节点一个这样的 PG，按节点 IP 排序（single_controller/ray/base.py:146-157）。

调度策略与通信组 scheduling

调度有三种：默认（随便找有资源的节点）、NodeAffinity（硬绑定或软绑定某台节点）、指定 PG 的 bundle。ray.util.collective 可以在 actor 之间建 NCCL 或 gloo 通信组。

MiMo：网关软亲和 GPU 节点，SGLang server 硬亲和；separate_async 模式用 collective 广播权重。

对象存储与 ObjectRef object store

每台节点有一块共享内存。task 的返回值和大参数放在这里，同机读取不用拷贝，跨机由 Ray 自动传输。ObjectRef 是取数据的凭证，用 ray.get 或 await 取。

MiMo：训练器把 prompt 批通过 Ray 调用参数（经对象存储）交给框架。训练张量不走这里，走 TransferQueue。

K8s 与 Pod

集群 = 控制面 + 工作节点

控制面：API server（所有操作的唯一入口）、etcd（存集群状态）、scheduler（按资源申请选节点）、controller（维持期望状态）。每台工作节点上有 kubelet，按 API server 的指令通过容器运行时（如 containerd）起停容器。

对比 docker：docker run 只在本机起容器；K8s 在很多台机器之上挑一台来起。RH2 现在是每台机器各管各的 docker。

Pod

最小的调度单位：一个或几个容器，共享网络（一个 IP）和挂载卷，整体被放到某一台节点上运行。可以先理解成“集群帮你挑一台机器起的容器”。

spec:
  containers:
  - name: main
    image: <任务镜像>
    command: ["bash","-lc","..."]   # 空转，等 exec 进来
    resources:
      requests: {cpu: "0.5", memory: 1Gi}
      limits:   {cpu: "4",   memory: 8Gi}

requests 与 limits

requests 用于调度：节点上的可分配量减去已占的 requests，够了才放得下。limits 是 cgroup 上限：CPU 超了被限速，内存超了被 OOM 杀掉。

MiMo：每个 Pod 申请 0.5 CPU / 1 Gi，最多用到 4 CPU / 8 Gi。2048 个 Pod 一共申请 1024 CPU / 2 TiB。

exec

和 kubectl exec 一样：客户端 → API server → 目标节点的 kubelet → 容器运行时，在已运行的容器里启动一个进程，输入输出通过 websocket 流回来。

MiMo：每条工具命令、每次测试都这样执行（kubernetes.py:474-546）。

kubeconfig 与 namespace

kubeconfig 里写着 API server 地址和凭证；namespace 是集群里的隔离分区。

MiMo：task 用 KUBECONFIG 连集群，namespace 默认 default。Ray 调度 Python 进程，K8s 调度容器，两边是独立的集群，task 通过 K8s API 远程操作 Pod。

Ray 怎么划分资源

不同组件用不同的放置方式。

Megatron worker进 PG。每台节点一个 STRICT_PACK 的 PG，8 个 bundle 各 {GPU:1, CPU:3}。每个 worker 申请 ⅓ 张卡（max_colocate_count = 3，给最多 3 个角色共卡留位置）。本配置不开 KL、不用 critic，只剩 actor 一个角色，被合并进一个 WorkerDict 进程。
SGLang server不进 PG。硬节点亲和，申请 0 张卡，自己设 CUDA_VISIBLE_DEVICES 用两张卡（TP2），和 Megatron 共用显存：生成时 Megatron 参数卸到 CPU，训练时 SGLang 释放权重和 KV。
网关 / RewardLoopWorker软节点亲和，按存活的 GPU 节点轮流放，每台一个；没有 GPU 节点时退到 CPU 节点。
训练驱动、框架、LB默认调度，代码里没指定位置。
每会话 Ray task默认调度，各记 0.5 CPU，没有亲和。哪台节点有空闲逻辑 CPU 就放哪台；集群里主要是 GPU 训练机推断。CPU 不够时 task 在 Ray 里排队，但会话的墙钟计时已经开始。
算一算：逻辑 CPU 够不够放 2048 个会话
只算 PG 预留和 task 记账；actor 运行时默认占 0 CPU，SGLang 的 CPU 设置未核对。真实 CPU 消耗不受这个数限制。

结论
  • Ray 负责调度和控制消息：创建会话、提交 task、分发“这一批是哪些键”。
  • 训练样本这类大数据写进 TransferQueue，训练侧的 64 个 worker 拿到键之后自己去拉，不经 Ray 对象存储汇总到驱动进程。
  • 权重不经过 Ray：同卡用 CUDA IPC，分离模式用 NCCL。
