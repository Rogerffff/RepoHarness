## 1. 已核实的代码事实（本机，HEAD `f7521d94`）

1. 行内（叶链级）收缩拒绝在 `fork_threshold_tokens=0` 下结构上不可触发：同一训练行只接受精确 token 前缀延续，prompt 长度单调不降；收缩先分行，`detect_context_shrink` 在行内永远为空。Codex 五案探针（真实 TrajectoryManager / capture / bringup_leaf_facts / 编排 / 投影 / 准入 / 转换）确认：`branch_shrink_reasons` 全空、每个生成 token 恰好训练一次。
2. 真正阻止压缩的只有 `CLAUDE_CODE_TRAINING_GUARD_ENVS` 里的 `DISABLE_COMPACT=1`，且它只关 auto/manual compaction；参考版本的 CC 源码快照里另有 Microcompact、工具结果裁剪等机制，它们不受该变量约束——若在目标 CC 启用，同样按 B 表示分行。目标 CC 实际启用了哪些层仍待真实请求核对（§0 已登记），不能从 B 表示或本机合成测试推出（Codex 09-11 复核文字余项）。
3. vendored `AnthropicAdapter` 只读 `messages` / `system` / `tools`，未知顶层字段被忽略、不会 400；它**不实现**服务端上下文编辑语义，响应里也不报告编辑结果。这只证明"未实现"，**不证明** CC 会回退到客户端压缩（Codex 反馈 1：撤回该推断）。`cache_edits` 若作为 user 内容块发送，走 `flatten_content` 路径，与顶层字段不是同一路径。目标 CC 是否发这些字段、最终怎样压缩，归 §0 已登记的真实请求核对。
4. 请求预算按现有守卫实际接纳的模型请求计（capture wire 包装 vendored `_check_turn_cap`）；"每次压缩恰好多一次请求"不是通用事实（memory 复用、失败回退、无摘要的裁剪都存在），本次不改预算计法、不免计、不把 25 定为正式预算（Codex 反馈 3）。

## 3. 语义说明（沿用现有实现，本 Brief 只是写清）

- 同策略、同 execution 捕获入口生成的摘要 = 一次真实动作：训练一次、用终局任务 reward、计入实际接纳的模型请求；重注入为 prompt 时是上下文（loss_mask=0），不重复训练。只有 harness 注入而无捕获生成的摘要不补造行为 logprob。
- 上下文改写的表示：不再是精确前缀延续的请求分行（FORK），旧动作保留自己的训练行；训练时重复计算的前缀是表示成本（I20 面 ② 观测），不是新语义。
- 恢复压缩是 harness 行为变化：模型看到的输入分布改变、可能多出摘要请求；写进运行配置说明；带压缩的长任务结果与此前禁压缩的 spike 不能直接混比。去掉强制禁用不保证每次运行都触发压缩（受目标 CC 配置与功能开关影响）。
