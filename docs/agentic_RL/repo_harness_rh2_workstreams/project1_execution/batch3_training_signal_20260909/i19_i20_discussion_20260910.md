## 2. I19：撤回原先“保持拒绝，先测压缩丢组率”的推荐

### 2.1 原判断错在哪里

原草案把“同一消息分支”与“拆分后的训练行”混为一谈。实际生产路径为：

```text
真实捕获与消息树
→ TrajectoryManager 按 token 前缀拆训练行
→ finish 包装为各行导出可训响应的身份 spans
→ bringup_leaf_facts 从该行 spans 提取 capture_record_ids
→ 对这些轮次执行 branch_shrink 检查
→ backfill、投影、组准入与训练数据转换
```

当前 `fork_threshold_tokens=0` 下，同一行只接受精确 token 前缀的延续，所以行内请求的 prompt 长度单调不下降。收缩先导致分行，后面的 `detect_context_shrink` 看不到分行边界两侧。只要保持当前健康接线、检查比例在 `(0,1)` 内，这个行内收缩拒绝就结构上不可触发。

证据：[阈值与分支判断](../../../../../rh2/src/slime/agent/trajectory.py)、[身份导出](../../../../../rh2/src/repoharness2/adapters/slime/turn_identity.py)、[实际 LeafFacts 构造](../../../../../rh2/src/repoharness2/adapters/slime/bringup.py)、[装配期拒绝位置](../../../../../rh2/src/repoharness2/adapters/slime/generate.py)。关键定位分别为 `classify_token_drift`、`export_leaf_identity_spans_with_coverage`、`bringup_leaf_facts`、`branch_shrink`。

因此，开启这个配置不能证明排除了压缩。也不应把它上移成 session 级硬拒绝：主 agent 的长上下文之后插入一个短上下文子 agent，同样会出现长度下降。

这不是本次已经证明的“I01 新引入回归”。旧正阈值也会把足够早的前缀收缩拆行；本次 100→40 的对照在阈值 0、1024 下均 FORK。能够确认的是当前检查位置无法实现旧 D-FA-6 所声称的保障。

### 2.4 推荐的窄改动及其语义

**建议恢复 harness 的正常压缩行为，沿用现有 B 表示，清理过时的压缩禁用与长度拒绝规则。无需先造一个压缩管理器，也无需先做 GPU 对比才能删除当前死守卫。**

改动面应是一次完整的小清理：

1. 删除 `generate.py` 的行内收缩拒绝，取消启动期强制 `reject_context_shrink=True`，清理相应 profile/env/配置与只保护旧规则的测试。具体调用清单在实施 Brief 中列明，历史证据不重写。
2. 从 `CLAUDE_CODE_TRAINING_GUARD_ENVS` 去掉强制 `DISABLE_COMPACT=1`，同步活动 launcher/配置中旧禁用值。**不是整删该函数**：另外三个键控制 CC 重试和 fallback，沿用已定责任边界。
3. 保留真实 token、capture 身份、logprob、唯一动作归属及 execution 计权的检查。保留或简化已有 session 收缩记录，但它只能称为上下文长度变化线索；不把线索条数当压缩次数，不给它新的拒绝权。
4. 若摘要生成经过同一策略、同一 execution 的捕获入口，建议沿用现有动作集合：摘要生成保留一次、使用终局任务 reward；摘要重注入为 prompt。它也沿用既有“模型请求次数”预算，不能另行暗中免计。若要专门排除摘要生成的梯度或预算，才是新的训练语义选择。

恢复自动压缩会使模型实际看到的输入发生变化，也可能多出摘要调用；这是需要记录在运行配置与实验说明中的 harness 行为变化。它并不要求改变 RL 算法，也不代表 I18 已解决。

真实 CC 仍留一项窄核对：在后续既定本地/基座诊断中检查一次实际压缩前后请求，确认摘要调用的模型与 session、capture 覆盖，以及是否发送服务端编辑字段。该核对用于确认目标版本的实际请求面；无需为枚举所有隐藏功能新增平台、长期挡板或专门八卡实验。

### 4.1 I17 的具体例子

假设一批有 10,000 个 `loss_mask=1` 的动作位置：

```text
10,000 个动作位置
├─ 2,000 因 ratio 过低被 DIS 拒绝
├─ 1,000 因 ratio 过高被 DIS 拒绝
└─ 7,000 被接受
   ├─ 2,000 支持集只有一个候选 token
   ├─ 1,000 支持集大于一个，但 advantage=0
   └─ 4,000 accepted 且 support>1 且 advantage≠0：候选信号
```

7,000 的接受数和 4,000 的候选信号数必须同时保留。后者也不等于“4,000 个 token 各自证明贡献了非零梯度”：参数梯度可能抵消，实际优化器行为还需第⑥面证明。这里的单例是词表采样支持集，不是 MoE 专家数。

当前 `dis_zero_advantage_accepted_tokens` 的实际定义包含 `support>1`，所以与单例类不重叠；汇总器显示时应说明这一点。`dis_zero_contribution_microbatch` 只表达该 microbatch 的 accepted=0，也不能替代真实全局零梯度判断。

### 4.3 必须先讲清的统计口径

1. **组、成员执行、训练行、token、optimizer step 是不同单位。** 一个 execution FORK 成三行，不是多做了三题，也不能将 reward、执行耗时或丢组损失算三遍。跨 run 关联包含 run 身份；训练侧沿用实际 sample/leaf/step 映射，不能仅凭局部 index 或文件顺序猜测。
2. **保留原始和、数量及未知数量。** 当前 `aggregate_train_losses(..., num_rollouts=...)` 会把所有指标除以该步 execution 数。比如原始 accepted=8,000、该步 8 executions，日志为 1,000；另一步均值 1,500 但只有 4 executions，两步总量为 `1,000×8 + 1,500×4 = 14,000`，不是 2,500。跨步比例用各自原始分子之和除以分母之和。全局归约后的多个 rank 副本只取一次。
3. **“发起”“已终结”“已被 buffer 取走”“确实参与了 applied step”分开。** 汇总时还没结束的长任务单列；结束事件缺失、未匹配成本和未知版本不能记为 0。候选动作与 applied step 的同批关系也不证明某个动作独自贡献了梯度。
4. **token 成本与计算成本分开。** `input_tokens_total` 是全部训练行输入长度之和。`input_tokens_excluding_last_row` 不是 B 相对阈值 1024 的额外成本；比较两种表示需要分别计算。各成员 elapsed 之和不是 run 墙钟、GPU 秒或可直接相加的提速空间。重叠阶段单独展示，不硬拼饼图。
5. **区分观测与解释。** session shrink 不能命名为压缩次数；同版本差异不能直接归因为 MoE；跨版本 sample log-ratio 不能不说明估计量就改名为 KL。若展示 entropy，要标明全词表还是采样支持集；不能把任意负 logprob 直接叫完整策略熵。
6. **按 task/长度的比较是诊断，不自动改训练分布。** 例如短任务保留率 90%、长任务 30% 值得查原因，但不能让监控程序据此自己重采样、改预算或放宽准入。

### 4.4 实施节奏与成本

建议用一个首版范围推进：**七面都应有基础摘要，细节按当前真实 producer 补齐；暂不加入 I18 路由度量，也不修改算法和自动处置。**

第一步盘点并接通现有 audit/事件的消费者，提供 run 总览、按 task/原因/长度的切片以及少量原始记录链接。第二步只对确实缺失的发起/消费身份、有限分布和阶段事实补轻量 producer。可以复用同一套汇总逻辑周期输出摘要与结束后报告，不先建设常驻服务或独立监控平台。

常开内容以每 attempt、每组、每 step 的少量标量与有界分桶为主；高基数 task/执行明细保留在已有文件中，由消费者切片。复用已计算的 support 和 detached log-ratio，不添加 actor forward，不导出全 token CPU 数组，不逐 token 同步。新增计数的设备同步成本由实现与审查明确；监控自身的耗时、写出字节量也应可测。

同版本 logprob 诊断沿当前已有路径使用。I24 将来若移除额外 forward，需要同时安排这项诊断的保留方式，不能由 I20 反向规定所有训练步永远多跑一次。大 tape 比较、完整词表分布或新增引擎事件属于专项诊断，不因“完整监控”自动常开。

实现验证重点是指标运输与口径：两个成员各多行不重复计权、跨 run/index 不错连、CP/DP 不重计、缺失不填零、均值还原正确、纯观测前后 loss/梯度不变。CPU 能验证消费者和多数归属/分母；已有分布式数值测试可复用。真实开销与实际缺失比例随原定 GPU 作业测，不为每个计数器安排新实验。
