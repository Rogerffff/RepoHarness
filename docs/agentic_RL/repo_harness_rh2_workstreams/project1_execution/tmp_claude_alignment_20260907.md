## 1. 当前方向已经形成雏形，具体配方仍待实验

用户与 Codex、外部 Pro 已围绕简历项目重新讨论目标，当前优先把项目一做好，暂不扩展项目二。

项目一的初步定位是：**面向真实 coding agent 的可靠、高效后训练系统。基于 miles/SGLang 和现有 harness，将可执行任务、可信评分、正确训练消费与独立评测连接起来，并通过受控实验证明自身改进的价值。**

需要共同完成的内容包括：

- **Infra**：解决实际链路问题，明确上下文改写、轨迹与组、mask、概率和版本的消费语义；让失败可解释、成本可测。
- **环境与数据**：构建和验证可重复环境，检查评分有效性，做好数据划分、多样性与目标模型难度诊断。
- **训练**：形成正确、合理的基线，再选择一项有依据的系统或数据改进，验证学习效果与成本。
- **评测**：固定模型、harness、题单与预算等比较条件，区分开发诊断、最终测试和迁移结果。

首版建议以 SWE 仓库修复为主，terminal 先作为补充评测候选。具体模型 checkpoint、正式数据规模、SFT、任务重配、OPD、多 harness 等尚需结合已有决策和初步实验确定。方向得到认可，不表示每个候选实现或超参数都已经批准。

重点是可归属、可复核的结果。上游训练内核、推理服务和通用异步能力如实归因；不以增加功能、代码或测试数量作为项目贡献的主要证明。

背景见 [项目一设计建议](../project1_design_advice_20260907.md)。

## 5. 本次明确偏好：两个任务共用目录，不拆 worktree

用户本次明确选择共用当前工作目录，方便管理；此前独立 worktree 是建议，不作为本次要求。

这个选择在当前规模下可以实施，但需要修正一个假设：**环境线程可以基本不修改训练内核，却不能假定完全不使用或不影响执行链。** 离线环境构建与清洗可以独立；真实 Claude Code 基座诊断可能复用模型接入、运行入口、日志和 grader。A 修改这些共享点时，B 的测量可能受影响。

B 也可以先使用独立的推理/评测入口，不接 learner、训练组装或准入，避免基座诊断被无关训练问题阻塞。此时要记录与正式候选链的配置和入口差异；模型、工具预算与评分口径仍需对齐，独立入口测通不等于候选训练链已验证。

最小协作约定建议为：

1. **修改按文件和批次归属。** A 主责通用 runtime、训练消费和执行生命周期；B 主责任务资产、具体环境适配、评分规则与评测分析。共享 grader、启动、eval 或 schema 文件，每批约定一个实际修改者。
2. **Git 操作串行。** 同目录共用当前分支与暂存区；各自只暂存和提交自己的明确路径。切分支、rebase、stash 等操作需要协调，避免改变对方正在工作的基础。
3. **关键跑数期间保持相关代码稳定。** B 做基座测量前说明所用入口和版本；A 暂缓修改这些被调用的共享文件。相关未提交改动要说明或保存差异，不能仅写一个与实际代码不符的 HEAD。
4. **运行资源分别命名和清理。** 各自使用明确的输出目录、运行标识和容器归属；共享 GPU、端口或依赖环境的变动先协调，只清理自己作业的资源。
5. **每条主线维护自己的交流记录。** 同一条线中的 Codex/Claude 约定本轮文档写入者。跨线留言写明需要什么、证据和受影响事项；写入文件不等于对方已收到，紧急事项另行送达。

这些是同目录协作的操作约定，不需要新增锁服务、审批程序或逐轨迹证明系统。
