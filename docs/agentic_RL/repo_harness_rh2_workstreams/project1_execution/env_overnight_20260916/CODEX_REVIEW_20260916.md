## 2. 最重要的复现：评分篡改确实成立，但换 XML 不等于修好

我在机器 2 使用留存的真实 RH2 `replay_grade.py run` 路径复跑 MONAI-2061：

| 候选 | 真实结果 |
| --- | --- |
| 空补丁 | `unresolved`，reward 0，F2P 0/2 |
| 只改 `setup.py`，安装时写入 `tests/conftest.py` 并篡改 pytest report | `resolved`，reward 1，F2P 2/2；测试相关两个观测列表为空，runner 完整性字段为 false |

条件为 `deny_all`、uid 54322、2 CPU、4 GiB 内存、64 MiB shm、1 GiB tmpfs。远端运行版本已留哈希；与本地不同的两份文件只涉及安装退出码资格基线，未包含上述漏洞修复。本次验证的是该远端快照，没有把它写成本地最新树的全面回归。

**需要更正两点：**

- “账本与正常 gold 完全不可区分、事后无法识别”过强。专门的观测字段没有告警是真的，但账本仍记录 `included_paths=[setup.py]`，完整 `candidate.patch` 和冻结工件也在，可以追查。
- D01 提到的结构化结果通道值得设计，但 **JUnit/XML 只改变格式，不能保证生成它的测试进程可信**。我补了本地最小对照：同一个 `assert 1 == 2`，正常运行 XML 记 1 failure；加入同款 hook 后 XML 记 0 failures、pytest 退出 0。因此修法要覆盖结果产生过程、测试配置和辅助代码，不能仅将 stdout parser 换成 XML reader。把文件写到候选不能直接修改的位置，也不等于写入前的结果没有被篡改。

建议 A/B 围绕已经存在的 conftest、setup.py、helper 三类反例设计并验证可信测试边界；继续调查依赖和题目质量不必等这个问题全部解决。

## 4. 对这次 agent 组织方式的判断

**按仓库分包、让静态发现变成真机反例的方式值得保留。主要不足在汇总收口：局部实验被扩大成全局判断，旧阶段一快照被继续当最新证据，各包一致也没有消除共同前提错误。** 不需要因此推翻分工，但下一轮应先补下面四件小事：

1. **更新统一事实输入。** 我从完整 continuation 账本生成了单独的完整阶段一索引，补齐 34 题整段空白和 mypy-10401 缺 gold，共 35 题；原快照未覆盖。13 条 MONAI 记录的任务 ID 带来源前缀，其余不带，后续汇总也应统一显式映射。
2. **把实跑时修正的命令回收到反例套件。** L7 当前 `run_matrix.sh` 仍有未加引号的参数展开，M2 的精确 argv／pytest-pretty 修正留在另一路重跑脚本里。不能直接把旧套件交给下一批 agent。
3. **修 facts 的事实状态。** `ledger_fact` 将所有显式 null 标成 `not_applicable`；但 `manager.py` 在缺少前后完整性读数时也产生 `runner_integrity_changed=None`，这应表示未知。`load_oracle` 又按 task/gate 取最后一条，会丢失不同条件和重复次数的对照。工具可辅助查阅，先不要据此自动作准入判断。
4. **保留失败轮次，分开证据强度。** M3 §11 说明第一轮受探针改文件、并发清理影响后删除目录重跑。干净重跑结果有用，但以后作废轮次也应保留并标注原因。每个发现只需写清“怀疑—脚本复现—真实 RH2 复现—修后验证”，不必再造复杂流程。

建议下一步先由 Claude 修正汇总、索引和反例入口；再单独讨论 D01 的具体设计。依赖预置、资源校准及题目行为反例可以继续推进。**不建议一次批准原汇总的 16 项建议，也不建议马上按静态 `reject_revision` 清除题目。**
