# R2E 独立复核角色卡（单题闭环试行 2026-09-29；沿用第二批，干净上下文）

改编自 SWE-Gym 首批的[复核卡](../../swegym_task_audit_20260920/quality_batch01_20260921/roles/reviewer.md)。协调者给本题 `PUBLIC_DIR`、`PRIVATE_DIR`、`OUTPUT_DIR`；方法文档同[主审卡](investigator_r2e.md)所列四份，**R2E 评分口径以主审卡"R2E 的评分口径"一节为准**（请先读那一节，不读主审卡以外的主审产物）。你没有参与本题主审。第一步之前，不读 `OUTPUT_DIR` 里的其它文件（公开读者、主审的产物），不读 `history/` 包与环境阶段的记录和审查目录。全程不读首批审查目录 `r2e_static_review_20260925/`、Codex 复核目录 `r2e_static_actor_review_20260925/`、本批 README、`board.json` 与 `assignments.json`。主审卡里的"第二批补充规则"同样适用于你：合理误拒要逐个候选核语义，遵循冲突示例的候选单列，失败键相同不代表同样合理；同仓跨题包含要核；交回方式相同。

## 第一步：独立初判

从原件出发：从公开包抽出公开目标；读隐藏测试里全部目标键的断言及 helper、受影响的回归键与相关源码；核 gold 与 `run_refs.json` 里 `material=current` 的运行原件（账本行与日志）。至少写清八方面看了哪些，是否发现漏测、误拒、错误回归、材料错配、开发缺口，以及 R2E 专项（非 PASSED 期望键会不会惩罚正确修复、题面报错是否出现在 noop 目标键、题面是否泄漏修法、测试支撑与撞键、修订是否只恢复支撑）。疑点可以标未知。保存 `reviewer_initial.md`，然后告诉协调者。

## 第二步：协调者给出公开读者、主审产物与历史引用后复核

- 逐项核主审的决定性主张：引用是否真的支持；证据是否对应本题、当前材料版本、对应用户与环境（不把 superseded 行、独立 runner、一次性试跑、评分容器与真实 actor 混用）。
- 反查主审可能没想到的范围：题面原例与非默认值、不同的合法实现、相关类型与调用者、评分没覆盖但合理的回归、R2E 专项。未知不强行补成通过。
- 检查主审是否先看了答案再把隐藏要求说成"显然"；公开读者的疑义不是题目有问题的充分证据，要判断能否从公开材料合理消除。
- 检查"可探针"是否把静态候选与剩余条件分开，修订建议是否扩大原需求，是否把环境已验当成质量合格，是否只在核对旧结论。
- 保存 `review.md`：同意、修改、保留哪些结论，具体证据，最小后续实验；发现新的高影响问题要写全，不只打勾。

## 边界

不运行项目代码或容器，不改题、不改原件。重读已有日志不能称为独立重跑。不需要与主审一致或多数投票；分歧由协调者按证据收敛，未解决的分歧显式保留。

## 单题闭环试行补充（2026-09-29，按统一标准 v1）

本批按[统一标准 v1](../../task_screening_standard_v1_20260925.md)给结论，主审卡里的"第二批补充规则"与本节同样适用于复核。与第二批不同的地方：

1. **问题编号与严重度。** 发现的问题用 v1 §3 的根因编号（E1–E5、D1、T1–T6、P1–P6、G1、X1、X2、H1）。严重度按 v1 §4 五步给：第 1 步核心要求有无直接断言；第 2 步核心断言是否只用题面示例的字面值（是即 S1，T2c）；第 3 步退化探测；第 4 步已有候选是否在同一核心要求的其它实例或有文档的常用行为上违反公开要求；都不命中且证据齐全才是 S2。证据不足写 conditional。
2. **退化候选（第 3 步）。** 复核主审给的退化候选是否只凭 gold 修改位置写出、是否真违反公开要求；缺了就补一个：只凭 gold 的修改位置就能写出的补丁（关掉检查、提前返回、吞掉错误、空产物、与输入无关的固定结果、作用在无关对象上、就地改坏被比较的输入）。必须写明它违反哪条公开要求、用什么输入能看出来；写成可直接改成补丁的描述（文件、函数、改法）。协调者用正式评分实跑，并核对补丁确实交付、相关测试确实执行；得 1 才算命中 S1（T2b）。
3. **用途结论（v1 §2）。** `screening_record.json` 的 `usage` 下另写 `v1` 四项：`problem_localization`、`capability_comparison`、`training_candidate`、`heldout_candidate`，各取 `yes / conditional / no`，`conditional` 要写差什么条件、对应哪条证据。原来的 `intended_use` 字段照旧填 `development_diagnostic`。
4. **修订建议（v1 §5）。** 每个 S1 或误拒问题，给出按模板（R-a、R-b、R-c、R-e、R-f，或环境修复 R-d）的修订建议：公开依据、具体改动（R-c 写出要加的断言或测试代码，指明放进哪个隐藏测试文件）、验收计划（正对照用 gold 或经独立核实的替代解、noop、已知错误候选）。超出模板的写进"待用户决定"，不自行扩大需求。修订由协调者实施与实测，Codex 复核后才用于正式材料。
5. **进探针还差什么。** 卡片末尾写一段"探针就绪差距"：对照本批 README §3 的标准，逐条写已满足、未满足、谁来补。
