## 已经证明什么

同一原 FrozenPatch、官方脚本、材料、资源和原评分预算下，预制权限能明显减少重复交权开销。每次评分仍创建全新容器和可写层；官方文件和每级祖先目录仍执行保护与自证。

| 固定输入 | 现行 fresh，2 次 | 预制 fresh | 每次解析测试数 | 结论 |
| --- | ---: | ---: | ---: | --- |
| DVC9395 | 232.79、248.72 秒 | 解释器权限：97.41、97.61 秒 | 42 | 中位数减少 59.5%，逐测试状态一致 |
| Pandas48106 | 1134.62、1130.36 秒 | 权限加第三方依赖：770.60、855.66 秒 | 1040 | 中位数减少 28.2%，状态一致；主要余项仍是源码安装／构建 |
| Coverage EA69 | 45.35、41.23 秒 | 仓库权限：14.89、15.37 秒 | 49 | 中位数减少 65.0%，逐测试状态一致 |

实施建议：优先集成权限预制加全新容器评分；原容器保持显式实验模式，Prime 等线上证据齐备后再比较。该建议尚未变成生产默认配置。

这些是少量固定输入对照，不是 p95 或全题集收益估计。DVC 与 Pandas 原候选仍为 0 分，EA69 仍为 1 分；结果一致只说明本片未改变这些输入的评分，EA69 既有语义争议没有因此解决。

DVC 的真实 `GradingQueue` 四次串行完成用时 386.17 秒，两路并发为 207.40 秒，吞吐提高至 1.86 倍。两路每次评分约 100.53–102.05 秒，串行约 93.26–94.99 秒；整体完成更快，但不能称单次计算成本降低。每个评分子进程分别持有公共 `cpu_slot`，协调器不运行 Docker。

## 准备成本与无效尝试

准备成本单列，不能隐藏到服务耗时之外：DVC 权限模板 157.32 秒；Pandas 权限模板 509.57 秒，第三方依赖层另需 6.17 秒，新镜像空补丁资格检查 721.67 秒；Coverage 先有 1.99 秒的解释器前缀模板，再加 35.99 秒仓库权限层，两层累计约 37.98 秒。派生镜像都绑定不可变源镜像、profile 和准备配方摘要。按这些中位数差值粗算，只计成功准备，DVC 与 Coverage 各复用约 2 次可覆盖准备成本；Pandas 计入新镜像资格检查约需 4 次。这个摊销估计不含本批研发、失败尝试与其他验收开销。

- Coverage 仅预制解释器权限没有效果：其声明前缀不存在，单次仍为 43.31 秒。定位到仓库交权后才取得收益。
- Pandas 权限单独对照为 843.19 秒，只做 1 次。第三方依赖模板仍需执行原候选源码安装／构建；不能用少量运行差异宣称依赖层本身已有稳定收益。
- Pandas 第一次依赖模板准备失败，旧版本未保留完整失败日志；后来补齐失败回执并修正准备入口，第二次成功。失败原因未完全复证，不把推断写成事实。
- Coverage 第一次原容器夹具在制造污染时遇到原基线尚不存在的官方测试目录，未进入评分。夹具已改为先建目录；失败记录保留，不能计入成功对照。

## 原容器评分的范围

已实现默认关闭的 `bringup → generate → GradingQueue` 接口：harness 启动前封存，持久化 FrozenPatch 后交接；核对 physical attempt 和完整基线，撤网并核实际网络为空，停止 actor 进程，核固定环境，恢复整个工作树，再只重放冻结成果。镜像／资源不兼容或复用容量已满时直接 fresh；环境污染时先关闭原 scope，再用同成果、同绝对期限和原 profile 尝试一次 fresh。

删除责任只有一个 owner。提交者取消会等待 worker 收口；已停止但删除失败按既有规则隔离，保留租约和网络，无法确认停止则立即 run-fatal。创建者仍记为实际创建者 `slime_adapter`，不能因交接改写历史。

DVC 的 grader-profile CPU 原型评分为 58.98 秒，另有 67.64 秒封存／模拟 solve 准备，42 项状态一致。这个数字不能当作真实 rollout 的端到端加速。实际 rollout profile、真实撤网和真实队列的交接也已在 DVC 与 Coverage 通过：评分分别为 55.97、15.68 秒，预先封存分别为 13.31、2.67 秒；完整准备加污染夹具分别为 64.03、41.92 秒。逐测试状态均一致，旧进程归零、环境匹配、基线与官方文件恢复、Git 反控和清理均通过。Coverage 复用并未比权限优化后的 fresh 更快。solve 仍为固定成果污染夹具，未调用真实 Claude Code 或 GPU 模型，生产开关保持默认关闭。

Pandas 的 grader-profile 原型也通过，1,040 项测试状态一致，环境匹配、旧进程归零、基线／官方文件恢复、Git 反控和清理均通过；评分为 876.90 秒，另有 313.56 秒准备。该次评分本身就慢于两次优化 fresh，不能作为加速证据。准备中的环境封存占 165.18 秒，环境树共 280,070 项；恢复与复核阶段 142.66 秒，说明强恢复的成本随环境规模增长。实际生产 Pandas actor/grader 镜像还不同，当前接口会 fresh 回退。

另一个 Coverage CTracer 反控已验证：修改真实 C 源码并设置旧 mtime 时，已有扩展不会体现新文本；强制构建后加载了不同 SHA 的扩展并体现新文本。三个原候选本身只改 Python 文件，因此本片不宣称已经证明所有编译型任务的重建正确性。

## Prime 的实际状态

VM 与 Docker 不视为相同隔离方式；执行、网络、资源和清理事实分别记录。完整条件见 [实现边界](design.md)。
