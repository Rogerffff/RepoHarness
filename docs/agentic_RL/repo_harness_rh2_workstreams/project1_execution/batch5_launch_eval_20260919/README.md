### 6.1 I21：保留 A/B 两种方式，先补共同接线

**用户决定**：A 独立固定 checkpoint 评测与 B 暂停训练后复用现有引擎可以共存；若 B 能方便复用 miles、增量代码不多，可以一起做。若接入复杂，后置 B，不阻塞第一次训练。不要求首训前两种方式都实现完，也不把等待所有在飞任务结束预先定为唯一办法。

**本轮静态核对**：

- `miles/ray/rollout/eval_dispatch.py:29`：共享引擎分支直接 await `rollout_manager.eval`。`train_async.py` 在权重发布之后 await 该 dispatch，因此这条标准驱动路径会等待 eval 返回才继续下一轮训练/发布。
- `miles/rollout/fully_async_rollout.py:188`：共享引擎 eval 清除 `_producer_resumed`，阻止 worker 后续提交新组；finally 恢复。该函数没有等待 `_active_groups` 结束，已启动的 harness/评分仍可能执行。暂停提交不等于全链已经排空。
- `rollout_manager.py` 在 train/eval 函数路径相同时复用同一实例；这是共享 producer 暂停生效的重要现成接线。
- RH2 `adapters/miles/generate_fn.py:144` 仍先走训练身份与 prepared assignment，再透传 evaluation；不能仅开启 eval 参数便宣称 formal 评测已接通。

**当前窄工作**：复用同一 harness、任务解析与评分，明确 eval 任务/attempt 身份、模型来源及结果运输，避免把训练组过滤语义带进评测。B 的增量范围在实施 Brief 中说明：现成暂停实际覆盖什么、在飞任务如何处置、异常能否恢复、共享资源会不会干扰已批墙钟处置。无需为此预建通用在线调度器；不把一次性 shutdown 当成可恢复 pause。上述为接入核查内容，未运行真实 eval，也尚不能确定增量代码量。

必需的 before/after 结果仍须真正完成并对应确定权重，不能用 dispatch/skip 代替成功。结果使用已有模型、harness、题集、预算和评分配置身份，不增加每次请求全模型哈希。题目与统计协议由 B 负责，A 负责公共接线。
