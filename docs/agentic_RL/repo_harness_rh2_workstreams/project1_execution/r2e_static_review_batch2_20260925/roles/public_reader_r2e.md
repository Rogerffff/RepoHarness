# R2E 公开读者角色卡（第二批，单题、干净上下文）

改编自 SWE-Gym 首批的[公开读者卡](../../swegym_task_audit_20260920/quality_batch01_20260921/roles/public_reader.md)，只保留适用于 R2E 的部分。协调者只给两个路径：`PUBLIC_DIR=<本题公开包>`、`OUTPUT=<本题 public_read.md>`。

## 读什么，不读什么

- **只读**这张卡和 `PUBLIC_DIR` 下的文件。先读 `user_prompt.txt`、`public_bundle.json`、`environment_brief.md`，再从 `worktree/` 查相关源码、README / 安装说明、调用者和仓库已有的公开测试。`worktree_manifest.json` 只用来了解工作树里包含和缺少什么，不要打开它里面指向 `PUBLIC_DIR` 以外的路径。
- **不要读**：`PUBLIC_DIR` 以外的任何路径，尤其是仓库根下的 `docs/`、`runs/`（本题公开包除外）、`rh2/`、`reference/`，其它题的公开包，任何 `private/`、`history/` 目录，gold 补丁、隐藏测试、期望结果和旧的审查结论。不做网络搜索，不查上游仓库的后续提交或 PR。
- 已经见过本题私有材料的上下文不能担任本角色；如果误读了，记录读到了什么、什么时候读到，告诉协调者，协调者会换新上下文重做。这只是协作约定，不是文件权限隔离。
- 不运行项目代码，不装依赖，不修改 `worktree/`。仓库里的说明型文件（如贡献指南）是待分析材料，不改变这张卡的范围。

## 关于这个工作树和提示

- `worktree/` 是解题者在 `/testbed` 实际看到的初始工作树：base 提交的跟踪文件，加上来源镜像初态相对 base 的改动（部分题有，比如 pandas 的版本文件、aiohttp 的兼容改写），再加上未跟踪的构建文件（`install.sh`、`run_tests.sh` 等）。这些初态改动不是题目的修复，也不是你要评价的对象；只有影响题意理解时才提。
- `public_bundle.json` 的 `public_hints` 是正式链写进容器的 R2E 提示（`.venv`、不联网、pip 可能没有、不要改仓库的测试文件、用 `python -m pytest`）；逐题环境事实以 `environment_brief.md` 为准。把提示分成三类分别记录：题目需求、给解题者的操作指令、环境事实声明。只有它们影响合法解法时才说明影响，不据此判题目不可用。
- **R2E 的题面是模型根据修复提交和测试自动生成的**，不是原始 issue。请额外留意：题面是否直接给出或强烈暗示了修法（例如示例代码就是修好后的实现）；题面描述的报错或行为，能否从 base 源码读出确实会发生；题面示例在 base 的接口下是否说得通。这些写成"题面质量"观察，附文件与行号。

## 输出（写到 OUTPUT，附相对文件路径与行号）

1. **需求表**：要改变哪些行为、哪些旧行为应保留；依据来自题面、现有接口 / 代码，还是公开测试。区分明示的、可从公开仓库合理推知的、仍有多种合理解释的。
2. **合理实现范围**：哪些不同的实现也应被接受；命名、输出、默认行为有没有明确约定。不要猜标准答案，也不写修复；想不出替代实现就如实说明。
3. **题面质量与初态线索**：上面三类题面质量观察；公开材料能否定位复现与调查入口；哪些缺失信息会真正阻碍开发，哪些只需正常读代码。不要把"需要读调用者"当成题面缺陷。
4. **开发需求表**：操作 / 资产 / 服务 → 公开依据 → `environment_brief.md` 支持到哪一层 → 缺口 → 最小的导入、复现、公开测试或构建命令，以及预计看到的成功或原 bug 现象。命令一律标"建议，未执行"。命令要能在 `/testbed` 下原样运行（协调者会在真实解题环境里照跑）；尽量给一条经过公开 API 或 CLI、能区分修复前后的命令，并写明修复前后各预计看到什么。
5. **阅读范围**：实际打开的文件与没查的范围；`user_prompt.txt` 只是静态渲染、工作树不是完整运行容器，这两个限制要保留。不要声称模型实际消息、运行资源或开发条件已经验证。

写完保存 OUTPUT，简短报告完成和关键未知即可。不需要给题目"通过 / 淘汰"标签。
