# 协作协议（唯一权威版本；状态：v1-rc，待用户确认"v1 生效"）

> 本文档是用户（owner）、Claude（实现者）、codex（审查者）三方协作方式的
> **唯一权威**。根目录 `CLAUDE.md` / `AGENTS.md` 只放硬规则摘要和指向本文
> 的链接，不复制正文（防漂移）。
>
> **本协议自身的修改权**：改变 T0/T1/T2 边界、角色权限、审批节奏，属于
> **T0**——必须用户明确批准后生效；纯文字澄清和链接修复属于 T2。审查
> 标准的修改权**按 review-standards.md §9 三档细分**（补锚点 T2 / 收紧
> 范围 T1 / 增删维度与改强制性 T0）——标准需要随事故演进，粗粒度 T0 会
> 堵死演进。治理机制本身只在三类信号下修订：流程失效证据（熔断反复触发、
> T0 上报过频或过疏）、角色/资源变化、阶段转换改变成本结构。
> 任何修订必须同步两个入口的摘要。
>
> 定案过程：Claude 提案 → codex 修正四点（全采纳）→ 用户三项选择（学习
> 台账 / 暂不亲自写码 / 阶段级确认）→ codex 协议审查七条（全采纳，
> 2026-07-23 本版）→ **待用户确认 v1 生效**。

## 1. 角色分工

| 角色 | 职责 |
|------|------|
| 用户 | 项目 owner：架构与训练语义的最终决策者、实验目标制定者 |
| Claude | 主要实现者：按已确认设计写代码/测试/文档；起草决策包与 Owner Brief |
| codex | 独立审查者 + 设计顾问 + 代码讲解者：写码前审设计、写码后审实现、阶段性带用户过关键链路 |

codex 不只在事后抓 bug：重要批次开工前先审设计，减少"写完一千行再推翻"。

## 2. 决策分级（T0 / T1 / T2）

| 等级 | 含义 | 谁决定 | 何时沟通 |
|------|------|--------|----------|
| T0 | 改变项目语义、长期架构、实验有效性或重大成本 | 用户拍板 | **写代码前** |
| T1 | 在已确认语义下选择具体工程实现 | Claude 自主，codex 检查 | 实现后在报告中明确列出 |
| T2 | 不改变行为和契约的局部细节 | Claude 自主 | commit 留痕即可 |

### T0 升级规则（任意一条为真即 T0，不按"算法 vs infra"分类）

```text
1. 改变训练样本准入、reward、loss 权重或算法语义
2. 改变公共 schema、协议或唯一事实来源
3. 改变跨组件状态所有权或崩溃恢复语义
4. 新增可能产生系统性样本偏置的拒绝路径
5. 降低既有安全边界
6. 引入重要依赖、fork 或外部服务
7. 明显增加 GPU 成本、开发周期或运维复杂度
8. 推翻已经由用户确认的决定
```

### 边界细则（易混处的判例）

- **落实已确认的 fail-closed 规则 = T1**（如"audit 持久化失败必须停训"
  定案后，用 fsync/typed exception/WorkerHalted 实现它都是 T1）；
  **新增一种会剔除轨迹的 fail-closed 规则 = T0**（规则 4）。
- 超时、重试次数等可能造成长度偏置的参数调整：至少 T1 强报告；影响明显
  时升 T0。
- 把已定案的"失败停训"悄悄改成"丢样本继续训"：T0（规则 1+8）——训练
  分布变了。
- `reason_code`、schema 字段名、公共错误码**不是 T2**（机器契约）；变量
  命名、docstring、日志文案才是 T2。
- **测试 oracle 不是 T2**（codex 标准审查 7）：修改测试期望值、增加
  skip/xfail、改 pytest marker、改测试数据语义、改 acceptance evidence
  或 gate fixture——这些改变"什么算正确"，至少 T1 强报告（否则可以
  通过改答案把真实 bug 变绿）。纯搬迁（digest 不变+引用同步）才是 T2。
- **提交纪律**：协议/标准变更、工具链配置、存量源码清理分开提交
  （混提无法独立审阅与回滚）。
- **公共 schema 的粒度**（防止"加任何字段都打断用户"）：改变字段语义、
  必填性、兼容性或唯一事实来源 = T0；**按已批准设计**新增字段或发布新
  schema version = T1 强报告；非契约的内部模型/局部变量 = T2/T1。
- **熔断阈值分档**：指标统计方式与初步校准实验 = T1；**会触发
  task_quarantine / run_halt 或系统性改变训练覆盖率的正式阈值 = T0**
  （首训前预注册并由用户确认）；纯告警黄线 = T1。
- **推翻既有结论的改动，无论多小，一律在报告 ④ 段显式标出**（历史教训：
  轮次 14 推翻轮次 9 的硬耦合——这类最容易让 owner 认知与现状脱节）。

### T0 决策包格式（Claude 起草，不许只问"同意吗"）

```text
要决定什么
现有代码事实
两到三个可选方案
推荐方案及理由
不同选择的长期代价
哪些以后还能改，哪些改起来很贵
```

## 3. 任务流程（FA-2A 起生效）

```text
1. 阶段决策包    Claude 起草本阶段全部近期 T0（只含即将影响本阶段的，
                 不提前冻结远期项）→ codex 审设计 → 用户拍板一次
2. 计划更新      Claude 只改 05 计划；codex 复审计划；通过后才写码
3. 小批实现      每批一个明确目标的纵向切片（如 F2-1 只解决身份贯穿），
                 不一次改五个组件；每批开工前 Claude 发一页 Owner Brief
                 （目的/数据流/关键不变量/无 T0 声明）——**不阻塞开工**，
                 批内冒出新 T0 才停下来问
4. 独立审查      codex 按 §5 清单审实现
5. 修复闭合      Claude 修真问题；发现改变设计的回到 T0 流程；
                 每轮收尾发六段报告（§4，对话消息形态）
6. 学习回顾      每批产出学习摘要进台账；阶段末 codex 带用户过一条关键链路
7. 阶段验收      代码、测试、证据、遗留风险、下一阶段决策统一收口
                 （阶段末报告同样走 §4 模板）
```

节奏定案（用户 2026-07-23 选择）：**阶段级确认**——决策包拍板一次，
小批 Brief 只供了解不等回复，批内 T0 即停。

## 4. 每轮报告模板（六段，缺段视为报告不完整）

**报告的形态**：不是独立文档，而是每个工作轮次（一个小批实现、或一轮
codex 审查的处置）收尾时 Claude 在**对话里发给用户的总结消息**——对应
§3 流程第 5/7 步的收口动作。报告内容按条分流进权威文档（见下），报告
全文不另建档（防止与权威文档重复维护而漂移）：

| 报告段 | 持久化去向 |
|--------|------------|
| ① 拍板结果 | 05 计划 / 对应决策包文档 |
| ② T1 决策 | `implementation-notes.md` 当轮小节 |
| ③ 挡板变动 | 权威状态页的挡板登记表 |
| ④ 推翻的旧结论 | `implementation-notes.md` + 权威状态页标注 |
| ⑤ 测试/账本 | 账本文件本身（inspect 重算）+ commit message |
| ⑥ 学习摘要 | `learning-log.md` 对应主题分区 |

```text
① 待用户拍板的 T0（常为空；非空时附决策包格式）
② T1 决策摘要及理由
③ 临时挡板变动：新增 / 命中 / 解除（对照权威状态页登记表）
④ 推翻或修正了哪些旧结论
⑤ 测试、证据与账本状态
⑥ 学习摘要：本轮一条关键调用链、一个核心不变量、一个失败场景
```

报告 ② 段只列本轮**最重要的 1~3 项** T1（其余进 notes 即可）。用户
平时至少看 **①③④⑥，并快速浏览 ②**——T1 决策正是学习工程设计的主要
来源，不建议完全跳过。每轮末尾附"本轮没有改变哪些已定案语义"一句
（防实现过程悄悄改设计）。

## 5. 审查（维度与规范见 `review-standards.md`，本节只留治理规则）

审查的**技术规范**——五级审查矩阵（决策包/执行计划/切片/集成与验收/
训前总审计）、维度 A~N 定义、T0 完整性扫描、finding 八要素、N/A 证据
规则、集成审查强制产物与 Owner Gate Packet、Claude 交接前自检清单、
风格工具化与提交纪律——全部以
**`review-standards.md`** 为唯一权威（2026-07-24 从本节拆出，理由：
治理与技术规范混在一起两边都改不动；审查按尺度分级而非给单次审查加
并行人手）。本节只保留两条治理规则：

### 分歧收敛机制（codex 协议审查 1）

```text
codex finding 必须包含：当前行为、违反的不变量、证据、影响、建议分期。

Claude 对每项只能三选一回应：
  accepted                     —— 采纳并修复
  rejected_with_evidence       —— 拒绝，附源码/论文/实测证据
  deferred_with_owner_and_gate —— 递延，指明归属批次与闸门

codex 最多再复核一轮：
  涉及 T0 或正式训练闸门仍有分歧 → 交用户决定；
  普通 T1 分歧 → 双方证据与残余风险记入 notes，不无限来回。
```

### 修复循环熔断（codex 协议审查 2——识别"问题来自结构"，不是限制轮数）

任一触发即**停止增量修补**，先提交根因分析与替代设计（回到 T0/设计
检查点流程）：

```text
同一状态边界连续两轮出现新 P0；
或某个修复本身引入新 P0；
或修复所需改动已跨越原切片的多个 ownership 边界。
```

依据：FA-1 九轮修补的教训——单测数量持续增长不代表架构正在收敛。

## 6. 学习机制（用户 2026-07-23 选择：学习台账 + 暂不亲自写码）

- **学习台账**：`learning-log.md`（workstreams 根）按主题分区积累——
  每轮报告的 ⑥ 归档进对应主题；codex 的组件讲解（一张流程图 / 三个关键
  类 / 一条成功路径 / 两个失败路径 / 五个不变量 / 三处值得读的代码）
  也归档于此。面试前当复习材料整体过一遍。
- **关键路径学习课程表**（codex 提议，台账的主题分区依此）：
  ① async/await、event loop、task cancellation；② 线程 vs event loop、
  call_soon_threadsafe；③ producer/consumer、queue、backpressure；
  ④ identity、idempotency、lease/ACK、at-least-once；⑤ 状态机、事务式
  持久化、崩溃恢复；⑥ policy version、staleness、off-policy 修正与 DIS；
  ⑦ fail-closed 的数据偏置与 fail-loud。
- **面试必答清单**（台账首节维护，起点八条）：task→rollout→optimizer
  step 全链；三层身份为什么是三层；各组件在哪个线程/进程；为什么 infra
  failure ≠ reward=0；为什么 fully async 需要 policy version 和 DIS；
  为什么缺员组不能静默可变 n；为什么 fail-closed 仍可能造成偏置；真实
  跑过哪些 GPU 实验、发现了什么、哪些结论未验证。
- 亲自写码：现阶段不在主干预留任务；保留"复盘性重写"选项（用户任选
  组件重写作练习，不进主干）。
- 没有新知识的轮次，⑥ 段允许如实报告"无新增"——不为满足模板重复
  写内容。

## 8. 近期 T0 决策包范围（FA-2A 开工前）

只决定即将影响 FA-2A 的四项（codex 修正 4：不提前冻结远期项）：

1. episode timeout 的终止分类与训练语义
2. F2-4 崩溃恢复与 replay identity 语义
3. CaptureRegistry 终局：单 owner + 消息传递 vs 长期跨线程共享锁
4. 拒绝率熔断按 task / component / run 三种 fault domain 如何分流

**显式延后**：DIS 分母档位（provenance_tokens vs accepted_tokens）等
FA-4 接线前再定。**不是 T0 的**：overlap 挡板——已定案"临时保正确性、
正式训练前必须解除"，按闸门 + T1 工程任务跟踪，不再作为选择题。

决策包文件：`fa/fa2a_decision_package.md`（Claude 起草 → codex 设计
审查 → 用户拍板）。

**决策包状态落账（codex 协议审查 7）**：每份决策包头部必须带：

```text
status: draft / approved / superseded
owner_decision: <用户对各项的选择>
```
