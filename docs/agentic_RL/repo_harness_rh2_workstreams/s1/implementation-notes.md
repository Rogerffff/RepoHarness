- [S1-1b] **契约收紧修复（S1-1 复核发现的 6 个泄漏 R1~R6，全部先证实"修复前可通过"再变成 fail-closed 回归测试）**。反例回归清单：
  - R1 `GradingReport` unresolved + reward=1.0 → 现拒收（二值锁：unresolved 恰为 0.0）；
  - R2 resolved + reward=NaN → 现拒收（基类 `allow_inf_nan=False`，NaN 能穿过一切数值比较校验器）；
  - R3 resolved + reward=0.5 → 现拒收（二值锁：resolved 恰为 1.0）；
  - R4 tests_failed + 四计数全空 → 现拒收（tests_failed 必须四计数齐全；解析不出计数应归因新增的 `test_log_parse_failed`）；

  - R6 `TrajectoryProjection` branches=2 + segment_count=5 → 现拒收（投影层互检 segment_count == len(branches)）。
  新增测试 40 个（含 14 个 schema 的 allow_inf_nan 参数化锚点），全套 274 → 314 绿。
- [S1-1b] **reward 二值锁带版本字段**：`GradingReport.reward_scale_version = Literal["binary_v1"]`（default 同值）。未来连续 reward 必须显式新增枚举值并同步改校验器，不允许在 binary_v1 下静默放宽——0.5 这类中间值只有在升版评审后才可表示。
- [S1-1b] **`test_log_parse_failed` 归 infra 族**：语义 = "测试跑了但官方 parser 从日志解析不出结果"，是基建问题不是模型负样本，与 `infra_failure` 一样只配 failed_to_grade、强制 reward=None、必填 infra_failure_detail、禁携计数。`INFRA_FAILURE_CATEGORIES` 常量已导出（S1-4 manager 用）；envpack parser 层照旧永不产出 infra 族（test_grading_outcome_fields_never_emits_infra_failure 断言已同步覆盖新成员）。
- [S1-1b] **capture 收紧两条**：`response_token_count>0 ⇒ response_token_ids_ref 必填`（partial/failed 不豁免——无 ids 引用的计数声明无凭据）；`capture_status=failed ⇒ capture_failure_reason 必填`（失败不可无因），同时 failed 豁免 raw_meta_info 的"至少一个"规则（请求失败可能根本没拿到 meta_info，强求会逼生产者伪造 digest）。
- [S1-1b] **accepted 语义定案（不新增字段）**：`BackendHandshake.accepted` 仅表示后端物理接收；可训练性唯一权威是 EligibilityReport（policy_staleness 维度）。accepted=True + staleness_within_threshold=False 是合法形态（后端有权接收过期样本，H10），测试证明该形态下 online 档照样不可表示（`test_accepted_is_physical_receipt_not_trainability`）。按 R2 单一权威原则拒绝新增第二个可训练性字段。
- [S1-1b] **fan-out 建模定案（orchestrator 决策落地）**：单投影多 branches 为权威——一个 rollout/session 产一个 TrajectoryProjection，compaction/fan-out 分段全部作为其 branches；`RewardFacts.segment_count`（在场时）必须 == len(branches)，多分支投影必须申报 segment_count；`parent_rollout_id` 只用于跨 rollout 的 GRPO 同题兄弟组，不用于 rollout 内分段。正反测试与 guide §6.6 样例齐备。
- [S1-1b] **两条投影层互检补强**：N-3 mask=0 span 与来源互检（sampled_assistant 源上的 mask=0 只许降级类理由 replayed_sibling_response / retokenization_drift_downgraded，禁标 prompt_context 类——防止把降级事实伪装成普通上下文）；N-4 `kept_token_count >= response_token_count`（top-p 每 token 核集合至少 1 个）。
- [S1-1b] marker 扫描改为按字典序遍历名单（一行）：多 marker 命中时返回值跨进程确定（不同 PYTHONHASHSEED 下 frozenset 迭代序不同），evidence 可复现比对；已加确定性回归测试。
- [S1-1b] **envpack（S1-2）二值锁影响核查结论：不受影响**。`grading_outcome_fields` 本就只产出恰好 1.0/0.0 且 tests_failed 分支四计数齐全，全部现有 fixture/调用无需改动；仅把"parser 永不产出 infra"断言从单值升级为覆盖 `INFRA_FAILURE_CATEGORIES` 全族。
- [S1-3] **模块落位 `adapters/slime/projection.py`**（包形态，S1-6 的 generate.py 同包），公开面：`project_from_slime` / `assert_renderer_class`（U-G 守门）/ `decode_int32_tape`（tape 解码唯一实现点）/ `SlimeProjectionError` / `SlimeBranchAnnotation` / `SlimeRewardInput`。adapter 对 slime Sample 只做 duck 型属性读取（不 import slime/torch），base64 tape 用 stdlib `base64+struct` 按 int32 小端解码（与 `torch.frombuffer` 在 x86_64/aarch64 的字节序一致）。
- [S1-3] **mask=0 来源注释走显式参数，不塞 Sample.metadata**：slime loss_mask 只有 0/1，"这段 0 是工具输出还是兄弟重放"只有编排层知道，经 `SlimeBranchAnnotation.context_runs` 显式传入（未注释的 mask=0 默认 tool_result/tool_or_env_context）。不用 metadata 走私是因为宿主 metadata 归 S1-5 派生视图白名单管（只许两个白名单键）。
- [S1-3] **"tape 请求了没返回"的降级标注落点 = 拒绝产出投影 + 机器可读 reason_code**：TrajectoryProjection schema 刻意不可表示该状态（top_p<1.0 必须带全 tape；MoE 请求了 routing 不得谎报 dense 声明），所以投影层的"降级"没有带病对象可产出，唯一合法出口是 `SlimeProjectionError`（reason_code：`top_p_tape_requested_but_missing` / `routing_tape_requested_but_missing`）。与 capture 层"请求了 tape 没返回禁止 complete"首尾相接，另有兜底面：回链记录非 complete（`capture_record_not_complete`）或回链记录 response 计数之和 < 分支 mask=1 数（`capture_backing_insufficient`）同样拒收。
- [S1-3] **LogprobProvenance 的 precision/sampling_backend 由调用方参数补充**：capture schema（A4 清单）没有这两个字段，事实源是引擎 server_info（S1-0 探针 dtype=bfloat16、sampling_backend=pytorch）；engine 名与版本从 capture 记录取并要求全体一致。`weight_version` 取 Sample.weight_versions 的唯一值；mid-rollout 权重更新（多版本）时置 None，混版本事实归 BackendHandshake.weight_versions_seen。
- [S1-3] **fan-out 账目自证 + 申报交叉检查**：`segment_count` 恒由投影按 len(branches) 自填、`rollout_loss_denominator` 按全分支 mask=1 token 总数自算（slime rollout_mask_sums 语义），调用方不许直接给；slime 侧账目经 `declared_segment_count` 传入，与实际叶链数不一致即拒收（两叶链申报 1 段的反例）。每分支必须 ≥1 个 mask=1 token（对齐 slime `has_trained_response` 过滤）。
- [S1-3] **fixture (b) 取 S1-7a 真实形态**：dense（无 routing，`not_applicable_dense_model`）+ top_p=0.95 带 top-p tape（A2：dense 只是没有 routing）；top_p=1.0 的 `not_applicable_top_p_1` 应急路径以变体测试单独覆盖。fixture (a) 分支 b0 与 uh_probe_result.json 逐值同形（15/16、offsets 17、routing [30,48,8]）。
- [S1-4] **评分容器通道 = 直接 docker CLI（asyncio subprocess），不经 verifiers DockerRuntime**。三条理由：① verifiers DockerRuntime 硬编码 `--network host` 且不支持 label——评分容器要 `--network none`（P9）+ label 记账（P1），子类化后 `start()` 几乎整段重写，无复用价值；② grading 与 envpack 同属框架无关库层（S1-6 slime 绑定同样要用 manager），零 verifiers/swebench import 纪律已用子进程探针钉死（`test_grading_package_imports_no_verifiers_or_swebench`）；③ P1 清扫与 P4 杀容器注入本就在 docker CLI 层操作。docker 调用是构造参数 `DockerRunner`（P7 backend-neutral，FakeDocker 注入即证明）。
- [S1-4] **网络策略单一来源 = SandboxLease**：manager 先构造 `SandboxLease(purpose="grading")`（schema 层锁死 deny_all，S1-1 已定），`docker run` 的 `--network none` 从租约推导——想给评分容器开网必须先改契约。租约存 `manager.leases` 作 evidence。
- [S1-4] **归因决策树补齐 scoring.py 留白（manager 掌握 replay 证据后的改判规则）**：我们的 `git apply` 在 clean checkout 上已成功、eval 日志却出官方坏码（缺标记/RESET_FAILED/TESTS_ERROR/TESTS_TIMEOUT）→ 判 `test_log_parse_failed`（infra 族，reward=None），不再沿 parser 层的 patch_apply_failed 映射（那对我们的流程是事实性错误——patch 明明 apply 成功了）。杀容器/超时/checkout 血缘失败/workspace 导不出 → `infra_failure`。
- [S1-4] **zero-parsed-tests 加严（本机实测证实必要）**：`apply_ok=True` 且 `num_parsed_tests==0`（标记齐全、内容垃圾）时，官方 silent-success 语义会产出"可信度为零"的结论并落成 reward=0 假负样本（用官方 parser 对垃圾日志实测确认）；manager 强制改判 `test_log_parse_failed`（reward=None）。这正是故障注入"日志不可解析"的落点。
- [S1-4] **hygiene 检出后仍评分（剥离段后重放）+ 结论封顶**：测试篡改/禁区污染段**整段剥离**出 cleaned patch，其余照常重放评测（对齐 MAI"评分前 reset 再评"的形态）；若剥离后测试全过，结论强制 `unresolved+tests_failed`（四计数如实，f2p_pass 可以是满的），hygiene verdict 记录真实原因——契约"非 clean 不得 resolved"的第一道执行点在 manager，schema 校验器是第二道。fixture 实测：src 修复 + tests 篡改并存 → f2p_pass=1 但 reward=0。
- [S1-4] **patch 导出口径 = `git add -N . && git diff HEAD --binary`**：intent-to-add 让未跟踪新文件（含污染企图，如 grader/secret.txt）进导出面；`--binary` 保二进制可重放；agent 在 workspace 里本地 commit 会让 diff 基线漂移 → clean base 上 apply 失败 → patch_apply_failed（真容器用例演示了这一真实形态）。解析不了头行的 diff 段 fail-closed 当污染剔除（`<unparseable_diff_segment>`）。
- [S1-4] **本机行为验证形态（U-D）**：自建 arm64 轻量镜像 `rh2-s14-grading-fixture:v1`（python:3.12-slim + git；git 是评分容器真实依赖，官方 SWE 镜像同样自带）+ 手工小 git repo（源文件 + 官方测试文件）。官方 parser 走 psf/requests 配置键（真 `make_test_spec → get_logs_eval → get_eval_tests_report` 链路）解析容器内**真实执行**的测试输出——resolved/tests_failed 由 patch 重放后的代码行为决定，不是罐头日志。四类故障注入（篡改/污染/杀容器/解析失败）全部真容器实测通过，见 `s1/grading_p_matrix.md`。
- [S1-4] **队列反压策略 = block_submitter**（P11 三选一最保守：阻塞提交方即反压 rollout 准入）；每次打满产出 `BackpressureEvent`（reason_code=`grading_backpressure_queue_full`，EligibilityReport.reason_codes 可直接用），排队等待从 submit 起计时（含被阻塞段）进 `GradingTimingRecord.queue_wait_seconds`。F5 用户版默认并发 4/队列 8，均可配置（`GradingQueueConfig`）。
- [S1-5] **S1 cap 实现方式**：`governance/gate.py` 显式常量 `S1_TIER_CAP = "offline_or_sft_candidate"`（带注释：S2 安全加固完成后由验收流程改常量并升 `GATE_VERSION` 解除，不设运行期开关）。封顶按严重度只降不升——七维全过的 merit=online 被压到 offline 并写理由码 `s1_default_ceiling_offline`；merit 本来就是 audit 的不会被"抬"到 offline。常量值与理由码由 `test_s1_tier_cap_constant_pinned` 钉死。
- [S1-5] **组修复信号表示法 = 新建 `GroupRepairSignal`（governance/gate.py），不复用 handshake.GroupSignal**：GroupSignal 是整组账目（delivered/degraded 计数，由后端 adapter 跨 n 条 rollout 聚合），gate 判定的是单条轨迹。信号字段：trajectory/group/parent_rollout id、`degraded`、`failed_dimensions`（七维固定顺序）、reason_codes、report_ref，在 `GateOutcome` 与 `FinalizedRollout` 返回值中一等暴露（任务要求 evaluate -> EligibilityReport，为一等暴露信号改为返回 GateOutcome{report, signal}，报告仍是权威载体）。**degraded 按七维事实判定、不含 S1 封顶**——若封顶也算降级，S1 期间每组全员 degraded，GLM-5 组修复规则会把所有组整组丢弃，S1-7a 的 debug training step 一个样本都拿不到（n=4 组里 1 条 infra 失败的正确账目 = degraded 1 / 可交付 3）。信号未注册 SCHEMA_REGISTRY（进程内传递为主；若 S1-6 决定持久化，与 BackpressureEvent/bundle 两 schema 同批收编，S1-9 定）。
