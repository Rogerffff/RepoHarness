四方工具能力详细对比 · Codex / Claude Code / mini-SWE / RepoHarness

面向 RepoHarness 16G 后续设计的详细对照　·　Codex 数据源:reference/codex/ commit 61cbf357(已核实 exec_command 字段、apply_patch.lark 语法、workspace permission profile)　·　Claude Code 数据源:reference/claude-code-typescript-src/　·　mini-SWE 数据源:评测 worktree 真实配置/日志　·　RepoHarness 数据源:本仓库 Stage 16G.0–16G.2 公开 evidence　·　配套:RepoHarness 能力总表(中心)、Codex 专题、扫盲版三方对比

这页是什么:把同一件软件工程动作(看文件/搜代码/改 patch/跑测试/写复现/装依赖/...)在四个 harness 里分别怎么做、字段叫什么、有什么细节,放在一页对照清楚。让你不必再回去看源码或几份长文档。

结构:① 四个 harness 一段话各自简介 → ② 顶部总览对比表(一眼看全貌,点跳到详细) → ③ 拿一个真实修 bug 任务,从定位到收口走完整闭环,4 个 harness 并排对照 → ④ 16 个工具能力的深度卡片(每个:介绍 + 具体例子 + 4 列 harness 做法 + 给 RH 启示) → ⑤ 关键差异和给 RH 的启示总结。

一句话结论:Codex 和 Claude Code 都把"模型多轮调工具+真命令+受控修改"做成核心闭环,只是风格不同(Codex shell+apply_patch 中心 / Claude Code 结构化分层)。mini-SWE 是"只给 Bash"的能力下限参照。RepoHarness 16G 路线既不是抄一家,也不是回到极窄工具面 —— 而是 Claude Code 的结构化文件导航 + Codex 的 apply_patch + 自研受控公开命令 + 自研训练数据治理。

读法提醒:这页是能力语义对照,不是安全模型照搬。Codex / Claude Code 是产品态,可以用真人 approval、用户授权和本机沙箱兜底；RepoHarness 是训练态,不能让 RL 样本依赖真人审批,必须把同等语义落到确定性 profile、公开/隐藏环境隔离、quarantine、artifact 脱敏和训练资格门禁上。

1 · 四方简介(一句话各自定位)

🟠 Codex (OpenAI)

产品态本地开发代理运行时。多入口(TUI/exec/app-server/SDK)同一 codex-core,Rust 实现。模型可见工具偏 shell+patch 中心:shell_command / exec_command+write_stdin(统一执行)、apply_patch(Lark grammar 验证)、update_plan/goal、MCP、code mode、multi-agent。安全靠 PermissionProfile(workspace 写但保护 .git/.codex/.agents)+ 跨平台 sandbox(Seatbelt/bubblewrap)+ Guardian 自动审查 + Hooks 生命周期 + rollout-trace 分层审计。

🟢 Claude Code (Anthropic)

产品态开发代理,显式结构化分层。TypeScript 实现。模型工具明确拆分:Read(文本/图片/PDF/notebook)、Grep/Glob(独立搜索)、Edit(exact replace)、Write(新建/覆盖)、Bash(完整 shell + 权限)、TodoWrite、AgentTool(子代理)、MCPTool、ToolSearchTool(延迟工具发现)、LSPTool(符号/诊断)。权限 3 档(allow/ask/deny)+ deny 优先 + suggestions 恢复路径 + Hooks(PreToolUse/PostToolUse)。

🟡 mini-SWE-agent

能力下限参照:只给一个 Bash。模型每轮发一条 shell 命令,通过 stdout/stderr/exit code 反馈迭代。看文件 cat、搜 grep、改用 sed/tee、跑测试 python -m pytest ...、装依赖 pip install。安全主要靠外层容器(SWE-Bench Docker /testbed)。没有结构化工具、没有显式权限/审计层、没有 todo / MCP。象征意义:即使只给 Bash,也能形成"定位→复现→改→验证"闭环(动态诊断能力下限)。

🔵 RepoHarness(我们)

训练 harness,不是产品。Python。当前默认 core:read_file/grep/glob_files/symbol_search(轻量 AST)/edit_file/create_file + write_file(带 expected_hash)+ apply_patch(结构化批量,Codex 同款方向);delete/move/mkdir 经 apply_patch 表达、独立工具仅 extended。16G.2B 已开启真实写入行为,16G.2C 已接通 final.patch / TrainingView / export projection 链路,但训练资格(policy_loss)仍关着,等 16G.6 freeze + 17B 真实数据闸门。16G.3 待补:run_public_command/run_project_test/scratch_python。16G.4 收口持久 shell(进 extended) + 依赖 + 权限恢复 + 训练 linkage。安全靠确定性 path policy + 训练资格门禁,不靠真人审批。

读这张表读出什么:
① Codex 的"apply_patch 一次改多文件"是它的特色 —— 一次工具调用解决 4 步可能其他 harness 要 3-4 次。但同时它什么都靠 exec_command,模型每个动作都套一层 shell command。
② Claude Code 工具最分化 —— 每一步用一个专门工具(Read/Edit/Write/Bash),模型 action attribution 最清楚,但工具数最多。
③ mini-SWE 最直接 —— 一个 bash 走天下,简单但安全/审计全靠外层容器。
④ RepoHarness(16G 完成后) = "Claude Code 的结构化文件导航 + Codex 的 apply_patch + 自研受控公开命令 + 自研训练数据治理"。这是故意混合的设计,不是任一家的复刻。

4 · 详细卡片 —— 16 个工具能力逐个展开

① 看文件 (read)
读仓库内的文件内容,带行号便于引用。
例子 想看 config_parser.py 第 30-60 行写了什么
🟠 Codex
普通模型工具面没有 Claude Code 那种专门 Read。靠 exec_command{cmd:"cat -n config_parser.py"} 或 head -n 60 config_parser.py。app-server / 客户端 API 里有文件读写接口,但那不是这页讨论的普通模型可见 SWE 工具。
🟢 Claude Code
Read(FileReadTool):支持 文本 + 图片 + PDF + notebook;行范围、token 预算、大文件分页;有专门的输出协议防"递归 Read"。
🟡 mini-SWE
cat config_parser.py 或 sed -n '30,60p' config_parser.py。一次给全部,大文件可能被 truncation 截断。
🔵 RepoHarness
read_file(path, start_line, end_line):纯文本 + 行范围 + 工作区路径校验 + 隐藏路径过滤(.git/runtime_private/hiddenverifier 拒绝)。无多模态(post-16G optional)。
给 RH 的启示:结构化 read 是 Claude Code/RH 路线的优势(更可审计、更易做截断/脱敏)。Codex 用 shell 读文件靠的是 exec_command 的输出截断 + 沙箱;RH 不必学这点,保留结构化 read_file。多模态读取(图片/PDF)留 post-16G,不阻塞主线。
② 搜索 / 文件发现 (grep / glob)
在仓库内容里搜文字/正则,或按文件名 pattern 找文件。
例子 找所有定义 parse_config 的位置 + 找所有 test_*.py
🟠 Codex
shell:exec_command{cmd:"rg 'def parse_config' -n"};文件发现:find . -name 'test_*.py'。没有专门 Grep/Glob 工具。
🟢 Claude Code
独立工具:Grep(pattern) + Glob(pattern)。结果可在 UI 折叠展示(权限独立,不需 Bash 权限)。
🟡 mini-SWE
grep -rn "def parse_config" .(-r 递归 + -n 行号);文件:find . -name 'test_*.py'。
🔵 RepoHarness
grep(query) + glob_files(pattern) + list_files。和 Claude Code 一对一对齐。
给 RH 的启示:独立 Grep/Glob 是更好的设计 —— Codex 走 shell 是因为它整体 shell 中心。RH 保留独立的搜索工具是对的(更易做输出截断+权限隔离)。
③ 符号导航 / LSP
跳到定义、找引用、类型诊断 —— 比文本搜索更精确的代码理解。
例子 找 parse_config 的所有调用处 / 看类型签名
🟠 Codex
没有原生 LSP 工具。靠 shell + grep 模糊定位。
🟢 Claude Code
LSPTool:LSP server 集成 —— goto definition、find references、hover info、诊断。懒加载。
🟡 mini-SWE
无。靠 grep。
🔵 RepoHarness
symbol_search:轻量 Python AST 搜索(类/函数/方法),不是完整 LSP。post-16G optional。
给 RH 的启示:这一块不是主 RL 阻塞项(post-16G optional)。Claude Code 强 LSP 主要因为它是产品态,需要 IDE-like 体验。RH 训练阶段轻量 AST 够用,深 LSP 留后续。
④ 改一处代码 (exact edit)
把已有文件里的一段文本精确替换成新文本。
例子 把 raise KeyError(...) 改成 return DEFAULT_TIMEOUT
🟠 Codex
没有专门 Edit。用 apply_patch 的 *** Update File: hunk(@@ 上下文 + +/- 行)。一处改也走 apply_patch。
🟢 Claude Code
Edit(file, old, new):exact replace,要求 old 在文件中唯一匹配。简单可靠。
🟡 mini-SWE
sed -i 's/raise KeyError.../return DEFAULT_TIMEOUT/' config_parser.py 或重写整个文件。sed 语法易错。
🔵 RepoHarness
edit_file(path, old, new):和 Claude Code 一对一。Stage 16G.2 完成后,复杂多文件改用 apply_patch 表达。
给 RH 的启示:edit_file 不残缺,和 CC Edit 同级。Codex 没专门 Edit 是它的设计选择,不代表 RH 必须跟进。"单处改用 edit_file,多处/跨文件用 apply_patch"是清晰的能力分工。
⑤ 新建 / 覆盖文件 (write)
建一个新文件,或覆盖一个已有文件。
例子 新建 tests/test_config_parser.py;覆盖 defaults.py 加常量
🟠 Codex
走 apply_patch 的 *** Add File:(新建)或 Update File(覆盖)。没有独立 Write。
🟢 Claude Code
Write(file, content):新建/覆盖统一。
🟡 mini-SWE
cat > new.py <<'EOF' ... EOF 或 echo "..." > new.py(重定向覆盖)。
🔵 RepoHarness
分开两个:create_file(只新建,已存在拒)+ write_file(mode, expected_content_hash)(覆盖必须带 hash,防 stale 覆盖)。这是和 CC/Codex 都不同的安全细节。
给 RH 的启示:"create-only vs overwrite-with-hash" 拆开是 RH 比 CC/Codex 更严的训练态选择 —— RL 数据要干净,模型不能盲目覆盖文件。Codex 通过 apply_patch 的 @@ 上下文做类似保护;CC Edit 要求 old 唯一匹配作隐式保护;RH 把这个变成显式 expected_hash。
⑥ 多文件 patch / 结构化批量 ★
一次表达"跨文件多处改动 + 新增 + 删除 + 移动"的批量操作。
例子 函数改名涉及 3 文件 8 处,要一次原子完成
🟠 Codex
apply_patch(核心特色):Lark grammar 定义的 freeform tool。结构:*** Begin Patch / hunks / *** End Patch,hunks 含 Add File / Delete File / Update File(可含 Move to) + @@ 上下文 / +/- 行。执行前 验证 patch+路径,进 sandbox+approval+file change event,streamed argument diff(UI 看进度)。
🟢 Claude Code
没有专门 apply_patch。多文件靠多次 Edit + Write 组合,模型自己规划顺序。简单但调用次数多。
🟡 mini-SWE
生成一个 patch 文件,git apply file.patch。或多次 sed/cat。
🔵 RepoHarness
apply_patch(operations=[{op, path, old_text/new_text, expected_content_hash/expected_source_hash, reason}]):结构化 typed operations(非行号 unified diff,additionalProperties:false 硬禁自由 diff)。全预检 → 快照 → apply → 失败 rollback + partial_failure → invalid_for_training。delete/move op 强制 model 提供 reason。和 Codex 同方向,RH 加了 hash + reason + 训练资格分层。
给 RH 的启示:apply_patch 是 Codex/RH 同方向选择,Claude Code 不必照搬。但 RH 用 JSON 结构化 operations 比 Codex 的 Lark grammar 文本更易解析、less LLM-prone-to-malformed;hash + reason 字段是 RH 训练态独有(产品态 Codex 不需要)。Codex 给我们的最大启示:apply_patch 必须进事件流和 file change lifecycle(对 RH 即 16G.2C 的 final.patch / TrainingView linkage)。
⑦ 删 / 移 / 建目录
删除文件、改名/移动、建目录(常含批量重构)。
例子 删除过时模块、把 helper 移到新 package、建 tests/ 目录
🟠 Codex
都走 apply_patch:Delete File hunk(删)、Update File + *** Move to:(移动 + 可同时改内容)、隐式靠 Add File 自动建父目录。无独立 mkdir。
🟢 Claude Code
Write + Bash 组合:Bash("rm old.py")、Bash("mv a.py b.py")、Bash("mkdir -p tests/")。
🟡 mini-SWE
rm old.py、mv a.py b.py、mkdir tests。直白。
🔵 RepoHarness
core 默认走 apply_patch 的 ops(delete_file/move_file/mkdir,带 hash + reason)。独立 delete_file/move_file/mkdir 保留 schema、仅 swe_public_extended 暴露;16G.5 parity probe 再决定是否提升为 core 默认。
给 RH 的启示:这正是 16G.2B preflight 修正后的决策。Codex 的"全经 apply_patch"给了正面证据(用一个结构化批量入口覆盖文件组织变更);CC 的"用 Bash" RH 不能学(训练态没真人审批,Bash 是 reward-hacking 风险口);独立工具 vs apply_patch ops 留 16G.5 用真实任务证据来决定。
⑧ 跑命令 / shell ★
让模型执行任意/受控命令获得环境反馈。
例子 跑 import smoke、pytest case、tox -e py311、查工作目录
🟠 Codex
exec_command + write_stdin(核心特色)。当前源码里的 ExecCommandArgs 约 11 个字段:cmd / workdir / shell / login / tty / yield_time_ms / max_output_tokens / sandbox_permissions / additional_permissions / justification / prefix_rule；其中 additional_permissions 只有在 exec permission approvals 启用时进入 schema。支持 PTY、长会话、stdin 续写。命令受 sandbox + execpolicy + approval 三重控制。
🟢 Claude Code
Bash:完整 shell + 权限系统 + sandbox + 后台任务管理。危险命令需 ask。
🟡 mini-SWE
就一个 Bash,爱跑啥跑啥。动态诊断下限。安全靠外层容器。
🔵 RepoHarness
当前:execute_bash 窄 allowlist(rg/grep/安全 git/pytest/受限 python)+ 默认不开;bash legacy 极窄。16G.3 待补 run_public_command:受控公开命令工具,schema 借鉴 Codex 的字段精神(cwd/timeout/输出截断/sandbox/justification/拒绝结构化恢复),但不照搬真人 approval 和自由扩权。故意不给裸 Bash(防 reward-hacking)。
给 RH 的启示:Codex 的 exec_command schema 是 run_public_command 的重要设计模板,但不是可直接复制的训练工具。字段层面应吸收 cwd/timeout/output budget/sandbox profile/justification；权限层面要改成 deterministic profile 和拒绝恢复,不能把 additional_permissions / require_escalated 这类真人审批语义直接暴露给 RL。不需要给 PTY/write_stdin(那是持久 shell,留 16G.4 extended)。同时 16G.3 必须保证命令在当前候选 patch 的公开投影或一次性临时副本里执行,不能让模型读到 runtime-private/run_dir/gold/test_patch；Docker network policy 对未知值应 fail closed；模型可读 artifact 必须是 sanitized,raw artifact 只能审计可见。
⑨ 跑定向测试
不是全跑,而是只跑那一个失败的测试 case。
例子 只跑 tests/test_config_parser.py::test_missing_timeout
🟠 Codex
exec_command{cmd:"python -m pytest tests/test_config_parser.py::test_missing_timeout -q"}。没有专门"项目测试工具",靠 exec_command 跑。
🟢 Claude Code
Bash("python -m pytest tests/test_config_parser.py::test_missing_timeout")。
🟡 mini-SWE
python -m pytest tests/test_config_parser.py::test_missing_timeout -x(-x 首失败停)。
🔵 RepoHarness
当前:run_tests() 无参数,只跑配好的固定反馈 —— 不能定向(P0 阻塞)。16G.3 待补 run_project_test(test_profile_id, selector, args):支持 pytest case / Django label / tox env / nox session / 项目自定义 smoke,但必须绑定到 task-declared 或 manifest-derived public test profile,不能接受任意 name 字符串。
给 RH 的启示:这是核心缺口。Codex/CC/mini-SWE 都能"只跑一个" —— RH 不能,会让模型学不会针对性验证。run_project_test 是 16G.3 P0,且应和 run_public_command 共享 substrate(同一套 cwd/timeout/输出截断/拒绝语义)。selector 设计要支持多种测试框架(pytest/unittest/Django/tox/nox)。还必须有 public test 防篡改边界:如果模型改了公开测试文件、测试配置或路由,应拒绝或从 clean public test snapshot 执行,并用 public_test_source_clean=false / result_valid_for_training=false 阻止“改测试后通过”进入训练。

🟡 mini-SWE

🔵 RepoHarness
当前:无正式工具。execute_bash 允许极受限 inline python;diagnostic_shell 能做但仅诊断侧通道、不进训练。16G.3 待补 scratch_python(code):在临时空间执行,产物默认不进 final.patch(patch hygiene 过滤),可读公开源码但禁 hidden,输出脱敏,且必须看到模型当前候选 patch。
给 RH 的启示:scratch 是 16G.3 P0,且 RH 设计可以比 Codex/CC 更干净 —— 通过"专用 scratch 空间 + 默认排除 final patch + hidden 隔离"避免 Codex/CC 那种"scratch 文件可能误进 patch"的问题。这是训练态的优势。第一版若只支持 Python,文档和 schema 都应明确为 Python 专用复现工具,不能宣称已经覆盖所有语言的 scratch 能力。

🟡 mini-SWE

给 RH 的启示:持久 shell 是真实需要(起服务、跨调用装依赖再用),但RL 训练对可复现性敏感(持久状态难复现/审计)。Codex 的方案是"真持久 + 强 sandbox + 事件审计";RH 的方案是"core 用'每次重放环境上下文'(无状态结构化命令 + harness 自动 cd/venv) + extended 给真持久 shell"。两条路都行,RH 选 core 无状态 + extended 持久是为了训练干净度。

② RepoHarness 的设计哲学(在四方对照下变得清晰)

RH 不是 Codex/CC 的复刻,而是一个有意混合 + 训练态特有的设计:
① 从 Claude Code 拿:结构化文件导航(Read/Grep/Glob/Edit/Write/symbol_search 的清晰分工)→ 让 RL 训练 action attribution 更可解释。
② 从 Codex 拿:apply_patch 作为结构化批量入口(grammar 验证 + file change event 思路)→ 用一个工具覆盖 delete/move/mkdir,减工具数量;exec_command 的字段精神 → 喂 run_public_command 设计。
③ 不学的:Codex 的"什么都靠 shell"(RH 保留专用读/搜/编辑)、CC 的"用 Bash 做文件组织"(RH 故意不给裸 bash,防 reward-hacking)、mini-SWE 的"只给 Bash"(下限参照,不是目标)。
④ 训练态独有(三家都没有):hidden verifier 隔离、gold patch 防泄漏、expected_hash 防 stale 覆盖、apply_patch ops 的 model-provided reason(reward attribution)、policy_loss 训练资格门禁、"全预检+rollback+partial_failure→invalid_for_training"的数据干净度防线、每题私有 overlay(跨题隔离)。

③ 给 16G 后续的具体启示

  • 16G.3 run_public_command schema:借鉴 Codex exec_command 的字段精神(尤其 justification 模型提供"为什么跑"),但把真人 approval / 动态扩权改写为 deterministic profile、结构化拒绝和 quarantine。三个新工具(public_command / project_test / scratch_python)共享 substrate。
  • 16G.3 run_project_test:必须支持 selector(pytest case / Django label / tox env / nox session / 项目 smoke);看 Codex/CC/mini-SWE 都能定向、唯独 RH 当前 run_tests 无参,这是 P0 缺口。入口要绑定 PublicTestProfile,避免 name+args 变成任意命令通道,并且要阻断 public test tampering。
  • 16G.3 scratch_python:RH 设计可以比 Codex/CC 更干净 —— 专用 scratch 空间 + 默认排除 final patch + hidden 隔离 + 使用当前候选 patch。
  • 16G.4 持久 shell:走 extended profile + 四条边界(session_reset / artifact_hygiene / path_redaction / public_safe_projection)。core 保持无状态结构化命令 + harness 自动重放环境上下文(cd/venv),不必给真持久 shell。
  • 16G.4 依赖:Codex workspace_write 模板 + RH 每题私有 overlay + 共享依赖只读 + 受控 setup profile。
  • 16G.4 权限恢复:已有结构化字段,关键是 16G.5 probe 模型是否真学会换工具,可作 auxiliary reward。
  • 16G.2C TrainingView 分层:学 Codex rollout-trace 的"先观察后解释"——模型可见 / runtime 证据 / verifier-only / reward-only 严格分层,不混进一个 transcript。
  • post-16G schema 预留:subagent_thread_id / sidechain_transcript_ref / tool_source / tool_namespace / authorization_outcome 等字段,Codex 的 v1/v2 演进表明早预留比晚改 schema 便宜。
一句话总结:这页讲清的不是"哪家工具更好",而是"同一件事各家怎么做、字段叫什么、为什么不同"。结合 Codex 的成熟现实证据(产品态多年迭代)、CC 的结构化分层模型(action 可解释)、mini-SWE 的能力下限参照(动态诊断闭环最低标准),RH 16G 的设计在四方对照下站得住 —— 既不抄一家,也不退回 toy,目标是结构化清晰 + 真实能力 + 训练态独有的安全/审计/数据治理。
