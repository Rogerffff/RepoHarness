Sequential Implementation Plan

RepoHarness 接入 verl 的顺序实施计划

这一页对应 repo_harness_verl_workstreams/01-sequential-implementation-plan.md。它把原先容易跑偏的并行开发方式收敛为一条顺序路线：先完成 Stage 0 的共享 contract 冻结，再通过 Stage 0H 的 contract hardening v1 固定 token、mask、log probability、visibility、cancellation、timeout、cleanup 和 throughput 硬门槛，然后改造 RepoHarness runtime 与 training_fast，最后接入 verl adapter，并为 fully async 预留扩展点。

单一路线，分阶段执行 Stage 0H 独立执行关口 覆盖 Harness 训练提速改造 计划页面，不承载执行日志

总体路线

当前不再拆成两个互不沟通的并行工作方向。正式开发顺序是：先让 RepoHarness 自身具备稳定的 episode runtime、训练快速模式、审计引用、计时资源统计和并发安全，再让 verl adapter 调用这个已经稳定的 runtime。

Stage 0-0H

Contract Freeze / Hardening

冻结共享 contract、canonical fixture 和 route / visibility 规则，再用 Stage 0H 把训练张量形状、response span、audit opaque refs、DataProto 可见性、取消清理和吞吐阈值变成硬门槛。

Stage 1-5

Schema / Runtime / Gateway

新增训练后端无关 schema 包和最小 LLMGateway.generate_turn(...)，抽出 run_episode(...)，实现 run mode、recorder、timing/resource summary，并迁移真实模型调用到 gateway。

Stage 6-9

Training Fast

解决 workspace、container、verifier、预算、no-progress、上下文瘦身、资源租约和并发安全问题。

Stage 10-12

verl 接入

实现 TrainingView -> AgentLoopOutput、RepoHarnessVerlAgentLoop、VerlLLMGateway 和端到端 smoke。

Stage 13

Fully Async 预留

为中断、恢复、policy version、staleness、异步 reward backfill 和资源 lease 生命周期预留字段。

关键原则：verl adapter 不能成为第二套 Harness。它只做翻译和桥接；软件工程任务、workspace、工具、verifier、reward、recorder 和 audit 都应该由 RepoHarness runtime 统一负责。

Stage 0H contract gate 说明

Stage 0H 是 Stage 0 和 Stage 1 之间新增的实施关口。它不是在写完整 runtime，也不是在提前接入 verl；它的任务是先把“什么样的训练轨迹才算合法”固定成可测试、可审计、可拒绝的 contract。换句话说，Stage 0 冻结对象名字和字段范围，Stage 0H 冻结这些字段的训练语义和安全边界，Stage 1 之后的 schema、runtime、adapter 都必须按这个关口验收。

本节只说明 Stage 0H 的设计目的和验收边界。实际已完成的 fixture、测试和报告，请查看独立的 执行结果汇报页面。

为什么必须单独做 Stage 0H

RepoHarness 接入 verl 的失败风险不主要在“能不能调用一个 Python 函数”，而在“这个函数返回的训练样本能不能真的进入 PPO / GRPO batch”。如果 response_ids、response_mask、response_logprobs 形状不一致，或者 provider route 样本被伪装成 online rollout 样本，训练会在很晚才暴露问题。

另一个风险是泄漏。hidden verifier、gold patch、accepted label、完整 reward metadata、绝对 run_dir 或 evaluator-only logs 一旦进入 raw_prompt、AgentLoopOutput.extra_fields、TransferQueue 或 DataProto.non_tensor_batch，模型就可能看到不该看到的信息，后续 reward 和训练统计都会失真。

这一步实际交付什么

Stage 0H 交付的不是完整功能，而是一组硬门槛：canonical fixture、字段变化规则、visibility denylist、token provenance 规则、route 枚举、允许进入 verl batch 的 opaque refs、取消超时清理 contract，以及 training_fast 是否真的降低固定成本的量化检查。

完成以后，后续 agent 实现 Stage 1 到 Stage 13 时就不能靠口头理解自由发挥。字段新增、route 新增、artifact 引用、log probability 缺失、空 response、overflow、泄漏字段和清理失败都必须被测试明确接受或拒绝。

当前慢点和必须改造的部分

如果直接把当前 full-audit evaluation 模式用于在线强化学习 rollout，训练吞吐会被模型调用等待、容器和 workspace 固定成本、verifier、artifact 写入、大上下文和无进展探索拖慢。因此 Harness 侧必须在接 verl 之前完成 training_fast 相关改造。

慢点 风险 计划中的改造
模型调用等待 如果推理后端吞吐不足、排队严重或者单次生成过长，单条轨迹仍会成为 rollout 吞吐瓶颈。第一版在线训练主线优先走 verl 管理的本地推理服务，不默认走外部 API。 LLMGateway、verl LLMServerClient、vLLM / SGLang batching、sticky session / prefix cache、generation timeout、max output tokens 和推理服务并发控制。
容器和 workspace 固定成本 即使 image 已构建，每条任务仍要创建容器、materialize workspace 和 setup。 workspace snapshot、dependency cache、copy-on-write episode workspace、可选 warm container pool。
baseline / final verifier 每条任务完整 verifier 会占用大量非模型时间。 baseline cache、verifier worker pool、queue wait 统计；第一版仍同步等待 final reward。
full audit artifact 完整 raw model request、raw model response、可选推理痕迹和超大 prepared messages 会拖慢写入。 run_mode=training_fast、轻量 recorder、hash/ref/压缩/抽样策略。
上下文准备和大文件读取 大文件进入上下文会放大后续 token 成本。 range read、短 grep context、ranked snippets、context budget、file size policy。
无进展探索 重复搜索、连续只读、没有 patch progress 会浪费 rollout 资源。 no-progress stop、max turns、重复工具调用限制、patch progress heuristic。
串行 rollout 单条轨迹慢时，在线强化学习必须靠并发摊薄延迟。 run directory 隔离、workspace lease、artifact lock、推理 route 并发限制，后续演进 fully async。
指标缺失 没有结构化 timing/resource summary 时无法判断瓶颈。 每条 episode 输出 TimingSummary 和 ResourceSummary。

Contract hardening v1：进入实现前的硬门槛

这部分来自审查报告要求补强的问题。它的作用是先把训练语义固定住，再开始写代码。也就是说，后续 agent 不能只证明接口能跑，还必须证明 token、mask、log probability、reward、可见性、取消清理和训练吞吐都满足第一版 contract。

训练张量形状

prompt_ids 不能超过 rollout.prompt_length；有效样本的 response_ids 不能为空，也不能超过 rollout.response_length。

response_ids、response_mask、response_logprobs 必须等长。正式 PPO / GRPO batch 中所有样本都必须有 log probability，工具 observation 对应 log probability 填 0.0。

Span 级 token provenance

新增 response_spans，解释每一段 response token 来自 assistant generation、tool observation、environment observation，还是被排除或截断。

每段要能关联 GenerationRecord、tool call、artifact ref、mask 值、logprob policy、policy version、global_steps、min_global_steps 和 max_global_steps。

审计引用不可泄漏

完整 AuditRef 保存在 RepoHarnessEpisodeResult 和本地审计 artifact 中；进入 verl batch 的只能是 repo_harness_* 命名空间下的扁平 opaque refs。

不能把绝对 run_dir、reward metadata 路径、final verifier 路径、gold patch 路径放进 AgentLoopOutput.extra_fields。

可见性覆盖普通和异步路径

RepoHarnessVerlAgentLoop 从 kwargs 构造 request 时必须使用 allowlist。普通 AgentLoopWorker postprocess 和 main_ppo_sync.py / TransferQueue 路径都要做 visibility test。

最终 DataProto.tensor_batch、non_tensor_batch 和 meta_info 不能携带 hidden verifier、gold patch、accepted label 或 evaluator-only logs。

取消、超时和清理

run_episode(...) 从 Stage 2 起就要定义 cancellation / timeout / cleanup contract。外层 coroutine 取消、provider timeout、verifier timeout、Docker command timeout 和 workspace cleanup 失败都要有明确归属。

清理失败不能覆盖原始 episode 状态，但必须写入 diagnostics 和 ResourceSummary.cleanup_status。

training_fast 量化门槛

training_fast 相比 full_audit 的 artifact bytes 至少下降 50%，或者逐类说明为什么无法达到。

fake gateway 下 8 条最小 episode 的非模型 p95 wall time 默认低于 180 秒；每条 TimingSummary 至少解释 95% 的 outer wall time。

这部分已经同步到 shared_contracts/06-contract-hardening-v1.md。后续如果实现阶段想调整这些规则，应先改 shared contracts，再改顺序计划和 HTML。

Stage 0、Stage 0H 到 Stage 13

每个阶段都包含目标、主要工作、出口标准和需要注意的边界。后续交给 agent 实施时，应从前往后推进，不能跳过前置 contract、Stage 0H hardening、schema、runtime 和训练提速基础。

0

冻结 shared contracts 和 canonical fixture

确认 RepoHarnessEpisodeRequest、RepoHarnessEpisodeResult、LLMGatewayRequest、LLMGatewayResponse、TrainingView、GenerationRecord、ResponseSpan、AuditRef、TimingSummary 和 ResourceSummary 的字段边界。

增加 canonical JSON fixture 和 sha256 manifest，所有后续阶段都必须运行同一套 serialization test。fixture 需要覆盖单轮成功、多轮工具调用、response overflow invalid、empty response invalid、mixed logprob batch rejection 和 audit path access denial。

固定唯一 route 枚举：verl、openai、deepseek、local_vllm、local_sglang、replay、mock。route=verl 的真实推理后端用 inference_backend=sglang|vllm 表示。

出口：文档、fixture、版本矩阵和字段变化流程稳定；字段改动必须先更新 shared contracts；进入 Stage 1 之前还必须通过 Stage 0H 的 hardening gate。

0H

contract hardening v1 执行关口

把审查中发现的训练语义风险转成硬性 contract：token shape、mask、log probability、response_spans、route 枚举、provider invalid_for_online_rl、audit opaque refs、raw_prompt visibility、TransferQueue / DataProto 可见性、cancellation / timeout / cleanup 和 training_fast 量化门槛。

这一阶段先落 fixture、最小测试和 blocked-by-stage 报告。对于必须等 Stage 1 schema、Stage 2 runtime、Stage 10 converter 或 Stage 12 verl postprocess 才能真正执行的测试，允许先显式标记为红灯，但必须写清解除阶段和解除条件。

出口：contract hardening v1 fixture、文档一致性检查、sha256 manifest、visibility baseline 和 blocked-by-stage report 已落地；能立即验证的检查全部通过；不再存在旧式嵌套 audit ref、绝对 run_dir 或 provider route 伪装 online RL rollout sample 的说法。

1

新增训练后端无关 schema 包和最小 LLMGateway

新增 src/repo_harness/rl/，包含 episode.py、gateway.py、training_view.py、timing.py 和 visibility.py。

短执行计划见 repo_harness_verl_workstreams/04-stage-1-execution-plan.md。第一项实现工作必须复用 Stage 0H canonical fixture，接入正式 schema roundtrip 和非法字段拒绝测试。

定义最小 async LLMGateway.generate_turn(request) protocol 和 fake/mock gateway，供后续 runtime 测试使用。schema 包不能 import verl，并默认沿用 StrictBaseModel 禁止未知字段。

出口：schema 可构造、序列化、反序列化；fixture sha256 稳定；fake gateway 可支持最小 runtime 单元测试。

2

抽出 RepoHarnessRuntime.run_episode(...)

从当前 CLI / evaluation runner 的 run task 主链路中抽出可组合 runtime facade。CLI 继续存在，但改为构造 RepoHarnessEpisodeRequest 后调用同一个 run_episode(...)。

parse task/config
  -> build RepoHarnessEpisodeRequest
  -> materialize workspace
  -> prepare context
  -> run agent loop
  -> run final verifier
  -> compute reward
  -> record artifacts
  -> build RepoHarnessEpisodeResult

Stage 2 就要前置 cancellation / timeout / cleanup contract：run_episode(...) 内部必须有 try/finally 或等价资源保护，确保释放 workspace lease、container lease、artifact writer 和 verifier worker future。

出口：CLI run task 仍能跑；runtime 可以用 fake gateway 跑最小 episode；succeeded、failed、no_progress、timeout、infrastructure_error、invalid_task、cancelled 状态不会混淆；agent loop 中途取消的 smoke test 能看到确定的 cleanup diagnostics。

3

实现 run_mode 与 training_fast recorder

支持 full_audit、training_fast 和 training_debug。其中 training_fast 面向在线训练，减少大体积 artifact 写入，但保留 hash、引用、patch、reward、verifier summary、timing summary 和 audit reference。

RunRecorder 需要支持 recorder profile，artifact manifest 要标记 artifact 是完整、压缩、抽样、截断还是仅 hash。visibility test 必须覆盖 raw_prompt、extra_fields、transcript projection 和 export projection。

出口：同一条任务能用 full_audit 和 training_fast 跑；training_fast artifact bytes 至少下降 50%，或者逐类解释原因；fake gateway 下 8 条最小 episode 的非模型 p95 wall time 低于配置阈值；结构化 AuditRef 和进入 batch 的 opaque refs 仍能反查关键证据。

4

实现 TimingSummary 和 ResourceSummary

每条 episode 都要解释时间花在哪里、资源如何使用。Timing 至少拆分 rollout wall time、workspace materialization、Docker setup、dependency restore、baseline verifier、context prepare、model call、tool、final verifier、reward compute、artifact write、cleanup 和 queue wait。

Resource 至少记录 workspace backend、docker image digest、container lease、snapshot key、snapshot cache hit、dependency cache hit、baseline cache hit、container reuse hit、network policy、permission policy、inference route 和 verifier worker pool。

出口：成功、失败、timeout 和 infrastructure error 都有 timing/resource summary；可以用 summary 定位训练吞吐瓶颈。

5

完善 LLMGateway route 实现和模型后端迁移

把 RepoHarness agent loop 中的真实模型调用逐步收敛到 LLMGateway.generate_turn(...)。在线强化学习主线优先支持 route=verl，也就是通过 VerlLLMGateway 调用 verl 已管理的 LLMServerClient、vLLM 或 SGLang；OpenAI、DeepSeek 等外部 provider route 保留为评测、调试或离线兼容路线。

第一版保留现有 provider client 入口作为兼容层，并新增 ProviderLLMGateway 包装现有外部 API 调用。这样不会破坏当前外部测评和 V5 debug，后续再逐步把公开主路径迁移到 LLMGateway。

每次模型调用产生 GenerationRecord，记录 turn、model_call_id、prompt ids、output token ids、log probabilities、stop reason、route、inference_backend、policy version、global_steps、min_global_steps、max_global_steps、request hash 和 response ref。正式训练 token 不能从最终 transcript 重新分词伪造。

第一版固定 RepoHarness tool call parser 为权威 tool semantics。parser 后的 assistant message 和 tool calls 只能作为结构化解释，不能反过来构造训练 token；provider route 默认 invalid_for_online_rl=true。

出口：现有模型调用路径通过 gateway 仍能跑；fake/mock gateway 可稳定生成测试轨迹；route=verl 的具体实现留到 Stage 11；provider route 样本不会被伪装成 rollout policy sample。

6

workspace/container 复用和训练环境加速

解决已经有 Docker image 但每条任务仍要创建容器、workspace、setup、baseline 和 verifier 的固定成本。第一版采用可审计的 snapshot / lease 系统，而不是不可控的全局共享环境；优先做 workspace snapshot 和 dependency cache，warm container pool 放到后续优化阶段。

建议 snapshot key 绑定 repo_ref、base_commit、environment_id、docker_image_digest、setup_command_hash、dependency_lock_hash 和 toolchain_version。episode workspace 必须从 clean snapshot 派生，不能污染下一条样本。

Mac 本地第一版使用目录复制作为正确性基线，可选 APFS clone；Linux / Vast.ai 通过 preflight 选择 cp --reflink=auto、overlayfs、Docker volume snapshot 或安全回退。

出口：第一条任务可创建 snapshot；后续同 key 任务可复用；并发 episode 不共享可写 workspace；ResourceSummary 记录 cache hit、lease id 和 cleanup 结果。

7

verifier worker pool 和 reward 边界

第一版仍然在 episode 返回前拿到 final reward，但 verifier 执行层可以池化、限流和记录排队时间。

submit final verifier
  -> verifier worker pool 执行
  -> await result
  -> compute reward
  -> build RepoHarnessEpisodeResult
  -> return TrainingView / AgentLoopOutput

第一版不做 async reward backfill，也不返回没有 reward 且看起来像普通成功的 online RL 样本。基础设施错误、timeout 和 invalid task 必须和模型任务失败分开。

出口：reward 可同步返回；verifier queue wait 和执行耗时进入 TimingSummary；基础设施错误不会误训模型。

8

训练预算、no-progress 控制和上下文瘦身

增加训练模式预算：max_turns、generation timeout、retry budget、max output tokens、max prompt tokens、max total tokens、max model calls、max tool observation tokens、max verifier seconds 和 max workspace materialization seconds。reasoning_effort / thinking_mode 这类字段只在外部 provider route 支持时作为兼容配置，不是 route=verl 主线的必需项。

工具系统要支持 range read、结构化片段读取、短 grep context 和 ranked snippets。context builder 避免整文件泛读，把大文件以 hash、snippet ref 或分段摘要进入上下文。

出口：训练模式不会默认跑 60 轮无进展探索；大文件不会默认完整进入后续上下文；no-progress 默认标记 invalid_for_training=True，只有显式 reward policy 才能把部分 no-progress 当作 negative sample。

9

并发安全和资源租约

为多条 episode 并发运行打基础。run id、episode id、workspace id、artifact manifest path 必须唯一；recorder 写入需要 lock 或单 writer；workspace lease 支持 acquire、release、cleanup 和 diagnostics。

推理 route 需要 concurrency limit、rate limit 和 retry budget。取消和 timeout 要清理 workspace、container lease 和 artifact writer。

出口：两条极小 episode 并发运行通过；cleanup 失败有 diagnostics；ResourceSummary 能反查资源租约。

10

TrainingView 到 AgentLoopOutput 的转换

在真正接 verl 前，先把 RepoHarness 的训练视图转换成 verl agent loop 可消费的输出形态。

TrainingView.prompt_ids -> AgentLoopOutput.prompt_ids
TrainingView.response_ids -> AgentLoopOutput.response_ids
TrainingView.response_mask -> AgentLoopOutput.response_mask
TrainingView.response_logprobs -> AgentLoopOutput.response_logprobs
TrainingView.reward_score -> AgentLoopOutput.reward_score
TrainingView.verl_metrics -> AgentLoopOutput.metrics
TrainingView.extra_fields + AuditRef opaque refs -> AgentLoopOutput.extra_fields

必须检查 token、mask、log probability 长度对齐。assistant generated token 的 mask 为 1，tool observation 和 padding 为 0，并且对应 response_logprobs=0.0。正式 PPO / GRPO smoke 不允许 response_logprobs=None，也不允许同一 batch 中部分样本缺失 log probability。

AuditRef 不能作为嵌套对象进入 extra_fields。进入 AgentLoopOutput.extra_fields 的只允许 repo_harness_* namespaced flat scalar 和 opaque refs；不要提前写 raw_prompt，它由 verl postprocess 从 kwargs["raw_prompt"] 写入。

出口：不启动 verl server，也能使用本地 reference/verl 的 AgentLoopOutput 和 postprocess 行为测试转换；overflow fixture、empty response fixture、mixed logprob batch rejection fixture 和 nested object exclusion 都通过。

11

RepoHarnessVerlAgentLoop 与 VerlLLMGateway

在 Harness runtime 和训练视图稳定之后，再接入 verl。adapter 包第一版放在独立 src/repo_harness_verl/，并通过可选 extra 安装；RepoHarness core 不能因为普通 CLI 使用或外部 API 测评而强制安装 verl 全量依赖。

async def run(self, sampling_params: dict, **kwargs) -> AgentLoopOutput:
    request = RepoHarnessEpisodeRequest.from_verl_kwargs(kwargs)
    gateway = VerlLLMGateway(
        server_manager=self.server_manager,
        tokenizer=self.tokenizer,
        processor=self.processor,
        sampling_params=sampling_params,
    )
    result = await runtime.run_episode(request, llm_gateway=gateway)
    return to_agent_loop_output(result.training_view, result.audit_ref)

kwargs["raw_prompt"] 只能包含模型可见 prompt。RepoHarnessVerlAgentLoop 必须对 kwargs 使用 allowlist，只允许 raw_prompt、agent_name、task_id、run_config_ref、budget_ref、agent_policy_ref、episode_seed 和明确声明的模型可见 context refs。

route=verl 时，token provenance 必须来自当轮真实 LLMServerClient.generate(...) 返回。sticky session 使用外层 request_id=episode_id，不要混淆 server 内部每轮生成 request id。

出口：Mac 本地 fake LLMServerClient smoke 和小型 verl agent loop smoke 通过；本地不要求启动真实 vLLM / SGLang server；AgentLoopOutput.extra_fields 中的 repo_harness_* opaque refs 可由离线审计工具反查 RepoHarness run directory；adapter import 不强迫普通 CLI 安装完整 verl。

12

端到端 smoke、性能 smoke 和 visibility 验收

验证整条链路可以训练消费，而不是局部测试通过。

verl dataloader sample
  -> RepoHarnessVerlAgentLoop.run(...)
  -> RepoHarnessRuntime.run_episode(...)
  -> VerlLLMGateway
  -> tool/workspace
  -> final verifier
  -> reward_score
  -> TrainingView
  -> AgentLoopOutput
  -> verl postprocess
  -> DataProto

必须检查 prompt ids、response ids、response mask、reward score、opaque audit refs、postprocess 后的 raw_prompt visibility、TimingSummary、ResourceSummary 和 training_fast artifact 体积下降。

验收要覆盖普通 AgentLoopWorker._agent_loop_postprocess(...) 路径和 main_ppo_sync.py / TransferQueue 路径，并检查 DataProto.tensor_batch、non_tensor_batch 和 meta_info 的 visibility 与 batch dimension。

Stage 12-A：Mac 本地结构验收

Mac 本地使用 verl-lite 验收，不要求安装 vLLM、SGLang、flash-attn、liger-kernel 或 CUDA 相关依赖。它只证明 RepoHarness 和 verl adapter 的接口、字段、训练视图转换和 visibility 规则正确。 

RepoHarnessRuntime.run_episode(...)
  -> fake/mock LLMGateway
  -> TrainingView
  -> AgentLoopOutput
  -> response_ids / response_mask / response_logprobs 长度检查
  -> extra_fields / AuditRef opaque refs / raw_prompt visibility 检查
  -> DataProto shape debug smoke

本地还要跑 RepoHarnessVerlAgentLoop.run(...) + fake LLMServerClient.generate(...) + fake TokenOutput。fake logprobs 只用于 debug smoke 的长度和 mask 对齐检查，不能代表正式 PPO / GRPO 训练。

Stage 12-B：Vast.ai GPU 训练前验收

Vast.ai 或其他 Linux GPU 实例负责真实训练前验收。这里必须启动真实 verl server manager、vLLM / SGLang AsyncLLMServer，并通过真实 LLMServerClient.generate(...) 得到 token ids 和 logprobs。 

verl server manager
  -> vLLM / SGLang AsyncLLMServer
  -> real LLMServerClient.generate(...)
  -> real TokenOutput.token_ids / log_probs
  -> RepoHarnessVerlAgentLoop.run(...)
  -> TrainingView
  -> AgentLoopOutput
  -> DataProto
  -> PPO / GRPO batch smoke

真实验收必须检查 tokenizer / chat template 一致性、真实 response_logprobs 非空且长度对齐、rollout_log_probs 形状为 [batch_size, rollout.response_length]、rm_scores 存在或 invalid 样本已过滤、sticky session / prefix cache、Ray GPU resource scheduling、Linux workspace snapshot backend preflight、training_fast artifact 体积和 opaque audit refs 回查能力。

出口：Mac 本地验收通过只能表示“接口正确”；Vast.ai 真实验收通过后，才表示这条链路达到训练前可用状态。

13

为 fully async 演进预留

第一版先跑通同步 reward 的 agent loop，后续再演进 fully async。需要预留 episode interrupt / resume、partial output 或等价 checkpoint、policy version、global_steps、min_global_steps、max_global_steps、staleness、async verifier reward backfill、cancelled / resumed / stale trajectory 过滤策略和 workspace lease 生命周期。

fully async 前置检查要记录 actor_rollout_ref.actor.use_rollout_log_probs=True 或当前 verl 版本等价配置、algorithm.rollout_correction.bypass_mode 的选择、stale trajectory 的过滤或权重策略，以及跨多个参数版本时的 token span / model call span 版本范围。

出口：GenerationRecord 保留 policy version、global_steps、min_global_steps 和 max_global_steps；LLMGatewayResponse.extra_fields 保留 verl TokenOutput.extra_fields 中的版本信息；RepoHarnessEpisodeResult.status 能表达 cancelled 和 timeout；AuditRef 能指向恢复所需状态 artifact。

这些选择已经按当前讨论固定为第一版默认方案。后续 agent 应按这里执行；如果要改变，需要先更新 Markdown 计划和 shared contracts。

training_fast 默认不保存完整 raw model response，只保存 hash、大小、截断 preview 和 artifact reference。
training_fast 禁止保存明文 reasoning / thinking trace；training_debug 可以显式开启外部 provider 调试材料。
环境复用第一版优先做 workspace snapshot 和 dependency cache，warm container pool 后置。

最小成功定义

第一版成功不是训练出模型，而是把软件工程任务转成可训练、可审计、可回查的 verl batch。 

一条软件工程任务
  -> RepoHarnessRuntime.run_episode(...)
  -> training_fast artifact
  -> reward_score
  -> TrainingView
  -> AgentLoopOutput
  -> verl postprocess
  -> DataProto
  -> 有效样本可进入 PPO/GRPO trainer 的 batch
  -> invalid 样本被过滤或明确置零 loss weight
  -> 可以通过 opaque audit refs 回查完整轨迹证据
如果这个闭环跑通，并且 timing/resource summary 能说明主要瓶颈，才进入更大规模 rollout 和 fully async 设计。
