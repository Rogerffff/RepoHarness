1 · 这一轮就是和 Claude Code 的对照吗？

是的。16G.0 这个阶段的标题本身就是「Claude Code 类工具面与完整 scaffold 能力差距盘点」—— 它的全部目的就是拿 RepoHarness 的工具面去对照 Claude Code 这类真实 SWE agent，看差在哪、会不会把模型训歪。evidence 里专门有一份 stage16g0_claude_code_tool_inventory.json，盘了 19 项 Claude Code 能力。

但要诚实说一句：这一轮的「Claude Code 那一侧」是有意做轻的。它的每一条证据都只指向 reference/.../AGENTS.md 这一个导航文件，描述偏高层；而且 16 条差距矩阵里的 claude_code_baseline 字段是同一句模板话（「目标是 Claude Code 类真实 SWE agent 工具面；具体实现不能直接照搬」），不是逐能力的 Claude Code 基线。换句话说：当前 evidence 做的是「RepoHarness 自己有什么、缺什么」，逐项 Claude Code vs RepoHarness 的并排对照还没真正做。

这恰恰是你直觉对的地方 —— 需要一个并排对照来说明。好消息是：深度对照本来就是后面 16G.5（Claude Code parity probes + mini-SWE-agent 对照诊断）要干的事。在它之前，我用我之前对 Claude Code TypeScript 源码的分析，先给你一版第一手对照表（下一节），既回答你的问题，也顺便暴露当前 evidence 这块的薄弱处。

3 · 16 个差距详解（按类别展开）

P0 最高优先 · P1 高 · P2 中 · P3 低不阻塞　|　状态枚举：partial 有一半 · missing 没有 · present_default 默认就有 · present_diagnostic_only 只在诊断侧 · present_non_default 非默认才有 · unknown 待查清

▸ 命令 / shell / 测试反馈（7 条，含全部 4 个 P0 —— 这是核心痛点）
parameterized_public_test_commandP0partial→16G.3
问题：run_tests 无参数，模型表达不了「只跑这一个失败的 pytest case / Django label」。训练风险：难做信用分配，模型可能转向静态猜测而非定向验证。
证据：run_tests 无参数；execute_bash 变体能跑安全 pytest，但不是所有 scaffold 默认暴露。建议：设计 run_public_command / run_project_test。
project_command_routingP0partial→16G.3
问题：没有统一项目命令 router（tox / nox / sphinx / repo 脚本 + selector 参数）。真实任务常依赖这些。
证据：现有 run_tests 只跑配置反馈路径。建议：设计 project command routing，区分 public commands / setup commands / hidden verifier。
scratch_python_or_reproduction_scriptP0partial→16G.3
问题：没有正式 scratch python 工具，模型缺安全的复现脚本路径，或可能把临时脚本误混进 final patch。
证据：execute_bash 允许轻量 literal python；diagnostic_shell 能复现但 diagnostic-only。注：本轮没真跑执行 probe，结论是策略推断。
dependency_setup_or_private_overlayP0partial→16G.4
问题：依赖安装被保守拒绝，缺 per-episode 私有 overlay，真实 SWE 任务常需装依赖或建临时环境。
证据：Stage 16B 对依赖变更默认保守拒绝；私有 overlay 仍不是正式训练能力。
diagnostic_shell_formal_training_statusP1present_diagnostic_only→16G.4
问题：最有价值的调试行为被 diagnostic-only 分类，不能直接进 policy loss。这正是你关心的持久 shell：文件 projection 持久，但 cwd/env 每次命令受策略重置，且不进训练。
建议：决定升级为 formal public diagnostic profile，还是新增 run_public_command（对应你定的 core/extended 分步）。
final_only_public_diagnostic_decouplingP1unknown→16G.3
问题：final-only / hidden evaluator 当前会一并禁用 run_tests 或 diagnostic_shell——安全上合理，但可能同时挡住公开诊断命令。隐藏 verifier 不可见是硬边界；公开诊断是否可见是工具面设计问题，两者被混在一起。状态 unknown 是诚实的——需要 16G.3 查清。
execute_bash_narrow_but_not_toyP2present_non_default→16G.1
结论：不是完整 Bash，也不是空工具——窄而可审计。允许 rg/grep、安全 git 子集、pytest、受限 Python heredoc。建议作为 safe_structured_only profile 保留，但别误当主 SWE 工具面终点。
▸ 编辑 / 文件操作（2 条）
apply_patch_or_unified_diff_toolP1missing→16G.2
问题：有 edit_file 和 create_file，但没有 Claude Code 风格 apply_patch / 多文件 patch 工具，复杂多文件修改、rename、delete、large patch 效率低。
write_delete_move_mkdir_operationsP1partial→16G.2
问题：create_file 存在；但 delete / move / mkdir / write_file 未形成完整结构化工具面，建目录、改名、删旧文件受限。
▸ scaffold / 默认面（1 条）
default_training_scaffold_identityP1present_default→16G.1
关键事实：默认训练 scaffold 是 simple_react（含 bash + create_file），不是 patch_focused_react。风险：如果 review 误把 patch_focused_react 当默认，会错判 create_file / bash 缺失。建议 16G.1 固定 profile taxonomy。
▸ 任务管理 / 扩展（3 条）
todo_or_task_managementP2partial→16G.2
update_working_state 存在，但没有 Claude Code 风格 todo_write / task list，长任务规划、回溯、状态跟踪可能弱于目标部署环境。
subagent_mcp_plugin_skillP3missing→16G.1 schema 预留
完整 MCP、插件、技能、子代理不在当前工具面中。不阻塞 17B/20，但应在 trajectory schema 预留能力位。16G.1 只做 schema/profile 预留，暂不实现。
symbol_search_lsp_depthP3partial→16G.5
symbol_search 是轻量 Python AST 搜索，不是完整 LSP，对非 Python 项目或深层语义导航帮助有限。P3 后续增强，不阻塞 17A。
▸ 已有但需后续验证（2 条，好消息）
permission_denial_recoveryP2present_default→16G.6
不是从零缺失。CommandPolicyDecision 和 ToolResult 已有 reason_code、recovery_hint、safe_argv 等结构化恢复字段。建议把它作为 probe 和 reward/辅助信号候选，而不是重新设计基础字段——后续验证模型是否学会用这些恢复建议。
tool_result_artifact_replayP2present_default→16G.1
read_tool_result_artifact 存在；长输出分页和 artifact 回读是当前工具面的一部分。需继续证明不同工具的 raw artifact 不泄漏 runtime-private 内容。
▸ 训练目标 linkage（1 条）
patch_capture_verifier_reward_linkageP1partial→16G.6
问题：Stage 16E/16F 已绑定 final.patch、hygiene、projection、reward/export，但新工具操作还未全部映射进训练目标。新增 file/patch/scratch 工具若不接入 linkage，会形成「跑了但不进 reward」的无效训练目标。建议为每类工具动作定义 final patch / verifier / reward / export 的 linkage gate。

5 · 我对这一轮的一个补充意见

盘点本身扎实，但有一点你心里要有数，并在进 16G.1 时盯住：

  • Claude Code 那一侧目前是「导航级」而非「源码级」。19 条 Claude Code 能力全部只引用 AGENTS.md 导航文件，没有逐条落到真实工具源码（比如 Bash 的权限链、Edit 的精确替换协议、Task 的子代理隔离）。这导致差距矩阵的 claude_code_baseline 是模板话，无法支撑「我们到底要对齐 Claude Code 的哪个具体行为」。
  • 这不阻塞 16G.0 完成（它本来就是 inventory，深度对照属于 16G.5），但我建议：进 16G.1 设计 profile 时，对每个要补的工具，明确写出「Claude Code 对应工具的具体语义」作为设计基线，而不是等到 16G.5 才补。否则容易出现「我们补了一个 run_public_command，但它和 Claude Code 的 Bash 在权限/输出/恢复语义上对不齐」的情况。
  • 第 2 节那张对照表可以直接作为 16G.1 的设计输入起点。
