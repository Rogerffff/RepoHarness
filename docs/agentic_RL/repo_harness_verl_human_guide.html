为什么改成顺序阶段和共享 contract

RepoHarness 接入 verl 不是一个单点改动。它同时涉及训练后端适配和 Harness 自身训练模式优化。如果直接并行开发但没有共同接口，很容易出现字段不一致、reward 边界不一致、审计引用丢失、token mask 错误和并发污染。因此当前计划改成先固定 contract，再改 Harness runtime 和 training_fast，最后接 verl adapter。

共同入口

Shared Contracts

先冻结 episode、gateway、training view、audit ref、timing、resource 和 acceptance 的共同协议。

Stage 1-9

Harness Runtime / Training Fast

先让 RepoHarness 更快、更轻、更稳定地产出训练轨迹、reward、timing 和 audit reference。

Stage 10-12

verl Adapter

再让 verl 调用稳定的 RepoHarness runtime，并返回 verl 可训练的 AgentLoopOutput。

阶段门槛

Contract Tests

所有阶段必须运行同一套 canonical fixture、visibility、mask、audit 和 smoke tests。

第一版目标

普通 Agent Loop

先跑通普通 verl agent loop，确认 token、mask、reward 和 audit 边界，再进入 fully async。

现在的 run_task(...) 和未来 run_episode(...) 的区别

维度 当前 run_task(...) 未来 RepoHarnessRuntime.run_episode(...)
定位 命令行评测入口，适合 repo-harness run-task 这种完整本地运行。 可复用 episode runtime，既能被 CLI 调用，也能被 verl、slime 或本地 batch runner 调用。
输入 task_path、config_path、output_dir、run_id。 RepoHarnessEpisodeRequest，包含 task、agent policy、workspace policy、budget、run mode、visibility policy。
模型调用 内部直接根据 config 创建 ModelClient。 由外部注入 LLMGateway。这让同一条 runtime 可以路由到 OpenAI、DeepSeek、replay、verl、本地 vLLM、SGLang 或未来 slime。
输出 返回 run directory 路径，训练字段需要后处理再读文件。 返回 RepoHarnessEpisodeResult，直接包含 training_view、audit_ref、reward、verifier summary、patch summary、timing summary 和 diagnostics。
训练适配 不适合直接作为 verl Ray worker 内的稳定接口。 是 verl adapter 调用 RepoHarness 的正式边界。
设计原则是：保留 run_task(...) 作为 CLI 包装层，逐步把它内部的主流程抽到 RepoHarnessRuntime.run_episode(...)。这样不会破坏现有命令行评测，又能给 verl adapter 一个结构化、可测试、可并发调用的 episode 接口。
