1 · 核心产出的产物（重点）

共 9 份证据 JSON + 1 份人类可读 md + 1 个共享代码模块 + 1 个 CLI 命令 + 测试。核心是下面 4 样：

① 工具 registry 契约（全阶段的"图纸"）

stage16g1_tool_registry_contract.json

把 16G.0 的 27 条能力逐条写成机器记录，每条都同时声明：归属 profile、owner stage、artifact 可见性、拒绝反馈 policy、训练投影 policy、安全边界。这是 16G.2–16G.4 必须照着实现的契约。

实测：27 条全到位，其中 17 条标 blocking_for_main_swe_rl、4 条 post_16G_optional，计数与 summary 完全一致。每条都带 required_stage_from_stage16g0 字段做交叉核对（防 owner stage 被偷改）。

② 四档 profile 分类（主训练默认 = swe_public_core）

stage16g1_profile_taxonomy.json

定义 4 档工具面：safe_structured_only / swe_public_core（primary_training_default=true）/ swe_public_extended / redteam_restricted。详见第 2 节。硬规则已落实：core 明确排除持久 shell。

③ 训练资格门禁规范（数据怎么进训练）

stage16g1_training_eligibility_gate_spec.json

定义工具事件/轨迹/profile 的训练资格规则。关键是把"单个工具事件"和"整条样本"分层：allowed_in_policy_loss_trajectory(事件能否出现在 RL 轨迹) vs sample_policy_loss_candidate_effect(对整条样本资格的影响)。这阶段只定"哪些能进哪个管道"，不碰 reward 数值（留给 Stage 19）。

④ 机器验收器 + 共享模块 + run_episode smoke

src/repo_harness/stage16g_tool_profile.py · CLI: inspect-stage16g1-tool-profile · stage16g1_run_episode_profile_smoke_report.json

新增共享模块(builder/inspector/测试共用一套逻辑)+ CLI 验收命令 + 一个真实的统一入口 smoke。smoke 真的走了 run_episode_task → EpisodeExecutionSpecBuilder → RepoHarnessRuntime.run_episode → compat_projection，并把 swe_public_core 这个 profile id 和 registry 摘要带进了公开投影 —— 不是只读 JSON 的假 smoke。

2 · 四档 profile 细看（实际内容）

profile包含的能力关键边界
safe_structured_only 只读/搜/编辑/建文件/patch 审计类（17 条 allowed）
禁：bash 公开命令、持久 shell、参数化测试、scratch、项目命令、依赖（6 条 forbidden）		 最保守的低风险基线
swe_public_core 主训练默认 在 safe 基础上 + bash 公开命令/参数化测试/scratch/项目命令/依赖（大多标 planned，留给 16G.2–16G.4 实现） forbidden + must_not_include 都含 persistent_diagnostic_session —— 持久 shell 进不来
swe_public_extended core + persistent_diagnostic_session（无 forbidden） required_safety_boundaries 额外要求：session_reset / artifact_hygiene / path_redaction / public_safe_projection
redteam_restricted allowed 为空（专用于压力测试） primary_training_default=false、run_episode_required=false —— 不做主训练默认
注意 core 里大量能力现在是 planned 而非 implemented —— 这是诚实的：16G.1 只画图纸、不实现工具，所以 apply_patch / run_public_command 等都还是"计划态"，等 16G.2/16G.3 真正实现后才会从 planned 变成 implemented。这也是为什么这些能力现在 allowed_in_policy_loss_trajectory=false。

4 · 几个值得注意的实现点

  • schema 比计划最小集多了 2 个字段（合理扩展）：required_stage_from_stage16g0(每条能力记下 16G.0 的原始阶段，供 inspector 交叉核对 owner stage 没被偷改) 和 persistent_session_boundary_policy(绑定持久 shell 的安全边界)。这两个都是好补充。
  • 枚举值现在落定了(上轮字段词典里的 🟡 待定项)：repo_harness_status = present / partial / proposed_tool_required / diagnostic_only_current / schema_reserved；sample_policy_loss_candidate_effect = preserves_sample_candidate_if_all_trajectory_gates_pass / makes_sample_ineligible_until_owner_stage_complete / makes_sample_diagnostic_only_or_schema_reserved。我已把这些真实枚举回填进上一篇 HTML 的字段词典。
  • smoke 被子代理复核修正过：初版只验证 EpisodeExecutionSpec 事实(偏静态)，复核后改成真实调用 run_episode_task。implementation-notes 如实记录了这次修正(符合 CLAUDE.md 第 2 条)。
  • 诚实标注未实现：apply_patch / run_public_command / run_project_test / scratch_python 全部只进 registry 的 planned 态，没假装已实现。open question 也留了一个给 16G.2(write_file 独立工具 vs 扩展 create_file 覆盖语义)。
