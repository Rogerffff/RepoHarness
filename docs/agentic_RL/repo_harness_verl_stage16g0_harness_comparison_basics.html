三个 Harness 工具对比（扫盲版）

这是 完整阶段报告 第 4 节的展开版　·　面向「不熟悉命令行 / shell / bash，也不熟悉这三个 harness 工具」的读者，从最基础讲起，每条配小例子

读这篇你会搞清楚三件事：① 命令行 / shell / bash 到底是什么；② 这三个系统（Claude Code、mini-SWE-agent、RepoHarness）给 AI 的"工具"长什么样、有什么根本不同；③ 我们这个 RepoHarness 到底差在哪、为什么有些地方是"故意"差的。

0 · 先扫盲三个概念

① 什么是"命令行 / shell / bash"？

平时我们用电脑是鼠标点图标。程序员还有另一种方式：敲文字命令让电脑干活。这个"敲命令的文字界面"就叫命令行，背后负责解释命令的程序叫 shell，bash 是最常见的一种 shell。

举几个最基础的命令，看一眼就懂：

ls                    # 列出当前文件夹里有哪些文件
cat login.py          # 把 login.py 的内容整个打印到屏幕
grep "password" *.py  # 在所有 .py 文件里找含 "password" 的行
python -m pytest      # 运行测试
pip install requests  # 安装一个第三方库

bash 的特点是 "什么命令都能敲、能自由组合" —— 非常强大，也非常自由。对人来说很方便；但如果把这种"什么都能敲"的能力交给一个正在被训练的 AI，自由就可能变成"作弊的口子"（第 2 节细讲）。

② 什么是 agent 的"工具"？

AI agent 不是直接坐在键盘前敲字。它每一步只能做一件事：调用一个"工具"（本质是一个预先定义好的函数），填好参数，系统执行后把结果（文字）返回给它，它再决定下一步。

同样是"读文件"，两种风格：

# 风格 A：给 AI 一个万能终端（bash），它自己敲命令
AI: cat login.py
系统: (打印整个文件文本)

# 风格 B：给 AI 一个专用工具，参数固定、结果结构化
AI: read_file(path="login.py", start_line=1, end_line=50)
系统: { 行号化的内容, 是否还有更多, ... }

风格 A 自由但难管控；风格 B 受控、可审计、好截断好脱敏。这正是三个 harness 的分水岭。

③ 三个 harness 的根本区别（一个类比）

mini-SWE-agent

= 一把瑞士军刀

AI 只有一个工具：bash。看文件、搜代码、改文件、跑测试，全靠敲命令。像一个程序员坐在裸终端前。

简单直接，但全靠这一把刀，安全和审计要靠外面套一层容器。

Claude Code

= 一整套专用工具箱

每件事一个专用工具：Read 读、Grep 搜、Edit 改、Write 建、Bash 跑命令…… Bash 只是工具箱里的其中一把，而且按它要过安全检查。

这是真实产品形态：强能力 + 分层 + 权限。

RepoHarness（我们的）

= 工具箱，但终端那把被锁起来了

读/搜/改的专用工具很齐全（接近 Claude Code）；但"自由敲命令"那把（bash/execute_bash）被做得很窄、默认不放出来。

因为这是训练 AI 的环境，怕 AI 用终端作弊或偷看答案（第 2 节）。

你这次说的「mini-SWE 基本就是纯 bash」完全对 —— 它就是"一把瑞士军刀"。所以下面对比时，mini-SWE 那一列基本都是"敲某条 bash 命令"；重点看的是 Claude Code（产品标杆）和 RepoHarness（我们）之间的差距。

1 · 逐件事对比（每件事配一个小例子）

下面每张卡片是"假设要做某件事，三个 harness 分别怎么做"，最后给一个差距判定。

① 我想看 login.py 写了什么
mini-SWE
敲 cat login.py → 屏幕打印整个文件
Claude Code
按 Read("login.py") → 返回带行号内容，文件太大自动分页、告诉它"还有更多"
RepoHarness
read_file("login.py") → 和 Claude Code 几乎一样
够用 ✓ 读文件三家都行，RH 是结构化方式，比裸 cat 更好控制。
② 整个项目里，哪儿定义了 login 这个函数？
mini-SWE
grep -rn "def login" .（grep=找文字，-r=递归翻子目录，-n=显示行号）
Claude Code
Grep("def login")
RepoHarness
grep("def login") + 还有 glob_files（按文件名找）、symbol_search（按函数/类名找）
够用 ✓ 搜索三家都行，RH 甚至多给了 symbol_search。
③ 把 timeout = 30 改成 timeout = 60
mini-SWE
敲 sed -i 's/timeout = 30/timeout = 60/' config.py（sed 是文本替换命令，语法晦涩、容易改错），或干脆重写整个文件
Claude Code
Edit(config.py, old="timeout = 30", new="timeout = 60") —— 精确找到那段、替换
RepoHarness
edit_file(...) 和 Claude Code 一模一样
够用 ✓ 改单处三家都行，RH/CC 的方式比 mini-SWE 的 sed 更安全。
④ 把一个函数改名，涉及 3 个文件、8 处
mini-SWE
写脚本批量替换，或生成一个补丁文件再 git apply
Claude Code
连续按 8 次 Edit（Claude Code 也没有"一次改多文件"的按钮）
RepoHarness
连续 8 次 edit_file —— 能做，只是没有更省事的批量 / apply_patch 工具
差一点 ⚠️ 是"效率"差距不是"能不能"。注意连 Claude Code 都靠多次 Edit，所以这不是硬伤（前面单独聊过 apply_patch 不是必需）。
⑤ 新建一个文件 / 删文件 / 建文件夹
mini-SWE
建：echo "..." > new.py（>=把输出写进文件）；删：rm old.py；建夹：mkdir tests
Claude Code
建/覆盖：Write("new.py", 内容)；删/移/建夹靠 Bash
RepoHarness
create_file 能建（默认 scaffold 有）；但没有覆盖写 / 删文件 / 移动 / 建文件夹的工具
差一点 ⚠️ 能建新文件，但删/移/建目录这套文件操作还缺（16G.2 要补）。
⑥ 我改完了，只想跑那个原本失败的测试看好没好 核心差距
mini-SWE
python -m pytest tests/test_login.py::test_bad_password -x —— 想跑哪个跑哪个（:: 后面是具体那一个测试名）
Claude Code
用 Bash 跑同样的命令，一样能精确指定单个测试
RepoHarness
只有 run_tests()，不能填参数 —— 它只会跑"预先配好的那一整套"，你没法说"只跑这一个"
明显差距 ❌ 这是最关键的缺口之一。AI 学不会"针对性验证"，只能要么全跑、要么不跑 → 容易被训成"懒得跑测试、靠静态阅读猜答案"。（16G.3 P0）
⑦ 我怀疑某函数对空字符串有 bug，想写 3 行脚本试一下
mini-SWE
echo "import mod; print(mod.f(''))" > t.py && python t.py
Claude Code
Write 一个临时脚本 + Bash 跑它
RepoHarness
没有正式的"写临时脚本并运行"工具；只能用很受限的内联 python，或诊断侧通道（且不进训练）
明显差距 ❌ 写复现脚本是真实调试的常见动作（"先复现 bug 再修"），RH 还没有正式的 scratch_python。（16G.3 P0）
⑧ 这个项目要先装依赖、或跑项目自带的命令才能测
mini-SWE
直接敲 pip install -e .、tox、make test 等
Claude Code
用 Bash 跑，危险命令可能要批准
RepoHarness
装依赖类命令大多被拒绝；没有统一的"项目命令"入口（tox/nox/sphinx 等）
明显差距 ❌ 影响"需要先搭好环境才能跑"的真实任务。（依赖 16G.4 / 项目命令 16G.3）
⑨ 通用"跑任意命令"（shell 本身的能力）
mini-SWE
这就是它的全部 —— 一个 bash，爱跑啥跑啥
Claude Code
有 Bash 工具，但危险命令要过权限/批准
RepoHarness
execute_bash 只允许白名单（rg/grep/安全 git/pytest/受限 python），而且默认不开
明显差距，但故意为之 这是 RH 和 mini-SWE 唯一明显弱的点。为什么故意 → 看下一节。

2 · 为什么 RepoHarness 故意把 shell 锁起来？

关键背景：这是用来训练 AI 的环境，不是给人用的工具。训练时我们会用"测试通过没通过"给 AI 打分（reward）。如果给 AI 一个完整 bash，它可能学会"作弊刷分"而不是"真的解决问题"。几个具体的作弊口子：

如果给完整 bash，AI 可能…具体例子（大白话）
偷标准答案敲 cat .../gold_patch.diff 把"标准修复补丁"直接抄过来
偷看隐藏测试敲 cat .../hidden_test.py 看判分用的测试，然后专门糊弄这些测试，而不是真改对
翻历史找答案敲 git log / git show 看仓库后来那个"修复 commit"长什么样
篡改测试把测试文件改成"永远通过"，分数就上去了，但 bug 根本没修
污染环境乱装东西、改公共依赖，让后面的题结果都变了，训练数据不可复现
外联偷东西敲 curl 某网址 把信息传出去或下载答案
这些统称 reward hacking（刷分作弊）。一旦 AI 在训练里学会了走这些捷径，它就学不到真本事，而且换到真实环境立刻露馅。所以 RepoHarness 不敢直接给完整 bash。
但"锁住 shell"不等于"让 AI 变弱"。正确目标是：在堵死作弊口子的前提下，让 AI 仍拥有真实的诊断能力。这就是 16G.3 要做的 run_public_command —— 你可以把它想成一个"只能跑安全公开命令的受限终端"：能跑测试、能跑复现脚本、能看失败输出，但碰不到标准答案、隐藏测试、历史记录，也改不了公共环境。

一句话：mini-SWE 是"给一把没有保险的刀"，RepoHarness 想要的是"给一把带安全锁的刀"——同样能干活，但砍不到不该砍的地方。

3 · 差距一览（一眼看清强在哪、弱在哪）

能力和 Claude Code 比说明
看文件 / 搜代码 / 找文件够用结构化工具齐全，甚至多了 symbol_search
读长输出 / 回看大结果够用有 artifact 回读
沙箱隔离 / 防偷答案够用（更强）RH 在防泄漏、防作弊上比 mini-SWE 强得多
改单处代码够用edit_file 精确替换
新建文件差一点能建，但缺覆盖写
多文件 patch / 删 / 移 / 建目录差一点能凑合做，效率低（16G.2 补）
跑定向测试（只跑一个）明显差距run_tests 无参数（16G.3 P0）
写复现脚本（scratch）明显差距没有正式 scratch_python（16G.3 P0）
跑项目命令 / 装依赖明显差距没统一入口、依赖多被拒（16G.3 / 16G.4）
自由跑任意命令故意受限用受控 run_public_command 替代裸 shell
任务清单（TodoWrite）差一点有 update_working_state，较弱
符号跳转 / LSP / 子代理 / 插件可后置不阻塞主线，以后再说
一句话总结：RepoHarness 在"看 / 搜 / 改 / 防作弊"上已经够用甚至更强；真正的差距集中在"让 AI 动手验证"这一块 —— 跑定向测试、写复现脚本、跑项目命令、装依赖。这正是真实程序员"改一点→跑一下→看结果→再改"的核心循环，也是 16G.2–16G.4 要补的重点。

4 · 补充：人类可读分析文档里、之前 HTML 没汇报到的几点

① 明确的"现在不应该做什么"（3 条红线）

不要做为什么
不要直接进 Stage 17B / Stage 20（冻结数据 / 生产训练轨迹）主工具面还没定型，现在冻结会把 AI 训练到一个"不稳定、和目标环境不一致"的工具面上，等于在错误地基上盖楼
不要把"直接给完整 shell"当成快速解法见第 2 节那一串作弊风险；快是快，但训出来的能力是假的
不要把 16G.5 当成"第一次认真对比"这就是上次 follow-up 修正的事：对比要在动手前（16G.0）做完，否则 16G.1–16G.4 改完才发现方向错了要返工。16G.5 只做"改完后验收"

② 和 OpenHands / SWE-Gym / DeepSWE 的关系（关于"装依赖、搭环境"）

除了 Claude Code 和 mini-SWE，业界还有一类系统（OpenHands、SWE-Gym、DeepSWE）特别强调"可执行环境"——也就是能真实地装依赖、搭构建、跑完整项目。文档指出：如果 RepoHarness 不补"依赖安装 / 每题私有环境 / 项目命令路由"这块，在那些"必须先把环境搭好才能跑"的真实任务上，会明显弱于这类系统。这条对应 16G.4 的依赖环境收口。

③ 正式 scratch_python 不只是"能跑脚本"，要回答一串问题

文档强调，做 scratch_python 时，"能跑"只是第一步，真正要定清楚的是：

临时脚本写在哪里？是否允许 import 项目代码？
能否读写 workspace 文件、能否访问依赖环境？
输出怎么截断和脱敏？
脚本本身会不会混进 final.patch（最终提交的补丁）？
脚本跑出来的结果，算不算进训练信号（reward / 导出）？
失败时，是模型的错、环境的错、还是 harness 的错？

这也是为什么 16G.0 没有假装"已经能跑 scratch"——它诚实地把这块标成了"只做了静态策略检查、没真跑"。

④ 权限拒绝："不是没有字段，而是字段怎么帮 AI 学会改进"

一个容易误会的点：RepoHarness 的拒绝信息已经有结构化字段（reason_code 拒绝原因、recovery_hint 恢复建议、safe_argv 安全写法）。所以后续不是"从零造字段"，而是要验证：AI 看到拒绝后，是否真的学会"换个安全工具再试"，而不是被吓得"干脆少用工具、少验证、直接猜答案"。这是行为层面的事，不是字段层面的事。

整体不变的结论：RepoHarness 是"看/搜/改/防作弊很强、动手验证能力欠缺"的 harness——不是 toy，但还不能直接做 RL。下一步进 16G.1 定工具 profile，然后 16G.2（文件操作）、16G.3（公开命令/测试/复现）、16G.4（依赖/持久 shell/训练 linkage）依次补齐，最后 16G.5 实证验收。

5 · 进阶扫盲：Docker 后端怎么撑起"装依赖→多 turn 用"

前面聊到"装依赖跨 turn 用"其实不需要真正的持久 shell，只需要三样东西：每题私有 overlay + L2 每次重放环境上下文 + 让 run_public_command 复用每题持久容器。这三个名词背后是 Docker 和 Python 环境的基础概念，这一节从头讲。

5.0 · 先补 Docker 基础三件套（理解后面全靠它）

名词大白话
镜像 image一个打包好的"系统快照"，里面有操作系统、Python、预装的依赖。它是只读模板，像一张刻好的光盘。
容器 container用镜像启动起来的运行实例。像把光盘装进电脑跑起来。可以同时跑很多个容器，互相隔离。
可写层 / 分层文件系统镜像是只读的；启动容器时，会在镜像最上面盖一个可写层。你在容器里写文件、pip install 装包，全写进这个可写层，动不到底下的只读镜像。
      ┌─────────────────────────┐  ← 可写层（容器自己的，你的改动都在这）
      │  pip 装的包、改的代码…    │
      ├─────────────────────────┤
      │  只读镜像 image          │  ← 只读，多个容器可共享同一个镜像
      │  (OS + Python + 通用依赖) │
      └─────────────────────────┘

记住这张图，下面的"overlay"和"持久容器"都是它的变体。

5.1 · 每题私有 overlay 是什么

要解决的问题：训练要跑成百上千道题，它们共用一个很大的基础环境（OS + 通用依赖）。但每道题可能要装自己额外的依赖。如果所有题都往同一个环境里装：

  • 题 A 装 numpy==1.20、题 B 要 numpy==1.26 → 互相冲突、污染；
  • 题 A 装的东西改变了题 B 的结果 → 训练不可复现（同一道题重跑结果都不一样，reward 信号就脏了）。

解法 = 每题私有 overlay：每道题在共享只读基础之上，叠一个只属于自己的可写层（overlay）。"overlay"就是"覆盖层"的意思 —— 一个可写层盖在只读基础上面。

      只读共享基础（base，所有题共用，省时间省空间）
        Python 3.11 + 项目通用依赖
              │
   ┌──────────┼──────────┐
   ▼          ▼          ▼
 题A 私有层   题B 私有层   题C 私有层      ← 每题一个可写 overlay
 numpy1.20   numpy1.26   ...

 题A 看到的 = base + A层；题B 看到的 = base + B层；互不影响
 题做完 → 丢弃该私有层（base 始终干净、只读）

三个好处（正好对应训练需求）：

隔离A 题装的不影响 B 题 → 可复现
安全私有层可写、共享 base 只读 → 模型改不了公共环境（堵住第 2 节"污染环境"那个作弊口子）
效率不用每题从零搭一套完整环境，大头共享，只 overlay 各自的小差异
它和"每题持久容器"是什么关系？其实每题起一个容器就天然是一种 overlay —— 容器自带的那个可写层（5.0 那张图最上层），就是这道题的私有 overlay。所以最简单的实现就是"每题一个容器"：题内复用、题间销毁，可写层天然隔离。更精细的做法是用 Linux 的 OverlayFS 显式挂载（共享更大的只读 base、只 overlay 依赖目录），但概念是同一个。

5.2 · L2「每次重放环境上下文」是什么

先补三个基础概念：

cwd 当前工作目录命令"在哪个文件夹里跑"。在 /repo 里跑 pytest tests/ 和在 / 里跑，结果不同。
环境变量一些"全局设定"，命令运行时能读到。例：PATH（去哪找可执行程序）、PYTHONPATH（Python 去哪找模块）。
venv 虚拟环境Python 的"独立依赖小屋"。python -m venv .venv 建一个，source .venv/bin/activate 激活后，pip install 装进这个小屋、python 用这个小屋的包。"激活"本质就是改了几个环境变量（让 PATH 指向 .venv/bin）。

问题：每次 docker exec 都是一个全新的 shell —— cwd 回到默认、环境变量清空、venv 没激活。所以 turn 1 做的 cd /repo && source .venv/bin/activate，到 turn 3 那个全新 exec 一概不记得。

L2 解法：让 harness 自己记住这道题的"环境上下文"（工作目录 + 该设的环境变量 + venv 路径），每次执行命令前自动重新套上。模型只管说要跑什么，harness 在底层补全：

模型只说：   run_public_command("python -m pytest tests/test_x.py::test_y")

harness 实际执行：
  docker exec <这道题的持久容器> bash -lc \
    "cd /repo && source .venv/bin/activate && python -m pytest tests/test_x.py::test_y"
       ▲              ▲                              ▲
    回到工作目录    激活venv(上一turn装的包在这)        模型真正要跑的命令

模型看起来像"一直在同一个会话里连续操作"，但底层每次都是独立、确定的 exec。harness 就是那个"每次帮你站回正确位置、系好围裙"的人。

为什么这比"真持久 shell"更适合训练？因为确定性。每条命令的运行环境是 harness 明确构造、可记录、可复现的 —— 不依赖"上一条命令碰巧把环境改成了什么"。装的依赖在文件系统（私有 overlay）里持久，所以 source .venv/bin/activate 后照样用得到上一 turn 装的包；而 cwd/env 不需要真持久，因为 harness 每次重放。

5.3 · 让 run_public_command 跑在"每题持久容器"上，大概怎么做

好消息："每题持久容器"这套基础设施，现在的 diagnostic_session 已经实现并验证过了。要做的不是从零造，而是"复用基础设施 + 换一套语义"。

diagnostic_session 已经做好的【基础设施】—— 直接复用：
   session_id = run_id + task_id
   → 找/建一个【这道题专属的持久容器】
   → 同一题多次调用复用它（文件、装的依赖都还在 ← 就是"持久"）
   → 题结束 / 超时 → 销毁容器（跨题隔离）

run_public_command 要换掉的【语义】—— 重做：
   ✗ 不用 diagnostic_shell 那种宽权限
   ✓ 改用 public-only 命令策略（白名单 + AST 校验，只允许公开测试/项目命令/受控复现）
   ✓ 碰不到 hidden verifier / gold patch / runtime-private / git history / 共享依赖写
   ✓ 结果可进训练轨迹（training-eligible）、脱敏、带 reason_code / recovery_hint

拆开看就是两件事：

  • ① 持久容器基础设施（容器复用、文件持久、跨题销毁）—— diagnostic_session 已有，直接复用；它天然提供了 5.1 的"每题私有 overlay"。
  • ② 高权限诊断语义（宽命令、能进侧通道）—— 不复用，换成 public-only 策略 + 训练资格门禁。

每次执行 = 在那个持久容器里 docker exec，前面套上 5.2 的环境上下文（cd + venv + env），命令先过 public 策略校验，结果标成可进训练。

一个类比：diagnostic_session 已经修好了"一间每题专用、用完就拆的实验室"（持久容器）。我们要做的不是再盖一间实验室，而是给它配一套"只能做公开安全实验的操作规程"（public 命令策略），并让实验产出能正式记进训练数据。

所以回答你的问题：用 Docker 后端、不上外部 sandbox 服务，不难 —— 因为最难的"每题持久容器 + 跨题销毁"已经用 Docker 跑通了；run_public_command 复用同一套 Docker 机制，只换策略和训练资格。真正费工的是"真交互式持久 shell / 后台常驻进程"（L3），而那个我们本来就为了可复现性主动延后到 extended。
把三者串起来（一句话）：每题持久容器给你"装的东西不丢"（= 每题私有 overlay，隔离又安全）；L2 每次重放环境上下文给你"模型感觉像连续操作"（但底层确定可复现）；run_public_command 复用这套基础设施 + 换 public 策略给你"能跑测试/复现、又不会作弊、还能进训练"。三件事合起来，就实现了"装依赖→多 turn 用"，全程不需要真正的持久 shell，也不需要外部 sandbox。
