Stage 2 用一句话三件事概括

① 定形状

把未来所有训练 / 评测路径都要对齐的入口签名钉下来：async run_episode(request, *, llm_gateway) → EpisodeResult。后续 CLI、本地批处理、verl adapter 都要走这一个入口。

② 跑骨架

用 FakeLLMGateway 跑通 1 turn 最小 happy path，证明 request → gateway → EpisodeResult 这条形状是闭合的、能产出结构化结果。

③ 钉契约

16 个测试把 8 种 status、TrainingView 只能用 gateway token、cleanup 不覆盖主状态、provider route 不可 online RL、overflow 结构化 invalid、绝对路径不能漏进 batch 等边界全部锁死。

读 Stage 2 代码时最容易误读的两点：
① RepoHarnessRuntime 不是 run_task 的替代品，是它未来的入口形状。
② LLMGatewayModelClientAdapter 单测之外没人调用，只是给未来桥接 legacy AgentLoop 留的接缝。

③ 核心组件详解

每张卡片包含：签名 · 输入 · 输出 · 调用方 · 边界。签名照搬 runtime.py 的源代码定义。

数据类RepoHarnessRuntimeOptions

runtime-only 配置容器（frozen dataclass）。用来把"本机才知道的事"和"会进训练 batch 的 episode 事实"在编译期就物理切开，避免绝对路径 / callable 漏进可传播 schema。

@dataclass(frozen=True) class RepoHarnessRuntimeOptions: config_path: str | Path | None = None output_dir: str | Path | None = None project_root: str | Path | None = None task_path_resolver: TaskPathResolver | None = None require_resolved_task_path: bool = False require_runner_paths: bool = False executor_max_workers: int = 1 episode_timeout_seconds: float | None = None cleanup_callback: CleanupCallback | None = None default_success_reward: float = 1.0 default_failure_reward: float = 0.0 minimal_final_verifier_status: Literal["accepted","rejected"] = "accepted" execution_mode: str = "minimal_gateway"

为什么需要这个对象（一句话）

判断口诀：①「这个字段能 json.dumps 吗？」②「换到另一台机器上对方还能正确解释吗？」
任一答案是 否 → 必须放 Options。例如 cleanup_callback 是 lambda 没法序列化、/home/roger/runs/config.yaml 换机器就坏，所以二者都不能进 RepoHarnessEpisodeRequest。

字段按用途分组

每个字段都给一个具体值的例子，并说明"为什么必须放 Options"和"当前是否被消费"。

字段 / 默认 状态 作用 + 具体值例子 为什么必须在 Options（不能进 EpisodeRequest）
🗂 组 A：本机路径与 task 解析（Stage 5+ 真接 run_task 时才连通）
config_path
默认 None		 占位 未来传给 load_run_config(config_path) 读评测配置。
例："/home/roger/runs/swe-bench/config.yaml"		 是绝对本地路径，跨机器无意义；进入 batch 会让训练数据带本机目录信息（既泄露隐私，也让回放在其它机器上失败）。
output_dir
默认 None		 占位 artifact / trajectory 落盘的目录，runner 会写到 {output_dir}/{run_id}/。
例："/tmp/runs/run-001"		 同上，是本机 IO 目标。一份训练 batch 跑在 100 个 GPU 上，每个 worker 的 output_dir 都不同，所以这是"机器级"信息而非"episode 级"信息。
project_root
默认 None		 占位 仓库根，用来把相对 task path / 相对 fixture path 解析成绝对路径。
例："/home/roger/Desktop/claude-code-verl-stage0h"		 纯本机路径；同一份 batch 在另一台机器上 project_root 可能完全不同。
task_path_resolver
默认 None		 占位 从 EpisodeRequest 推出本地 task 文件路径的可调用对象。
例：lambda req: f"/data/tasks/{req.task_id}.yaml"		 是一个 Python Callable，根本无法 JSON 序列化；只能在本进程里活着。
require_resolved_task_path
默认 False		 生效 保险开关。设 True 时如果 request 和 resolver 都给不出 task_path → 抛 InvalidTaskError。
用法：本地批跑时显式设 True，防 silent skip。		 "是否要强制要求本地路径解析成功"这种策略只对当前这次本机运行有意义，跨机器场景里另一台机可能根本不需要本地 task 文件（比如 prompt 已经预渲染好）。
require_runner_paths
默认 False		 生效 另一把保险。Stage 5+ 真要跑 run_task 时设 True，没有 config_path / output_dir 就早抛错，不要走到一半才崩。 同上，是"本次运行的执行策略"而不是 episode 身份。
⏱ 组 B：超时与清理（Stage 2 已经真正在用）
episode_timeout_seconds
默认 None		 生效 episode 整体的机器侧硬上限。run_episode 用 asyncio.wait_for(...) 包裹 gateway 调用；与 request.budgets.max_wall_seconds 取较小者。
例：开发机设 30.0，生产 batch 设 600.0。		 同一个 episode（同 task_id、同 prompt）在开发机和生产机上想要的 timeout 不同。这是"机器策略"。Episode 逻辑预算 budgets.max_wall_seconds 仍然在 EpisodeRequest 里，两者职责切开。
cleanup_callback
默认 None		 生效 同步或 async 回调，episode 结束 / 失败 / 取消都会跑（用 asyncio.shield 保护）。
例：lambda: docker.containers.get(cid).remove(force=True)。		 Callable 无法序列化；而且回调的目标（docker socket / 本地容器 ID）也是本机资源。绝对不能进 batch。
🎯 组 C：reward / verifier 占位（minimal path 自洽用，Stage 5+ 退役）
default_success_reward
默认 1.0		 生效 真实 reward function 还没接通时，episode succeeded 的占位奖励。
例：单测里设 2.5 验证 reward 是否正确写入 TrainingView.reward_score。		 同一个 episode 在不同实验里可能希望奖励标签不同（A 组用 1.0，B 组用 0.5 做消融）。这是"运行策略"而非 episode 身份。Episode 本身只承诺"是否成功"，奖励数值由 runtime 决定。
default_failure_reward
默认 0.0		 生效 同上，episode failed 时用。例：消融实验里把 failure 改成 -1.0 看是否影响收敛。 同上。
minimal_final_verifier_status
默认 "accepted"		 生效 Stage 2 minimal path假装的 verifier 结果。_status_from_minimal_verifier() 直接读它决定 succeeded 或 failed。
例：单测里设 "rejected" 走失败分支。		 这是"我没有真实 verifier 时假装的结果"，**纯 minimal-path 调试参数**。Stage 5+ 真 verifier 接通后这个字段就退役了。不能进 EpisodeRequest——episode 本身不该规定"我应该被判 accepted"。
🏷 组 D：执行模式与并发（标记 + 未来 executor）
execution_mode
默认 "minimal_gateway"		 生效 字符串标签，写入 ResourceSummary.execution_mode + gateway tracing，方便审计回放时一眼分辨这次 episode 走的哪条路径。
未来值："minimal_gateway" / "legacy_run_task_bridge" / "verl_full"。		 属于"本机这次跑用了哪条代码路径"，是审计元数据而不是 episode 身份事实（同一个 episode 在不同代码路径下应该产出"相同"的逻辑结果，只是 trace 不同）。
executor_max_workers
默认 1		 占位 Stage 5+ 用 asyncio.to_thread(...) 包同步 AgentLoop / PytestVerifier 时限制并发 worker 数。
例：开发机设 1，生产 16 核机设 8。		 纯机器配置（多少核 / 内存多大）。Episode 本身不该规定"我必须用 8 worker"，这是 runner 侧的事。

构造期校验（__post_init__）

  • executor_max_workers < 1 → ValueError（防 0 worker 死锁）。
  • episode_timeout_seconds ≤ 0 → ValueError（0 秒立即超时无意义）。
谁会用构造 RepoHarnessRuntime(options=...) 时传入。1000 个 episode 共享一份 options（"机器规格"），每个 episode 只传干净的 request。
硬边界这里的字段绝不能复制到 RepoHarnessEpisodeRequest 或 TrainingView。Stage 2 的测试 [test_stage2_runtime_options_paths_do_not_leak_into_batch_fields](../../tests/unit/test_repo_harness_rl_stage2_runtime.py#L86) 就在锁这条边界。

类RepoHarnessRuntime

Stage 2 的主入口。包装 options，对外暴露 async run_episode(...) 一个公共方法。

class RepoHarnessRuntime: def __init__(self, options: RepoHarnessRuntimeOptions | None = None) -> None async def run_episode( self, request: RepoHarnessEpisodeRequest, *, llm_gateway: LLMGateway, ) -> RepoHarnessEpisodeResult def resolve_runner_inputs(self, request) -> RuntimeResolvedInputs

输入

  • request：Stage 1 已定义的 RepoHarnessEpisodeRequest（episode_id / task_ref / budgets / visibility_policy …）。
  • llm_gateway：实现 LLMGateway.generate_turn(...) 的对象（Stage 2 测试里用 FakeLLMGateway）。

输出 RepoHarnessEpisodeResult 的关键字段

  • status ∈ 8 种之一（见 §⑤）。
  • invalid_for_training / invalid_for_online_rl：训练资格 flag。
  • training_view：仅来自 gateway 的 token 事实。
  • budget_consumption / timing_summary / resource_summary / audit_diagnostics。
内部依赖调用 llm_gateway.generate_turn(...)，并内部使用 asyncio.wait_for 实现 episode timeout，使用 asyncio.shield 保护 cleanup。
调用方当前只有 Stage 2 单元测试；未来 CLI / 本地批处理 / verl adapter 都将复用同一个入口。
边界第一版只支持 1 turn 最小 gateway path，不调用真实 verifier / workspace / docker / reward。
不抛异常所有失败都被转化成有 status 和 audit_diagnostics 的结构化结果，绝不向外抛 asyncio.CancelledError / TimeoutError。

函数map_episode_status(...)

纯函数 helper：把现有 runner 的离散事实合并成 8 种 Stage 2 status 之一。优先级从上到下。

def map_episode_status( *, final_verifier_status: str | None = None, baseline_status: str | None = None, run_outcome: str | None = None, agent_stop_reason: str | None = None, provider_error_type: str | None = None, infrastructure_error: bool = False, invalid_task: bool = False, timeout: bool = False, cancelled: bool = False, ) -> Literal["succeeded","failed","invalid","invalid_task", "infrastructure_error","cancelled","timeout","no_progress"]

决策优先级（从高到低）

  • 1. cancelled=True → cancelled
  • 2. 任意 timeout 标记或 reason 包含 timeout / timed_out / deadline_exceeded → timeout
  • 3. invalid_task / baseline_status="invalid" / run_outcome="invalid_task" → invalid_task
  • 4. infrastructure_error / final_verifier_status="error" / 有 provider_error_type → infrastructure_error
  • 5. stop reason ∈ {no_progress, stalled, max_no_progress} → no_progress
  • 6. verifier accepted / outcome success → succeeded
  • 7. verifier rejected / outcome failed → failed
  • 8. 其余 → infrastructure_error（防漏）

具体例子

  • final_verifier_status="provider_timeout" → timeout（因为字符串含 "timeout"）。
  • provider_error_type="HTTPError" → infrastructure_error。
  • agent_stop_reason="deadline_exceeded" → timeout。
  • 全部参数 None → infrastructure_error。
调用方对外暴露给 CLI 桥接和后续 Stage 5+ adapter；Stage 2 内部并不使用（内部走 _status_from_minimal_verifier()）。
边界纯函数、不读 IO、不抛异常；测试 [test_stage2_runtime_status_mapping_table](../../tests/unit/test_repo_harness_rl_stage2_runtime.py#L149) 用真值表方式锁定。

适配器LLMGatewayModelClientAdapter

新旧接口接缝：让旧的同步 AgentLoop 不改代码就能"看见" async LLMGateway。

class LLMGatewayModelClientAdapter: def __init__(self, *, llm_gateway, episode_id, route, inference_backend=None) def generate(self, request: ModelRequestContext, recorder) -> ModelResponse def to_gateway_request(self, request: ModelRequestContext) -> LLMGatewayRequest def to_model_response(self, request, response: LLMGatewayResponse) -> ModelResponse

调用方向：旧 → 新

  • ModelRequestContext（旧 ModelClient 协议）→ LLMGatewayRequest（Stage 1 contract）。
  • 搬运字段：messages / tools / sampling / provider_options / budget_state / visibility_policy / tracing。

调用方向：新 → 旧

  • LLMGatewayResponse → ModelResponse。
  • 把 response.tool_calls 转成 ToolCall pydantic 实例；构造 ModelCallEvent（含 token 计数、provider request id、duration）。

异常InvalidTaskError

class InvalidTaskError(ValueError): ...

两种触发场景：① request.task_ref.task_path 是绝对本地路径（违反 visibility）；② require_resolved_task_path=True 但 resolver 返回 None。被 run_episode 内部捕获并转成 status="invalid_task"，不变成 infrastructure error。

④ run_episode(...) 内部流程

一次 episode 在 runtime 内部的 7 步流水线。每一步都有明确的失败归类，所有异常最终被收敛进 status / status_reason / audit_diagnostics。

1 解析 + 校验 request RepoHarnessEpisodeRequest.model_validate(request)，确保 pydantic schema 通过。
2 resolve_runner_inputs 拒绝绝对 task_path；运行 task_path_resolver；按 require_* 检查。失败 → InvalidTaskError。
3 构造 LLMGatewayRequest 把 request.raw_prompt / budgets / visibility 折成一份 1-turn gateway request（turn=0, model_call_id={episode}-turn-0）。
4 await generate_turn 若设置 episode_timeout_seconds 或 budgets.max_wall_seconds，用 asyncio.wait_for(...) 包裹，取较小者。
5 校验 gateway 响应 检查 route / inference_backend 一致性、token 长度、logprob 是否存在、是否走 provider route。见 §⑥。
6 cleanup（必跑） 无论成功/失败/取消都执行 cleanup_callback，用 asyncio.shield 防止被外层取消打断。
7 组装 EpisodeResult 填 TrainingView（只用 gateway token 事实）/ BudgetConsumption / TimingSummary / ResourceSummary / AuditRef。
异常 → 状态 映射：asyncio.CancelledError → cancelled；TimeoutError → timeout；InvalidTaskError → invalid_task；其他 Exception → infrastructure_error。Cleanup 失败只写入 audit_diagnostics 和 ResourceSummary.cleanup_status，不会覆盖主 status。

⑧ 初版后审查发现的 6 项修复

Stage 2 初版通过目标测试后，额外审查发现 6 个未覆盖的契约和审计完整性问题，已经全部转成回归测试并在 runtime 中修复。

问题修复
route=verl 的请求收到 provider route 响应时，仍可能被当作 online RL 样本。新增 route + inference_backend 一致性校验；provider response 一律不能进入正式 online RL。
verifier rejected 时，TrainingView.extra_fields.repo_harness_status 可能错写为 succeeded。_extra_fields(...) 使用真实 episode status 写入。
provider_timeout / task_timeout / tool_timeout 等旧状态未完整映射到 timeout。map_episode_status 现在识别包含 timeout / timed_out / deadline_exceeded 的 reason。
request.task_ref.task_path 可以携带绝对本地路径。request 内 task path 拒绝绝对路径；只允许通过 runtime options 或 resolver。
prompt overflow 会抛 schema 异常，没有返回结构化 invalid。prompt overflow 返回 status=invalid、status_reason=prompt_length_exceeded。
overflow 缺少 BudgetConsumption / AuditDiagnostic。overflow 现在写入 stop_reason、诊断；response overflow 额外记录 rollout_response_length 与 actual_response_length。
