产物展开说明

RepoHarnessRuntimeOptions

这是 Stage 2 新增的 runtime-only 配置对象，专门承载本地运行所需但不能进入训练 batch 的信息，包括 config_path、output_dir、project_root、task_path_resolver、executor_max_workers、episode_timeout_seconds 和 cleanup_callback。

它的作用是把本地机器路径和资源设置从 RepoHarnessEpisodeRequest 中隔离出来，避免绝对路径、运行目录或 evaluator-only path 被误放进可传播 schema。

RepoHarnessRuntime.run_episode(...)

这是 Stage 2 的核心 async facade。它接收 RepoHarnessEpisodeRequest 和 LLMGateway，先解析 runtime-only 输入，再构造一轮 LLMGatewayRequest，调用 llm_gateway.generate_turn(...)，最后返回结构化 RepoHarnessEpisodeResult。

它现在覆盖成功、失败、timeout、cancelled、invalid task、infrastructure error 和 invalid overflow 结果，并保证 cleanup 失败只进入 diagnostics 和 ResourceSummary.cleanup_status，不会覆盖主状态。

LLMGatewayModelClientAdapter

这是给现有同步 AgentLoop 预留的新旧接口接缝。它可以把旧的 ModelRequestContext 转成 LLMGatewayRequest，并把 LLMGatewayResponse 转回旧的 ModelResponse。

Stage 2 只实现 adapter 的确定性映射和单元测试，不把完整 CLI run_task(...) 路径强行迁移到 runtime，也不迁移真实 OpenAI、DeepSeek、vLLM 或 SGLang provider route。

map_episode_status(...)

这个 helper 把现有 runner 事实映射到 Stage 2 的 result status。它优先处理 cancelled、timeout、invalid task、infrastructure error，再处理 no-progress、accepted 和 rejected。

它已经覆盖 provider_timeout、provider_timeout_or_transport_error、task_timeout、tool_timeout 以及带有 deadline_exceeded 语义的失败原因。

TrainingView 构造

最小 runtime 只用 gateway 返回的 token 事实构造训练视图：prompt_ids 来自 LLMGatewayResponse.prompt_ids，response_ids 来自 output_token_ids，response_logprobs 来自 output_logprobs。

如果缺少 log probability、使用 provider route、response route 与 request route 不一致，或者发生 prompt / response overflow，结果都会标记为不能进入正式 online RL，而不是伪造可训练样本。

overflow 审计

prompt overflow 和 response overflow 现在都会返回结构化 invalid result。结果里会写入 BudgetConsumption.stop_reason 和 AuditDiagnostic，方便后续复查为什么该 episode 被挡在训练之外。

response overflow 还会记录 rollout_response_length 和 actual_response_length。prompt 长度字段当前不在 BudgetConsumption schema 中，因此 prompt overflow 的具体长度差异先写入 diagnostic message。

审查 follow-up 修复

Stage 2 初版通过目标测试后，额外审查发现 6 个未覆盖的 contract 和审计完整性问题。本次已经把它们全部转成回归测试，并在 runtime 中修复。

问题 修复结果
request 是 route=verl 时，gateway 返回 provider route 仍可能被当作 online RL 样本。 新增 response route 和 inference backend 一致性校验；provider response route 一律不能进入正式 online RL。
final verifier rejected 时，TrainingView.extra_fields.repo_harness_status 可能错误写成 succeeded。 训练视图现在使用真实 episode status 写入 batch 可传播状态字段。
provider timeout、task timeout、tool timeout 等旧状态没有完整映射到 timeout。 状态映射 helper 现在识别包含 timeout / timed_out / deadline_exceeded 的 provider error 和 agent stop reason。
request.task_ref.task_path 可以携带绝对本地路径。 request 内 task path 现在拒绝绝对路径；本地绝对路径只能来自 runtime-only options 或 resolver，不进入 batch 字段。
prompt overflow 会抛出 schema 异常，没有返回结构化 invalid result。 prompt overflow 现在返回 status=invalid、status_reason=prompt_length_exceeded 的结构化 episode result。
prompt / response overflow 虽然返回 invalid result，但缺少 BudgetConsumption 和 AuditDiagnostic。 overflow 结果现在写入 BudgetConsumption.stop_reason 和审计诊断；response overflow 还记录 rollout_response_length 与 actual_response_length。

目标

Stage 2 要把当前 CLI / evaluation runner 的任务运行链路抽成可复用的 RepoHarnessRuntime.run_episode(...)。第一版可以复用现有同步 agent loop、workspace、verifier、reward 和 recorder 逻辑，但外层接口必须是 async，和 Stage 1 已落地的 async LLMGateway.generate_turn(...) 对齐。 

class RepoHarnessRuntime:
    async def run_episode(
        self,
        request: RepoHarnessEpisodeRequest,
        *,
        llm_gateway: LLMGateway,
    ) -> RepoHarnessEpisodeResult:
        ...
这一阶段的关键词是 runtime facade。它不是 training_fast，不是 TrainingView -> AgentLoopOutput converter，也不是 RepoHarnessVerlAgentLoop。

第一项工作

先做只读梳理，不直接重写 runner。需要确认当前运行链路从 task/config 到 workspace、context、agent loop、final verifier、reward、artifact 和 summary 的数据流。

实施前必须固定的执行边界

Stage 2 不能只新增一个 async 函数外壳，然后在内部继续绕回旧 provider client。下面这些边界需要先写清楚，再进入代码实现。

LLMGateway 接入现有 AgentLoop

当前 AgentLoop 调用的是同步 ModelClient.generate(...)。Stage 2 第一优先选择是新增临时 LLMGatewayModelClientAdapter，把旧 ModelRequestContext 转成 LLMGatewayRequest，再把 LLMGatewayResponse 转回旧 ModelResponse。

如果完整 legacy agent loop 桥接风险过大，Stage 2 只能交付明确标记的 fake gateway 最小 runtime path，不能声称完整 agent loop 已经接入 gateway。

request 到本地 runner 输入的映射

现有 run_task(...) 需要 task_path、config_path、output_dir 和 run_id。Stage 2 应新增 RepoHarnessRuntimeOptions 或等价 runtime-only 配置来承载 config_path、output_dir、本地 resolver 和 executor 设置。

RepoHarnessEpisodeRequest 继续描述可移植 episode 事实，不能为了复用旧 runner 把绝对路径、run directory 或 evaluator-only path 塞进可传播 schema。

取消、executor 和清理语义

如果用 asyncio.to_thread(...) 或 executor 包同步 runner，外层 coroutine 被取消时，底层线程不会自动停止。Stage 2 必须使用受控、有限并发的 executor，并把 runtime 可控资源放入 try/finally 或等价保护。

cancellation smoke 第一版只能验证 fake/minimal path 或 runtime 可控的 cancellation 标记与 cleanup，不能宣称已经能强制中断任意同步 Docker、verifier 或 provider 调用。

TrainingView 构造边界

Stage 2 不能通过最终文本重新分词来伪造 online RL token。fake gateway smoke 可以直接使用 LLMGatewayResponse 的 token 事实构造最小 TrainingView。

真实旧 provider 或 replay 路径如果没有 token ids 和 log probability，必须标记 invalid_for_online_rl=true，只能作为 diagnostic result、SFT、preference 或 offline replay 的候选证据。

  1. 梳理现有 run_task(...) 数据流，明确哪些输入来自 CLI，哪些事实属于 episode request，哪些证据进入 episode result。

  4. 新增临时 LLMGatewayModelClientAdapter；如果这一步暂缓，必须明确完整 AgentLoop 尚未接入 gateway。
  5. 用 Stage 1 async FakeLLMGateway 跑最小 episode smoke，验证能返回结构化 RepoHarnessEpisodeResult，并验证 fake gateway 确实被调用。
  6. 实现状态映射 helper，覆盖 accepted、rejected、no progress、timeout、invalid task、infrastructure error 和 cancelled。

关键 contract

LLMGateway 不可绕过

Stage 2 测试必须能证明 runtime 使用了传入的 llm_gateway。如果只交付 fake/minimal path，也必须明确完整 AgentLoop gateway 接入尚未完成。

状态边界

invalid_task 和 infrastructure_error 必须默认 invalid_for_training=true、invalid_for_online_rl=true，不能被当成普通模型失败样本。

取消和清理

run_episode(...) 必须使用 try/finally 或等价资源保护，确保 workspace、container、artifact writer 和 verifier future 有确定处理。

audit ref

即使发生 timeout、cancelled 或 infrastructure error，也应尽量产出最小 AuditRef 或明确的 infrastructure error artifact，避免只有外层异常没有可审计证据。

fake gateway

Stage 2 只需要 async fake gateway 支持最小 runtime 单元测试，不需要真实 vLLM、SGLang、Ray 或 verl server。

token 事实来源

TrainingView 只能从 gateway 返回的 token 事实构造。缺少 token ids 或 log probability 的旧 provider / replay path 不能伪装成正式 online RL 样本。
