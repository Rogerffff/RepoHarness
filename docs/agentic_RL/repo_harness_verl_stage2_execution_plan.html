Stage 2：抽出 RepoHarnessRuntime.run_episode(...)

这一页是 Stage 2 的独立执行计划汇报页。它只说明即将执行的边界、文件、顺序、验收方式和不做事项，不记录已经完成的 Stage 2 代码结果。Stage 2 的目标是抽出可复用 async episode runtime facade，让后续 CLI、本地批处理和 verl adapter 都能调用同一个 RepoHarness episode runtime。

Stage 1 已完成 Stage 2 待执行 不提前实现 verl adapter

目标

Stage 2 要把当前 CLI / evaluation runner 的任务运行链路抽成可复用的 RepoHarnessRuntime.run_episode(...)。第一版可以复用现有同步 agent loop、workspace、verifier、reward 和 recorder 逻辑，但外层接口必须是 async，和 Stage 1 已落地的 async LLMGateway.generate_turn(...) 对齐。 

class RepoHarnessRuntime:
    async def run_episode(
        self,
        request: RepoHarnessEpisodeRequest,
        *,
        llm_gateway: LLMGateway,
    ) -> RepoHarnessEpisodeResult:
        ...
这一阶段的关键词是 runtime facade。它不是 training_fast，不是 TrainingView -> AgentLoopOutput converter，也不是 RepoHarnessVerlAgentLoop。

第一项工作

先做只读梳理，不直接重写 runner。需要确认当前运行链路从 task/config 到 workspace、context、agent loop、final verifier、reward、artifact 和 summary 的数据流。

必须先读

src/repo_harness/evaluation/runner.py、src/repo_harness/agent_loop/loop.py、src/repo_harness/model_client/protocol.py、src/repo_harness/workspace/backend_factory.py。

也要对齐

src/repo_harness/trajectory/recorder.py、src/repo_harness/reward/schemas.py、src/repo_harness/verifier/schemas.py 和 Stage 1 的 src/repo_harness/rl/ schema。

实施前必须固定的执行边界

Stage 2 不能只新增一个 async 函数外壳，然后在内部继续绕回旧 provider client。下面这些边界需要先写清楚，再进入代码实现。

LLMGateway 接入现有 AgentLoop

当前 AgentLoop 调用的是同步 ModelClient.generate(...)。Stage 2 第一优先选择是新增临时 LLMGatewayModelClientAdapter，把旧 ModelRequestContext 转成 LLMGatewayRequest，再把 LLMGatewayResponse 转回旧 ModelResponse。

如果完整 legacy agent loop 桥接风险过大，Stage 2 只能交付明确标记的 fake gateway 最小 runtime path，不能声称完整 agent loop 已经接入 gateway。

request 到本地 runner 输入的映射

现有 run_task(...) 需要 task_path、config_path、output_dir 和 run_id。Stage 2 应新增 RepoHarnessRuntimeOptions 或等价 runtime-only 配置来承载 config_path、output_dir、本地 resolver 和 executor 设置。

RepoHarnessEpisodeRequest 继续描述可移植 episode 事实，不能为了复用旧 runner 把绝对路径、run directory 或 evaluator-only path 塞进可传播 schema。

取消、executor 和清理语义

如果用 asyncio.to_thread(...) 或 executor 包同步 runner，外层 coroutine 被取消时，底层线程不会自动停止。Stage 2 必须使用受控、有限并发的 executor，并把 runtime 可控资源放入 try/finally 或等价保护。

cancellation smoke 第一版只能验证 fake/minimal path 或 runtime 可控的 cancellation 标记与 cleanup，不能宣称已经能强制中断任意同步 Docker、verifier 或 provider 调用。

TrainingView 构造边界

Stage 2 不能通过最终文本重新分词来伪造 online RL token。fake gateway smoke 可以直接使用 LLMGatewayResponse 的 token 事实构造最小 TrainingView。

真实旧 provider 或 replay 路径如果没有 token ids 和 log probability，必须标记 invalid_for_online_rl=true，只能作为 diagnostic result、SFT、preference 或 offline replay 的候选证据。

执行顺序

  1. 梳理现有 run_task(...) 数据流，明确哪些输入来自 CLI，哪些事实属于 episode request，哪些证据进入 episode result。
  2. 先定义 RepoHarnessRuntimeOptions，明确 config_path、output_dir、本地 path resolver 和 executor 设置来自 runtime-only 配置。
  3. 新增 async RepoHarnessRuntime.run_episode(...) facade，内部可以先包同步实现，但必须通过 LLMGateway 或明确标记的 fake/minimal path。
  4. 新增临时 LLMGatewayModelClientAdapter；如果这一步暂缓，必须明确完整 AgentLoop 尚未接入 gateway。
  5. 用 Stage 1 async FakeLLMGateway 跑最小 episode smoke，验证能返回结构化 RepoHarnessEpisodeResult，并验证 fake gateway 确实被调用。
  6. 实现状态映射 helper，覆盖 accepted、rejected、no progress、timeout、invalid task、infrastructure error 和 cancelled。
  7. 前置 cancellation / timeout / cleanup contract，确保外层 coroutine 取消、episode timeout、provider timeout、verifier timeout、Docker command timeout 和 cleanup 失败有明确归属。
  8. 确认 cleanup 失败不会覆盖原始 episode 状态，但会写入 diagnostics 和 ResourceSummary.cleanup_status。
  9. 明确 TrainingView 构造边界：只能使用 gateway token 事实；缺少 token / log probability 的 legacy provider path 必须 invalid_for_online_rl=true。
  10. 最后再评估是否让 CLI run task 调用 runtime facade；如果风险过大，保留原 CLI 路径并在测试和文档中说明。

关键 contract

LLMGateway 不可绕过

Stage 2 测试必须能证明 runtime 使用了传入的 llm_gateway。如果只交付 fake/minimal path，也必须明确完整 AgentLoop gateway 接入尚未完成。

状态边界

invalid_task 和 infrastructure_error 必须默认 invalid_for_training=true、invalid_for_online_rl=true，不能被当成普通模型失败样本。

取消和清理

run_episode(...) 必须使用 try/finally 或等价资源保护，确保 workspace、container、artifact writer 和 verifier future 有确定处理。

audit ref

即使发生 timeout、cancelled 或 infrastructure error，也应尽量产出最小 AuditRef 或明确的 infrastructure error artifact，避免只有外层异常没有可审计证据。

fake gateway

Stage 2 只需要 async fake gateway 支持最小 runtime 单元测试，不需要真实 vLLM、SGLang、Ray 或 verl server。

token 事实来源

TrainingView 只能从 gateway 返回的 token 事实构造。缺少 token ids 或 log probability 的旧 provider / replay path 不能伪装成正式 online RL 样本。

出口标准

RepoHarnessRuntime.run_episode(...) 是 async 接口，并接收 RepoHarnessEpisodeRequest 和 LLMGateway。
本地执行路径和资源位置通过 runtime options 或显式 resolver 提供，不能把绝对 config_path、output_dir、run_dir 放入 batch 可传播 schema。
Stage 2 测试能证明 runtime 没有绕过 llm_gateway：要么通过临时 adapter 进入现有 agent loop，要么明确只交付 fake/minimal path 且不声称完整 agent loop 已接入。
fake gateway 最小 episode 能产出结构化 RepoHarnessEpisodeResult。
cancelled、timeout、invalid_task、infrastructure_error 的训练无效语义明确。
cancellation smoke 能看到确定的 cleanup diagnostics 或最小 infrastructure error artifact，但不能声称外层 coroutine cancellation 可以强制停止任意同步 run_task(...) 线程。
TrainingView 第一版只能从 gateway token 事实构造；缺少 token ids 或 log probability 的 legacy provider / replay path 必须标记 invalid_for_online_rl=true。
CLI run task 仍保持原有可用性；如果尚未完全桥接 runtime facade，必须明确记录原因。
