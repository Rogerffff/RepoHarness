Stage 11 完成态 ↔ Stage 12 端到端 smoke 缺口分析

本页是独立缺口分析报告，不属于任何 stage 的实施计划。基于对 Stage 0H – Stage 11 已实施代码的 grep + 对 Stage 12 端到端 smoke 计划的字面要求逐条核对得到。结论：即使 Stage 11 全部完成，仍然有 3 个核心缺口阻止 Stage 12 真正端到端 smoke——这 3 个缺口都没有任何 stage 计划负责填补。

Stage 11 完成后 verl 真的能调 RepoHarness，但调到的 runtime 仍然是 1-turn LLM-only 骨架——workspace / 工具调用 / 真实 verifier 这三块在 Stage 6/7 提供了零件，但没有任何 stage 计划把它们注入 RepoHarnessRuntime.run_episode。Stage 12 端到端 smoke 字面要求"tool/workspace + final verifier + reward_score"成立，但实际只能跑出"prompt_ids / response_ids / response_mask / response_logprobs 形状正确、reward 为占位值"的 fake-end-to-end 验收。

③ 3 个核心缺口总览

缺口 A · workspace materialize

Stage 6 提供 WorkspaceSnapshotManager，没人接进 runtime。Stage 12 要求"workspace lease 可反查"——做不到。

归属：计划缺失

缺口 B · agent loop 多轮 + tool

runtime 内 _generate_minimal_turn 写死 turn=0，没接现有 AgentLoop。模型在 verl 训练时只跑 1 turn，没有任何工具调用。

归属：计划缺失

缺口 C · 真实 verifier callable

Stage 7 VerifierWorkerPool 框架就绪，RepoHarnessRuntimeOptions.final_verifier_callable 字段就绪，但没人用真实 PytestVerifier 填进去。

归属：计划缺失

三个缺口互相串联：A 不接，B 没地方跑（无 workspace 无法 `pytest`）；B 不接，C 没东西验（无 patch 无法判 accepted）。必须同时补，单独补一个等于没补。

事实证据

当前 runtime 的"turn" 写死

# runtime.py: _generate_minimal_turn async def _generate_minimal_turn(self, request, llm_gateway): gateway_request = LLMGatewayRequest( ..., turn=0, # ← 写死，永远只跑 1 turn tools=[], # ← 写死，没有工具 context_revision=0, messages=request.raw_prompt, ... ) return await llm_gateway.generate_turn(gateway_request)

对 Stage 12 要求 #10 的影响

TimingSummary.tool_seconds、context_prepare_seconds 在 schema 里有，但 runtime 实际跑出来都是 0。"能拆分 model/tool/workspace/verifier/artifact 时间"——分桶定义有，tool 和 workspace 桶实际产值都是 0。

更严重的语义后果

verl 训练理论上是让模型与仓库交互（读代码、改代码、跑测试），但 Stage 11 完成时这个交互根本不发生。模型在 RepoHarnessVerlAgentLoop 调度下只输出 1 次（turn=0），输出的 token 直接拿去算 reward——这退化为"完成式 / one-shot generation"，不是 agentic RL。

⑥ 缺口 C · 真实 verifier callable 没注入 pool

事实证据

  • VerifierWorkerPool：✅ 实现完整，含双层 BoundedSemaphore + queue timeout + cancellation 等
  • Stage7RewardBoundaryResult：✅ 实现完整，含 12 种 error_type 映射

  • 真实 PytestVerifier 包装成 callable 后传入：❌ 无任何代码做这件事

对 Stage 12 要求 #4 的影响

"reward_score 可用"——不能做。reward 由 build_stage7_reward_boundary(final_verifier=...) 计算，final_verifier 来自 callable 调用结果。callable 不是真的 → final_verifier 不是真的 → reward_score 是占位值（默认按 options.minimal_final_verifier_status 给 1.0 或 0.0）。

⑧ 假如不补的后果：Stage 12 实际能验收什么

如果直接按当前计划进入 Stage 12 而不补桥接阶段，下面是 Stage 12-A (Mac 本地结构验收) 实际能跑出来的事：

✓ 能验收

  • verl AgentLoopWorker 调度路径通畅
  • kwargs allowlist + visibility 边界全部生效
  • RepoHarnessEpisodeRequest schema 安全 id / 路径
  • VerlLLMGateway 调 LLMServerClient → token_ids 真实
  • AgentLoopOutput shape + 长度对齐
  • DataProto tensor / non-tensor / meta_info visibility
  • invalid 样本 route gate（mock/replay/openai 拒绝）

✗ 不能真验收（但表面会通过）

  • reward_score 是占位值，不反映真实 pytest 结果
  • multi-turn agentic 行为 = 0（永远 turn=0）
  • 模型与 workspace 交互 = 0
  • TimingSummary 中 tool/workspace 桶 = 0
  • ResourceSummary.snapshot_key / lease_id = None
  • training_fast vs full_audit artifact 对比意义弱（runtime 不真写大量 artifact）
  • Stage 12-B Vast.ai GPU 训练前验收会通过形状检查但训练效果未知
最严重的隐患：Stage 12-A Mac 本地验收会全部通过，因为它只检查"接口、字段和训练视图转换正确"（见 sequential plan §15.A）。但真实训练时模型并没有跟 repo 交互——只是输出一段 token，被打了个假 reward。这种"端到端 smoke 通过"会给后续 vast.ai GPU 训练制造虚假的信心。
