2 · 关键设计决策（配例子）

① create_file 保持"只新建"，另加独立的 write_file

create_file 现在的语义是"只新建，已存在就拒"。计划不允许把它偷偷改成可覆盖（会破坏旧轨迹和模型对它的理解），而是另起一个 write_file(path, content, mode, expected_content_hash?)，mode = create / overwrite / upsert。

例子 要覆盖 defaults.py：先 read_file 拿到内容 hash=abc → write_file("defaults.py", 新内容, mode="overwrite", expected_content_hash="abc")。upsert 默认不进 core（怕模型盲目覆盖未知文件）。

② apply_patch 用"结构化批量操作"，不是 unified diff / git apply

apply_patch 不等于 patch -p1 / git apply / 任意 shell。它接收一组结构化 operation（replace_text / write_file / delete_file / move_file / mkdir），每个带路径 + 内容哈希，不靠行号定位。

关键是"全预检通过后再写"的原子语义：先把所有 operation 都检查一遍（路径合法、hash 匹配、不越界），全过了才真正落盘；预检中任一失败 → 一个文件都不动。

例子 函数改名涉及 3 文件 → apply_patch([replace_text×2, move_file, write_file])，要么全部成功，要么工作区完全不变。删除和移动 operation 需要模型提供 reason，说明为什么这次删除或移动是正确修改。
partial_failure（预检过了、但落盘时极少数运行时失败）→ 必须报 rollback_status，且整条 episode 标 invalid_for_training（只能当诊断，不进训练）。

③ 覆盖/删除/移动都强制 expected_hash（v1 主路径）

覆盖写、删除、移动、apply_patch 的 replace_text，第一版必须显式带 expected hash —— 不能靠"上次 read 的隐式缓存"。这是防 stale edit（你读完之后文件被改了，你还按旧内容覆盖）。

例子 read 到 hash=abc，但文件在你写之前被改成 hash=xyz → write_file(..., expected_content_hash="abc") 被拒绝（reason_code=hash 过期），而不是盲目覆盖。隐式缓存便利语义可后续加，但必须带 observation 绑定 + stale 测试。

④ 写入工具有明确输入规模上限

不能接受无限大的内容/路径/operation 列表。建议起步上限（可调，但必须写进契约+executor+测试）：

限制上限超限
路径字符数1024path_too_long
单文件内容1 MiBcontent_too_large
apply_patch 操作数50too_many_operations
总写入2 MiBpatch_too_large

超限在预检阶段拒绝，绝不产生半应用的工作区变更。

⑤ 文件操作必须进 final.patch，不能只改工作区

新工具要用真实 run_episode 证明改动能进 final.patch / hygiene / projection。两个细节很关键：

  • mkdir 空目录不进 git diff（Git 不追踪空目录）—— 所以它的成功事实来自 tool event / operation audit / TrainingView，而不是要求空目录出现在 final.patch；只有目录下产生了文件才要求那个文件进 final.patch。
  • move 在 final.patch 里可能表现为 rename，也可能 delete+add（取决于 diff 相似度检测）—— 两种都允许，但结构化 operation facts 必须保留 move 语义、source/target path 和 source hash。

⑥ 所有文件工具复用同一个底层服务 file_mutation.py

新建一个共享模块统一管：路径解析、hidden/runtime-private/版本控制/宿主路径拒绝、UTF-8 检查、expected hash 校验、预检+执行、统一 reason_code/recovery。这样 edit/create/write/delete/move/mkdir/apply_patch 不各写一套路径检查和拒绝语义（避免出现"这个工具能越界、那个不能"的不一致漏洞）。

5 · 我的审查观察 + 你该拍板的决策

先说好的：这版计划和我们之前的讨论高度一致。① apply_patch 用结构化批量 + 上下文哈希而非行号 unified diff —— 正是我之前建议的（模型易产坏 diff，结构化更稳）；② create_file 保留原语义、另加 write_file —— 解决了 16G.1 留的那个 open question；③ 持久 shell 仍被挡在 core 外；④ 明确不碰 reward 数值（留 Stage 19）。保守、可审计、边界清楚。

知情 R1 · 默认训练 scaffold 的工具面要变宽，但不能过宽

16G.0/16G.1 都没动工具。16G.2 起，simple_react（当前训练默认 scaffold）会拿到 write_file 和 apply_patch。删除、移动、建目录先通过 apply_patch operation 表达，独立 delete/move/mkdir 不默认暴露。这样既补齐真实文件组织能力，又降低强化学习阶段的工具选择负担。

我的看法：合理且必要。建议盯一点——新工具进 DEFAULT_TOOL_ORDER 后，模型提示语别鼓励它用 shell 重定向/裸 patch（计划 2A 验收已要求这条），否则白补了结构化工具。

可拍板 R2 · 强制 expected_hash 的人体工学代价

v1 要求覆盖/删除/移动前必须显式带 hash —— 模型每次改这类操作前都得先 read_file 拿 hash。安全（防 stale 覆盖）但稍繁琐，会让轨迹多几步 read。

我的看法：v1 这样保守是对的（RL 要干净可复现，盲目覆盖是 reward-hacking/脏数据来源）。后续可加"带 observation 绑定的隐式 read-cache"便利语义降低步数。需要你点头：v1 接受这点繁琐换安全（我建议接受）。

真实架构待补 R3 · "进入 profile"目前还是 scaffold 驱动，没有运行态 profile 选择层

计划 §6.5 老实说了：当前工具是通过 scaffold 的 allowed_tools 进入 execution spec 的，还没有完整的"运行时选 profile"机制。所以"工具进了 swe_public_core"这件事，验收要同时查真实 scaffold 暴露 + profile taxonomy delta，不能只看文档里的 profile 名。

我的看法：计划已用 §9.10 防住"只改文档"。但这暴露一个真实待补点：profile 现在是"声明"，scaffold 才是"现实"，两者还没合一。这个 gap 最终要在 16G.6 冻结时面对（把 profile 做成真正能选用的运行态）。先记着，不阻塞 16G.2。

实现时盯 R4 · rollback 健壮性 + partial_failure 处理

apply_patch 全预检通过后，落盘阶段仍可能极少数运行时失败 → 要 rollback。但 rollback 本身也可能失败。计划正确地把这类 episode 标 invalid_for_training + 进 safety probe（不伪装成成功/普通拒绝）。

我的看法：处理方向对。实施时（2B）要重点用真实文件系统 probe 验证：rollback 真的把工作区还原干净，否则那条 episode 必须坚决踢出训练。这是数据干净度的关键防线。
需要你回的，主要是 R2（v1 接受"覆盖前先 read 拿 hash"的繁琐换安全——我建议接受）。R1/R3/R4 是知情 + 实施时我会帮你盯。其余设计决策（upsert 不进 core、apply_patch 结构化、输入上限）我都认为合理，默认按计划走。如果你认可，就可以让 agent 按这版计划进 16G.2A 了，我照例在它做完后独立核查（重点：apply_patch 事务原子性、expected_hash 强制、partial_failure→invalid_for_training、新工具真进 final.patch、core 仍无持久 shell）再给你完成报告，并更新能力总表对应卡片。

6 · 问答环节

6.1 · 工具是怎么决定模型能看到的？（DEFAULT_TOOL_ORDER → scaffold → profile）

这是理解 R3 的基础。结论先说：现在最终决定模型能看到/调用哪些工具的是 scaffold（的 allowed_tools）；profile 目前只是文档声明，"怎么在运行时强制 gate 工具"还没做，留到 16G.6。

概念是什么角色
DEFAULT_TOOL_ORDERtools/minimal.py 里的列表：决定默认按什么顺序放进模型上下文。它是默认放进模型上下文的"可用工具清单"（每个工具的 schema：名字+说明+参数），整个 episode 每一轮都在（不只首轮）。非默认工具仍可通过显式 profile / scaffold 用 build_tool 构造。默认菜单
scaffoldagent loop 模板，定义"几个阶段、每阶段模型看哪些工具(allowed_tools)"。simple_react≈DEFAULT_TOOL_ORDER 全部；patch_focused_react 更窄真正在跑、真正决定可见工具
profile（16G.1 概念）命名的工具面策略(safe/core/extended/redteam)，taxonomy 写"core 含哪些、禁哪些、训练资格如何"目前只是契约/文档
现在：   run_episode(scaffold_id="simple_react")
         → 模型看到的工具 = simple_react 的 allowed_tools
         → "它等于 swe_public_core" 是【推导出来的对应】，不是运行时强制
           （16G.1 smoke 里 derived_profile_id_for_current_default_scaffold=swe_public_core 就是这种推导）

缺的：   run_episode(profile="swe_public_core")
         → 运行时【直接照 core 定义】算出该给哪些工具、禁的(如持久 shell)坚决不给、套用 core 训练资格
         → 跟用哪个 scaffold 解耦
点菜类比：profile 像"套餐菜单"（写明 core 套餐有哪些菜、禁哪些），scaffold 像"后厨当前在做的菜清单"。现在没有"下单系统"让你点"core 套餐"后厨就照做——后厨清单是另一套人工维护、靠人对齐。缺的就是这个"按 profile 下单、运行时强制"的层。

所以现在 profile 和 scaffold 可能漂移（文档说 core 不含持久 shell，但万一某 scaffold 实际暴露了，光看文档发现不了）→ 16G.2 验收必须同时查"profile 文档怎么说" + "scaffold 实际暴露什么"。真正的修法（把 profile 做成运行态强制选择、和 scaffold 合一）留到 16G.6 冻结。

6.2 · 4 个补充问答

Q1 · 既然已有 edit_file，为何 structured_edit_existing_file 还排 P0？CC 不也只有 Edit？edit_file 有缺陷吗？

edit_file 本身不残缺，和 CC 的 Edit 同级（都是 exact-replace 精确替换）。计划 §4 对这条的实际目标是"保留 edit_file，靠 batch patch 补齐复杂修改"——也就是说这条的 P0 实际落在 apply_patch 上，两者绑在一起。registry 标它 partial/P0，是因为把"稳健的复杂/多文件编辑"整体当成主 RL 必需，"只有单点 exact-replace"对这个高标准算 partial。

我的看法（你质疑得对）：CC 都靠多次 Edit 完成多处修改、并没有 apply_patch，所以 apply_patch 是效率/原子性的选择，不是硬需求。edit_file 够用；这条的 P0 更多是"编辑面整体要够稳"的体现，真正的新增工作就是 apply_patch 的 batch replace_text。

Q2 · write_file 是覆盖已存在文件的工具吗？"独立工具 vs 扩展 create_file"在 16G.2 定了吗？

定了。计划 §5.1 明确：新增独立 write_file，create_file 保持"只新建"不动（不偷改旧语义，免得破坏旧轨迹和模型对它的理解）。

write_file(path, content, mode, expected_content_hash?) 支持 create / overwrite / upsert 三种 mode。它相对 create_file 的新增价值主要是 overwrite（覆盖已存在文件，必须带 expected_content_hash 防 stale 覆盖）；upsert 默认不进 core（怕模型盲目覆盖未知文件）。

我的看法："另起 write_file、不动 create_file"是对的——保持既有工具语义稳定，新能力放新工具，边界清楚。

Q3 · delete/move/mkdir 都要新增工具吗？还是像 CC 用 Write+Bash？

修正后的设计是：不走 Bash，也不默认暴露三个独立工具。删除、移动、建目录先作为 apply_patch.operations，独立 delete_file / move_file / mkdir 保留为 extended / 实验 profile 能力。delete/move 强制 expected_hash 和模型提供的 reason。

为什么不学 CC 用 Bash：这正是我们之前定的"结构化优先"。CC 用 Write+Bash 做文件组织变更，但 RH 主训练 core 故意不给裸 bash（防 reward-hacking/泄漏，见安全红线）。所以用结构化 operation 替代 CC 的"Bash 做文件操作"——能力覆盖到，但形态更可控可审计。

Q4 · task_management_todo 在 16G.2 要实现吗？计划里包含吗？

在计划里（作为子阶段 16G.2D），但是非阻塞、不强制做完整 TodoWrite。16G.2D 可二选一：①保持 update_working_state 轻量语义（补 projection 和训练资格说明），或 ②新增更接近 Claude Code TodoWrite 的结构化任务状态工具。

无论哪条，它都不能阻塞 write_file / apply_patch 以及 apply_patch operation 中 delete / move / mkdir 语义这条 P0 主线。即使没做完，只要：P0 文件工具全完成 + task_management_todo 明确标 non-blocking + acceptance summary 记 remaining_followup + 16G.5 parity probe 会重新检查它，就允许作为非阻塞 follow-up 记录。

我的看法：合理。todo 是轨迹质量项不是改代码主线，放非阻塞、留到能和真实任务一起评估，是对的取舍。
