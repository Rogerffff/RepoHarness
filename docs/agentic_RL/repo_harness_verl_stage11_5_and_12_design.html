Stage 11.5 + Stage 12 设计详解

这两个阶段是整个 RepoHarness × verl 工作流最重要的两步：Stage 11.5 把前序 8 条 bridge 真正接通让 RepoHarnessRuntime 能跑真实软件工程 episode；Stage 12 在此基础上分 A / B / C 三层完成端到端 smoke——Mac 本地结构验收 → GPU 真实小模型 episode smoke → 小 batch trainer smoke。计划修订后完全覆盖了之前 缺口分析中提出的 3 个核心缺口。

⓪ 设计要点一句话

Stage 11.5 引入 runtime_execution_mode 区分"minimal_gateway（contract 测试用）"和"real_episode（必须接通 workspace + tool + agent loop + verifier + reward + artifact）"，并明确 8 条 bridge 要求；Stage 12 分 A/B/C 三层：12-A 用 fake gateway / fake LLMServerClient 在 Mac 本地证 real_episode bridge 跑通 + adapter 转换正确，12-B 用 Qwen2.5-Coder-7B-Instruct 真实模型 + 极小仓库任务在 Vast.ai GPU 跑真 vLLM/SGLang 端到端，12-C 再把它送进 PPO/GRPO trainer 验收 DataProto 形状和 invalid 样本过滤。

关键设计："基础设施链路是否跑通"和"模型是否成功修复任务"必须分开判定——模型一次没修好不算基础设施失败。

① runtime_execution_mode：Stage 11.5 引入的新概念

这是 runtime-only 配置，放在 RepoHarnessRuntimeOptions 上。不能和 RepoHarnessEpisodeRequest.run_mode（full_audit/training_fast/training_debug，控制 recorder 策略）混用。两者分别管两件不同的事。

minimal_gateway

用途：contract / adapter / DataProto shape smoke
只跑：llm_gateway.generate_turn(...) 1 turn
禁止用于：声称"完整 RepoHarness episode 端到端可用"
证明 LLMGateway token / mask / logprob / visibility contract 正确
不跑 workspace / tool / verifier / reward

real_episode

用途：Stage 12 前置真实 runtime smoke
必须进入：workspace materialize、tool、agent loop 多轮、verifier、reward、artifact
验收前置：Stage 12-A/B/C 端到端 smoke 唯一可信凭证
真实软件工程 episode 闭环
每段 token 来源、mask、logprob 策略可追溯
关键规则（plan §15 决策 #11/#12）：
  1. Stage 11.5 不删 minimal_gateway，它仍用于快速结构测试。
  2. 但任何端到端训练可用性的证据都必须来自 real_episode 路径。
  3. Stage 12 在所有报告中必须明确具体是哪条路径产生的证据。

② Stage 11.5 必须接通的 8 条 bridge

这 8 条是 real_episode 模式的入场券，每条对应"前序某个 Stage 的能力"→"接进 run_episode 真实执行"。

1workspace runtime bridge Stage 6 的 WorkspaceSnapshotManager + dependency cache + copy-on-write episode workspace + lease cleanup 接入 run_episode。禁止把本地绝对路径放进 RepoHarnessEpisodeRequest。
2agent loop bridge 真实 RepoHarness AgentLoop 通过 LLMGatewayModelClientAdapter 调 LLMGateway（避免绕过 gateway）。多轮工具调用、tool observation、context revision、budget state、no-progress stop 保持原有语义。
3tool / workspace bridge 工具的读 / 写 / 搜索 / 测试 / workspace command 必须作用在当前 episode 独立 writable workspace，不污染 snapshot 或其它 episode。
4recorder bridge Stage 3 的 full_audit / training_fast / training_debug recorder profile 必须用于真实 agent loop 产物，不只是最小 fake gateway 路径。
5verifier / reward bridge 真实 final verifier callable 从 task + workspace + runtime-only config 构造，经 Stage 7 verifier worker pool（或受控 direct path）执行。reward boundary 必须用真实 VerifierResult，不能用 minimal_final_verifier_status 占位伪装。
6timing / resource bridge TimingSummary / ResourceSummary 必须反映真实事实：workspace / tool / context prepare / model call / verifier / reward / artifact / cleanup。无法获得 → diagnostics，不能静态占位冒充。
7cancellation / cleanup bridge 取消 / timeout / verifier timeout / workspace cleanup failure / run directory lock conflict 仍遵守 Stage 2 / 7 / 9 已固定的状态和资源释放语义。
8token provenance bridge real_episode 的 TrainingView 不能从最终 transcript 重新分词。必须由每轮 LLMGatewayResponse + GenerationRecord + 工具 observation token projection 汇总，每段 token 保留来源、mask、logprob 策略。

③ Stage 11.5 阶段出口（5 条）

#验收项
1runtime_execution_mode=real_episode 可以在本地用 fake/mock gateway 跑通至少一条极小仓库任务：真实 materialize workspace、真实执行工具、真实产生 patch 或 workspace state、真实运行 verifier、真实生成 reward、真实写入 artifact / timing / resource evidence。
2minimal_gateway 继续存在，但文档 / 测试 / 报告必须明确"只覆盖 contract / adapter / DataProto 结构"，不覆盖完整软件工程任务闭环。
3ResourceSummary 能反查 snapshot key、workspace lease、cleanup_status 和可公开的 workspace reference；不泄漏本地绝对路径。
4TimingSummary 至少能区分 model / tool / workspace / verifier / reward / artifact / cleanup / queue_wait 主要分桶；某桶为 0 必须是因为该 episode 确实没执行对应动作。
5TrainingView.response_spans 能解释多轮 agent loop 中 assistant generation 和 tool observation 的 token 来源；工具 observation token 的 mask / logprob 规则继续遵守 Stage 0H contract。

Stage 11.5 明确边界

  • 不启动真实 Ray / SGLang / vLLM / PPO / GRPO trainer（留给 Stage 12）。
  • 不要求 warm container pool 或分布式资源租约。
  • 不删 minimal_gateway。

④ Stage 12 三层验收 A / B / C

Stage 12 不是一个不可分的整体——分三层，必须按顺序逐层通过。Mac 本地通过只表示"本地真实 runtime bridge 和 adapter contract 正确"；GPU + Vast.ai 通过才表示"真实训练前链路可用"。

12-A · Mac local

Mac 本地真实 runtime bridge smoke

工具：verl-lite / reference stubs
依赖：不需要 vLLM / SGLang / flash-attn / CUDA
证明对象：Stage 11.5 的 real_episode bridge 能跑真实 RepoHarness episode
必须真实执行：workspace / tool / verifier / reward
12-B · GPU 真实模型

GPU / Vast.ai 真实小模型端到端 smoke

模型：Qwen2.5-Coder-7B-Instruct 或同级 code instruct
任务：极小仓库任务（buggy_calculator 等）
证明对象：route=verl 在真实推理服务下 + 真实模型 + verl postprocess 下可用
不进 trainer loss 路径（留给 12-C）
12-C · trainer batch

小 batch trainer smoke

依赖：12-B 通过
证明对象：小 batch 能进 PPO / GRPO trainer 关键路径
不要求收敛 / 统计意义的训练结果
只要求 batch 语义正确 + invalid 样本处理明确 + loss 输入形状 + log probability 来源正确

⑤ Stage 12-A：Mac 本地真实 runtime bridge smoke 详解

必须同时跑通两条路径：

路径 ① · debug / diagnostic smoke：fake gateway + real_episode

RepoHarnessRuntime.run_episode(...) ↓ fake/mock LLMGateway ↓ real_episode runtime bridge # ← Stage 11.5 关键 ├─ workspace snapshot / lease ├─ RepoHarness agent loop ├─ tool execution ├─ final verifier └─ reward boundary ↓ RepoHarnessEpisodeResult / TrainingView ↓ extra_fields / AuditRef / raw_prompt visibility 检查
注意：这条 mock route 路径只用于 debug / diagnostic runtime smoke。mock 不能进 formal online RL converter，也不作为正式 PPO / GRPO 样本可训练性的证据。

路径 ② · formal converter smoke：fake LLMServerClient + route=verl

RepoHarnessVerlAgentLoop.run(...) ↓ RepoHarnessRuntime.run_episode(...) ↓ real_episode runtime bridge ↓ RepoHarness agent loop ↓ VerlLLMGateway ↓ fake LLMServerClient.generate(...) # ← 假的 server，但产生 route=verl 的 token ↓ fake TokenOutput ↓ route=verl token facts / GenerationRecord ↓ tool / workspace / verifier / reward ↓ AgentLoopOutput ↓ response_ids / response_mask / response_logprobs 长度检查

想验证 formal online RL converter 必须走这条路径——由 adapter 产生 route=verl 的 token、mask、logprob 事实。

12-A 验收边界

允许禁止

使用 fake logprobs 做长度和 mask 对齐测试（仅 debug smoke） 验证真实 Ray GPU resource scheduling

— 伪造 AgentLoopOutput.as_dict() / postprocess / TransferQueue / DataProto visibility 等核心转换逻辑

12-B 11 条验收点

#验收点
1tokenizer / processor / chat template 与训练模型一致
2response_ids 来自真实生成路径，不从最终 transcript 重新分词伪造
3response_logprobs 非空，并与 response_ids、response_mask 长度对齐
4rollout_log_probs 出现在 DataProto tensor batch 中，形状 [batch_size, rollout.response_length]
5rm_scores 存在 或 样本被明确过滤；invalid 样本不能悄悄参与 policy loss
6sticky session / prefix cache 的 request_id 语义正确
7Ray actor、server manager、LLM server、RepoHarness workspace worker 在同一台或多台 GPU 实例上并发运行
8workspace snapshot backend 在 Linux 文件系统通过 preflight：支持 cp --reflink=auto / overlayfs / Docker volume snapshot / 安全回退目录复制
9training_fast artifact 体积下降，AuditRef 可回查 run dir / transcript / events / patch / reward / timing/resource summary
10TimingSummary 能看到 model / tool / workspace / verifier / artifact 拆分
11ResourceSummary 能看到 inference route / container lease / snapshot key / cache hit / verifier worker pool
关键判定规则："基础设施链路是否跑通" 和 "模型是否成功修复任务" 必须分开。极小任务中应至少包含一个极易成功的正例任务，但模型单次没修好应记为 rejected episode 或模型失败样本，不能误判为基础设施失败。

SGLang vs vLLM

SGLang 真实 smoke 和 vLLM contract smoke同阶段完成，允许一个作为主验收、另一个作为 parity smoke。若 Vast.ai 镜像条件只支持其中一个，必须在 preflight 记录原因和补齐计划（plan §18 决策 #13）。

⑦ Stage 12-C：小 batch trainer smoke 详解

12-B 证明单条或少量真实模型 episode可用后，12-C 再验证小 batch 进 PPO / GRPO trainer。

设计原则

  • 不要求模型收敛
  • 不要求产出有统计意义的训练结果
  • 只要求：batch 语义正确 + invalid 样本处理明确 + loss 输入形状 + log probability 来源正确

6 条验收点

#验收点
1DataProto.batch 中 prompts / responses / response_mask / rollout_log_probs / rm_scores 形状符合 verl trainer 要求
2DataProto.non_tensor_batch 和 meta_info 通过 visibility 检查
3PPO / GRPO smoke 必须记录 actor_rollout_ref.rollout.calculate_log_probs=True 或当前 verl 版本等价配置
4进 trainer 前必须显式跑 formal batch validator：所有 valid 样本必须 route=verl + response_logprobs 非空 + generation_records 全来自 verl；invalid 样本过滤 / 重采样 / 置零 loss weight 策略可审计
5invalid / timeout / infrastructure error / no-progress / 缺失 logprob 的样本不悄悄进有效 policy loss
6若采用丢弃 / 重采样 / 置零 loss weight，必须在 metrics 和 audit evidence 中可见
三层完成的含义：
  1. 12-A 通过 → "本地真实 runtime bridge 和 adapter contract 正确"
  2. 12-B 通过 → "真实推理 + 真实小模型 + 极小仓库任务 episode 端到端 OK"
  3. 12-C 通过 → "真实训练前链路可用"
只有三层都通过，整个 Stage 12 才算完成。

⑧ 与之前 缺口分析的对照

缺口分析提了 3 个核心缺口；修订后的 plan 通过 Stage 11.5 的 8 条 bridge 把它们全部包含。下表是一一对照：

缺口 原缺口分析判定 Stage 11.5 对应 bridge 现状
缺口 A · workspace materialize 没人接 bridge #1（workspace runtime bridge）+ #3（tool/workspace bridge） 明确要求
缺口 B · agent loop 多轮 + tool 没人接 bridge #2（agent loop bridge）+ #3（tool/workspace bridge）+ #8（token provenance bridge） 明确要求
缺口 C · 真实 verifier callable 没人接 bridge #5（verifier/reward bridge）—— 明确禁止 minimal_final_verifier_status 占位伪装 明确要求
附带改进：runtime 时间 / 资源真实事实 bridge #6 timing/resource bridge ← 明确要求
附带改进：取消 / 清理一致性 bridge #7 cancellation/cleanup ← 明确要求

仍需小心的地方

  • Stage 11.5 是独立 stage而不是 Stage 11 的子任务，避免被混淆。
  • plan §18 决策 #11 把 Stage 11.5 钉死为 Stage 12 的前置阶段——这条规则需要在所有 stage 11 / 12 执行报告中显式引用。
  • 12-A 必须真跑 workspace/tool/verifier/reward，禁止用 minimal_gateway 冒充端到端（plan 已经明文写）。
  • 12-B 必须把"基础设施跑通"和"模型修复"分开判定——这条非常容易被混淆，监控仪表必须分两个指标。
