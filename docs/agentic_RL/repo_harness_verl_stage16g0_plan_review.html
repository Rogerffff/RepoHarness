1 · 为什么会有这个阶段

你的核心担忧（已写进 AGENTS.md 第 96–131 行）是这条因果链：

工具面太窄（为了防作弊把动作空间压死）
  → 模型在 harness 里没法形成「定位→复现→改→验证」的真实闭环
  → RL 奖励会强化「少运行命令、少复现、靠静态阅读猜 patch」的行为
  → 训练出来的模型在当前 harness 看着干净，一迁移到真实环境就断层

说得更直白：如果这个 harness 连一个「只给 Bash」的 mini-SWE-agent 都不如，那在里面做强化学习就没有意义。这个项目最终要训练的是「在接近 Claude Code 的真实工具环境里替用户解决问题」的能力。

三份背景材料对这件事的看法并不完全一致，这点很关键，我放到第 6 节专门讲。

2 · Stage 16G.0 到底是什么

它被定位成 Stage 17A（数据 registry）之前的一个 P0 分析任务。它是「盘点 / 差距分析 / 验收」阶段，本身不做任何能力改造。改造留给后面的 16G.1 / 16G.2。

做 这一阶段会做的

  • 盘点 Claude Code 参考源码里到底有哪些工具（Read / Grep / Glob / Edit / Write / Bash 的分层）
  • 盘点 RepoHarness 当前真实有哪些工具、哪些默认可见、哪些只在诊断侧通道
  • 逐个 scaffold 列出模型真正能看到的工具，并核对「声明的工具」和「真正注册的 executor」是否一致
  • 产出能力差距矩阵、风险报告、Stage 17 放行/阻断结论，以及后续 16G.1+ 的改造建议

不做 这一阶段明确不碰的（计划第 17–28 行）

  • 不新增或修改任何模型可见工具
  • 不放宽 execute_bash 或 diagnostic_shell 策略
  • 不改 run_episode(...) / run-episode-task / AgentLoop / EpisodeExecutionSpec 的行为
  • 不启动远端 GPU、不做真实 RL 训练
  • 不冻结 Stage 17 的真实训练数据 split
  • 不把 Claude Code 的实现直接抄进 RepoHarness

换句话说：这一阶段结束时，代码行为应该和现在一模一样。如果实施 agent 改动了 src/repo_harness/tools/、command_policy.py 或 runtime 行为，那就是越界了 —— 这是你 review diff 时第一个要确认的点。

4 · 计划假设 vs 代码实证（我替你核对过了）

计划的核心前提是「当前工具面过于保守、过窄」。我让一个子 agent 去代码里逐条核实，结论是：这个前提只对了一半，而且计划点名的几样东西和代码对不上。实施 agent 如果照搬计划的措辞，盘点就会失真。

计划的说法 / 假设代码里的实情（已核实）结论
工具面「过窄」，像 toy 默认 scaffold simple_react 其实有 12 个工具：list_files / glob_files / read_file / read_tool_result_artifact / grep / symbol_search / update_working_state / edit_file / create_file / bash / run_tests / git_diff。结构化工具相当丰富，比「只给 Bash」的 mini-SWE-agent 在导航/搜索维度更强 部分成立
execute_bash 是「极窄安全子集」 是多层黑名单，禁管道/重定向/$(...)/任意命令，但允许 rg/grep/git status·diff·ls-files·grep/pytest/python -m pytest/受限 heredoc。说「窄」对，说「极窄到没法工作」夸张了 夸张了
盘点 patch_focused_react_mini_shell scaffold 这个 scaffold 不存在。真实存在的是 simple_react / patch_focused_react / patch_focused_react_execute_bash / patch_focused_react_diagnostic_shell / single_shot_patch / planner_coder_verifier 假设错误
权限拒绝可能只给一句纯文本，模型学不到恢复路径（计划 4.8 节的担忧） 已经是结构化的。command_policy.py 返回 reason_code / recovery_hint / safe_argv / policy_version 等字段。计划该「确认并复用」而不是当成缺失从零设计 已部分实现
diagnostic_shell 只是诊断侧通道，不进正式训练轨迹 属实。它不在默认工具表里，tool_surface_profile="persistent_diagnostic_session"，明确和 Stage 16A 的 execute_bash 分离 属实
缺 write_file / apply_patch / run_public_command / todo_write 属实，这四个确实不存在。但 create_file 是存在的（在默认表里）—— 别把它也算成缺失 属实
这意味着什么？ 真正的差距不是「工具太少」那么简单，而是更微妙的两点：①哪个 scaffold 是训练默认很关键 —— patch_focused_react 相比 simple_react 砍掉了 bash 和 create_file。如果训练默认用的是 patch-focused 这一系，那模型确实失去了「建文件」和「自由跑命令」的能力，这才是 gpt_advice 说「把 create_file 加回默认 scaffold」的由来。② 缺的是参数化公开测试 / 公开命令 / 多文件 patch这类「动态验证」能力，不是基础导航能力。请要求实施 agent 在盘点里如实写清这两点，不要用「工具太窄」一笔带过。

5 · 你需要重点检查 / 拍板的决策

绿 我认为合理，知情即可 黄 需要你确认方向 红 影响重大，强烈建议你明确表态

D1 盘点为主 + 只读 probe，不改代码行为 知情即可

决策 花一整个阶段做分析，期间不改任何工具行为。

最新版变化：新版（988 行）已不再是「纯纸面盘点」 —— 4.7 节要求跑少量只读可执行 probe（用现有 fixture 实测默认 scaffold 能否跑通「读→搜→改→patch→reward」、能否建文件、能否跑单个公开测试），但明确「不改 harness 行为、不放宽策略、不写真实训练数据」。这是个好改进：结论从此有代码实证撑腰，而不是主观判断。

支持：风险极不对称 —— 如果训练环境选错，后面几个 stage 的 RL（Stage 21–25）全白做，那是几百到上千 GPU 小时。先花几天分析便宜得多。

风险：分析瘫痪。20 份 JSON 报告很容易膨胀成「为了写报告而写报告」，拖延几周还没结论。

我的建议：接受这个阶段，但给它设一个时间盒（比如「2–3 天内出第一版 capability_gap_matrix + capability_probe + readiness_gate，其余报告可以后补」）。验收标准应盯「gap 矩阵、probe 实证和放行结论是否清晰可执行」，而不是「20 份 JSON 是否齐全」。
你 review diff 的第一红线没变：src/repo_harness/tools/、command_policy.py、runtime 行为都不该被改动，probe 只能读不能改。

D2 工具面四档 profile，swe_public_core 作主默认 确认方向

决策 计划预设了四档工具面，并暗示 swe_public_core 是未来主 RL 默认工具面：
profile定位
safe_structured_only当前的安全结构化基线，可保留，但不应再当主 RL 工具面
swe_public_core 候选主线读/搜/编辑/建文件/apply_patch/公开命令/diff/任务状态/artifact 回读
swe_public_extended更接近 Claude Code/Cursor：持久 shell、LSP、后台任务、子代理、MCP
redteam_restricted专门用来压力测试 reward hacking / 越权 / 泄漏

这其实是整个 16G 方向最关键的前瞻性设计，虽然 16G.0 名义上「不实现」，但它在这里就把目标钉死了。

✅ 你已表态：训练环境尽量贴近真实部署，靠确定性边界（而非削能力）防 reward hacking。这个北极星是对的，和 gpt_advice 里 Cursor Composer 的「训练≈评测≈部署」原则一致。
我的细化建议（已和新路线图吻合）：北极星不变，但分步走 —— core 先用无状态 run_public_command 拿干净、可复现、可审计的 reward 信号；持久 shell 放 swe_public_extended，等 Stage 18 轨迹 schema 和监控能 hold 住持久状态再升训练资格。理由是持久 shell 除了安全，还有「可复现性」和「轨迹 schema 复杂度」两个代价。完整辨析见「持久 shell 专题」。

D3 公开命令的路线岔口：run_public_command vs 升级 diagnostic_shell 影响重大

决策 让模型能跑「单个 pytest case / Django test label / import smoke / 项目脚本」这类定向公开测试，有两条路：
  • 路 A：新建一个结构化的 run_public_command(...) 工具（gpt_advice 力推这条）—— 返回值结构化、命令受 AST 校验、明确区分 public 命令和 hidden verifier
  • 路 B：把现有的 diagnostic_shell 从「诊断侧通道」升级成「正式训练工具」

计划把具体选哪条显式标成 open question 留给 16G.1，但「要解决这个能力缺口」这个框架在 16G.0 就定了。当前的事实是：run_tests 不接受参数（只能跑配好的全套），所以模型无法表达「只跑这一个失败的测试」 —— 这是 gpt_advice 和 gap 分析都认同的真实痛点。

最新版变化：新路线图其实把两条路排成了先后两步，不再是 either/or —— 16G.3 做无状态结构化命令（run_public_command / run_project_test / scratch_python），16G.4 才做 controlled 持久 diagnostic shell。这正好是我推荐的排序。

我的倾向（和你的 shell 决策连起来）：路 A（run_public_command）先行做主 RL 默认 —— 它把「public 可见 / hidden verifier 不可见」做成确定性规则，且无状态，reward 信号干净。持久 shell（路 B 的升级版）留到 16G.4 + extended profile。16G.0 阶段你只需确认：这个排序被如实记录，没有 agent 把持久 shell 提前塞进 core 默认。

D4 这个阶段会主动「卡住」真实训练 必须表态

决策 计划预设的放行闸门（stage17_readiness_gate）默认值是：
允许  Stage 17A：schema-only 工作（=true）
阻断  Stage 17B：真实数据冻结（=false）
阻断  Stage 20：warm-start 数据生产（=false）
阻断  Stage 21：正式 RL 训练（=false）

解锁条件是：16G.1 工具面设计完成 + 16G.2 实现并验证 + 16.5 代表性诊断（20–30 题）通过。翻译成大白话：你点头做 16G.0，就等于接受真实训练被推迟到工具面改造 + 诊断都做完之后。

✅ 你已拍板：接受延迟（选项①）。先把工具面改造 + 16.5 代表性诊断做扎实，再进真实数据冻结 / warm-start / RL。这符合 AGENTS.md「未通过代表性诊断前不冻结数据、不启动 RL」的原则。
对实施 agent 的含义：16G.0 的 readiness_gate 默认值（17B/20/21 = false）保持不变，不允许某个 agent 在没有 probe + gap 矩阵硬证据的情况下擅自把 17B 改成 true。

D5 失败样本要保留为训练负样本，不能默认过滤 确认原则

决策 权限拒绝、无效工具调用、patch 应用失败、坏命令、未知路径 —— 这些不能统统当噪声丢掉，要区分「模型行为 / 权限拒绝 / 基础设施失败 / harness 崩溃」，前者作为可学习的负样本/局部反馈保留。

同时划清两条边界：确定性硬失败（读 hidden verifier、读 gold patch、逃逸宿主文件系统、篡改测试、污染依赖、利用 git history）vs LLM-as-judge 监控（可疑 reward hacking、异常大 diff、假验证）。原则：LLM judge 只能当监控/审查/隔离/辅助奖励，绝不能当唯一安全边界 —— 真正的边界靠确定性 policy + sandbox + 路径隔离。

这是个好原则，我赞同。提醒一点：第 4 节已经发现 command_policy 已经返回结构化拒绝信息（reason_code / recovery_hint / safe_argv）。所以这块不是「从零造」，而是「盘点已有的、补齐缺的（比如 retryable 标志、negative-sample 落库）」。请让 agent 别把已有能力写成空白。

D6 必须先确定「哪个 scaffold 是 canonical 训练默认」 事实前提

决策 整个差距分析的结论强依赖一个事实：统一入口 run-episode-task 默认用的是哪个 scaffold？

因为 simple_react（有 bash + create_file）和 patch_focused_react（砍掉 bash + create_file）的能力差很多。如果默认是后者，那「模型能不能建新文件 / 跑命令」的答案完全不同。这是我这次核对时唯一没能从代码 100% 确认的关键事实，需要 16G.0 第一步就钉死。

给实施 agent 的硬要求：scaffold_capability_matrix.json 必须明确标出「哪个 scaffold 绑定为 run-episode-task / run_episode 默认」，并核对它声明的工具 == 构造出的 executor registry == 运行时注入的 registry（三层一致）。三层不一致是真实 bug 源（模型以为能调某工具，实际调不到）。

★ 持久 shell 专题（回应你的提问）

你问到「run_public_command 和持久 shell 的区别」「是不是已经实现了持久 shell」「训练贴近部署 + 靠其他手段防作弊是否合理」。我去代码里核实过了，下面是结论。

① 两者的本质区别：状态跨调用保不保留

维度run_public_command（目前不存在，16G.3 候选）持久 shell（persistent shell）
状态模型无状态、单发：每次调用 = 跑一条命令，独立进程会话累积：cwd / env / 后台进程跨调用保留
典型能力「给我这条公开命令的结构化结果」「调用1 cd src && export X=1，调用2 仍在 src、X 还在」
能否「装依赖→下一步用它」不能（每次新进程）能
reward 信号可复现性高（无累积状态）偏低（网络/时序/后台竞态）
可审计 / 轨迹 schema 难度低高（中断点 resume 难做）

② 你记得「已实现持久 shell」—— 对，但有关键 nuance

当前 diagnostic_shell 确实是「持久」的，backend 是 docker_persistent_container（生产）/ local_filesystem_persistent（测试），同题内多次调用复用同一容器。但它持久的是「工作区文件系统 + 容器」，不是「shell 会话状态」：

  • ✅ 调用1写的文件，调用2能看到（文件系统持久）
  • ❌ 调用1 cd subdir，调用2 回到根目录（cwd 每次重解析，adapter.py:631）
  • ❌ 调用1 export X=1，调用2 X 没了（每次新起 bash -lc，env 重置，docker_adapter.py:1481）

而且它被标成 invalid_for_training=True（除非 docker backend + 一长串 hygiene 全过 minimal.py:2521），所以现在是诊断侧通道，不进训练轨迹。execute_bash/bash 则完全无状态，连单次调用内的 cd x && pytest 都禁（&&/;/| 被拦，command_policy.py:824）。

准确现状：有「半持久」诊断 shell（文件持久、会话状态不持久、且不进训练），没有「真持久会话 shell」，正式训练工具几乎无状态。所以你担心的「跨调用持久化状态的命令会受限」是真实存在的，而且比直觉还紧一点。

③ 你的哲学「训练≈部署 + 用其他手段防 reward hacking」是否合理？

合理，是对的北极星。这正是 gpt_advice 里 Cursor Composer 的核心原则。把工具能力压窄来防作弊，本质是在优化一个错误环境。

但诚实地讲，持久 shell 除了「安全」之外还有两个代价（这不是反对你，是说明为什么我建议分步而非 core 直接上）：

  1. 可复现性代价：持久 shell（能装依赖、开后台进程）让同一条轨迹不可确定性复现 —— 装依赖有网络/时序，后台进程有竞态。RL 的 reward 需要干净可复现，否则信用分配被噪声污染。
  2. 轨迹 schema 复杂度代价：评测 worktree 差距分析 G12 已点出「任意中断点 durable resume 不完整」。持久跨调用状态会让 Stage 18 的 chunk / resume schema 明显更难做对。
我的结论（你已采纳的方向 + 细化）：北极星不变（extended profile 上持久 shell 对齐真实部署），但分步走 ——
• 主 RL 默认（core）先用无状态 run_public_command，拿干净、可复现、可审计的 reward 信号；
• 持久 shell 放 swe_public_extended，等 Stage 18 轨迹 schema + 监控能 hold 住持久状态再升训练资格。
这正是新路线图 16G.3（无状态结构化命令）先于 16G.4（controlled 持久 shell） 的排序 —— 不是「能力妥协」，是「先拿干净信号、再提保真度」。防作弊靠 4.9 节的确定性边界（沙箱 / 路径隔离 / 无网络 / 共享依赖只读 / 题间 session 重置 / 每次调用仍过 AST 扫描 / artifact hygiene），LLM-as-judge 只做监控，不当唯一边界。
