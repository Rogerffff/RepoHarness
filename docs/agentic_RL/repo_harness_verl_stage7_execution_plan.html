⚡ 核心目标流程：reward 必须在 EpisodeResult 返回前完成

这是 Stage 7 的铁律。runtime 不会先返回"看起来 succeeded 但没有 reward"的样本，再由后台补 reward。

⚡ VerifierWorkerPool 的双层 BoundedSemaphore 设计

这是 Stage 7 计划文档第 136-145 行最强调的安全约束：ThreadPoolExecutor(max_workers=N) 只限制运行的 worker，不限制内部队列长度，这等于没限流。Stage 7 必须用 admission semaphore 在进入 executor 之前就阻断超额请求。

① _admission_slots: BoundedSemaphore(max_workers + max_pending_jobs)

所有提交的 job 必须先抢这个 slot。这包括正在排队的和正在执行的。
抢不到 → queue_timeout，job 永远不会进 executor 队列。
cancellation / close 后必须 release，避免永久泄漏 admission 名额。

② _worker_slots: BoundedSemaphore(max_workers)

抢到 admission 后再抢 worker。worker_slots 用完时仍在 admission 内排队，但不会被 ThreadPoolExecutor 内部队列吞掉。
_worker_ids: SimpleQueue 维护稳定 worker id（"verifier-worker-0" / "verifier-worker-1" …），写入 VerifierJobResult。
关键测试：queue_timeout_happens_before_unbounded_executor_queue 显式证明超额 job 在进入 executor 之前就被拒绝，不会被 ThreadPoolExecutor 内部无界队列收下后再"假装超时"。

字段定义

cancellation 处置（实测能力声明）

场景处置
job 还在 admission queue 里（未抢到 admission_slot）cancellation 直接生效，admission_slot 释放，job 永远不会执行
job 抢到 admission，但还没抢到 workercancellation 生效，admission + 未占用的 worker_slot 释放

⑤ build_stage7_reward_boundary(...)

这个 helper 是 Stage 7 的语义核心。把"模型解决了任务"和"基础设施给不出可信结果"区分开。

def build_stage7_reward_boundary( *, final_verifier: VerifierResult | None, pool_result: VerifierJobResult | None = None, reward_metadata_ref: str, final_verifier_ref: str, patch_stats: dict[str, Any] | None = None, event_counts: dict[str, int] | None = None, source_refs: dict[str, Any] | None = None, reward_compute_seconds: float = 0.0, ) -> Stage7RewardBoundaryResult

5 步决策流程

  1. 合并 final_verifier 和 pool_result.verifier_result 来源（pool 模式下后者优先）。
  2. map_stage7_verifier_status(verifier, pool_result) → (status, status_reason)。
  3. 计算 invalid_for_training = status ∈ {invalid, invalid_task, infrastructure_error, cancelled, timeout, no_progress}。
  4. compute_reward_metadata(verifier, ...) → RewardMetadata。
    双层防护：如果 status 已经判 invalid，但 reward_metadata 还显示 valid → 用 model_copy(update={final_reward: 0.0, invalid_for_training: True}) 强制覆盖。
    如果 reward_metadata 自己判 invalid → status 也升级为 invalid。
  5. 注入 extra_fields：4–5 个 flat scalar / opaque ref（reward_metadata_ref / final_verifier_ref / pool_id / worker_id / queue_wait_seconds）。
