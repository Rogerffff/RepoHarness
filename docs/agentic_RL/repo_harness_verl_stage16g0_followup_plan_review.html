Stage 16G.0 Follow-up（基线契约）计划审查

审查对象：50-stage-16g-0-follow-up-baseline-contract-execution-plan.md（计划已写，尚未执行）　·　配套：16G.0 发现详解、完成态审查

一句话：这版补充计划正确地修正了我们一起发现的排序问题 —— 把「第一次认真对照 Claude Code / mini-SWE-agent」从 16G.5 提前到 16G.1 之前，避免 16G.1–16G.4 改完才发现对错了目标、返工。它还顺手修掉了我上次指出的两个弱点（Claude Code 那侧只引用导航文件、差距矩阵用模板话）。方向我赞成。

但有一个真实的不对称需要你拍板：Claude Code 的源码本地全在（可做一手契约），而 mini-SWE-agent 没有官方仓库源码，只有评测 worktree 里的配置 + 运行日志（二手 public-safe 摘录）。计划没指明这些文件在哪，agent 很可能退回到更弱的 gpt_advice 总结。这是第 4、5 节的核心。

1 · 这版补充计划要做什么

它是 16G.0 的补充验收阶段（不是重做）。同样零行为改动、不碰工具/策略/runtime。它新增 4 份 JSON 产物，把「目标工具环境」逐能力写成可审计的契约：

新增产物作用
stage16g0_claude_code_baseline_contract.jsonClaude Code 逐能力契约：每条能力的「模型怎么看见 / 怎么执行 / 权限怎么约束 / 结果怎么回流」，每条至少引用一个真实源码文件（不许全指向 AGENTS.md）
stage16g0_mini_swe_agent_baseline_contract.jsonmini-SWE-agent 的 Bash-first 基线，和 Claude Code 分开写，不混成笼统「真实 SWE agent」
stage16g0_per_capability_baseline_comparison.json 最核心27 项能力逐条三方对齐：Claude Code 基线 / mini-SWE 基线 / RepoHarness 现状 / gap_type / required_stage / 是否阻塞主 RL
stage16g0_stage16g_implementation_requirements.json把差距转成 16G.1–16G.5 的执行要求，明令不许推给 Stage 17

builder 还要加 3 个新检查：① 禁止 Claude Code 能力的证据全指向 AGENTS.md；② 禁止 5 条以上记录用完全相同的基线话术；③ 所有「阻塞主 RL」的项必须映射到 16G.1–16G.4，不能只挂到 16G.5 或 Stage 17。这三个检查正好把我上次担心的「模板化、推迟对照」用机器卡死。

2 · 为什么这是对的修正（你这次的判断很关键）

原来的排序里，16G.5 才第一次认真对照 Claude Code / mini-SWE-agent。问题是 16G.1（定 taxonomy）→16G.4（实现工具）都在 16G.5 之前。如果到 16G.5 才发现「我们补的 run_public_command 和 Claude Code 的 Bash 在权限/输出/恢复语义上对不齐」，前面四步就要返工。把基线契约提到 16G.1 之前，等于先定好「对齐标准」再动手 —— 这是标准的「先写验收标准、再实现」工程纪律。

而且它把对照拆成两个独立基线（Claude Code 的分层结构化工具环境 vs mini-SWE-agent 的稳定 Bash 闭环），这点很重要：你最担心的「连只给 Bash 的 mini-SWE-agent 都不如」是和 mini-SWE 比，「是否真实 Claude Code 风格能力」是和 Claude Code 比 —— 两个问题不能用一个笼统基线回答。计划把它们分开了。

4 · 我识别出的设计问题 / 风险

高 R1 · mini-SWE-agent 源指向不明确，agent 可能退回最弱证据

计划 §3.2 只笼统说「评测 worktree 已保存的 public-safe excerpt」，没点名具体文件。如果执行 agent 不知道那份 yaml 配置和 config excerpt 存在，会直接掉到优先级 3 的 gpt_advice 二手总结，然后把整个 mini-SWE 基线标成低置信。那样这次「和 mini-SWE 对照」就名存实亡。

建议（启动前必须告诉 agent）：明确指向评测 worktree runs/pre-verl-swebench-verified-score-gap-investigation-20260521T000000Z/ 下的 mini_swe_agent_*.yaml 和 public_source_mini_swe_agent_swebench_config_excerpt.txt 作为 tier-2 主证据；框架内部细节标 primary_source_verification_required=true。这样 mini-SWE 基线能到中高置信，而不是低置信。

中 R2 · RepoHarness 的战略立场被留成开放问题

§5.2 说 RepoHarness「可以选结构化工具优先，也可以把 Bash 拆成 run_public_command / scratch_python / controlled diagnostic shell」。但你其实已经定了：core 用无状态结构化公开命令、持久 shell 留 extended。如果不把这个决定写进基线对照和实现要求，对照表只会记录「RepoHarness 在自由 shell 上弱于 mini-SWE」，却不说明这是有意为之还是缺陷，16G.1 又得重新纠结一次。

建议：把你的立场作为显式设计假设写进 implementation_requirements 顶部 —— 「主 RL core 采用结构化公开命令优先，持久 shell 归 extended，靠确定性边界而非削能力防 reward hacking」。这样 mini-SWE 的 Bash-first 基线就被解读为「能力覆盖目标」而不是「实现形态目标」。

中 R3 · 4 份新产物不会被现有 acceptance_summary 的 sha256 绑定

第一轮的 stage16g0_acceptance_summary.json 用 sha256 绑定了 18 份报告，但它不知道这 4 份新文件。计划没说要更新它。结果：新证据游离在顶层验收之外，无法像第一轮那样「计数可复核、sha 可回查」。

建议：新增一份 stage16g0_followup_acceptance_summary.json，绑定这 4 份的 sha256，并保持第一轮 summary 不变（immutable）。或者在计划验收标准里加一条「更新或新建 acceptance summary 绑定 follow-up 产物」。

中 R4 · 16G.5 角色变了，但旧文档还把它写成「第一次对照」

这版计划 §9.3 明确 16G.5 此后只做改造后的实证 parity probe。但原 49-... 计划 §9 和我之前给你的发现详解 HTML 里，16G.5 还写着「Claude Code / mini-SWE-agent 对照诊断」，读起来像第一次对照。叙事不一致，接手的人会混淆。

建议：执行这版 follow-up 时，顺手把原 49 计划 §9 的 16G.5 描述改成「改造后实证 parity probe」，并在我那份发现详解里同步（我可以帮你改）。

低·知情 R5 · 基线契约从此成为 16G.1–16G.4 的「权威」

§9.1/§9.2 规定 16G.1–16G.4 的每个实现项都必须能追溯到一个 baseline comparison 的 capability_id。这是好纪律，但代价是：基线契约一旦写错或写薄，整条 16G 链都继承错误。所以这份 per_capability_baseline_comparison.json 是高风险高价值产物 —— 它产出后值得你（和我）认真复核一遍，而不是和其它 JSON 一样抽查。3 个 builder 检查能挡住机械错误，但挡不住「方向性判断错误」。

5 · 你需要做的决策

D-A mini-SWE-agent 的证据等级

本地拿不到官方仓库源码。你接受用评测 worktree 的配置 + 运行日志（tier-2）作为 mini-SWE 基线主证据、框架细节标注待官方源验证；还是要求先去 fetch 官方 mini-SWE-agent 仓库（需要网络/vendoring）再做？
