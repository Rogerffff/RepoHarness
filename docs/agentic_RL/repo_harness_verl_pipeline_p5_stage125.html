② Profile 1 · DataProtoPaddingProfile

测量什么

DataProto 的 batch 里有多少 token 是真实输出、多少是 padding。指导我们怎么调 prompt_length / response_length，避免大量算力浪费在 padding 上。

完整 schema · dataproto_profile.py:12

12│class DataProtoPaddingProfile(StrictBaseModel): 13│ schema_version: str = "repo_harness_verl_stage12_5_dataproto_padding_profile_v0" 14│ batch_size: int # batch 实际 size 15│ prompt_length: int # 被 pad 到的 prompt 上限 16│ response_length: int # 被 pad 到的 response 上限 17│ actual_prompt_tokens_p50: float # 实际 prompt token 50 分位 18│ actual_prompt_tokens_p95: float # 实际 prompt token 95 分位 19│ actual_response_tokens_p50: float 20│ actual_response_tokens_p95: float 21│ padded_token_ratio: float # 0-1：padding 占总 slots 比例 ★ 核心指标 22│ loss_mask_token_ratio: float | None # loss_mask 中非零比例 23│ response_mask_zero_ratio: float # response_mask 中 0 的比例（tool obs 占比） 24│ length_overflow_filtered_sample_count: int # 因长度超限被过滤的样本数 25│ diagnostics: list[str]

核心算法

28│def build_dataproto_padding_profile(data_proto, *, length_overflow_filtered_sample_count=0): 33│ batch = getattr(data_proto, "batch", {}) 34│ prompts = batch.get("prompts", []) 35│ responses = batch.get("responses", []) 36│ response_mask = batch.get("response_mask", []) 37│ attention_mask = batch.get("attention_mask") 38│ loss_mask = batch.get("loss_mask") 45│ 45│ # 用 attention_mask 算实际 prompt token 数（每行 sum） 45│ prompt_counts = _prompt_token_counts(attention_mask, batch_size=batch_size, prompt_length=prompt_length) 46│ response_counts = _row_sums(response_mask) 47│ total_slots = batch_size * (prompt_length + response_length) 48│ actual_tokens = sum(prompt_counts) + sum(response_counts) 49│ # ★ 核心公式：padding 占总 slot 比例 49│ padded_ratio = 0.0 if total_slots <= 0 else max(0.0, min(1.0, 1.0 - actual_tokens / total_slots))

用法

每个 batch 出 1 份 profile。若 padded_token_ratio > 0.5 说明 prompt/response 上限设置可能过大，可调小；若 actual_response_tokens_p95 接近 response_length，只能说明高分位样本已经接近长度上限，存在截断风险，不能推出 99% 的样本都被截断。

③ Profile 2 · InferenceServerProfile

测量什么

vLLM / SGLang 推理服务的性能指标：prefill 阶段耗时、decode 阶段耗时、queue wait、tokens-per-second 吞吐、prefix cache 命中率、KV cache 抢占数、GPU 利用率。Stage 12.5 同时记录 metric 来源（Prometheus 抓取 / client-side 估算），避免读到错的指标。

⑥ Profile 5 · Stage125BatchRefillReport

测量什么

batch 中可能有大量无效样本（缺 logprob / timeout / infrastructure error / 长度超限）。Stage 12.5 提供 batch refill 机制：分类每条样本，剔除无效的，可选重采样补齐。最终生成可审计的 SampleClass 分类报告。

⑧ Stage 12.5 集成时序

这里讲的是 Stage 12.5 profile helper 和 evidence 验收如何围绕真实训练链路工作。它们用于诊断和验收，不是 RepoHarness 与 verl 之间的训练样本主契约，也不要理解成每条 episode 返回时必然同步写出 5 个文件。

[episode 跑完 EpisodeResult 返回 verl AgentLoopOutput] ↓ [verl postprocess → DataProto] ↓ [Stage 12.5 profile / evidence helper] ├─ build_dataproto_padding_profile(data_proto) → dataproto_padding_profile.json ├─ build_inference_server_profile(prom_text or client_records) → inference_server_profile.json ├─ build_ray_worker_resource_profile(...) → ray_worker_resource_profile.json ├─ build_tokenization_profile(records) → tokenization_profile.json └─ build_refill_report(classifications, policy) → batch_refill_resample_report.json ↓ [trainer step 完成] ↓ [Stage 12.5 verifier/recorder/tool hot path 报告] └─ verifier_recorder_tool_hot_path_report.json ↓ [visibility + batch validation] └─ visibility_and_batch_validation_report.json ↓ [Stage 12.5 final acceptance] ├─ check_stage12_5_evidence_bundle(bundle_dir, scope="remote") # 应该收齐 14 文件 ├─ 跑 formal batch validator（每条 valid 样本 route=verl） ├─ 跑 visibility check（extra_fields 全 allowlist） ├─ 跑 cache validation（snapshot / dependency env cache_hit 命中验证） └─ build_stage12_5_acceptance_summary(...) # acceptance_ready = True ? ↓ [acceptance_ready = True → 同步基线通过，可进入后续异步改造]

Stage 12.5 完成后的能力

依赖环境复用 在共享 cache_root、相同依赖规格、相同 dependency cache key 的前提下，1000 条 episode 跑同一 task 时，pip install 理论上只需要跑 1 次（参考 Page 1 时间账）。
瓶颈定位 5 个 profile 报告能精确指出训练 wall time 的去处：模型 / tokenizer / verifier / workspace / artifact 各占多少。
batch 完整性 invalid 样本不再悄悄进 trainer，refill report 显示分类统计。
不放松安全 所有 Stage 0H–12 的训练安全规则保持。无 trick，吞吐提升来自真实复用而非"关 verifier"。
