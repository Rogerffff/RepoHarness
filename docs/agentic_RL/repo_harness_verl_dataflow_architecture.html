verl 只提供 server 能力

adapter 不重建 server，不管理参数同步，只调用既有 server manager。

RepoHarnessRuntime + VerlLLMGateway

第一次把 messages 通过 chat template 转成 prompt_ids_0，并调用 LLMServerClient.generate(...)。

输入：LLMGatewayRequest 输出：LLMGatewayResponse 底层：TokenOutput(token_ids, log_probs)

连续 token 流开始

保存真实 generation 路径上的 prompt ids 和 output token ids。

解析工具调用，执行 RepoHarness 工具，再把工具观察编码成 token ids
4. 工具执行

verl 不执行工具

verl 只负责 rollout 调度和模型服务。软件工程工具由 RepoHarness 管理。

RepoHarness tools / workspace

根据模型输出解析出的 function name 和 JSON args 执行工具，例如 read_file、edit_file、run_tests。

输入：tool_name + JSON args 工具层输出：tool_result_text 随后由 tokenizer helper 生成：tool_response_ids

mask 规则写入

模型输出 token 是训练目标，工具观察 token 是上下文，不是训练目标。

LLM token: mask=1 tool observation token: mask=0
第二轮 generate 的输入不是 messages，而是上一轮拼好的整条 token 流
5. 第二次生成

同一个 request_id

使用同一个 episode_id 作为 sticky session id，便于 prefix cache 和审计追踪。

LLMServerClient.generate(...)

第二轮直接传入完整 token prefix：初始 prompt + 第一轮 LLM token + 工具观察 token。

输入：prompt_ids=continuous_token_stream 输出：output2.token_ids

追加最终回答或 patch

如果这一轮没有工具调用并触发结束，就把最终模型 token 加入 response。

final LLM token: mask=1
终止后跑 verifier 和 reward，但 verifier/reward 结果不进入 token 流
6. 验证与组装

verl 等待结果

第一版是 episode 内 blocking wait，返回时 reward 已经确定。

Verifier + reward + recorder

对最终 workspace / patch 运行 final verifier，计算 reward，写 transcript、events、artifact manifest 和 audit ref。

输出：reward_score 输出：audit_ref / verifier_summary

AgentLoopOutput

把连续 token 流切成 verl 需要的字段。verl 后处理可以把 reward_score 写到 rm_scores 的最后一个有效 response token 位置，但 reward 不是 token，也不是模型可见文本。

prompt_ids response_ids response_mask reward_score + extra_fields.audit_ref
AgentLoopWorker 把 batch 内多条 AgentLoopOutput pad 成 DataProto，再交给 actor worker 训练
7. PPO 训练

AgentLoopWorker batch merge

合并 N 条 AgentLoopOutput，补齐长度，形成 verl 训练批次。

RepoHarness 不参与 loss

RepoHarness 只提供轨迹、mask、reward 和审计引用。

FSDP / Megatron Actor Worker

对 prompts ⊕ responses 前向，计算新的 log probabilities，并用 PPO objective 更新模型。

Tensor[B, prompt_len] Tensor[B, resp_len] mask=0 的工具 token 不进 loss

完整正例链路：一条 SWE 任务的两轮模型生成

下面按一条 SWE 任务讲清楚数据形态。这个例子和你给出的链路一致：第一轮模型输出工具调用，RepoHarness 执行工具并把工具观察放回上下文；第二轮模型输出最终 patch 或 final answer 并终止。如果真实任务有第二次、第三次工具调用，只需要重复“模型 token 段 + 工具观察 token 段”的模式。

PPOTrainer / dataloader 产出模型可见 prompt

输入是一条 SWE dataset row，例如 repository、base commit、issue 描述和任务 id。输出是 messages 或 raw_prompt，仍然是文本形态。

[
  {"role": "system", "content": "..."},
  {"role": "user", "content": "Fix bug in foo.py"}
]

AgentLoopWorker 调用 RepoHarnessVerlAgentLoop.run(...)

传入 verl sample、sampling_params 和 agent loop config。这个阶段仍然没有训练张量，也还没有 workspace 工具执行。

构造 RepoHarnessEpisodeRequest，并准备第一次模型调用

RepoHarnessVerlAgentLoop 负责把 verl sample/config 映射成 RepoHarnessEpisodeRequest。字段细节由共享 Contract 页面定义，这里只关心跨模块对象边界。

prompt_ids_0 = tokenizer.apply_chat_template(
    messages,
    tools=tool_schemas,
    add_generation_prompt=True,
)
# 形态：list[int]，例如长度为 312
# 记录：GenerationRecord.prompt_ids = prompt_ids_0

第一轮调用 LLMServerClient.generate(...)

真正传给 verl server 的是 prompt_ids_0，不是 messages。返回是 TokenOutput，里面有模型输出 token、log probabilities 和停止原因。

output1 = await llm_server_client.generate(
    request_id=episode_id,
    prompt_ids=prompt_ids_0,
    sampling_params={...},
)
# output1.token_ids: list[int]，例如长度为 87
# output1.log_probs: list[float]
# output1.stop_reason: "tool_call_detected"

解析工具调用并执行 RepoHarness 工具

工具解析可以为了拿到 function name 和 JSON args 做最小 decode，但正式训练 token ids 不动，也不把整段 transcript 重新 decode 后再 encode。工具执行本身是纯字符串和文件系统操作，不需要 tokenizer。

tool_calls = tool_parser.extract_tool_calls(output1.token_ids, tool_schemas)
tool_result_text = await harness.run_tool("read_file", {"path": "foo.py"})
# tool_result_text 是字符串，例如 "def foo():\\n    return None\\n..."

把新的工具观察 encode 成 token ids，并拼接连续 token 流

这里的 encode 只针对“新产生的工具观察文本”，不是把旧 transcript 重来一遍。工具观察会成为下一轮模型能看到的上下文，但它不是模型自己生成的训练目标，因此 mask 为 0。

tool_response_ids = tokenizer.apply_chat_template(
    [{"role": "tool", "content": tool_result_text}],
    add_generation_prompt=True,
    remove_system_prompt=True,
)
# 形态：list[int]，例如长度为 412

continuous_ids = prompt_ids_0 + output1.token_ids + tool_response_ids
response_mask = [1] * 87 + [0] * 412
if output1.log_probs is not None:
    response_logprobs = output1.log_probs + masked_placeholder_for_tool_tokens
else:
    response_logprobs = None
# 工具 token 的 placeholder 只在 mask=0 时占位；不能伪装成可训练 log probability。

第二轮模型调用直接使用连续 token 流

第二轮不再传 messages，而是传入上一轮已经拼好的 continuous_ids。同一个 episode_id 作为 sticky session id，便于 prefix cache 和审计关联。

output2 = await llm_server_client.generate(
    request_id=episode_id,
    prompt_ids=continuous_ids,
    sampling_params={...},
)
# 输入长度示例：312 + 87 + 412 = 811
# output2.token_ids: list[int]，例如长度为 142，包含 patch 或 final answer

终止后切片，组装 AgentLoopOutput

初始 prompt 留在 prompt_ids，后面的模型 token 和工具观察 token 放在 response_ids。response mask 长度必须和 response ids 相同。

prompt_ids = continuous_ids[:312]
response_ids = continuous_ids[312:] + output2.token_ids
response_mask = [1] * 87 + [0] * 412 + [1] * 142
if response_logprobs is not None and output2.log_probs is not None:
    response_logprobs = response_logprobs + output2.log_probs
else:
    response_logprobs = None
# 如果任一模型生成阶段没有可用 log probability，整体按缺失处理并记录原因。

跑 verifier、计算 reward，但不把 reward 放回 token 流

verifier 读取最终 workspace、patch、测试结果和任务验证计划，输出 reward_score、verifier_summary 和 audit_ref。这些是训练 label 和审计引用，不能让模型看到，也不能进入 response_ids。verl 后处理可以把 reward_score 转成 rm_scores，并放在最后一个有效 response token 的位置。

return AgentLoopOutput(
    prompt_ids=prompt_ids,
    response_ids=response_ids,
    response_mask=response_mask,
    response_logprobs=response_logprobs,
    reward_score=reward,
    metrics=AgentLoopMetrics(...),
    extra_fields={"audit_ref": audit_ref, "episode_id": episode_id},
)

连续 token 流：哪些 token 训练，哪些 token 只做上下文

verl 最终训练主路径看到的是 token ids 和 mask。工具观察 token 仍然在上下文里，因为后续模型生成需要读到工具结果；但是工具观察不是模型自己生成的 token，因此不能作为 policy loss 的 target。注意，进入 padded batch 后，padding token 的 mask 也会是 0，所以需要区分“未 padding 的工具观察 mask=0”和“padding 后的补齐 token mask=0”。

prompt_ids 初始 system + user prompt，例如 312 token。 不属于 response loss。
LLM round 1 模型输出工具调用，例如 87 token。 response_mask = 1。
tool observation 工具返回文本 encode 后，例如 412 token。 response_mask = 0。
LLM round 2 最终 patch / final answer，例如 142 token。 response_mask = 1。 
AgentLoopOutput.prompt_ids
  = prompt_ids_0

AgentLoopOutput.response_ids
  = output1.token_ids
  + tool_response_ids
  + output2.token_ids

AgentLoopOutput.response_mask
  = [1] * len(output1.token_ids)
  + [0] * len(tool_response_ids)
  + [1] * len(output2.token_ids)

AgentLoopOutput.response_logprobs
  = output1.log_probs
  + masked_placeholder_for_tool_tokens
  + output2.log_probs

上面这一行只描述 log probabilities 可用时的理想形态。若 provider 或 verl server 没有返回某一轮 log probabilities，response_logprobs 应为 None 或带明确缺失原因，不能为了凑字段而伪造可训练 log probability。

如果真实任务有两次工具调用，形态就是：prompt_ids 后面接 LLM1(mask=1)、tool1(mask=0)、LLM2(mask=1)、tool2(mask=0)、LLM3(mask=1)。规则不变：模型生成 token 训练，工具观察 token 只作为上下文。

进入 PPO 训练时发生什么

到训练阶段，参与 actor forward 和 PPO loss 的主路径是 padded Tensor。与此同时，raw_prompt、extra_fields、audit_ref 等非张量字段仍可能随 DataProto.non_tensor_batch 传播，所以它们也必须经过 visibility 检查，不能包含 hidden verifier、gold patch、reward metadata 明文或 accepted label。 

batch["prompts"]            : Tensor[B, prompt_len]
batch["responses"]          : Tensor[B, resp_len]
batch["response_mask"]      : Tensor[B, resp_len]
batch["rollout_log_probs"]  : Optional[Tensor[B, resp_len]]
batch.non_tensor_batch      : raw_prompt / extra_fields / audit refs

new_log_probs = actor.forward(prompts concat responses)

if rollout_log_probs is not None:
  ratio = exp(new_log_probs - rollout_log_probs)
  loss = -min(ratio * advantage, clip(ratio, 1 - eps, 1 + eps) * advantage)
  loss = loss * response_mask

# response_mask=0 的工具观察 token 不贡献 policy loss。
AgentLoopOutput.response_logprobs 是可选字段。只有它存在并且长度与 response_ids 对齐时，才应该进入 DataProto.batch["rollout_log_probs"]。正式在线训练如果依赖 rollout log probabilities，必须显式开启、记录并校验；调试路径可以让它为 None，但不能把缺失的 log probability 伪装成有效训练字段。
一句话总结：RepoHarness 负责产生真实软件工程环境中的轨迹、工具观察、patch、verifier reward 和审计引用；verl 负责把这些轨迹变成 token Tensor，并按照 response mask 只训练模型自己生成的 token。两者通过 RepoHarnessEpisodeRequest、LLMGateway、TrainingView 和 AgentLoopOutput 解耦。
