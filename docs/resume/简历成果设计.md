我的判断很明确：**即使暂时不做大规模 SWE RL，RepoHarness 仍然非常有意义；但你必须把“项目结果”从“模型分数提升”转成“Agentic RL 数据与环境基础设施的可量化证据”。**

对吸引大厂面试官来说，**一个严谨、可复现、可审计、能接 verl 的 SWE agent harness，比一个算力不足下勉强跑出来的微弱 RL 分数更有说服力**。不过，最好还是补一个很小的 RL proof-of-concept：不一定在完整 SWE-bench Lite 上训练，而是在小型可执行 repo task / SWE-smith 子集 / 自造 micro-SWE 环境上证明你的 RepoHarness 能闭环接入 verl。

---

## 1. 不做大规模训练，这个项目是否还有意义？

有，而且意义不小。

这些大厂文章反复强调的核心点之一就是：**Agentic RL 的瓶颈不只是训练算法，而是 Agent runtime、环境、轨迹、verifier、reward、防污染、异步 rollout、样本过滤这些基础设施。** Forge 把 Agent 抽象成 trajectory producer，并通过 Gateway Server / Data Pool 把 Agent 和训推引擎解耦；ROLL/ROCK 则把训练、环境执行、Agent CLI 拆成不同组件；这些都说明“harness / environment / trajectory data plane”本身就是 Agentic RL infra 的核心组成部分，而不是附属代码。 

你的 RepoHarness 当前最像这几类系统中的：

```text
Agent Runtime + SWE Environment + Verifier/Reward + Trajectory Data Plane
```

而不是：

```text
完整大规模 RL Trainer + Rollout Scheduler + KV Cache System
```

所以如果你不做大规模 RL，项目仍然可以成立，但你需要把结果表达成：

> 我构建了一个面向 Agentic Post-training 的 SWE agent execution harness，能够生成可复现、可审计、可过滤、可接入 RL/SFT/preference 训练的轨迹，并通过严谨的 verifier 与 contamination control 保证 reward 可信。

这和文章里强调的“环境清洁度、测试可信度、false positive 过滤、final verifier 隔离、trajectory producer 解耦”是同一个方向。ROLL 相关材料甚至把环境污染、测试泄露、false positive 看成会系统性毒化 RL 的问题，而不是普通工程瑕疵。

---

## 2. 但是，只展示代码而没有数字是不够的

如果目标是吸引大厂面试官，RepoHarness 不能只停留在：

```text
我实现了 task adapter / Docker workspace / verifier / export
```

你需要把它量化成几个维度的结果。

我建议你至少做四类指标。

---

## 3. 第一类结果：benchmark correctness / verifier 可信度

这是 RepoHarness 最应该优先量化的部分。

SWE-bench 官方说明，评估流程本质上是：设置 Docker 环境、应用模型生成的 patch、运行测试、判断 patch 是否解决 issue；官方也列出了常见评估指标，包括 total、submitted、completed、resolved、unresolved、empty patches 等。([SWE-bench][1]) SWE-bench 官方仓库也说明现在使用 Docker 做更可复现的评估，并给出了在 SWE-bench Lite 上运行 evaluation harness 的方式。([GitHub][2])

你可以做一份 **RepoHarness Verifier Correctness Report**，包括：

| 指标                               | 你要证明什么                                                   |
| -------------------------------- | -------------------------------------------------------- |
| gold patch replay pass rate      | 官方 gold patch 在 RepoHarness formal verifier 中能否通过        |
| no-op fail rate                  | 不做修改是否会失败，防止 false positive                              |
| strict patch replay success rate | agent workspace 里的 patch 能否在独立 verification workspace 重放 |
| verifier determinism             | 同一 patch 多次验证结果是否一致                                      |
| hidden artifact leakage rate     | hidden tests、gold patch、reward metadata 是否进入模型上下文        |
| evidence hash drift rate         | summary / audit report 与真实 evidence refs 是否一致            |
| invalid sample block rate        | diagnostic-only / skipped / contaminated 样本是否被导出拦截       |

这类结果即使没有 RL，也非常有价值，因为它直接证明你的 harness 是训练数据可信性的基础设施。

面试官看到这类报告，会知道你不是在写一个“能跑工具的 agent demo”，而是在做真正 Agentic RL 需要的 **reward integrity infrastructure**。

---

## 4. 第二类结果：agent evaluation 分数

你仍然应该跑一些 SWE-bench evaluation，但不要一开始就把“训练提升”作为目标。

SWE-bench Lite 官方定位就是低成本、快速迭代的评测子集，包含 300 个任务，并且官方明确建议在 compute efficiency 是 concern 时报告 SWE-bench Lite，而不是 full SWE-bench。Lite 页面还提到有 23 个 development instances，可用于 active development。([SWE-bench][3]) SWE-bench Verified 则是 500 个经过人工验证的实例，目的是提供更可靠的 coding agent / LM 评估。([SWE-bench][4])

你可以做三档 evaluation：

```text
Tier 0: 23 SWE-bench Lite dev instances
Tier 1: 50-100 个 curated SWE-bench Lite tasks
Tier 2: 完整 300 SWE-bench Lite
```

指标不要只报 resolved rate，还要报：

```text
pass@1 resolved rate
completed rate
empty patch rate
patch replay failure rate
formal verifier failure rate
environment setup failure rate
mean / p50 / p95 episode time
mean / p95 tool calls per task
mean / p95 generated tokens per task
mean / p95 verifier time
contamination-denied sample count
```

如果你用同一个模型，比较 RepoHarness 和 mini-SWE-agent / SWE-agent / OpenHands 的表现，结果会更有说服力。SWE-bench 官方 experiments 仓库也鼓励提交或查看 reasoning traces，并说明如果系统涉及 best@k / 多次 rollout，trajectory 应该反映所有 rollouts 和选择机制。([GitHub][5]) 这正好和你的 trajectory store / acceptance bundle 设计对齐。

你不一定要打到 leaderboard 高分。你要证明的是：

> RepoHarness 能稳定、无泄漏、可审计地跑完整 SWE evaluation，并产出训练可用轨迹。

---

## 5. 第三类结果：系统吞吐与长尾分析

这部分会非常贴合大厂 Agentic RL infra 的关注点。

文章里反复提到 rollout 是 Agentic RL 的主要瓶颈，短 episode 和长 episode 差异极大，严格同步会被长尾拖住，纯 greedy 异步又会产生分布偏移。Forge 用 Windowed FIFO 控制吞吐和分布偏移之间的 trade-off，ROLL/slime 走异步 sample buffer，Seer 则在同步语义下拆细 rollout。 

你可以不训练模型，先做一个 **RepoHarness Rollout System Report**：

```text
并发 worker 数: 1 / 2 / 4 / 8 / 16 / 32
任务集: SWE-bench Lite dev / curated 50 tasks
模型: 同一个 API model 或本地 model
```

报告这些指标：

```text
episode throughput: tasks/hour
p50 / p90 / p95 / p99 episode latency
tool execution latency breakdown
Docker setup latency breakdown
verification latency breakdown
agent LLM latency breakdown
container reuse / cleanup success rate
failure reason distribution
retry recovery success rate
resume success rate
artifact write overhead
```

再额外做一个“长尾调度模拟”或真实实验：

```text
同步 batch barrier:
  等所有 task 完成再汇总

first-finish-first-consume:
  谁完成谁进入 export queue

windowed / bounded queue:
  限制过早消费快样本
```

即使你不改 verl，只在 RepoHarness runner 层做这个实验，也很有价值。因为它直接展示你理解 Agentic RL rollout 的核心问题：**不是平均速度，而是长尾、环境失败、样本分布和训练可用性。**

---

## 6. 第四类结果：training-readiness，而不是一定要 SOTA training

这类结果最适合你的项目定位。

你可以展示：

```text
1. 生成 N 条完整 SWE trajectory
2. 每条 trajectory 有 token/action/tool/verifier/failure metadata
3. export 为 SFT / RL / preference JSONL
4. 每条 export 都能追溯到 evidence bundle
5. diagnostic-only / invalid / contaminated 样本被自动拦截
6. verl adapter smoke test 能消费这些 trajectory
```

也就是说，量化：

```text
export success rate
export rejection reason distribution
trajectory replay success rate
schema validation pass rate
token/action span coverage
tool_call/tool_result pairing coverage
loss_mask coverage
reward metadata completeness
policy_version / rollout metadata coverage
```

这会非常贴近 Forge / slime 强调的 TITO、Gateway、Data Pool、Agent 作为 trajectory producer 的方向。Forge 明确说复杂 Agent 中 TITO 和上下文管理会导致 token 一致性工程成本很高；slime / GLM 方向也强调 rollout token metadata 需要被训练侧直接消费，而不是事后从文本重建。

## 7. 是否应该找小 SWE 数据集训练一下？

**最好做，但不要把完整 SWE-bench Lite 当作训练集。**

如果你在 SWE-bench Lite 上训练，再在 SWE-bench Lite 上报 resolved rate，面试官会非常警惕 contamination。SWE-bench Lite 是官方评测子集，300 个任务用于更低成本评估；它另有 23 个 dev instances 可用于开发。([SWE-bench][3])

更推荐的做法是：

```text
训练:
  SWE-smith 子集 / SWE-Gym / 自造 micro-SWE tasks / 你自己从 repo 生成的任务

评估:
  SWE-bench Lite dev 23
  curated SWE-bench Lite 50
  完整 SWE-bench Lite 300
  可选 SWE-bench Verified 子集
```

SWE-smith 很适合你，因为它本身就是面向训练 SWE agents 的工具和数据方向。SWE-smith 官方介绍说它可以把 GitHub repo 转成 SWE-gym，创建 file localization、program repair、SWE-bench 风格任务，并提供 SWE-agent 训练流程；项目介绍还提到生成了 50k+ task instances，用于训练 SWE-agent-LM-32B。([SWE Smith][6])

所以，如果你想快速做训练结果，我建议：

```text
不要：直接训练 SWE-bench Lite，然后报 Lite 提升
要：用 SWE-smith / 自造 repo tasks 训练，在 SWE-bench Lite 上做 held-out eval
```

## 8. 你这 8 卡 96GB 算力够不够？

如果你说的是 RTX PRO 6000 Blackwell 96GB，那么这不是“没有算力”，而是一个很不错的小型实验集群；NVIDIA 官方产品页说明 RTX PRO 6000 Blackwell 配备 96GB GDDR7 显存。([NVIDIA][7])

但它仍然不适合把目标定成：

```text
训练一个真正强的 SWE agent，在 SWE-bench Lite/Verified 上显著超过开源 SOTA
```

原因不是 GPU 显存一个维度。SWE agent RL 的成本主要来自：

```text
长 episode
多轮 LLM 调用
Docker setup
pytest / build / install
repo checkout
环境恢复
verifier
失败重试
长尾同步等待
多 rollout sampling
训练/rollout 权重同步
```

对 SWE RL 来说，**CPU、内存、SSD、Docker cache、网络、环境调度** 往往和 GPU 一样重要。8 卡 96GB 可以跑很好的 prototype，但不要用它挑战 frontier-scale SWE RL。

我会按下面这样规划：

| 目标                                       | 是否适合 8×96GB | 建议                             |
| ---------------------------------------- | ----------: | ------------------------------ |
| RepoHarness evaluation / verifier report |        非常适合 | 优先做                            |
| SWE-bench Lite 300 pass@1 eval           |          适合 | 可用 API model 或本地 model         |
| 7B/14B local coder model LoRA/SFT        |          适合 | 快速出训练结果                        |
| 7B/14B 小型 online RL                      |          适合 | 用 micro-SWE / SWE-smith subset |
| 32B full online SWE RL                   |        勉强且慢 | 不建议作为快速目标                      |
| 70B+ agentic RL                          |         不现实 | 不作为项目目标                        |

## 9. 最推荐的快速路线：不要一上来做完整 SWE RL

我建议你按这个路线做，最能快速产生“可展示结果”。

### 阶段 A：先做 RepoHarness Benchmark Report

目标：证明 harness 本身可靠。

用 23 个 SWE-bench Lite dev instances + 50 个 curated Lite tasks。

产出：

```text
gold patch replay pass rate
no-op fail rate
formal verifier determinism
strict patch replay success rate
hidden leakage check
artifact hash check
failure taxonomy
Docker phase coverage matrix
```

这一步最快，也最稳。

---

### 阶段 B：跑模型评测，不训练

目标：证明 RepoHarness 能做真实 SWE agent eval。

选择 2-3 个模型：

```text
一个强 API model
一个中等 API model
一个本地 coder model
```

每个模型跑：

```text
23 dev
50 curated Lite
可选完整 300 Lite
```

产出：

```text
resolved rate
completed rate
empty patch rate
avg tool calls
avg tokens
p50/p95 latency
failure distribution
trajectory samples
```

这里你甚至可以把 RepoHarness 和 mini-SWE-agent 做同模型对比。SWE-bench 官方 leaderboard 也提供 mini-SWE-agent 视角，并说明 Verified 可用于比较不同 LMs 在 minimal bash environment 下的表现。([SWE-bench][4])

这类结果会非常直观。

---

### 阶段 C：接 verl，但先做 smoke test + micro-RL

目标：证明你的 RepoHarness 能接 RL 框架，而不是只会 offline eval。

实现：

```text
RepoHarnessVerlAgentLoop(AgentLoopBase)
VerlLLMGateway
GenerationRecord
AgentLoopOutput conversion
```

先不要跑完整 SWE-bench RL。做一个 micro-SWE 环境：

```text
小型 Python repo
单文件 bug
确定性 pytest
无外部依赖
每个任务 1-5 分钟内完成
100-500 train tasks
50 held-out eval tasks
```

训练一个 7B/14B coder model 的 LoRA 或轻量 adapter。

指标：

```text
reward curve
resolved rate before/after
tool misuse rate before/after
invalid patch rate before/after
empty patch rate before/after
avg episode length before/after
verifier pass rate before/after
```

这足以证明：

> RepoHarness 不是只能评测，它可以进入 online agentic RL pipeline。

---

### 阶段 D：再尝试 verl fully_async_policy

verl 的 fully async policy 文档说，它把 Trainer 和 Rollouter 完全解耦，支持 asynchronous sample generation / training、streaming、freshness control 和 partial rollout；核心组件包括 Rollouter、MessageQueue、Trainer、ParameterSynchronizer。文档还说明当前支持 megatron/fsdp + vLLM，并且 vLLM 需要使用基于 AgentLoop 的 server mode。([Verl Documentation][8])

这对你的 RepoHarness 是好消息，因为你前面设计的：

```text
RepoHarnessVerlAgentLoop
  -> RepoHarnessRuntime
  -> VerlLLMGateway
```

本来就是 AgentLoop 入口。fully_async 外层变了，RepoHarnessRuntime 可以基本不变。

但第一版不要直接开 partial rollout。verl 文档里说 `partial_rollout=True` 会在参数同步时中断正在生成的 rollout，参数同步后继续生成；这能减少等待 active tasks 完成的时间。([Verl Documentation][8]) 对 SWE harness 来说，这要求你能可靠保存和恢复 Docker workspace、context revision、tool state、trajectory state、artifact refs。你虽然已经有 interrupted checkpoint / resume manifest，但我建议：

```text
先 fully_async + partial_rollout=False
再实现 pause/resume stress test
最后 partial_rollout=True
```

## 10. 8 卡下的具体训练建议

如果你想快速出结果，我建议不要从 32B 起步。

### 方案 1：最稳

```text
模型: 7B coder model
训练: LoRA / QLoRA / PEFT
任务: 100-500 micro-SWE train tasks
评估: 50 held-out micro-SWE + 23 SWE-bench Lite dev
GPU: 2-4 张 rollout，2-4 张 train，剩余视资源调整
```

目标不是高分，而是漂亮的 learning curve。

你要展示：

```text
step 0 resolved: 12%
step N resolved: 25%
invalid patch: 30% -> 15%
tool misuse: 20% -> 8%
avg turns: 18 -> 12
```

即使分数不大，也能说明 RL pipeline 有效。

### 方案 2：更贴近 SWE

```text
模型: 14B coder model
训练: LoRA
任务: SWE-smith 子集 / 自建 repo tasks
评估: curated SWE-bench Lite 50
GPU: 4 rollout + 4 trainer
```

这个比 7B 更有展示价值，但调参时间更长。

### 方案 3：如果你想展示“数据基础设施”更强

```text
API teacher / strong local model 生成 1k-5k trajectories
RepoHarness 过滤、审计、导出
7B/14B student 做 SFT
held-out micro-SWE / Lite dev eval
```

这比 online RL 更容易快速得到稳定结果，也更适合展示你的 trajectory data plane。

### 方案 4：不要优先做

```text
完整 SWE-bench Lite online RL
同一 task 多 rollout GRPO
32B+ full parameter online RL
partial rollout + full async + long context 一起上
```

这几个同时做，工程风险很高，很可能花很多时间却没有漂亮结果。

## 14. 我的最终建议

不要把目标定成：

```text
用 8 卡训练出一个强 SWE agent
```

这个目标太容易失败，也不公平。

应该把目标定成：

```text
用 8 卡和有限时间，证明 RepoHarness 是一个可靠的 SWE Agentic RL 数据与环境基础设施；
同时用一个小规模 online RL 实验证明它能接入 verl 形成训练闭环。
```

更具体地说：

1. **SWE-bench Lite 用来评估，不要用来训练后再报 benchmark。**
2. **训练用 SWE-smith subset / micro-SWE / 自建 repo tasks。**
3. **优先做 verifier correctness、contamination control、trajectory audit、failure filtering、latency breakdown。**
4. **接 verl 做 thin adapter，不要一开始重写 fully async server。**
5. **小规模 RL 只需要证明 reward 能涨、工具错误能降、held-out 能提升。**
6. **把项目定位成 Agentic RL infra，不是模型 SOTA 训练。**

如果从大厂面试官视角看，一个完成度高的 RepoHarness 项目最有吸引力的地方不是“你用有限算力训练了多强的模型”，而是：

> 你证明了自己理解并实现了 Agentic RL 最难落地的部分：真实环境、可信 reward、可审计轨迹、failure filtering、训练接口和 rollout 解耦。
