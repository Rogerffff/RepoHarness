RepoHarness Stage 1 学习资料

RL Schema、Pydantic 校验与 Python 项目规范

这篇讲义面向 Stage 1 新增的 src/repo_harness/rl/ 代码。它的重点不是背诵 Pydantic API，而是理解一个真实 Python 项目如何把文档中的 contract、训练数据边界、可见性规则和测试验收转化成可执行的 schema 类。

重点：Pydantic v2 重点：schema 设计 重点：visibility 边界 重点：负向测试
学习总览 代码地图 Pydantic 核心 校验层次 Token 与 Mask 可见性边界 Protocol 与 Fake 测试规范 Python 语法 阅读方法

一、你在 Stage 1 最应该学什么

Stage 1 的代码主要是 schema 和测试，所以 Pydantic 的确是主线。但是更重要的能力是：你要学会如何用 schema、validator、类型标注和测试，把“这个系统允许什么、不允许什么”变成代码里稳定执行的边界。

1. Pydantic Schema

学会用类描述数据结构，用字段类型和 Field(...) 描述单字段约束，用 @model_validator 描述跨字段规则。

2. Contract 编程

Stage 1 不是普通业务功能，而是在把 shared contracts 固化为正式 Python 对象。代码的职责是“明确接受合法输入，明确拒绝非法输入”。

3. 可见性边界

学会区分模型可见内容、训练 batch 可传播字段、audit-only 证据和 evaluator-only 隐藏内容。这是 agentic RL 项目里非常关键的数据治理能力。

4. 批量规则

学会区分“一条样本自身是否合法”和“一个 PPO / GRPO batch 是否整体可训练”。这类层级区分是工程设计能力，不只是语法。

5. Fake Backend

学会先用 FakeLLMGateway 测试 runtime 形状，而不是一开始就依赖真实模型服务、Ray、vLLM 或 SGLang。

6. 负向测试

学会测试“不应该通过的输入是否真的失败”。对于 schema 边界，负向测试和正常 roundtrip 测试同样重要。

二、Stage 1 新增代码地图

读这部分代码时，不建议从第一行读到最后一行。更好的方式是先看每个文件负责哪一层边界，然后再进入具体类和校验函数。

episode.py
定义 episode 级输入和输出，例如 RepoHarnessEpisodeRequest、RepoHarnessEpisodeResult、EpisodeStatus、BudgetConsumption、reward / verifier / patch summary。它回答“这条 episode 怎么跑，以及跑完以后整体状态是什么”。
training_view.py
定义训练视图和审计引用，例如 TrainingView、ResponseSpan、AuditRef、validate_training_view_for_online_rl(...)、validate_formal_online_rl_batch(...)。它回答“哪些 token 进入训练，哪些 token 只作为观察，以及怎么回查 audit 证据”。
gateway.py
定义模型调用抽象，例如 LLMGatewayRequest、LLMGatewayResponse、GenerationRecord、LLMGateway protocol 和 FakeLLMGateway。它回答“RepoHarness 不直接依赖 verl，如何拿到一轮模型输出和 token 级事实”。
visibility.py
定义 route 枚举、provider route 默认训练无效、模型可见字段检查、batch extra fields allowlist、opaque ref 校验和工具访问审计 fixture。它回答“哪些内容禁止进入 prompt、batch 或模型工具可读路径”。
timing.py
定义 TimingSummary 和 ResourceSummary。Stage 1 先提供结构，后续 Stage 4 会加强完整性和解释率要求。

你可以把 Stage 1 理解为“给 Stage 2 到 Stage 12 准备共同语言”。后续 runtime、training_fast、converter、verl adapter 都应该消费这些 schema，而不是各自发明一套字段。

三、Pydantic v2 核心知识

1. Schema 类是什么

在这个项目里，schema 类不是普通“数据袋子”。它有三个作用：

  1. 定义对象有哪些字段。
  2. 定义字段是什么类型。
  3. 定义对象创建时必须满足哪些规则。
class EpisodeBudgets(StrictBaseModel):
    schema_version: str = "repo_harness_verl_episode_budgets_v0"
    max_turns: int | None = Field(default=None, gt=0)
    max_tool_calls: int | None = Field(default=None, ge=0)
    no_progress_policy: dict[str, Any] = Field(default_factory=dict)

这段代码表达了三个层次：

写法 含义 为什么重要
int | None 字段可以是整数，也可以为空。 有些预算可能暂时不设置，但一旦设置就必须是整数。
Field(gt=0) 字段值如果存在，必须大于 0。 max_turns=0 这种无意义配置会被拒绝。
default_factory=dict 每个对象创建自己的空字典。 避免多个对象共享同一个可变默认值。

2. 为什么使用 StrictBaseModel

Stage 1 schema 都继承 StrictBaseModel。这个项目里的含义是：schema 默认应该严格，不能悄悄接受未知字段。原因很简单，训练系统里一个多余字段可能不是“无害信息”，而可能是 hidden verifier、gold patch、reward metadata 或绝对路径泄漏。

对初学者来说，严格 schema 的价值是：如果调用方传错字段名，程序应该尽早报错，而不是默默忽略或把错误数据继续传到后续训练环节。

3. Literal 固定字符串枚举

GatewayRoute = Literal[
    "verl",
    "openai",
    "deepseek",
    "local_vllm",
    "local_sglang",
    "replay",
    "mock",
]

Literal 表示字段只能取这些值之一。它比普通 str 更安全，因为 "sglang"、"verl_llm_server_client" 这类未登记 route 会被拒绝。这样可以防止文档、fixture、adapter 各自使用不同名字。

4. @model_validator(mode="after") 做跨字段校验

单个字段的类型正确，不代表整个对象正确。比如 response_ids、response_mask 和 response_logprobs 各自都是列表，但长度必须对齐。 

@model_validator(mode="after")
def validate_training_view(self) -> "TrainingView":
    if len(self.response_ids) != len(self.response_mask):
        raise ValueError("response_ids and response_mask must have equal length")
    if self.response_logprobs is not None and len(self.response_logprobs) != len(self.response_ids):
        raise ValueError("response_logprobs must align with response_ids")
    return self

mode="after" 的意思是：Pydantic 已经把字段解析成对象属性之后，再运行这个函数。此时你可以访问 self.response_ids、self.response_mask 等多个字段，检查它们之间的关系。

5. model_validate 和 model_dump

Stage 1 测试里常见两个动作： 

view = TrainingView.model_validate(payload)
roundtrip_payload = view.model_dump(mode="json")
方法 作用
model_validate(...) 把普通 Python 字典解析成 Pydantic 对象，同时触发字段校验和 model validator。
model_dump(...) 把 Pydantic 对象转回普通字典，用于 JSON 保存、测试 roundtrip 或传给其他模块。

四、Stage 1 的四层校验模型

这部分代码最值得学习的不是某个 validator 怎么写，而是它把规则分成了不同层级。每一层只负责自己该负责的事情。

字段级校验

使用类型标注和 Field(...) 检查单个字段。例如 turn: int = Field(ge=0) 表示轮次不能是负数，prompt_length: int = Field(gt=0) 表示长度必须大于 0。

对象级校验

使用 @model_validator(mode="after") 检查同一个对象内部多个字段之间的关系。例如 LLMGatewayResponse 要求 output_token_ids 和 response_mask 等长，并且 gateway 层的 response_mask 必须全为 1。

可见性校验

使用 visibility.py 中的 helper 检查 forbidden marker、绝对路径、非 opaque ref、嵌套 evaluator-only 字段等。它不是某个单独对象的业务逻辑，而是整个训练边界的通用守门员。

Batch 级校验

使用 validate_formal_online_rl_batch(...) 检查一个正式 online RL batch 是否整体可训练。比如 mixed log probability 不是单条样本自己能判断的问题，必须放到 batch 层检查。

一个好的 schema 设计不是把所有规则都塞进一个类，而是让每条规则待在它应该待的层级。单样本规则放在单样本 schema，跨样本规则放在 batch helper，通用安全规则放在 visibility helper。

五、Token、Mask 和 Log Probability 的重点

RepoHarness 接入 verl 的训练视图中，最容易出错的地方是把“模型生成的 token”和“工具返回的 observation token”混在一起。Stage 1 的 schema 在提前固定这个边界。

prompt_ids 初始 system message、user task 和可见上下文。它是模型输入，不是 response loss 的目标。
assistant_generation 模型自己生成的 token，例如工具调用 JSON 或最终回答。response_mask=1。
tool_observation 工具返回内容编码成 token 后进入上下文。它不是模型生成内容，response_mask=0。
assistant_generation 后续模型基于工具观察继续生成。仍然是模型生成 token，response_mask=1。 
AgentLoopOutput.response_ids
  = assistant_round_1_token_ids
  + tool_observation_token_ids
  + assistant_round_2_token_ids

AgentLoopOutput.response_mask
  = [1] * len(assistant_round_1_token_ids)
  + [0] * len(tool_observation_token_ids)
  + [1] * len(assistant_round_2_token_ids)

为什么工具 observation 的 log probability 是 0.0

工具 observation token 不是模型生成的，所以没有真正的 rollout log probability。为了让 response_logprobs 和 response_ids 长度对齐，Stage 1 规定 response_mask=0 的位置可以填 0.0。后续 PPO loss 会乘以 response_mask，这些位置不会贡献 loss。 

for mask, logprob in zip(self.response_mask, self.response_logprobs):
    if mask == 0 and logprob != 0.0:
        raise ValueError("response_mask=0 tokens must use response_logprobs=0.0")

ResponseSpan 的作用

response_mask 只能告诉我们某个 token 训不训练，但不能告诉我们这个 token 来自哪里。ResponseSpan 用连续片段解释来源：

source_type mask 规则 含义
assistant_generation response_mask_value=1 模型生成 token，参与 policy loss。
tool_observation response_mask_value=0 工具返回内容，只作为后续上下文。
environment_observation response_mask_value=0 环境观察内容，只作为上下文。
padding_excluded / truncated_excluded 不设置 mask 值 解释为什么某些内容没有进入未 padding 的 response 序列。

六、可见性边界和 opaque reference

visibility.py 是 Stage 1 最值得认真读的文件之一。它展示了真实项目里如何防止敏感字段、隐藏评测信息和本地路径泄漏到训练路径。

1. 什么不能进入模型可见内容

模型可见内容包括 raw_prompt、messages、后续可能进入模型上下文的文本。下面这些内容不能出现：

  • hidden_verifier：隐藏验证器结果。
  • gold_patch：标准答案 patch。
  • accepted_label：最终是否通过的标签。
  • complete_reward_metadata：完整 reward 解释文本。
  • provider_secret：供应商密钥或凭据。
  • evaluator_only_logs：只属于评测器的日志。
def validate_no_forbidden_model_visible_content(value: Any, *, field_name: str) -> None:
    visible_text = _collect_text(value)
    for token in RAW_PROMPT_FORBIDDEN_TOKENS:
        if token in visible_text:
            raise VisibilityContractError(...)

2. 为什么检查 key，也检查 value

泄漏不一定只出现在 value 里，也可能出现在字段名里。例如： 

{
  "repo_harness_gold_patch": "some opaque looking value"
}

如果只检查字符串 value，就会漏掉这个问题。Stage 1 的 _collect_text(...) 和 _walk_key_values(...) 会同时递归检查 key 和 value。

3. 为什么使用 rh://... opaque reference

训练 batch 里可以携带短引用，但不能携带模型工具能直接读取的本地绝对路径。比如下面这个值就不应该进入 batch： 

/Users/roger/Desktop/claude-code-verl-stage0h/runs/some-run/reward.json

正确方向是使用 opaque reference： 

rh://audit/run_001/reward_metadata

这个引用可以被离线审计工具解析，但模型通过普通 read_file 或 grep 工具不能直接拿它当本地路径读取。

4. Batch extra fields 的设计规范

未来进入 AgentLoopOutput.extra_fields 或 verl DataProto.non_tensor_batch 的字段必须短小、扁平、命名空间明确。 

extra_fields = {
    "repo_harness_episode_id": "episode_001",
    "repo_harness_run_id": "run_001",
    "repo_harness_audit_manifest_ref": "rh://audit/run_001/manifest",
    "repo_harness_invalid_for_training": False,
}

这里有三个规范：

  1. 字段名必须以 repo_harness_ 开头。
  2. 字段值必须是扁平 scalar，也就是字符串、数字、布尔值或空值。
  3. 如果字段名以 _ref 结尾，字符串值必须是 rh://... opaque reference。

七、Protocol、async 和 FakeLLMGateway

Stage 1 的 LLMGateway 不是具体实现，而是一份接口协议。它告诉 runtime：“你可以调用一个拥有 generate_turn(...) 方法的对象，但不要关心它背后是 fake、provider、verl、vLLM 还是 SGLang。” 

@runtime_checkable
class LLMGateway(Protocol):
    async def generate_turn(self, request: LLMGatewayRequest) -> LLMGatewayResponse:
        """生成一轮 assistant 输出，并返回 token 级事实。"""

1. Protocol 的意义

Protocol 是 Python 的结构化接口。意思是：一个类不一定要显式继承 LLMGateway，只要它有兼容的 generate_turn(...) 方法，就可以被当作 LLMGateway 使用。

2. 为什么是 async 接口

verl 的 AgentLoopBase.run(...) 是异步函数，真实模型服务也通常是异步调用。Stage 1 先把接口设计成 async，可以避免 Stage 2 或 Stage 11 再返工接口形状。

3. FakeLLMGateway 学习重点

FakeLLMGateway 是测试用的确定性实现。它不调用真实模型，只返回预设或默认的 LLMGatewayResponse。这让 Stage 2 可以在没有真实 verl server 的情况下测试 runtime 主流程。 

gateway = FakeLLMGateway([
    {
        "route": "mock",
        "model_call_id": "call_001",
        "assistant_message": {"role": "assistant", "content": "done"},
        "prompt_ids": [1, 2, 3],
        "output_token_ids": [10, 11],
        "output_logprobs": [-0.1, -0.2],
        "response_mask": [1, 1],
    }
])

学项目时要特别注意 fake 的价值：fake 不是“假代码”，而是为了让核心流程先被稳定测试。真实外部系统越复杂，越应该先有 fake 或 mock 把接口形状测清楚。

八、测试规范：不仅测能过，还要测会拒绝

Stage 1 对你学习 Python 项目规范最有价值的一点，是它有很多负向测试。schema 代码的正确性不只是“合法样本能创建对象”，还包括“非法样本必须被拒绝”。

1. Fixture roundtrip 测试

roundtrip 的典型流程是：

  1. 读取 tests/fixtures/repo_harness_verl/*.json。
  2. 用正式 schema 做 model_validate(...)。
  3. 用 model_dump(...) 转回普通字典。
  4. 再次 validate，证明序列化和反序列化稳定。

这能证明 Stage 1 schema 没有绕过 Stage 0H fixture，也没有另起一套新样例。

2. 负向测试

负向测试通常使用 pytest.raises(...)： 

with pytest.raises(ValidationError, match="provider routes must default invalid_for_online_rl=true"):
    ProviderRoutePolicy(
        route="openai",
        invalid_for_online_rl=False,
        allowed_uses=["evaluation"],
    )

这个测试不是在证明 provider route 不能存在，而是在证明 provider route 默认不能伪装成正式 online PPO / GRPO rollout 样本。

3. 推荐你读测试时带着这几个问题

  • 这个测试是在证明合法输入能通过，还是非法输入会失败？
  • 这个失败是字段类型错误、跨字段关系错误，还是 visibility 泄漏？
  • 这个规则属于单条样本，还是属于整个 batch？
  • 测试复用了 canonical fixture，还是自己临时构造了一个最小负例？为什么这样选择？

九、你可以顺手学习的 Python 语法

from __future__ import annotations

让类型标注延迟求值。这样类方法返回自身类型时可以写 -> "TrainingView"，也能减少一些循环引用和运行时类型解析问题。

Any 的使用边界

dict[str, Any] 表示值暂时不限制类型。它应该只出现在确实开放的扩展字段，例如 provider_options 或 extra_fields。越核心的 schema 字段，越不应该滥用 Any。

deque

FakeLLMGateway 用 collections.deque 保存预设响应。popleft() 可以高效地从队列左侧取出下一条响应，适合模拟多轮模型调用。

集合运算

unknown_uses = set(self.allowed_uses) - OFFLINE_PROVIDER_ALLOWED_USES 表示找出用户传入但不在允许集合里的用途。这是 Python 中很常见的白名单检查写法。

递归遍历嵌套结构

_walk_key_values(...) 会递归遍历字典和列表，检查嵌套 key / value 是否包含 forbidden marker。真实项目里，安全检查通常不能只看第一层。

type alias

EpisodeStatus = Literal[...]、FlatScalar = str | int | float | bool | None 都是类型别名。它们能让复杂类型有一个清晰名字，也方便多处复用。

十、建议你的阅读和练习顺序

如果你想真正掌握这部分代码，不建议一开始就读完整文件。可以按下面顺序学习。

先读 TrainingView

它最直观，直接涉及 prompt_ids、response_ids、response_mask、response_logprobs 和 reward_score。先理解“什么 token 训练，什么 token 不训练”。

再读 ResponseSpan

它补充解释 token 来源。你要确认每个 span 的 mask 规则、区间规则和 global steps 范围规则。

接着读 visibility.py

重点理解 validate_no_forbidden_model_visible_content(...)、validate_batch_extra_fields(...)、validate_gateway_extra_fields(...) 和 validate_opaque_ref(...)。

然后读 LLMGatewayRequest 和 LLMGatewayResponse

这一步理解模型调用边界。尤其要记住：gateway 层只返回模型生成 token，所以它的 response_mask 必须全为 1。

最后读 RepoHarnessEpisodeRequest 和 RepoHarnessEpisodeResult

这两个对象更像 episode 总入口和总出口。读它们时要关注状态语义：succeeded 不等于任务成功，invalid_task 和 infrastructure_error 不能被当成模型失败样本训练。

练习建议

  1. 手写一个最小合法 TrainingView 字典，然后用 TrainingView.model_validate(...) 解析。
  2. 把其中一个工具 observation 的 log probability 从 0.0 改成 -0.5，观察报错。
  3. 在 extra_fields 里加入 "audit_ref": {...}，观察为什么会被拒绝。
  4. 创建两个 FormalOnlineRLSample，一个有 response_logprobs，一个没有，然后调用 validate_formal_online_rl_batch(...)。
  5. 用 FakeLLMGateway 构造两条响应，连续调用两次 generate_turn(...)，观察请求和响应如何被记录。

你学完这部分后，应该能做到三件事：看懂 Pydantic schema 类在检查什么；判断一个规则应该放在字段级、对象级还是 batch 级；理解为什么训练系统必须严格区分模型可见内容、工具观察、reward、audit 和 evaluator-only 信息。
