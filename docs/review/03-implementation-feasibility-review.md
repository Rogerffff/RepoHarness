# Implementation Feasibility Review

## 总体评价

本次审查只读取了 `docs`、`README.md` 和 `src/repo_harness`，没有修改任何文件。

整体判断：RepoHarness 当前文档已经具备“从方向进入工程设计”的基础，核心闭环、模块分层、第一阶段边界和训练导向都比较清楚。尤其是 `README.md` 和 `src/repo_harness/__init__.py` 明确说明当前没有实际运行功能，第一阶段只做设计和骨架，这一点执行得比较严格。

但是，从“后续工程实现者可以直接进入实现”的标准看，文档还没有完全达到可落地实现的精度。主要缺口集中在：缺少统一对象模型、缺少配置结构、缺少端到端数据流、缺少源代码目录和模块边界约定、缺少错误类型统一表，以及运行产物和事件结构还不够机器可执行。

## 主要问题

1. 接口和对象定义仍偏概念化。文档列出了 `Tool` 契约字段、任务字段、验证器输出和事件字段，但还没有形成统一的 `TaskDefinition`、`RunConfig`、`RunWorkspace`、`ToolCall`、`ToolResult`、`PermissionDecision`、`VerifierResult`、`TrajectoryEvent`、`ExportRecord` 对象清单。实现者需要自行推断对象字段，容易导致不同模块重复定义类似结构。

2. 命令行入口和配置字段不足。系统架构文档提到命令行与配置层负责读取任务列表、模型配置、运行参数、权限模式和输出目录，但没有给出配置文件示例和字段定义。建议补齐任务路径、模型提供方、模型名称、最大轮数、最大工具调用次数、执行模式、权限模式、输出目录、默认超时时间、并发数量、日志级别、截断长度、随机种子和是否保留工作区等字段。

3. 模块边界存在后续重复逻辑风险。当前 `Tool System` 负责工具执行，`Workspace / Sandbox Adapter` 也负责执行命令和保存差异。如果不明确“所有文件系统写入和进程执行最终必须经过工作区适配器”，后续 `bash`、`run_tests`、`apply_patch` 容易各自实现路径检查、超时、输出截断和差异捕获。

4. 验证器、测试工具和普通命令的关系需要明确。建议规定：`run_tests` 调用验证器的中间反馈路径；任务结束后再调用一次最终验收路径；两者共享测试配置、结果解析器和 `VerifierResult` 结构。

5. 事件结构对非工具事件不够友好。当前事件字段要求每条事件包含 `tool_name`、`tool_input`、`tool_output_preview` 等字段，但运行开始、模型调用、上下文截断、验证器完成、任务终止、导出完成都不是工具事件。建议改为“通用事件字段 + 按事件类型扩展字段”。

6. 错误处理和失败分类尚未统一。终止原因、验证器错误和失败诊断类型方向一致，但没有统一枚举、归属关系和转换规则。后续统计、导出和奖励计算会因此变得脆弱。

7. 运行产物约定有目录样例，但缺少文件内容契约。`task.yaml` 是原始任务还是规范化任务、`final.diff` 与 `final.patch` 的区别、完整工具输出保存在哪里、导出元数据文件如何命名、失败运行是否也必须产生完整产物，目前还没有明确。

8. 第一阶段边界执行严格，但“骨架”略偏空。如果目标是帮助后续实现者直接开工，可以在文档中补充未来目录树和每个模块的输入输出，而不是增加实际功能代码。

## 建议修改

1. 增加一篇“对象模型与数据流”文档，集中定义核心对象、字段、必填项、可选项、来源模块和消费模块。
2. 在系统架构文档中增加模块所有权表，明确每个模块负责什么、不负责什么、可以调用哪些下游模块、必须产出哪些事件。
3. 增加命令行和配置文件设计，给出完整 YAML 示例，并说明批量评测默认不使用需要人工确认的权限模式。
4. 在工具系统和工作区文档中明确：路径解析、符号链接处理、工作目录、环境变量、命令超时、进程中断、输出落盘、差异捕获统一由工作区或执行适配器负责。
5. 在验证器文档中补充 `run_tests` 中间反馈与最终验收验证器的关系，并规定任务结束后必须基于最终工作区重新运行验证器。
6. 将事件结构调整为分类型结构：运行事件、模型事件、工具事件、权限事件、验证器事件、上下文事件、终止事件、导出事件分别定义扩展字段。
7. 统一错误类型、终止原因和失败诊断类型，形成一张机器可读的分类表，并说明哪些错误允许模型重试，哪些错误直接终止运行。
8. 在运行产物文档中补充每个文件的内容契约、生成时机、失败场景下是否必须生成，以及训练导出如何引用原始运行目录。

## 必须保留的优点

1. 必须保留“工具结果必须回流到下一轮模型上下文”的不变量，这是多轮智能体利用环境反馈修复问题的核心。
2. 必须保留“训练奖励和离线评测共用同一套验证器”的原则，这是 RepoHarness 区别于普通代码智能体演示项目的关键价值。
3. 必须保留权限系统和执行边界的区分。当前文档没有夸大 Docker 执行模式的安全性，这一点非常重要。
4. 必须保留 transcript 和 events 分离的设计。前者适合对话重放，后者适合统计、诊断和训练导出。
5. 必须保留第一阶段范围克制：只做设计文档和 Python 包骨架，不提前实现运行循环、工具系统、沙箱执行器、验证器或强化学习集成。
6. 必须保留 scaffold 可替换的设计，让 single-shot patch、simple ReAct 和 planner-coder-verifier 能在同一任务、同一工具、同一验证器下比较效果。
